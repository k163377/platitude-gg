# check ハング調査で残った観察

負荷・天井でだけ出る赤は、待ちの組み方の規約違反として直す(.claude/rules/code.md・core.md §非同期・並行テスト・
app-ui.md §UI 自動化)。直らないまま残るものは、止まった段(`awaited` の行)と再現条件を添えてここへ足す。

- **次の手の候補は「数席の gate が並走し続ける」を平常として選ぶ**(要判断) —— 1 本の天井(600 s)はその gate のレーンを 10
  分塞ぎ、撃ち直しの分まで全席の待ちに乗る。全席に効く順:
  - **来ない前提は待たずに名前を付けて落とす** —— 動詞の多くは対象(行・worktree・タグ)を名前で引き、無ければ拍ごとに待ち
    直す(`if (row < 0) return`)。古い census の行や preset の取り違えでは両 OS とも 600 秒の天井まで待ち、負荷の天井と見
    分けがつかない(例: `middle-hand description --preset long`)。`PageSettled` の後にまだ無ければ `unmet=<何>` で即 FAIL
    にする
  - `cargo xtask waits` に「完了を持つのに sampler を持たないドライバ」を名指す検査を足す(今は当たるドライバが無い)—— 規
    約を静的な検査に落とし、機械を食わずに再発を止める
  - host のテストが起こす git の本数を減らす —— 起動の代金は全席で食い合うので、減らせば全席が速くなる。測ってから(モ
    ジュールごとの起動本数)、多いものを雛形の複製に替える(verify のデモリポジトリと同じ手)。製品の executor を通る git
    は 1 本ごとに `conhost.exe` も 1 本立てる(下の要判断)
  - **潜在(観測なし)**: verify の run のアプリは読みの時間制限 30 s(`DEFAULT_TIMEOUT`)のまま走る。最も重い同居では 1 コ
    ミットの `git log` が 27 s まで伸びた。`settings-tools` は同居下で棚卸しの 30 s を毎回払っている
  - **採らない**: 無進捗が N 秒続いたら打ち切る検知(常時負荷では正当な待ちも伸び、閾値が負荷に依存する)/ 赤いユニットの
    単独での撃ち直し(同居下では単独にならず、負荷を足すだけ)/ 予算の重み付けや OS の優先度 (他席を遅らせるだけで総量は変
    わらない)/ N 本並走の stress(P3-確認事項 §触らないと決めたもの)

- **`session_integration::diff_reads::a_click_stops_the_git_of_the_read_it_passes` が gate の負荷の下で赤**(記録のみ —
  ユーザー判断。観測は Linux の `test it (all) linux` で 1 回、全席の `gate-logs/failed` でもその 1 回だけ。単独
  (`linux test -p platitude-core --test it session_integration::diff_reads`)と撃ち直しの gate では緑)—— 先の読み込みの
  `git cat-file blob :0:src/a.rs` が、次のクリックの中断より先に exit 0 で走り切っ
  た(`the passed read's source was read`)。テストは最初の読みを `poll_once` で 1 度だけ進めて「自分の git の中で待ってい
  る」と見るが、その git が probe か `cat-file` かは縛っていない —— 負荷で probe が先に済むと、次の poll で `cat-file`
  まで進みうる形
- **頼まれていない fetch が撮影を跨ぐ run は、絵どうしの状態が食い違っても緑**(未対応。コードからの導出で、食い違った絵
  は未観測)—— タブを開いた時の fetch と間隔の fetch は、動詞の完了と無関係に落ち着く。`PageSettled.missing` に「頼まれて
  いない fetch が出ている」項は無く、完了と app.png が fetch の最中(帯の fetch ボタンに輪が出ている)、overlay.png /
  scene.png が落ち着いた後、という run が通る (`pictured … holds=` が比べるのは部品の型の集合だけ)。fetch の終わりに依る
  動詞は `repoTab.fetching` を自分で待っている(`AutoActPublishVerbs` / `WindowBandActs` / `AutoActFileRowVerbs`)
- **`diff-reread above --preset manyhunks` が gate の負荷の下で `same=false`**(未対応)—— 2026-11-10 の席 c の gate (他席
  の gate と同居、動詞 102 本が予算待ち)で 1 回。全席の gate 台帳では host の 229 run 中この 1 回だけ、単独の 8 本並走は
  8/8 緑、撃ち直しの gate も緑。2026-11-25 の席 b の段 2 の gate(host の 110 本が予算待ち、計 13 分)で 2 回目 —— 報告も
  形も同じで、書き込みから完了まで約 2.1 s、負荷の軽い直前の gate --related では 3 s で緑。報告は
  `diff_reread how=above kept=true same=false still=false` —— 手の下の行の delegate は同じ高さに立っているが、手を置いた
  時の行の字を出していない。完了は「書き込みの後に diff の model へ行が 1 回届いた」 (`rowsArrived` を数えた
  `reads > readsBefore`)で、その読みが書き込みの後に始まった物かは縛っていない。`Harness.writeFile` は `std::fs::write`
  (切り詰めてから書く)なので、書き込みと重なった読みが途中のファイルを読んだ形が候補(未検証)。その run の書き込みから完
  了までは約 2.5 s で、読み直しの始まりはログに出ていない(`diff request round trip` の行は開いた時の 1 本だけ)。同じ完了
  の形は `wip-reread`(`AutoActHoverGoneVerbs` の `unstagedReads > readsBefore`)も持つ
- **`menu-follow far-moved --preset others-behind` が gate の中で天井**(未対応)—— 2026-11-18 の席 e の段 1 の gate(他席
  の gate と同居)で 1 回。`awaited menu_follow_read waiting=followed,row for 597889ms`: 外から撃った
  `git update-ref refs/remotes/…` の後、`remotesModel` が動いた先を言わず、灰になる行も出ないまま —— 外の ref の変化を窓
  が読み直していない形。全席の gate 台帳ではこの行の 54 run 中この 1 回だけ、単独は 3/3 緑。読み直しが外の変化をどの経路
  で知るか(監視か間隔の読みか)は未読
- **動詞の行の増え方**(ユーザー決定: 反映前テストの機械化.md §段ごとに何を回すか)。未着手の案: 読むだけの動詞を 1 起動で
  複数走らせる(run ごとの独立 = ハーネスの契約を変える)
- **動詞の判定の穴**(未対応):
  - **判定行が待つ条件そのもので、壊れても名前付きで落ちない**(壊れると 600 秒の天井まで行く): `window_floor fits=` /
    `window_fill fills=` / `pane-bar` / `text-bar` の ink / `graph-head-go` / `details-failure` /
    `signature-tip`・`stash-tip` の `tip=true` / `graph-tail` の `truncated=true` / `diff_row act= ready=true`(行が届い
    た時点で出る — `diff-file`・ `line-tools`・`stage-hunk`・`stage-line`・`discard-hunk-go`)/ `rename-tag-box` の
    `box=true`
  - **どちらの側を取ったかを見ていない**: `take-side-ours` / `take-side-theirs` は完了が「行が conflicts を出た」なの
    で、 ours と theirs を入れ替えても緑
  - **対の片方が census に無い**(判定表には行が在る): `remote-menu origin:marked` / `remote-url origin:marked` /
    `nav-add-remote folded`・`--preset noremote` / `find-drop`(空の問い合わせの側)/ `stash-state` の
    ready・clean・conflicts / `switch-stopped main`(rebase の離脱の質問)/ `settings-repo <引数>` /
    `switch-lands feature/topic-a:2` / `rename-local-upstream :replace`・`:leave` / `settings-eol input`・`inherited`
  - **判定の値を動詞が自分で書いている**: `reset-soft` / `reset-mixed` の `mode=`(ドライバのラベル。本当の差の `files=`
    は判定に無い)、`edit-message-focus` の `focused=`、`pull-ahead` の `log=true`
  - **ドライバが実入力を迂回する**: 左メニューの `delete-branch` 系は `page.deleteRow` を、`stage-hunk` は
    `page.stageSelection` を、`move-branch` は `switchTo('force')` を直に呼ぶ
  - **QML の TypeError では run が落ちない**(`verify::outcome::Outcome::passed` は QML の TypeError を見ない)。判定行の
    無い動詞は、経路の途中で関数が消えても絵が変わるだけで緑になる(例: `settings-git` の開く道)
  - **判定行の無い動詞が、その行だけが通る分岐を持つ**(反映前に回しても「止まらない」ことしか言えない):
    `diff-keep-folded` (手で畳んだ上で diff を開く `foldForDiff` の早期 return — `nav_rail collapsed=true diff=false` を
    判定すれば証人になる)/ `diff-split src/steps.rs --preset coloured`(色が 2 列の行へ塗り直される
    `repaint_rows split=true`。色が届くのと 2 列への切り替えの前後は時機で決まる)
- **git 1 本ごとの `conhost.exe`**(要判断 — 製品の git の起こし方を変える): 製品の executor は git を `CREATE_NO_WINDOW`
  で起こすので、git 1 本ごとに隠れ console の `conhost.exe` が 1 本立つ。**動詞 1 run の代金の大半がこれ**(gate-load
  §git の console と QML のキャッシュの代金)。console 無し(`DETACHED_PROCESS`)は採れない (`process::family` の
  `win32::CREATE_NO_WINDOW` のコメント)。**意味を保ったまま払わない形**は、アプリが起動時に隠れ console を 1 つ持
  ち(`CREATE_NO_WINDOW` で起こした子の console へ `AttachConsole`)、 git をフラグ無しで起こしてそれを継がせる形 —— 子も
  孫も今と同じ隠れ console に居て、conhost はアプリに 1 本。 Win32 の console API を app に入れる(FFI)ことと、Qt のロ
  グ・console の制御イベントへの影響を測ることが要る。テスト(cargo test)は親の console を継げばよいので、executor が「自
  分に console が在れば継がせる」だけでも host の `test it` は払わずに済む
- **動詞 1 run の残りの代金**(実装できる、未着手): host の fixture は雛形のコピー(gate-load §動詞 1 run の中身)で、雛形
  を組む時に loose object を pack し git の見本フック `*.sample` を置かなければ作る entry が 6 割減る。
  **ハードリンクは効かない** —— run の木は 1 日残るので、よく使う雛形の object は NTFS の 1 ファイル 1,023 リンクを数
  gate で使い切る / Linux の launcher(verb ごとのエンジンの `exec`)は、コンテナの中に常駐する runner に verb を流せば消
  える
- **host の `pgg-demo` に残る run の木**: gate 1 本ごとに `test xtask` が preset のコピーを残し (`demo::template::tests`
  の `crate::demo::create` に guard が無い)、`basic` のコピーも返されずに残る(`ownership::give_back_claimed` は「誰も
  走っていない」時だけ返す)。壁時計には乗らない (Defender は CPU の律速でない)ので、翌日の sweep に任せている。コメント
  だけの変更でも全 preset を組み直すのは設計どおり(`demo::template` の `fingerprint`)
- **host の `test gate (all)` と重なった間、host の動詞が伸びる**(sandbox の gate をプロセスを起こし続けながら回すため。
  倍率とステップ自身の所要は gate-load §反映前の gate 1 本)。`tab-*` の動詞 (単独で 4〜7s)はこの窓で 83〜163s になっ
  た。**そのステップ自身の所要は同じ木で揺れ**、他の gate が居ない窓の方が長い回もある — 揺れの原因は未読

- **`start_again`(git 実行ファイル変更の再起動)を機械に持たせるか**(採否待ち)—— Qt 破棄の後ろに在るが動詞が無く、通した
  のは実窓の 1 回だけ(P5-確認事項 §実測済み)。推奨は `settings-git-path other` の回数押しを通す変種を足し、親の半
  分(`want_restart` の配線・lock が spawn より先に落ちること・trail が `qt-tearing-down > exiting`・「a driven run does
  not start one」)を機械に持たせる形。後継が立つ半分はハーネスが設計上拒む
- **dump を full のままにするか**(数百 MB が本体 checkout の `target\tmp\pgg-verify\<run>` に残る。stack だけなら 1 MB
  級)—— 推奨は full のまま**本数の天井**(pgg-verify 配下に `app.dmp` が 2 本立っていたらそう言って終わる)。製品は dump
  を書かず、撮るのは天井で刈った run だけで 1 日で掃かれる。**残る穴は teardown を壊した木で全動詞が `exiting` で詰まる
  回**

- **環境失敗が静寂に化ける待ちは、頼んでいない catch-up の側に残る**(健全環境では起きない): `set_auto_fetch` が撃つ
  fire-and-forget は設計どおり上へ何も報せないので、その run の失敗を名指すのは `Patience` が吐くイベント一覧の中の
  `ls-remote` の行だけ

## 次の 1 回で何が読めるか

天井で刈られた run の読み方(`the stations it reached:` / `it got as far as` / `wedge.txt` / アプリ側 watchdog の
`awaited` / `frames` / `page` / `wedge-check` の 4 つの形)は verify-ui スキル §壊れない動詞の実装と反復、
`out of time in` は `crates/platitude-app/src/harness/deadline.rs`(モジュールコメントと `account` が組む文)。ここに在る
のは exit の中の停止を読む分だけ。

- **`threads at the ceiling:` と `a dump of the app:`** — 刈る直前のスレッド一覧と、 Windows の full dump(shot dir の
  `app.dmp`)。`exiting` で終わる trail に **alive 1 本**が並べば `ExitProcess` の中(他スレッドは終了済み = DLL detach の
  区間)で、`the main thread stands in:`(Windows のみ)と dump の `~*k` がその 1 本の stack = 止まっている DLL と関数を名
  指す(frame の **module は正確・関数名は最寄りの export なので近所の名前**、exe は PDB が無いので `+offset` 止ま
  り)。**alive が複数**なら exit の手前で、名前(Linux)/ 名前と開始モジュール(Windows =
  `<id> <state> <wait> <名前>@<module> cpu=`)が誰を待っているかを言う (全スレッドの stack は `threads.txt` の
  `stack <tid> …` 行)。 **`exiting` の平常の顔**: `main@platitude-gg.exe` + `-@ntdll.dll` × 6(スレッドプールの待
  機、EventPairLow)+ `-@WINMM.dll` × 1 (タイマー)。Qt / tokio / deadline のスレッドは無い。ここに `QSGRenderThread` /
  `tokio-rt-worker` / `QQmlThread` が並んだら teardown の生き残りで、それが次の読み所。注文した停止(`--fault-hang`)では
  dump を撮らない。 `could not be listed — the listing ran out of time after Ns and was ended` /
  `no dump: the dumper ran out of time` は「診断が止まった」の意味で、アプリの回収と報告はその後も進む。
  `could not be ended` と pid が付く行だけは診断プロセスが残っている可能性を言う。dump の撮り方(`rundll32 comsvcs.dll`
  を使わない理由)は `verify::look::DUMP_SCRIPT` のコメント
- **`> qt-tearing-down ` の駅** — `hub-down` と `exiting` の間で `QApp` を落とす区間。ここで止まる trail は Qt の破
  棄(engine / application の destructor)の中で、`exiting` で止まる trail とは別の答え
