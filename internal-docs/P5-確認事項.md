# Phase 5(配布準備)確認事項

配布準備期に検証・判断する項目を先行して積む場所。
P3 分は [P3-確認事項.md](P3-確認事項.md)。

## 積み(未検証)

### 1. diff プレビューの画像デコーダ範囲

プレビュー(`platitude-core::preview`)が画像扱いする拡張子のうち、実際に
描画できるかは実行環境の Qt imageformats プラグイン次第。デコーダが無い
形式は「Preview unavailable」+ サイズ表示に劣化する(壊れない)。
開発環境の Qt には qgif / qico / qjpeg / qsvg のみ同梱で、png / bmp は
Qt 本体組み込み。**webp / tif / tiff / avif は劣化表示**。

検証・判断:

- **qtimageformats を配布物に同梱するか(本命)**。webp / tiff の
  プラグイン DLL を置くだけで、アプリ側のコード変更なしに描画可能になる。
  サイズは数百 KB 級。ライセンス確認(libwebp = BSD-3 / libtiff = MIT 系)と
  3OS の deploy 手順(windeployqt / macdeployqt / Ubuntu tar.gz)への
  追加が必要
- **avif**: Qt 標準プラグインが無い。候補は
  (a) 劣化表示のまま、
  (b) kimageformats 系プラグインの同梱(LGPL — 依存ライセンス方針の確認要)、
  (c) Rust 側デコードして PNG に変換(依存が大きく軽量方針と要相談)
- **WebView(Qt WebEngine)フォールバックは非推奨の見込み**。
  Windows の Qt WebView は実体が WebEngine(Chromium 同梱)。data URL を
  渡せば webp / avif も描けるが、配布 +150MB 級・別プロセスのメモリ・
  Chromium のネットワークスタック同梱で、軽量目標 / メモリ予算 300MB /
  「ネットワーク非通信」の主張([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
  に同時に抵触する。採用するならこれら全部の再検討が前提

### 2. forge との距離(`gh` を呼ぶか) — **かなり後の判断**

PR バッジの実データ(P4)とリモートブランチの改名・削除まわりで、
「`gh` CLI があれば済む」場面が出る。判断はずっと後で構わないが、決めるまでは
**呼ばない**。

- 絶対制約は「ネットワーク通信は git コマンド経由のみ」「forge API のクレートを
  入れない」。`gh` は**クレートではなく外部 CLI** なので条文には触れないが、
  **アプリが forge へ通信させることに変わりはない**ので、制約の趣旨としては同じ側
- 判断するなら同時に決めること: 未インストール環境での degrade(バッジが出ないだけ)/
  認証(`gh auth` に委譲。アプリはトークンを受け取らない)/ オフライン job での扱い /
  「ネットワーク非通信」の主張([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
  の書き換え
- 当面の代替: PR バッジは `ls-remote refs/pull`(git 経由)で足りる見込み。
  リモートブランチの改名・削除は git だけで済んでいる(push の合成と `push --delete` —
  デザイン規約 §リモートブランチの改名 / §リモートブランチを消す)。残る判断は
  「forge の rename(PR が付いてくる)まで要るか」だけ

### 3. 配布物への同梱一覧(既知分の集約)

- `pg-todo-editor.exe` を本体と同じディレクトリへ(rules-refs/core.md の pg-todo-editor 項。
  無いと interactive rebase だけが動かない)。**これは `platitude-core` の bin ターゲット**
  (`src/bin/pg-todo-editor.rs`)なので、`cargo build --release -p platitude-app` では
  **作られない**。素の Ubuntu で `target/release` を覗いて不在に気付いた(実測)—
  配布物を組む手順は必ずワークスペース全体をビルドする
- **Qt6Network は Qt6Qml のロード時依存として同梱が必須**。したがって非通信の主張は
  「同梱しない」ではなく「**アプリ自身の import table に通信系なし + ネットワーク系
  プラグイン除外**」で立てる(実測 [ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
- imageformats プラグインの選定(上記 §1 の結論)

### 3.5 CI を軽量と完全性に割る(CLAUDE.md の段 2 / 段 3)

**CI は 1 本ではなく 2 本**にする。分ける理由は費用ではなく**鳴る頻度**で、滅多に
答えの変わらない検査を毎回の反映に混ぜると、赤が出た時に「また例のやつ」と読まれる。

- **軽量 CI(段 2)= 反映のたび**: 3OS の fmt / clippy / test、Linux の
  `cargo xtask linux verify-ui`(触った動詞)、**`cargo xtask linux bare`**。
  bare がここに居てよいのは、**宣言済みの依存だけを入れたイメージに対して起動
  するかを見るだけ**だから — ネットワークも要らず、答えは起動するかしないかの
  2 値で、鳴る時は必ず「配布物に何を足すか」の話になる
- **完全性 CI(段 3)= リリース前と、依存・環境・Qt を触った時**: 上の全部に加えて
  **`cargo xtask linux bare --discover`**(依存リストを素の Ubuntu から導出し直す)、
  完全オフライン job、3OS のスクショ目視、性能実測

**`--discover` を軽量側に入れない** — apt を何度も叩き、ネットワークに依存し、
答えは普段まったく変わらない。**逆に、依存を触った PR では必ず段 3 を回す**
(`Cargo.toml` / `ci/linux/Dockerfile` / QML の import が変わった時)。

### 4. CI のフォント整備(スクショに日本語を出す)

CI は未整備のため、整備時にジョブへ折り込む(2026-08-08 決定)。判定基準は
demo `basic` の日本語コミット(`docs: 利用案内の骨子を日本語で直す`)が
3OS の PNG で**日本語字形**(直 / 骨 が中国語字形でない)で写ること。

- **ubuntu job**: `fonts-noto-cjk`(+ `fonts-dejavu-core`)を明示インストール —
  ランナーイメージの偶然に依存しない。あわせて「Ubuntu デスクトップは
  fonts-noto-cjk 標準搭載」というチェーンの前提を `fc-list` で実証する
- **windows job**: offscreen の FONTDIR は .ttc を読まない(verify-ui スキル)ため、
  Windows 標準の日本語フォントは全て使えない。**TTF の日本語フォント
  (例: Noto Sans JP)を CI 環境の FONTDIR に用意する** — CI 環境の話であり、
  利用者の環境には何も入れない
- **macos job**: offscreen でも CoreText のフォント DB なので追加不要の見込み。
  Hiragino Sans が写ることの確認のみ

### 5. 非 JP ロケール機での等幅フォールバック実測

等幅(diff 本文・コマンドログ)内の日本語だけは named family が和文を持たず
(Windows / macOS。デザイン規約 §タイポグラフィ)、OS のロケール依存フォールバックに
残っている。JP ロケール機では JP 字形になるが、**非 JP ロケールの Windows / macOS の
実ウィンドウでどの字形になるかは未実測**(offscreen では測れない — フォント DB が違う)。

- EN ロケールの VM で実ウィンドウ起動し、日本語入り diff の字形を目視する
- 中国語字形が出るなら対策を判断: JP 等幅サブセットの exe 埋め込み
  (qrc + `FontLoader`。**利用者環境にインストールはしない**)が第一候補。
  フォントのライセンスは OFL 系が主で、現行の依存ライセンス方針(MIT / Apache 系)の
  対象外につき人間の承認が要る

### 7. 引いたフラグのダッシュが他 OS の等幅で釣り合うか

`push -f` のダッシュはトークン長の罫で引いてある(規約 §git 用語のコード表記)。
**罫の長さは固定で、周りの字幅は OS が解決した等幅 family 次第**なので、
字が広い family では短く、狭ければ長く見えうる。実測できているのは
Cascadia Mono(Windows)だけ。

- macOS(Menlo)/ Ubuntu(DejaVu Sans Mono / Noto Sans Mono)の実機で
  `push -f` と、その後ろに立つ `!` の間合いを目視する
- ズレていた場合、罫の長さを family で分岐させない —— 分岐は 3 OS ぶんの
  微調整を抱えることになる。トークン 1 つで釣り合う長さを選び直す

### 8. アプリアイコンの mac / Linux 側

**焼くところまでは 3 OS ぶん済んでいる。動いているのは Windows だけ**で、
mac / Linux は資産と定義が置いてあるだけ(実機が無いので繋いでも走らせられない)。

| OS | 置き場所 | 中身 |
|---|---|---|
| 共通 | `crates/platitude-app/assets/icon-<n>.png` | 16 / 20 / 24 / 32 / 48 / 64 / 128 / 256 / 512 / 1024。**16 と 20 だけ小サイズ版から**、残りはマスターから(規約 §アプリアイコン の 24px 境界) |
| Windows | 同 `platitude.ico` + `.rc` / `.res` + `build.rs` | exe のリソース(絵と**表示名**の両方。§11)。窓の側は `src/winframe.rs` |
| macOS | 同 `platitude.icns` | 10 スロット(`icp4` / `ic11` / `icp5` / `ic12` / `ic07` / `ic13` / `ic08` / `ic14` / `ic09` / `ic10` = 1x と 2x の両方) |
| macOS | `packaging/macos/Info.plist` | バンドル定義。**`@VERSION@` / `@BUNDLE_ID@` が未置換なので、このままでは妥当な plist ではない** |
| Linux | `packaging/linux/platitude-gg.desktop` | hicolor への install コマンドはファイル内のコメント |

**ラスタライズ手段は (a) を採った**: 生成物をコミットして依存ゼロを保ち、焼き直しは
手作業とする(手順は `platitude.rc` のコメントと
[.claude/rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md))。(b) の `cargo xtask` +
SVG レンダラは、色を直す頻度が上がったら再考する。**大きいサイズを焼く時の罠**:
128px 以上をブラウザのヘッドレスで撮る場合、`--window-size` にそのまま渡すと最小
ウィンドウ幅にクランプされて図の一部しか写らない。広いビューポートで描いて左上を
切り出す。

残るのは**実機と、決めていない 2 つ**。

- **bundle identifier が未定**(`@BUNDLE_ID@`)。逆 DNS で、**署名と quarantine の
  記録がこれを鍵にする**ので、notarize より前に確定させる。リモートが決まっていない
  ため今は置いていない
- **バンドルを組む手続きの置き場所**。`Info.plist` の 2 つの置換と `Contents/` の
  構築(`MacOS/platitude-gg` + `Resources/platitude.icns`)で、`cargo xtask` が候補
  (CLAUDE.md: タスクランナーは xtask)。mac 実機が無い間は書いても走らせられない
- **macOS の外形**: Big Sur 以降の Dock はアイコンが角丸正方形に揃うため、規約の
  角丸タイルはそのまま使えるはず。ただし Apple は 1024 の canvas に対して実描画領域を
  一回り小さく取る慣習があり、そのまま焼くと**隣のアイコンより大きく見える**。実機で
  Dock に並べて確認する
- **Linux の実機確認**: `.desktop` の `StartupWMClass` が実際の WM_CLASS と一致するか
  — ズレるとランチャに**アイコンの無い 2 つ目のエントリ**が出る。両方ともスラグに
  揃えてあるが(Qt の `application_name` = 主張の根拠)、X11 と Wayland の両方で見る

### 9. 大きすぎるアバターを与えた時

**取り込み時に縮める形で仕様は確定済み**(正本は [デザイン規約.md](デザイン規約.md)
§アバターを与える と [.claude/rules-refs/core.md](../.claude/rules-refs/core.md) の picture 項 / 実測は
[ci/baseline/avatar-shrink-windows-x64.md](../ci/baseline/avatar-shrink-windows-x64.md))。
**縮小前の fps は測らないと決めた** —— 答えがどちらでも判断が動かないため。
P5 に残るのは実機だけ:

- **実 4K モニタの実窓**で顔が期待どおりの解像度に見えるか。`Canvas` が device 解像度で
  ラスタライズすることは offscreen で確認済み(保存辺 256 はそれを前提に選んだ)なので、

- **Canvas の図形が非アンチエイリアスで焼かれている**のが offscreen 経路だけの性質か、

### 10. 窓の縁に残っている 2 つ(Windows)

タブ行が OS のタイトルバーを兼ねる形(規約 §ウィンドウの縁。実装は
`ExpandedClientAreaHint` による frameless = 窓 = クライアント — rules-refs/app-ui.md)に残る
**機能の欠け**。白い 1px は frameless 化で非クライアント領域ごと消えて**解決済み**
(過渡期の `WM_NCPAINT` 塗りも撤去済み。「窓自身のビットか DWM の合成か」を
`PrintWindow` で分ける実測の作法は rules-refs/app-ui.md)。

| 残っているもの | いま何が起きているか |
|---|---|
| 窓メニューの `移動` / `サイズ変更` | 出るが効かない。この 2 つは**窓に caption があるかを先に見る**が、`WS_CAPTION` は戻せない — 戻すと OS が帯の上に caption を描き直す(rules-refs/app-ui.md) |
| Snap Layouts | 最大化ボタンの矩形を `HTMAXBUTTON` で答える必要がある。hit-test のサブクラス自体は**もう在る**(`winframe::hit_test` — `WM_NCHITTEST` は全点アプリが答えている)ので、残る作業は `HTMAXBUTTON` にすると**非クライアント化する押下・hover をボタンに映す側**(`WM_NCLBUTTONDOWN/UP` の自前処理と hover 表現) |

判断:

- 窓メニューは、OS のものを出すのをやめて**自前のメニューにする**道もある
  (`AppMenu` で描き、行から `WM_SYSCOMMAND` を撃つ)。`移動` / `サイズ変更` は
  そのままでは撃てないので、出す行を絞るか諦めるかの判断が要る。メニューを
  **出すこと自体**は済んでいる(サブクラスの `WM_NCRBUTTONUP` → OS のメニュー)—
  ここで言うのは中身の 2 行が効かない方
- どちらも Windows だけの話であることも込みで優先度を決める

### 11. 配布ビルドが名乗るバージョン

**表示名は片付いた**(`assets/platitude.rc` の `VERSIONINFO` / `FileDescription` =
`Platitude GG`)。残るのは版番号だけ。

以前ここに「やってみて未解決」と書いてあったのは**測る道具の方が壊れていた**:
`FileVersionInfo`(= PowerShell の `Get-Item .VersionInfo`)は、この形のリソースの
**文字列フィールドを全部空で返す**。固定ブロックは読めている(非ゼロの
`FILEVERSION` を焼いた探りで `FileVersionRaw` だけが 1.2.3.4 になった)ので、
欠けているのは文字列の側だけ。**同じバイト列から Win32 の `VerQueryValue` は 4 つ
全部を返し**、シェルの 2 つの読み手 —— `AssocQueryString` /
`ASSOCSTR_FRIENDLYAPPNAME`(ジャンプリストが名前を引く経路そのもの)と
エクスプローラの「ファイルの説明」列 —— はどちらも `Platitude GG` を答える。
**この 2 つで読む**、が結論(罠は `platitude.rc` のコメントにも置いた)。

版番号は**どこにも書いていない**。Cargo.toml が正本で、`Info.plist` は
`@VERSION@` のプレースホルダを置いて配布手続きに埋めさせる形だが、`.rc` は
**焼いた `.res` をコミットしてリンクする**ので同じ手が使えず、今は固定ブロックが
0.0.0.0(= `FILEVERSION` を書かない時に `rc.exe` が書く値そのもの)。

- 配布物の版表記を決める時に、**Windows の `.res` と mac の `Info.plist` を同じ 1
  か所から埋める**(`cargo xtask` が候補 —— §8 のバンドル手続きと同じ置き場所)
- 埋めるまでは `FileVersion` / `ProductVersion` の**文字列を足さない**。版を 2 か所
  に書くと必ずずれる(CLAUDE.md 規約の運用)

### 12. 2 つ目のプロセスを実機で押した時

ヘッドレスで確かめたのは「ロックが取れなければゲートを出し、ファイルには
一切触らない」まで(`cargo xtask verify-ui solo` = Windows / Ubuntu 両方 PASS)。
実機でしか見えないのは 3 つ:

- **ジャンプリストの起動エントリ**(`Platitude GG` と名乗るようになった、あの行)を
  押した時の見え方 — ゲートの窓がどう出るか、`Close` で素直に閉じるか
- **mac の `.app`**: Finder / Dock からの 2 回目は OS 自身が既存プロセスを起こす
  ので、ここへ来るのは CLI から直に叩いた時だけ。その時の見え方
- **リダイレクトされた `%APPDATA%` / ネットワークホーム**。ロックを訊けなかった
  側(`Claim::Unknown`)は**そのまま起動する**設計なので、転んでも「2 つ立つ」=
  この機能が入る前に戻るだけだが、実際にそう転ぶかは踏んでみないと判らない

### 13. 遅い置き場所でフォルダを選んだ時の無反応

ピッカーが受理してからタブが出る(または開けなかったと出る)までの間、画面は
何も言わない。手元の実測では **30〜36ms**(Windows warm・非リポジトリ / bare /
8 階層下の walk-up のいずれも 3 回ずつ)なので 1〜2 フレームで済み、待ちの意匠を
持たないと決めた(規約 §リポジトリを開く)。

**測れていないのは応答しない共有ドライブ・スピンダウンしたディスク**で、そこでは
`repo::open` のタイムアウト(10 秒)まで無反応になりうる。実機で測り、必要なら
「N ms 超えたらリングを出す」の N をトークンとして足す(**閾値の新設は人間の承認が
要る** — 今ある `tipDelayMs` / `hoverKeepMs` はどちらも hover の語彙なので流用しない)。
なお `path.is_dir()` が先に false を返す経路は多くが `plain` に落ちるため、この窓に
入るのは「ディレクトリとしては見えるが git が answer を返せない」場合だけ。

## 実測済み

### Linux: 素の Ubuntu が実際に要求するもの(2026-08-09 実測)

ツールチェーンも Qt も持たない `ubuntu:24.04` に、**ビルド済みバイナリと Qt の
ツリーだけ**を置いて起動するまでを 1 パッケージずつ足して測った。ここまでの Linux
検証は全て**ビルドした環境の中**での話で、「建てた場所で動く」までしか言えていな
かった。

**バイナリ自身が動的リンクするのは 9 件だけ** — `libQt6Core` / `libQt6Gui` /
`libQt6Qml`(同梱が要る)と、素の Ubuntu に最初からある `libc` / `libgcc_s` /
`libm` / `libstdc++`。**それ以外の未解決はゼロ**で、glib も GL も fontconfig も
**アプリの依存ではなく Qt の依存**だった。

**ローダが実際に止まった順**(止まった物だけを足していく形で確定):

| 止まった先 | 足したパッケージ |
|---|---|
| `libglib-2.0.so.0` | `libglib2.0-0t64` |
| `libEGL.so.1` | `libegl1` |
| `libfontconfig.so.1` | `libfontconfig1` |
| `libxkbcommon.so.0` | `libxkbcommon0` |
| `libgssapi_krb5.so.2` | `libgssapi-krb5-2`(Qt6Network 経由。git を入れると依存で付いてくる) |

これに **git 本体**(製品の前提)を足した状態で**起動し、offscreen でスクリーン
ショットまで到達した**。`libgl1-mesa-dri`(llvmpipe)は**要らなかった** — 開発
イメージに入れてあるが、offscreen で起動するだけなら無くても立つ。

**QML モジュールは `ldd` に映らない** — `Quick` / `QuickControls2` は実行時に
dlopen されるので、`ldd` の結果だけを見て同梱物を決めると**起動してから QML の
ロードで落ちる**。`QML_IMPORT_PATH` / `QT_PLUGIN_PATH` を Qt のツリーへ向ける必要
がある。

**日本語は素の Ubuntu では豆腐になる** — `fc-match 'Noto Sans CJK JP'` も
`fc-match sans:lang=ja` も **DejaVu Sans** に落ちる(CJK グリフを持たない)。
デザイン規約のチェーンが Ubuntu 側に名指ししている `Noto Sans CJK JP` は
**標準では入っていない**ので、パッケージが `fonts-noto-cjk` を依存に持つ必要が
ある(§4 の CI 整備と同じ前提を、利用者側にも立てる話)。
