# Phase 5(配布準備)確認事項

## 積み(未検証)

### 1. diff プレビューの画像デコーダ範囲

プレビュー(`platitude-core::preview`)が画像扱いする拡張子のうち描画できるかは
実行環境の Qt imageformats プラグイン次第。デコーダが無い形式は
「Preview unavailable」+ サイズ表示に劣化する(壊れない)。
**webp / tif / tiff / avif は劣化表示**。

検証・判断:

- **qtimageformats を配布物に同梱するか(本命)**。プラグイン DLL を置くだけで
  コード変更なしに描画可能。ライセンス確認(libwebp = BSD-3 /
  libtiff = MIT 系)と 3OS の deploy 手順への追加が必要
- **avif**: Qt 標準プラグインが無い。(a) 劣化表示のまま /(b) kimageformats 系の同梱
  (LGPL — 依存ライセンス方針の確認要)/(c) Rust 側デコードして PNG に変換
  (依存が大きく軽量方針と要相談)
- **WebView(Qt WebEngine)フォールバックは非推奨の見込み** — 実体は Chromium 同梱で、
  ネットワークスタック同梱が「ネットワーク非通信」の主張
  ([実装計画.md](実装計画.md) §11)に抵触する

### 2. forge との距離(`gh` を呼ぶか) — **かなり後の判断**

PR バッジの実データ(P4)とリモートブランチの差し替え・削除まわりで「`gh` CLI があれば
済む」場面が出る。決まるまでは git だけ。

- `gh` は外部 CLI なので絶対制約の条文には触れないが、アプリが
  forge へ通信させる点で制約の趣旨としては同じ側
- 判断時に同時に決めること: 未インストール環境での degrade(バッジが出ないだけ)/
  認証(`gh auth` に委譲)/
  「ネットワーク非通信」の主張([実装計画.md](実装計画.md) §11)の書き換え
- 当面の代替: PR バッジは `ls-remote refs/pull`(git 経由)で足りる見込み。残る判断は
  「forge の rename(PR が付いてくる = 本物の改名)まで要るか」だけ

### 3. 配布物への同梱一覧(既知分の集約)

**表示の置き場は About**(ユーザー案 2026-10-05)。LGPL-3.0 は、実行中に著作権表示を出すならそこに Qt /
qtbridge の表示とライセンス本文への案内を含めることを求める(§4(c))ので About が合う。GPL と LGPL の本文は
binary と一緒にファイルでも渡す(§4(b))— About はそのファイルを読んで見せる。中身(crate・Qt とその第三者部品・
tree-sitter の文法・構文定義)は依存を上げるたびに変わるので、`cargo xtask` で生成して CI で照合する。
qtbridge の上流の修正で `vendor/qtbridge-interfaces` を消しても、消えるのは改変版のソースと改変告知を
示す 1 項だけ(LGPL の表示と再リンクの道は残る)。

- `pgg-todo-editor.exe` を本体と同じディレクトリへ(rules-refs/core.md の pgg-todo-editor
  項)。**これは `platitude-core` の bin ターゲット**なので `cargo build --release -p platitude-app`
  では作られない — 配布物を組む手順は必ずワークスペース全体をビルドする
- **既定ビルドの Qt では Qt6Network は Qt6Qml / Qt6Quick のロード時依存として同梱が必須**(外せるのは Qt の
  カスタムビルドだけ —— 非通信の証明の前提。[実装計画.md](実装計画.md) §11.2)
- **mac の bundle に入れる Qt は `crates/xtask/src/package/contents.rs` の許可リストが正本**(ユーザー決定
  2026-10-05: 必要最低限だけを入れ、Qt の更新で余計な物が入らないようにする)— Qt のプラグイン 6 本(`platforms` の
  cocoa と offscreen、imageformats の gif / ico / jpeg / svg)、QML モジュール 13 本(アプリが実行中にディスクで引く物)、
  その結果入るフレームワーク 24 本。外した物は理由と並べて同じファイルにある: ネットワーク系のプラグイン(tls /
  networkinformation = 実装計画 §11.2)、sqldrivers、QtWidgets のスタイル(libqmacstyle だけが QtWidgets を
  連れてくる)、iconengines、`QtQuick.LocalStorage`(それだけが QtSql と SQL ドライバを連れてくる)、Fusion 以外の
  スタイル、Qt が自分で描くダイアログ(mac のダイアログは Cocoa の物。ネイティブのダイアログが無い offscreen では
  Qt が描く側を読みに行くので、offscreen の bundle ではダイアログが開かない)など。
  package は組んだ bundle をリストとちょうど突き合わせ、多くても少なくても名指して赤にする。`ui/` の import も
  qmlimportscanner で読み、書いた import がリストの外の時と、Qt のモジュールを辿った先にどちらのリストにも無い
  モジュールが出た時も赤(scanner が読めなかったファイルがあった時も — そのファイルの import は答えから抜ける)—
  **Qt を上げた時はこの赤でリストを見直す**。プラグインと QML の置き場は `Contents/Resources/qt.conf` が名指す
  (`PlugIns` / `Resources/qml`)。macdeployqt 6.12 は qt.conf を書かず、Qt 6.12 は bundle の中なら無くても同じ 2 つを
  探す(qlibraryinfo.cpp の `appleBundleSuffixes`)
- **アプリのスタイルが Fusion に決まっているのは import の順による** — スタイルの指定(`QQuickStyle`・
  `QT_QUICK_CONTROLS_STYLE`・`qtquickcontrols2.conf`)はどこにも無く、Main.qml が素の `import QtQuick.Controls` より
  先に `QtQuick.Controls.Fusion` を import するので Qt がそれをスタイルに取る(qquickstyleplugin.cpp の compile-time の
  選択。机の trace は `QtQuick.Controls.Fusion imported before QtQuick.Controls; using compile-time style selection`)。
  `SplitHandleBar` と Qt が自分で描くダイアログの素の import もそれで Fusion を読む。素の `QtQuick.Controls` が先に
  処理される形にすると、mac では既定のスタイル(macOS)が要り、bundle はそれを積んでいない
- imageformats プラグインの選定(§1 の結論)
- **配布物の import 検査**(実装計画 §11.2)は Qt のカスタムビルド(§14)の 3OS の配布物で組む —— Windows の
  [windows-x64.md](../ci/baseline/windows-x64.md) の import は既定ビルドの Qt の実測で、検査の元にはならない
- **syntect / two-face が埋め込む構文定義の著作権表示**。定義は 100 本超で
  それぞれ別ライセンス。two-face の `acknowledgement` モジュールが全文をプログラムから返すので、
  **`cargo xtask` で deny.toml の allow リストと突き合わせて落とす**。Apache-2.0 の定義は
  NOTICE と改変告知が要る(§15 も参照)
- **Octicons(MIT)から描き直した印**([デザイン規約.md](デザイン規約.md) §出典とライセンス):
  ファイルは同梱しないが、MIT の表示を第三者表示に載せるかを決める
- **同梱クレートのうち MIT を選べないものの表示**。SPDX 式が OR なら許可枝に MIT を
  選べるが、AND と単独綴りは選び直せないので、表示と義務の要否をここで決める:
  - `foldhash` = Zlib 単独 / `tree-sitter-elixir` = Apache-2.0 単独(§15-3)。
    **全文同梱・NOTICE・改変告知の要否はライセンスごとに違う**ので個別に決める
  - qtbridge 一族 = `LicenseRef-Qt-Commercial OR LGPL-3.0-only`(LGPL 側。静的リンクの扱いは §14)。
    **`qtbridge-interfaces` は改変版を同梱している**(`vendor/qtbridge-interfaces`):
    改変したソース・改変告知と日付(`PLATITUDE-MODIFIED.md`)・LGPL 本文はリポジトリに在る。
    配布物からそのソースへ辿れる形にする
  - **対象の絞り込みは `cargo tree -e normal,no-proc-macro --target all`** — proc-macro とその依存
    (`proc-macro2` → `unicode-ident` 等)はコンパイラの中で走るだけで本体に入らない。
    `cargo deny list` は build 依存も含み(`codespan-reporting` = Apache-2.0 単独は build 専用で
    再配布しない)、dev 依存は含まない
- **Qt は組んだ版と同じものを同梱する**: qtbridge-runtime 0.3 は Qt の private ヘッダ
  (`QtQml/private/qqmldata_p.h` の `QQmlData`)を読んで組まれるので、private の ABI が
  変わる別のマイナー版の Qt では動く保証が無い(システムの Qt を使う配布形は取れない)。
  qtbridge-runtime はビルド時に `Qt6QuickTest` もリンクするが、本体の import には残らない
  (release の本体が直に読む Qt は Windows も Linux も `Qt6Core` / `Qt6Gui` / `Qt6Qml` だけ —
  exe の dependents / ELF の `NEEDED` で確認)。**mac の本体は残す** — Mac のリンカは使われないライブラリも
  ロード時の依存に残すので、本体は `QtQuickTest` と `QtTest` も直に読み(`otool -L`、Snapshot の
  run 37238446842)、bundle に入る

### 3.5 CI の構成(push は mac だけ・全部は版が動いた時と週 1)

**入口は用途ごとに分け、中身は呼ばれる側の workflow(`workflow_call`)で共有する**(正本はファイル):

| workflow(Actions の一覧の名前) | 起動 | 中身 |
|---|---|---|
| `light.yml`(Light check (macOS, on push)) | main への push(`**.md` だけなら起きない)。走っている run は次の push が取り消す | macOS の clippy・test(`ci.yml`)、mac の撮影の `linux` 段(`shots.yml`) |
| `full.yml`(Full test (3 OS)) | `deps/*/after` タグの push・PR・週 1(金曜 19:00 JST)・手動 | 3OS の fmt・clippy・test・`periodic` のテスト・`shipped`、deny(`ci.yml` の全部)、mac の撮影の全行(`shots.yml` の `all`) |
| `snapshot.yml`(Snapshot build (macOS, not a release)) | 手動 | Full と、それを待たずに並ぶ mac の `cargo xtask package`(§8)。**中で Full が回るので、Full を別に撃たない**(同じ commit の 3OS と mac の全行が 2 重になる)— パスワード付きの DMG を run の artifact に残す(保持 30 日) |
| `shots.yml`(Shots (macOS)) | 手動(既定は census の全行。段で絞り、名指した行は段の行に足す — §3.6) | light / full からも段を渡して呼ばれる |

- **push を mac だけに絞る理由**: main に来る commit は land の gate が Windows とコンテナで回した物なので、push で足りないのは机の無い mac だけ(fmt と `shipped` も gate が持つ)。gate の選択から漏れた物と、commit 無しで動く物(runner のイメージ・RustSec の advisories)は週 1 の Full が拾う
- **依存の更新は land のタグで Full を起こす**: land は出荷ビルドの版を動かすと `deps/<日付>/after` を打って自分で push する(反映前テストの機械化.md §版を動かした land のタグ)ので、Full は更新を終えた commit そのものを測る。最低 git と Dockerfile の `FROM` はタグを打たない — CI の環境に効かず、段 3 の gate が回す。action の更新は Dependabot の PR で Full が回る
- **Full が走っても Light は止めない** — タグは land の時点で上がり、main の push は後でまとめてなので、2 つは別の commit を測ることが多い
- **`ci.yml` はファイル名を変えない** — `.qt-version` より前の commit は Qt の版をそこに持ち、xtask がそこから読む(`qt::former_pin`。綴りは `gate::graph` のテストがこの木のファイルで確かめる)
- **snapshot は暗号化した DMG で残す**(ユーザー決定 2026-10-05)— public のリポジトリの artifact は GitHub にログインした誰でも落とせ、§3 の表示はまだ同梱しないので、平文の binary を置くと配布になる。パスワードを知る人にしか中身が渡らない形にして、表示の用意を本番(§3)まで待つ(「暗号化した物を置くのは配布ではない」は解釈で、保証ではない)。パスワードはリポジトリの secret **`SNAPSHOT_DMG_PASSWORD`**(ユーザーが設定する。無ければ package の手順が組む前に赤)。開け方: run のページの artifact から `.dmg` を落とす → 開いてパスワード → `Platitude GG.app` を Applications へ → ad-hoc 署名なので初回は「プライバシーとセキュリティ」の「このまま開く」。パスワードを他人に渡せば、その人への配布になる
- 段との対応: Light は机の無い OS の段 2 相当(テストと `linux` 段の撮影)、Full は段 3 の「3OS CI」。段 3 の残り(<!--cmd:linux.bare-->`cargo xtask linux bare --discover`・性能実測)は机で回す

Qt の導入はどの workflow も `.github/actions/qt` を呼ぶ — 版の正本は `.qt-version` で、action も xtask もそのファイルを読む(workflow は版を持たないので、編集しても gate のステップは 1 つも動かない)。action は全部 commit の SHA で名指してあり、その追従は Dependabot(`.github/dependabot.yml` — 週 1、全 action を 1 本の PR に。crate は対象外)。**週 1 の物は金曜 19:00 JST に揃える**(Full の schedule と Dependabot。jackson-module-kogera の Dependabot と同じ時刻 — ユーザー決定 2026-10-05)。

**Windows の Qt は aqtinstall のリリース版では入らない**(6.11 以降はツールチェーンごとのフォルダ
`qt6_<版>/qt6_<版>_msvc2022_64/` に置かれ、3.3.0 は `qt6_<版>/qt6_<版>/Updates.xml` を探して止まる)。
CI もコンテナも、対応(miurahr/aqtinstall#1000)を含む固定コミットを入れる。版は `ci/linux/Dockerfile` の
`AQT_SOURCE` で、CI の `.github/actions/qt` もその行を読む。

**各ジョブの手順は 3OS とも通る**(fmt・clippy・テスト・`shipped`・deny・mac の撮影)。構文・キー・
`${{ }}` の式・呼ぶ側と呼ばれる側の入力の突き合わせは actionlint で検査する(v1.7.12。composite action の
中身と `run:` のシェルは対象外 — shellcheck を積んでいない)。
**リポジトリの Actions 設定は、外部の action を許可していることが前提**(Settings → Actions → General。
「自分のリポジトリの action だけ」だと、workflow は 1 行も実行されずに `startup_failure` で終わる)。
**xtask が macOS 向けに組めることは机で確かめられる**: `rustup target add aarch64-apple-darwin` の後
`cargo clippy --locked -p xtask --all-targets --target aarch64-apple-darwin -- -D warnings`(check だけなので
リンカも SDK も要らない。xtask の OS 分岐を触ったら撃つ)。core / app は tree-sitter の C と Qt を mac 向けに
組めないので、机では確かめられない。

runner の上で分かっている事:

- **Qt のアーカイブは `master.qt.io` から直に落ちる**(3OS とも 1 分以内)。`download.qt.io` はアーカイブを近い
  ミラーへ 302 で返す(`--base https://download.qt.io/` は aqt の既定値そのもので、付けても同じ)。ミラーは
  run ごとに変わる。チェックサム(`.sha256`)と `Updates.xml` は `download.qt.io` が直に返す
- **macOS の runner は SIP が無効**(`shots.yml` が `csrutil status` を印字する)。`.github/actions/qt` は SIP の
  有無によらず効く形(`RUSTFLAGS` で Qt の `lib` を rpath に埋める)— SIP が有効な機械では、step の
  `/bin/bash` が立つ所で `DYLD_*` が環境から落ち、`DYLD_FRAMEWORK_PATH` は cargo に届かない
- **`pipx run --spec` で固定コミットの aqt が 3OS で入る**(macOS の runner の Python は PEP 668 で素の
  `pip install` を拒む)
- **`deny` job**: action のコンテナは `rust-toolchain.toml` を見て toolchain を入れる。
  **`advisories` を回すのはこの job だけ**(机の `cargo xtask deny` は bans / sources / licenses)なので、
  この job の赤は workflow ではなく RustSec の指摘でありうる
- **macOS で xtask・core・app が組めて、`cargo test --workspace` が通る**(xtask の単体と gate のスイートを
  含む。一時ディレクトリが `/var` → `/private/var` の symlink の下に在ることで割れるテストは無い)。`shipped` と
  `replay` → `verify-ui` も通る
- **macOS では demo リポジトリが run のたびに残る**(`demo repositories kept: what is still running could not be
  read`)。`reap::others_in_this_group` が macOS では答えを持たないため。runner は使い捨てなので実害は無く、
  Mac の机で撃つようになった時に `sysctl` の `KERN_PROC` で埋める
- **offscreen の macOS は起動のたびに `Populating font family aliases took … ms … "Sans Serif"` を出す**
  (65〜88ms)。Qt の offscreen プラグインの既定フォントが `Sans Serif` 9pt(`qoffscreenintegration.cpp` の
  `OffscreenTheme`)で、CoreText にその名前が無いため。アプリは窓に `Theme.uiFamily` を名指すので絵には
  出ない。Cocoa の窓では既定がシステムフォントなので、この探索は起きない
- **キャッシュは 4GB 弱**(`rust-cache` 5 本と Qt 3 本。リポジトリの上限は 10GB)。`rust-cache` を書くのは
  main の run だけで、鍵には `QMAKE`(= Qt の版)が入る。Qt の cache は導入の直後に書く — job が後で赤く
  なっても次の run は落とし直さない。同じ鍵を並走の job が先に予約した時は `Unable to reserve cache` の
  警告で済む(PR の run は PR のスコープへ書く)
- **YAML の anchor**(`&checkout`)は job をまたいで展開される
- **所要**(cache の無い run): Linux 13 分・macOS 16 分・Windows 33 分・deny 1 分。
  `shipped` のビルドは Linux 3 分半・macOS 4 分・Windows 8 分
- **`cargo xtask package` の署名と DMG は runner で通る**: `PlugIns` の下の dylib と `Resources/qml` からそれへの
  link という bundle の形で、`codesign --deep` が `PlugIns` の下まで署名して `--verify --deep --strict` が通り、
  `hdiutil` の暗号化と開け直しも通る(Snapshot の run 37238446842 — 中身は許可リストより多い bundle)
- **Qt の plugin は universal binary**(x86_64 + arm64)で、`otool -l` は load command をアーキごとに出す —
  同じ run path が 2 回並ぶ。`install_name_tool -delete_rpath` は全アーキから 1 度に消すので、2 回目は「無い」と
  断られる。`package` は run path を 1 本ずつに畳んでから消す(`bundle::rpaths`)
- **`periodic` のテストは runner の 3OS で通る**(各 70 本。Full の run 37331246562: Windows 32 秒・macOS 7 秒・
  Ubuntu 2 秒)

まだ見ていない事:

- **許可リスト(§3)で組んだ bundle が runner の上で通ること**(机では Mac の手順を撃てない)— リストは Snapshot の
  run 37238446842 の package の job のログと、机の Qt 6.12 で撃った trace から組んだ: フレームワーク 24 本はその run で
  macdeployqt が辿った依存と Qt の CMake のリンク先から、qmlimportscanner が辿る 32 本はその run の import の一覧から、
  QML モジュール 13 本は机の `shipped` の起動と動詞 6 本(設定・コンボ・メニュー・カード・ツールチップ・アバター)の
  `QML_IMPORT_TRACE` から(場所を引かれたのはどれもちょうど 13 本)。mac で読み違えていれば package がその名前を挙げて
  赤になる。この bundle で起動の判定(dyld が bundle の外から読んだ image が 0 本)と署名が通るかもそこで見る。
  `hdiutil create` は runner で `Resource busy` の断続的な失敗が知られている(actions/runner-images#7522)— 出たら
  job を撃ち直し、繰り返すなら手を考える
- **呼ばれる側の workflow の上で、Light の取り消しが呼ばれた job まで止めること**と、`deps/*/after` の push で
  Full が立つこと(Light / Full / Snapshot から `ci.yml` / `shots.yml` を呼ぶ形と、`rust-cache` の鍵が
  `light` / `full` で分かれることは run 37331182896 / 37331246562 / 37331306019 で走った)
- **Dependabot の PR が `.github/actions/qt` の中の action(`actions/cache/restore` / `save`)も拾い、SHA の隣の
  版コメントも書き換えること**(更新の確認は走っている。PR は action に新しい版が出た時に立つ)

### 3.6 macOS の撮影(`shots.yml`)— 実機の代わりに CI の runner で撃つ

撃ち方と読み方は verify-ui スキルの mac.md。runner の上で `cargo xtask replay` が verify-ui の行を 1 本ずつ撃ち、
判定は手で撃った run と同じ・絵とログは artifact に残る。

- **写るのは CoreText のフォントと macOS の経路まで**。offscreen の QPA は Apple では CoreText のフォント DB を
  使い(`qoffscreenintegration.cpp`、Qt 6.12)、描画は software scene graph(`RhiBasedRendering` が false)。
  **Cocoa の窓(タイトルバー・ネイティブメニュー・Metal の描画・Dock)は写らない**
- **撃つ行**: Light(main への push)= 段分け表の `linux` 行(判定がフォントで決まる行)/ Full = census の全行 /
  `shots.yml` の dispatch = 段(既定は `all` = census の全行)と名指した行・言語(既定は日本語 — 机とコンテナが
  日本語の機械なので)。段を `none` にして行も無い dispatch は job ごと skip される。**Light / Full が呼んだ撮影の run と artifact は呼んだ側の
  run に載る**(`gh run list --workflow light.yml` / `full.yml`、Snapshot の中の Full は `snapshot.yml`。
  `shots.yml` の一覧に出るのは dispatch だけ)
- **Full の週 1 の schedule は正時(0 分)なので、GitHub が混む時は遅れることがあり、負荷次第では落とされる**
  (公式の記述。落ちた週は手動で撃つ)。**public のリポジトリで 60 日活動が無いと GitHub が止める**(Actions のページから戻す)
- **代金**: リポジトリが public の間、標準 runner(`macos-26` = arm64)は分の課金が無く、artifact と cache の
  保管も無料(cache はリポジトリごと 10GB まで)。**private にすると分で課金され、macOS の分単価は Linux の
  約 10 倍**($0.062 対 $0.006)なので、その時は Light と Full の自動の起動を外して手動だけにする。
  larger runner(`-large` / `-xlarge`)は public でも有料 — ラベルは標準のまま
- **席の枝を撃つには、その枝が GitHub に在ることが要る**(dispatch の `--ref`)。main は push 済みならそのまま撃てる

runner の上で分かっている事:

- **offscreen の run は macOS で絵を出す**(`screenshot saved=true`。Windows と同じ software の経路)。
  `linux` 行の判定(幅・切れ・段)は Hiragino Sans / Menlo で通る。所要は 1 行 1〜8 秒で、最初の
  1 行に release ビルドが乗る(cache の無い run で 5 分半、`linux` 行だけの job 全体で 10 分)
- **census の全行(700 本前後)は job 全体で 40 分前後**(Replay の天井 270 分の内)。判定は Windows / Linux と同じ行が
  通り、mac でだけ落ちるのは下の「行の高さ」が効く行
- **`defaults write -g AppleLanguages` / `AppleLocale` は runner で通る**(`ja-JP` / `ja_JP` が読み返せる)。
  日本語の run の絵では、省略の `…` が中央寄りの和文字形で出る(§20)
- **和文は UI フォントで崩れずに出る**(コミット件名・長い和文の折り返し・和欧混植・名前の中抜き省略)
- **Hiragino Sans は Yu Gothic UI / Noto Sans JP と字の箱が違う** — 行の箱が低く(`FontMetrics.height` が小さい)、
  その下に leading を持ち(`fontMd` で 7px)、数字の幅が広い。フォントから寸法を出す所は mac でだけ別の答えになる。
  その差が効く所と、そこの組み方:
  - **操作パネルのボタン(fetch / push / stash / Search)の枠は、mac でだけ中身の深さが床になる** — 枠の深さは
    ブランチ名 2 行ぶんの高さ(`OpsPicker.pairHeight`)と、語と印を縦に積んだ中身(`ActionButton.stackDepth` =
    40px)の大きい方(`TopBar.actionDepth`)。2 行ぶんは mac 30px・Ubuntu 43px・Windows 44px(`band_actions` の
    `cellH`)で、2 行ぶんだけに揃えると mac では語のチップが枠の上辺に重なり、印が下辺で切れる。中身が
    収まっているかは `boxed=` が言い、`linux` 段の `band-actions*` 3 本が push のたびに mac でも判定する
  - **欄(`LineText` = `TextEdit`)は行を箱の中央に置く** — `TextEdit` は leading を行の下に足すので、置かないと
    欄の字は同じ書体のラベルより leading の半分だけ上に立つ(mac の `fontMd` で 3px。箱の下端に引く下線は字から
    9px 離れる。leading の無い Windows / Ubuntu の書体では 0px と 4px)。**同じ書体・同じ大きさのラベルと欄を
    同じ行に並べる所は、ベースラインで揃える**(diff の帯の `DIFF`・パス・`—`、欄の切った印 `…`)— leading が奇数の
    書体では中央合わせの半画素が部品ごとに別の向きへ丸められ、1px 残る。帯の `DIFF` とパスが同じ行に立つかは `hunk_tools caption=` が
    判定する(`linux` 段)
  - **hunk 見出しの `Stage hunk` は、隣の `Discard hunk` と同じ深さのボタンに取る** — `Discard hunk` は長押しの
    印のぶん深く、上端で並べると語が書体しだいで上にずれる(mac 4px・Windows 2px)。2 語が同じ行に立つかは
    `hunk_tools level=` が判定する(`linux` 段)
  - **畳んだレールの数字は、行の箱で積むと mac でだけ印に触る** — 行の高さを固定しても基線は行の上端 + ascent に
    落ち、12px の ascent は Hiragino Sans 約 11px・Yu Gothic UI 13px・Noto Sans JP 14px。数字はインクで置く
    (規約 §左メニューを畳む)。Hiragino Sans の数字のインク(0〜9 の外形)は印の箱の下の 10px に 9.8px で、余りは
    画素に満たない — 中央は端数のまま出す(余りを 1px と数えると、数字が間の下へはみ出す)。
    数字のインクが印の箱の下で中央に立つかは `nav-fold` の `counts=` が判定する(`linux` 段。`face=` が書体の値を言う)
  - **`CardText`(`TextEdit`)を語と同じ行に置く所は、ベースラインを揃える** — 行の既定の縦中央では、文は
    leading の半分だけ隣の語より上に立つ(mac 2〜3px)。揃えている所: 状態カードの各行・質問バーの見出しと
    `push` のチップ・edit 停止の行と `edit` のチップ・設定の単位(`minutes` ほか)・DISCARDS の帯の文と
    `Restore` / `Load … more commits`・左メニューの事実行と ahead の数・コミットカードの日付と co-author(置き方は
    rules-refs/app-ui.md の `CardText` の行)。状態カードの各行が揃っているかは `badges-all-hover` の `level=` が
    判定する(`linux` 段)。他の所は判定行が無く、Full の絵で見る
  - **右パネルの最小幅で、親 2 本以上 + co-author のコミットは日付の時分が入らない**(Windows / Linux は入る)。
    日付は時分を丸ごと手放す(`2026-10-04…`。`co_authors … date=day`)。欄の切り目は字の境目に置く(末尾は
    丸ごと立つ最後の字の後ろ、中央切りのパスは印の後ろが丸ごと立つ字から)— 画素で切ると co-author 名の `語` や
    パスの `s` が半分だけ残る
  - 1 行の入力欄(Commit summary)は低くなるだけで、字は収まる

  mac の絵は main に載せてから `shots.yml` でしか撮れない。runner の絵で見た形: 操作パネルの枠は `cellH=40`・
  `boxed=true` で語と印を包む / hunk の 2 語は同じ行(`level=true`)/ 作者行は名前の下線が字のすぐ下・日付は
  `date=day`(`2026-10-04…`)・切れた co-author 名は字の境目・親ハッシュは 3 桁 / パスの中央切りは `crate…hot.rs`
  と字が欠けない / 断られた push の報せバーは降りきって写る / diff の帯の語は 1 本のベースラインに立つ
  (`DIFF` とパスは `hunk_tools caption=true`・0px。パスの中央切りの頭と尾、`—` と worktree 名は判定行が無く、
  `diff-band-sweep` と `carried-read` の絵で見る)

まだ見ていない事:

- 英語の run(`locale=en`)と並べた字形の差 — `—` `…` と、等幅の中の和文フォールバック(§5 / §20)。
  等幅の中の和文(diff 本文・コマンドログ)を撮る行は `linux` 段に無いので、行を名指して撃つ
- Replay が天井(270 分。job は 300 分)で切れた時の残り方 — そこまでの絵とログは artifact に残る
  (`summary.md` は replay が最後に書くので出ない — 行ごとの `ok` / `FAIL` は step のログ)。
  切れた時に撃っていた 1 行の絵とログは書きかけでありうる(step の天井が止めるのは起点のシェルで、
  その子は job の終わりまで残りうる)

**実ウィンドウの撮影は未作成**。runner のイメージは bash からの画面収録を許可済み(`screencapture` が撃てる —
actions/runner-images の TCC 設定)で、足りないのはハーネスの側: 絵を保存した後も窓を立てたまま待つ駅と、
そこで外から撮る口。§8(Dock のアイコン)・§22(アプリメニュー)を CI で見るにはこれが要る。

### 13. 遅い置き場所でフォルダを選んだ時の無反応

`path.is_dir()` が先に false を返す経路は多くが `plain` に落ちるため、この窓に
入るのは「ディレクトリとしては見えるが git が answer を返せない」場合だけ。

### 14. Qt のカスタムビルド(床を削る最後の手・非通信の証明の前提)

**[P3-確認事項.md](P3-確認事項.md) §性能 の手(グラフ行の C++ ヒープ)を打ち切った後の、床を削る最後の手。**
実測は [perf-windows-x64.md](../ci/baseline/perf-windows-x64.md)。**多タブでの実測は
未取得** — 基準リポジトリ 2 本を開いて `PGG_MEM_REPORT=1` で 1 本目と突き合わせる。

**先に潰した道(結論は rules-refs/app-ui.md の同項)**:

- 同梱物の削減 — 除外候補はどれも実行時にロードされない
- QML の事前コンパイル(qmlcachegen)— 予算の 0.4%
- `Qt6Network` の除外 — 既定ビルドでは `Qt6Qml` / `Qt6Quick` のハードインポート

**試すこと**:

- **`-no-feature-qml-network`** — `Qt6Qml` と `Qt6Quick` の QtNetwork へのリンクと、QML の XMLHttpRequest を
  外す feature フラグ(qtdeclarative 6.12.0 の CMake)。**ネットワーク非通信の証明([実装計画.md](実装計画.md)
  §11.2)の前提** — 配布物から Qt6Network が外れて初めて、配布物の検査が組める
- 使っていない feature の `-no-feature-*` で `Qt6Qml` / `Qt6Quick` / `Qt6Gui` の常駐が
  どれだけ減るか
- **静的リンクは別項** — LGPL-3.0-only での静的リンクは再リンク可能な
  オブジェクトの提供義務が付き、ライセンスの判断は人間の承認が要る

**負担**: 3OS ぶんの Qt を自前でビルドし CI で持つコスト。qtbridge の要求バージョンにも縛られる。

**止め時**: カスタムビルドで起こした窓 1 枚(`cargo xtask perf --no-open`)で

### 19. IntelliJ の Code Provenance を戻す(開発環境)

開発機の IntelliJ(2026.2 系)は Registry `code.provenance.chatter.analytics.enabled`
を **false** にしてある。既定の true では bundled プラグイン "Code Provenance by Qodana"
が `chatter.exe observe` を約 65 秒間隔で起動し、起動 1 回につき tree-sitter の native lib を
`%TEMP%` へ展開したまま残す。報告は [QD-16236](https://youtrack.jetbrains.com/issue/QD-16236)。

QD-16236 が解決したら:

1. IntelliJ を対象版へ上げ、`Help | Find Action` → `Registry...` で該当キーを **true** へ戻す
2. 1 時間、`%TEMP%\tree-sitter-ng-lib_*` が増えないことを確認する(直っていなければ 1 時間で数十件以上出る)
3. 出るなら false に戻し、QD-16236 に実測を添えて差し戻す

false のままで失うのは JetBrains 側へ送る chatter analytics だけ。true へ戻すと
`code-provenance\chatter\v1` のローカル記録も再び育つ(数 GiB 規模)。

### 20. 英文中の `—` `…` の字形(macOS の JP ロケール実機)

Qt は shaping の言語を `QLocale()`(= OS のロケール)から HarfBuzz へ渡す
(`qtextengine.cpp`、Qt 6.12)。日本語フォントがロケールで持ち替える字形が、英文に続く
`—` `…` に出うる —— 和文字形は全角のダッシュ・中央の三点で、`—` が両 OS で同じ長さ・
同じ位置という据え置き(デザイン規約 §寸法「字で出ていた記号は 5 種」)から外れる。

- Windows: `Yu Gothic UI` は JP ロケールでも欧文字形(実測。ヘッドレスの `Noto Sans JP`
  だけが和文字形になる — verify-ui スキル windows.md)
- Ubuntu: 言語の出所は Qt の版によらず LANG(Qt が起動時に `setlocale(LC_ALL, "")` を
  呼び、HarfBuzz の既定言語もそれを読む)。**日本語デスクトップ(`ja_JP.UTF-8`)では和文字形**
  (実測。検証のコンテナも同じ LANG で、Linux の絵は和文字形)。幅の差は 1px 前後でレイアウトは崩れない
- **直すのはレイアウトが崩れる時と、全く違う表現に見える時だけ**(ユーザー決定 2026-10-02)——
  和文字形の `…` `—` そのものはアプリが上書きしない
- **macOS が未実測** —— Finder から立てた GUI には LANG が無く、`QLocale()` は
  システム設定の言語を答える。JP ロケールの実機で設定画面の説明文の `—` と、
  グラフのチップの省略の `…` を `Hiragino Sans` で目視し、上の 2 つに当たるかだけを見る。
  実機が無い間は `shots.yml` の日本語の run の絵で読む(§3.6 — runner の言語設定が Qt に届くかは同節の確認事項)
- **CI の絵は bundle でない素のバイナリの答え** —— macOS はアプリのロケールの言語を、ユーザーの言語と
  bundle が宣言する言語の突き合わせで決める。[Info.plist](../packaging/macos/Info.plist) が宣言するのは
  `CFBundleDevelopmentRegion = en` だけ(`CFBundleLocalizations` / `CFBundleAllowMixedLocalizations` は無い)
  なので、出荷する `.app` は日本語の Mac でも英語のロケールで立ちうる = runner の日本語の run とは shaping の
  言語が違いうる。どのロケールで立ったかは `QT_LOGGING_RULES=qt.core.locale.debug=true` で起動時に出る
  (`qlocale_mac.mm` — ロケール・優先言語・bundle の宣言が並ぶ)。`.app` を組んだ時にこれで確かめ、上の
  目視はその条件で読む

### 21. macOS の `cargo xtask linux`(docker の経路)

エンジンは Windows が WSL の wslc、Linux はコンテナ無し、**macOS は docker のまま**(`linux::engine`)。
wslc に無い 3 つ(`--init` → イメージの tini、Go テンプレート → `--format json`、`builder prune`)を
両方に通る綴りへ寄せた後、docker で撃ったのは JSON の一覧の形(Docker Desktop for Windows の `images` /
`volume ls` / `image inspect`)だけ —— `ps --format json` のラベルの読みと gate のコンテナ(tini で起動・
`exec`・`rm --force`)は docker で通していない。mac の実機で `cargo xtask linux test -p platitude-core` と、
Linux 側を持つ `cargo xtask gate` を 1 回ずつ

### 24. Linux(xcb)の Menu キーで開く右クリックメニュー(実機)

規約 §メニュー のキーボードは「どの OS でもキーボードの居場所が答える」。xcb は Menu キーで要求を**ポインタの位置**に
出し、続けてキーの事象を出す(`QXcbKeyboard`)—— 作りは、ポインタの下に届いた要求を断り(窓は
`KeyMenu.placeless`、欄は右ボタンの有無とキャレット)、キーの事象でキーボードの居場所を開く(rules-refs の
`KeyMenu` の行)。コンテナの verify-ui は offscreen で、xcb の事象は来ない。実機で見るもの:

- ポインタを別の面(グラフの上・別の欄の上)に置いて Menu キーを押し、**キーボードの居場所のメニューが 1 枚だけ**
  対象の下に開く(ポインタの下には開かない)
- ポインタがキャレットを持つ欄の上に在る時の Menu キーが、ポインタの下ではなくキャレットの下に開く
- Wayland では要求の出し方が別(Qt の wayland プラグイン)—— 同じ 2 点を見る

### 25. DISCARDS の高度な検索(操作の種類などを名指して絞る)

DISCARDS の帯のフィルタは、項目が見せている文面(題・中身の行・worktree・時刻の書き方)のどれかに、打った行を

- 書き方はグラフの検索の名指し(P3-確認事項 §ウィンドウ chrome の「アドバンス検索」の `author:` / `date:` 等)と揃える

### 26. 画面表示中の読み込みの間隔の実機での振る舞い

規則と決定は P3-確認事項 §画面表示中の読み込みの間隔。定数はこの机(Windows・SSD)の実測で決めた
([poll-cost-windows-x64.md](../ci/baseline/poll-cost-windows-x64.md))。机の無い環境で見るもの:

- **HDD・低性能機**: 小さいリポジトリが床の 5 秒に留まるか(床に乗るのは 1 回の重さ 250ms まで)、重いリポジトリが
  天井へ寄って止まらず進むか。重さは原因を区別しない(CPU の取り合い・ディスク待ち・枠待ちのどれでも伸びる)
- **macOS**: 窓が前面に無い間は App Nap が CPU の優先度・タイマー・I/O を絞るので、15 秒は保証の外。
  保証が要ると判断したら App Nap を避ける宣言(`NSProcessInfo` の activity)が要る
- **Linux / macOS**: `Instant` は休止中を数えない(Windows は数える)。規則は時計を見ないので推定は変わらず、
  期限が過ぎて見えるかどうかだけが違う(どちらでも他の worktree は 1 本ずつ追いつく)

### Linux: 日本語の Ubuntu 24.04 デスクトップが積むもの

**検証のコンテナ(ci/linux/Dockerfile の app ステージ)はこれを再現する**(ユーザー決定 2026-10-02)。
宣言する依存(runtime ステージ)は最小のまま。

- **どのデスクトップにも在る**: 既定の選択 `ubuntu-desktop-minimal` の Depends が `fonts-dejavu-core`・
  `language-selector-common`、Recommends が `fonts-noto-cjk`・`fonts-noto-core`・`fonts-noto-color-emoji`・
  `fonts-ubuntu`・`fonts-liberation`(noble の apt で読んだ)
- **日本語を選ぶと足される**: インストーラ(subiquity の `LocaleModel`)が `check-language-support -l ja` の
  答えを入れる —— ubuntu:24.04 での答えは `fonts-noto-cjk-extra`・`fonts-noto-core`・`ibus-mozc`・
  `language-pack-ja`・`mozc-utils-gui`(language-selector 0.225 の `pkg_depends` に `fn:ja::fonts-noto-cjk-extra`)。
  ISO の pool にこれらは無く、**ネットにつながずに入れた機械には入らない**。後から「言語サポート」を開くと補完を
  促され、Japanese Team の `ubuntu-defaults-ja`(24.04 では Remix の ISO に代わる配布)も `fonts-noto-cjk-extra`
  に依存する。LANG は `ja_JP.UTF-8`
- **Qt の描き方を変えるのは 2 つだけ**(qmltestrunner で styleName・幅・grab の画素を、宣言どおり / 言語セレクタ
  有り / ja_JP / 英語デスクトップ / 日本語デスクトップの構成で比べた):
  - `fonts-noto-cjk-extra` —— 太さの面が増える。UI は使わない(上の段落)
  - `LANG=ja_JP.UTF-8` —— 英文中の `…` `—` が和文字形になり、`'` `.` が 1px 未満ずれる(§20)
- **language-selector-common の fontconfig 規則**(Noto Sans CJK JP の 18px 以下を hintnone ほか)と
  noto-core / color-emoji / ubuntu / liberation は、UI の字の画素を 1 つも変えない —— UI の family は全部
  名指しで、届くのは名指しの family に無い字のフォールバックだけ。コンテナはフォントを積み、規則は積まない
  (Python ごと要る)。**family を名指ししない字(窓の font を継がない qmltestrunner の Controls)だけは
  noto-core で幅が変わる**(`tst_askfields` の長い remote 名が 329 → 314px)—— qmltest の幅の前提は字面に依らせない
