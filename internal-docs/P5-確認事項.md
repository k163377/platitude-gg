# Phase 5(配布準備)確認事項

配布準備期に検証・判断する項目を先行して積む場所。
P3 分は [P3-確認事項.md](P3-確認事項.md)。

## 積み(未検証)

### 1. diff プレビューの画像デコーダ範囲

プレビュー(`platitude-core::preview`)が画像扱いする拡張子のうち描画できるかは
実行環境の Qt imageformats プラグイン次第。デコーダが無い形式は
「Preview unavailable」+ サイズ表示に劣化する(壊れない)。開発環境の Qt は
qgif / qico / qjpeg / qsvg のみ同梱、png / bmp は Qt 本体組み込み。
**webp / tif / tiff / avif は劣化表示**。

検証・判断:

- **qtimageformats を配布物に同梱するか(本命)**。プラグイン DLL を置くだけで
  コード変更なしに描画可能・数百 KB 級。ライセンス確認(libwebp = BSD-3 /
  libtiff = MIT 系)と 3OS の deploy 手順への追加が必要
- **avif**: Qt 標準プラグインが無い。(a) 劣化表示のまま /(b) kimageformats 系の同梱
  (LGPL — 依存ライセンス方針の確認要)/(c) Rust 側デコードして PNG に変換
  (依存が大きく軽量方針と要相談)
- **WebView(Qt WebEngine)フォールバックは非推奨の見込み** — Windows の実体は
  Chromium 同梱で、配布 +150MB 級・別プロセスのメモリ・ネットワークスタック同梱が
  軽量目標 / メモリ予算 /「ネットワーク非通信」の主張
  ([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))に同時に抵触する

### 2. forge との距離(`gh` を呼ぶか) — **かなり後の判断**

PR バッジの実データ(P4)とリモートブランチの差し替え・削除まわりで「`gh` CLI があれば
済む」場面が出る。決まるまでは git だけ。

- `gh` は外部 CLI なので絶対制約の条文には触れないが、アプリが
  forge へ通信させる点で制約の趣旨としては同じ側
- 判断時に同時に決めること: 未インストール環境での degrade(バッジが出ないだけ)/
  認証(`gh auth` に委譲。トークンは gh が持つ)/ オフライン job での扱い /
  「ネットワーク非通信」の主張([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
  の書き換え
- 当面の代替: PR バッジは `ls-remote refs/pull`(git 経由)で足りる見込み。リモート
  ブランチの差し替え・削除は git だけで済んでいる。残る判断は「forge の rename(PR が
  付いてくる = 本物の改名)まで要るか」だけ

### 3. 配布物への同梱一覧(既知分の集約)

- `pgg-todo-editor.exe` を本体と同じディレクトリへ(rules-refs/core.md の pgg-todo-editor
  項。無いと interactive rebase だけが動かない)。**これは `platitude-core` の bin
  ターゲット**なので `cargo build --release -p platitude-app` では作られない(素の
  Ubuntu で不在に気付いた実測)— 配布物を組む手順は必ずワークスペース全体をビルドする
- **Qt6Network は Qt6Qml のロード時依存として同梱が必須**。したがって非通信の主張は
  「**アプリ自身の import table に通信系なし + ネットワーク系
  プラグイン除外**」で立てる(実測 [ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
- imageformats プラグインの選定(§1 の結論)
- **syntect / two-face が埋め込む構文定義とテーマの著作権表示**。定義は 100 本超で
  それぞれ別ライセンス(確認済み: Kotlin = Apache-2.0 / Rust = MIT)。two-face の
  `acknowledgement` モジュールが全文をプログラムから返すので、**`cargo xtask` で
  deny.toml の allow リストと突き合わせて落とす**。Apache-2.0 の定義は
  NOTICE と改変告知が要る。テーマは syntect 同梱の `base16-ocean.dark` のみ(§15 も参照)
- **同梱クレートのうち MIT を選べないものの表示**。SPDX 式が OR なら許可枝に MIT を
  選べるが、AND と単独綴りは選び直せないので、表示と義務の要否をここで決める:
  - `unicode-ident` = `(MIT OR Apache-2.0) AND Unicode-3.0` — **AND なので Unicode
    License v3 が外せない**。proc マクロ経由だけでなく proc-macro2 → qtbridge の通常依存
    でも本体に入るので、build 時だけという逃げ道が無い
  - `option-ext` = MPL-2.0 単独 / `foldhash` = Zlib 単独 / `tree-sitter-elixir` =
    Apache-2.0 単独(§15-3)。**全文同梱・NOTICE・改変告知の要否はライセンスごとに違う**
    (MPL-2.0 のソース公開義務は改変したファイルにしか掛からない)ので個別に決める
  - **対象の絞り込みは `cargo tree -e normal`** — `cargo deny list` は build 依存も含み
    (`codespan-reporting` = Apache-2.0 単独は build 専用で再配布しない)、dev 依存は含まない

### 3.5 CI を軽量と完全性に割る(CLAUDE.md の段 2 / 段 3)

**CI は 2 本**。分ける基準は**鳴る頻度** — 毎回の反映に載せるのは
答えが動く検査だけ。

- **軽量 CI(段 2)= 反映のたび**: 3OS の fmt / clippy / test、Linux の
  `cargo xtask linux verify-ui`(触った動詞)、`cargo xtask linux bare`(宣言済みの
  依存だけのイメージで起動するかの 2 値。ネットワーク不要で、鳴る時は必ず
  「配布物に何を足すか」の話になる)
- **完全性 CI(段 3)= リリース前と、依存・環境・Qt を触った時**: 上の全部に加えて
  <!--cmd:linux.bare-->`cargo xtask linux bare --discover`(依存リストを素の Ubuntu から導出し直す)、
  `periodic` のテスト(`cargo test --workspace -- --ignored ::periodic::` = 日常の段に見合わないテスト。
  rules-refs/core.md `periodic`)、完全オフライン job、3OS のスクショ目視、性能実測
- **定期フルテスト = 週 1(未作成)**: 完全性 CI と同じ中身(= <!--call:gate.full-->`gate --all --fresh`)を schedule で回し、日常の段から
  外した物のデグレを拾う —— `periodic` のテスト(実 git の結合テストのうち git の挙動そのものを確かめる物を含む)と、
  段分け表(`crates/xtask/verb-tiers.txt`)が段 3 に回した動詞(`full` の行と、`linux` 以外の全行のコンテナ側)。
  **`land` の gate は段 2 なのでこれらを回さない**(`gate::for_landing` は `--all` を付けない)ので、段 3 を回さない
  期間が長いほど、Linux の時機でだけ出る競合・最低版の git でだけ壊れる流れ・git の挙動の変化が溜まる。日常の段
  (軽量 CI・`gate`)は `#[ignore]` で `periodic` を回さない

**`cargo xtask structure` は軽量側**(行数上限。ビルド不要で数秒)。ただし**基準線が縮んだ時にツールが `crates/xtask/structure-baseline.txt` を書き換える**ので、後段に `git diff --exit-code crates/xtask/structure-baseline.txt` を置く — 置かないと「縮んだのに commit されていない」が CI で緑のまま流れる。

**`cargo xtask shipped` は `target/shipped/` に 2 本目の release を組む**(gate が動詞の隣で回すための自前 profile — 反映前テストの機械化 §hook の下)。CI では deps をもう 1 度コンパイルする代金が OS ごとに乗るので、軽量側に置くなら `shipped` に profile を選ばせる口(`--profile release`)を作るか、完全性側へ寄せるかを初回 CI の時間で決める。

**`--discover` は完全性側**(apt を何度も叩き、ネットワークに依存し、答えは
普段変わらない)。逆に、依存を触った PR(`Cargo.toml` / `ci/linux/Dockerfile` /
QML の import が変わった時)では必ず段 3 を回す。

### 4. CI のフォント整備(スクショに日本語を出す)

CI 整備時にジョブへ折り込む。判定基準は demo `basic` の日本語コミット
(`docs: 利用案内の骨子を日本語で直す`)が 3OS の PNG で**日本語字形**
(直 / 骨 の字形で見分ける)で写ること。

- **ubuntu job**: `fonts-noto-cjk`(+ `fonts-dejavu-core`)を明示インストール —
  前提はジョブが自分で作る。「Ubuntu デスクトップは fonts-noto-cjk
  標準搭載」というチェーンの前提も `fc-list` で実証する
- **windows job**: offscreen の FONTDIR は .ttc を読まない(verify-ui スキル)ため
  Windows 標準の日本語フォントは全て使えない。TTF の日本語フォント(例: Noto Sans JP)
  を CI 環境の FONTDIR に用意する — 置くのは CI 環境だけ
- **macos job**: offscreen でも CoreText のフォント DB なので追加不要の見込み。
  Hiragino Sans が写ることの確認のみ

### 7. 引いたフラグのダッシュが他 OS の等幅で釣り合うか

`push -f` のダッシュはトークン長の罫で引いてある(規約 §git 用語のコード表記)。
罫の長さは固定で周りの字幅は OS が解決した等幅 family 次第。実測できているのは
Cascadia Mono(Windows)だけ。

- macOS(Menlo)/ Ubuntu(DejaVu Sans Mono / Noto Sans Mono)の実機で `push -f` と
  後ろの `!` の間合いを目視する
- ズレていた場合も**トークン 1 つで釣り合う長さを選び直す**(family ごとの分岐は
  3 OS ぶんの微調整を抱える)

### 8. アプリアイコンの mac / Linux 側

焼くところまでは 3 OS ぶん済み。動いているのは Windows だけで、mac / Linux は資産と
定義が置いてあるだけ(実機が無い)。

| OS | 置き場所 | 中身 |
|---|---|---|
| 共通 | `crates/platitude-app/assets/icon-<n>.png` | 16 / 20 / 24 / 32 / 48 / 64 / 128 / 256 / 512 / 1024。**16 と 20 だけ小サイズ版から**、残りはマスターから(規約 §アプリアイコン の 24px 境界) |
| Windows | 同 `platitude.ico` + `.rc` / `.res` + `build.rs` | exe のリソース(絵と**表示名**の両方。§11)。窓の側は `src/winframe.rs` |
| macOS | 同 `platitude.icns` | 10 スロット(`icp4` / `ic11` / `icp5` / `ic12` / `ic07` / `ic13` / `ic08` / `ic14` / `ic09` / `ic10` = 1x と 2x の両方) |
| macOS | `packaging/macos/Info.plist` | バンドル定義。**`@VERSION@` / `@BUNDLE_ID@` が未置換なので、このままでは妥当な plist ではない** |
| Linux | `packaging/linux/platitude-gg.desktop` | hicolor への install コマンドはファイル内のコメント |

ラスタライズは生成物をコミットして依存ゼロを保ち、焼き直しは手作業(手順は
`platitude.rc` のコメントと [.claude/rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md)。
`cargo xtask` + SVG レンダラは色を直す頻度が上がったら再考)。**大きいサイズを焼く時の
罠**: 128px 以上をブラウザのヘッドレスで撮る場合、`--window-size` にそのまま渡すと
最小ウィンドウ幅にクランプされて図の一部しか写らない。広いビューポートで描いて左上を
切り出す。

残るのは実機と、決めていない 2 つ:

- **bundle identifier が未定**(`@BUNDLE_ID@`)。逆 DNS で、署名と quarantine の記録が
  これを鍵にするので notarize より前に確定させる。リモートが決まっていないため今は
  置いていない
- **バンドルを組む手続きの置き場所**。`Info.plist` の 2 つの置換と `Contents/` の構築
  (`MacOS/platitude-gg` + `Resources/platitude.icns`)で、`cargo xtask` が候補。
  mac 実機が無い間は書いても走らせられない
- **macOS の外形**: 規約の角丸タイルは Dock の角丸正方形にそのまま合うはずだが、
  Apple は 1024 の canvas に対して実描画領域を一回り小さく取る慣習があり、そのまま
  焼くと隣のアイコンより大きく見える。実機で Dock に並べて確認する
- **Linux の実機確認**: `.desktop` の `StartupWMClass` が実際の WM_CLASS と一致するか
  — ズレるとランチャにアイコンの無い 2 つ目のエントリが出る。両方ともスラグに
  揃えてあるが(Qt の `application_name` = 主張の根拠)、X11 と Wayland の両方で見る

### 10. 窓の縁に残っている 2 つ(Windows)

タブ行が OS のタイトルバーを兼ねる形(規約 §ウィンドウの縁。実装は
`ExpandedClientAreaHint` による frameless — rules-refs/app-ui.md)に残る**機能の欠け**。

| 残っているもの | いま何が起きているか |
|---|---|
| 窓メニューの `移動` / `サイズ変更` | 出るが効かない。この 2 つは**窓に caption があるかを先に見る**が、`WS_CAPTION` は戻せない — 戻すと OS が帯の上に caption を描き直す(rules-refs/app-ui.md) |
| Snap Layouts | 最大化ボタンの矩形を `HTMAXBUTTON` で答える必要がある。hit-test のサブクラス自体は在る(`winframe::hit_test`)ので、残る作業は `HTMAXBUTTON` にすると非クライアント化する押下・hover をボタンに映す側(`WM_NCLBUTTONDOWN/UP` の自前処理と hover 表現) |

**実窓の 125% / 150% も同じゲートで見る** — QML の側は `QT_SCALE_FACTOR` を渡した
offscreen の run で両倍率とも壊れていない(帯・窓ボタン・右端の間合い)。読めていないのは
**OS が渡す非クライアントの寸法**の方で、それは実機で拡大率を変えた画面にしか出ない
(frame と client の一致は `winframe/api.rs` が実測を持つ)。

判断:

- 窓メニューを自前で描く道もある(`AppMenu` で
  描き、行から `WM_SYSCOMMAND` を撃つ)。`移動` / `サイズ変更` はそのままでは撃てない
  ので、出す行を絞るか諦めるかの判断が要る。メニューを出すこと自体は済んでいる
  (サブクラスの `WM_NCRBUTTONUP` → OS のメニュー)— 効かないのは中身の 2 行
- どちらも Windows だけの話であることも込みで優先度を決める

### 11. 配布ビルドが名乗るバージョン

表示名は片付いた(`assets/platitude.rc` の `VERSIONINFO` / `FileDescription` =
`Platitude GG`)。残るのは版番号だけ。

**読み手の罠**: PowerShell の `Get-Item .VersionInfo` はこの形のリソースの
**文字列フィールドを全部空で返す**(固定ブロックは読める)。正しく読む経路は
`platitude.rc` のコメント / rules-refs/app-ui.md の同項が正。

版番号は**どこにも書いていない**(Cargo.toml が正本)。`Info.plist` は `@VERSION@` を
配布手続きに埋めさせる形だが、`.rc` は焼いた `.res` をコミットしてリンクするので同じ
手が使えず、固定ブロックは 0.0.0.0(`FILEVERSION` を書かない時の `rc.exe` の既定値)。

- 配布物の版表記を決める時に、Windows の `.res` と mac の `Info.plist` を**同じ 1 か所
  から埋める**(`cargo xtask` が候補 — §8 のバンドル手続きと同じ置き場所)
- `FileVersion` / `ProductVersion` の文字列は埋める側と同時に足す(版を 2 か所に書くと
  必ずずれる)

### 12. 2 つ目のプロセスを実機で押した時

ヘッドレスで確かめたのは「ロックが取れなければゲートを出し、ファイルには一切触らない」
まで(`cargo xtask verify-ui solo` = Windows / Ubuntu 両方 PASS)。実機でしか見えないのは 3 つ:

- **ジャンプリストの起動エントリ**を押した時の見え方 — ゲートの窓がどう出るか、
  `Close` で素直に閉じるか
- **mac の `.app`**: Finder / Dock からの 2 回目は OS 自身が既存プロセスを起こすので、
  ここへ来るのは CLI から直に叩いた時だけ。その時の見え方
- **リダイレクトされた `%APPDATA%` / ネットワークホーム**。ロックを訊けなかった側
  (`Claim::Unknown`)は**そのまま起動する**設計なので、転んでも「2 つ立つ」= この機能が
  入る前に戻るだけだが、実際にそう転ぶかは踏んでみないと判らない

### 13. 遅い置き場所でフォルダを選んだ時の無反応

ピッカーが受理してからタブが出るまでの間、画面は何も言わない。手元の実測では
**30〜36ms**(Windows warm・非リポジトリ / bare / 8 階層下の walk-up 各 3 回)なので
1〜2 フレームで済み、この間は無表示と決めた(規約 §リポジトリを開く)。

**測れていないのは応答しない共有ドライブ・スピンダウンしたディスク**で、そこでは
`repo::open` のタイムアウト(10 秒)まで無反応になりうる。実機で測り、必要なら
「N ms 超えたらリングを出す」の N をトークンとして足す(**閾値の新設は人間の承認が
要る** — 今ある `tipDelayMs` / `hoverKeepMs` は hover の語彙)。
なお `path.is_dir()` が先に false を返す経路は多くが `plain` に落ちるため、この窓に
入るのは「ディレクトリとしては見えるが git が answer を返せない」場合だけ。

### 14. Qt のカスタムビルド(床を削る最後の手)

**[P3-確認事項.md](P3-確認事項.md) §app の手(グラフ行の C++ ヒープ)を打ち切った後の、床を削る最後の手。**

### 18. `Restart to apply` の長押しから後継が立つまで(Windows の実窓 1 回)

設定画面で git の実行ファイルを差し替えた後の `Restart to apply`(長押し →
`main::start_again` が同じ exe を spawn)は、**人が 1 度も通していない**。
**ヘッドレスでは原理的に撮れない** —— 押した先で窓が閉じるので絵が無く、運転中の run は
後継を起こさないよう塞いである(塞がないと動詞を再生しながら run の設定ディレクトリを
掴んで親より長生きする)。機械が言えるのは `offers=` / `held=` = **差し出しの条件と
ボタンの姿まで**。

実窓で見るのは 4 つ: 長押しが 500ms で確定するか / 窓が同じタブで戻るか /
帯の版が新しい方になっているか / 設定画面を開き直した時に欄が書いたパスのままか。
**起動時に落ちた側は機械が撮っている**(`settings-git-path stored-missing` = 保管の git が
無い状態で立ち上げ、章が赤で `Nothing to run at that path.` と言い `inUse=` が `PATH` の
先を名乗る。両 OS)ので、残っているのはこの 4 つだけ。

### 19. IntelliJ の Code Provenance を戻す(開発環境)

開発機の IntelliJ(2026.2 系)は Registry `code.provenance.chatter.analytics.enabled`
を **false** にしてある。既定の true では bundled プラグイン "Code Provenance by Qodana"
が `chatter.exe observe` を**開いているプロジェクトごとに約 65 秒間隔**で起動し、起動
1 回につき tree-sitter の native lib を `%TEMP%` へ展開したまま残す(Windows はロード済み
DLL を unlink できないので `deleteOnExit` が黙って失敗する)。**1 日あたり千数百件・
約 1GiB** 積もる。上流は tree-sitter-ng の `NativeUtils.libFile()`、報告は
[QD-16236](https://youtrack.jetbrains.com/issue/QD-16236)(同型の既報は IJPL-254064)。

QD-16236 が解決したら:

1. IntelliJ を対象版へ上げ、`Help | Find Action` → `Registry...` で該当キーを **true** へ戻す
2. 1 時間、`%TEMP%\tree-sitter-ng-lib_*` が増えないことを確認する。**間隔が分単位なので、
   直っていなければ 1 時間で数十件以上出る** —— 出なければ解決
3. 出るなら false に戻し、QD-16236 に実測を添えて差し戻す

false のままで失うのは JetBrains 側へ送る chatter analytics だけで、IDE の provenance 収集
(paste / 補完 / リファクタリング / stash / chat session / MCP tool call のリスナー)は
動き続ける。true へ戻すと `code-provenance\chatter\v1` のローカル記録も再び育つ(数 GiB 規模)。

## 実測済み

### Linux: 素の Ubuntu が実際に要求するもの

正本は <!--cmd:linux.bare-->`cargo xtask linux bare --discover` の DECLARE 行(素の `ubuntu:24.04` に
バイナリと Qt のツリーだけを置き、ローダが名指した 1 件ずつを入れて起動するまでを
機械が測る — [ci/linux/Dockerfile](../ci/linux/Dockerfile) の runtime ステージが
同じリストを持つべき対照)。手作業の実測はこの自動化に上書き済みで、残る結論だけ:

**バイナリ自身が動的リンクするのは 9 件だけ** — `libQt6Core` / `libQt6Gui` /
`libQt6Qml`(同梱が要る)と、素の Ubuntu に最初からある `libc` / `libgcc_s` /
`libm` / `libstdc++`。それ以外の未解決はゼロで、glib も GL も fontconfig も
**Qt の依存**。`libgl1-mesa-dri`(llvmpipe)は offscreen 起動
だけなら不要。

**QML モジュールは `ldd` に映らない** — `Quick` / `QuickControls2` は実行時に dlopen
されるので、`ldd` の結果だけで同梱物を決めると起動してから QML のロードで落ちる。
`QML_IMPORT_PATH` / `QT_PLUGIN_PATH` を Qt のツリーへ向ける必要がある。

**日本語は素の Ubuntu では豆腐になる** — `fc-match 'Noto Sans CJK JP'` も
`fc-match sans:lang=ja` も **DejaVu Sans** に落ちる(CJK グリフを持たない)。
デザイン規約のチェーンが名指しする `Noto Sans CJK JP` は標準では入っていないので、
パッケージが `fonts-noto-cjk` を依存に持つ必要がある(§4 の CI 整備と同じ前提を
利用者側にも立てる話)。

### 17. 基準リポジトリの形をどこまで寄せるか
