# Phase 5(配布準備)確認事項

## 積み(未検証)

### 1. diff プレビューの画像デコーダ範囲

プレビュー(`platitude-core::preview`)が画像扱いする拡張子のうち描画できるかは
実行環境の Qt imageformats プラグイン次第。デコーダが無い形式は
「Preview unavailable」+ サイズ表示に劣化する(壊れない)。
**webp / tif / tiff / avif は劣化表示**。

検証・判断:

- **qtimageformats を配布物に同梱するか(本命)**。プラグイン DLL を置くだけで
  コード変更なしに描画可能。ライセンス確認(libwebp = BSD-3 /
  libtiff = MIT 系)と 3OS の deploy 手順への追加が必要
- **avif**: Qt 標準プラグインが無い。(a) 劣化表示のまま /(b) kimageformats 系の同梱
  (LGPL — 依存ライセンス方針の確認要)/(c) Rust 側デコードして PNG に変換
  (依存が大きく軽量方針と要相談)
- **WebView(Qt WebEngine)フォールバックは非推奨の見込み** — 実体は Chromium 同梱で、
  ネットワークスタック同梱が「ネットワーク非通信」の主張
  ([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))に抵触する

### 2. forge との距離(`gh` を呼ぶか) — **かなり後の判断**

PR バッジの実データ(P4)とリモートブランチの差し替え・削除まわりで「`gh` CLI があれば
済む」場面が出る。決まるまでは git だけ。

- `gh` は外部 CLI なので絶対制約の条文には触れないが、アプリが
  forge へ通信させる点で制約の趣旨としては同じ側
- 判断時に同時に決めること: 未インストール環境での degrade(バッジが出ないだけ)/
  認証(`gh auth` に委譲)/ オフライン job での扱い /
  「ネットワーク非通信」の主張([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
  の書き換え
- 当面の代替: PR バッジは `ls-remote refs/pull`(git 経由)で足りる見込み。残る判断は
  「forge の rename(PR が付いてくる = 本物の改名)まで要るか」だけ

### 3. 配布物への同梱一覧(既知分の集約)

- `pgg-todo-editor.exe` を本体と同じディレクトリへ(rules-refs/core.md の pgg-todo-editor
  項)。**これは `platitude-core` の bin ターゲット**なので `cargo build --release -p platitude-app`
  では作られない — 配布物を組む手順は必ずワークスペース全体をビルドする
- **Qt6Network は Qt6Qml のロード時依存として同梱が必須**(非通信の主張の立て方は
  [実装計画.md](実装計画.md) §11.2)
- imageformats プラグインの選定(§1 の結論)
- **mac / Linux の非通信 baseline**(Windows の [windows-x64.md](../ci/baseline/windows-x64.md) に
  当たる物 —— 本体の import、同梱 Qt の推移的依存、同梱一覧)は CI の初回ビルドで取る
- **syntect / two-face が埋め込む構文定義の著作権表示**。定義は 100 本超で
  それぞれ別ライセンス。two-face の `acknowledgement` モジュールが全文をプログラムから返すので、
  **`cargo xtask` で deny.toml の allow リストと突き合わせて落とす**。Apache-2.0 の定義は
  NOTICE と改変告知が要る(§15 も参照)
- **同梱クレートのうち MIT を選べないものの表示**。SPDX 式が OR なら許可枝に MIT を
  選べるが、AND と単独綴りは選び直せないので、表示と義務の要否をここで決める:
  - `foldhash` = Zlib 単独 / `tree-sitter-elixir` = Apache-2.0 単独(§15-3)。
    **全文同梱・NOTICE・改変告知の要否はライセンスごとに違う**ので個別に決める
  - qtbridge 一族 = `LicenseRef-Qt-Commercial OR LGPL-3.0-only`(LGPL 側。静的リンクの扱いは §14)。
    **`qtbridge-interfaces` は改変版を同梱している**(`vendor/qtbridge-interfaces`):
    改変したソース・改変告知と日付(`PLATITUDE-MODIFIED.md`)・LGPL 本文はリポジトリに在る。
    配布物からそのソースへ辿れる形にする
  - **対象の絞り込みは `cargo tree -e normal,no-proc-macro --target all`** — proc-macro とその依存
    (`proc-macro2` → `unicode-ident` 等)はコンパイラの中で走るだけで本体に入らない。
    `cargo deny list` は build 依存も含み(`codespan-reporting` = Apache-2.0 単独は build 専用で
    再配布しない)、dev 依存は含まない
- **Qt は組んだ版と同じものを同梱する**: qtbridge-runtime 0.3 は Qt の private ヘッダ
  (`QtQml/private/qqmldata_p.h` の `QQmlData`)を読んで組まれるので、private の ABI が
  変わる別のマイナー版の Qt では動く保証が無い(システムの Qt を使う配布形は取れない)。
  qtbridge-runtime はビルド時に `Qt6QuickTest` もリンクするが、本体の import には残らない
  (release の本体が直に読む Qt は Windows も Linux も `Qt6Core` / `Qt6Gui` / `Qt6Qml` だけ —
  exe の dependents / ELF の `NEEDED` で確認)

### 3.5 CI を軽量と完全性に割る(CLAUDE.md の段 2 / 段 3)

**CI は 2 本**。分ける基準は**鳴る頻度** — 毎回の反映に載せるのは
答えが動く検査だけ。

- **軽量 CI(段 2)= 反映のたび**: 3OS の fmt / clippy / test、Linux の
  `cargo xtask linux verify-ui`(触った動詞)、`cargo xtask linux bare`(ネットワーク不要)
- **完全性 CI(段 3)= リリース前と、依存・環境・Qt を触った時**: 上の全部に加えて
  <!--cmd:linux.bare-->`cargo xtask linux bare --discover`(依存リストを素の Ubuntu から導出し直す)、
  `periodic` のテスト(`cargo test --workspace -- --ignored ::periodic::`。
  rules-refs/core.md `periodic`)、完全オフライン job、3OS のスクショ目視、性能実測
- **定期フルテスト = 週 1(未作成)**: 完全性 CI と同じ中身(= <!--call:gate.full-->`gate --all --fresh`)を schedule で回し、日常の段から
  外した物のデグレを拾う —— `periodic` のテストと、段分け表(`crates/xtask/verb-tiers.txt`)が段 3 に回した動詞。
  **`land` の gate は段 2 なのでこれらを回さない**(`gate::for_landing` は `--all` を付けない)

**在る workflow**(正本はファイル): `ci.yml` = 3OS の fmt / clippy / test / `shipped`、`offline-test`、`deny`。`shots.yml` = macOS の撮影(§3.6)。Qt の導入はどちらも `.github/actions/qt` を呼ぶ — 版の正本は `.qt-version` で、action も xtask もそのファイルを読む(workflow は版を持たないので、編集しても gate のステップは 1 つも動かない)。action は全部 commit の SHA で名指してあり、その追従は Dependabot(`.github/dependabot.yml` — 週 1、全 action を 1 本の PR に。crate は対象外)。上の割り方のうち `linux verify-ui` / `linux bare` / `structure` / `periodic` / 週 1 のフルは未作成。

**`cargo xtask structure` は軽量側**。ただし**基準線が縮んだ時にツールが `crates/xtask/structure-baseline.txt` を書き換える**ので、後段に `git diff --exit-code crates/xtask/structure-baseline.txt` を置く — 置かないと「縮んだのに commit されていない」が CI で緑のまま流れる。

**`cargo xtask shipped` は `target/shipped/` に 2 本目の release を組む**。CI では deps をもう 1 度コンパイルする代金が OS ごとに乗るので、軽量側に置くなら `shipped` に profile を選ばせる口(`--profile release`)を作るか、完全性側へ寄せるかを初回 CI の時間で決める。

依存を触った PR(`Cargo.toml` / `ci/linux/Dockerfile` / QML の import が変わった時)では必ず段 3 を回す。

**Windows の Qt は aqtinstall のリリース版では入らない**(6.11 以降はツールチェーンごとのフォルダ
`qt6_<版>/qt6_<版>_msvc2022_64/` に置かれ、3.3.0 は `qt6_<版>/qt6_<版>/Updates.xml` を探して止まる)。
CI は対応(miurahr/aqtinstall#1000)を含む固定コミットを `.github/actions/qt` の `AQT_SOURCE` で入れる。
Linux のコンテナはリリース版のまま(Linux の配置は変わっていない)。

**workflow は机上で書いた物で、1 度も走っていない**。構文・キー・`${{ }}` の式は actionlint で検査してある
(v1.7.12 で 2 本とも指摘なし。composite action の中身と `run:` のシェルは対象外 — shellcheck を積んでいない)。
**xtask が macOS 向けに組めることは机で確かめられる**: `rustup target add aarch64-apple-darwin` の後
`cargo clippy --locked -p xtask --all-targets --target aarch64-apple-darwin -- -D warnings`(check だけなので
リンカも SDK も要らない。xtask の OS 分岐を触ったら撃つ)。core / app は tree-sitter の C と Qt を mac 向けに
組めないので、机では確かめられない。
最初の run で確かめること:

- **許可リストの外への接続が block で止まること、3OS とも**。harden-runner の block は macOS / Windows では
  v2.20.0 から(README の対応表は「Audit mode only」のまま)。漏れは止められた接続として job のログに出る —
  足す先はその job の `allowed-endpoints`。**annotation に `Reverting agent` が出ていないことも見る**(Linux の
  agent は許可したドメインを起動時に解決できないと block ごと外す)
- **Linux の `apt-get update` が、許可リストに無い接続を止められても進むこと**(runner のイメージが足した
  source と apt の hook の分。止められた接続は annotation に出る — 足すか雑音として受けるかを決める)
- **Windows の cargo が証明書の失効確認で止まらないこと**。Windows の cargo は `http.check-revoke` が既定で
  有効で、schannel が CA の CRL / OCSP(:80)へ出る。どれも許可リストに無いので、block が効いていれば
  crate の取得が `0x80092013`(revocation server was offline)で落ちうる。出たら止められたホストを足すか、
  job の env に `CARGO_HTTP_CHECK_REVOKE=false`(`--locked` の checksum は残る)
- **Qt のアーカイブが `master.qt.io` から直に落ちること**。`download.qt.io` はアーカイブを近いミラーへ 302 で
  返す(`--base https://download.qt.io/` は aqt の既定値そのもので、付けても同じ)。ミラーは run ごとに変わり
  許可リストに書けない。チェックサム(`.sha256`)と `Updates.xml` は `download.qt.io` が直に返す
- **macOS のビルドが Qt を読めること**。SIP が有効な機械では、step の `/bin/bash` が立つ所で `DYLD_*` が
  環境から落ちる = `DYLD_FRAMEWORK_PATH` は cargo に届かない。runner で SIP が有効かどうかは机上で確定
  できないので、`.github/actions/qt` はどちらでも効く形(`RUSTFLAGS` で Qt の `lib` を rpath に埋める)にして
  あり、`shots.yml` は `csrutil status` を印字する
- **`pipx run --spec` で固定コミットの aqt が 3OS で入ること**(macOS の runner の Python は PEP 668 で素の
  `pip install` を拒む)
- **`deny` job**: action のコンテナは `rust-toolchain.toml` を見て toolchain を入れる(`static.rust-lang.org`)。
  コンテナ自体のビルド(Docker Hub / Alpine)は harden-runner の step より前に済む前提。**`advisories` を
  回すのはこの job だけ**(机の `cargo xtask deny` は bans / sources / licenses)なので、初回の赤は workflow
  ではなく RustSec の指摘でありうる
- **YAML の anchor**(`&harden` ほか)が job をまたいで展開されること
- **`cargo xtask` が macOS で初めて走る**(`shipped`、`replay` → `verify-ui`)。予算の台帳の錠・プロセスの
  刈り取り・`ps` の読みが mac で答えるか。**xtask 自身のテスト(単体と gate のスイート)と、core / app の
  mac 向けコンパイルもここが初回**
- **macOS の一時ディレクトリは symlink の下に在る**(`/var/folders/…` の `/var` は `/private/var` への symlink で、
  git は辿った後のパスを答える)。渡したパスと git の答えを突き合わせるテスト・動詞がここで割れないか
- **`rust-cache` と Qt のキャッシュが 10GB(リポジトリの上限)に収まること**。`rust-cache` を書くのは main の
  run だけで、鍵には `QMAKE`(= Qt の版)が入る。Qt の cache は導入の直後に書く — job が後で赤くなっても
  次の run は落とし直さない(PR の run は PR のスコープへ書く)
- **Dependabot の PR が `.github/actions/qt` の中の action(`actions/cache/restore` / `save`)も拾い、SHA の隣の
  版コメントも書き換えること**

### 3.6 macOS の撮影(`shots.yml`)— 実機の代わりに CI の runner で撃つ

撃ち方と読み方は verify-ui スキルの mac.md。runner の上で `cargo xtask replay` が verify-ui の行を 1 本ずつ撃ち、
判定は手で撃った run と同じ・絵とログは artifact に残る。

- **写るのは CoreText のフォントと macOS の経路まで**。offscreen の QPA は Apple では CoreText のフォント DB を
  使い(`qoffscreenintegration.cpp`、Qt 6.12)、描画は software scene graph(`RhiBasedRendering` が false)。
  **Cocoa の窓(タイトルバー・ネイティブメニュー・Metal の描画・Dock)は写らない**
- **撃つ行**: main への push = 段分け表の `linux` 行(判定がフォントで決まる行)/ 週 1 = census の全行 /
  dispatch = 名指した行・tier・言語(既定は日本語 — 机とコンテナが日本語の機械なので)。行も tier も
  名指さない dispatch は job ごと skip される
- **週 1 の schedule は、public のリポジトリで 60 日活動が無いと GitHub が止める**(Actions のページから戻す)
- **代金**: リポジトリが public の間、標準 runner(`macos-26` = arm64)は分の課金が無く、artifact と cache の
  保管も無料(cache はリポジトリごと 10GB まで)。**private にすると分で課金され、macOS の分単価は Linux の
  約 10 倍**($0.062 対 $0.006)なので、その時は push と schedule を外して dispatch だけにする。
  larger runner(`-large` / `-xlarge`)は public でも有料 — ラベルは標準のまま
- **席の枝を撃つには、その枝が GitHub に在ることが要る**(dispatch の `--ref`)。main は push 済みならそのまま撃てる

最初の run で確かめること:

- offscreen の run が macOS で絵を出すこと(`screenshot saved=true`。Windows と同じ software の経路)
- `defaults write -g AppleLanguages` / `AppleLocale` が runner のセッションで Qt に届くこと — 日本語の run と
  英語の run で `—` `…` の字形か等幅の和文フォールバックが変わるか(§5 / §20 はこの 2 本の絵で読める)
- `linux` 行の判定(幅・切れ・段)が Hiragino Sans / Menlo で通ること。赤は絵で分ける —「mac で実際に切れている」
  か「判定の閾がフォントに依っている」か
- 週 1 の全行が Replay の天井(270 分。job は 300 分)に収まること。越えた run も、そこまでの絵とログは
  artifact に残る(`summary.md` は replay が最後に書くので出ない — 行ごとの `ok` / `FAIL` は step のログ)。
  切れた時に撃っていた 1 行の絵とログは書きかけでありうる(step の天井が止めるのは起点のシェルで、
  その子は job の終わりまで残りうる)

**実ウィンドウの撮影は未作成**。runner のイメージは bash からの画面収録を許可済み(`screencapture` が撃てる —
actions/runner-images の TCC 設定)で、足りないのはハーネスの側: 絵を保存した後も窓を立てたまま待つ駅と、
そこで外から撮る口。§8(Dock のアイコン)・§22(アプリメニュー)を CI で見るにはこれが要る。

### 4. CI のフォント整備(スクショに日本語を出す)

判定基準は demo `basic` の日本語コミット
(`docs: 利用案内の骨子を日本語で直す`)が 3OS の PNG で**日本語字形**
(直 / 骨 の字形で見分ける)で写ること。

- **ubuntu job**: `fonts-noto-cjk`(+ `fonts-dejavu-core`)を明示インストール。

### 6. 最低 git バージョンの実バイナリでのスモーク

マニュアル照合は [git最低バージョン整合.md](git最低バージョン整合.md)。残るは
最低バージョンの実バイナリで一巡すること:

- 最低バージョンの git(= Ubuntu 24.04 の apt 標準)で `cargo test --workspace` と
  PGG_AUTO_ACT スモークを回す。**GitHub の `ubuntu-24.04` runner が積む git は apt 標準ではない**
  (git-core の PPA 版 — イメージの一覧で 2.55 系)ので、`ci.yml` の Linux job は最低版を踏んでいない。
  CI で踏むなら job の中で [ci/linux/Dockerfile](../ci/linux/Dockerfile) のイメージを組んで回す —
  harden-runner は `container:` の job では動かないので、VM の上から docker を撃つ形になる
- 特に見るもの: `cherry-pick --no-edit`(個別マニュアル外 — gitcli の `--no-`
  一般規定でカバーしている 1 件)と、`switch` / `restore`(2.43 時点 EXPERIMENTAL
  表記)の挙動一致

### 7. 引いたフラグのダッシュが他 OS の等幅で釣り合うか

`push -f` のダッシュはトークン長の罫で引いてある(規約 §git 用語のコード表記)。
実測できているのは Cascadia Mono(Windows)だけ。

- macOS(Menlo)/ Ubuntu(DejaVu Sans Mono / Noto Sans Mono)の実機で `push -f` と
  後ろの `!` の間合いを目視する
- ズレていた場合も**トークン 1 つで釣り合う長さを選び直す**(family ごとの分岐は
  3 OS ぶんの微調整を抱える)

### 8. アプリアイコンの mac / Linux 側

動いているのは Windows だけで、mac / Linux は資産と定義が置いてあるだけ(置き場所は
[デザイン規約.md](デザイン規約.md) §アプリアイコン)。

焼き直しは手作業(手順は `platitude.rc` のコメントと
[.claude/rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md))。**大きいサイズを焼く時の
罠**: 128px 以上をブラウザのヘッドレスで撮る場合、`--window-size` にそのまま渡すと
最小ウィンドウ幅にクランプされて図の一部しか写らない。広いビューポートで描いて左上を
切り出す。

残るのは実機と、決めていない 2 つ:

- **bundle identifier が未定**(`@BUNDLE_ID@`)。署名と quarantine の記録が
  これを鍵にするので notarize より前に確定させる

### 19. IntelliJ の Code Provenance を戻す(開発環境)

開発機の IntelliJ(2026.2 系)は Registry `code.provenance.chatter.analytics.enabled`
を **false** にしてある。既定の true では bundled プラグイン "Code Provenance by Qodana"
が `chatter.exe observe` を約 65 秒間隔で起動し、起動 1 回につき tree-sitter の native lib を
`%TEMP%` へ展開したまま残す。報告は [QD-16236](https://youtrack.jetbrains.com/issue/QD-16236)。

QD-16236 が解決したら:

1. IntelliJ を対象版へ上げ、`Help | Find Action` → `Registry...` で該当キーを **true** へ戻す
2. 1 時間、`%TEMP%\tree-sitter-ng-lib_*` が増えないことを確認する(直っていなければ 1 時間で数十件以上出る)
3. 出るなら false に戻し、QD-16236 に実測を添えて差し戻す

false のままで失うのは JetBrains 側へ送る chatter analytics だけ。true へ戻すと
`code-provenance\chatter\v1` のローカル記録も再び育つ(数 GiB 規模)。

### 20. 英文中の `—` `…` の字形(macOS の JP ロケール実機)

Qt は shaping の言語を `QLocale()`(= OS のロケール)から HarfBuzz へ渡す
(`qtextengine.cpp`、Qt 6.12)。日本語フォントがロケールで持ち替える字形が、英文に続く
`—` `…` に出うる —— 和文字形は全角のダッシュ・中央の三点で、`—` が両 OS で同じ長さ・
同じ位置という据え置き(デザイン規約 §寸法「字で出ていた記号は 5 種」)から外れる。

- Windows: `Yu Gothic UI` は JP ロケールでも欧文字形(実測。ヘッドレスの `Noto Sans JP`
  だけが和文字形になる — verify-ui スキル windows.md)
- Ubuntu: 言語の出所は Qt の版によらず LANG(Qt が起動時に `setlocale(LC_ALL, "")` を
  呼び、HarfBuzz の既定言語もそれを読む)。**日本語デスクトップ(`ja_JP.UTF-8`)では和文字形**
  (実測。検証のコンテナも同じ LANG で、Linux の絵は和文字形)。幅の差は 1px 前後でレイアウトは崩れない
- **直すのはレイアウトが崩れる時と、全く違う表現に見える時だけ**(ユーザー決定 2026-10-02)——
  和文字形の `…` `—` そのものはアプリが上書きしない
- **macOS が未実測** —— Finder から立てた GUI には LANG が無く、`QLocale()` は
  システム設定の言語を答える。JP ロケールの実機で設定画面の説明文の `—` と、
  グラフのチップの省略の `…` を `Hiragino Sans` で目視し、上の 2 つに当たるかだけを見る。
  実機が無い間は `shots.yml` の日本語の run の絵で読む(§3.6 — runner の言語設定が Qt に届くかは同節の確認事項)
- **CI の絵は bundle でない素のバイナリの答え** —— macOS はアプリのロケールの言語を、ユーザーの言語と
  bundle が宣言する言語の突き合わせで決める。[Info.plist](../packaging/macos/Info.plist) が宣言するのは
  `CFBundleDevelopmentRegion = en` だけ(`CFBundleLocalizations` / `CFBundleAllowMixedLocalizations` は無い)
  なので、出荷する `.app` は日本語の Mac でも英語のロケールで立ちうる = runner の日本語の run とは shaping の
  言語が違いうる。どのロケールで立ったかは `QT_LOGGING_RULES=qt.core.locale.debug=true` で起動時に出る
  (`qlocale_mac.mm` — ロケール・優先言語・bundle の宣言が並ぶ)。`.app` を組んだ時にこれで確かめ、上の
  目視はその条件で読む

### 21. macOS の `cargo xtask linux`(docker の経路)

エンジンは Windows が WSL の wslc、Linux はコンテナ無し、**macOS は docker のまま**(`linux::engine`)。

`exec`・`rm --force`)は docker で通していない。mac の実機で `cargo xtask linux test -p platitude-core` と、
Linux 側を持つ `cargo xtask gate` を 1 回ずつ
