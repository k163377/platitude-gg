# Phase 5(配布準備)確認事項

配布準備期に検証・判断する項目を先行して積む場所。
P3 分は [P3-確認事項.md](P3-確認事項.md)。

## 積み(未検証)

### 1. diff プレビューの画像デコーダ範囲

プレビュー(`platitude-core::preview`)が画像扱いする拡張子のうち、実際に
描画できるかは実行環境の Qt imageformats プラグイン次第。デコーダが無い
形式は「Preview unavailable」+ サイズ表示に劣化する(壊れない)。
開発環境の Qt には qgif / qico / qjpeg / qsvg のみ同梱で、png / bmp は
Qt 本体組み込み。**webp / tif / tiff / avif は劣化表示**。

検証・判断:

- **qtimageformats を配布物に同梱するか(本命)**。webp / tiff の
  プラグイン DLL を置くだけで、アプリ側のコード変更なしに描画可能になる。
  サイズは数百 KB 級。ライセンス確認(libwebp = BSD-3 / libtiff = MIT 系)と
  3OS の deploy 手順(windeployqt / macdeployqt / Ubuntu tar.gz)への
  追加が必要
- **avif**: Qt 標準プラグインが無い。候補は
  (a) 劣化表示のまま、
  (b) kimageformats 系プラグインの同梱(LGPL — 依存ライセンス方針の確認要)、
  (c) Rust 側デコードして PNG に変換(依存が大きく軽量方針と要相談)
- **WebView(Qt WebEngine)フォールバックは非推奨の見込み**。
  Windows の Qt WebView は実体が WebEngine(Chromium 同梱)。data URL を
  渡せば webp / avif も描けるが、配布 +150MB 級・別プロセスのメモリ・
  Chromium のネットワークスタック同梱で、軽量目標 / メモリ予算 300MB /
  「ネットワーク非通信」の主張([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
  に同時に抵触する。採用するならこれら全部の再検討が前提

### 2. forge との距離(`gh` を呼ぶか) — **かなり後の判断**

PR バッジの実データ(P4)とリモートブランチの改名・削除まわりで、
「`gh` CLI があれば済む」場面が出る。判断はずっと後で構わないが、決めるまでは
**呼ばない**。

- 絶対制約は「ネットワーク通信は git コマンド経由のみ」「forge API のクレートを
  入れない」。`gh` は**クレートではなく外部 CLI** なので条文には触れないが、
  **アプリが forge へ通信させることに変わりはない**ので、制約の趣旨としては同じ側
- 判断するなら同時に決めること: 未インストール環境での degrade(バッジが出ないだけ)/
  認証(`gh auth` に委譲。アプリはトークンを受け取らない)/ オフライン job での扱い /
  「ネットワーク非通信」の主張([ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))
  の書き換え
- 当面の代替: PR バッジは `ls-remote refs/pull`(git 経由)で足りる見込み。
  リモートブランチの改名・削除は git だけで済んでいる(push の合成と `push --delete` —
  デザイン規約 §リモートブランチの改名 / §リモートブランチを消す)。残る判断は
  「forge の rename(PR が付いてくる)まで要るか」だけ

### 4. CI のフォント整備(スクショに日本語を出す)

CI は未整備のため、整備時にジョブへ折り込む(2026-08-08 決定)。判定基準は
demo `basic` の日本語コミット(`docs: 利用案内の骨子を日本語で直す`)が
3OS の PNG で**日本語字形**(直 / 骨 が中国語字形でない)で写ること。

- **ubuntu job**: `fonts-noto-cjk`(+ `fonts-dejavu-core`)を明示インストール —
  ランナーイメージの偶然に依存しない。あわせて「Ubuntu デスクトップは
  fonts-noto-cjk 標準搭載」というチェーンの前提を `fc-list` で実証する
- **windows job**: offscreen の FONTDIR は .ttc を読まない(verify-ui スキル)ため、
  Windows 標準の日本語フォントは全て使えない。**TTF の日本語フォント
  (例: Noto Sans JP)を CI 環境の FONTDIR に用意する** — CI 環境の話であり、
  利用者の環境には何も入れない
- **macos job**: offscreen でも CoreText のフォント DB なので追加不要の見込み。
  Hiragino Sans が写ることの確認のみ

### 5. 非 JP ロケール機での等幅フォールバック実測

等幅(diff 本文・コマンドログ)内の日本語だけは named family が和文を持たず
(Windows / macOS。デザイン規約 §タイポグラフィ)、OS のロケール依存フォールバックに
残っている。JP ロケール機では JP 字形になるが、**非 JP ロケールの Windows / macOS の
実ウィンドウでどの字形になるかは未実測**(offscreen では測れない — フォント DB が違う)。

- EN ロケールの VM で実ウィンドウ起動し、日本語入り diff の字形を目視する
- 中国語字形が出るなら対策を判断: JP 等幅サブセットの exe 埋め込み
  (qrc + `FontLoader`。**利用者環境にインストールはしない**)が第一候補。
  フォントのライセンスは OFL 系が主で、現行の依存ライセンス方針(MIT / Apache 系)の
  対象外につき人間の承認が要る

### 7. 引いたフラグのダッシュが他 OS の等幅で釣り合うか

`push -f` のダッシュはトークン長の罫で引いてある(規約 §git 用語のコード表記)。
**罫の長さは固定で、周りの字幅は OS が解決した等幅 family 次第**なので、
字が広い family では短く、狭ければ長く見えうる。実測できているのは
Cascadia Mono(Windows)だけ。

- macOS(Menlo)/ Ubuntu(DejaVu Sans Mono / Noto Sans Mono)の実機で
  `push -f` と、その後ろに立つ `!` の間合いを目視する
- ズレていた場合、罫の長さを family で分岐させない —— 分岐は 3 OS ぶんの
  微調整を抱えることになる。トークン 1 つで釣り合う長さを選び直す

### 8. アプリアイコンの配布物と OS ごとの外形

意匠と色は確定済み(規約 §アプリアイコン)。残るのは**ラスタライズと外形**で、
どちらも実機が要る。原本は `crates/platitude-app/assets/` の SVG 2 本。

- **どのサイズにどちらの SVG を焼くか**は規約が決めている(24px 境界)。`.ico` も
  `.icns` もサイズごとに別の絵を持てる形式なので、**16 / 20 / 24 は小サイズ版を
  焼く**。単一サイズから縮小させない
- **ラスタライズ手段の判断**: (a) 生成済みの `.ico` / `.icns` / PNG をリポジトリへ
  コミットして依存ゼロを保つ / (b) `cargo xtask` に SVG レンダラ(resvg 系。
  MIT / Apache-2.0 でライセンスは通る)を足して再生成可能にする。**軽量が目標**なので
  既定は (a) 寄り。ただし色を直す度に手作業が要る点と引き換え
- **macOS の外形**: Big Sur 以降の Dock はアイコンが角丸正方形に揃うため、規約の
  角丸タイルはそのまま使えるはず。ただし Apple は 1024 の canvas に対して実描画領域を
  一回り小さく取る慣習があり、そのまま焼くと**隣のアイコンより大きく見える**。実機で
  Dock に並べて確認する
- **Linux**: hicolor テーマの各サイズ PNG と、`.desktop` の `Icon=` をスラグ
  (`platitude-gg`)で合わせる。Qt の `application_name` も既にスラグなので
  (規約 §用語 のアプリ名)、`.desktop` 側で綴りを分ける必要は無い
- **ウィンドウアイコン(Qt 側)は配布物とは別**。タスクバーのウィンドウが持つ絵で、
  qrc へ入れて起動時に設定する。こちらは実機なしで確認できるので Phase 5 を待たない
