# Codex の入力量と実行往復を抑える運用

Claude を主環境とし、規約・検証器・座席 allocator の正本を共有する。
Codex 固有の差はルートの `AGENTS.md` と `.codex/config.toml` に閉じる。
この文書は運用の調査・変更時だけ読む。全タスクの開始時にはロードしない。

## 2026-09-10 の観測

本体 `b5340916`、ローカル Codex 設定、2026-09-08〜10 のセッション記録を確認。
Claude の直近関連セッション `96514a2f-bba3-40bb-85f8-c15a2f9b61f7` の最終報告と
現在の規約を照合した。既存の関連作業を同じセッションで完結する運用は維持する。

Codex のユーザー設定は Astra / reasoning effort `high` / service tier `default`。
プロジェクトには Codex 用 `AGENTS.md` / `.codex/config.toml` がなかった。
Claude の hooks は `.claude/settings.json` にあるが、その登録は Codex での実行を
意味しない。今回の座席取得失敗も、この実行環境の差を見落としたものだった。

### 記録に現れたコスト

下表は Astra の親タスク3件の **最後に記録された累積値**。単発リクエストの値でも
5時間枠の請求値でもなく、キャッシュ入力は入力の内数、推論出力は出力の内数。

| タスクID | 入力 | うちキャッシュ | 出力 | うち推論 | ツール呼び出し |
|---|---:|---:|---:|---:|---:|
| `01a0802e-9724-78c2-afd0-fc3ba0bf91eb` | 10,986,294 | 9,901,440 | 37,133 | 13,359 | 81 |
| `01a08687-56e7-71c2-ac44-a0dd6ee13060` | 10,763,416 | 9,762,048 | 36,136 | 9,860 | 75 |
| `01a07daf-4937-75a0-88e9-a838a577fddf` | 2,734,988 | 2,599,808 | 15,153 | 3,742 | 25 |

入力のキャッシュ比率は約90.1% / 90.7% / 95.1%。「約1,100万」をすべて新規入力と
扱うのは誤り。反対に、キャッシュが多いから長い文脈の往復が無料とも扱わない。
2件目の最後の使用量が増えた記録は79件、各 `last_token_usage.input_tokens` の平均は
約136,246、最大228,512。ツール結果を読む往復で大きな文脈が繰り返し使われている。
最初の入力も3件とも約27,000トークンあり、ツール・アプリ・共通指示などを含む開始時の
固定負担がある。ただしこの数字だけから各指示やプラグインの寄与は分離できない。

1件目には累積カウンタの減少が1回あり、2件目にはない。したがってタスク間の累積値を
無条件で足した「期間総使用量」は作らない。先頭2件には compacted 記録が各1回ある。
両者の対象箇所や作業内容は異なり、high/medium/xhigh の比較実験ではない。

先頭2件のツール出力には、明示的な切り詰め通知が27/81件、23/75件あった。
画像を除くtext/input_text部分は合計964,878文字、627,591文字。文字数はトークン数に
換算していない。単に返答を短くするより、こうした大きな読み込みを絞る余地がある。

採取方法: ローカル `.codex/sessions/2026/09/{08,09,10}` の JSONL を読み、プロジェクト
cwd と `turn_context.model` を確認。`event_msg/token_count/info` の最後の
`total_token_usage` を採用した。推論を output に再加算せず、cached を input に再加算
しない。親と guardian の記録は別扱い。本調査中のタスクは表から除外した。
実測の input/output 内訳がなく total だけの履歴もあり、それらはモデル別比較から除外。
`token_count` は同じ使用量を再通知することがあるので、イベント数をリクエスト数に
読み替えない。画像の base64 を含む JSON の文字数もテキストトークン数にはしない。

### 増幅要因と対策

1. **大きい入力 × ツール往復**。ソース・差分・規約のまとめ読みと切れた出力が実際に
   ある。まずパスと識別子を検索し、必要な範囲だけ読む。独立した読み取りをまとめても、
   合計出力が大きければ逆効果。出力上限は「見なかった部分を無視してよい」という意味
   ではなく、次の検索を狭める合図にする。
2. **Claude の文脈を再構築するコスト**。catch-up 自体は必要だが、履歴を丸ごと読むと
   過去のツール結果まで再投入する。関連する最近の1セッションから user/assistant の
   テキストを抽出し、未解決の判断がある場合だけ広げる。現在の Git を最終的な根拠にする。
3. **常時指示と参照文書の混同**。観測時の `CLAUDE.md` は12,704 bytes、
   `.claude/rules-refs/app-ui.md` は513,324 bytes、同 `core.md` は94,617 bytes、
   verify-ui の `SKILL.md` は46,723 bytes、`verbs.md` は304,131 bytes。
   bytes はトークン数ではない。既存の「正本を分割し、各論を検索する」設計を活かし、
   Codex 側で全文ロードを追加しない。適用対象の rules と必須の手順は省略しない。
4. **高い推論設定**。high は調査・並行性・設計の難問では有用だが、定型確認まで同じ
   設定にすると追加コストの候補になる。今回の記録だけで推論設定の因果効果は断定できない。
   文脈と往復を減らした上で medium を比較する。モデル/effort の設定は今回変更しない。
5. **待ち・再検証・認可失敗の往復**。gate の終了を元のハンドルで待ち、変化のない
   tail/status の往復を避ける。既存の gate の選択とキャッシュを使い、合格済みの検証を
   理由なく増やさない。座席ID欠落による失敗は取得前に防ぐ。品質条件は下げない。

5時間枠は生トークン合計だけでは説明できない。公式にはモデル、タスクの規模、文脈、
推論、ツール、検索、キャッシュが影響するとされる。個別タスクの枠消費への正確な換算式は
今回確認できていない。API価格や Enterprise の credits 単価を Plus の枠に換算しない。
公式の Plus の目安にも Astra は5〜45、Terra は25〜200 local messages / 5 hours と
幅がある。これは固定メッセージ上限でも今回の作業の予測でもない。
[OpenAI: Pricing](https://learn.chatgpt.com/docs/pricing)

## 追加したハーネスと有効化

- `AGENTS.md`: Claude規約への入口、対象別の読み込み、短いcatch-up、座席IDのbridge、
  範囲を絞った出力、待機・検証・引継ぎの運用を定める。Claude側のファイルは編集しない。
- `.codex/config.toml`: `tool_output_token_limit = 4000` のみ。履歴に保持する個々の
  ツール結果を制限する設定であり、推論量・総トークン・利用枠を制限する設定ではない。
  大きい診断は完全なログを残し、必要部分を分けて取得する。

プロジェクトを信頼した状態で、その checkout から新しく開始した Codex で確認する。
既に開始済みのタスクや、mainへ反映していない別worktreeには自動適用されたと扱わない。
ルートの `AGENTS.md` は起動時の指示探索対象。設定の上位レイヤーに上書きがあれば
そちらが優先される。アプリが保持するモデル/effortは、この設定では変えない。
[OpenAI: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、
[OpenAI: Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)

信頼済みプロジェクトの設定と優先順位は
[OpenAI: Config basics](https://learn.chatgpt.com/docs/config-file/config-basic) を参照する。

指示の自動ロードは、次の通常タスクの冒頭で適用元を確認する。利用枠を消費する確認専用の
モデル呼び出しを何度も追加しない。静的な文書検査や gate PASS は、実際のアプリでの
設定ロード・行動改善・利用枠削減の証明ではない。

## 座席の「空席なし」を繰り返さない

`seats::Identity::current` は `CLAUDE_CODE_SESSION_ID` / `CLAUDE_PID` を読み、
`CODEX_THREAD_ID` を読まない。両方空だと理由が `claude-seat ` だけのロックを作り、
`standing` / `wrote_it` が自分の所有と認識できない。`claim_existing` は None を返し、
最終的に `assign` の一般的な「空席なし」メッセージになる。権限昇格だけでは直らない。

今回、Codex IDを渡さないままsandbox外で再実行し、e/fに無名ロックを残した。
実行前後の記録・ロック内容・更新時刻でこの呼び出しの副作用を特定し、eの新規ロックを
戻し、fの元の理由を復元した。その後 `CLAUDE_CODE_SESSION_ID = CODEX_THREAD_ID` を
その呼び出し内だけに設定すると、引数なしの allocator がeを正常に返した。
もともとあった他の無名ロックには触れていない。

**予防は失敗後のunlockではなく、取得前のidentity bridge**。IDがない場合は呼ばない。
各shellは環境変数を引き継ぐとは限らないため、必要な呼び出しごとにbridgeする。
共有アプリPIDや短命なshell PIDを所有者にしない。session IDだけのclaimには終了時の
生存判定がないので、landしない終了時は同じIDで <!--cmd:seat.release-->`cargo xtask seat release` を行う。
未マージのcommit/dirtyはallocatorが引き続き保護する。

## 既存ファイルの変更提案（未実施）

優先度が最も高いのは `crates/xtask/src/seats.rs` の改善。

- `Identity::current`: 明示的なhook session ID、Claudeのsession ID、Codexのtask IDを
  空文字を除いて解決する。既存Claude動作を維持し、所有者が解決できなければ最初の
  lock以前に具体的なエラーで止める。
- `lock_or_read` / `claim_existing` / `assign`: 全席使用中、所有者欠落、Git実行失敗、
  権限不足を区別する。無名ロックを残して次の席へ進む経路をなくす。
- 対応テストは一時Gitリポジトリで「IDなしなら副作用ゼロ」「Codex IDで取得し再取得が
  同じ席」「他タスク/Claude/手動lockは保護」「Git失敗の診断」を確認する。
  この修正ならプロンプトを読み忘れても誤動作を防げる。今回は既存編集の許可前なので
  adapterによる予防までとし、Rustは変更しない。

Codexユーザー設定の `model_reasoning_effort = "high"` は、普段の限定的な作業で
`medium` を試す候補。難しいレビューなどはhighを維持する。Astraを使う選択自体は尊重し、
モデルを自動変更しない。別モデルとの比較は必要なら同種の限定タスクで行う。

Claudeの規約を削る、共通の検証を緩める、sandbox/承認を無効化する変更は提案しない。
プラグインの常時定義も入力負担の候補だが、今回の記録だけで寄与を定量分離できないので
一括無効化はしない。

## 効果の確認

次の通常作業で、同程度の変更規模・同じモデル/effortについて、初回入力、非キャッシュ
入力、出力（推論は内数）、ツール往復、切れた出力の再読回数、完了までの時間、検証結果を
比較する。枠の使用率を比較するなら前後の reset 時刻と他タスクの同時利用も記録する。
利用枠のための改善で別のベンチマークを大量に走らせない。

合格条件は、必要な規約・Claudeの最新判断・検証結果を保ち、余分な再読/往復が減ること。
4000の上限で必要な診断の回収が増えるなら、範囲の切り方と上限を再検討する。
削減率と5時間枠の延命率は導入後の比較まで未検証とする。
