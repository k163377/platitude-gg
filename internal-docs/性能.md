# 性能 — 予算・設計規則・計測・記録

**性能に影響を与える変更**(UI 操作の経路・読み込み・常駐データ・描画・起動・画面表示中の読み込み)**の前に読む**。予算と設計規則はここが正本、予算に対する数字の正本は記録 [perf-windows-x64.md](../ci/baseline/perf-windows-x64.md)(本書は撃ち方と記録の置き方)。**Claudeクラウドでは計測しない**([クラウドセッション.md](クラウドセッション.md))。

## 予算

`JetBrains/kotlin` 級(10万コミット超・refs 5 万本、うちタグ 4.5 万)で: 起動→グラフ初回表示 3 秒以内 / 操作応答 100ms / スクロール 60fps / メモリ 300MB 以下。

- 指標ごとに何を測って何で判定するか(操作フィードバック・重い diff と git の書き込み・子の git・長時間使用)は [メモリと操作応答の改善計画.md](メモリと操作応答の改善計画.md) §2
- **メモリは net で読む**(§計測の各論「perf の判定行は net で読む」)。report の MB は実質 MiB(同 改善計画)

## 設計規則

- **UI 操作の経路の同期処理はコミット数・refs の本数から独立** — 遅延読み込みと差分更新が基本
- **ref 同士の突き合わせは索引を 1 本作ってから回す**(`session::RefJoins` / `refs::RemoteBranches`)
- 常駐データの持ち方(`crate::Name`・平らな索引・確保の個数・mimalloc 不採用)は [rules-refs/core.md](../.claude/rules-refs/core.md) §セッション・実装の決定事項
- 形を選ぶ前に支配項を読む — プロセス起動ほかの代金は [code-costs](../ci/baseline/code-costs-windows-x64.md)
- 未着手の非同期化の候補は [非同期化の候補.md](非同期化の候補.md)

## 計測

**いつ**: 段 3(リリース前と依存・環境を触った時 — gate スキル)で記録 §判定 を撃ち直す。それ以外は変更の効果を確かめる時に A/B で撃つ(§cacheとA/B)。**実窓を使うので、席から撃つのはユーザーが明示した時だけ**(`PGG_ALLOW_GUI=1` — CLAUDE.md §ビルド・テスト)。

**判定の 4 行を撃ち直す 2 行**(コーパスの形・座り・画面の条件は記録 §計測条件):

```
cargo xtask corpus
PGG_ALLOW_GUI=1 cargo xtask perf --at <測る commit> --repo <上の 1 行が印刷した path> --runs 5
```

### ケース

連続するケースは周回境界も含めて異なるOIDにする。同じ行の再クリックは改名などの
別ジェスチャーになる。

`--cases <file.tsv>` はヘッダー無しの4列: `name<TAB>full-oid<TAB>path<TAB>completion`。
空行と `#` 行は無視する。nameは英数字・`-`・`_`、OIDは完全長、pathはそのコミットの変更
ファイル一覧に載るパス。completionは `raw` または `coloured`。一覧の順に選択・diffを開き、
`--cycles N` でN周する。反復には異なるOIDが2つ以上必要。

```
cargo xtask perf --repo <corpus> --cases <cases.tsv> --cycles 50 --runs 5
cargo xtask perf --repo <corpus> --cases <scroll-cases.tsv> --diff-scroll --runs 5
cargo xtask perf --repo <corpus> --select-oid <full-oid> --file <path> --completion coloured --runs 5
```

合否はケースごとに判断する。プロセス内反復と別プロセスのrunは別の軸。

通常の変更、多数ファイル変更、小さい変更を含む大きなソース、長いdiffを固定ケースにする。
画像・非対応言語は `raw` として別ケースにする。`coloured` は最終 `DiffModel.coloured` が
立つ対象専用。時間切れは失敗のまま記録する。rawが測るのは画像デコード前まで。

`perf_diff_frame` は対象diffの初回表示、`perf_colour_frame` は同じfingerprintの最終色付けが
反映されたフレーム。
`--diff-scroll` は各操作で可視diffを2秒スクロールし、正の移動量と終了後の可視行を要求する。
短くoverflowのないdiffは失敗なのでスクロール用一覧は分ける。グラフの12秒計測とは別系列。
反復と併用する時は、全操作の計測時間を含む `--watchdog-ms` を指定する。

### cacheとA/B

- `--cache warm` が既定。同じ経路の捨てrunで温める。
- `--cache first --runs 1` は、このinvocationの最初のプロセス。OS cacheの状態は
  別に確かめる。
- `--cache cold --cold-prepare <executable>` は利用者指定のOS固有プログラムを各run直前に
  実行する。repositoryと測定binaryの2引数を渡し、成功終了を準備完了とする。
  準備失敗・期限超過は測定失敗。
  プログラムがどのcacheをどう冷却したかを記録に併記する。成功終了が示すのは準備が
  走ったことだけ。

```
cargo xtask perf --repo <corpus> --at <A> --compare <B> --runs 3 --cases <cases.tsv>
```

A/Bの `--runs` はABBAブロック数。3なら各6回。
画面・Hz・renderer・features・corpus・GPUの記録が変われば比較を中止する。古いcommitが新しい
計測口を持たない場合、要求したケースや色付けの証跡欠落を失敗とする。

### 短いメモリ峰

100msのWorkingSet最大とは別にWindowsの `PeakWorkingSet64`、Linuxの `VmHWM` を
`memory.csv` の `os_peak_working_set_bytes` に記録する。OSが保持するプロセス寿命中の
最大常駐量で、サンプル間の短い峰を検出する。
private commitの峰・割当回数・発生時刻は分からないので、
差が問題になる場合は別の診断runでOSの割当トレースを採る。帰属取得の計測負荷は別runへ
置き、OS最大は素の値で記録する。

### workload別の比較

`cargo xtask corpus --against <reference>` は以下を別profileとして出力する。
プロファイルは軸ごとに独立して読む。

| profile | 入力 | 対応する性能 |
|---|---|---|
| startup/status | 追跡数・directory・index・無視ファイル・git設定 | 起動・status完了 |
| refs | refs数・注釈タグ比・remote階層 | refs読込・ナビゲーション |
| graph/scroll | lane幅・chip数・文字量・フォールバック | frame分布・停止・常駐量 |
| diff | 変更数・ソースサイズ各分位・言語・変更量 | raw/coloured完了・diff scroll |

### OS別の証跡

既定の出力先は `target/perf/<os>-<arch>/<run>/`。
Windowsの正本は [perf-windows-x64.md](../ci/baseline/perf-windows-x64.md)。Linux と macOS arm64 は実機待ちで、取る物と残す物は
[P5-確認事項.md](P5-確認事項.md) §23。

### 計測の各論

撃つ人・記録を読む人が知っておくことだけ。仕組みと罠は各モジュールのコメント(`perf::sampler` / `perf::measure` / `perf::display` / `perf::corpus` / `perf::rig` / `perf::fonts` / `xtask::still`)。画面の名前(Qt の `ScreenInfo.name` は OS の `DISPLAYn` と一致しない)は `perf::sampler` の `Sample::display`、詳細フレーム列の時刻(到着時刻でなく各行の `clock_ms` を読む)は `harness::perf_probe` の `end_scroll`、画面を invocation の間ずっと起こしておく仕組み(`away_ms` が答えるもの)は `perf::sampler::keep_awake`。

- **性能計測は機械の状態も測って、駄目な run は落として撮り直す**: 落とす条件(ロック / セキュアデスクトップ・最小化・落ち着いた後の画面移動・配信フレームが画面の Hz の半分未満・ベンチが 30 秒で終わらない・対象以外が機械の 35% 超)・撮り直し(`--retries` 既定 3、被さりは 2 度で諦める)・捨て run の省略は `perf::sampler`(`Conditions::complaint`)・`perf::measure`(`Spoiled`)・`perf::warmth`。対象プロセスの CPU は job object で子孫の git まで込み。`--allow-noisy` は全部の関門を開く。CPU の閾は「並行ビルドが居る」を捕るためで、ブラウザや IDE が開いている程度(24 スレッドで 11〜32%)では落とさない
- **表示に依らず測るのは `perf --software`**: software scene graph は画面の点灯・消灯に依らず完走する(点灯前提の D3D run は 1 tick の消灯で落ちる)。**読めるのはメモリだけ**: software の WorkingSet は D3D の床が無い別の量なので、同じ commit の D3D 値と並べて読む。frame gate は効かせず、ロック・被さり・CPU の閾は効く(仕組みは `perf::options` の `software`・`perf::measure`)
- **窓は名前の付いた画面へ固定する**(`--screen`): **どの画面に出たかが fps をそのまま決める**ので、fps は画面の Hz に対する割合で読み、`over_16_ms` を「どの Hz でも同じ問い」として読む(置き方は `perf::artifacts` / `perf::display`)
- **ベンチマークリポジトリは `HEAD` では固定できない** — 測るのは `cargo xtask corpus` が生成する合成リポジトリで、**本体 checkout 直下の gitignore 済み `.pgg-perf-corpus/` に 1 つ**(理由と token の取り方は `xtask::corpus` / `perf::corpus`)。記録を取り直す時は記録の token を `--corpus` へ渡す。**kotlin との距離は `cargo xtask corpus` と `cargo xtask corpus --against <repo>` が同じ実装で両列を出す** — 正本は [perf-windows-x64.md](../ci/baseline/perf-windows-x64.md) §コーパスと kotlin の距離。**形を変えると token が変わり判定表ごと撮り直し**になる
- **計測したビルドを名乗らせる**: manifest の `features=` が何を頼んだかを持つ。`perf --shipped` は出荷ビルド(feature 無し)を測る — 答えられるのは**メモリと `graph stream finished` までの時間だけ**で、リポジトリは `state.toml` の `[tabs]` から開く(出荷ビルドに引数の口は無い)
- **計測は計測台(rig)で撃つ — `cargo xtask perf --at <rev>`**: roster 外の worktree `.claude/worktrees/rig`(`seats::RIG`)に名指しの commit を載せて release ビルドし、exe を commit 単位で置く(`perf::rig`。同じ commit の 2 度目はビルド無し)。**測られるのは commit だけ**(席の編集を測るなら commit してから `--at HEAD`。`--at` 無しは席の exe = 編集込み)。**触るのは機械だけ** — EnterWorktree(名前でも path でも)と Write / Edit は hook が deny、rig が dirty なら perf は reset せず拒む。証跡は撃った席の `target/perf/` に落ちる。**CPU の並行は増えない** — 実窓の計測は他席のビルドと同時に撃てば foreign 35% で落ちる(隣で続けてよいのは編集・思考・git だけ)— **その順序付けは `still` がやる**
- **perf の判定行は net で読む(`--no-font-walk` で素の gross)**: 一族(`Yu Gothic UI`)に無いグリフを 1 つ組むと Qt がフォント DB の全 family を populate する(`QPlatformFontDatabase::fallbacksForFamily` が writing system で絞る前に全 family へ `ensurePopulated()` を当てる = プロセスに 1 回。絵文字でも JIS 外の簡体字でも同じ、日本語は一族が持つので呼ばない)。`QFontDatabase` の fallback / emoji API も `QFont::families` も一覧の順を変えるだけで populate は止まらない。止まるのは色フォントを primary にした時だけで、それは run 分割 = 却下。なので `cargo xtask perf` は較正 run `run-font-walk` を毎回先に撃ち、歩きの差を report の `font walk` 行に出して、`net` = working set − 差 を判定行にする(較正の組み方は `perf::fonts` と `WindowPerfDriver.qml`)。**offscreen では歩きは出ない**(FreeType DB にフォントが無い)ので、歩きの代金は `cargo xtask perf` でだけ読む
- **計測は機械を止めて撃つ(`xtask::still`)**: 仕組みは `crates/xtask/src/still.rs` の `//!`(要約は 反映前テストの機械化.md §計測との直列化)。hold 中にセッションが撃つ compile する cargo は pre-shell hook が deny する — 通るのは `cargo xtask …` / `cargo run -p xtask …` と compile しない sub-command(fmt / tree / metadata 等)だけ(判定は `hook::still`)

## 記録の管理

- **予算に対する答え(§判定)の正本は [perf-windows-x64.md](../ci/baseline/perf-windows-x64.md)**。冒頭に測った木(`git rev-parse <commit>:crates/platitude-core` / `…:crates/platitude-app`)・Qt・corpus token を名乗らせ、**同じ木・同じ Qt で撮った節だけを並べる**。別の木の表はそう名乗らせ、読むのは表の中の差だけ
- **比べてよいのは条件を揃えた値だけ** — 揃える軸は §cacheとA/B(画面・Hz・renderer・features・corpus・GPU)
- run の生データは `target/perf/<os>-<arch>/<run>/`(§OS別の証跡)。記録へ写すのは判定と読み
- **1 つの問いに答えた実測は `ci/baseline/<主題>-<os>-<arch>.md`** — 今あるもの: コードの判断の代金 [code-costs](../ci/baseline/code-costs-windows-x64.md) / 画面表示中の読み込み [poll-cost](../ci/baseline/poll-cost-windows-x64.md) / refs の join [refs-join](../ci/baseline/refs-join-windows-x64.md) / 先端を他が掴んでいるか [head-reach](../ci/baseline/head-reach-windows-x64.md) / git の実行枠 [git-slots](../ci/baseline/git-slots-windows-x64.md) / アバター [avatar-log](../ci/baseline/avatar-log-windows-x64.md)・[avatar-shrink](../ci/baseline/avatar-shrink-windows-x64.md) / メッセージ・パッチの渡し方(一時ファイルと stdin)[input-costs](../ci/baseline/input-costs-windows-x64.md)・[Linux](../ci/baseline/input-costs-linux-x64.md) / 差分ペインの画像の運び方 [preview-pictures](../ci/baseline/preview-pictures-windows-x64.md) / 依存更新の前後(段 3 の性能実測を撃った最後の 1 本)[deps-update](../ci/baseline/deps-update-windows-x64.md)
- **コメントに時間・メモリ・機材構成の実測値を書かない**(rules/code.md)— 数字が要るなら code-costs へ 1 行足してそこを指す
- 判断・却下・要調査は確認事項へ(下の §現状と残件)
