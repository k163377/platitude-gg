# 反映前テストの機械化(gate)

入口は `cargo xtask gate`(USAGE が正)。

**gate と check が撃つ cargo は全部 `--locked`**(`cargo xtask` の alias 自身も)。`Cargo.lock` を書き換えたい cargo は
「lock file needs to be updated」の赤で止まる(依存の変更は人の許可が要る = CLAUDE.md 絶対制約。ロックを本当に更新する時
は人が `cargo update -p <crate>` を撃って commit する)。`cargo fmt` だけは素のまま(依存を解決しな
い)。CI(`.github/workflows/ci.yml`)の cargo も同じ綴り。

**手で撃つコンテナ行にも `linux` が付ける**(`/work` はホストの checkout そのもの。既定が locked で、例外とその理由は
`linux::UNLOCKED_VERBS`)。

赤いステップのログの写しは `target/gate-logs/failed/<run>/` に残る(cargo がロックファイルで止まった赤の証拠と、その読み
方は `gate::evidence` / `linux::watched_from_inside`)。

## 依存木(`gate::graph`)

ノードはファイル(workspace 相対、末尾 `/` はディレクトリ)。辺 `a → b` は「a が b を読む」。逆閉包(reach)= 変更ファイルを
読む全ファイル。何を辺に数えるか(`mod x;` は辺ではない・再エクスポート・manifest と build script・OS ごとの `cfg`・QML
の伝播・テストだけの参照)と、鍵の入力への逆読みは `gate::graph` のコメントが正。

**Markdown(`.md`、拡張子の大小文字を問わない)の変更はテスト選択の外** — 依存の辺・テスト選択の起点・ステップのキャッシュ
入力から除く(コードや assets・ハーネスのディレクトリ内でも同じ)。`structure` / `waits` / `versions` / `docs` / `wrap`
/ <!--call:relied-messages.check-->`relied-messages check` / `verbs` / `fmt` の常時チェックは残る。

- 文字列リテラルが workspace のファイル / ディレクトリを名指ししていれば辺(xtask の structure が `ui/` を読む等。辺の外
  に置く文字列は `graph::literal_paths`)。**ステップの鍵が名指すパスや、別の commit・遅れた木を読むためのパスは、その
  ファイルの読みとは別** — だから分割して綴る(`plan::core()` / `qt::former_pin`。丸ごと綴るとそのファイルが名指した先の
  読み手になり、たとえば core の 1 ファイルの変更が `plan.rs` から runner の全テストへ届く)
- **CI の workflow(`.github/`)はどのステップも読まない** — 編集しても選ばれるのは常時チェックだけで、計画は
  `no step reads these` に挙げる。机・コンテナ・CI が共有する Qt の版は `.qt-version` に在り、workflow の行ではない
- **ディスクから読む到達はデータとして渡る**(`graph::Carried`)— ファイルの名指しで選ぶステップ(動詞・wedge)と、コードし
  か読まない clippy は、コードが変わった時(`Whole`)だけ選ばれ、そのコードのテストはどれでも選ばれる。製品の変更は統合バ
  イナリの手前で止まる
- **製品データの到達を狭めるのは構造の分離** — 製品を読む処理と、入力値だけで成立する共通定義が同じモジュールに居ると、
  後者を引く読み手まで製品データが届く。共通定義を葉モジュールへ責務で分けて参照関係を消す(`budget::machine` /
  `hook::approval` / `linux::tested` / `app_build`)。伝播規則や鍵の生成規則への除外条件、モジュール名の除外リスト、読ま
  ないことの自己申告、パス文字列を認識されにくくして逃がす変更は作らない。実測と残る入口は §製品データとして届く xtask
  の単体テスト

**木そのものへの苦情は毎回の gate が読む**(`graph::complaints`)—「全パス解決」と「root に読み手なし」の 2 つで、赤けれ
ば**入口で拒む**。どちらも今の変更の落ち度ではないが、**解決しないパスは引かれなかった辺**で、その辺が運ぶはずだった選択
が丸ごと欠ける。root の規則は rules/structure.md §分割。

診断: `cargo xtask gate deps --file <path> --why <path> --show` / `--history <n>`(診断はキャッシュを使わず毎回ソースから
読む)。

`.cargo/` / `vendor/`。ソースのグラフに映らないので、選択と鍵の両方に入れる。

**Cargo.\* の変更は reach を全ファイルにし、テストは filter 無しで全部回す**(ソースのグラフには依存の更新が映らな

ら(`graph::build`)、`clippy.toml` は全クレートの clippy(両側)だけ、`deny.toml` は `deny` だけ、**コンテナのイメージの材
料(Dockerfile・`.qt-version`)はコンテナ側の全ファイル**(`plan::scopes`)。**TOML のコメントだけの変更は何も選ばな

だそれを名指す読み手を変更として数える**(`Graph::naming`)。**reach の製品 QML 部品を登録表のどの行も示していなければ
gate は赤**(名指し。singleton / `QtObject` root は item tree に立たないので対象外。行が示す物の読み方は §選択の正本)。

### 版を動かす変更は段 3

**crate・toolchain・Qt・最低 git の版を動かす差分は、段 2 の `gate`(= `land` の gate)が自分で段 3 の計画へ上が
る**(`plan::pins` → `plan::Scope::whole_tier`: `periodic` のテスト、段分け表の `whole` の行、全行のコンテナ側)。新しい版
はソースの辺が届かない所を壊すので、reach を全部にするだけでは足りない。**上がるのはその版で組んで走らせる側だけ** — 最
低 git と Dockerfile のベースイメージはコンテナの版(host の git は最低版ではなく、host のシステムはイメージの物ではな
い)なので、host は reach のまま。版を運ぶ行は次の 5 つで、**同じファイルの他の行の変更では上がらない**:

| ファイル | 版を運ぶ行 | 上がる側 |
|---|---|---|
| `Cargo.lock` | 全行(crate の解決済みの版。manifest の要求だけの変更はロックを動かさなければ何も変えない) | 両側 |
| `rust-toolchain.toml` | 全行 | 両側 |
| `crates/platitude-core/src/version.rs` | `pub const MINIMUM_GIT` の行 | コンテナ |
| `ci/linux/Dockerfile` | `FROM` の行と、既定値を持つ `ARG` の行(ベースイメージ = 最低版の git とシステムライブラリ。Ubuntu の版 `UBUNTU` と、Qt を入れる aqtinstall `AQT_SOURCE` は既定値で持つ) | コンテナ |
| `.qt-version` | 空行と `#` で始まるコメント以外の全行(机・コンテナ・CI が入れる Qt。版とその横のコメントだけを持つファイル。版は空行とコメントを除いた最初の行 — xtask は `qt::pinned_in`、CI の Qt action は同じ規則を shell で読む) | 両側 |

- 上がっても**鍵の変わらないステップはスタンプで済む**。版が鍵に入る経路: `Cargo.lock` / toolchain は cargo を撃つ全ス
  テップ、`version.rs` は core を読むステップ、Dockerfile と `.qt-version` はコンテナの全ステップ(イメージの材料 =
  `linux::image_tag`)。**host の Qt は機械の設置物で木に無い**(版は `.qt-version` が名指す)— その配置と版は host の同一
  性として鍵に入り(`gate::environment`)、入れ替えれば Qt を読むステップの鍵が動く
- **版を書くのは上の 5 つのファイルの 1 箇所ずつ**。書式が他のファイルを読めず写すしかない版 — workflow の runner 名と
  action の commit — は常時ステップ <!--call:versions.agree-->`versions` が源と揃える: OS ごとに runner 名は 1
  つ(`-latest` は版を名指さないので不可)、Ubuntu の runner 名は Dockerfile の `UBUNTU`、action は全ての写しが 1 つの
  commit とその版のコメント。CI の Qt action は aqtinstall を Dockerfile の `AQT_SOURCE` の行から読む
- **段 1(`--host-only`)は上がらない**(日常の段は host の速い半分のまま)。`--keep-going` は付かない(`land` は最初の赤で止
  まる)
- 段 3 の残り(<!--call:linux.bare-->`linux bare --discover`・CI の Whole test・性能実測)は gate の外で、版を動かした時は
  手で回す。出荷ビルドの版を動かした land だけは、Whole test が `land` の push する `deps/*/after` タグで走る(§版を動か
  した land のタグ)

## 動詞の絞り込みは比較表示に留める(`steps::lines_showing_the_change`)

**実行するのは登録表の全行**(§選択の正本)。変更した QML 部品そのものを示す行の数(読み手は数えない — 構成の読み手は
`Main` まで遡り、核は全行が示す)は `verbs: 662 selected …; by what they show: 31` と印字するだけで、実行を絞らない(表自
身の動きが負う行は `plan::rows_the_tables_owe`)。絞らない理由: 示す物は宣言から読んだ近似で、閉じた popup の宣言時の
binding の副作用や、核の部品の状態をどの run が変えるかは静的に出ない。絞るなら、主題の申告が完全であることの担保(run の
`shown:` を人が読み続けること)と、落ちる行が担っていた assertion と経路の行き先を確かめてから(要判断は P3-確認事項)。

## キャッシュとスタンプ(`gate::stamp`)

ステップの緑は `(id, コマンド, 契約, host の同一性, 読むパスごとの id)` の鍵で `<git-common-dir>/pgg-gate/steps/<key>`
に記録する(席をまたいで共有)。host の同一性は host が供給する入力(OS・Qt / QML の環境変数・Qt とフォントの配置・git の
版)で、読めなければそのステップは `unkeyed`。**シェル自身の変数(`PATH` / `HOME` / `USERPROFILE`)は入れない** — cargo が
`cargo xtask` ごとにその木の `target/debug` を PATH に前置し、シェルごとに綴りも違うので、入れると緑が席とシェルをまたい
で運ばれない(`gate::environment`)。同 commit の 2 度目は何も回らず、rebase で SHA が変わっても読む tree が同じなら緑のま
ま。鍵の中身 — Markdown を除いたディレクトリの指紋(`gate::inputs`)、コメントと空白で動かない code id とそれで鍵を持つス
テップ(`inputs::code_id` → `lex::normalized`、`plan::owed`)、行の約束と判定(`Step::contract`)— は各モジュールのコメント
が正。**アプリをビルドして走らせるステップは製品 2 クレートを丸ごと読む**(テスト専用の配下を指紋から落とさない理由と代金
は `plan::steps::binary_steps`)。

`--host-only` は host 側だけ回して commit に `container=false` で記録し、両側の gate はコンテナ側だけ追加で回す(**両側の
スタンプが既に在る commit へ `--host-only` を撃っても格下げしない**)。`--fresh` はスタンプを無視。`--dry-run` は各ステッ
プの行に鍵を添える(入力の変更がどのステップの鍵を動かすかを、スタンプ無しで読む口)。

commit スタンプ `<git-common-dir>/pgg-gate/commits/<sha>` は必要ステップが全部緑の時だけ、clean な tree の commit にだけ
書く(書式は `gate::stamp`)。

run の残骸は gate が入口で掃く(1 日より古い run のディレクトリ — `verify::sweep_yesterdays_runs`、preset の雛形は
`demo::template`)。**`cargo xtask demo-repo` が建てた木は `.pgg-keep` の印で掃除から外れ、印に寿命は無いので消すのは人の
仕事**(`verify::keep`)。コンテナのエンジンの側(ボリューム・イメージ・build cache)は `linux` が入口で掃く(keep 集合と古い
runner との共存・エンジンが答えない時の止まり方は `linux::housekeeping` / `linux::alive` / `linux::engine::put`、共有
registry の錠は ci/linux/Dockerfile)。名前と生死の読みに残る罠は `linux::checkout_name` / `linux::Alive` のコメン
ト、vhdx の話とエンジンが答えなくなる停止の記録は P3-確認事項 §開発環境(Linux コンテナ)。

## 群の並走と動詞の並列(`gate::sides` / `gate::sides::verbs`)

側の中のステップは **build directory を共有しない 3 群**(checks = cargo の `target/debug` と `target/shipped` /
built-app = 動詞と `bare` が読む `target/release` / どちらも読まない `qmltest`)**に分けて並走させ**、先頭の always ス
テップだけは**両側より前に**単独で回す。動詞は側ごとに 1 ブロック: **最初の未キャッシュの 1 本が単独で走ってビルドし、残
りは `--no-build` で `--jobs` 本ずつ並列**。`--jobs` の既定は**論理 CPU の 1/3、1〜8**(`budget::default_jobs`。値と並走
の根拠は §実測)。群の止まり方・アプリ自体が組めなかった赤の扱い・xtask のステップを runner の複製から起動する理由は
`gate::sides` / `gate::runner` のコメント。

## 最初の赤で止まる(`gate::halt`)

**赤が 1 つ出た run の判定はもう決まっている**。残りを走らせて得られるのは、通ったステップの stamp だけ —— そして **動詞
は app と core の木を丸ごと読む**ので、赤への直しはその stamp をほぼ必ず全部無効にする。

- **最初の赤で両側が止まる**。止めたステップと始めなかったステップは ledger に **`halted`** の行(stamp は無く、次の run
  が払う)
- **`--keep-going` は残りを走らせる**(**`--whole`(段 3)はこれが既定**)。**always-step の赤は `--keep-going` でも止まる**
- 止め方(予算の順番待ちの譲り方・子ごとの終わらせ方・自前のコンテナを立てる `linux` のステップを止めない理由)と代金は
  `gate::halt` のコメント

## 機械の予算と優先キュー(`budget`)

**gate 1 本の負荷はプロセスの束**で、席が同時に gate を回せばその全部が足し算になる。**数えるのは全部のステップ**: ス
テップ 1 個 = 1 単位で、走る前に機械共通の予算から **ticket** を取り、終わったら返す。両側は同じ予算から引く。重み(LIGHT
/ COMPILE)・予算の大きさ(gate 1 本ぶん)・台帳の形は `budget` のコメントが正。

**優先度は 3 段**(ユーザー決定): **main 反映(`Rank::Landing`)> 起動(`Rank::Launch`)> 他のテスト(`Rank::Normal`)**。起
動(`cargo xtask launch`)で**数えるのはビルドと起動まで**で、立った窓自体はユーザーの物で予算の外(verb を headless で撃つ
のはテストなので `Normal`)。

**規則は 1 文**: *待っている単位は、順序付けたキューの「空きに収まる先頭部分」に居れば走ってよい。収まらない 1 本でその
先頭部分は終わる*(`budget::queue::admits`)。同順位は席の持ち回り(`queue::order`)。

**保証しないこと**: 上の段を優先したまま preempt しない以上、**land や起動が連続する間の下の段の待ち時間は保証できな
い**。割り込みの速さは走っている単位の長さで決まる(→ §割り込みを妨げる単位)。**起動の fast path も機械が満杯なら待
つ**(待った分はその場で 1 行言う)。

**生死は lock、ただし lock が空いても仕事は残りうる** — 単位は自分が起こしたプロセスの番号と名前を ticket に書き、room
を返すのはそのプロセスが**消えてから**(逆向きの自動返却は「予算の 2 倍で静かに走る機械」を作る。判断と代金は
`budget::ledger` の `leftover`、プローブは `subprocess`)。**なので spawn する所はすべて子を ticket に書く**(gate のス
テップは `watched::run_step`、単体コマンドは `budget::watched` / `budget::child_started`)。居残りは `cargo xtask budget`
が `LEFTOVER` と名指し、**止めるのは人の仕事**。

**ticket を取る場所は 2 種類だけ**: (1) **runner がステップを回す所**(`gate::step::run_one` / `gate::runner` /
`replay::run_line`)、(2) **それ自体が 1 単位である単体コマンドの入口**(`verify-ui` / `linux` / `shipped` / `launch` /
`package` = `budget::standalone`)。その下の子は親の ticket の下(`PGGDEV_BUDGET_HELD`)。**コンテナへの道は印を 2 つとも付
ける**(`linux::marked`。片方だけ付いた道は機械を二重に数える)— 席の `.git` はマウントの外を指すのでコンテナの中から台帳
へ道が無く、数えるのは host 側の `linux` コマンド。

**land 同士は受付順に 1 件ずつ**(`Pool::turn`)。**ロック順序**: 木の gate(`lanes::sole` — 即拒む)→ land の turn → 計測の
hold が空くのを待つ(`still::until_free_in`)→ ticket → 計測へ announce(`still::busy`)。単位は ticket を 1 個だけ丸ごと取
るので循環しない(順序の理由は `budget` / `budget::ledger` のコメント)。

**tree に gate は 1 本**: 2 本目は 1 本目の pid と経過を名指しして拒む(`lanes::sole`。`land` の gate も同じ lock)。

**run は木に何も書かない**(§選択の正本・§観測)。登録表(`verb-lines.txt`)と段分け表(`verb-tiers.txt`)は人が書く入力で、読
めない表は空として読まない —— 登録表の読めない行はファイル名:行番号付きのエラーで gate の計画・`verbs`・`replay` を止
め(`gate::lines`)、段分け表の読めない行は計画では無い行として落ち、`verbs`(常時ステップ)が行番号で名指して赤にす
る(`gate::tiers`)。

## 割り込みを妨げる単位(`gate::record`)

**preempt しないので、land が待たされる上限は「その瞬間走っている単位の長さ」**。だから gate の記録は**長い単位を上位 5
本、両側まとめて**言う(`longest <id> <時間> (weight N) / …`)。**次に割るならこの行が名指す物**。

分割の代金と制約(先に読む): 起動と fixture の費用が単位ごとに増える。**統合テストは 1 バイナリ**(core.md)なので
`tests/it` はそのまま — 割るなら実行集合・cwd・環境・成果物・終了コードが同一であることを機械で確かめてからにす
る。**`tests/it` は割らない**(理由は `gate::plan::steps` の `it_steps` のコメント、数字は
[gate の負荷の内訳](../ci/baseline/gate-load-windows-x64.md) §割り込みを妨げる単位)。

## land

land の結果と時間内訳は席の `target/land-runs/` に残る。失敗時の未完了区間は `unfinished` と結果の理由で読む。gate 内部
の内訳は `target/gate-runs/`。

1. branch を checkout している worktree(席)を探す。無ければ拒む(gate はそこで回す)/ **席が反映の列の先頭でなければ拒
   む**(§land の列)/ 席が汚れていれば拒む / main を持つ席があれば拒む / **`/land` の発話(permit の記録)より後にその席が
   board に載せた run があれば、何も動かす前に拒む**(`land::approval`)— land は席の run を外すので、指示の後に載せた絵(=
   ユーザーがまだ承諾していない UI)が見られないまま消える。セッションは board に載せた絵で承諾を得て、次の `/land` で
   land し直す(その発話より前の run は外れる)。**拒んだ land は permit を waiting にする** — 以後は run を board から下
   げても、ユーザーの次の発話まで land を拒む。gate の後、main を動かす直前にもう一度確かめる。セッションの無い land(人
   の手)と permit の記録が無い land は問わない
2. **permit を読み直す**(ここと 6 の直前。`land::permit_still_open`)— 背景で撃った land はユーザーの次の発話より長く生
   き、その発話が permit を閉じる。閉じていれば何も動かさずに止まる。
3. 走っている xtask が席の build slot(`<seat>/target/debug/xtask`)なら、その名前から退く — 実行中の image は置き換えられ
   ず、5 の gate が同じ slot を組み直すため(退く名前と罠は `land::run` の `step_out_of_the_build_slot`)。続け
   て <!--call:gate.install-->`gate install`(冪等)
4. main が branch の祖先でなければ席で `git rebase main`。止まれば `--abort` して報告
5. 席で gate(段 2・両側)。赤なら止まる(branch は rebase 済みのまま、main は動かない)。緑は commit のスタンプそのもの —
   gate のステップは木に何も書かないので、通った木と commit は同じ物
6. primary が main を checkout していれば `merge --ff-only`、どこにも無ければ `fetch . branch:main` → hook がスタンプを
   確かめる。動いたらこの land が走った permit を spent にする(§land の許可)
7. **出荷ビルドの版を動かした land は、前後に annotated タグを打って push する**(§版を動かした land のタグ)
8. **この land を撃ったセッションの物を片付ける**(`land::leftovers`、land の順番を握ったまま)。対象はそのセッションの
   branch — git で作った物(作ったセッションは git hook が記録する — §git hook)と、アプリがそのセッションの起動用に作った
   worktree の branch(そのセッションの SessionStart か、land が会話記録の置き場から記録する — `seats::start`)— のうちど
   の木も出していない物(main と席の branch `worktree-<letter>` を除く)と、それを出している worktree(primary・席
   a〜f・rig・land した木自身を除く)。**消すのは、main か rebase 前の branch が中身を全部持つ物だけ**で、worktree はさら
   に lock・未コミットが無く誰も使っていない物だけ。**使用中で消えなかった起動用 worktree は手放
   し**(`left-behind`)、**以後の land は誰のでも、手放された物を同じ規則で判定し直して消す**。**手放された物のほかは、他
   セッション・アプリ・ユーザーが作った物と、記録の外にある物を判定も名指しもしない**(誰が作ったか分からない物は作り手の
   物かもしれない)。残した自分の物は理由付きで `leftovers:` の行が名指す — 控え等はそのセッションが報告前に消
   す(CLAUDE.md §Git 運用)。セッションの無い land(人の手)は何も片付けない。判定の手順・OS ごとの使用中の見方・記録の外に
   ある物の一覧は `land/leftovers.rs`、起動用 worktree の見分け方とアプリの扱いは `seats/start.rs` のコメント
9. board の掃除と**席の claim の解放**。誰の claim でも外す(land はユーザーの「この作業は終わり」の言葉。手書きの lock
   だけ残す)。そのまま作業を続ける側は、次の編集・入席・会話の始まり(compact・再開は除く)か `cargo xtask seat` で claim
   が戻る。**絵は claim を戻さない**(`seats::may_picture`)— land 後の載せ直しで席を握り続けて他が使えなくなる形を作らな
   い。land しない終わり方で返すのは <!--cmd:seat.release-->`cargo xtask seat release`。他人の claim が乗った席だけ、
   ユーザーの指示による <!--cmd:seat.takeover-->`PGGDEV_ALLOW_TAKEOVER=1 cargo xtask seat takeover <letter>` で動
   く。**claim は会話のもの** — session id は会話を通して不変ではない(中断したプロンプトの編集・`/clear` で変わる)の
   で、claim はアプリのセッション(`CLAUDE_CODE_HOST_SESSION_ID`)も名乗り、どちらかが合えば自分の物とする。claim の動
   き・空き席を渡す順・id の変わり目の扱いは `seats/claim.rs` / `seats/offer.rs` / `seats/handout.rs` のコメント

履歴は線形。反映後の席は main の先端に居る。

### 版を動かした land のタグ(`land::tags` / `land::versions`)

履歴は線形で land の範囲を示す merge commit が無いので、**依存を更新した land の範囲はタグ 2 本が示す**。land が main を
動かした後、land 前の main と land 後の main で出荷ビルドの版(Qt・Rust toolchain・出荷バイナリが引く crate — 読む所と数
え方は `land::versions`)を読み比べ、違えば打つ。

- **§版を動かす変更は段 3 より狭い** — 最低 git と Dockerfile の `FROM`・`ARG` の既定値は試験環境の版で、製品が走る版で
  はないので打たない
- **名前**: `deps/<日付>/before` = land 前の main(旧版で最後の commit)/ `deps/<日付>/after` = land 後の main(更新と追従
  の改善が済んだ所)。日付は land 後の main の先端の committer date。同じ日の 2 本目からは `deps/<日付>-2/…`。本文は 2 本
  とも同じ移動の一覧(書式は `land::tags`)
- **push**: `branch.main.remote` へ 2 本まとめて(両方か、どちらも無しか)。プロンプトを待たず、止まった転送は諦め
  る(`land::tags` の `push`)— land はまだ land の順番を握っている
- **main は既に動いているので、タグと push の失敗は land を赤にしない** — `note:` で言う。push の失敗には手で撃つ
  `git push` を添える
- **性能の前後比較**: crate と toolchain の `channel` は commit と一緒に動く(perf の rig は `--at` の commit を checkout
  した木で cargo を回す)ので、2 本をそのまま `perf --at` に渡せば比べられる。**Qt は木に無く host の設置物**だが、rig は
  `--at` の commit が名指す版(`.qt-version`、それより古い commit は CI workflow の `QT_VERSION:` 行 ——
  `qt::pinned_at`)の Qt で建てて走らせる(`perf::rig`。その版が host に無ければ組めずに止まる。`--qt` は両側を 1 つの Qt
  に揃える = Qt を固定した比較)ので、Qt の移動も 2 本をそのまま渡せば比べられる
- **host に入れた物のうち鍵に入らない物の入れ替えは木に映らない**(C++ ツールチェーンの更新等。Qt とフォントの配置・git
  の版は host の同一性として鍵に入る — `gate::environment`)ので、これでは打たれない

### land の列(line)

`/land` を打った席は反映の列に並ぶ(`crates/xtask/src/land/line.rs`)。順は `/land` を打った時刻、追い越しは無く、**先頭だ
けが land する**(land は先頭でない席を拒む)。並んでいる間セッションは何もせず、起こすのはコマンドの終了(トークンを使わな
い)。他席の枝は読まない — 先に反映された物を正として rebase し、読むのは下の read の差分だけ。**turn を取った後に止まっ
た land(止まった rebase・赤い gate・gate 後の承諾待ち・閉じた permit・拒まれた fast-forward)は、その席を列から外
す**。turn より前の拒否(汚れた席・checkout の無い枝・先頭でない席)は直して撃ち直せる。turn より前に承諾待ちを見つけた
land は permit を waiting にするので、項目は外れずとも列に立たない。

- **項目はセッションの `.permits/<session>.line`** — UserPromptSubmit hook が permit と並べて書く(`/land` で作り、他の発
  話で消す)。**列に立つ条件**: permit が open、外れていない、席に他の会話の claim が乗っていない(claim の無い席は立つ)。
  席の外で打った `/land` の項目は列に立たない。会話が新しい session id で続いても同じ会話の項目として扱
  う。<!--call:seat.release-->`seat release` も項目を終える(項目の中身・錠・id の付け替えは `land::line` のコメント)
- **位置は 3 つ**: 先頭 = 反映中(rebase → レビュー → 修正 → 確認 → 再編 → docs → land)/ 次 = 準備(先頭の反映に CLAUDE.md
  か land・review-points・verify-ui・gate の SKILL.md の変更があれば何もしない。それ以外の `.claude/` と
  `internal-docs/` の変更はその差分だけ読んで判断。どちらでもなければ main へ rebase して自分のコードの明確な不備だけ直
  す)/ 3 番目以降 = 待機(何もしない)。段ごとの手順は land スキル
- **コマンド**: <!--cmd:land.line-->`cargo xtask land line`(列と自分の位
  置)/ <!--cmd:land.wait-next-->`cargo xtask land wait next`(次か先頭になったら終わ
  る)/ <!--cmd:land.wait-head-->`cargo xtask land wait head`(先頭になったら終わ
  る)/ <!--cmd:land.leave-->`cargo xtask land leave <why>`(自分で外れる)。wait は数秒おきに列を読むだけで、列に居なく
  なった瞬間に理由を言って error で終わる。次の席に伝える先頭の規約変更が読めなければ「読めなかった」と言う。pre-shell
  hook はこれらを land の guard に掛けない(main を動かさない)
- **外れる**: turn を取った後に止まった land は自分で外す(上)/ 反映する物の無い land は正常終了で項目を終える(permit は
  消費しない)/ ユーザーの判断が要ると分かった席は、次でも先頭でも、訊く前に `land leave`(スキル)/ **先頭が 2 時間静かな
  ら外す** — 判定は awake と同じ「機械で何も起きていない」(仕組みは `land::line` の `settle_the_head`)。外れた項目は理由
  を持って残り、その席の land と Stop hook が理由を言う。**並び直す経路は無い** — ユーザーの次の `/land` が最後尾に付け
  る(permit は止まった land では消費されないが、列の項目は `/land` しか作らない)
- Stop hook の反映未達の報せに位置が付く(次 / 3 番目 / 外れた理由)

### land の許可(permit)

Codex の入口は `hook codex-session` の UserPromptSubmit(`hook::codex_land`)。`session_id` と所有中の席を照合
し、`turn_id` と発話の digest を記録して同じ発話の再読を無作用にする。本体 checkout 起点でも列には所有中の席を登録す
る。hook の未更新・未信頼時は <!--call:land.line-->`land line` と land 本体が `CODEX_THREAD_ID` のローカル会話記録の最新
user 発話から同期する。同期は待機中・fast-forward 直前にも行い、spent / waiting や離脱を同じ発話で取り消さない。本文を指
定して許可を作る CLI は無い。記録形式・診断・初回導入は [Codex ハーネス](codex/ハーネス.md#land-の発話同期)。

main を書くのは `cargo xtask land` だけ — セッションの git による `merge` / `push … :main` / `branch -f main` /
`update-ref` は Claude の pre-shell hook と Codex の PreToolUse が**常に deny**(行のどこにあっても、前に何を付けても通ら
ない。`PGGDEV_ALLOW_MAIN=1` は land と無関係で、残る用途は primary checkout で直接 commit する例外 `hook/commit.rs` だ
け)。land が通るかは UserPromptSubmit hook がユーザー発話そのものから読む permit が決め
る(`crates/xtask/src/hook/permit.rs`): **ユーザーの文の先頭が `/land`(land スキル `.claude/skills/land`)なら open、それ
以外のユーザーの文は closed**(アプリが展開したコマンドの形も同じに読む)。land が承諾待ちの run を見つけると
waiting(§land の 1)。pre-shell hook は land を open の時だけ通す。

- **発話 1 回 = main が動く land 1 回**。open を spent にするのは main を fast-forward した land 自身。止まった land(汚
  れた席・赤い gate・止まった rebase)は何も消費しない — 順番を取る前の拒否(汚れた席)は直して同じ発話のうちに撃ち直せ、順
  番の後に止まった land(赤い gate・止まった rebase)は列から外れて次の `/land` を待つ(§land の列)。spent の後の 2 本目は
  deny。permit の対象は land だけ
- **次の発話で消える**(spent・waiting・open のどれでも)。訂正・質問への答え(「1で」「OK」)・別件の承認は許可を持ち越さな
  い。もう一度 `/land` と打てばまた開く。列の項目(§land の列)も同じ発話で消え、走っている land は fast-forward の直前に
  permit を読み直して止まる
- **触るのはユーザーの発話だけ**: 要約で持ち込まれる文脈、チップの起動文(提案元の Claude が書いた文)、機械のメッセー
  ジ(タスクの終了・CI・サブエージェントの報告・他セッションのメッセージ)、子セッションの報告は素通り。**アプリが発話の前
  に付ける注記は読み飛ばしてその後をユーザーの文として読み**、注記だけのプロンプトは素通り。それ以外のタグ — 貼り付けの
  `<pasted_content>` など — で始まる発話はユーザーの文(見分け方は `hook::permit` の `the_users_words`)。レビューの注
  記(`hook::review`)も同じ発話だけに答える
- **`/land` は他セッションへ渡らない** — `/land` の行を含むメッセージ・起動文は pre-tool hook が deny(§セッション間の連
  絡)。他のセッションに反映させる時は、ユーザーがそのセッションで `/land` を打つ
- 「反映」の語を含む `/land` 以外の発話は何も開かず、hook が「許可は `/land` だけが開く」とセッションに注記する
- Stop hook は現在のツリーの未反映 commit と未コミットファイルを数え、open なら反映未達、waiting なら承諾待ち、spent な
  ら反映後の未反映作業を `systemMessage` で告げる。未着手の修正や他のツリーまでは検出しない

開くのがコマンドだけなのは、語が質問・否定・説明(「反映作業のeffortが何だったか教えて」「反映はまだ実行しない」)に
も、Claude が書いたチップの起動文(「main へ反映した」)にも出て、そのどれもが許可を開けてしまうため。打たれたコマンドは発
話の先頭でしか成り立たず、Claude の文がそこへ届く経路(起動文・メッセージ)は hook が塞ぐ。

### セッション間の連絡(`hook::contact`)

アプリは提案カードや `start_session` から始めたセッション(子)を提案元へ結び、子がターンを終えるたびに提案元へ報告を入れ
て 1 ターン走らせる(`<side-sessions-event>` で終わるプロンプト)。SendMessage も双方向に案内される。このプロジェクトでは
セッション同士を、ユーザーが頼んだ時のほかは影響させない:

- **子は最初のターンで自分を切り離す** — アプリの `detach_session`(`session_id: "self"`)。切り離した子はサイドバーの最上
  位へ移り、ターンの終わりを提案元へ知らせない(提案元と一緒にはアーカイブされず、取り消せない)。子の最初のプロンプト(起
  動文。見出し行が `(from the session that started this one):` で終わる)に UserPromptSubmit hook が注記し、呼ばずに最初
  のターンを終えようとすると Stop hook が 1 度だけ止める。呼んだ結果(拒否も含む)で催促は終わる。ツールが拒むのは、他セッ
  ションと worktree を共有する子と、ツールの説明の言う「ユーザーが置いたセッション(fork・task chip)」— 提案カードを押し
  て始めた子は切り離せる(2026-11-04 実測。拒否の条件は `hook::contact` の `DETACH`)
- **報告は block しない** — UserPromptSubmit で block しても、ユーザーの画面には「プロンプトがブロックされました」のカー
  ドが残る。アプリの設定にも Claude Code の設定にも、子の報告を黙って止める項目は無い。だから報告は出所(子の切り離し)で
  止める。切り離す前の子・切り離しを拒まれた子の報告と、ユーザーの発話に相乗りした注記は届く
- **送るかはセッションがユーザーの発話から読む** — 承諾の「送る」、題名だけで宛先を言う「「…」へ送れ」も頼んだうちに入
  る。hook は SendMessage / `send_message` の宛先も発話の語も見ない(語の組で読むと、言い回しの違う依頼を止めるため)。連
  絡の答えは、受け手が自分の会話でユーザーへ返す(送り返すのは受け手のユーザーが頼んだ時)
- `/land` の行を含むメッセージ・起動文(SendMessage / `send_message` / `start_session` / `hand_off_to_session`)は deny

## git hook

`reference-transaction` は `prepared` で非 0 終了すると更新を中止する(git ≥ 2.28)— セッションの git が main を動かす経路
を、checked-in のスクリプト 1 本が全部受ける。

**gate が答えるのはセッションの git にだけ**。環境にセッションの印 — `CLAUDECODE`(Claude Code が自分の起動する全プロセス
に置く)か `CODEX_THREAD_ID`(Codex が自分の走らせる shell に置く会話の ID)— が無ければ素通し(印の綴りは
`gate::hooks::SESSION_MARKS`)— ユーザー自身の端末・IDE・アプリの窓の git は、main への直 commit も巻き戻しも自
由。`cargo xtask launch` の窓は両方の印を落として起動する(ユーザーが操作する窓なので)。headless の verify-ui は印を残
す(操作しているのはセッション)。

**印が消えたら gate は黙って誰も止めなくなる**ので、Claude の SessionStart が印の不在を報せる。

セッションの git に対する verdict は、両側・on-main のスタンプへの fast-forward だけを通す(通す・拒む条件は
`gate::hooks::verdict`)。`PGGDEV_GATE_SKIP=1` はユーザーの手段で、セッションが綴るコマンドは deny する — Claude は
pre-shell hook、Codex は PreToolUse(`hook::codex_git`)。印の削除も検証を省略する設定変更に当たるので、Claude は
`CLAUDECODE` を綴るコマンドを、Codex は `CODEX_THREAD_ID` を設定・削除するコマンドと環境を空にするコマンドを deny す
る(Codex は席の持ち主を調べるのにこの値を読むので、読むだけは通す)。

**遠隔の main への refspec(`git push origin x:main`)は git hook を通らない**(手元の `refs/heads/main` が動かない)。セッ
ションのものは、Claude の pre-shell hook と Codex の PreToolUse が、手元の main を書く git と同じ判定(`hook::git` の
`main_write_refusal`)で、行のどこにあっても deny する。どちらもコマンドの文字列で読むので、alias・スクリプト越しの push
と、Codex が既に通した実行へ後から送る入力(`write_stdin` では PreToolUse が再発火しない)は止まらない — main に入った物の
残りの確認は push の CI(`push.yml`)と週 1 の Whole test。

**`core.hooksPath` を外す git には git hook が答えない**ため、Claude と Codex のツール実行前 hook が
`git -c core.hooksPath=…`・`--config-env` による上書きと `git config` による設定・削除を拒む(`hook::hooks_path`)。設定の
読み取りは通す。alias・スクリプト内部や Git 設定ファイルの直接編集を検出する境界ではない。

hook は **branch を作ったセッションの記録**も書く(land の片付けが読む — §land の 8)。記録の形・`pack-refs` の罠・印の無
い git の扱いは `.githooks/reference-transaction` と `gate::hooks` の `maker` / `Made`。

install(<!--cmd:gate.install-->`cargo xtask gate install`。Claude と Codex の SessionStart、および `land` が毎回撃つ —
Claude クラウドは撃たず、未信頼の Codex hook は動かない)は hook を `<git-common-dir>/pgg-gate/hooks/` に複製して
`core.hooksPath` をそこへ向ける — 席の reset / 削除で消えず、答えるのは install した tree の xtask。複製元・既存の
`core.hooksPath`・実行ビット・git 自身のガードとの関係は `gate::hooks` のコメント。

## hook は自前の build directory で動く(`--profile hooks`)

Claude Code の hook(`.claude/settings.json` の全 event)と git の `reference-transaction` は
`cargo run --quiet -p xtask --profile hooks -- …` で xtask を起動する。cargo は **profile の
directory(`target/<profile>/`)をビルドの間ずっとロックする**ので、`target/debug` で動く hook は、同じ tree で gate が回
す `cargo test` / `clippy` のコンパイルが終わるまで待つ。代金は xtask のソースが変わった tree で次の hook が 1 度 xtask
を組み直すこと。手で撃つ <!--cmd:hook.event-->`cargo xtask hook <event>` は `target/debug` の xtask(alias)で、答えは同
じ。

**shipped も自前の build directory**(`--profile shipped` = `target/shipped/`、Cargo.toml): `shipped` はハーネス無しの
release で、動詞はハーネス付きの release。同じ directory だと互いの binary を置き換え合うので、gate は `shipped` を
checks 群で動詞の隣に回す(§群の並走)。代金は tree ごとに release の複製 1 つ。

## ユーザーが読む文の言語(`hook::language`)

ユーザーが読む文 — ツールの合間の一言・締めの文・wrap_up の欄 — は日本語。ツール呼び出しの多いターンほどツール結果の英語
へ流れるので、出た場所で言う: 合間の一言は PostToolUse の注記、締めの文は Stop の block(1 ターン 1 回)、wrap_up の
欄(`recap` / `ask`)は PreToolUse の deny。注記と理由は日本語で書く。識別子やコマンドを混ぜた日本語は日本語、短い英語は判
じない(各 event での読み方・英語の判定と採らなかった線・他の注記との合わせ方は `hook::language` と `hook/mod.rs` のコメ
ント)。

## 選択の正本(`gate::lines` / `gate::shown`)

**gate が回す動詞の正本は `crates/xtask/verb-lines.txt`(登録表)で、人が書く**。1 行 =
`<verify-ui の行> TAB <その run が絵に立てると約束する製品部品(主題)、無ければ ->`。`*` の行は全 run が立てる物。**主題
は検証義務の宣言で、宣言しただけでは検証済みにならない**: run の絵の census に約束した部品が欠けていれば FAIL(§検証時
点)、緑の run だけがその部品の証拠。表の作り直しは run の証拠から機械で(`*` = 全 run の共通集合、各行 = それ以外に会った
物)。run は何も書き戻さない(§観測)。**行の綴りは `verify-ui` が読み返す形**(`verify::canonical_line` — 既定と同じ物を名
指した `--preset basic` は書かない。理由は `verify::repos` の `DEFAULT_PRESET`)。

**選択は reach だけで決まる**: reach にアプリの QML(`ui/` / `auto/`)か app の `main.rs` が入る時・ハーネス(`verify` /
`demo`)のコードが動く時・全体 —— どれも登録表の全行(段分け表で段を落とす。§段ごとに何を回すか)。同じ比較元・同じ木・同じ
表なら、実行履歴・並行順・読みの到着順によらず同じ集合になる。**表自身の動きも負う**: 登録表に足した行・約束(`*` 行 + 主
題)の変わった行・段分け表で段の動いた行は、他に何も動いていなくても負う(`plan::rows_the_tables_owe`)。行が示す物で絞った
数は計画に `by what they show:` として印字するだけで、実行は絞らない(§動詞の絞り込みは比較表示に留める)。

**「誰が示すか」は QML のソースから静的に読む**(`gate::shown` — popup が開く物・条件で組まれる物・root の宣言という境界
と、核の定義はそのモジュールのコメント)。静的な構成は `by what they show:` の比較と `cargo xtask verbs --shown / --why`
の診断にだけ使い、検証義務は行の約束で読む — **唯一の証人**(`plan::steps::owed_lines`)も、変更が届いた部品を反映前の行が
1 つも約束せず `whole` の行だけが約束すれば、その行は反映前でも回る。

**正本の整合は `cargo xtask verbs`(毎回の gate の常時ステップ)が検める**(`verify::coverage` — 拒む物の一覧はそのモジュー
ルのコメント)。**gate は reach の製品部品を登録表のどの行も約束していなければ入口で赤**(`plan::uncovered` —— 構成の閉包
で「立つはず」の部品は証拠ではないので数えない。新しい popup・Loader の中身・`Main` が組む部品も、それを立てる行(か `*`
行)に名指すまで通らない。別のファイルの根として着られる部品は着る側の約束で足りる。`--verb` の行も登録済みに限る)。

## 観測(`verify::observed`、`WindowCensus.qml`)

`WindowCensus.qml`(`platitude.auto`)が窓のオブジェクト木を歩く瞬間は 2 つで、和はとらない。**動詞の完了のター
ン**(`WindowHarness.finish` → `markCompletion`)と、**各成果物が保存されたターン**(`AutoShotDriver.pictured` →
`reportAt(artifact)`: `app` / `overlay` / `scene`)。app の絵の時点の歩きが
census(`census run=<id> page=<settled|arriving> …` と `census=A,B,…`)で、完了時の歩きと各絵の時点の歩きを突き合わせた答
えが、全 run が全成果物に対して持つ共通の主張
`pictured run=<id> artifact=<a> name=window holds=<bool> gained=… lost=…`(§検証時点)。**run はこれを
`<shot dir>/census.txt` に残し、登録行の約束との差を `shown:` の 1 行で言う** —— 会ったのに約束の無い部品(行を広げる候
補)は助言、約束したのに会わなかった部品は判定の違反(`contract:`、§検証時点)。木には書かない。数え方(一覧の delegate は表
示中で view の枠に掛かる物だけ・固定の枠は非表示でも数える・popup は開いている物だけ)は `WindowCensus.qml` のコメント。

**時計で木を歩かない**。歩く瞬間は run 自身の縁 —— 完了と各成果物の保存 —— で、どちらも動詞と撮影の因果の中にある。縁の
間に流れる壁時計(読みの着地・休止の満了)は run が握っていない時間で、そこで窓が動けば完了時の歩きと絵の時点の歩きが食い
違い、`pictured … name=window holds=false` が run を赤にする(動詞が仕掛けた物を待たずに終わった、の自白)。`gained=` が絵
の時点で増えた部品、`lost=` が消えた部品。完了の歩きは歩き直さない(縁の取り方は `WindowHarness.finish` /
`WindowCensus.reportAt` のコメント)。読みが全部着いた窓を写すのは動詞の完了の義務(`complete … page=settled`、§検証時
点)。

**動詞は自分が仕掛けた物が届いてから完了する**(開いた diff = `DiffPane.diffSettled` / 書いた後の読み直し =
`RepoPage.diffSettling` / 回数押しは `AutoActDriver.holdToEnd` / replay の途中の作業ツリーの行 =
`AutoActHistoryVerbs.replayRow`。規則は verify-ui スキル §壊れない動詞の実装と反復)。

settled の規則(`PageSettled`)が待つ読みの一覧は `PageSettled.qml` の `missing`。

**約束は 1 日の run から作り、雛形の id は UTC の日ごとに変わる**(日付は建てた日から逆算する —— `demo::template` の
鍵)。id の字で決まる絵は約束にしない: `find-hint-key head:3` は打ちかけの 2 文字が件名に当たった日だけ選択が動き、commit
のファイル行(`FileRowDelegate`)が写る(`AutoActFindVerbs` の `head:<n>` のコメント)。**作り直した約束は、UTC の日をまたい
だ run でも通ることを確かめる** —— またがずに入れると、翌日から全席の gate がその行で止まる。

## 検証時点(`Awaited.claim`)

**run の契約は、run 自身の id の下で言われる構造化行で読む** — 言うのは harness の機構(`Awaited` / `StageTimer` /
`CompletionRoute` / `WindowCensus` / `AutoShotDriver`)、言われた順に検めるのは xtask(`verify::contract` /
`verify::stages`)。他の run の行は数えず(混ざれば違反)、見つけた違反は後の行で消えない。xtask は違反を `contract:` の行
で名指して FAIL にする(`verify::outcome`)。

**観測・遷移・完了は分ける**(動詞の書き方は rules-refs/app-ui.md「観測・遷移・完了は分ける」):

1. **観測** `Awaited.all(名, 項)` は今揃っているかを答えるだけで、段を動かさない。
2. **遷移** は op(`PageStage` / `WindowStage`)だけが動かす — その op の拍の中、拍の最後の観測が真の時だけ(入力は押した物
   の受理が答え)= 拍の回数で動く段は無い。**op 同士は順序づけない** —— 要る依存だけを合流(`after=owner/op/段`)で言う。鎖
   が切れたら QML 側がその場で run を終え(`Awaited.breach`)、xtask も同じ鎖を検める(`verify::stages`)。
3. **完了の証拠は役割と観測時点で 3 つに分ける**(`op.complete({ when, report[, arriving][, lost][, name] })`): 入力
   前・押下中・入力直後に成り立った事実は証人(`op.witness`)、完了時にも要る条件は `when`、完了時の状態は `report`。報告
   は `when`・page の読み・page の保留が揃った読みのターンに読み、同じターンの読み直しと一致した時だけ言
   う(`CompletionRoute`)。**段で言う行は履歴**: 動詞の主張(must_say)は完了の報告だけで照合し、撮影結果は Qt の撮影行、性
   能検証(`perf`)は計測した時点を持つ `measurement` 行だけで照合する — 互いに代用しな
   い(`verify::contract::Said::satisfies`)。
4. **絵の主張**(`Awaited.claim` → `pictured`)は各成果物が保存されたターンに読み直す。全 run は `name=window`(完了時に
   立っていた部品の集合が絵でも同じ)を持ち、**絵も page で判定する**(settled か、完了が `arriving` に名指した読みだけが
   届いていない状態 — 部品の集合の一致で代用しない)。
5. **census** は app の絵の歩きで、登録行の約束(`*` 行 + 主題)に絵が欠けていれば違反。

**完了条件は主題の因果と、page が settled であること**(rules/app-ui.md)—— 主題の条件は `when` に置き、page の項もそのま
ま残す(完了の経路が page を待つのは、報告を読む時点を settled にそろえるため)。行の中身を読む動詞は
`Awaited.built(view)` で delegate が建ったことを先に読み、報告の関数の中で行を引き直す(先に掴んだ delegate は読む時には
プールに戻っていることがある)。

**機械の検査は構造で拒む**(`cargo xtask waits`、marker では通らない): ファイル単位の規則は `waits::stages`、op から走る
コードを呼び出しを辿って beat / press / read の文脈の責務で判定するのは `waits::reach`、拍を数えて数と比べる待ちは
`waits::beats`。

**各検査が保証すること**: **静的検査**(`waits`)は、op から到達するコード(呼び出しを辿った全部)が文脈の責務だけをすること
—— 入力は press の中だけ、ハーネスの状態は op の API・起動の条件・宣言した機構の関数だけ、読みは読むだけで前の値を持ち込
まない、辿れない呼び出しは名指す —— を保証する。保証しないもの: 製品の Rust slot の分類は受け手の可変性と字句の印に頼
る(内部可変性を印の無い形で使う `&self` は読みに数える)、型の分からない受け手は名前の和で引く、op の外のシグナル・ハンド
ラ(`Connections` 等)は文脈に入らない — そこで latch した縁(op の世代が始まる前に来うる)はハーネスの状態として op と読み
から読まれ、証人と違って op・時点を持たない —、待つ項が主題の因果として正しいか(何を待つべきか)は読まない。**実行時検
査**(`Awaited` / `CompletionRoute` と `verify::contract` / `verify::stages`)は、段がその op の拍の中で拍の最後の観測が真
の時だけ・宣言した順に 1 回ずつ動き、入力が段ごと世代に 1 回で、完了の報告が `when`・page の読み・page の保留の揃った読
みのターンに読まれて同じターンの読み直しと一致し、証人がその op・世代・段で保存されて完了の行に名指されることを保証す
る。**どちらも保証しないもの**: 待ちの因果 —— 観測した項が動詞の入力によって成り立ったこと、待つべき物を待ったこと。段の
履歴が正しいことはそれを示さない(正しい順に正しい回数動いた段が、別の原因で揃った項の上に乗っていることはありうる)。それ
は動詞の主張(完了の報告・絵の主張・census)と、遅延を注入した run(`--slow-git` ほか)と、レビューが見る。

**検査そのものの検証**: 機構は順序を握った QtTest(`tst_stages.qml` と 1 ファイル 1 件の `tst_stage*.qml`)、行の鎖は
`verify::stages` / `verify::contract` の単体、辿る検査は `waits::reach::tests` と Qt が走らせる `tst_reachforms.qml`。撮
り直しが元からであることは `cargo xtask shot-check`(`verify::shot_check`)、完了が書き込みの記録を待つことは
`cargo xtask records-check`(`verify::records_check`)が注入で確かめる(gate の選択は `plan::steps::shot_inputs` /
`records_steps`)。

## QML のループ(`verify::loops`)

**Qt が警告で言うだけのループは赤**: `Binding loop detected`(バインディングが自分の読む値を書いた)と
`possible QQuickItem::polish() loop`(polish の中で polish し直した)は、Qt がバインディングの書き込みを捨てる・polish を
打ち切るだけで続けるので、終了コード・QtTest の判定・絵のどれにも出ない。読むのは verify-ui の run の
行(`verify::outcome`)と、qmltest の runner の `-o` ログと stderr(`qmltest::judged` — QtTest のログは最初の case から始ま
るので、部品を組んで最初に束ねる時の警告は stderr にしか出ない)。**`verify::loops::ALLOWED` に理由付きで載っていない物は
FAIL**、載っている物も出た run で 1 行言う。表はファイル名と `QML ` 以降の語で引く(url は app と staging で違い、行は上
のコメントで動く)ので、1 行は部品の全インスタンスに効く —— 載せるのは直せない理由がある時だけ。`ignoreWarning` で受けた
テストの警告はログに出ない(テストが故意に起こすループは赤にならない)。

## どの層が何を持つか(検証の割り当て)

**名前ではなく「何を壊すと落ちるか」で決める**。gate が回すのは選ばれたテストだけなので、同じ主張を 2 つの層に置くと高い
方の代金だけが増える。

| 壊れると落ちる物 | 担当 | 実体 |
|---|---|---|
| 値から結果を決める規則(判断・分類・拒否条件・表示変換) | Rust 単体 / QML のデータ駆動テスト | 対象と同じ `.rs` の `#[cfg(test)]` / `tests/qml/tst_*.qml` |
| QML 部品の描画・入力・シグナル | 実部品を使う QtTest | `tests/qml/tst_*.qml`(1 ファイル 1 プロセスで各 1 回。全ての失敗を残す — §QtTest の代金はテスト本体) |
| git のコマンド・設定スコープ・終了コード・ファイルの更新 | 実 git 統合テスト | `crates/platitude-core/tests/it/` |
| Rust モデル → QML の接続・実ウィンドウ・OS 固有挙動 | verify-ui | `_PGG_AUTO_ACT` の動詞 |

**同じ画面を出すだけは重複ではない**。違う境界を見ている run は残す。**削る前に移行先を足し、代表的な規則を一時的に壊し
て担当が赤くなることを確かめる**(確かめていない移行は、単体が製品実装を呼んでいない・部品テストが製品の binding を通って
いない・残した run が実モデルを見ていない、のどれかで空振りする)。**run の観測(`census.txt`)は実行記録で、同等性の証明で
はない** — 動詞を統廃合したら判定表(`verify::verbs`)・docs・登録表(`verb-lines.txt`)・段分け表を揃え
る(`cargo xtask verbs` が崩れを言う)。

## 残る候補の棚卸し

残りは主張の形で分類する。1 本の run はたいてい複数の主張を抱えているので、**主張ごとに層を割り当ててから、割り当て先の
無い主張が残った run だけを残す**。「must_say の見出しが違う」「実 git を書く」「hover や描画を扱う」は、どれも単独では
残す理由にならない。

| 形 | どんな主張か | 例(**候補であって調査結果ではない**) |
|---|---|---|
| **A 拒否条件の表** | 読んだ値から「断る / 断らない」を決め、1 つの報せに出す | 書き込みの報せ(`push-outdated` / `stale-part` / `rename-taken` / `remote-refused` / `tag-refused`) |
| **B 同じ部品の状態表** | 1 つの部品へ違う状態を入れて姿を見る | `window-floor` / `nav-tip` / `carried-read`・`carried-stand` / `path-tip` / `fetch-hover` / `publish-taken` |
| **C 実 git の書き込みを伴う** | 押した所から git が書くまで | `delete-branch-go` / `push` / `stash-pop-row` |
| **D 実ウィンドウ・OS 固有を含む** | 窓の形・フォント・hover・実描画 | `window-fill` / `*-hover` / `*-tip` |

**C は「実 git の検証が要る」と「その verify-ui ケースが要る」を分ける**。割ると: 文言差 → 単体・QtTest / git の結果 →
統合 / 操作と画面の接続 → 代表 UI 1 本。D も同じ —— 残るのは hover そのものだけ。

B を削る条件は A と違う —— 状態を注入できるかではなく、**その状態を決めているものを引数にできるか**(`tab-widths` は「窓
の持ち物とフォント」を測定値として引数に落とした)。

**候補の機械的な洗い出しは 2 つの一致で引く**: 同じ動詞の行同士で (1) `verify/verbs/*.rs` の**その引数が当たる行**が同
じ、(2) 登録表の行が示す部品の集合(主題と、run の `census.txt` が実際に会った物)が同じ。(1) は `plain` の行で比べてはい
けない —— 行は `Arg::Is` / `WithPreset` / `Ends` で引数ごとに分かれていて、`rename-branch-box` は名前ごと、`push-hover`
は preset ごとに別の判定を持つ。両方一致しても最後はドライバの分岐を読む(`nav-open-then` の 6 行は must_say が同じでも
`afterOpen` の 6 分岐)。

**断りの文の行は、その文(= 断るかどうかの判定)を持つ QtTest が在る腕だけ `held:` にする**: `Words.nameClashed` の 4 腕と

`nameClash` / `renamedWorktreeFor` → `Words`)は別の腕の素の行が反映前に通

### QtTest の代金はテスト本体

**QtTest は各ファイルを独立した `qmltestrunner` で 1 回ずつ実行する**(`qmltest::run_each`)。QML engine の破棄では隔離で
きない型登録・plugin のプロセス状態を、別ファイルへ持ち越さない。**runner は数本を並べて立てる**(`qmltest::at_once` —
ファイルの代金は製品のタイマーを待つ本体で CPU ではないので、並べた本数ぶん壁時計が割れる。gate の予算での重みは
`budget::unit::weight_of`)。途中で赤になっても残りを全て実行し、全ての失敗をファイルの順で返す。成功するまでの再実行や、
一括 run を単独 run の成功で置き換える経路は無い。**赤い run の証拠は残す**(staging と manifest。終わりの判定・保持の
枠・置き場は `qmltest` のコメント)。ゲートは依存入力が同じ成功を再利用する。**段 3 は同じファイルを 1 プロセスでも回
す**(<!--call:qmltest.together-->`qmltest --together`): 1 本ずつ緑で一緒だと赤 = ファイルが互いに独立でない、を最初に崩
れた境界と一緒に名前付きの赤で出す。land の gate(段 2)には乗らない。

`grabImage` は窓の描画 1 回の費用を持つため、複数の部品は 1 枚の root に並べて各箱を読む(`tst_iconink.qml`)。製品のタイ
マーを検証する時間は縮めない。プロセスの代金の実測と、全件 1 プロセスで落ちた形の記録は P3-確認事項 §開発環境(QtTest の
run)。

### 1 行を消すと何が減るのか

**①実行数 → ②単独の仕事 → ③壁時計 は、間に「混雑の倍率」と「どの上限が効く区間か」の 2 つを挟まないと繋がらない**。**②を
並列数で割るだけの見積もりは外す**。

- **① 実行数** —— 数えた値で、推定は入らない。
- **② 過去ログ上の実行時間合計は混雑込みの経過時間であって、取り除ける仕事ではない**。同じ仕事が gate の中では単独の
  3〜4 倍に伸び、雛形を組んだ run や側の build を背負う run の秒は**その行の費用ですらない**。
- **③ 壁時計 — A/B で測った**。同じ木・同じ選択で登録行(当時の census)だけを 531 → 399 行に落とし、`gate --fresh` を複数
  回ずつ: **1 行 = 壁時計 0.49s**。尾では host の動詞の待ち行列が host の枠で飽和しているので、行を消せば待ち行列は短く
  なる。**ただし host の checks の鎖が床**で、動詞側がそこまで落ちれば止まる。

**上限は 2 つ在り、別のもの**。**片側の枠 = `jobs` 本**(`budget::default_jobs`)は**その側の動詞が同時に何本走れる
か**、**機械の予算**(`budget::unit::demand`)は**両側と、同じ機械の他の gate が分け合う**もの。台帳から同時実行数を数える
時は、1 秒ごとの時刻 `t` について **開始 ≦ t < 終了** の run を数える —— 区間をまたぐ run を「その秒に居た」と数えると、
続けて走った 2 本が同じ秒に二重に乗る。**区間の平均同時実行数 = 各 run とその区間の重なり時間の合計 ÷ 区間長**(run の所
要時間をまるごと足す数え方は、区間にはみ出した分まで数える)。

**`chip-menu feature/topic-a` を静かな機械で `--no-build` で回し、`PGG_LOG=info` の時刻から段を読んだ**。`whole=1491ms`
のうち、動詞の報告行までの**この census 行が在る理由の、実際の仕事**は 33ms。最初のログ行 → `opened repository tab` の
655ms は engine + 窓 + QML のロード + 設定の読み + タブを開くまでの複合。

**ここから一般化しないこと**: これは 1 ケース(`settings-tools` は**単独でも 10.1s**)。**「app の時間 = 起動」ではな

| `whole` | — | 両側 | Whole test | `git` / `picture` / `held` / `perf` / `other` |
| `twin` | — | — | — | 別の行と同じ道を通り、判定も同じか弱い。**登録表には載せない**(載っていれば `verbs` が赤) |
| `host` | host | host | Whole test | **最低版の git では別の答えになる形**(reftable のロック・設定で書く pre-push)。コンテナは段 3 でも回さない。理由は `git:` で始める |

- **段 3 の「登録表の全行」に twin は入らない** — twin は登録表に載らない。行が全部 twin の動詞はどの gate も回さず、そ
  の数は `cargo xtask verbs` の `verbs no gate runs` 行が言う
- **`whole` の行は、同じ道を通る反映前の行(寄りかかる先)を名指す**。表と登録表の整合は `cargo xtask verbs`(毎回の gate
  の常時ステップ)が検め、崩れると赤 —— 寄りかかる先を段 3 へ送ったり消したりすると、ここで止まる
- **唯一の証人の例外**(`plan::steps::owed_lines`): 変更が届いた部品を `whole` の行しか出していなければ、その行は反映前で
  も回る。対象は登録表が約束する製品部品であり、駆動コードではない
- 反映前に見えないのは Linux の時機でだけ出る競合と最低版の git でだけ壊れる UI の流れで、UI を配線したら触った動詞を
  `cargo xtask linux verify-ui` で撃つ(verify-ui スキルの完了条件)
- 行を足す時の段の決め方は rules-refs/app-ui.md「動詞の行を足したら段を決める」、段ごとの行数は `cargo xtask verbs` と
  gate の計画の `verbs:` 行、反映前の gate 1 本の代金は [gate-load](../ci/baseline/gate-load-windows-x64.md) §反映前の
  gate 1 本

**core の実 git 結合テスト**(`tests/it`)の分け方は rules-refs/core.md `periodic`。固定のコマンド行は単体が読
む(`refusing::git()` が聞いた argv — `branch::tests` / `remote::list::tests` / `remote::fetch::tests` ほか)ので、段 3 に
置くのはその行の後ろで git が書く物だけ。

## 段 1 / 段 2 / 段 3

段の中身の正本はここと §段ごとに何を回すか(gate スキル「確認は 3 段」はその要約)。

- 段 1(日常)= <!--cmd:gate.daily-->`cargo xtask gate --host-only`。差分で選んだステップの host 側だけ(コンテナ無し)。ス
  タンプは `container=false`
- 段 2(反映前)= `cargo xtask gate`。差分で選んだステップを両側で回し、動詞は段分け表で反映前に回る行を host で、`fonts`
  行だけをコンテナでも回す(§段ごとに何を回すか)。**land の gate もこの段 2**(`gate::for_landing` は `--whole` を付けな
  い)。**例外は版を動かす差分で、段 2 のまま段 3 の計画を回す**(§版を動かす変更は段 3)
- 段 3(全体)= <!--cmd:gate.whole-->`cargo xtask gate --whole`(差分を見ない。登録表の全行と `periodic` のテスト、全件 1
  プロセスの QtTest(<!--call:qmltest.together-->`qmltest --together`)を両側で回す。スタンプを読まず(`--fresh` 込み)、赤
  の後も残りを回す(`--keep-going` 込み))+ <!--call:linux.bare-->`linux bare --discover` + CI の Whole test + 性能実測

**いつ何が走るか**(各 workflow の理由はそのファイルの冒頭、一覧と runner の上の事実は P5-確認事項 §3.5 / §3.6):

| いつ | 走るもの | 中身 |
|---|---|---|
| 作業中(任意) | 段 1 | 上の段 1 |
| 反映前(席で手で — 時機は gate スキル §gate を撃つ時機・`land` の中で自動) | 段 2 | 上の段 2。全部緑なら commit に `container=true` のスタンプ |
| main が動く時(git hook) | `gate verdict` | テストではない。スタンプ(両側・on main・ff)を確かめる(§git hook) |

す(§land)。いずれも既存のキャッシュを使う。

run ごとの内訳は `target/gate-runs/<epoch>-<pid>.txt` に残る(最新 200 本)。**遅い gate の原因は内訳で読む**。**束ねた読
み**は [gate-load](../ci/baseline/gate-load-windows-x64.md)。

## 世代の掃除(`xtask::sweep`)

cargo は置き換えた成果物を消さない。`target/` を 1 世代に有界にするのが `sweep` —— gate と land の末尾で、**世代キー**が
前回 sweep 時と違う時だけ走る(<!--call:gate.whole-->`gate --whole` は無条件)。段 1(`--host-only`)はコンテナを立てずこの
木だけを掃き、コンテナのボリュームは次に Linux 側を持つ run が、ボリューム自身のスタンプで決める。

単独で撃つ: <!--cmd:sweep.now-->`cargo xtask sweep` / <!--cmd:sweep.dry-run-->`cargo xtask sweep --dry-run`。Linux 側は
同じ verb をコンテナで撃つ(`cargo xtask linux sweep` — 対象はボリューム)。生きている集合(正規集合)・消す物・recency
floor・ビルド中のロック・ボリュームの判断とその罠は `sweep.rs`(usage の `sweep` 節も同じ)。

## 計測との直列化(`xtask::still`)

`cargo xtask perf` は run の間だけ機械を止める hold を置く。ビルドは compile の chokepoint で announce して hold が消え
るのを待ち、hold は announce 済みのビルドが終わるのを待つ。セッションが撃つ cargo は pre-shell hook が hold 中に止め
る。`cargo xtask still` が今の状態を印刷する。置き場・生死の判定・天井・step の親子(`PGGDEV_STILL_UNDER`)・自分で
announce する verb・CPU 閾との関係は `still.rs` の `//!`、hook が通す物は `hook/still.rs`。
