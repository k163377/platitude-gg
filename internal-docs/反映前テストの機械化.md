# 反映前テストの機械化(gate)

**何をするか**: 変更ファイルからその依存木(逆方向の閉包 = 変更を読む全ファイル)を機械で抽出し、その範囲の**テストだけ**を両 OS で回し、緑を commit にスタンプする。`land` と git hook がそのスタンプを要求するので、**テストの選び忘れも実行漏れも main に届かない**。入口は `cargo xtask gate`(USAGE が正)。

**gate と check が撃つ cargo は全部 `--locked`**(runner のビルド・clippy・test・deny・verify の release / shipped ビルド・コンテナ側の同じ物・`linux offline`、それに `cargo xtask` の alias 自身)。`Cargo.lock` を書き換えたい cargo は「lock file needs to be updated」の赤で名乗って止まり、緑の下でロックが動く経路は無い(依存の変更は人の許可が要る = CLAUDE.md 絶対制約。ロックを本当に更新する時は人が `cargo update -p <crate>` を撃って commit する)。`cargo fmt` だけは依存を解決しないので付けない。CI(`.github/workflows/ci.yml`)の cargo も同じ綴り。付けた経緯は P3-確認事項 §check ハング調査 の `Cargo.lock` の項。

## 全体像(4 層)

| 層 | 役割 | 実体 |
|---|---|---|
| gate | 差分 → 依存木 → ステップ抽出 → 実行 → スタンプ | `crates/xtask/src/gate/`(`graph` / `plan` / `census` / `stamp` / `hooks` / `deps`) |
| land | 席で rebase(遅れていれば)→ gate → fast-forward | `crates/xtask/src/land.rs` |
| git hook | **セッションの git** による `refs/heads/main` の更新は**フル・on-main スタンプ**への ff だけ | `.githooks/reference-transaction`(`core.hooksPath` は絶対パス。SessionStart と `land` が `gate install`) |
| Claude hook | `PGG_GATE_SKIP` / `CLAUDECODE` を含むコマンドの deny / main を書く git の deny と **land の許可**(§land の許可)/ Stop で未達の反映と席の gate 状態を `systemMessage` | `crates/xtask/src/hook/` |

## 依存木(`gate::graph`)

ノードはファイル(workspace 相対、末尾 `/` はディレクトリ)。辺 `a → b` は「a が b を読む」:

**Markdown (`.md`、拡張子の大小文字を問わない)の変更はテストへ波及させない**。変更一覧には残すが、依存の辺・テスト選択の起点・ステップのキャッシュ入力から除く。コードや assets・ハーネスのディレクトリ内でも同じ。`structure` / `waits` / `docs` / `fmt` の常時チェックは残し、規約・ハーネスの整合性を確認する。コードも変わった場合は、そのコードが要求するテストを選ぶ。明示的な `--all` / `--verb` は引き続き実行対象を追加する。

- Rust: `use` / インラインの `crate::` `super::` `self::` `platitude_core::` / **素の名で始まるパス**(`mod x;` した子 = `self::x`、`use super::*` 等の glob import が持ち込む親の子と再エクスポート = `super::x`)がモジュールへ解決される(`pub use` 再エクスポートを辿る。glob 再エクスポートは候補全部)。**`mod x;` 宣言は辺ではない**(宣言は依存ではなく、宣言する root / mod.rs が全体へのハブになる)。**インライン `mod tests {}` の中の `super` は自分自身**。テストは `#[test]` / `#[tokio::test(…)]` / インライン `mod tests {` を持つファイルが定義する(`#[cfg(test)] mod x;` の宣言は違う)
- 文字列リテラル(コメント・文字・エスケープを正しく読んだ上で)が workspace のファイル / ディレクトリを名指ししていれば辺(xtask の structure が `ui/` を読む等)。ディレクトリノードは配下の全ファイルを読む。**統合バイナリ(`tests/*.rs`)のリテラルは辺にしない**(サンドボックスの fixture が実木を名指すだけ)。**パスの形をした文字列が読み取りとは限らない** — 次の 3 つは辺にしない:
  - **バイト文字列(`b"…"` / `br"…"`)** は生成物のバイト列でありパスではない(`corpus::shape::content_into` が symlink へ書く `b"../"`。自分のディレクトリに解決して、書いた側が隣の全ソースの読み手になっていた)
  - **自分を含むディレクトリ**(`../` と `starts_with("crates/")` が解決する先)。「隣の全部を読む」は全木の答えであって依存ではない
  - **`crates/xtask/verb-census.txt`** は plan の入力でステップの入力ではない(gate が動詞を選ぶために読み、動詞が書き戻す。commit 済みのそれを開くテストは無い)。辺にすると、それを名指すファイルが届く全テストの鍵に入り、land が書き直した census を commit した後の再 gate が同じ答えのために全部走る

  そして**ステップの鍵が名指すパスは、そのファイルが読むパスではない** — `plan.rs` の `core()` / `app()` / `harness()` / `qml_dirs()` が**パスを分割して綴る**のはこのため(丸ごと綴ると core の 1 ファイルの変更が plan.rs を読み手にし、そこから runner の全テストへ届く)
- `CARGO_BIN_EXE_<name>` を綴るファイルは、その名の bin root への辺(同じパッケージの `src/main.rs` / `src/bin/<name>.rs`。**`src/bin/*.rs` も各々 crate root**)。**統合バイナリのリテラルでもこれだけは辺**(バイナリを撃つテストの依存はここにしか書かれていない — `use` する先が無い)。解決しない名は unresolved
- insta snapshot は名前が言うモジュールの辺
- QML: 大文字の語が他の QML ファイル名なら型参照の辺、`#[qobject]` の型名なら app のモデルファイルへの辺
- **コメントと文字列の中身は読む前に落とす**(コメントの `Main.qml` は依存ではない)

逆閉包(reach)= 変更ファイルを読む全ファイル。**QML ノードは QML の読み手とディレクトリノードにだけ伝播**(QML 変更は Rust の単体テストに届かない。届くのは QML をディスクから読む xtask のテストだけ)。

**クレート root は宣言と再エクスポートだけ**(structure.md §上限 の下の項)— root にヘルパがあると全モジュールが root を読み、root は全モジュールへ dispatch するので、どの変更も全体に届く。xtask の `git_query` 等は `tree` / `subprocess` に、core の `type Name` は `model` に居る理由。

**木そのものへの苦情は毎回の gate が読む**(`graph::complaints`)—「全パス解決」と「root に読み手なし」の 2 つで、赤ければ**何も走らせずに拒む**。どちらも今の変更の落ち度ではないが、**解決しないパスは引かれなかった辺**で、その辺が運ぶはずだった選択が丸ごと欠ける。plan が既に持っているグラフから読むので追加のコストは無い(以前はこの 2 つを `cargo test -p xtask` の 1 本が言っていて、その 1 本が選ばれるかどうかは偶然の辺次第だった)。同じ関数を単体テストも呼ぶ。

診断: `cargo xtask gate deps --file <path> --why <path> --show` / `--history <n>`(診断はキャッシュを使わず毎回ソースから読む)。

## ステップの抽出(`gate::plan`)

| ステップ | 条件 | 側 | キャッシュキー(読むもの) |
|---|---|---|---|
| structure / waits / docs / verbs / fmt | 常時(秒。キャッシュしない) | host | — |
| `deny`(= `cargo deny check bans sources licenses`) | `deny.toml` の変更、またはビルド入力の変更(= reach 全ファイル。閉包が動くのはマニフェスト経由だけ) | host | `deny.toml` + Cargo.toml / Cargo.lock + `crates/*/Cargo.toml` |
| `clippy -p <crate>` / `linux clippy -p <crate>` | reach にそのクレートの .rs | host / linux | クレート dir + Cargo.* + toolchain(+ Dockerfile) |
| `test -p <crate> --lib\|--bin -- <module::>…` | reach の中でテストを**定義する**ファイル(`#[test]` かインライン `mod tests {`。`#[cfg(test)] mod x;` の宣言は違う)。root が含まれれば全部 | host(core / xtask は linux も) | 選んだテストファイルの**前方閉包**(それらが読む全部)+ Cargo.* |
| `test -p <crate> --test <binary> -- <module::>…` | reach の統合バイナリ(`tests/it/main.rs` と `tests/*.rs` は各々が crate root)。`main.rs` / `support/` が含まれれば全部 | host(core / xtask は linux も) | 同上 |
| `qmltest` / `linux qmltest` | reach に製品の QML(`ui/`)か `tests/qml/tst_*.qml` か `qmltest.rs`(全体の時も) | host / linux | `ui/` + `tests/qml/` + `qmltest.rs` |
| `shipped`(`target/shipped` に組む — §hook の下) | reach に QML か app の main.rs | host | app + core + Cargo.* |
| `verify-ui <行>` / `linux verify-ui …` | reach の部品を census に持つ行(+ `--verb`)。ハーネスに reach が入る時と全体検証は census の全行。絞り込み候補は比較表示のみ(次節)。**側ごとに 1 ブロックで、最初の未キャッシュの 1 本が単独でビルドし、残りはそのビルドを `--no-build` で `--jobs` 本ずつ並列に使う**(§動詞の並列。キャッシュ済みの動詞のビルドは別の tree のものかもしれないので、この実行でビルドした時だけ)。**board には載せない**(`verify::suite_words` が `--no-board` を行に入れる — 撮影も判定も census もそのままで、載せる側だけを止める。board に載るのは明示的に撃った run だけ) | host / linux | app + core + xtask の verify / demo + Cargo.*(+ Dockerfile) |
| `linux bare` | reach に app / core の .rs か QML、または Dockerfile の変更 | linux | app + core + xtask/src/linux + Dockerfile + Cargo.* |

`deny` が回すのは `bans` / `sources` / `licenses` の 3 つだけ — `advisories` は RustSec DB を github.com から取るので**段 2 はオフラインで完結させ、4 つ目は CI(`.github/workflows/ci.yml` の `deny` job)に残す**。cargo-deny 未導入は**赤**(docker / qmake と同じ扱い。スキップすると policy 未検査のまま commit にスタンプが付く)。

**ビルド入力の変更(`Cargo.toml` / `Cargo.lock` / `rust-toolchain.toml` / `clippy.toml` / `.cargo/` / `crates/*/Cargo.toml` / `crates/*/build.rs` / `crates/platitude-app/assets/` / Dockerfile)は reach を全ファイルにし、テストは filter 無しで全部回す**(`--all` と同じ。ソースのグラフには依存の更新が映らない)。**消えたソース(`.rs` / `.qml` / `qmldir`。改名の旧名も — diff は `--no-renames` で読む)も同じ** — グラフは今の木から読むので、消えたファイルには読み手の辺が立たず(`Main.qml` が消した部品を名指したままでも unresolved になるだけ)、reach がそのファイル 1 つで閉じて何も回らない(`plan::gone_source`)。**消えたテストは例外**(`tests/` 下の `.rs` と `tst_*.qml` — `plan::gone_test`)— `.rs` は自分のバイナリの外から名指されることが無く、消す時に必ず動く root / mod.rs の変更がそのバイナリ全体に届く(宣言を残せば `fmt` が解決できずに赤)。`tst_*.qml` は誰にも名指されず、`qmltest` は reach のパスで選ばれる(消えたファイルも changed として reach に立つ)。どのステップも読まない変更(docs 等)は「no step reads these」で名指し。**reach の QML 部品を census のどの行も出していなければ gate は赤**(名指し。singleton / `QtObject` root は item tree に立たないので対象外)。

## 動詞の絞り込みは比較表示に留める(`plan::verbs_in_snapshot`)

**実行するのは reach が名指す行**。census は終了時点の表示であり、途中で使った部品の履歴ではない。`settings-escape` は `SettingsDialog.escapeOut()` を呼んで閉じるため、終了時の census に `SettingsDialog` が無い。この不在を根拠に除外すると、終了処理を壊してもその検証が実行されず gate が PASS する。動詞は写真に加えて状態と操作結果も検証する。

変更部品を終了時の census に持つ行は **shadow 候補として数えるだけ**(基底 → 派生は `census::worn_by`)。singleton・Rust 等、表示部品で表せない変更では実行集合の件数を使う。**reach がハーネス(`xtask/src/verify`・`demo`)に入れば、QML への辺が無くても census の全行を実行する**。ビルド入力等で全体検証になった場合も全行。docs 等、動詞が読まない変更は候補を増やさない。

**実行数と候補数を別々に印字する**(`verbs: 353 selected; shadow candidate: 15 ...`)。候補の少なさは安全性の証明ではない。実選択への適用には、途中で閉じる popup・破棄される Loader 等も含む依存の記録と、候補外の検証を落とさない故障注入の比較が必要。

## キャッシュとスタンプ(`gate::stamp`)

ディレクトリを入力に持つステップは、Markdown を除いた配下のファイル名・モード・種別・object id から指紋を作る(`gate::inputs`)。Git のディレクトリ tree id をそのまま鍵にすると、検証済みコードの隣へ Markdown を追加・編集・削除しただけでテストが再実行されるため。ディレクトリ以外の入力はファイルの object id を使う。

ステップの緑は `(id, コマンド, 読むパスごとの object id)` の FNV-64 で `<git-common-dir>/pgg-gate/steps/<key>` に記録(ファイルは `HEAD:<path>` の object id、ディレクトリは上記の指紋。**木全体を `git ls-tree -r -t` 1 回で引く** — ステップ × 入力ごとに `rev-parse` を spawn すると、259 ステップの計画だけで分の桁になり、隣の席が gate を回していれば十分の桁になる)。同 commit の 2 度目は何も回らず、rebase で SHA が変わっても読む tree が同じなら緑のまま。`--host-only` は host 側だけ回して commit に `full=false` で記録し、フルの gate はコンテナ側だけ追加で回す(**フルのスタンプが既に在る commit へ `--host-only` を撃っても `full=false` に格下げしない** — 同じ main・同じ base のフルは残り、land が段 2 をやり直さずに済む)。`--fresh` はスタンプを無視。環境(ホストの Qt 等)はキーに入らない。

**依存木そのものも棚に載る**(`gate::reuse`): 鍵は **commit の root tree の object id + 読んだ実行ファイルの全バイトの FNV-64**、置き場は `<git-common-dir>/pgg-gate/graphs/`(席をまたいで共有 — 同じ tree へ rebase した席は隣の席が読んだ物を読む)。**未コミット・未追跡が 1 つでもある木では載せも読みもしない**(グラフは作業ツリーから読むので、commit の tree はそれを説明していない)。payload 全体のチェックサムと終端を照合し、欠損や破損があればソースから読み直す。保つのは build の後まで残る物だけ(辺・逆辺・モジュール・unresolved)で、往復は**この木自身のグラフ**で検査する(scaffolding をやめたフィールドが選択でなくここで捕まる)。実測: 730 ファイルを読むのは温まっていて 0.2s、**cargo build の直後は 5.6s**(Windows・再現する)。gate は毎回・land は 2 回払っていた。

**実行ファイルの更新時刻・コピー先は鍵に含めない**。同じ内容の runner を別名・別時刻で複写してもグラフは変わらない。プロセスごとに実行ファイルを一度読み、サイズ・時刻が同じでも内容が変われば別の鍵にする。land はビルド枠を空けるため実行中のファイルを退避・削除するので、その前に指紋を保持する。読み取り失敗も保持し、同じパスへ後から作られた別の実行ファイルをこのプロセスの reader として使わない。root tree のキーは維持する(グラフはソースだけでなく、文字列が指す任意ファイルの存在やディレクトリ配下も読む)。入力木が変わった場合は従来どおり再構築する。

`graph cache` 行は端末と `target/gate-runs/` の両方へ残る。`hit` / `miss` / `not used`、入力 tree と reader の指紋、欠損・破損・読み込み失敗・未コミット変更などの理由、保存の成否を分けて報せる。キャッシュを読めない・保存できない場合はソースから得たグラフを使い、キャッシュの不調だけでは検証を落とさない。

**再現比較(2026-09-11、Windows、入力 main `77d0d399`、同じ本体 checkout を `--dir` で読む `gate --dry-run`)**: それぞれ温めた実行ファイルを複写し、内容はそのままで更新時刻だけ変えた。変更前は計画 14.2s / graph 14.0s(再構築)、変更後は計画 0.4s / graph 0.2s(`kept`)。別セッションの UI 作業がある環境の 1 対で、絶対時間の保証ではない。因果性は回帰テストで固定する: 同一バイト・異なる時刻・別 worktree で再利用、同じ長さと時刻でもバイトが違えば再構築、入力 tree の変更・未追跡・破損で再利用しない。比較ログは計測した席の `target/graph-cache-paired-before.log` / `target/graph-cache-paired-after.log`。
run の残骸は gate が掃く: 動詞 1 本ごとに `%TEMP%` の `pgg-verify` / `pgg-demo` / `pgg-linux`(と xtask のテストの `pgg-census`)へ run 固有のディレクトリを claim して置き去りにするので、**gate は入口で 1 日より古い物を背景スレッドで消す**(`verify::sweep_yesterdays_runs`。実測 2026-09-06: 3 日で 6 万個・6GB)。**preset の雛形は run の隣に立つので同じ掃除に乗る**(掃かれた雛形は次の run が組み直す)。gate を通らない口が 1 つあり——コンテナの中には gate が居ない——ので、**雛形を組む時にも同じ掃除を撃つ**(`demo::template`。組むのは指紋 1 つにつき 1 度なので、掃除もその頻度)。絵の正本は board で、run の直下に残る PNG は 1 日で捨ててよい物。

**掃くのは run が置き去りにした物だけ**: `cargo xtask demo-repo` は人が見るために木を建てる口なので、根に `.pgg-keep` を置き、掃除はこれを持つエントリを日付に関わらず飛ばす(`verify::keep`。run が建てる木 — `demo::create` / `create_named` — には付かない)。**印に寿命は無い**(床を何日に引こうと、人がその木をいつまで開いているかは掃除には分からない)ので、**印の付いた木を消すのは人の仕事**。**開いているかは訊かない** — アプリはタブのリポジトリにハンドルを持たない(git は操作ごとのサブプロセス・ディレクトリは監視しない)ので開いている木にも「誰も掴んでいない」と答え、これから見る木は定義上誰も掴んでおらず、`pgg-linux` では掴む側が mount の向こうに居る。

commit スタンプ `<git-common-dir>/pgg-gate/commits/<sha>`: `main=` `base=` `onto_main=`(base == main)`full=` `step=…`。必要ステップが全部緑の時だけ書く。汚れた tree では `run` しない。

## 群の並走と動詞の並列(`gate::side` / `gate::verbs`)

側の中のステップは **build directory を共有しない 2 群に分けて並走させる**。**checks 群**(clippy・test・deny・qmltest・shipped — `target/debug` と `target/shipped`)は計画の順に直列で、**最初の赤で群が止まる**(ビルドが落ちた群の後続は雑音)。**built-app 群**(verify-ui の動詞と linux の `bare` — 動詞の 1 本目がビルドする `target/release` を読む側。`plan::Step::release`)はその隣で走る。先頭の always ステップ(structure / waits / docs / verbs / fmt)だけは 2 群の前に単独で回す — 秒で答え、そこの赤は人がまず直す物で、隣で動詞を回しても直しがアプリを変えて緑を無効にする。代金は同居: 動詞 1 本が host 中央値 4 s → 6 s に伸び、cold では host の checks 鎖(`test it`・`shipped`)が壁時計になる。それでも直列より 16〜22% 短い(§実測)。

動詞同士が共有するのは最初の 1 本がビルドする release だけ(repo / config / shot は run ごとに一意で atomic に claim される = verify-ui スキル)。なので側の動詞は 1 ブロック: **最初の未キャッシュの 1 本が単独で走ってビルドし(赤なら次の 1 本が単独で — 赤い 1 本目がビルドを残したとは限らない)、残りは `--no-build` で `--jobs` 本ずつ並列**。**赤い動詞はブロックを止めない** — 動詞は次の動詞が読む物を壊さず、緑は個別に stamp されるので、直した後の撃ち直しが負うのは赤だけ。ブロックに赤があれば群はブロックの後で止まる(linux の `bare` は走らない)。**例外はアプリ自体がビルドできなかった赤**(その動詞の log に `could not compile` / `cargo build --release failed`): 次の 1 本も同じソースを同じエラーまで組むだけなので、ブロックをそこで止めて回さなかった本数を名指す(直列に組めば手前の clippy が先に落ちて動詞に届かない形。並走では clippy の赤が隣で出るだけで動詞ブロックは止まらない)。

**xtask のステップは runner の複製から起動する**(`gate::runner`)。計画は `cargo run --locked -p xtask -- <verb>` と綴ったまま(stamp の鍵がどの機械でも同じ 1 行を名指すため)、実行時に `gate::launched` が先頭を複製のパスに差し替える。cargo は `target/debug` をビルドの間ロックするので、`cargo run` の launcher は 8 本並列の launcher 同士と linux 側の host launcher で待ち合っていた(実測 2026-09-06: 1 gate の host log 135 本中 16〜35 本に `Blocking waiting for file lock on build directory`、90 本に `package cache` 待ち → 複製にして 0 本と 2 本)し、並走では隣の群の `cargo test` のコンパイル中ずっと待つことになる。gate は入口で `cargo build -p xtask` を 1 度撃ち(rebase 直後の land でも木のコードになる)、`target/debug/xtask` を `target/gate-logs/xtask-runner-<pid>` に複製してそこから撃つ — 走っている自分を撃つ形は取れない(land が自分の slot を退かせている)。古い複製は次の gate が掃く(走っている run が握っている物は残る)。

`--jobs` の既定は**論理 CPU の 1/3、1〜8**(`gate::default_jobs`)。動詞 1 本 = アプリ 1 個(QML エンジン + offscreen ラスタ)+ それが起こす git で、両側が同時に走る。値の根拠は §実測。

## 機械の予算と優先キュー(`budget`)

**gate 1 本は 1 プロセスぶんの負荷ではない** — ビルドし、workspace のテストを回し、動詞を何本も回し、それを両側で同時にやる。席が同時に gate を回せばその全部が足し算になる。**数えるのは全部のステップ**: ステップ 1 個 = 1 単位で、走る前に機械共通の予算から **ticket** を取り、終わったら返す(`gate::run_one`。既にある粒度なので、まずここで導入する)。両側は同じ予算から引く — 同じ機械だから。

**重みは 2 つだけ**(`budget::weight_of` — コマンドの語で決まる): **LIGHT=1** = コンパイラを起こさない 1 プロセス(`--no-build` の動詞・structure / waits / docs / verbs / deny / qmltest・`cargo fmt`)/ **COMPILE=4** = コンパイラかテストバイナリを起こす物(clippy・test・shipped・bare・コンテナ側の同じ物・release を組む 1 本目の動詞・gate 入口の runner ビルド)。**重みは投入制御であって CPU・メモリの上限ではない**(cargo は中で並列に動く)。

**予算 = gate 1 本ぶん**(`budget::demand(jobs)` = `2 × (COMPILE + jobs × LIGHT)`。24 論理 CPU・jobs 8 で 24)。**単独 gate が自分自身を待たない値**であり、2 本目の gate は「もう 1 機械分」ではなくその中を分け合う。全プロセスが同じ `default_jobs()` から計算するので相談は要らない。`--jobs` を既定より大きく撃った gate は ticket にその値を書き、生きている ticket の最大値がプールになる(明示の指示が全員に見える)。

**優先度は 3 段**(ユーザー決定 2026-09-09): **main 反映(`Rank::Landing`)> 起動(`Rank::Launch`)> 他のテスト(`Rank::Normal`)**。起動は `cargo xtask launch` = 人が画面の前で待っている窓で、どのテストより前・land より後に入る。**数えるのはビルドと起動まで**で、立った窓自体はユーザーの物なので機械を握らない(verb を headless で撃つのはテストなので `Normal`)。

**規則は 1 文**: *待っている単位は、順序付けたキューの「空きに収まる先頭部分」に居れば走ってよい。収まらない 1 本でその先頭部分は終わる*(`budget::queue::admits`)。ここから全部出る —

- **上の段が先**: 並び順は rank → その席の中で何巡目か → 到着順(`queue::order`)
- **上の段を遅らせる仕事は入れない**(= 補充停止): 空きが足りない単位の所で歩きが止まるので、終わった単位が返した分は後ろの小さい仕事に取られず、その単位のために溜まる。予約という別の機構は要らない。**land だけでなく起動にも同じに効く**(待っている起動の前にテストは入らない / 起動は land を止めない)
- **重い単位が軽い単位に飢えない**: 収まらない 1 本を飛び越す(backfill)と、ある席の動詞 1 本 × 無限が後ろの `cargo test`(重み 4)を永久に追い越す
- **land が使わない空きは使う**: landing の単位が収まった後の残りはキューの先へ流れる

**同順位は席の持ち回り**: 待ち行列は「rank → **その席が配られた重みの累計** → 到着順」で並ぶ。動詞を 100 本積んだ席が 1 本しか積んでいない席の前に立たない。**小さい答えは 2 つとも間違う** —

- **「キューの中で何番目か」**: 1 回目は正しく a を出すが、a が着席した次の瞬間、a の 2 本目も b の 1 本目も「自分のキューの先頭」なので**また a が出る**
- **「その席が今走らせている重み」**: a の 1 本目が走っている間だけ正しい。**終わった瞬間に両方 0 になり**、古い方(= a)がまた出る

なので累計は **ticket ではなく台帳(`pgg-budget/served`)に置く** — 配った単位より長生きしないと意味がないから。重み(本数ではない)で数えるのは、分け合っているのが重みだから(`cargo test` 1 本の席は動詞 4 本の席と同じだけ取っている)。**行は「配った時」ではなく「並んだ時」に作る**: 最初から並んでいて配られていない席は配られた席より**下**に、他人の 1 時間の途中から来た席はその席と**同じ高さ**に立つ必要があり、行が無いとこの 2 つが区別できず古い方が勝つ。後から来た席の高さは「今ここに居る席の最小値」(貸しも借りも無い)。巡目は rank の中で数える(ある席の landing がその席の通常仕事を 1 巡下げない)。

**保証しないこと**: 上の段を優先したまま preempt しない以上、**land や起動が連続する間の下の段の待ち時間は保証できない**。割り込みの速さは走っている単位の長さで決まる(→ §割り込みを妨げる単位)。**起動の fast path も機械が満杯なら待つ** — 待った分はその場で 1 行言う(`waited … for room on the machine`)。

**モジュールの割り方**(`crates/xtask/src/budget/`): `queue` = 規則(ファイルも時計も触らない)/ `ledger` = 規則が読む物(プール・ticket・その下の lock)/ `unit` = 訊く側(重み・持ち物・起こしたプロセスの申告)/ `cli` = `cargo xtask budget`。`mod.rs` は宣言と再エクスポートだけ。

**台帳**は `<git-common-dir>/pgg-budget/`(`admit.lock` = 1 度に 1 つの判断 / `seq` = 到着番号 / `served` = 席ごとの累計 / `t-<seq>` と `t-<seq>.lock`)。**生死は lock**(`still` / `lanes` と同じ): 誰も握っていない ticket は死んだプロセスの物。**管理プロセスは存在しない** — 台帳が管理者で、参加者全員がそれを保つ。

**ただし「lock が空いた」は「仕事が消えた」ではない**。gate をステップの途中で殺すと、その cargo・rustc・コンテナ・アプリは走ったまま残る(unix は自前の process group、Windows は親が居ないだけ。`reap`)。そこで room を配ると、**誰も気付かないまま投入制限が破れる**。なので単位は**自分が起こしたプロセスの番号を ticket に書き**、掃除する側はその番号がまだ**走っている**間は room を返さない。

**書く場所は 1 つに決めない — spawn する所すべて**。gate のステップは渡された ticket に書く(`check::run_step`)。単体コマンドは自分の ticket が 1 個だけなのを使って、プロセス全体で 1 つの置き場(`budget::MINE`)へ書く(`budget::child_started` / `watched`)ので、`tree` の release ビルド・`verify-ui` のアプリ・`shipped` のアプリ・`linux` の docker build と docker run・`bare` / `offline` のコンテナが**関数の間にパラメータを配らずに**言える。**コンテナは特に効く** — `docker run` を起こした側を殺してもコンテナは走り続けるので、番号を書いていなければ重み 4 が消えたまま負荷だけ残る。**見えるのは docker CLI まで**で、その CLI も殺されたコンテナはプロセス表の外(`docker ps` の領分)。`cargo xtask budget` はそれを `LEFTOVER: this unit's process is gone and pid N is not` と名指す。**止めるのは人の仕事** — 残るのは cargo・コンテナ・アプリで、`cargo xtask kill` が刈るのは最後の 1 つだけ。

- **zombie は「居ない」**(`subprocess::behind` が `ps` の state を読む)。終了済みで CPU もメモリもロックも持たないのに番号だけ残る形で、**親を殺された子は誰も wait しない** — コンテナの中では PID 1 が cargo なので永久に残る。生きていると読むと room がコンテナの寿命ぶん塞がる(実測: この形で統合テストが 120 秒ハングした)
- **「訊けなかった」は「居ない」ではない**(`subprocess::listed_by_tasklist`)。`tasklist` が拒否されたり、ポリシーで制限されていたりすると一致する行が返らず、**居ないのと同じ形に見える**。この機械の claim は全部この答えで破られる(席・run・予算の room)ので、非ゼロ終了かエラー出力があれば第 3 の答え(訊けなかった = 生きている扱い)にする
- **番号は使い回される**ので、番号だけで判断しない: 単位は**起こしたプログラムの名前も同じ瞬間に書き**(`Ticket::child_name`)、掃除する側は番号と名前を 1 つの問いとして訊く(`subprocess::image_still_at`)。名前は**起こした側の綴りをそのまま**書く — 名前を読むのはプロセス 1 つぶんの費用で、gate の 700 ステップ全部で払うことになる。読む側と綴りが揃うように、書く時にプローブの語彙へ寄せる(`subprocess::as_probed`。**Linux はプロセス名を先頭 15 文字しか持たない**ので、gate の runner の複製 `xtask-runner-12345` は `ps` からは `xtask-runner-1` で返る = 全文で記録すると全ステップが他人に見える)
- **`LEFTOVER_CEILING`(90 分 = ステップが走ってよい最長)は報告であって返却ではない**。判断はプローブが全部で、経過時間はその一部でもない —— 遅れていようが**その負荷は機械に在る**ので、まだコンパイルしている占有者の room へ 4 重み分を入れるのは、この機構が止めるためだけに在る過剰購読そのもの(しかも誰も気付かない)。天井を超えた居残りは `LEFTOVER OVERDUE` として名乗り(`Ticket::overdue`。台帳は 1 度言ったことを覚えるので、覗きに来た全員が言い直さない = `Ticket::told`)、room は握ったまま。**訊けなかったプローブも同じ扱い** —— 答えられなかった問いは配ってよい理由にならない
- **代金は「人が手で終わらせる room が有り得る」こと**: 番号も名前も継いだ他人と、プローブが恒久的に拒否される機械では、そのプロセスが終わるか ticket を消すまで room は空かない。**この向きを選ぶのは、逆向き(自動返却)が「予算の 2 倍で静かに走る機械」を作り、下流の誰にも検出できないから**。そして**待つ側は永久には待たない** —— 動かないキューは `QUIET_CEILING`(30 分の完全静止)で赤くなり、その行が `LEFTOVER OVERDUE` と番号を名指す。黙って止まるのではなく、原因を名乗って落ちる
- **天井の起点は ticket を登録した時ではなく機械を渡された時**(`Ticket::ran_since`。登録時からだと、混んだ機械をキューで待った単位は走り出した最初の 1 秒で「遅れている」と報告される)
- 待ちが 1 本もいない普通の道では、この番号は誰も見ない: **ticket は持ち主が仕事を終えてから降りる**(`run_step` は子の終了を待つ)

**land 同士は受付順に 1 件ずつ**(`Pool::turn`): `land` は入口で turn を取り、rebase → gate → census → ff の全部を握ったまま進む。turn は予算の外(重み 0)で、landing の単位は別に `Rank::Landing` で取る。

**ロック順序**: 木の gate(`lanes::sole` — 待たずに拒む)→ land の turn → **計測の hold が空くのを待つ**(`still::until_free` — 何も announce しない)→ ticket → 計測へ announce(`still::busy`、`check::run_step` の中)。**単位は ticket を 1 個だけ、丸ごと取る**ので部分的に握って待ち合う形が無く、`still::hold` 側は ticket を取らないので循環しない。**hold を待つのを ticket より先にするのは診断のため** — 先に ticket を取ると、動けない単位が台帳では「running」に見えて、**キュー待ちと起動後の無進捗が区別できなくなる**。announce 自体はステップの中のままで、その隙に来た hold はそこで待つ。**admit した単位の子は親の ticket の下**(`PGG_BUDGET_HELD`。`check::run_step` が全ての子に付ける)。

**実行直前のキャッシュ再確認**(`gate::run_one`): ticket を取った直後にもう一度 stamp を見る。stamp はリポジトリの物(木の物ではない)なので、待っている間に別の席が同じ鍵を緑にしていることがある。**同時 miss は防げない**(両方走る)。**`--fresh` では見ない**(stamp を無視して走らせという指示そのもの)。

**ここで省略した動詞は「ビルドした」ではない**(`gate::Ran`)。動詞ブロックは最初の 1 本が release を組んでから残りを `--no-build` で回すので、**stamp で省略された 1 本を「組んだ」と読むと、残り全部が古いバイナリに対して緑を出す**。省略は `Ran::Stamped` として返り、ブロックは次の 1 本を単独で回す(組んだのは `Ran::Step` だけ)。

**予算は機械を余らせていないか(実測 2026-09-09、席 a、24 論理 CPU、動詞 722 本、`--fresh`、他席なし)**: 単独 gate では「予算の上限 = gate が出せる量」なので効く旋回は `--jobs` の側。**`--jobs 8` で sides 3m57s / `--jobs 16` で 3m47s** — 差は同一ステップのばらつき(54.7s ↔ 50.8s)の内で、**倍にしても縮まない**。走行中の台帳は `16/24 held, 0 waiting`(鎖が先に終わるので動詞 16 本だけ)で、その時の CPU が **85〜98%**。`--jobs 16`(動詞 32 本)にすると CPU は **45% へ落ちる** —— **余力ではなく競合**(ディスク・docker デーモン・WSL 側)で、投入を増やすと機械の稼働は下がる。**よって現在の予算は機械を余らせていない**。`--jobs` を上げるのは他の機械で測り直してからにする(CPU の数字は診断で、判定は壁時計)。

**「競合が減ったぶん投入を増やせる」は、この機械では取れない**。同じ run のログを数えると **732 ステップ中 cargo のロック待ちは 4 本だけ**(host の `package cache` 4 本 + コンテナの build directory 2 本、全部 2 つの鎖が同時に立ち上がる冒頭の数秒。**動詞 722 本には 1 本も無い** — runner の複製が既に消してある)。そして予算が機械全体を締めたことで**素で安全になった唯一の旋回が `--jobs`**(既定の「論理 CPU の 1/3」は、機械全体の制御が無かった頃の代用だった)。それを倍にしても縮まないので、**この機械に取り戻せる余力は無い**。1/3 を上げてよいのは、32 本同時でも CPU が落ちない機械を測った時だけ。

**ticket を取る場所は 2 種類だけ**: (1) **runner がステップを回す所**(`gate::run_one` / `gate::runner` / `check::run_side`)— Pool を 1 つ作ってステップごとに取る、(2) **それ自体が 1 単位である単体コマンドの入口**(`verify-ui` / `linux` / `shipped` / `launch` = `budget::standalone`)。**runner が (2) を使ってはいけない**: (2) は「このプロセスの ticket は 1 個」を前提に置き場(`budget::MINE`)を持つので、多数の ticket を持つ runner が通ると 1 本目だけが記録され、以降の子は既に降りた ticket へ書きに行く。その下は全部子で、親の許可を環境で引き継ぐ。**単体コマンドの ticket の中に入れ子は無い**(動詞が起こすビルドは動詞の分、`shipped` が起こすビルドは `shipped` の分)ので二重に数えない。**カウント外**は `perf`(機械を止める側なので ticket を取らない)と、コンパイルしない軽い verb(`structure` / `waits` / `docs` / `deny` / `qmltest` / `corpus` / `demo-repo` を素で撃った時)。

**コンテナの中は数えない — 数えるのは host 側の `linux` コマンド**。`docker run` に `PGG_BUDGET_HELD=1` を渡す(`PGG_STILL_UNDER` と同じ形)ので、中の xtask は親の ticket の下に居る。**これは必須で任意ではない**: 席の `.git` はマウントの外を指すファイルなので、**コンテナの中から台帳へ道が無い**(`budget::standalone` は台帳を探す前に印を見る)。

**印は 2 つで、付ける場所は 1 つ**(`linux::carried` が `docker run --rm` ごと組み立てて返す)。片方だけ付いた道は**機械を二重に数える道**で、`linux verify-ui` なら host 側が重み 4 を握ったまま中の動詞が自分の重みを待つ形になり、その対が並ぶと**どちらの半分も動けない機械**になる(実プロセスで再現済み)。コンテナを起こす道は 3 本(`linux <コマンド>` / `bare` / `offline`)あり、**構築子を 1 つにして「組み立てたが印を忘れた」を書けなくしてある**。4 本目は Linux ホストでコンテナを挟まずに走る道(`linux::here`)で、そこは子へ `budget::under` を付ける。

## 割り込みを妨げる単位(`gate::record`)

**preempt しないので、land が待たされる上限は「その瞬間走っている単位の長さ」**。だから gate の記録は待ち時間だけでなく**長い単位を上位 5 本、両側まとめて**言う(`longest <id> <時間> (weight N) / …`)。**次に割るならこの行が名指す物**であり、壁時計でも動詞の本数でもない。

分割の代金と制約(先に読む): 起動と fixture の費用が単位ごとに増える。**統合テストは 1 バイナリ**(core.md)なので `tests/it` は割らない — 割るなら実行集合・cwd・環境・成果物・終了コードが同一であることを機械で確かめてからにする。

**実測(2026-09-09、席 a、ステップ 730 = 動詞 720 + 10、空き機)**: 上位は `test xtask 22 linux` **38.5s** / `verify settings-tools` 26.4s / `test gate (all)` 18.2s / 動詞の重い方 16s 前後。**つまり land が最悪で待つのは 40 秒弱**で、これは動詞 1 本(中央値 4〜6s)の 6〜9 倍。**まだ割らない** — 40 秒は land 1 本(§land の実測)の 1 割に満たず、割れば起動と fixture がステップ数だけ増える。**割る時に最初に見るのはコンテナ側の `test xtask`**(host の同じモジュールは 0.6s なので、伸びているのはコンテナの起動と DrvFs 側)。それは分割ではなくコンテナの掛かりの問題で、答えも別。

## 予算の A/B(測り終わった記録 — 道具は今の木に無い)

**この節は数字の記録であって、今の木で撃てるコマンドではない**。比較相手の旧規則(側ごとのレーン)・それを選ぶ環境変数・モデル負荷を流す `budget bench` は、**`8285ca1d` を最後に木から外した**(比べる相手が決まった後も残しておく道具ではない)。撃ち直すならその commit を checkout する。

**規則を比べるので、規則以外は全部同じにする**: 同じ単位・同じ順序・同じ仕事量・同じ機械・その run 専用の台帳。実 gate ではこれが作れない(ステップは読んだ物でキャッシュされ、動詞は release ビルドに依存し、3 本同時に回すには 3 席要る)ので、**負荷は gate 1 本のモデル** —— 実測の所要時間(§実測)を `--scale` で縮めた単位列。**sleep ではなく実 CPU** を焼き(空き機で 1 度較正した仕事量を全プロセスへ配る)、COMPILE の単位は 4 スレッドで焼く。よって機械も競合も台帳もプロセス間通信も本物で、モデルなのは「どの単位が何秒か」だけ。

**このモデルが見せられない物**: 過剰購読が起こす赤(飢えた動詞が watchdog に刈られると 1 本 600s。§動詞の天井)と、実 gate のメモリ・コンテナ I/O・cargo の実際の並列度。**だからここの数字は「実 gate 3 本ならこうなる」を意味しない** — 見えていない機構が旧規則の側に付くのか新規則の側に付くのかは測っていない。**「差の下限」と読んではいけない**: 下限だと言うには、見えていない分が差を広げる向きにしか働かないことを測る必要がある。ここが言えるのは**同じ単位列・同じ仕事量を同じ機械へ流した時に、規則の違いだけでこれだけ動いた**まで。実物は §機械の予算と優先キュー の実 gate の行。

**実測(2026-09-09、席 a、Windows、24 論理 CPU、`--scale 5 --jobs 8`、予算 24、他席の gate 無し。`land queued` は landing の全単位のキュー待ちの合計、`waited` / `ran` は全プロセスの合計)**

**この A/B が見ていないもの**: コンテナ側(一時席 2 つに cold な volume を作る費用が測定より大きいので `--host-only`)と、**実 land**(land は main を進めるので、本物の main を動かさない条件では回せない。landing の位置には同じ重み・同じ時点の landing rank の実プロセスを置いた)。

受け入れの 1〜3 は**実 gate・実プロセス・実台帳**で押さえてある。

**読み方**

- **単独 gate の悪化はゼロ**(モデルで 0m37s 同値、実 gate でも差はばらつきの内)。予算が gate 1 本ぶんに取ってあるので、1 本しか居なければ誰も待たない — むしろ旧規則の側が側ごとのレーンで 2 秒待っている
- **キュー待ちの合計はほぼ動かない**(39m15s → 39m49s / 66m22s → 65m10s)。仕事の総量は同じで、**変わるのは「遅く走る」が「待ってから全速で走る」になる所** — その証拠が `ran` の −17〜22%(同じ仕事が短い実行時間で終わっている = 過剰購読が消えた)
- **land の待ちが半分近くになる**(1m17s → 0m42s)のが優先度と補充停止の効き目。旧規則にも landing の印はあった(動詞だけ)ので、差は「全単位へ広げた分 + 補充停止」
- **赤は全場面ゼロ**、単位数は規則によらず同一(1148)= 同じ検証集合を回している

**tree に gate は 1 本**: `<tree>/target/gate-running`(note)と `.lock` を握り、2 本目は 1 本目の pid と経過を名指しして拒む — 同じ build directory の同じステップを 2 度回し、互いの cargo を待ち合う(ツール呼び出しの timeout で背景へ回った gate を、終わったと思って撃ち直す形で起きる)。`--dry-run` は握らない(何も回さない)。`land` の gate も同じ lock。握っている process が消えれば空く(note は litter として上書き)。

host の run は census を書き直す(load → 自分の行 → save)ので、並列の 2 本が互いの行を失わないよう **`target/verb-census.lock` を 1 writer で握る**(`census::one_writer`。tree の中に置くと gate が拒む「未コミットの変更」になる)。書き出しは `target/verb-census.txt.part` に書いてから rename(途中で殺された run が半分の census を木に残さない)。

`check --verb` の動詞は直列(`check.rs`)。

## 動詞の天井(`verify::options::WATCHDOG_MS` = 600s)

**天井は失敗検出の backstop であって、「動詞は N 秒以内に終わる」の assert ではない**(.claude/rules/core.md §非同期・並行テスト)。run の天井は 1 つで、そこからアプリ側の watchdog(`PGG_AUTO_WATCHDOG_MS` = QML の `Timer`)・deadline スレッドの初回の覗き(天井 +10 秒)・親の刈り取り(天井 +20 秒)が全部決まる。

**120s は負荷で破れる**(実測 2026-09-08): 別セッションの gate と同居した run が `lanes host 3 verb(s) waited 4m09s / linux 4 verb(s) waited 7m54s` を出し、その回の `identity-tip` が `FAIL: identity-tip in 122.0s`。ログではアプリは起動してグラフまで到達しており(`auto_act ran=identity-tip` の後に `auto-act watchdog expired`)、同じ動詞を単独で撃つと PASS する。core 側は同じ問いを既にこの向きで解いてある(`tests/it/support/wait::OVERALL_BUDGET` = 900s、`QUIET_BUDGET` 120s の下の livelock 専用の床)。

**ただし高さは core と同じにしない** — こちら側は赤の代金が壁時計そのもので、しかも**全滅の赤では天井が動詞の本数だけ直列に積まれる**(`gate::verbs` は緑が 1 本返るまで単独で回す。「赤い 1 本目がビルドを残したとは限らない」ため)。core の 900s には無い非対称なので、その下の 600s に置く。

**代金(実測 2026-09-08、席 c、Windows、24 論理 CPU)**

- **赤 1 本の壁時計 = 天井 + 起動と QML ロード**(空き機で ~0.9s)。`--watchdog-ms 1` で 0.9s、`--watchdog-ms 300` で 2.4s。**天井に線形** —— 赤 1 本 122s → 602s。
- **全滅の赤**(QML がロードできない等、アプリ自体はビルドできている場合)は `N × 天井` が直列。QML の葉 1 枚(動詞 15 本・片側)で 31 分 → **2.5 時間**、`Theme.qml` 級(353 本)で 12 時間 → 59 時間。**どちらも今日の時点で待てる数字ではなく、実際に人が払うのは「最初の赤が出るまで」= 天井 1 本**(gate は動詞が終わるたびに赤を印字する)。ここを本当に安くするのは天井ではなく「QML がロードできなかった run を時計でなく事実で落とす」方([P3-確認事項.md](P3-確認事項.md) §check ハング調査で残った観察)。
- 緑の run は 1 秒も払わない(`Timer` は鳴らない)。600s のフル gate 1 本(動詞 710 本・両側)が `lanes host 11 verb(s) waited 6m15s / linux 41 verb(s) waited 76m03s` の同居下で 22m53s・赤なし。**事件を起こしたのと同じ条件で全部緑**。

**負荷の伸びは CPU の食い合いでは説明が付かない**(実測 2026-09-08、同じ動詞 `identity-tip` を N 並列): 単独 2.7s / 8 並列 5.5s / 24 並列(= 論理 CPU 数)7.9s / 48 並列(= 2 倍)10.8s。**2 倍の過剰購読で 4.0 倍**にしかならず、事件の 122s(45 倍以上)には遠い。つまり事件を起こした機構は未再現(メモリ圧・コンテナ側の DrvFs I/O が容疑)であり、**「実測した伸びの数倍」で高さを決めると測っていない機構に対して決めることになる**。だから backstop として置く。

**却下: 赤の撃ち直し**。最初に「watchdog 赤は 1 度撃ち直して両方赤なら赤」を書いたが、方針に照らして落とした —— 時計で出た赤を時計で薄める形で、「正しさは時間ではなく因果で待つ」に逆行する。負荷で赤が出るなら直すのは天井の高さで、判定の回数ではない。

**赤の読み方は 2 つに分かれる**(`verify::outcome` / `verify::wedge`)

| 赤 | 何が起きた | 報告 |
|---|---|---|
| `auto-act watchdog expired` | **イベントループは回っていた**(この watchdog は QML の `Timer` なので、鳴ったこと自体が証拠)。動詞の完了述語に届かなかっただけ | `the loop was turning the whole time … lanes: host N/8 held` —— その瞬間に機械が何本回していたかを添える |
| 天井で刈られた / exit 97 | プロセスが答えなくなった(ループが回っていないか、既に出た後) | `the app's own account:` 以下 5 行(駅・沈黙・写真・`lanes:`) |

2 つは排他で、`lanes:` はどちらか一方にしか出ない(同じ run の 2 度の probe は別の瞬間を指すので、2 行あると食い違う)。**「動詞が間違っている」と「機械に食われた」を分けるのは `lanes:` の数字と、その動詞を単独で 1 回撃った結果**。

## land

総時間は `land` の入口から測り、`preflight` / `queue`(land の順番待ち) / `prepare` / `rebase` / `gate` / fast-forward / 後処理を分ける。成功・失敗の結果、対象ブランチ、時間内訳を席の `target/land-runs/<epoch-nanos>-<pid>.txt` に保存し、最新 200 本を保つ。席の特定前に終了した場合は呼び出し元(判明していれば `--dir`)に保存する。失敗時の未完了区間は `unfinished` と結果の理由で読む。記録保存の失敗は警告し、反映自体の結果を変えない。gate 内部の内訳は従来どおり `target/gate-runs/` に残る。

1. branch を checkout している worktree(席)を探す。無ければ拒む(gate はそこで回す)/ 席が汚れていれば拒む — **ただし census 1 ファイルだけの汚れ(席で回した gate や動詞の書き直し)は 5 と同じ commit で land が積む** / main を持つ席があれば拒む
2. 走っている xtask が席の build slot(`<seat>/target/debug/xtask`)なら、その名前から退く(rename)。**実行中の image は置き換えられない**(Windows は `failed to remove file … (os error 5)`)ので、退かないと 5 の gate が撃つ `cargo build -p xtask` が同じ slot を書きに行って落ちる(6 の verdict は `target/hooks` の別 slot で組むので当たらず、primary の slot は退かない)。退いた複製は普通そのまま消える(**Windows でも消える** — cargo の slot は `deps/` のバイナリへのハードリンクで、走っている image でも別リンクが残っていればそのリンクは unlink できる)。消せない形(cargo がリンクでなくコピーした slot)で残った分は次の land が掃く。**席の runner から撃った land でも 5 の gate の runner ビルドは通る** — 落ちうるのは cargo が slot を差し替える段(`remove` の os error 5)だけで、rustc と link は走っている image の隣で古い `deps/` の名前を unlink して進む(2026-09-07 実測)
3. `gate install`(冪等)
4. main が branch の祖先でなければ席で `git rebase main`。止まれば `--abort` して報告
5. 席で gate(full)。赤なら止まる(branch は rebase 済みのまま、main は動かない)。**動詞が census を書き直して緑なら、land がその 1 ファイルを `chore(xtask): the verb census as the land's gate rewrote it` で席に commit してもう一度 gate する**(census はどのステップの入力でもないので、2 度目に走るのは **clippy の 2 本だけ** — clippy の鍵はクレート dir の tree id で、census はその中に居る。テストと動詞は全部キャッシュ。§依存木の 3 つ目より前は、census が全テストの鍵に入っていて 2 度目が両 OS で 4 群を回し直していた)。2 度目も書き直したら止まる — 変更でなく機械のタイミングで動いている census なので、人が 2 つの diff を読む
6. primary が main を checkout していれば `merge --ff-only`、どこにも無ければ `fetch . branch:main` → hook がスタンプを確かめる。動いたらこの land が走った permit を spent にする(§land の許可)
7. board の掃除と**席の claim の解放**。自分の claim と、プロセスが消えたセッションの claim を外す(生きている他セッションのものは残す)。反映済みの席は main の先端で空なので、letter は誰にでも渡せる — セッションが「もう頼まれない」ことを知る術は無く、デスクトップアプリの claude.exe は会話が開いている限り生き続ける(= プロセス死による roster の回収は来ない。2026-09-06 実測: 生きた claude.exe の claim が 4 席)。**そのまま作業を続ける側は次の編集で claim が戻る**(post-write hook)。間に他セッションが取っていたら `cargo xtask seat` で別の席へ移る = 温まった `target/` を失う代わりに、席が滞留しない。land しない終わり方で返すのは `cargo xtask seat release`

履歴は線形。反映後の席は main の先端に居る(`reset --hard main` 不要)。

### 反映前の完了確認

UserPromptSubmit は反映依頼を受けた時、適用中の指示・実装・レビュー指摘・必要な docs 更新・検証の照合をコンテキストへ追加する。依頼されたレビューや確認は、並列・バックグラウンド分を含めて結果を受け取り、指摘への対応と必要な再確認を終えてから land を呼ぶ。実行開始や無応答では完了としない。既知の追加作業を反映後に予定しない。外部の確認・判断が未取得なら反映を待ち、範囲を減らす場合はユーザーと合意する。最終 gate は land 内で同期実行し、PASS 前には main を動かさない。

clean な作業ツリーと gate の PASS は、まだ書いていない修正や未完了のレビューを証明しない。依頼範囲の完了はセッションが結果を確認して判断する。反映後に初めて判明した不備は、所有する席で修正・検証を完了し、未反映の branch/SHA を報告して再反映を依頼する。permit は追加の land を制限し、編集・commit・席取りは制限しない。

### land の許可(permit)

main を書くのは `cargo xtask land` だけ — セッションの git による `merge` / `push … :main` / `branch -f main` / `update-ref` は pre-shell hook が**常に deny**(前に何を付けても通らない。`PGG_ALLOW_MAIN=1` は land と無関係で、残る用途は primary checkout で直接 commit する例外 `hook/commit.rs` だけ)。land が通るかは **UserPromptSubmit hook がユーザー発話そのものから読む permit** が決める(`crates/xtask/src/hook/permit.rs`): 発話に「反映」があれば `.permits/<session>.land`(primary の `.git` の隣)を open で書き、無ければ closed で書く。pre-shell hook は land を **open の時だけ通す**。

- **発話 1 回 = main が動く land 1 回**。open を spent にするのは **main を fast-forward した land 自身**(`hook::permit::landed`)であって hook ではない。止まった land(汚れた席・赤い gate・止まった rebase)は何も消費しない — 直して同じ発話のうちに撃ち直せる。spent の後の 2 本目は deny。必要な修正・検証は続けられる
- **次の発話で消える**(spent でも open でも)。訂正・質問への答え(「1で」「OK」)・別件の承認は許可を持ち越さない。もう一度「反映」と言えばまた開く
- **ユーザーの発話でない prompt は触らない**: 要約で持ち込まれる文脈(`This session is being continued …`)と、`<task-notification>` / `<ci-monitor-event>` のようなタグで始まる機械のメッセージは open を閉じない
- 差し引く形(容器): 反映され / 反映済 / 反映前 / 未反映 / 反映漏れ / 反映するな / 反映しな / 反映せず
- deny 文は必要な修正・検証を完了して未反映の branch/SHA と残件を報告するよう案内し、完了して gate を通るまでは「マージ可」と言わせない。**Stop hook は現在のツリーの未反映 commit と未コミットファイルを数え、open なら反映未達、spent なら反映後の未反映作業を `systemMessage` で告げる**。HEAD が main に届いていても未コミットの修正を拾う。clean かつ未反映 commit が無ければ通知しない。未着手の修正や他のツリーまではこの通知で検出しない

判定語が「反映」1 語なのは実測: 全 transcript の land 592 本のうち、直前のユーザー発話が容器差し引き後に「反映」を含むのは 518 本。含まない 74 本の発話は「起動」「1で」「修正して」「チップは積むで」— この仕組みが止めるべきもの。land / merge / マージ は読まない(製品語 — merge editor・マージン・tipLanded — として、候補語を含む発話 715 本の大半に出る)。

## git hook(実測)

`reference-transaction` は `prepared` で非 0 終了すると更新を中止する(git ≥ 2.28。Windows の git 2.55 とコンテナの最低 git で確認)。

**gate が答えるのはセッションの git にだけ**。環境に `CLAUDECODE`(Claude Code が自分の起動する全プロセスに置く印)が無ければ**何も見ずに通す** — ユーザー自身の端末・IDE・アプリの窓の git は、main への直 commit も巻き戻しも自由。判定は**スクリプトが cargo を呼ぶ前**に置く(IDE の git には cargo が PATH に無く、verdict まで行けば fail closed に当たるだけだから)。verdict 側も同じ印を読む(`gate verdict` を手で撃った時とテストのため。同じ名前を綴っているかは xtask の単体テストが見る)。`cargo xtask launch` の窓は印を落として起動する(ユーザーが操作する窓なので)— 同時に自動化ノブも落とすので「何かが操っている窓の git だけ素通し」にはならない。headless の verify-ui は印を残す(操作しているのはセッション)。

**印が消えたら gate は黙って誰も止めなくなる**ので、SessionStart が印の不在を報せる(session-start は定義上セッションの中で走るので、そこに無ければ壊れている)。

セッションの git に対する verdict の規則: `old == new` は通す(**`reset --hard HEAD` も transaction を回す**)/ 削除・スタンプ無し・`full=false`・`onto_main=false`・ff でない(巻き戻し・force)は拒む / `PGG_GATE_SKIP=1` は通す(セッションは pre-shell hook が deny。`CLAUDECODE` を綴るコマンドも同じ理由で deny — 印の削除も検証を省略する設定変更に当たる)。

install(`cargo xtask gate install`。SessionStart と `land` が毎回撃つ): `.githooks/reference-transaction` を **`<git-common-dir>/pgg-gate/hooks/` に複製**し(worktree からは編集できず、席の reset / 削除で消えない)、隣の `tree` ファイルに「verdict を答える checkout」を書き、`core.hooksPath` を複製の絶対パスにする。スクリプトは `tree` へ `cd` し git の hook 環境変数を捨ててから `cargo run -p xtask --profile hooks -- gate verdict` を撃つ(build directory は §hook のもの) — **git を打った tree の xtask ではなく、install した tree の xtask が答える**(primary の main が gate 以前なら primary の xtask には `gate` が無い。席の xtask が壊れていても main が止まらない)。複製元は primary の `.githooks`、無ければ今の tree の(= 初回反映)。`core.hooksPath` に他人の値が入っていれば上書きせずエラー。

罠: `fetch . x:main` と `branch -f main` は main が checkout 済みだと git 自身のガードが先に答える(`update-ref` だけが素の書き込みで、hook が唯一の守り)/ hook の実行ビットは index で `100755`、unix では install が複製に付け直す(git は実行できない hook を**黙って**無視する)/ **セッションの git** で cargo が PATH に無ければ **fail closed**(ユーザーの git は verdict へ行かないので当たらない)/ gate が撃つ動詞は census を書き直すので、**動いたら stamp せずに赤**(生成物を commit して撃ち直す。stamp は commit を名指すので、通った木がその commit でなくなる)。

## hook は自前の build directory で動く(`--profile hooks`)

Claude Code の hook(`.claude/settings.json` の全 event)と git の `reference-transaction` は `cargo run --quiet -p xtask --profile hooks -- …` で xtask を起動する。cargo は **profile の directory(`target/<profile>/`)をビルドの間ずっとロックする**ので、`target/debug` で動く hook は、同じ tree で gate が回す `cargo test` / `clippy` のコンパイルが終わるまで待つ — ツール呼び出し 1 回・プロンプト送信・ターン終了(Stop)のそれぞれが、走っているコンパイル 1 本ぶん止まる(実測: core の check 1 本の裏で `cargo run -p xtask` が 23 秒、空きなら 0.2 秒)。`hooks` profile は `dev` を継承した同じコードで、ロックだけが `target/hooks/` の自前(`Cargo.toml`。xtask は opt-level 0 — hook の仕事はファイルを数個読むだけで、セッションが待つのはコンパイルの方)。代金は xtask のソースが変わった tree で次の hook が 1 度 xtask を組み直すこと(依存が std だけなので秒の桁)。手で撃つ `cargo xtask hook <event>` は `target/debug` の xtask(alias)で、答えは同じ。

**shipped も自前の build directory**(`--profile shipped` = `target/shipped/`、Cargo.toml): `shipped` はハーネス無しの release で、動詞はハーネス付きの release。同じ directory だと互いの binary を置き換え合う(1 gate に release の relink 2 回、動詞が読んでいる最中に `shipped` が link し直す)ので、gate は `shipped` を checks 群で動詞の隣に回す(§群の並走)。代金は tree ごとに release の複製 1 つ(実測 1.6 GB)と、CI の `cargo xtask shipped` が deps をもう 1 度組むこと(P5-確認事項 §3.5)。

## census(`gate::census`)

`WindowCensus.qml`(`platitude.auto`)が **窓が届き終わった所**で窓の**オブジェクト木**を 1 度だけ歩き、`census page=<settled|arriving> waited= state= finish= failed= stale= wipRow= wipRowStands=` と `census=A,B,…` を報告。**答えの隣の項は、行が動いた時にその run 自身に理由を名乗らせるためだけに在る**(読むのは人で、機械が読むのは答えの 1 語目と `census=` の行だけ)— `failed` / `stale` は「rows が status と一致する」を迂回する 2 つの口で、そこを通った run は**作業ツリーの行が 1 本も無い pass**で settled と答えうる。その行は `WipTallyRow` の唯一の席(`GraphRowDelegate` の loader の中。他の `Wip*` は `visible` を落として木に立ったままなので数えられる)なので、**その行と一緒に立ち消える部品はこれ 1 つ**。verify-ui は PASS した run だけを `crates/xtask/verb-census.txt`(commit する生成物)に「打ち直せる行(verb・引数・`--preset`・`--select`・`--allow-write-failure`・`--old-git`・`--other-git`・`--system-title-bar`)→ 部品名の集合」で記録する(消えたファイルの名前は次の書き込みで全行から落ちる。`--repo` / `--restore` / `--config-dir` / `--no-census` と**コンテナの中**の run は記録しない)。**基底型は派生名の下に隠れる** —— item tree が答えるのは一番外側の型だけで、`GraphFind` として置かれた物は `FindBar` とは名乗らない。なので gate は**根の型でソースを引いて基底 → 派生 → census と辿る**(`census::worn_by` / `through_wearers`)。**動詞の選択と「誰も出していない」の判定は同じこの辿りを通す** —— 片方だけだと、基底を触った変更が動詞を 1 つも選ばないか、逆に絶対に緑にならない名指しで止まる(2026-09-03 実測: `CloseToolButton` を触ると `FindBar` が名指しされ、`FindBar` は誰の census にも入りようがない)。

**歩くのは 1 回、時計では歩かない**。時計で歩くと、記録されるのは「run が見せた物」ではなく「tick が当たった物」になる — run が出して引っ込めた行は、tick が間に合った機械の census には入り、間に合わなかった機械の census には入らない(実測: `avatar-remove` の `AvatarAssignRow` は 100ms tick でしか入らず、tick を遅らせると消える)。そうなると commit 済みの生成物がアプリに触っていない作業の最中に動き、**dirty な木では gate が走らない**ので無関係な作業まで止まる。だから **gate 自身が census を書き直す**(手で撃った run に任せると、QML を変えた直後に gate が撃つ行がまさに stale なまま捨てられ、後から誰かが手で撃った時に木が汚れる)。

**歩く場所は動詞の縁ではなく「窓が届き終わった所」**(`WindowCensus.settled`)。動詞は自分が触った物が答えた時点で完了し、その裏でリポジトリはまだ読まれている — 開く時のログ走査は最初の status より先に始まるので、**作業ツリーの行(と行の上のタリー)は status が頼み直したパスで届く**。動詞の縁で歩くとその読みの手前と向こうが run ごとに入れ替わり、答えが 1 名前ぶん違う(実測 2026-09-05: `settings-eol true` は逐次 10 run 中 4・同時 10 run 中 9 で `WipTallyRow` を落とし、`file-menu-conflict both.txt --preset conflict-kinds` は同時 10 run 全部で落とした。**どの run も「settled」と答えて行を書き直していた**)。PNG は動詞の縁で撮るので**絵は census の歩きに依らない**。歩きが遅れる分は **run の終わりが待つ**(`AutoShotDriver.waitsForCensus` — overlay / scene と同じ part を 1 つ持つ)。窓が一生落ち着かない run は watchdog の担当(`shot state … census=waiting`)で、ここに通してしまう時計は無い。

**歩くのは「届き終わった後に磨かれたフレーム」で、届き終わった縁そのものではない**(`WindowCensus.arm` — 絵が頼まれて窓が settled なら `requestUpdate()` で 1 フレーム頼み、その `afterAnimating` で歩く)。木に立っているのは view が建てた delegate で、view が行を建てるのはモデルが行を渡した時ではなく、窓がフレームのために item を polish する時。近い 2 つの時点はどちらも「行の無い一覧」を記録する: **絵の callback は posted event なので、その前に積まれていた event が先に走る** — diff の行の到着はモデルの reset で、reset と次の polish の間に会った一覧は delegate を 1 つも持たない(`diff-follow` / `line-back` が `DiffRowDelegate` を落とす形)。**settled が立つ縁はデータの縁**なので、refs が届いた同じ呼び出しの中で歩くと nav の一覧はまだ行を建てていない(実測: `tab-hold 0` が refs を最後に受けた run で `NameCell NavItemDelegate NavRowBody` を落とした)。`afterAnimating` は「このフレームの item を全部 polish した」と窓が GUI スレッドで言う語で、その語とハンドラの間に走れる物は無い。フレームの前に読みが出れば settled が落ちて腕が下り、次に settled が立つ縁がもう 1 フレーム頼む。

**動詞は自分が仕掛けた物が届いてから完了する** — settled は「ページが開く時の読み」を全部名指すが、動詞が開いた diff はその外に居る(`RepoPage.diffSettling` / `DiffPane.diffSettled` が言う)。開いた diff は git のサブプロセス 1 つ向こうから届くので、報告行が `diff=true` と言う動詞(`diff-fold` 系)と、diff を開いたまま報せのバーを待つ動詞(`notice-over-diff` — 報せバリアが diff の着地も待つ)は、行が届くまで完了しない。書いた後に行を読み直す動詞(`line-back` / `diff-follow`)は、書き込みの答えの後にページが頼み直す読みが落ちる(`diffSettling`)まで待つ。**長押しは終わりが press**(`AutoActDriver.holdToEnd`): 長押しは `Metrics.holdMs` 分だけ tick の先で終わり、その間に run が押していない書き込み(開く時の fetch・動詞自身が頼んだ fetch)が答えて `writeSeq` を動かす。開始時点で張った write barrier はその答えで通り、カードが立ったまま・行が半分だけ塗られたまま・何も書かれていない絵を撮って、そのカードを census に載せる(実測: `push-tag v1.5:drift` は 500ms の長押しの 130ms で完了し、gate の負荷の下では長押しが終わった後に完了した)。腕は `expectWriteAtPress` で塞ぎ、行の `held`(ペイン経由なら `discardHunkRequested` / `askConfirmed`)で `pressedWrite` を撃つ。

**`pageSettled` は「まだ届く途中の読み」を全部名指す**(`WindowCensus`)。`state` が `""`(パスを渡されていないタブ = `open-picker`)と `"error"`(開くのを断られた = `open-not-a-repo`)はどちらも届き終わり。`"open"` は `workTree.loaded` / `refsLoaded` / `finishCount > 0` / 選択コミットの読み(`pageDetailsSettled`)に加えて、**グラフの行が status と一致していること** —— `GraphModel.wipRow`(今持っている行の先頭が作業ツリーの行か)と `WorkTree.wipRowStands`(その status なら立つべきか)が同じ値であること。両方とも**歩き自身が組み立てられる 1 つの規則**(`platitude_core::graph::wip_row_stands`)から出るので、書き写しでずれない。`finishCount > 0` だけでは足りない —— 開いた直後の 1 本目は status を待たずに走るので、作業ツリーの行を積んだかどうかはその競争の結果でしかない。歩けなかったグラフ(`failed` / `stale`)は待つ物が無いので、持っている物のまま届き終わり扱い。

**行を書き直すのは「行がもう届かないページ」を撮った run だけ**。`settled` と答えた run だけが行を書き直し、`arriving` の run は**和集合で足すだけ**にする(**言わなかった run も `arriving` 扱い** — 名前を黙って失わない側に倒す)。歩きが settled を待つようになった今、`arriving` が出るのは歩きより先に run が終わる形が入り込んだ時で、その時に**名前が消えない**ことがこの二本道の役目。これが無いと commit 済みの生成物が機械のタイミングで動き、gate を回すたびに中身の無い census コミットが要求される。

**書き換えた側が集合差を名乗る**(`census::Shift`)。353 行の生成物は**部品 1 つの増減で全行が書き換わる**ので、diff からは「新部品が全行に入った」と「1 行だけが揺れた」を見分けられない(実測: `a2cc9b9b` → `1eb65a90` の差は `op-exit-go continue --preset rebase-staged: +FileRowDelegate` の 1 行だけ、`1eb65a90` → `cbbdd660` は `+DiffReach` が 353 行・`-FileRowDelegate` が 174 行の 706 行 diff)。なので **run と gate / land の記録が、語ごとに「どの動詞の行が得た / 失った」を要約行で言う**: 全行が動いた語は `+DiffReach all 353 lines` の 1 行に畳み、**`NAMED_AT_MOST` 本以下しか動かなかった語は動詞名を並べる**(揺れはそこに出る)。少ない方から先に並ぶ。verify-ui の 1 本は自分の行の分を `(+DiffReach)` と括弧で言い、自分以外も動いた語には行数が付く。**赤くする閾値ではない** —— 判定は今までどおり「木が動いたか」だけで、これは読ませるための行。

歩き方(実測で決めた規則): 窓そのものは item でないので別に記す(`Main`)/ `children` でなく `data`(子 item + リソース)を辿る — Popup(全ダイアログ・全メニュー)は item でない / **閉じた popup とその中身は数えない**(宣言済みの全ダイアログが全動詞に付いて区別が消える)が、**閉じた popup の中も歩く**(chip のカードは閉じたメニューの中に宣言された開いたメニュー)/ Loader の中身は `item` で(popup を load すると `data` に出ない)/ **サブメニューは親の `contentData` に「行」としてしか出ない**ので `menuAt(i)` で取り、親が見えていれば見えている扱い(親の行がサブメニューの顔)/ **Control の `background` は content でも data でもない**ので名前で辿る(`AppCardFace` は全カード・全メニューの地で、この道が無いとどの動詞も出さない)/ `pragma Singleton` と `QtObject` root は木に立たないので coverage の対象外。avatar 系の 4 動詞は写真のパスが要るので verify-ui が 2×2 の PNG を合成して既定引数にする(機械パス入りの行は再現できない)。

**故障注入の限界**(2026-09-07): 葉に存在しない型を入れた木で候補 15 本と `shipped` が赤になった。ただし未知の型はモジュール全体を読めなくするため、候補外が安全である証拠にはならない。`settings` の終了時 census に pane があり、`commands-copy` に無いことも、途中で使わなかった証明にはならない。`tests/gate/selection.rs` は終了時 census から消えたダイアログの動詞に失敗を注入し、その失敗で gate がスタンプを拒むことを検査する。

**赤い QML の gate は高い**: 動詞 1 本の赤は watchdog の待ちぶんで、上の 15 本 + `shipped` で **33 分**(host のみ)。動詞を狭めることは、緑の時間だけでなく**赤の時間**も同じ比で削る。

**デモリポジトリは preset ごとに 1 度組んで、run はそれを複写する**(`demo::template`)。同じ preset は毎回同じリポジトリなので、最初に来た run が組み、以後は複写だけになる。**指紋は task runner の実体 + `git --version`** — 雛形の中身を決める入力がそのまま鍵で、xtask を組み直せば全部組み直る(`--old-git` の run もデモは実 git で組むので分かれない)。組むのは一時名で、`rename` できた 1 本が勝つ(同時に来た run は自分のを捨てて勝者を読む)。**雛形は run の隣に立つ** — 複写が書き換えるのは葉の名前 1 つで済むため。Windows では**同じディレクトリが 1 つのリポジトリの中で 2 通りに綴られる**(`.git/config` は `std::env::temp_dir()` が返す `C:/Users/WRONGW~1/…`、`gitdir` は git が解決した `C:/Users/wrongwrong/…` — 実測)ので、パス全体を置換する形は半分を取り逃がす。**git の持ち物の外で自分のパスを名乗る preset は複写せず組む**(追跡されているファイルを書き換えると、雛形が clean な所で複写だけ dirty になる)—— 現在の preset はすべて複写できる(拒否は実行時の判定 = `demo::template` の `REFUSED` 印)。**コンテナは 1 verb で終わるので、デモのディレクトリは volume**(でないと中の run は毎回雛形を組んで捨てる)。

複写の代金(2026-09-06、空き機、`demo-repo <preset>` の壁時計。xtask の起動 ~50ms 込み): `basic` 1671ms → 138ms / `tags` 1173 → 109 / `stack` 5332 → 194 / `spread` 4273 → 272 / `manytags` 4209 → 980 / `worktrees` 966 → 104 / `conflict` 463 → 68 / `empty` 146 → 51。**135 動詞のうち 66 本が `basic`**(うち 55 本は `--preset` を書かない既定)。

フル gate(`--all --fresh`、2026-09-06、空き機、24 論理 CPU、`--jobs 8`、ステップ 285 = 動詞 135 × 2 側 + テスト・clippy・shipped・bare・deny、release ビルド済み・雛形あり): **1m59s、赤なし**。checks 群と動詞を並走させる根拠の A/B(同じ木・動詞 135 × 2 側・cold は app / core / xtask のソースを touch): 直列 3m52s(cold)/ 3m03s(warm)に対し並走 3m14s / 2m23s = **−16 / −22%**。

| | 直列ステップ | 動詞 |
|---|---|---|
| host | 115s(`test it` 63s・`test xtask` 13s・`test gate` 12s・`shipped` 10s) | 598s ÷ 8 = 75s(n=135、中央値 4s) |
| linux | 78s(`test xtask` 34s・`test core` 15s) | 814s ÷ 8 = 102s(n=135、中央値 6s) |

**壁時計は直列ステップの側**で、host は `test it` 1 本がその半分以上。動詞はもう critical path に無い — デモリポジトリ生成を削っても、次に効くのは checks 鎖の方(`--jobs` を上げても動詞しか速くならない)。**gate の数字は他席の `target/gate-running` の pid が生きていない時にしか読めない**(同居した run では動詞 1 本が 7.9s まで伸びる)。動詞 1 本の中身はアプリ自身の run 4.0 s、act 完了から census が歩くまで中央値 0.17 s、残りが複写・launcher・写真。

`--jobs` の既定 8 の根拠(2026-09-05、ステップ 251 の頃): **`--jobs 8` 3m00s / `--jobs 4` 4m40s**。動詞側にしか効かないので、鎖が壁時計になった今は上げても縮まない。

差分の gate 1 本(2026-09-07、空き機、24 論理 CPU、`--jobs 8`、QML の葉 1 枚、両側 `--fresh`、release ビルド済み): **0m31s、ステップ 44(動詞 15 × 2 側)**。内訳は run の記録が言う —— gate lock 0.0s / graph 0.0s(棚)/ tree ids 0.0s / census 0.0s / plan 0.1s / prepare 0.0s / runner 0.5s / **sides 31.8s**。**棚に無い時の graph は 5.7s** で、それが計画のほぼ全部。

## 段 1 / 段 2 / 段 3

- 段 1(日常)= `cargo xtask gate --host-only`。Stop hook が「席 d は N commit ahead、gate 未実行 / host 側のみ」を `systemMessage` で告げる(block はしない)。**作業中はこれだけ** — 完了判断のために full を撃つのは 1 度で足りる
- 段 2(反映前)= `cargo xtask gate`。「マージ可」と報告する前に**席で 1 度**回す
- 段 3(フル)= `cargo xtask gate --all`(差分を見ない = 旧 `check`)+ `linux bare --discover` + 3OS CI + 性能実測

**段 2 を 2 度撃たない**。反映の指示を受けたら `land` へ渡す — land が席で rebase → gate → ff まで自分でやり、緑のステップは全部キャッシュで通る(rebase が動かした分だけが走る)。**レビューで直した後の最終検証も land の中の gate に集約する**: 直してから単独 gate を回し、その後 land がもう一度 gate を回す形は、同じ答えのために段 2 を 2 本走らせるだけ。**census も同じ** — 動詞が書き直した census を手で commit して再 gate する往復は land の仕事(上の §land 5)。

run ごとの内訳は `target/gate-runs/<epoch>-<pid>.txt` に残る(最新 200 本)。**壁時計だけでは遅い gate の原因は分からない** — 計画(グラフ・tree の listing・census)・runner のビルド・両側・予算待ち・**長い単位の上位 5 本**を別々に測って 1 ブロックで言う。`--dry-run` も同じブロックを言う(記録は残さない = 何も走っていない)。

## 計測との直列化(`xtask::still`)

`cargo xtask perf` は run の間だけ `<git-common-dir>/pgg-still` に hold を置く。ビルドは
compile の chokepoint(`tree::app_exe` / `shipped_exe`、`check::run_step` の各 step)で
announce され、始める前に hold が消えるのを待ち(最大 60 分)、逆に hold はその時点の
announce(`<git-common-dir>/pgg-busy/<pid>-<n>`)が終わるのを待つ(最大 30 分)。gate の
step は `run_step` が 1 つずつ announce し、step の子は `PGG_STILL_UNDER=1` で親の下に居て
自分では待たない(gate の verify-ui が「gate を待つ perf」を待つ deadlock の回避)。生死は
pid でなく note の隣の `.lock` を開き続けているかで判定する(殺された xtask のロックは OS が
離す)。セッションが撃つ cargo は pre-shell hook が `cargo xtask` と compile しない
sub-command だけ通し、他は hold 中 deny する。`cargo xtask still` が今の状態を印刷する。
理由は [rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md) の「計測は機械を止めて撃つ」。

## 検証

- `cargo test -p xtask`: graph の単体(バイト文字列・自分を含むディレクトリ・census を辺にしない)+ 実木の不変条件(`graph::complaints` — gate が毎回読むのと同じ関数)+ グラフの棚の往復(実木のグラフを書いて読み戻し、辺・逆辺・モジュール・unresolved が一致、欠損・改変した payload は拒否)+ `tests/gate/`(`main.rs` + `selection` / `stamps` / `hook` / `landing` / `budget`、sandbox は `support.rs`)の使い捨てリポジトリ(選択・キャッシュ・host-only・hook の全経路・赤いステップ・land の rebase → gate → ff・build slot からの退避・pseudo-run の再利用・汚れた席・衝突する rebase・`deny.toml` だけの変更・**動詞の選択**: 葉も reach の全行を保持 / 終了前に閉じたダイアログ / QML の辺が無いハーネス / shadow の件数)
- 予算は 3 段: **規則**は純関数の単体(`budget::queue` — land が先 / 席の round-robin / 巡目は rank の中 / 収まる先頭部分 / 補充停止 / 残りは先へ流れる / turn は FIFO)。**台帳**はスレッド間(`budget::tests` — 返した空きを次が取る / landing が先で待っていた gate はなお待つ / 補充停止 / 死んだ ticket と名前だけの lock の掃除 / **居残りは番号が同じでも名前が他人なら手放す** / **天井を超えても生きている子の room は返さず報告する(子が居なければ天井に関係なく返す)** / **ticket の日付は登録時ではなく機械を渡された時に付く**)。**OS が持つ部分**は実プロセス間(`tests/gate/budget.rs` — 別プロセスが待つ / landing が先に入る / **殺した保持者が機械を返す** / land の turn は 1 件ずつ / 親の ticket の下の子)。**待ちは全部、到着通知(台帳に名前が出る)か明示の解放(`--until` のファイル)で駆動する** — 時計は 1 つも無い
- Linux: `cargo xtask linux test -p xtask`(実プロセスの 5 本は `flock` 側の答え。Windows は `LockFileEx` 側)
