# 反映前テストの機械化(gate)

**何をするか**: 変更ファイルからその依存木(逆方向の閉包 = 変更を読む全ファイル)を機械で抽出し、その範囲の**テストだけ**を両 OS で回し、緑を commit にスタンプする。`land` と git hook がそのスタンプを要求するので、**テストの選び忘れも実行漏れも main に届かない**。入口は `cargo xtask gate`(USAGE が正)。

## 全体像(4 層)

| 層 | 役割 | 実体 |
|---|---|---|
| gate | 差分 → 依存木 → ステップ抽出 → 実行 → スタンプ | `crates/xtask/src/gate/`(`graph` / `plan` / `census` / `stamp` / `hooks` / `deps`) |
| land | 席で rebase(遅れていれば)→ gate → fast-forward | `crates/xtask/src/land.rs` |
| git hook | **セッションの git** による `refs/heads/main` の更新は**フル・on-main スタンプ**への ff だけ | `.githooks/reference-transaction`(`core.hooksPath` は絶対パス。SessionStart と `land` が `gate install`) |
| Claude hook | `PG_GATE_SKIP` / `CLAUDECODE` を含むコマンドの deny / Stop で席の gate 状態を `systemMessage` | `crates/xtask/src/hook/` |

## 依存木(`gate::graph`)

ノードはファイル(workspace 相対、末尾 `/` はディレクトリ)。辺 `a → b` は「a が b を読む」:

- Rust: `use` / インラインの `crate::` `super::` `self::` `platitude_core::` / **素の名で始まるパス**(`mod x;` した子 = `self::x`、`use super::*` 等の glob import が持ち込む親の子と再エクスポート = `super::x`)がモジュールへ解決される(`pub use` 再エクスポートを辿る。glob 再エクスポートは候補全部)。**`mod x;` 宣言は辺ではない**(宣言は依存ではなく、宣言する root / mod.rs が全体へのハブになる)。**インライン `mod tests {}` の中の `super` は自分自身**。テストは `#[test]` / `#[tokio::test(…)]` / インライン `mod tests {` を持つファイルが定義する(`#[cfg(test)] mod x;` の宣言は違う)
- 文字列リテラル(コメント・文字・エスケープを正しく読んだ上で)が workspace のファイル / ディレクトリを名指ししていれば辺(xtask の structure が `ui/` を読む等)。ディレクトリノードは配下の全ファイルを読む。**統合バイナリ(`tests/*.rs`)のリテラルは辺にしない**(サンドボックスの fixture が実木を名指すだけ)
- `CARGO_BIN_EXE_<name>` を綴るファイルは、その名の bin root への辺(同じパッケージの `src/main.rs` / `src/bin/<name>.rs`。**`src/bin/*.rs` も各々 crate root**)。**統合バイナリのリテラルでもこれだけは辺**(バイナリを撃つテストの依存はここにしか書かれていない — `use` する先が無い)。解決しない名は unresolved
- insta snapshot は名前が言うモジュールの辺
- QML: 大文字の語が他の QML ファイル名なら型参照の辺、`#[qobject]` の型名なら app のモデルファイルへの辺
- **コメントと文字列の中身は読む前に落とす**(コメントの `Main.qml` は依存ではない)

逆閉包(reach)= 変更ファイルを読む全ファイル。**QML ノードは QML の読み手とディレクトリノードにだけ伝播**(QML 変更は Rust の単体テストに届かない。届くのは QML をディスクから読む xtask のテストだけ)。

**クレート root は宣言と再エクスポートだけ**(structure.md §上限 の下の項。`the_crate_roots_have_no_readers_and_every_path_resolves` が守る)— root にヘルパがあると全モジュールが root を読み、root は全モジュールへ dispatch するので、どの変更も全体に届く。xtask の `git_query` 等は `tree` / `subprocess` に、core の `type Name` は `model` に居る理由。

診断: `cargo xtask gate deps --file <path> --why <path> --show` / `--history <n>`。

## ステップの抽出(`gate::plan`)

| ステップ | 条件 | 側 | キャッシュキー(読むもの) |
|---|---|---|---|
| structure / waits / docs / fmt | 常時(秒。キャッシュしない) | host | — |
| `deny`(= `cargo deny check bans sources licenses`) | `deny.toml` の変更、またはビルド入力の変更(= reach 全ファイル。閉包が動くのはマニフェスト経由だけ) | host | `deny.toml` + Cargo.toml / Cargo.lock + `crates/*/Cargo.toml` |
| `clippy -p <crate>` / `linux clippy -p <crate>` | reach にそのクレートの .rs | host / linux | クレート dir + Cargo.* + toolchain(+ Dockerfile) |
| `test -p <crate> --lib\|--bin -- <module::>…` | reach の中でテストを**定義する**ファイル(`#[test]` かインライン `mod tests {`。`#[cfg(test)] mod x;` の宣言は違う)。root が含まれれば全部 | host(core / xtask は linux も) | 選んだテストファイルの**前方閉包**(それらが読む全部)+ Cargo.* |
| `test -p <crate> --test <binary> -- <module::>…` | reach の統合バイナリ(`tests/it/main.rs` と `tests/*.rs` は各々が crate root)。`main.rs` / `support/` が含まれれば全部 | host(core / xtask は linux も) | 同上 |
| `qmltest` / `linux qmltest` | reach に製品の QML(`ui/`)か `tests/qml/tst_*.qml` か `qmltest.rs`(全体の時も) | host / linux | `ui/` + `tests/qml/` + `qmltest.rs` |
| `shipped`(`target/shipped` に組む — §hook の下) | reach に QML か app の main.rs | host | app + core + Cargo.* |
| `verify-ui <行>` / `linux verify-ui …` | census がその行で reach の部品を出したと記録している行(+ `--verb`)。**側ごとに 1 ブロックで、最初の未キャッシュの 1 本が単独でビルドし、残りはそのビルドを `--no-build` で `--jobs` 本ずつ並列に使う**(§動詞の並列。キャッシュ済みの動詞のビルドは別の tree のものかもしれないので、この実行でビルドした時だけ)。**board には載せない**(`verify::suite_words` が `--no-board` を行に入れる — 撮影も判定も census もそのままで、載せる側だけを止める。board に載るのは明示的に撃った run だけ) | host / linux | app + core + xtask の verify / demo + Cargo.*(+ Dockerfile) |
| `linux bare` | reach に app / core の .rs か QML、または Dockerfile の変更 | linux | app + core + xtask/src/linux + Dockerfile + Cargo.* |

`deny` が回すのは `bans` / `sources` / `licenses` の 3 つだけ — `advisories` は RustSec DB を github.com から取るので**段 2 はオフラインで完結させ、4 つ目は CI(`.github/workflows/ci.yml` の `deny` job)に残す**。cargo-deny 未導入は**赤**(docker / qmake と同じ扱い。スキップすると policy 未検査のまま commit にスタンプが付く)。

**ビルド入力の変更(`Cargo.toml` / `Cargo.lock` / `rust-toolchain.toml` / `clippy.toml` / `.cargo/` / `crates/*/Cargo.toml` / `crates/*/build.rs` / `crates/platitude-app/assets/` / Dockerfile)は reach を全ファイルにし、テストは filter 無しで全部回す**(`--all` と同じ。ソースのグラフには依存の更新が映らない)。**消えたソース(`.rs` / `.qml` / `qmldir`。改名の旧名も — diff は `--no-renames` で読む)も同じ** — グラフは今の木から読むので、消えたファイルには読み手の辺が立たず(`Main.qml` が消した部品を名指したままでも unresolved になるだけ)、reach がそのファイル 1 つで閉じて何も回らない(`plan::gone_source`)。**消えたテストは例外**(`tests/` 下の `.rs` と `tst_*.qml` — `plan::gone_test`)— `.rs` は自分のバイナリの外から名指されることが無く、消す時に必ず動く root / mod.rs の変更がそのバイナリ全体に届く(宣言を残せば `fmt` が解決できずに赤)。`tst_*.qml` は誰にも名指されず、`qmltest` は reach のパスで選ばれる(消えたファイルも changed として reach に立つ)。どのステップも読まない変更(docs 等)は「no step reads these」で名指し。**reach の QML 部品を census のどの行も出していなければ gate は赤**(名指し。singleton / `QtObject` root は item tree に立たないので対象外)。

## キャッシュとスタンプ(`gate::stamp`)

ステップの緑は `(id, コマンド, 読むパスごとの object id)` の FNV-64 で `<git-common-dir>/pg-gate/steps/<key>` に記録(id は `HEAD:<path>` の blob / tree の id。**木全体を `git ls-tree -r -t` 1 回で引く** — ステップ × 入力ごとに `rev-parse` を spawn すると、259 ステップの計画だけで分の桁になり、隣の席が gate を回していれば十分の桁になる)。同 commit の 2 度目は何も回らず、rebase で SHA が変わっても読む tree が同じなら緑のまま。`--host-only` は host 側だけ回して commit に `full=false` で記録し、フルの gate はコンテナ側だけ追加で回す(**フルのスタンプが既に在る commit へ `--host-only` を撃っても `full=false` に格下げしない** — 同じ main・同じ base のフルは残り、land が段 2 をやり直さずに済む)。`--fresh` はスタンプを無視。環境(ホストの Qt 等)はキーに入らない。

run の残骸は gate が掃く: 動詞 1 本ごとに `%TEMP%` の `pg-verify` / `pg-demo` / `pg-linux`(と xtask のテストの `pg-census`)へ run 固有のディレクトリを claim して置き去りにするので、**gate は入口で 1 日より古い物を背景スレッドで消す**(`verify::sweep_yesterdays_runs`。実測 2026-09-06: 3 日で 6 万個・6GB)。**preset の雛形は run の隣に立つので同じ掃除に乗る**(掃かれた雛形は次の run が組み直す)。gate を通らない口が 1 つあり——コンテナの中には gate が居ない——ので、**雛形を組む時にも同じ掃除を撃つ**(`demo::template`。組むのは指紋 1 つにつき 1 度なので、掃除もその頻度)。絵の正本は board で、run の直下に残る PNG は 1 日で捨ててよい物。

**掃くのは run が置き去りにした物だけ**: `cargo xtask demo-repo` は人が見るために木を建てる口なので、根に `.pg-keep` を置き、掃除はこれを持つエントリを日付に関わらず飛ばす(`verify::keep`。run が建てる木 — `demo::create` / `create_named` — には付かない)。**印に寿命は無い**(床を何日に引こうと、人がその木をいつまで開いているかは掃除には分からない)ので、**印の付いた木を消すのは人の仕事**。**開いているかは訊かない** — アプリはタブのリポジトリにハンドルを持たない(git は操作ごとのサブプロセス・ディレクトリは監視しない)ので開いている木にも「誰も掴んでいない」と答え、これから見る木は定義上誰も掴んでおらず、`pg-linux` では掴む側が mount の向こうに居る。

commit スタンプ `<git-common-dir>/pg-gate/commits/<sha>`: `main=` `base=` `onto_main=`(base == main)`full=` `step=…`。必要ステップが全部緑の時だけ書く。汚れた tree では `run` しない。

## 群の並走と動詞の並列(`gate::side` / `gate::verbs`)

側の中のステップは **build directory を共有しない 2 群に分けて並走させる**。**checks 群**(clippy・test・deny・qmltest・shipped — `target/debug` と `target/shipped`)は計画の順に直列で、**最初の赤で群が止まる**(ビルドが落ちた群の後続は雑音)。**built-app 群**(verify-ui の動詞と linux の `bare` — 動詞の 1 本目がビルドする `target/release` を読む側。`plan::Step::release`)はその隣で走る。先頭の always ステップ(structure / waits / docs / fmt)だけは 2 群の前に単独で回す — 秒で答え、そこの赤は人がまず直す物で、隣で動詞を回しても直しがアプリを変えて緑を無効にする。代金は同居: 動詞 1 本が host 中央値 4 s → 6 s に伸び、cold では host の checks 鎖(`test it`・`shipped`)が壁時計になる。それでも直列より 16〜22% 短い(§実測)。

動詞同士が共有するのは最初の 1 本がビルドする release だけ(repo / config / shot は run ごとに一意で atomic に claim される = verify-ui スキル)。なので側の動詞は 1 ブロック: **最初の未キャッシュの 1 本が単独で走ってビルドし(赤なら次の 1 本が単独で — 赤い 1 本目がビルドを残したとは限らない)、残りは `--no-build` で `--jobs` 本ずつ並列**。**赤い動詞はブロックを止めない** — 動詞は次の動詞が読む物を壊さず、緑は個別に stamp されるので、直した後の撃ち直しが負うのは赤だけ。ブロックに赤があれば群はブロックの後で止まる(linux の `bare` は走らない)。**例外はアプリ自体がビルドできなかった赤**(その動詞の log に `could not compile` / `cargo build --release failed`): 次の 1 本も同じソースを同じエラーまで組むだけなので、ブロックをそこで止めて回さなかった本数を名指す(直列に組めば手前の clippy が先に落ちて動詞に届かない形。並走では clippy の赤が隣で出るだけで動詞ブロックは止まらない)。

**xtask のステップは runner の複製から起動する**(`gate::runner`)。計画は `cargo run -p xtask -- <verb>` と綴ったまま(stamp の鍵がどの機械でも同じ 1 行を名指すため)、実行時に `gate::launched` が先頭を複製のパスに差し替える。cargo は `target/debug` をビルドの間ロックするので、`cargo run` の launcher は 8 本並列の launcher 同士と linux 側の host launcher で待ち合っていた(実測 2026-09-06: 1 gate の host log 135 本中 16〜35 本に `Blocking waiting for file lock on build directory`、90 本に `package cache` 待ち → 複製にして 0 本と 2 本)し、並走では隣の群の `cargo test` のコンパイル中ずっと待つことになる。gate は入口で `cargo build -p xtask` を 1 度撃ち(rebase 直後の land でも木のコードになる)、`target/debug/xtask` を `target/gate-logs/xtask-runner-<pid>` に複製してそこから撃つ — 走っている自分を撃つ形は取れない(land が自分の slot を退かせている)。古い複製は次の gate が掃く(走っている run が握っている物は残る)。

`--jobs` の既定は**論理 CPU の 1/3、1〜8**(`gate::default_jobs`)。動詞 1 本 = アプリ 1 個(QML エンジン + offscreen ラスタ)+ それが起こす git で、両側が同時に走る。値の根拠は §実測。

**動詞のレーンは機械のもの**(`lanes`): 既定の本数は gate 1 本ぶんの値で、席が同時に gate を回すとその本数が足し算になる(3 席なら 24 アプリ + 24 コンテナが 24 スレッドに乗り、動詞が軒並み遅れて watchdog が赤を出す)。なので側ごとに `<git-common-dir>/pg-lanes/<side>-<n>.lock` を既定本数だけ置き、動詞は 1 本ずつ lock を取って走る(最初の 1 本も) — **gate が何本同時に走っても側の動詞は合計でその本数**。`--jobs` は「この gate の同時本数」で、既定より大きければレーンも増える(明示の指示)。他の gate に取られて待った分は側の終わりに 1 行(`lanes: N verb(s) waited for a lane held elsewhere`)。`check --verb` はレーンを取らない(直列)。

**land の動詞はレーンの先頭に立つ**(`Lanes::new(.., landing)`): main を動かすのは land だけなのに、隣の席の素の gate と同じ列に並んでいた(実測 2026-09-05: land の動詞 2 本がレーン待ち 3 分、隣の素の gate は 8 本で 11 分)。landing の動詞はレーンを待つ間 `pg-lanes/<side>-landing-<pid>.lock` を握り、素の gate の動詞はその印を見て空いたレーンを取らずに待つ(待った分は同じ 1 行に載る)。landing 同士は分け合い、誰も握っていない印は死んだ landing の物として次に見た動詞が片付ける。

**tree に gate は 1 本**: `<tree>/target/gate-running`(note)と `.lock` を握り、2 本目は 1 本目の pid と経過を名指しして拒む — 同じ build directory の同じステップを 2 度回し、互いの cargo を待ち合う(ツール呼び出しの timeout で背景へ回った gate を、終わったと思って撃ち直す形で起きる)。`--dry-run` は握らない(何も回さない)。`land` の gate も同じ lock。握っている process が消えれば空く(note は litter として上書き)。

host の run は census を書き直す(load → 自分の行 → save)ので、並列の 2 本が互いの行を失わないよう **`target/verb-census.lock` を 1 writer で握る**(`census::one_writer`。tree の中に置くと gate が拒む「未コミットの変更」になる)。書き出しは `target/verb-census.txt.part` に書いてから rename(途中で殺された run が半分の census を木に残さない)。

`check --verb` の動詞は直列(`check.rs`)。

## land

1. branch を checkout している worktree(席)を探す。無ければ拒む(gate はそこで回す)/ 席が汚れていれば拒む / main を持つ席があれば拒む
2. 走っている xtask が席の build slot(`<seat>/target/debug/xtask`)なら、その名前から退く(rename)。**実行中の image は置き換えられない**(Windows は `failed to remove file … (os error 5)`)ので、退かないと 5 の gate が撃つ `cargo build -p xtask` が同じ slot を書きに行って落ちる(6 の verdict は `target/hooks` の別 slot で組むので当たらず、primary の slot は退かない)。退いた複製は普通そのまま消える(**Windows でも消える** — cargo の slot は `deps/` のバイナリへのハードリンクで、走っている image でも別リンクが残っていればそのリンクは unlink できる)。消せない形(cargo がリンクでなくコピーした slot)で残った分は次の land が掃く。**席の runner から撃った land でも 5 の gate の runner ビルドは通る** — 落ちうるのは cargo が slot を差し替える段(`remove` の os error 5)だけで、rustc と link は走っている image の隣で古い `deps/` の名前を unlink して進む(2026-09-07 実測)
3. `gate install`(冪等)
4. main が branch の祖先でなければ席で `git rebase main`。止まれば `--abort` して報告
5. 席で gate(full)。赤なら止まる(branch は rebase 済みのまま、main は動かない)。**動詞が census を書き直して緑なら、land がその 1 ファイルを `chore(xtask): the verb census as the land's gate rewrote it` で席に commit してもう一度 gate する**(census はどのステップの入力でもないので全部キャッシュで通る)。2 度目も書き直したら止まる — 変更でなく機械のタイミングで動いている census なので、人が 2 つの diff を読む
6. primary が main を checkout していれば `merge --ff-only`、どこにも無ければ `fetch . branch:main` → hook がスタンプを確かめる
7. board の掃除と**席の claim の解放**。自分の claim と、プロセスが消えたセッションの claim を外す(生きている他セッションのものは残す)。反映済みの席は main の先端で空なので、letter は誰にでも渡せる — セッションが「もう頼まれない」ことを知る術は無く、デスクトップアプリの claude.exe は会話が開いている限り生き続ける(= プロセス死による roster の回収は来ない。2026-09-06 実測: 生きた claude.exe の claim が 4 席)。**そのまま作業を続ける側は次の編集で claim が戻る**(post-write hook)。間に他セッションが取っていたら `cargo xtask seat` で別の席へ移る = 温まった `target/` を失う代わりに、席が滞留しない。land しない終わり方で返すのは `cargo xtask seat release`

履歴は線形。反映後の席は main の先端に居る(`reset --hard main` 不要)。

## git hook(実測)

`reference-transaction` は `prepared` で非 0 終了すると更新を中止する(git ≥ 2.28。Windows の git 2.55 とコンテナの最低 git で確認)。

**gate が答えるのはセッションの git にだけ**。環境に `CLAUDECODE`(Claude Code が自分の起動する全プロセスに置く印)が無ければ**何も見ずに通す** — ユーザー自身の端末・IDE・アプリの窓の git は、main への直 commit も巻き戻しも自由。判定は**スクリプトが cargo を呼ぶ前**に置く(IDE の git には cargo が PATH に無く、verdict まで行けば fail closed に当たるだけだから)。verdict 側も同じ印を読む(`gate verdict` を手で撃った時とテストのため。同じ名前を綴っているかは xtask の単体テストが見る)。`cargo xtask launch` の窓は印を落として起動する(ユーザーが操作する窓なので)— 同時に自動化ノブも落とすので「何かが操っている窓の git だけ素通し」にはならない。headless の verify-ui は印を残す(操作しているのはセッション)。

**印が消えたら gate は黙って誰も止めなくなる**ので、SessionStart が印の不在を報せる(session-start は定義上セッションの中で走るので、そこに無ければ壊れている)。

セッションの git に対する verdict の規則: `old == new` は通す(**`reset --hard HEAD` も transaction を回す**)/ 削除・スタンプ無し・`full=false`・`onto_main=false`・ff でない(巻き戻し・force)は拒む / `PG_GATE_SKIP=1` は通す(セッションは pre-shell hook が deny。`CLAUDECODE` を綴るコマンドも同じ理由で deny — 印を消すのは escape を綴るのと同じ)。

install(`cargo xtask gate install`。SessionStart と `land` が毎回撃つ): `.githooks/reference-transaction` を **`<git-common-dir>/pg-gate/hooks/` に複製**し(worktree からは編集できず、席の reset / 削除で消えない)、隣の `tree` ファイルに「verdict を答える checkout」を書き、`core.hooksPath` を複製の絶対パスにする。スクリプトは `tree` へ `cd` し git の hook 環境変数を捨ててから `cargo run -p xtask --profile hooks -- gate verdict` を撃つ(build directory は §hook のもの) — **git を打った tree の xtask ではなく、install した tree の xtask が答える**(primary の main が gate 以前なら primary の xtask には `gate` が無い。席の xtask が壊れていても main が止まらない)。複製元は primary の `.githooks`、無ければ今の tree の(= 初回反映)。`core.hooksPath` に他人の値が入っていれば上書きせずエラー。

罠: `fetch . x:main` と `branch -f main` は main が checkout 済みだと git 自身のガードが先に答える(`update-ref` だけが素の書き込みで、hook が唯一の守り)/ hook の実行ビットは index で `100755`、unix では install が複製に付け直す(git は実行できない hook を**黙って**無視する)/ **セッションの git** で cargo が PATH に無ければ **fail closed**(ユーザーの git は verdict へ行かないので当たらない)/ gate が撃つ動詞は census を書き直すので、**動いたら stamp せずに赤**(生成物を commit して撃ち直す。stamp は commit を名指すので、通った木がその commit でなくなる)。

## hook は自前の build directory で動く(`--profile hooks`)

Claude Code の hook(`.claude/settings.json` の全 event)と git の `reference-transaction` は `cargo run --quiet -p xtask --profile hooks -- …` で xtask を起動する。cargo は **profile の directory(`target/<profile>/`)をビルドの間ずっとロックする**ので、`target/debug` で動く hook は、同じ tree で gate が回す `cargo test` / `clippy` のコンパイルが終わるまで待つ — ツール呼び出し 1 回・プロンプト送信・ターン終了(Stop)のそれぞれが、走っているコンパイル 1 本ぶん止まる(実測: core の check 1 本の裏で `cargo run -p xtask` が 23 秒、空きなら 0.2 秒)。`hooks` profile は `dev` を継承した同じコードで、ロックだけが `target/hooks/` の自前(`Cargo.toml`。xtask は opt-level 0 — hook の仕事はファイルを数個読むだけで、セッションが待つのはコンパイルの方)。代金は xtask のソースが変わった tree で次の hook が 1 度 xtask を組み直すこと(依存が std だけなので秒の桁)。手で撃つ `cargo xtask hook <event>` は `target/debug` の xtask(alias)で、答えは同じ。

**shipped も自前の build directory**(`--profile shipped` = `target/shipped/`、Cargo.toml): `shipped` はハーネス無しの release で、動詞はハーネス付きの release。同じ directory だと互いの binary を置き換え合う(1 gate に release の relink 2 回、動詞が読んでいる最中に `shipped` が link し直す)ので、gate は `shipped` を checks 群で動詞の隣に回す(§群の並走)。代金は tree ごとに release の複製 1 つ(実測 1.6 GB)と、CI の `cargo xtask shipped` が deps をもう 1 度組むこと(P5-確認事項 §3.5)。

## census(`gate::census`)

`WindowCensus.qml`(`platitude.auto`)が **窓が届き終わった所**で窓の**オブジェクト木**を 1 度だけ歩き、`census page=<settled|arriving> waited= state= finish= failed= stale= wipRow= wipRowStands=` と `census=A,B,…` を報告。**答えの隣の項は、行が動いた時にその run 自身に理由を名乗らせるためだけに在る**(読むのは人で、機械が読むのは答えの 1 語目と `census=` の行だけ)— `failed` / `stale` は「rows が status と一致する」を迂回する 2 つの口で、そこを通った run は**作業ツリーの行が 1 本も無い pass**で settled と答えうる。その行は `WipTallyRow` の唯一の席(`GraphRowDelegate` の loader の中。他の `Wip*` は `visible` を落として木に立ったままなので数えられる)なので、**その行と一緒に立ち消える部品はこれ 1 つ**。verify-ui は PASS した run だけを `crates/xtask/verb-census.txt`(commit する生成物)に「打ち直せる行(verb・引数・`--preset`・`--select`・`--allow-write-failure`・`--old-git`・`--other-git`・`--system-title-bar`)→ 部品名の集合」で記録する(消えたファイルの名前は次の書き込みで全行から落ちる。`--repo` / `--restore` / `--config-dir` / `--no-census` と**コンテナの中**の run は記録しない)。**基底型は派生名の下に隠れる** —— item tree が答えるのは一番外側の型だけで、`GraphFind` として置かれた物は `FindBar` とは名乗らない。なので gate は**根の型でソースを引いて基底 → 派生 → census と辿る**(`census::worn_by` / `through_wearers`)。**動詞の選択と「誰も出していない」の判定は同じこの辿りを通す** —— 片方だけだと、基底を触った変更が動詞を 1 つも選ばないか、逆に絶対に緑にならない名指しで止まる(2026-09-03 実測: `CloseToolButton` を触ると `FindBar` が名指しされ、`FindBar` は誰の census にも入りようがない)。

**歩くのは 1 回、時計では歩かない**。時計で歩くと、記録されるのは「run が見せた物」ではなく「tick が当たった物」になる — run が出して引っ込めた行は、tick が間に合った機械の census には入り、間に合わなかった機械の census には入らない(実測: `avatar-remove` の `AvatarAssignRow` は 100ms tick でしか入らず、tick を遅らせると消える)。そうなると commit 済みの生成物がアプリに触っていない作業の最中に動き、**dirty な木では gate が走らない**ので無関係な作業まで止まる。だから **gate 自身が census を書き直す**(手で撃った run に任せると、QML を変えた直後に gate が撃つ行がまさに stale なまま捨てられ、後から誰かが手で撃った時に木が汚れる)。

**歩く場所は動詞の縁ではなく「窓が届き終わった所」**(`WindowCensus.settled`)。動詞は自分が触った物が答えた時点で完了し、その裏でリポジトリはまだ読まれている — 開く時のログ走査は最初の status より先に始まるので、**作業ツリーの行(と行の上のタリー)は status が頼み直したパスで届く**。動詞の縁で歩くとその読みの手前と向こうが run ごとに入れ替わり、答えが 1 名前ぶん違う(実測 2026-09-05: `settings-eol true` は逐次 10 run 中 4・同時 10 run 中 9 で `WipTallyRow` を落とし、`file-menu-conflict both.txt --preset conflict-kinds` は同時 10 run 全部で落とした。**どの run も「settled」と答えて行を書き直していた**)。PNG は動詞の縁で撮るので**絵は census の歩きに依らない**。歩きが遅れる分は **run の終わりが待つ**(`AutoShotDriver.waitsForCensus` — overlay / scene と同じ part を 1 つ持つ)。窓が一生落ち着かない run は watchdog の担当(`shot state … census=waiting`)で、ここに通してしまう時計は無い。

**`pageSettled` は「まだ届く途中の読み」を全部名指す**(`WindowCensus`)。`state` が `""`(パスを渡されていないタブ = `open-picker`)と `"error"`(開くのを断られた = `open-not-a-repo`)はどちらも届き終わり。`"open"` は `workTree.loaded` / `refsLoaded` / `finishCount > 0` / 選択コミットの読み(`pageDetailsSettled`)に加えて、**グラフの行が status と一致していること** —— `GraphModel.wipRow`(今持っている行の先頭が作業ツリーの行か)と `WorkTree.wipRowStands`(その status なら立つべきか)が同じ値であること。両方とも**歩き自身が組み立てられる 1 つの規則**(`platitude_core::graph::wip_row_stands`)から出るので、書き写しでずれない。`finishCount > 0` だけでは足りない —— 開いた直後の 1 本目は status を待たずに走るので、作業ツリーの行を積んだかどうかはその競争の結果でしかない。歩けなかったグラフ(`failed` / `stale`)は待つ物が無いので、持っている物のまま届き終わり扱い。

**行を書き直すのは「行がもう届かないページ」を撮った run だけ**。`settled` と答えた run だけが行を書き直し、`arriving` の run は**和集合で足すだけ**にする(**言わなかった run も `arriving` 扱い** — 名前を黙って失わない側に倒す)。歩きが settled を待つようになった今、`arriving` が出るのは歩きより先に run が終わる形が入り込んだ時で、その時に**名前が消えない**ことがこの二本道の役目。これが無いと commit 済みの生成物が機械のタイミングで動き、gate を回すたびに中身の無い census コミットが要求される。

歩き方(実測で決めた規則): 窓そのものは item でないので別に記す(`Main`)/ `children` でなく `data`(子 item + リソース)を辿る — Popup(全ダイアログ・全メニュー)は item でない / **閉じた popup とその中身は数えない**(宣言済みの全ダイアログが全動詞に付いて区別が消える)が、**閉じた popup の中も歩く**(chip のカードは閉じたメニューの中に宣言された開いたメニュー)/ Loader の中身は `item` で(popup を load すると `data` に出ない)/ **サブメニューは親の `contentData` に「行」としてしか出ない**ので `menuAt(i)` で取り、親が見えていれば見えている扱い(親の行がサブメニューの顔)/ **Control の `background` は content でも data でもない**ので名前で辿る(`AppCardFace` は全カード・全メニューの地で、この道が無いとどの動詞も出さない)/ `pragma Singleton` と `QtObject` root は木に立たないので coverage の対象外。avatar 系の 4 動詞は写真のパスが要るので verify-ui が 2×2 の PNG を合成して既定引数にする(機械パス入りの行は再現できない)。

## 計測との直列化(`xtask::still`)

`cargo xtask perf` は run の間だけ `<git-common-dir>/pg-still` に hold を置く。ビルドは
compile の chokepoint(`tree::app_exe` / `shipped_exe`、`check::run_step` の各 step)で
announce され、始める前に hold が消えるのを待ち(最大 60 分)、逆に hold はその時点の
announce(`<git-common-dir>/pg-busy/<pid>-<n>`)が終わるのを待つ(最大 30 分)。gate の
step は `run_step` が 1 つずつ announce し、step の子は `PG_STILL_UNDER=1` で親の下に居て
自分では待たない(gate の verify-ui が「gate を待つ perf」を待つ deadlock の回避)。生死は
pid でなく note の隣の `.lock` を開き続けているかで判定する(殺された xtask のロックは OS が
離す)。セッションが撃つ cargo は pre-shell hook が `cargo xtask` と compile しない
sub-command だけ通し、他は hold 中 deny する。`cargo xtask still` が今の状態を印刷する。
理由は [rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md) の「計測は機械を止めて撃つ」。
