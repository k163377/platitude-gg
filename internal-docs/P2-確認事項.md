**「決定済み」は承認済み**。「要判断」は未決定で、UI 配線の前に決める必要がある。

## 決定済み

### 1. `checkout` ではなく `switch` / `restore` を使う（承認済み）

**内部コマンドと UI 表記は意図して分ける**という全体方針が確立した。
内部は最新 git の適切なコマンド、UI 文言は操作の意味を最もよく表す語を選ぶ。
用語表は [デザイン規約.md](デザイン規約.md#用語ui-文言) が正本
（ブランチ移動は **Switch to `<branch>`**、未コミット変更があるときは
「置いていく / 持っていく」を選ばせる）。

### 2. `GIT_LITERAL_PATHSPECS` を撤去し、`:(literal)` を個別に付ける（承認済み・UI に出ない内部判断）

環境変数は git 内部で使う pathspec magic まで無効化する。**実測: この変数が有ると
`git stash push -u` が「Saved working directory」と表示して exit 0 しながら、
untracked ファイルを一切 stash しない**。無言のデータ取りこぼしになる。
git 出力由来のパスは 1 件ずつ `:(literal)` で包む方式に変更した。
`git diff --no-index` の引数は pathspec ではないので付けない。

### 3. コミットメッセージの受け渡し

`<git_dir>/platitude/` のスクラッチファイル + `--file`。stdin は常に閉じたままにする
方針を維持するため。`--cleanup=whitespace` を明示固定し、リポジトリ側の
`commit.cleanup` 設定がエディタの内容を書き換えないようにした
（ユーザーが打った `#` 始まりの行が消えない）。hooks は git に委譲（`--no-verify` を渡さない）。

### 4. 失敗メッセージは stderr 優先・空なら stdout（承認済み）

`git commit` は「nothing to commit」を **stdout** に出して exit 1 する。
stderr だけを見るとエラー表示が空になるため、フォールバックを入れた。

### 4.5. auto fetch = 既定 1 分・0（入力空欄）で off・上限 60 分（**ユーザー指示**）

`RepoSession` がインターバルのタイマーを持ち、`Hub` がアプリ全体の値を保持して
新しいタブにも適用する。**同時に走る auto fetch は常に 1 本**（tokio の
Semaphore パーミットを write リクエストに持たせ、前回が終わるまでの tick は捨てる）。

`git fetch --prune --all` の失敗は**共有のエラー表示に出さない**。単にオフラインな
ノート PC が 1 分ごとにエラーバナーを出すのは無意味なので、op 名を `auto-fetch` に
分けてツールバーの `↻` インジケータ（色 + tooltip）だけに出す。手動 fetch は通常の
エラー経路のまま。

**設定の永続化は P4**。それまでは起動ごとに既定へ戻る（ダイアログにその旨を表示）。

### 5. ネットワーク系のタイムアウト = 180 秒（既定・設定で引き上げ可）

3 分あれば低速回線でも大規模リポジトリの通常 fetch は収まり、
ハングした接続を長時間生かし続けることもない。
セッションが値を保持し `setNetworkTimeout(seconds)` で引き上げられる
（**設定の永続化は P4**。それまでは起動ごとに既定へ戻る）。

### 6. `--force-with-lease` は expect の明示を推奨する形にした

裸の `--force-with-lease` はローカルの remote-tracking ref と照合するため、
**P4 の auto fetch が裏で ref を進めると安全網として機能しない**。
`PushForce::WithLease { expect }` でユーザーが実際に見ていたコミットを渡せるようにした。
UI 配線時にどちらを既定にするかは要判断（推奨: expect 明示）。

## 決定済み(UI 配線で確定)

### A. 破壊的操作の確認ダイアログ方針(**決定済み**)

実装計画 §5 で「ここで確立する」とされた項目。core 側は確認を一切しない
（`discard` / `clean` / `stash drop` / `branch -D` / force push / リモートブランチ削除は
そのまま実行する）ので、方針は UI 側で決めた。

**方針: 取り返しがつかないものだけ確認する。** 日常操作（stage / commit / switch /
fetch / 通常 push）は一切尋ねない — 毎回出る確認は「読まずに押すもの」になり、
本当に危ない場面での効き目まで削る。

確認を出す操作:

| 操作 | 失うもの | 実装 |
|---|---|---|
| force push | リモートの履歴 | 済(ボタンの長押し。右クリック経由のみ `root.confirm`。どちらも behind 数 = 相手が失うコミット数を時点付きで出す) |
| discard（unstaged 破棄） | 作業内容 | UI 未配線 |
| clean（untracked 削除） | ファイルそのもの | UI 未配線 |
| stash drop | stash 1 件 | UI 未配線 |
| branch -D（未マージ） | ブランチの指す先 | UI 未配線 |
| リモートブランチ削除 | リモートの ref | UI 未配線 |

**push 済みコミットのローカル書き換え(amend / squash / reword)は確認しない**
(切り替え・reset で戻せるし、広めるのは push 側が尋ねる)。要望の「警告を表示」は
**尋ねずに言う**形で満たす: amend チェック横の `already pushed` タグ・squash
メニュー行の同タグ・メッセージ保存行の警告行(いずれも警告色。実行は止めない)。

確認は**対象が見えている場所で聞く**のが基本(グラフ行 = チップ列の質問ストリップ、
編集テキスト = 保存行の差し替え)。`Main.qml` の
`root.confirm(heading, detail, acceptText, action)` が残る用途は force push の
メニュー経路と、対象行がグラフのウィンドウ外にある時の代役のみ。
文言は操作側が渡す（何を失うかは操作ごとに違うため）。

### B. 複数選択の一括操作

パスはブリッジを 1 件ずつ渡す（git のパスは NUL 以外どの文字も含み得るため、
1 本の文字列に詰める安全な区切り文字が無い）。
複数ファイルをまとめて stage する UI を作る場合、QML から N 回呼ぶ形になる。
セッションが直列化するので競合はしないが、N 回の git 実行になる。
一括が必要なら「選択集合を Rust 側に保持するモデル」を足す判断が要る。

### C. stage all / unstage all のセマンティクス

現状 `git add -A`（untracked 含む全部）と `git reset`（index を HEAD に戻す）。
GitKraken の "Stage all changes" は untracked を含む挙動なので合わせたが、
untracked を含めない案（`git add -u`）もある。

### D. hunk / 行選択のエンコード(**決定済み・文字列 spec は廃止**)

当初の `"1;3:0,4"` という文字列 spec は**使わずに終わった**。diff の各行が
自分の hunk 番号と hunk 内行番号を持つようにしたので、UI はクリックした行の
インデックスをそのまま `stageSelection(kind, path, origPath, hunk, line)` に渡す
（`line < 0` = hunk 全体）。パースが無ければズレようが無い。

インデックスは**表示中の diff 行位置そのもの**なので、適用後は diff の意味が変わる。
core 側は選択適用時に同じ diff コマンドを再実行して raw バイトから組み直す
（ズレていれば `git apply` が弾く）。UI は stage / unstage 完了時に diff を再取得する。

### E. 未マージブランチ削除の導線（**決定済み**）

削除は常に `-d` で試し、**失敗したら「未マージです。強制削除しますか」を出す**。
事前判定（`branch::is_merged_into`）はメニュー文言を変えたい場合の予備として残す。

### F. ブリッジへ出す core 機能の取捨（**決定済み・配線済み**）

| core の機能 | 判断 | 出し方 |
|---|---|---|
| 空コミット（`--allow-empty`） | 出さない | Commit は staged が 1 件以上ある時だけ通る（amend を除く）。空コミットを発行する導線は持たない |
| amend の `--reset-author` | 出す | **HEAD の author が現在の identity と違う時だけ** amend パネルにチェックを出す。付けると author date も now になる |
| `stash push --staged` | 出す | Stash ダイアログの選択肢。**部分ステージのファイル（status `MM`）がある間は無効化**（理由も出す）。untracked を含める指定との併用も塞ぐ |
| パス限定 stash | 出す | 変更ファイル行から「このファイルだけ退避」 |
| `hunk_count` | 出さない | hunk 数は diff 行モデルから UI 側で数えられる |

`--staged` を事前に塞ぐ理由（実測）: 同じファイルに staged と unstaged が
両方あると、git は**stash エントリを作った上で作業ツリーの除去に失敗し**
`Cannot remove worktree changes` で exit 1 する。作業ツリーと index は
1 バイトも変わらないので失うものは無いが、「エラーが出たのに stash だけ増える」
という一番読めない着地になる。`MM` は status から確実に判るので UI 側で塞ぐ。
`--include-untracked` との併用は git 自身が拒否する。
`--staged` で作った stash を staged のまま戻すには `pop --index` が要る
（素の pop では unstaged として戻る）。

## UI 実装時に必ず作るもの

### 起動時の identity 入力導線（**決定済み**）

`user.name` / `user.email` が未設定なら、**使い始めに入力させる**。
セッションはリポジトリを開いた時点で検出し、`identityReady` が false になる。
入力は `setIdentity(name, email, global)`。**`global=true` を既定**にする
（答えは「その人」についてであってプロジェクトではない）。

使用開始後に設定がクリアされたようなケースは、git の生エラーをそのまま見せる
（想定外の状態を隠さない）。

### 同名ローカルが在るリモートブランチへの移動(**実装済み**)

`Track`(`switch -c --track`)は**名前が埋まっていると fatal で落ちる**。
グラフのリモートチップをダブルクリックする導線ができて日常的に踏むようになったので、
`CheckoutTarget::ForceCreate`(`switch --force-create`)を足した — ローカルブランチを
その位置へ動かして着地するまでを **1 コマンド**で行う(git がどちらもやるか
どちらもやらないかなので、途中で片方だけ成立しない)。未コミット変更が邪魔なら
従来どおり丸ごと拒否されるので、`carry` → 「置いていく / 持っていく」の経路はそのまま効く。

`--track` は**渡さない**。既にあるブランチは与えられた upstream を持っており、
それを動かすことは upstream について何も言っていない。

UI はここだけ確認を出す(規約 §グラフ行のダブルクリック)。**ローカルにしか無い
コミットが誰からも指されなくなる唯一の経路**だから。
**捨てるものが無い場合も尋ねる(ユーザー指示・決定済み)**。`branch::is_merged_into`
で fast-forward かどうかは判るが、条件によって出たり出なかったりする確認は、
出た時に何を意味するのかが読めなくなる。この 1 問はいつも同じことを訊く。

### 未コミット変更がある状態での switch(**実装済み**)

デザイン規約の決定どおり**まず持っていく**（素の `git switch`）。
git が拒否した時だけ `SessionEvent::MoveBlocked` を出し、UI が
「置いていく（`checkout_stashing`）/ 持っていく（`checkout_merging`）」を選ばせる。
どちらも**1 つの write ジョブ**にした — 2 回キューに積むと、前半が失敗しても
switch が走って変更が移動先へ付いていく。stash のメッセージは git 既定の
`WIP on <branch>: …` のまま（どこから来たかを既に語る）。

「持っていく」は **stash → switch → `stash pop --index`**。`switch --merge` を
使わない理由は [デザイン規約.md](デザイン規約.md) の該当節にある（staged の区別が
残る / conflict しても stash が残って戻れる）。**pop の非ゼロ終了は失敗とは限らない** —
作業ツリー側の conflict なら適用済みなので、status の unmerged 有無で判定する
（`conflicts_now`）。staged 側の衝突で丸ごと拒否された時だけ `--index` 無しで
やり直し、そこでは区別を諦める。

拒否理由の判別は**git のメッセージ照合**（`branch::CheckoutBlock::from_message`）。
git に機械可読な答えが無く、「tracked は merge で通せる / untracked は stash しか
無い」で出す選択肢が変わるための例外。`LC_ALL=C` 固定なので文言は C ロケールのもの。
**照合できなければ `None` を返して通常のエラー経路**へ流す（文言が変わって困るのは
ダイアログだけで、正しさは損なわれない）。

### push の宛先解決は core が行う(**実装済み**)

`remote::plan_current_push` が `branch.<name>.remote` / `.merge` を読む。
upstream 未設定なら既定リモート（`origin` があればそれ、無ければ最初の 1 つ）へ
`--set-upstream` 付きで送る。**`origin/main` という文字列を分割して解決しない** —
リモート名に `/` が含まれ得る（`my/fork`）ため、確実に割れない。

force push は `--force-with-lease=<branch>:<oid>` で、**画面に出ていたリモートの
コミット**を expect に渡す（裸の lease は auto fetch が裏で ref を進めると
ただの force に化ける）。

## 既知の制限・残課題

- **末尾改行が無いファイルへの行追加を部分ステージできない（許容）**: 最終行に改行が
  無い場合、その後ろへ行を足す変更は「最終行に改行を足す」変更と不可分で、追加行だけを
  選んだ patch は unified diff として表現できない（pre-image と食い違い git が
  `patch does not apply` で拒否する）。**前提となる行を自動で選択に足す回避策は入れない**
  — 選んでいない行を黙って index に入れる方が害が大きい。最終行を**選ばず残すだけ**の
  ケースは、`\ No newline` マーカーが降格した context 行へ引き継がれるので通る。
- **untracked ディレクトリ**: `status -uall` で新規ディレクトリの中身をファイル単位に展開する。
  中の 1 ファイルだけを部分ステージできる代わりに、そのディレクトリの全ファイルを
  discard すると空のディレクトリがディスクに残る（git は空ディレクトリを追跡しないので
  status は clean のまま）。
- **ブリッジ未公開の core 機能**: `--allow-empty` と `hunk_count`。どちらも
  **出さない**判断（「決定済み(UI 配線で確定)」の F）。
- **設定の永続化が無い**（P4）: auto fetch の間隔・ネットワークタイムアウトは
  起動ごとに既定へ戻る。
- **数値入力欄の幅**: 設定ダイアログの分数入力に `160`（デザイン規約のレイアウト表に
  ある唯一の「入力欄の幅」＝検索ボックス）を流用した。分数には広い。
  小さい数値入力用のトークンを足すかは**要判断**。
- **署名の UI 表示**: `identity::verify_commit()` で署名状態を取れるが、
  コミット詳細への表示は未実装（P5 の diff 強化と同時が自然）。
  `signingActive` / `signingFormat` はブリッジに出してある。
