# Phase 2 確認事項

UI 変更を伴わない範囲で Phase 2 を実装した時点の、判断が要る点をまとめる。
「決定済み・承認待ち」は実装済みで、覆す場合はコード変更が必要。
「要判断」は実装していない・意図的に選択肢を残した点。

## 到達範囲

`platitude-core` の書き込み操作とセッション配線、`platitude-app` のブリッジスロットまで。
**QML は一切変更していない** ため、アプリ上の見た目と操作は Phase 1 のまま。
UI 側の残作業は「既にあるボタン・ホバー操作を `RepoTab` のスロットへ繋ぐ」こと。

| 領域 | core | セッション | ブリッジ | QML |
|---|---|---|---|---|
| ファイル/hunk/行ステージング | 済 | 済 | 済 | 未 |
| discard / clean | 済 | 済 | 済 | 未 |
| commit / amend | 済 | 済 | 済 | 未 |
| checkout・ブランチ作成/削除/リネーム | 済 | 済 | 済 | 未 |
| stash push / pop / apply / drop | 済 | 済 | 済 | pop/apply のみ配線済 |
| fetch / push / リモートブランチ削除 | 済 | 済 | 済 | 未 |

## 決定済み・承認待ち

### 1. `checkout` ではなく `switch` / `restore` を使う

実装計画 §5 は「checkout」表記だが、`checkout` はファイル復元コマンドを兼ねるため
パスと同名のブランチが曖昧になる。`switch` は HEAD しか動かさず、エラーメッセージも
その前提で書かれている。unstage に `restore --staged` を使うのと同じ理由。
→ 承認するなら実装計画 §5 の表記を合わせる。

### 2. `GIT_LITERAL_PATHSPECS` を撤去し、`:(literal)` を個別に付ける

環境変数は git 内部で使う pathspec magic まで無効化する。**実測: この変数が有ると
`git stash push -u` が「Saved working directory」と表示して exit 0 しながら、
untracked ファイルを一切 stash しない**。無言のデータ取りこぼしになる。
git 出力由来のパスは 1 件ずつ `:(literal)` で包む方式に変更した。
`git diff --no-index` の引数は pathspec ではないので付けない。

### 3. コミットメッセージの受け渡し

`<git_dir>/platitude/` のスクラッチファイル + `--file`。stdin は常に閉じたままにする
方針を維持するため。`--cleanup=whitespace` を明示固定し、リポジトリ側の
`commit.cleanup` 設定がエディタの内容を書き換えないようにした
（ユーザーが打った `#` 始まりの行が消えない）。hooks は git に委譲（`--no-verify` を渡さない）。

### 4. 失敗メッセージは stderr 優先・空なら stdout

`git commit` は「nothing to commit」を **stdout** に出して exit 1 する。
stderr だけを見るとエラー表示が空になるため、フォールバックを入れた。

### 5. ネットワーク系のタイムアウト = 600 秒（**提案値**）

「全実行にタイムアウト」の規約を満たしつつ巨大リポジトリの fetch を切らない妥協点。
キャンセルが本来の中断手段。要調整。

### 6. `--force-with-lease` は expect の明示を推奨する形にした

裸の `--force-with-lease` はローカルの remote-tracking ref と照合するため、
**P4 の auto fetch が裏で ref を進めると安全網として機能しない**。
`PushForce::WithLease { expect }` でユーザーが実際に見ていたコミットを渡せるようにした。
UI 配線時にどちらを既定にするかは要判断（推奨: expect 明示）。

## 要判断（UI 配線前に決めたい）

### A. 破壊的操作の確認ダイアログ方針

実装計画 §5 で「ここで確立する」とされた項目。core 側は確認を一切しない
（`discard` / `clean` / `stash drop` / `branch -D` / force push / リモートブランチ削除は
そのまま実行する）ので、方針は UI 側で決める必要がある。

確認を出す候補:

| 操作 | 失うもの | 復旧手段 |
|---|---|---|
| discard（unstaged 破棄） | 作業内容 | 無し |
| clean（untracked 削除） | ファイルそのもの | 無し |
| stash drop | stash 1 件 | reflog から辛うじて |
| branch -D（未マージ） | ブランチの指す先 | reflog |
| force push | リモートの履歴 | 相手側の reflog |
| リモートブランチ削除 | リモートの ref | 同上 |
| amend（push 済み） | 公開済みコミット | P3 の警告と重複 |

「復旧手段が無いものだけ確認する」が最小案。全部出すと日常操作が重くなる。

### B. 複数選択の一括操作

パスはブリッジを 1 件ずつ渡す（git のパスは NUL 以外どの文字も含み得るため、
1 本の文字列に詰める安全な区切り文字が無い）。
複数ファイルをまとめて stage する UI を作る場合、QML から N 回呼ぶ形になる。
セッションが直列化するので競合はしないが、N 回の git 実行になる。
一括が必要なら「選択集合を Rust 側に保持するモデル」を足す判断が要る。

### C. stage all / unstage all のセマンティクス

現状 `git add -A`（untracked 含む全部）と `git reset`（index を HEAD に戻す）。
GitKraken の "Stage all changes" は untracked を含む挙動なので合わせたが、
untracked を含めない案（`git add -u`）もある。

### D. hunk / 行選択のエンコード

QML → ブリッジは `"1;3:0,4"`（hunk 1 全体と hunk 3 の 0,4 行目）という文字列。
インデックスは**表示中の diff 行位置そのもの**なので、diff を再取得すると意味が変わる。
core 側は選択適用時に同じ diff コマンドを再実行して raw バイトから組み直す
（ズレていれば `git apply` が弾く）。UI 側は「操作後に選択をクリアする」必要がある。

### E. 未マージブランチ削除の導線

`branch::is_merged_into` で事前判定できる。
案: 削除メニューは常に `-d` で試し、失敗したら「未マージです。強制削除しますか」を出す。
事前判定してメニュー文言を変える案もある（git 実行 1 回分のコスト）。

## 既知の制限・残課題

- **コミット後にグラフが 2 回再構築される**: 書き込み後の `restart_log()` と、
  status 更新で dirty が false に変わったときの `update_wip()` 由来の再構築が重なる。
  実測 80ms 級なので実害は小さいが、UI 配線後にちらつきが見えるようなら
  「status 確定を待ってから 1 回だけ restart する」形に直す。
- **`\ No newline at end of file` の部分ステージ**: 末尾改行が無い行を「選択せず残す」
  ケースは、その行が context に降格した時点で改行が付く patch になる。
  git 本体の `add -p` にも同じ限界がある。マーカーは「元のマーカー文字のまま出力した行の
  直後」だけ残す実装にした。
- **untracked ディレクトリ**: `status -unormal` はディレクトリを 1 エントリ (`dir/`) で返す。
  stage/clean はそのまま通るが、部分ステージ（intent-to-add 経由）はファイル単位のみ。
- **user.name / user.email 未設定の事前警告が無い**: コミット時に git の長いエラーが
  そのまま出る。事前チェックを足すか、git の文言をそのまま見せるかは要判断。
- **ブリッジ未公開の core 機能**: 空コミット（`--allow-empty`）、amend 時の
  `--reset-author`、`stash push --staged`、パス限定 stash、`hunk_count`。
  UI が要求した時点で足せば良い。
- **`git commit` の GPG 署名**: リポジトリ設定に委譲している。署名鍵のパスフレーズを
  端末で聞くタイプの設定だと `GIT_TERMINAL_PROMPT=0` で失敗する。実機で要確認。
