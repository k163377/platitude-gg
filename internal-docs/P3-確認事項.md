## 残っている実装

フル interactive rebase はプラン編集モードとして配線済み(意匠の正本は
デザイン規約 §フル interactive rebase、実装対応は rules-refs/app-ui.md)。残る磨き:

- **reword の鏡写しは保存時**(行の subject は `setMessage` で更新)— 打鍵ごとの live
  反映にするなら `MessageEditor` に text-changed の口を切る
- **squash / fixup の「親へ畳む」を言うのは動詞チップだけ**(字下げは撤去 = 3 列を揃える
  指示)。モックにあった接続線(下の行へ肘)は未描画 — 描くなら行を跨ぐので pane 側の
  オーバーレイ
- **プランの読みに行数の上限は無い**(ユーザー判断)— `--root` プランは全履歴を
  `PlanRow` に組む。性能予算はベースライン(素で表示した時)の話で、利用者が自分で開いた
  全履歴プランの増分は最適実装の分として許容する
- **プラン行に ref チップが出ない**(`--update-refs` で連れて動くブランチの可視化)。
  行 0 = 現在ブランチ分だけでも出す価値あり
- **実行後の選択は既定挙動**(旧選択が消えて default select)— 「読んでいた行の
  書き換わった先を追う」は未接続。単体 reword の `followRewrittenCommit` は在るが、
  arm は `RepoPage.saveMessage` の 1 箇所だけで、プラン実行はそこを通らない
- **動詞チップに ▾ の描画が無い**(チップ押下と右クリックで開く)
- **捨てる物が在るプランの Esc は無言**(その側の `Discard` は長押しなので、1 度下りただけの
  鍵では撃てない)。**残る判断は手応えを足すか** —— 設定画面が持っている形(1 回目は失う物へ
  送って `✕` を armed にし、2 回目で閉じる = `SettingsDialog.escapeOut`)をプランへ移すなら、
  `Discard` を armed に見せる姿の決定が要る
- **ヘッダ / onto 行のブランチ名は開いた時点の写し** — 端末で base ブランチだけを
  動かされると名前は古くなる(挙動は oid 釘付けで正しいまま)。
  名前の生き直しは refs 更新との突き合わせが要る
- **行に掴み点(grip)の印が無い** — トークンに点サイズが無く、直書きは規約違反。
  行全体が掴み手で機能は成立。**印を戻すならトークン追加の人間承認とセット**
- **プラン行の選択は「模型の selected_row + ページの selectedOid」の二重持ち** —
  所有を模型の oid 1 本に寄せる余地あり(据え置き: 動く実害が無く、寄せると graph 選択との
  橋が別に要る)
- **クリーン停止の WIP 行は語が場面に合っていない**(`rebase-edit-stop` の絵)—
  `edit` 停止の着地はグラフ最上部の `Uncommitted changes` 行 + 右ペインの
  `UNCOMMITTED CHANGES (0)` + 空のファイル一覧で、**行は「無い物が在る」と名乗る**。
  席そのものは仕様どおり(出口カードはこの行の下に吊るので、行を消すとカードの席ごと消える)。
  **据え置き** — 停止の説明は同じペインの底の出口カードが持っている。直すなら行の語の側(席はそのまま)

### 参照していた行が消えた時の着地 — 残っているのはコミット行の側

今の着地(席 → HEAD、借りのある着地が先)は rules-refs/app-ui.md の `followVanishedCommit` の行。

**残っている要求(ユーザー)**: **コミット行を読んでいた時も、閲覧していた線に
合わせて遷移する**。今の着地は席と HEAD しか見ないので、**別ブランチのコミットを読んでいた
時は跨ぐ**。**コミットからブランチを毎回求めるのは到達可能性の walk**(性能予算「操作応答は
コミット数から独立」)なので採れない —— 安い案は **「そこへ連れて行った ref を控える」**
(左メニュー・チップ・タブからの着地でその ref を控え、チップの無い行のクリックは直前の控えを
引き継ぐ)。**着地は worktree へ翻訳して読む** —— その ref を持つ worktree が在ればその未コミット行、
無ければその worktree の HEAD、どの worktree も持っていなければ ref の tip。**定義はユーザー判断待ち**。

- **未コミット行はブランチでなく worktree で扱う**(ユーザー判断)—— detached のまま
  進めている worktree が在るため、鍵は worktree のパス 1 本
- **first parent で線を追う案は差し戻し済み**(ユーザー判断)—— 同じ親から分岐した 3 本目の
  兄弟が席に来ると跨ぐ(実例は `basic` の `feature/remote-only`)

**着地が 2 つ armed になる形は非決定**: `drop-commit-go` は、書き込みの答えが arm する 2 つ
(止まった = 未コミット行 / 先端が動いた = コミット)のどちらが先に着くかで絵が変わり、
並列の gate の中では census が動く(`followVanishedCommit` の側の話ではない)。

**diff のファイル一覧も同じ平仄に合わせる** —— 一覧の移り先(規約 §diff のファイル一覧)は、
上が決まってから横展開する。

意匠の正本は [デザイン規約.md](デザイン規約.md) §別の worktree を読む と §未コミット行が名乗るもの、
実装対応は rules-refs/app-ui.md。

- **開幕の巡回(`refresh_opening` → `refresh_carried`)はグラフの初回描画と同じ機械を
  取り合う**(食われるのは CPU)。
  直すなら開幕の 1 周を `LogFinished` の後へ遅らせる(focus の巡回はそのまま)。
  **予算 3s の内側なので今は据え置き**
- **worktree のメニューの手すり**(WORKTREE カード = 規約 §メニュー の入れ子。入口は WORKTREES の行・
  フォルダのチップを持つコミット行・別の worktree が持つブランチの行とチップ。**未コミット行はメニューを持たないまま**。
  **次に行を足す時も以下を守る**):
  - **カードは 1 つの部品を 2 つのメニューが持つ**(`RefWorktreeMenu` を `RefRowMenu` と `CommitRowMenu`)——
    入口ごとに行を書けば必ず食い違う
  - **未コミット行が持っている扉は「その worktree を開く」1 つだけ**。`worktree remove` / `prune` は
    破壊的で、その形を崩す
  - **フォルダのチップが扉になったのはメニューだけ** —— `encode::menu_kind_word` が `worktree` を返し、
    `ref_kind_word` は `""` のまま(改名・ダブルクリックの行き先にはならない)。**`ref_kind_word` の 1 行を

### worktree を作る — 承認待ちの仮決定

意匠の正本は [デザイン規約.md](デザイン規約.md) §worktree を作る。ユーザー決定は「衝突は押す前に言う・押した後の
衝突はグラフの上の黄の報せ(ログは開かない)・作る 2 行は WORKTREE カードの中」の 3 点だけで、**以下は他製品の調べ(GitKraken / Fork / Tower /
SmartGit / Sublime Merge / GitHub Desktop / VS Code / IntelliJ / Visual Studio / Git Extensions / TortoiseGit /
lazygit / magit)に合わせた仮決定**。覆す時はその行だけ差し替えられる形にしてある。

- **ブランチの扱い = 起点で決まる 2 行**(`Create worktree here…` = 新しいブランチ / `worktree add` = 行のブランチ
  そのまま)。他製品の多数派(新しいブランチは任意、既定は起点 —— ブランチの行はそのブランチ、コミット・タグ・
  リモートの行は新しいブランチ)。既存ブランチだけを許す形(SmartGit・2026-02 時点の Fork)と、常に新しい
  ブランチを作る形(GitButler)は少数派
- **detached の worktree は作らない** —— 製品の「行き先は必ずブランチ」に合わせた。他製品で出すのは少数
  (Tower / TortoiseGit / lazygit が明示の副選択肢として)
- **置き場は `<親>/<repo>.worktrees/<branch の / を ->` で、聞かない**。多数派は本体の隣の `<repo>-<branch>`
  (GitHub Desktop / IntelliJ。Git Extensions・magit は `_`)で、VS Code が `<repo>.worktrees/`。こちらを
  選んだのは**画面が worktree をフォルダ名で呼ぶ**から(`<repo>-` の前置きはタブの節・WORKTREES の行で毎回
  リポジトリ名を繰り返す)。**ほぼ全製品がフォルダピッカーを持つ** —— 置き場を選ばせるなら、名前の箱の
  後に聞く形(質問バー)か、設定の画面の 1 欄(リポジトリごとの置き場)のどちらか
- **作ったらこのタブがその worktree に立つ**。多数派は作ってすぐ開く(新しいタブ = GitKraken / Fork /
  Sublime Merge、新しい窓 = IntelliJ / SmartGit、今の画面 = GitHub Desktop / lazygit / magit)。この製品は
  1 リポジトリ 1 タブで、別の worktree を開くことはタブを立たせること(§タブの所作)
- **名前の箱の枠は `success`**(作るのは別の worktree が持つブランチ = そのチップの枠の色)
- **`worktree add` の行が埋まった行き先で灰になるのは §メニュー「選べない行は消す」の例外**(削除行の
  「今できない」と同じ扱い)。押す前に言う(ユーザー決定)の置き場がこの行しか無いため
- **消す側は今のまま**(ブランチを残す・force を出さない)。GitKraken / lazygit は「worktree を消してブランチも
  消す」を別の行で持ち、Fork は逆向き(ブランチの削除が worktree の削除を勧める)。多数派はブランチを残す
- **未配線**: 止まった操作が `switch` を阻む時の質問バー(§進行中の操作から出る)に「新しい worktree で行く」を
  置く案。今は右クリックの 2 行が操作の止まっている間も出るだけ
- **bare リポジトリのリンクされた worktree に立つタブでは 2 行とも出ない** —— 置き場の起点(リポジトリ自身の
  worktree = `MAIN` 行)が無い(`NavSectionModel.worktreesPlaced`)。bare + worktree の運用で作れるようにするなら、
  起点を bare の隣にするか置き場を聞くかを決める

### 破棄記録と復元 — 記録・一覧・仮表示・復元まで配線済み。残りは小さい意匠の判断

仕様の正本は [破棄記録仕様.md](破棄記録仕様.md)。

- **配線の範囲**:
  - **記録を書く**(`discards::record` / `discards::copy` / `session::discard_record`): discard(ファイル・hunk・行)・
    untracked の削除・`reset --hard`(行き先が持つパスに立つ untracked を含む)は捨てる前を読み、本体が残した状態を土台に
    捨てた分だけの写しにして、本体が通った時と、何かを捨ててから失敗した時に専用 ref の行にする(断られた discard は
    記録に残らない —— 本体の後に読み直して前と同じなら載せない)。ブランチ・タグ・stash・
    worktree・リモートの削除、force push、枝を一緒に動かした rebase(`--update-refs` でも設定でも、止まって continue で
    終わっても。2 本以上動いた時)は本体の後で書く。リモートの物は lease が読んだ物。記録の書き込みの失敗は書き込みとは
    別の失敗として報せ、本体は済んだまま
  - **一覧は開いた時に読む**(`discards::read_repo`)—— worktree の一覧・専用 ref・名前の空き(`for-each-ref`)を並べて読み、
    全 reflog を `log -g` 1 本、そこと記録が名指すコミットのうちどの ref も届かない物を `rev-list` 1 本(200 先端ごと)。
    **どの ref も届かないコミットを残さなかった動きは出さない**(記録の項目は名前を失ったので、届いていても出す)。
    `reset --hard` の写しはその reset の項目に、`--update-refs` の記録は動いた枝の項目をまとめて 1 項目にする
  - **選んだ項目はグラフへ渡る**(`RepoSession::show_discard`): 部品ごとの先端を walk に足し、それだけが届くコミットを破線・
    通常の濃さ、他の行を検索に外れた行と同じ薄さにし、スクロールと矢印キーをその区間に限り、最初の先端の行を選んで
    右のペインに読ませる。写しは未コミット行の形、drop した stash は stash の行の形で描く。土台を自分で持つ写し
    (`Stands-on:`)と、それを stash へ入れた entry は、土台ではなく捨てた時の HEAD の上に描く
  - **復元は 1 書き込み**(`RepoSession::restore_discard` / `OperationKind::Restore`): 部品を 1 つずつ戻し、記録から読んだ
    部品は `restored` の行を足して一覧から外す。reflog の動きは戻した枝が旧先端に届くので一覧から外れる
  - **捨てた直後の点灯**: 書き込みが離れた先端にどの ref も届かなくなった時(core の `RepoSession::tell_if_left` が
    `rev-list` 1 本で判定する: amend・reset・rebase 系・pull・Move here・detached からの離脱・rebase を終える continue)と、
    記録に行が増えた時(どちらも `SessionEvent::DiscardsChanged`)。一覧が開いていれば点けずに読み直す。枝・タグを作る
    書き込みの後も読み直す(復元の名前が埋まりうる)。読み直しの間も選んだ項目は保つ(`DiscardModel.keyAt`)
- **決まった意匠**(ユーザー決定):
  - 入口は左メニューの足元の席 1 つ(git commands の上)。開くと一覧が左メニューを覆い、git commands の席は残る。
    右上の操作パネルには置かない
  - 席の色は git commands と同じ。捨てた直後の点灯は、左メニューの行が手の下で着る白の重ね色(`bgHover`)を地に敷くだけ。
    **2 回明滅して消える**(`Metrics.blinkMs` = 250 の点・滅を 2 回。暫定 —— 正式には挙動を見て決める)
  - 席の名前は `DISCARDS`(節の名前と同じ複数形)。件数は出さない(大きくなると名前の場所を食う)
  - **git の操作を Ctrl+Z で戻す機能は作らない** —— 失った物は破棄記録から復元する(仕様の冒頭「Undo / Redo は持たない」)
  - 一覧の帯は左メニューのフィルタ行と同じ高さ。**帯の横一杯が閉じる押し場所**で、右端の `✕`(畳むブロックの席)は手が
    帯のどこにあっても明るくなる
  - **フィルタは帯の下の自分の行**(左メニューと同じ枠なしの欄。帯の中は狭くて使いにくい)。項目が見せている文面(題・
    中身の行・worktree・時刻の書き方)のどれかに、打った行を小文字にして部分一致(`encode::shown_matches`)。残らなければ
    `No results found`(VS Code・Windows・Chrome の検索と同じ語)。この文は行ではないので席の字下げを持たず、読み込みの
    輪が立つ所に中央揃え(コマンドログの空の一覧と同じ)。操作の種類などを名指す検索は P5(P5-確認事項 §25)
  - 読んでいる間は輪を出す: 一覧が空なら行の高さに 1 つ、項目が出ている上での読み直しは見出しの横に小さく
  - 一覧の行は左メニューの行の桁(`NameCell` の席と名前、右端に時刻)で、**選んでも開かない**(左パネルは狭い)。印の色は
    左メニューの節と同じで、捨てた未コミットの変更は右パネルの削除の赤(場所の言い分けは下の「印は場所も言う」)。題は種類を言う
    (worktree の削除は `Removed worktree <名前>` —— フォルダ名だけでは何の名前か分からない。タグの `Deleted tag X` と同じ)
  - **hover は行の詳細カード**(コミット行の hover カードと同じ形 = `RecoverHoverCard`): 題・部品ごとの中身・worktree・
    `<日時> (N min ago)`(日時が先 = 各行の頭が揃う。日付で書く段からは日時だけ)
  - 時刻は 1 分未満 `Just now` / 1 時間未満 `N min ago` / 1 日未満 `N h ago` / 暦で 1 日前 `Yesterday` / 7 日未満
    `N days ago` / それより前は日付
  - **詳細と復元はグラフの上の帯**(案 B = `RecoverBand`): 題・`<日時> (N min ago)`(別の worktree なら `· in <名前>`)・
    部品ごとの 1 行(印・失った物 — 戻る形。行は一覧の間隔で、部品ごとの `Restore` は行の高さに収める)。押す物は帯の右の
    `Restore` で、部品ごとにも戻せる項目は `Restore all` と部品ごとの `Restore`。**1 回の rebase が動かした枝はまとめて
    だけ**(一緒に動いた枝は一緒に戻す。コミット単位は仮表示の行から cherry-pick)。押す物と `✕`(仮表示を下ろす)は帯の
    縦の中央(報せの帯・質問バーと同じ)。語は他の製品が同じ行為に使う物(GitHub の
    `Restore branch`・Windows のごみ箱の `Restore all items`)。戻る形は `as branch X, tracking origin/X` /
    `as tag X` / `as a worktree there, on X` / `back to the stashes` / `back into <worktree>`。中身は `2 commits` /
    `No commits of its own`(名前だけが戻る)/ `3 uncommitted`(写さなかったファイルは `, 1 not copied`)/ `At <短い id>`
  - 一覧で選ぶと検索は `✕` と同じく閉じる。グラフでは復元対象を破線・通常の濃さで出し、それ以外を検索に外れた行と同じ薄さに
    する(対象を目立たせるのではなく、他を薄くする)。ビューは復元対象の区間へ移り(画面に収まる区間は真ん中に)、
    スクロールはその区間だけ
  - **グラフの中の破線 = 復元中**: 仮表示の行は、未コミット行と同じく**ノードの輪を破線**にする(コミット・未コミットの写し・
    stash の行)。行全体を囲む枠は、グラフに普通に描かれる以上、間に他の行が挟まる所で破綻するので採らない。コミットの顔は
    輪の内側に一回り小さく描き、輪と離す(輪を顔の縁に重ねると明るい顔の縁でにじむ)。エッジも破線で、仮表示の顔が続く所でも
    刻みが見えるよう、ノードから出る側を隙間から始める
  - 戻した時は、戻した先頭へグラフのフォーカスが行く程度にする(派手にしない)。項目は一覧から消える。写しが当たらず
    stash へ入れた時と、staged の側が当たらず unstaged で当てた時だけ、答えの要らない報せの帯が言う
  - **先頭がグラフの窓の外に在る部品**は押せず、帯が `Not loaded on the graph yet` と `Load N more commits`(グラフの
    末尾の語)を出す(仕様 §4: 窓に入るまで復元しない)
  - **長押しは今のまま**。破棄記録で戻せるようになった物をクリックへ降ろすかは、後で長押し全体をまとめて見直す時に
    決める。その時の区分: 手元で完結して戻せる物(ファイル・hunk の discard・`Discard everything after it`・stash の
    `drop`・コミットの `drop`・rebase プランの `Discard`・未マージの枝の削除・タグの削除)/ リモートを変える物
    (`push --delete`・`Delete both`・`push -f`・タグの上書き —— 手元に立て直せるだけ)/ 記録の外(進行中の操作の出口 ——
    途中の作業は記録しない)
  - 写しが当たらず stash へ入れる entry のメッセージは、写しの 1 行目のまま(`discard 2 paths on main`)。元の物を保ち、
    名前を変えるのは衝突する時だけ —— stash の文は重なっても衝突しない(drop / pop した stash は元のメッセージで戻る)
  - **印は場所も言う**(`RecoverMark`): ここだけ = 種類の印 / **リモートのタグだけ = 暗い段のタグ + 右肩の雲**(雲だけでは
    タグと言えず、同時の操作とは意味が違う)/ **ここと origin を同時に = 種類 / 雲の併記**(印が 2 つ = 取った物が 2 つ。
    その行だけ名前が `pairSpread` 右へずれる)/ リモートの枝 = 雲(REMOTES の印のまま)。帯の部品は 1 つずつなので併記は
    無く、リモートのタグの部品だけが右肩の雲を着る。右肩の印の大きさは段ではなく計算(デザイン規約 §寸法 の
    `iconBadgeMin`)
- **未コミットの写しの掃除機能を P5 あたりで足す**(ユーザー決定。写しの大きさに上限は持たない): 大きい物・
  n 日より前の物を指定して消す。前提: 記録の行は git の `gc.reflogExpireUnreachable`(既定 30 日)で消える(行の値どうしが
  親子で繋がらないので、90 日の `gc.reflogExpire` は効かない = 仕様 §2)。もっと長く残すなら、行を繋ぐ(前の行の値を親に
  持たせる = 行が在る間は失った物も gc から守られる)か、掃除と一緒に期限の設定を決める(未着手・要判断)
- **性能: 一覧を開いた時の届かないコミットの walk はタグの本数に比例する**(`discards::lost` の `rev-list … --not HEAD
  --branches --remotes --tags …`)。rev-list は全タグの object を読んでから walk するので、タグ 4 万本級のコーパスで
  1 本あたり秒の桁(`--tags` を外すと 100ms 未満)。背景の読みなので画面は止まらないが、開いてから項目が出るまでが
  その分延びる。タグだけが届く旧先端を「失った」と言わないための `--tags` なので、外すなら別の手(タグの peeled の
  値を索引にして walk の後で引く等)と一緒に決める
- **戻るのは捨てた物だけ**(ユーザー決定。頼んでいない hunk まで戻るのは不可): 写しは本体が残した状態を土台にした
  捨てた分だけの差で、復元はその差をパッチで当てる(仕様 §2.1・§4)。残る限界と案(どれも未着手・要判断):
  - **worktree へ直に戻らず stash の entry になる時**: 捨てた hunk の前後 3 行が捨てた後に変わった(パッチの文脈)・
    新しく作るファイルの所が埋まっている・merge 等が進行中。entry も捨てた分だけを持つが、当てるには同じファイルの
    未コミットの変更を先に退けることになる(`stash apply` が断る)。手法のままの低減 = 文脈が合わない時、ファイルごとの
    3-way(`merge-file`。土台 = 捨てた後・相手 = 捨てる前・自分 = 今)で衝突しなければ当てる(代金は復元の時だけ)。
    手法の見直し = 衝突も conflict の印付きで作業ツリーへ出し、帯が言う(「何も書かずに断る」を捨てて stash を経ない)
  - **破棄の待ちが git 7〜10 本ぶん延びる**(index を読み書きする物は index の大きさに比例。code-costs の
    `discards::copy`)。手法のままの低減 = 本体の後の読みとコミットを、書き込みの後の読み直しと並べて走らせる
    (書き込みの実行器に「次の書き込みより前に済ませる後続」を持たせる。見かけの待ちから後半が消える)。
    手法の見直し = 写しの木を写したパスだけにする(一時の index を空から組み、index の大きさに依らない。代わりに土台が
    根のコミットになり、`git stash branch` など全体の木を前提にする他ツールの操作が entry で使えない)

## ウィンドウ chrome — 形は決まり、残りは中身

形の正本は [デザイン規約.md](デザイン規約.md) §ウィンドウの縁。Windows の縁に残る 2 つ
(窓メニューの移動・サイズ変更 / Snap Layouts)は [P5-確認事項.md](P5-確認事項.md) §10。
ここに残るのは中身の方:

- **アドバンス検索**(基本検索の正本は規約 §コミットを探す):
  - **項目を名指しして探す形**(`author:` / `path:` / `date:`)。素の語を全軸のまま git へ
    降ろすと `--grep` と `--author` は AND なので和集合に 3〜4 スポーン要るが、接頭辞つきなら
    1 クエリ 1 スポーンで各接頭辞が git のフラグ 1 つに対応する
    (`git log --grep=… --author=… -G… -- <path> --format=%H` が SHA を返すので、印の仕掛けは
    基本検索のものを使い回せる)
  - **最初に出せるのは `description:`** — 外した 4 つのうち Description だけは行が既に
    持っているので、git を 1 プロセスも撃たずに出せる。判断は「据え置き、実使用をもう少し重ねてから」
  - **同時に決まるもの 3 つ**:
    1. **日付で探す**。Rust 側にタイムゾーン依存を 1 つ足すか、`LOG_FORMAT_ARG` に
       `%ad --date=format-local:%Y-%m-%d %H:%M` を 1 フィールド足す(`LOG_FIELDS` 8→9・
       parser の field 分岐・`CommitMeta` / `LogRow` / fixture)かの二択。**後者で決まり** —
       git が DST 込みで正しく組み、行が画面と同じ文字列を持つ。**`format-local` が読み手の
       時計に焼き付くのは織り込み済み**(規約 §author の hover)。範囲(`date:2026-08` /
       `--since` / `--until`)もそこで一緒に決まる
    2. **窓の外を探すか**。基本検索は読み込み済みの行しか見ない。git へ降ろす検索は窓の外も
       返せるので、返った SHA がグラフに無い時に何をするか(件数だけ言う / 窓を伸ばす /
       その行まで読み込む)が要る
    3. **パスで探す**(実装計画.md §14 のフィルタ 4 軸の最後)。`-- <path>` は git 側でしか
       解けない
  - **絞り込み(行の間引き)は引き続き別物** — レーンとエッジを「隠れたコミットを跨ぐ」形で
    引き直すことになり、core に 2 つ目の walk モードが要る
- **検索の入口をメニューにも置く案(未着手)**: アプリメニューに `Find commits…` の行を足す
  (規約 §メニュー に沿う)。キーが届かない場面の逃げ道にもなる —— `Shortcut` の既定 context は
  窓がアクティブになるまでキーを渡さない(rules-refs/app-ui.md の `Shortcut` の行)

  - **QTBRIDGES-332**: オブジェクトの消滅(`ExpiredWeakPtr`)や借用の失敗を、呼び出し経路ごとに

  - **独自 property 型の変換失敗**: 332 の本文に無い別の panic の経路(下の「QML から property へ

- **qtbridge — QML から property へ書いた時の答え**(`encode::wire_qml` の診断が実 QML で
  撮る。**分類は独自型の変換失敗の対応範囲と失敗時の方針**): Qt の型(`int` / `QString` /
  `QStringList`)は QML エンジンが property の型へ先に変換するので、変換できない値はエンジンが
  `Error: Cannot assign …` で拒み(状態は不変)、できる値は変換して入る(`QStringList` へ数の
  配列は文字列の配列、オブジェクトは空)。Rust には届かず、落ちない。**落ちるのは wire の型
  (`Listed` / `One` = Qt から見れば `QVariantList` / `QVariantMap`)の要素・欄の形を Rust が
  読めない時だけ**で、生成される `write_property` が `extern "C"` の中で panic する
  (qtbridge-gen 0.3 `qproperty_info.rs` の `Failed to convert QVariant for qproperty`、0.2 も同じ。
  上流の試験は不正な property id の panic だけで、変換失敗の試験は無い)。
  qtbridge 0.3 は `Constant` 以外の property を全部書き込み可で登録する(`dynamicmetaobjectbuilder.cpp` の `writable = !isConstant`)ので、

  製品は wire の型の 7 本を getter だけで出す(rules-refs/app-ui.md「`Listed` / `One` の
  property は `Read = getter`」)。**上流へ出したのは 2 点**(報告文の §2・§3、上の qtbridge の項の
  投稿に同梱): 書く道の無い property を書き込み不可で登録する / 変換できない値を abort でなく拒否に
  する。後者は QTBRIDGES-332 の本文に無い別の panic の経路(332 が挙げる原因はオブジェクトの消滅と
  借用の失敗)として関連事例に示したもので、332 の提案で対応されるとは決まっていない
- **`String::from(&QString)` の容量**(**分類は意図的な最適化と、追加改善の余地**): cxx-qt-lib
  0.10 は UTF-16 を直に読む(`from_utf16_lossy`。`toUtf8` の `QByteArray` とその複製を作らない —
  短い文字列で `toUtf8` 経由より 1.6 倍速い)。**容量を決めているのは std の側**: `from_utf16_lossy`
  は `decode_utf16` を `collect` するので `size_hint` の下限(UTF-16 長の半分)から伸ばし、兄弟の
  `from_utf16` は UTF-16 長で先に確保する。この半分から伸ばすので、
  和文・絵文字で 2〜4 回確保し、出来た文字列は長さの最大 1.33 倍の容量を持つ。UTF-8 長を数えて
  1 回で確保すると短い和文で 0.5〜0.7 倍の時間になるが、1000 字では 2 度の走査で 1.3〜1.4 倍遅く、

## 探索で見つかった残件

### core

- **`eol::attrs` の `check-attr` は 200 本ずつ区切る** —— 長いパス(深い階層)が 200 本並ぶと Windows の
  コマンドライン 32767 字を越え、起動が失敗して黙って「規則なし」に落ちる。`lfs::filtered` はバイト長で区切って
  いる(`ATTR_BYTES`)。改行コードの側は印の付いたパスだけを訊くので本数は普段少ないが、全行が CRLF に
  反転した大きな木では届く。直すなら同じ区切りを当てる

- **`cat-file --batch` の常駐(設計済み・未実装 — 採否は操作経路の実測で)**: 数字は
  [git-slots-windows-x64.md](../ci/baseline/git-slots-windows-x64.md) §プロセス再利用。効くのは diff を開く 1 点の
  直列 2 本 = `preview::blob_is_there` + `read_source`(`show` は置き換わらない)。設計:
  **① 1 リポジトリ 1 本** — `RepoSession` が持ち、`git cat-file --batch-command`(2.36+、最低版の
  内側)を `stdin` piped で spawn する = **プロセス層の「stdin は常に閉じる」の唯一の例外**で、
  常駐用の別 spawn 経路(`process::Resident`)に閉じ込め、`GitCommand` の道は閉じたまま。
  **② 要求と応答の対応** — 要求は 1 行ずつ、応答は `<oid> <type> <size>\n` + 本体 + `\n`
  (`missing` は 1 行)で、常駐の口は `tokio::sync::Mutex` で直列に使う(次の要求は応答の読み切りの後)。
  **③ キャンセル** — 要求を書いた後の cancel は応答を**読み捨ててから**
  返す(途中で口を離すと次の要求が前の本体を読む)。読み捨てが `SOURCE_BYTE_CAP`(4MB)を超える
  長さなら常駐ごと終了させて次で再起動する方が安い。**④ 異常終了・再起動** — 書き込み / 読み取りの
  EOF で `Dead` にし、次の要求が spawn し直す(1 回だけ再試行、2 度目は一発 `cat-file` へ落とす)。
  **⑤ アイドル解放** — 最後の要求から 30 秒で kill(タイマは `AutoFetchClock` と同じ手回し可能な形)、
  `RepoSession::close` で kill。**⑥ 保持メモリ** — `heap_report` に常駐の pid と生存を載せる。**⑦ 枠** — 常駐は
  spawn の 1 回だけ `Slots` の Here プールを通り(`Priority::Interactive`)、以後の要求は枠を取らない。
  **⑧ 観測** — コマンドログに出るのは常駐の起動 1 行
  だけ(`Kept::Unasked` の読みなので背景記録が on の時だけ `<spec>` を 1 行)。
  実装したら `perf_diff_frame` の p50 / max を [perf 記録](../ci/baseline/perf-windows-x64.md)
  §判定 の diff の行と並べて採否を出す

- **フル interactive rebase の実行は tab の書き込みの口を通らない**(`RebasePlanModel::run_plan` が

- **ページに入り切らないチップの一覧は、チップの席を明け渡す**(規約 §グラフ行のダブルクリック
  「1 行目はチップの席にそのまま座る」の外れる場面):縦の clamp

  **`ref-list <行> --preset stack` を行の深さを変えて撮れば両方比べられる**
- **チップのカードの幅の規則を機械が守っていない**: 規則は 2 つで、**採寸は行を `layOutNow()` して
  から読む**・**行のチップが要求してよい幅は採寸中だけページで、採寸後はカードの幅**
  (`.claude/rules-refs/app-ui.md` のチップ一覧の行)。固定できているのは前者の
  チップ側だけ(`tst_refstack.qml` の `RefChipRoom`)で、**`RefListPopup` 自体は
  `platitude`(`GitFacts`)を読むので qmltest では建てられない**。加えて
  **深いカード(ページに入り切らない長さ)の折り返しの下に長い名前が来る形は preset に無い**ので、
  gate はこの絵を撮らない(再現は使い捨てリポジトリ = ブランチ 1 本 + 40 タグ + 長い名前の

  **qmltest のステージングに `platitude` のスタブを足して `RefListPopup` ごと建てる** /
  **`--preset stack` に長い名前のタグを 1 本足す**(既存動詞の絵と census が動く)
- **文法経路の巨大ファイルに独自の上限が無い**: 天井は `SOURCE_BYTE_CAP`(4MB)だけで、
  4MB 級の minified / 生成ファイルは全体パース + 全行 span 化を払う。実害が出たら行数か byte の第 2 予算を検討
- **conflict した文法言語のファイルは色が出ない**(**bounded な直しが無い**): combined diff の着色は
  **行単位の増分**(`highlight::patch::combined_colors`)で、tree-sitter は**ファイル全体を 1 度に**読む側なので、
  マーカーの入った作業ファイルでは `tree::reads` が通らない。結果として tree-sitter だけが知る言語
  (.qml / .kt / .zig 等)は conflict の間だけ無色になる。
  **直すには 2 面を組み直して各々を parse するか、マーカー行を抜いて行番号を写し戻すかで、
  どちらも walk モードの追加**(= ハイライト設計の変更)なので、やるなら設計判断とセット
- **アプリ終了はローカル書き込みの完走を待つ**(配線は rules-refs/app-ui.md の「close ゲートは 1 本」の行、
  core 側は rules-refs/core.md の「ローカル書き込みは走り切る」の行)。残っている縁:
  - mid-write のタブを閉じて即再オープンした時、旧セッションの replay が走っている間、再オープンした
    タブは opstate バナー(abort 等)を進捗なしで出す — 押しても順序の後ろに並んで
    「進行中の操作は無い」と git に断られるだけなので壊れないが、名乗れてはいない。
    走行中コマンド名を window 層へ運ぶ配線(下の modal の項)と同じ穴。
    **別の worktree へ立ち位置を移して戻った時も同じ形**(離れた時のセッションが park した
    write が、戻って建て直したセッションの前に並ぶ)
  - 自動化 run の `Qt.quit()` は close 経由でゲートに来るが、run 完了後はゲートが
    1 回だけ譲り、`Hub::shutdown` の join が窓なしで待つ(その間 exe は生きている —
    二重起動ゲートに映る)
  - modal の間はコマンドログを開けない(何が走っているかはダイアログの 1 行だけ)。
    走行中コマンドの名前をダイアログに出すには window 層へ op 名を運ぶ配線が要る(未着手)。
    **mergetool が最長の実例** — quit はそれが閉じるまで立つが、ダイアログはそれを名指せない
- **write group に残っている読み手は「同じ drain の答え 2 本目に負ける」**(**残っているのは
  持ち主を持たない書き込み全般**): group(`writeRefused` / `writeStaleDiff` / `writeMovedHead` /
  `writeReworded` / `writeBranchOp` / `writeFetched` / `writeReport*`)は、**その notify が
  運んだ答えのうち「名前で待たれていなかった最後の 1 本」**だけを説明する
  (`drain::fold_into_group`)ので、持ち主を持たない答えが 1 つの drain に 2 本入ると先の
  1 本の分類は落ちる。**実害の観測は無い**(stage / unstage / discard の
  `StaleStage` 系・config・identity・merge / rebase 等)が、寄せるなら形は決まっている —
  頼むスロット自身が受付の id を書き留め、`settle_write` が id で配り、ページはその答えから
  報せを読む(`ops::PushOut` の 2 つが先例)
- **コマンドログは `CommandStarted.operation`(その write の id)を app へ運んでいない**
  (`hub::sink` が捨てる)— 操作単位でまとめて見せる意匠が決まったら `CommandMsg` へ乗せる。
  書き込みの 3 境界の id は `repo_tab::write_watch` まで渡してあるので、足すのは id の載せ替えだけ

- **撃つ git のパスは global だけ・広げるのは実使用感が言ってから**(正本は
  規約 §設定の画面 の `GIT EXECUTABLE` 項)。どちらも据え置きで、動かすのは要ると言われた時:
  - **リポジトリ単位の上書きが無い**(ユーザー決定)。出すなら `Application` の側の話 —— **このアプリ自身の設定**
    なので、群の分け方(規約 §設定の画面)が `Application` にも要ることになり、**1 分類 1 群の今の
    形を崩す**
  - **起動時に落ちたことを帯が言わない**。書いてある git が答えなければ `PATH` へ落として
    窓は開き(`Hub::resolve_git`)、**そう言うのは設定画面のその章だけ**。5 つ目のバッジを立てるなら
    §ウィンドウの縁 の意匠判断で、**`OLD GIT` と同じ「アプリが自分で言う」側**になる

- **窓の復元位置の実機確認が 2 つ残っている**(**実機待ち**。arithmetic は `tst_windowshape` が見ている):
  倍率の違う画面で戻るか(この机の 3 画面はどれも 96 dpi)/ 保存先モニタを外して起動 → 最寄りの画面に収まるか。
  カーソルを別画面に置いた起動は P5-確認事項 §実測済み
- **タブを復元する road だけ、パスの綴りに網が無い**(規約 §パスの区切り): 画面に出るパスは
  `urlpath::shown_path` を通って `/` になり、入口は `TabsModel` の 3 つ
  (`open_repository_path` / `restore_tabs` / `open_rejected`)と起動ゲートの 1 つ
  (`main::claim_store`)と設定の git のパス欄の 2 つ(`app_backend::start` の `git_path` / `git_path_in_use` —
  こちらは `settings-git-path` の `native=false` が両方を撃つ)。**タブの側を判定している動詞 `tab-name` が
  通るのは 1 つ目だけ**で、復元 road を撃つには `\` を書いた `state.toml` を `--config-dir` で
  仕込むことになり、**その形の run は census に載らない = gate が選ばない手動テスト**に
  なる。今は `shown_path` の単体テストで畳み方を守り、呼び出し側 1 行は網の外。閉じるなら道は
  2 つで、**復元を撃つ動詞を足す**(選ばれない手動テストが 1 本増える)か、**忘れようのない形に
  する**(入口が各々覚えている状態をやめる)。後者の置き場は `TabItem::standing()` ——
  行を作る唯一の door は在るが、**畳むのはそこでは遅い**: `landing_for` / `title_of` は
  その手前で綴りを読むので、door で畳んでも比較は畳まれていない方を見る
- **タグの雲バッジは、撮影に間に合わないことがある**(`band` で、**PASS したまま絵だけが違う**)。
  **欠ける時はサイドバーの行とグラフのチップが同時に欠ける**ので、遅れているのはモデルの側。
  **容疑はリモート側のタグの読み**(`session::RefJoins` / `remote_tags` = 行の `has_remote`)だが未検証。
  当面、雲バッジを見せる絵は**撮った絵の中にバッジが在ることを目で確かめてから**使う。
  閉じるなら動詞の完了にその join を足す

### 開発環境(Linux コンテナ)

- **席の木が、どのセッションの transcript にも削除コマンド無しに消えることがある**(いずれも未マージ commit を
  持ち作業ツリーは clean、持ち主セッションが再起動 / 再開で本体 checkout に戻った直後)。容疑はセッション終了時の
  worktree の keep / remove 問い合わせか CCD 側の後始末で、**原因は未特定**。枝の残った letter は `seats` と
  挨拶に「no tree」で出て、`cargo xtask seat takeover <letter>` が枝の上に木を生やし直す(`seats::grow_back`)。
  原因が判ったら、ここへ書き足すのではなく消す側の経路を塞ぐ

- **コンテナのイメージ・ボリューム・build cache は `linux` が入口で掃く**(`linux::housekeeping`。規則は
  [反映前テストの機械化.md](反映前テストの機械化.md) §キャッシュとスタンプ)。残る罠は 2 つ:
  - **名前は checkout ディレクトリの最後の 1 段のテキストだけ**(`checkout_name`)なので、
    **別の場所にある同名の clone のボリュームは孤児に見え**、逆に**同じ木を別の綴りで指した
    プロセス**(8.3 短縮名・大小違い。`seats::same_tree` が在るのはこの差のため)は別名を作る。
    今は volume を作る側(`workspace_root` = ビルド時の `CARGO_MANIFEST_DIR`)も
    `git worktree list` も長い綴りを返し、席の letter は 1 文字なので短縮も起きない
  - **`git worktree list` が挙げない木は死んだ扱い**。席の木が消える事象(上の項)の最中は letter の
    枝だけが残るので、その席のボリュームは孤児として消える。`seat takeover` が木を生やし直した
    後に `linux` を 1 度撃てば作り直るが、**target は空から**になる
- **消してもホストのディスクは戻らない** —— Windows のエンジン(wslc)はイメージ・ボリュームを
  セッションの `%LOCALAPPDATA%\wslc\sessions\wslc-cli-<ユーザー>\storage.vhdx` に置き、確保済みのブロックを
  削除後も抱えたままになる(2GB 書いて消しても 3865MB のまま。中は `discard` で mount されているので、
  空いたブロックは次の書き込みが使い直す = 育つのは同時に抱えた量の最大まで)。ファイルはスパースではなく、
  WSL のスパース VHD は破損の可能性を理由に既定で無効。縮めるには `wslc system session terminate` の後に
  管理者権限の `diskpart` の `compact vdisk` が要る

- **VM のメモリの上限は機械の設定で、木には無い**([実測](../ci/baseline/wsl-memory-windows-x64.md) が正。
  観測は `cargo xtask footprint <コマンド>`)。上限は `%LOCALAPPDATA%\wslc\settings.yaml` の `session.memorySize`
  (`.wslconfig` は効かない)で、swap は同じ大きさが付く。**冷えた target のビルド(イメージが組み直された直後の席の
  最初の gate)は 1 本で VM の中を 4.4GB 使い、同時に走る本数に比例して積む**(gate 1 本の Linux 側は最大 2 本 =
  席 2 つで 4 本)。上限が小さいと swap を使い切って VM の中で OOM が起き、殺されたコンパイラのステップが赤くなる
  (エンジンは生きているので、撃ち直せば暖まった分から続く)。大きいとホストの空きが尽きる。**この機械は 12GB**
  —— 冷えたビルド 4 本を swap で通す最小に近い値(既定の半分 = 15.5GB はホストの空きを 3MB まで食い、8GB は 4 本が進まない)。
  **VM はコンテナが無くなって 30 秒で消える**ので、上限が効くのは重い仕事の最中だけ
  - **確かめていない: 席 2 つ以上が Windows 側を含めて同時に gate を撃つ時の安定性**(実測記録 §確かめていないこと)。
    確かめたのは Linux 側だけの負荷・VM 全体の OOM の後もエンジンが答えること・記録にある停止と同じ条件を席 1 つで
    通ること・席 2 つを模した負荷(もう 1 席の Windows 側は無し)でエンジンが答え続け全部が通ることまで。
    **その模擬でホストの空きは 73MB まで落ちた** —— 詰まるのはエンジンではなくホストのメモリで、上限を下げると
    VM の中の swap と OOM の側へ寄る(12GB 未満の模擬は未測)

- **エンジンが答えなくなる停止 — VM の片付けの途中で `vmwp.exe` がカーネルから返らない**(WSL 3.0.1.0 /
  Windows 10.0.26300.9457。観測は 2026-10-04 の 2 件。スタックを読めたのは 2 件目で、1 件目は同じ外形)
  - **観測した事実**(時刻は JST)
    - 1 件目: 11:12:49 に立った VM が席 4 つの gate(途中で止めた 1 本を含む)を切れ目なく受け、最後のコンテナは
      11:30:28 に終わった。次の `wslc image inspect`(11:32:27)から返らなくなり、後続の 25 本も待ったまま。
      `wslc system session terminate`(11:43)は 60 秒答えず、以後の呼び出しは全部 `ERROR_INVALID_STATE`、進行中の
      build は `E_ABORT`、2 度目の terminate は exit 0 で VM が残る
    - 2 件目: 17:51:18 に立った VM を席 1 つの gate が 2 分使い、最後のコンテナの削除は 17:53:24(正常)。17:54:02 の
      `wslc images` から無応答。長く複数席が使った VM も、途中で止めた gate も条件ではない
    - どちらも `Microsoft-Windows-VHDMP-Operational` に VM の storage / swap.vhdx の切り離しが再起動まで無い
      (正常な VM は最後のコンテナの約 32 秒後に切り離し)。System ログ・crash dump には何も出ない
  - **止まっている連鎖**(2 件目の dump 4 本。シンボルは export だけなので、プロセス間の連鎖までが確定):
    `wslc` の呼び出しは `wslcsession.exe` の SRW ロック待ち ← ロックを持つ idle の片付けスレッドが COM で
    `wslservice.exe` を呼んで待つ ← `wslservice.exe` は `computecore!HcsWaitForOperationResult` で HCS の完了待ち ←
    **`vmwp.exe` の最後の 1 本が `vmflexio` → `vmvpci` → `vid!VidDestroySynicPort` → `NtDeviceIoControlFile` から
    返らない**(呼び出し元は `wsldevicehost.dll` を載せた `dllhost.exe` の HDV デバイススレッド = virtio デバイスの
    取り外し)。外形: `vmwp.exe` がスレッド 1 本(健全時は 130 本台)、`wslcsession.exe` に LpcReply 待ち 1 本と
    ロック待ち(`Get-Process` では `Unknown`)が呼び出しの数だけ、`IORelay` / `CrashDumpCollection` スレッドは無い
  - **戻らなかった手**: 2 件目で `hcsdiag kill <VM id>`・`Restart-Service WSLService`(停止待ちのまま)・
    `Stop-Process` で `vmwp.exe`(受け付けられるがプロセスは残る — スレッドがカーネルの中)・
    `Restart-Service vmcompute`(停止待ちのまま)・device host の終了、1 件目で `wsl --shutdown`(wslc の VM に
    触れない)と `wslc system session terminate`。**戻したのはどちらも機械の再起動だけ**
  - **device host は VM 1 台につき 26 スレッドを残す**(`vmdevicehost` 23 + `wsldevicehost` 3。正常に片付いた VM の分も
    消えない。54 台で 1416 スレッド・4631 ハンドル)。止まりとの因果は不明
  - **回避の設定(この機械に入っている)**: `%LOCALAPPDATA%\wslc\settings.yaml` の `session.hostFileShareMode: plan9` と
    `session.networkingMode: nat`。WSL 3.0.1 の `HcsVirtualMachine.cpp` は共有が virtiofs かネットワークが consomme の
    時だけ device host を作る(どちらも既定値)ので、**2 つ揃えて初めて** device host が VM から外れる。
    入れた後の観測: コンテナの共有は `9p`、`wsldevicehost` のプロセス 0、DNS と HTTPS は通る、plan9 の surrogate
    (`vp9fs.dll`)は VM と一緒に消える、全席の gate 19 本でエンジンが原因の赤なし(Linux 側の赤は席のテスト 1 本)。代償は同じステップ同士の比で
    動詞がほぼ不変(中央値 1.04)、`clippy-linux` が 1.5〜2 倍(標本 1〜8)、テストが 1〜2 割増。
    **解除条件**: WSL か Windows を更新したら 2 行を消して既定値で動かし、同じ外形で止まったら戻す。
    gate の時間が見合わなくなった時も消す
  - **確かめていない**: カーネルの中で返らない理由・引き金・1 件目が同じ連鎖だったか(スレッドを数えていない)・
    この設定で止まらなくなったか(2 件は起動から 48 時間後と 5 時間後)・この設定でのイメージの build と
    冷えた target のビルドの時間・`session.storagePath` の付け替えによる再起動なしの復旧
    (microsoft/WSL#41740 の 2026-10-03 のコメントが同じビルドで報告)
  - **dump の読み方**: この機械に debugger は無い。`System32\dbgeng.dll` を PowerShell の `Add-Type` から vtable 経由で
    呼ぶ(IDebugClient `OpenDumpFile` = 19、IDebugControl `OpenLogFile` = 8・`Execute` = 66・`WaitForEvent` = 93、
    dump 1 つに 1 プロセス)。`vmwp.exe` と `wslservice.exe` は管理者のタスクマネージャー、device host は
    ユーザー権限なのでスナップショットで取れる(witness は撮らない)
  - **xtask の側**(`linux::engine`): エンジンへの短い問い合わせと削除は天井付きで、答えが無い・非ゼロ・起動不能は
    「確認できなかった」として、撃ったコマンド・時刻(UTC)・経過・終了コード・stderr を付けて返す。イメージの有無は
    listing で読み、**不在を確認できた時だけ build へ進む**(`linux::built`)。天井は「制限時間内に答えなかった」
    としか言わない。掃除(`linux::housekeeping`)は答えの無い 1 本で止まり、その行はコンテナを起動せずに失敗する。
    xtask は共有の VM とセッションを止めず、答えの無かった操作を撃ち直さない。
    **天井が無いまま残るのは長い仕事そのもの**(`wslc build` とコンテナの `run` — gate の中ではステップの天井、
    単体コマンドは人が止める)と計器の `footprint`。天井の値(行の最初の問い合わせ 300 秒)は、WSL 3.0.1 が
    停止と起動の各段に置いているタイムアウトの合計(約 3 分)より上に置いた数で、エンジンには自分で天井を
    置いていない待ちもある —— 天井に届いたことから原因は読めない
  - **次に起きた時の証拠は xtask が自分で残す**(`linux::witness`。普段は走らず、エンジンが天井まで答えなかった時と
    listing を断った時だけ): `%TEMP%\pgg-engine\engine-<セッションの開始>-<pid>-<VM>` に、エンジンのプロセスと
    待っている `wslc` の一覧・ホストのメモリ・セッションのディスクの attach / detach の履歴・
    `wslc system session list`・**`wslcsession.exe` のスレッド一覧(状態と待ち理由)と dump**(管理者権限は要らない)。
    `wslcsession.exe` は全席が共有するので、**外からスレッドを止めない**: スタックは歩かず、dump は
    スナップショット(`PssCaptureSnapshot`)から書く —— スタックは dump の中にある。置き場は gate のコンテナが
    mount する `pgg-linux` の外(dump はプロセスのメモリで、レジストリの資格情報を含みうる)。
    同じセッションプロセスと VM に対しては最初の 1 回だけ撮り、後続の行はその場所を指す。残すのは行が撮った物・
    手で撮った物それぞれ新しい 3 つまで。
    xtask の外で `wslc` が黙っているのを見た時は <!--cmd:linux.witness-->`cargo xtask linux witness` が同じものを撮る
  - **止まったエンジンに触る前に**(terminate の前後で状態が変わり、再起動で全部消える): セッションは
    `wslc system session terminate`・`wslcsession.exe` の停止・`wsl --shutdown`・待ち手の kill を自分では撃たず、
    失敗文が指す witness の場所をユーザーに伝える。管理者にしか取れない 2 つは人の手で足す(手順は witness の
    `README.txt`): ① タスクマネージャーで `vmwp.exe` と `wslservice.exe` の dump ② WSL の `diagnostics/collect-wsl-logs.ps1 -Dump`
    (入っている版のタグの物。既定のプロファイルが provider `Microsoft.Windows.Wslc` を録る)。
    **起きる前の遷移は録っていない** —— 常時トレース(`rolling-wsl-logs.ps1`)は管理者権限の常駐が要るので回していない。
    dump で読めるのは止まっているスタックと待ち先まで
  - **していないこと**: 再現検証(全席の Linux 側を止めうる)・`session.idleTimeout`(正の整数秒、既定 30)の変更・
    upstream への報告(材料は 2 件目のスタックと、VM ごとに 26 スレッドが残る事実)

### 開発環境(スリープ止め `cargo xtask awake`)

要望のうち、このリポジトリの変更だけでは満たせず、実行側(Claude Code CLI かデスクトップアプリ)の変更が要る未達。
未達のまま残っていて、完了ではない。

リポジトリ側の Windows API 実測は[実測記録](../ci/baseline/awake-control-windows-x64.md)。
デスクトップアプリのログが読め、要求を 1 本の呼び出しに結び付けられる間は、[ログ補助](awake-ログ補助.md)
(不完全を承知で確度を上げる後追い。実スリープ試験の記録もここ)が下の 2 件の許可待ちと許可後を補う。
下は補助が止まっている・使えない時の挙動。補助があっても、実行前の保持を保証する正式な通知の不足は残る。

- **人が許可した後の、子プロセスを作らない呼び出し(MCP・WebFetch・WebSearch)は、許可から終了までスリープを止めない** ——
  「作業中は眠らせない」の未達。許可の要らなかった呼び出しは PreToolUse で開くので止め、シェル系は許可の後に
  起きた子で止める。穴は、許可待ちの印が立ってからその呼び出しの結果が書かれるまで
  - **取得経路が無い**(Claude Code 2.1.281 / 2.1.284 の本体で確認): 許可はアプリが `--permission-prompt-tool` への
    stdio の制御応答で返し、許可・実行開始を知らせる hook は無い(PermissionRequest は待ちに入る時だけで、入力に
    `tool_use_id` も無い)。実行するのはアプリ内の MCP(`ccd_*` / Claude_Browser / visualize / terminal /
    scheduled-tasks / mcp-registry / claude-in-chrome / computer-use)か claude.ai のコネクタ(遠隔)で、経路に割り込める点が無い
  - **保証の代替にはならないもの**: タイマー・プロセスの有無・ログの無音からの推定、自動許可、アプリの `main.log` の後追い
    (許可要求と応答の行は書かれるが、読むのは実行開始の後 = 実行前の保持を保証できない)、OpenTelemetry の
    `tool_decision`(非同期のバッチ送出で、同じく実行前に間に合わない)
- **アプリ内 MCP が自分で人に許可を求めている間は、スリープを止め続ける** —— 「人を待つ間は眠る」の未達。
  例: Claude_Browser の `navigate` / `preview_start` / `browser_batch` はローカルファイルを開く時にアプリ独自の
  許可要求 `browser:open_file` を出し(種類はほかに `browser:open_site` / `domain_transition` /
  `submit_credentials`、computer use の `computer:request_access`)、CLI の PermissionRequest も Elicitation も
  発火しないので、呼び出しは許可されるまで走っているままになる(実測: 許可まで 43 分、その間ずっと保持)。
  CLI が PermissionRequest を飛ばす許可要求(`personOnly`: 他人の artifact を読む WebFetch 等)も同じ。app.asar に MCP の Elicitation を呼ぶ箇所は無い(SDK の定義だけ)
- **要る変更(実行側)**: ① Claude Code CLI — 許可の解決時に実行より前に同期で走る hook(`tool_use_id`・判定・
  `agent_id` を運ぶ)、`personOnly` の許可要求でも PermissionRequest を走らせる、Elicitation / ElicitationResult の
  入力に呼び出し元の `tool_use_id`・`agent_id` を載せる ② デスクトップアプリ — 呼び出しごとの開始・入力待ち
  (アプリ独自の許可要求を含む)・再開・終了を外へ出す。対象はこの環境の MCP ツール全部と WebFetch / WebSearch
  (サブエージェント内も同じ) ③ デスクトップアプリ — 作業中の保持から、人を待っているターン
  (未解決の許可要求・質問)を外す(下の項)
- **デスクトップアプリ側の保持は、人を待っているターンを数え続ける** —— 「人を待つ間は眠る」の未達
  (アプリ 2.16120.0 / 2.19675.0 の本体 `app.asar` で確認)。アプリの「作業中の保持」(設定 → Claude Code
  「Keep computer awake while Claude works」= `ccKeepAwakeWhileWorking`)は、セッションを
  `turnRunning ?? isRunning` だけで数える。許可・質問(AskUserQuestion)待ちもターンの途中なので数えたままで、
  外れるのは進捗(`message` / `tool_permission_resolved`)が 60 分無い時(stalled。再起動で失う背景作業が
  あれば 3 時間まで)、解除はその 30 秒後。許可待ちを除く判定(`isRunning` かつ `pendingToolPermissions` に
  `confirm_` 以外が無い)は保持のコードの隣に定義されているが、どこからも呼ばれていない。
  holder は人待ちを数えないが、アプリの要求が残る間は眠れない(他プロセスの電源要求は取り下げられない)。
  実測は[運用中の記録](../ci/baseline/awake-control-windows-x64.md#運用中の記録): 5 分以上の質問待ち 9 回、
  眠れたのは 60 分を過ぎた 3 回だけで、どれもアプリの stalled 解除と同じ秒
  - **回避策: アプリの保持を Off にする(この機械は Off)** —— この repo の判定は holder だけになり、人待ちは
    無入力タイマーどおりに眠る。hook の無い他プロジェクトのセッションは作業中も保持されない(要る時はセッションの
    メニューの「Keep computer awake」を手で入れる)。上の「許可から終了まで止めない」穴もアプリの保持が覆わない
    (運用中の記録の 4 日間、ツールの許可画面は 1 件も出ておらず、穴に入る呼び出しは無い)。
    アプリを On で使う場合の代わりの手は、AskUserQuestion を hook で止めて本文で訊かせること
    (選択式の画面を失い、許可画面の待ちは直らない)

### 性能(メモリが予算の縁)

**性能改善の着手順**は [メモリと操作応答の改善計画.md](メモリと操作応答の改善計画.md) を参照。
**予算に対する答えは [perf-windows-x64.md](../ci/baseline/perf-windows-x64.md) が正**。

- **残る超過の正体は、一族に無いグリフ 1 つで Qt がフォント DB の全 family を populate する代金**
  (機構と効かないと分かった手は rules-refs/app-ui.md「perf の判定行は net で読む」)。**効く唯一の手は
  絵文字 run を別 Text に分けて色フォントを primary にすること**だが、簡体字には効かず、対症療法なので
  **却下**(ユーザー判断)。**決定: 代金は許容し、判定は歩きの分を引いた net で読む**。初回の停止は
  時間の判定の外に居る — 含めるなら絵文字の行を `--select-oid` で名指しする。上流(Qt)への報告は任意
- **ページを開く +72MB のうちヒープ +52MB は、Rust の 19.4 を引いた ~32MB が QML の
  オブジェクト群**(記録 §常駐の内訳)。**窓だけ(リポジトリ無し)でヒープ busy 72MB・37 万ブロック**。
  どの部品が太いかは未計測 — 詰めるなら item tree の census を
  部品ごとの個数に変えて、窓と `RepoPage` の何が何個建っているかを先に数える
- **net を予算の縁(判定の座りで max 294.9MB、峰と settled の座りで 300.4MB)へ押し上げた増分は
  C++ / QML の側で、Qt 6.12 でも Rust でもない**(要調査)。同じ座り・同じコーパスの撃ち比べ(net / 起動):
  `16ff3cb30`(09-15、Qt 6.10.3)256 / 1110ms ⇔ main `168b42b99` 295 / 1295ms(ABBA 各 6 回)。
  Qt 更新の前後 `0c86d42a7` ⇔ `5b668a3c4` は 293 / 1290 ⇔ 291 / 1240ms で差なし(ABBA 各 4 回)。
  製品コードの commit 列で点を撃つと(各 2 run)`25212bbad` 262 / 1117・`ff48d5871` 256 / 1130・
  `8ca8b0316` 271 / 1245 — **最初の段差は `ff48d5871`〜`8ca8b0316`(09-20〜09-22)**、残りはその後〜

  (記録 §Rust ヒープ)ので、増えたのは QML / C++ のヒープ。
  続けるなら区間を `perf --at <A> --compare <B> --runs 2` で二分する
- **`perf --software` はロック中は始まらない**: run の前に機械が静かになるのを待つ条件
  (`perf::sampler::wait_for_quiet`)に「セッションが対話中(アンロック)」が入っていて、
  `--software` でもそこで待ち、30 分で断る。ロック中に software の bench そのものが進むかは未検証

  トポロジから消えた時の `--screen` の pin も未検証
- **操作応答は縁**(数字は記録 §判定。**縁の正体は往復の揺れ**で、往復はプロセス生成が主)。

  - **diff を開く 1 点(人が待つ長さとしては最長)の critical path は `source_text` の直列 2 本**
    (`rev-parse --verify` → `cat-file blob`)。commit の diff は詳細一覧が status を知っている
    (`D` 以外は新側が在る)ので、`DiffTarget::Commit` に status を運べば probe 1 本が消える —
    rules-refs/core.md「読む前に `rev-parse --verify -q <spec>` で訊く」の commit 側だけの例外 = 規約判断
  - **詳細の `drain` は `reset()` で一覧のデリゲートを作り直す**。`dataChanged` + 末尾の insert / remove に

- **グラフを一度流した分は戻らないが、漏れではない** — **一度見た行の数**で頭打ちし、走った距離では

  設定で下げられる**(規約 §設定の画面 `COMMIT GRAPH`)

  - **却下: フル Shape 化** — バッジの punch(`destination-out` がレーンと顔をくり抜く)は Shape に無く、
    背景色の円での代替は選択行のハイライト上で破綻する。実装し直すなら punch を使わない意匠の再設計とセット
  - **却下: `CutName` の切り取りを二分探索にする**(実装して測って戻した — 差なし)。**elide の答えは
    正解の 2 文字以内から始まる**ので、ループは 2〜3 回しか回らない。**再提案には新しい実測が要る**。
    減らすなら文字列全体を測る操作(1 行につき 3 回 = `measure` の binding / `inkOf(whole)` の可否判定 /
    `end` 以外が使う elide)

### 画面表示中の読み込みの間隔 — 重さで決める(ユーザー決定)

規則は `session::pace`、駆動は `session::pacer`、実装対応は rules-refs/core.md「表示更新はポーリング」、
重さの実測と定数の根拠は [poll-cost-windows-x64.md](../ci/baseline/poll-cost-windows-x64.md)。

- **決定**: 自ツリーは既定 5〜15 秒(1 回が長い時は終わってから 3 秒置く。床がそれより短ければ床)。
  他の worktree は 1 本ずつ・期限の早い順・自ツリーの隙間で読み、収まらなければ自ツリーの回の直後まで 1 回だけ待って
  始める。他の worktree の天井は既定 45 秒。**床と天井はどちらも設定できる**(画面は `Application` の `REFRESH` の章。
  説明は「全リポジトリに効く / 自動の間隔は読みにかかる時間に合わせる / 短いほど早く出て資源を使う」だけ)。
  変えた設定は、もうセットした待ちにも効く。範囲と天井は処理能力が
  足りない時は努力目標。窓が戻った時に読む他の worktree は表示中の 1 本だけ。他の worktree の読み方は
  「自動 / 固定 / 読まない」(画面の語は `Automatic` / `Fixed` / `Off`)で、読まないでは秒の欄を出さない。
  off から戻すとまとめ読み 1 回ですべての worktree を読む。読み方のキーが無いファイルは自動
- **重さは代理指標**(git 子プロセスの寿命の合計)。CPU 使用率・I/O への影響・画面に出るまでの遅れは保証しない
- **worktree が多い時**: kotlin 級の worktree なら 7 本前後で 1 本の間隔が天井の 45 秒に届き、それより多いと重さの
  割合が本数に比例して増える(天井を守る側に倒している)
- **実機での振る舞い**(HDD・低性能機・macOS の App Nap・Linux)は P5-確認事項 §26

### 見た目の宿題(不具合ではなく、やりたいこと)

- **`row-card <行> --preset carried` は製品に無い画面を撮っている**: 別の worktree の
  未コミット行に hover カードは出ない —— 行は `isWip` なので `GraphRowDelegate.partAt` が `""` を
  返し、`openPointed` も `carried` で降りる。**動詞が `rowHoverRequested` を直に呼んで門を迂回する**
  ので、空のカードが撮れる。**しかも hover 先が run ごとに違う**: 別の worktree の行は自分の pass で届き、
  `PageSettled` はそれを待たないので、実 commit のカードか空のカードかの 2 通りになる(判定は commit で
  読むのでどちらでも緑)。census には無い(段分け表の `twin`)。動詞の近道そのもの(`rowHoverRequested` を
  直に呼ぶ)を `row-part` のように `pointerRowX` を通す形にするかは要判断

- **選択のある hunk で `Discard 3 lines` を出すか**: 行を選べるようになって「素の `×` には
  失うものを書く場所が無い」という理由が消えた。今は `Discard hunk` のまま(規約 §その他の操作)
- **サイドバーの張り付き行が「クリックの地」を着るか**: 一覧の行は `bgSelected` で「直前に
  クリックした行」を言うが、その行がスクロールで出て行って身代わり(`HeadPinRow`)に変わると、
  その地は消える。**グラフの張り付き行は行の 2 つの地を着る**(rules-refs/app-ui.md の
  `GraphHeadPin.pinPicked`)ので、揃えるなら `gestures.activeKey === factsKey` で `bgSelected` を 1 枚足す形。
  **置いてある理由は絵が撮れないこと** —— 「クリック済み + 自分の行が画面外」を同時に作る動詞が無い
  (足すなら `nav-pin-edge` に引数を 1 つ = 行が見えている間にクリックしてから末尾へ送る)
- **`AppCombo` の山の側だけが、字より広い所に立っている**: 枠と文字の間はアプリ全体で
  `spaceXs` に揃ったが(規約 §余白 の入力欄の項)、山の席は `spaceSm` のままで、印が箱の中に
  持つ余白と合わせて枠から 13px 空く。詰めるには §余白 の引き算で、引き算が負になるなら席を `iconSm` へ落とす側
  (§余白「引き算が負になったら席が広すぎる」= タブの `✕` の前例)
- **`ops-branch` の絵から木の印が抜けることがある**(判定は緑のまま): 動詞は refs の着地と
  WORKTREES の件数(`pageWorktrees.total > 0`)を待ってカードを開くが、ブランチ行の `held`
  (他の worktree が立っている = 木の印)は、一覧が持ち主を変えた時に core が refs を**読み直して**
  付け直す(`RepoSession::refresh_worktrees` → `read_refs`)ので、一覧の着地と読み直しの着地の
  間に開くと印の無いカードが撮れる。**直すなら「読み直しが着いた」を
  QML が読める形にする**(今はどちらの一覧にもそれを言う値が無い)。実窓でも、同じ隙間に
  カードを開けば印の無いカードが出る
- **規約 §ウィンドウの縁 に fetch / push / stash を帯の部品として書いた節が残っている**

## 刈り込みで見つかった網の穴と不具合

### 文書が古い(測り直して書き直す作業)

- **fetch / push / stash は操作パネル(`TopBar.actionSeat`)に在るが、規約はまだ帯に置いている**: §窓の床 の
  「帯の床 = … + 帯の右側全部」「fetch / push / stash も畳んだ姿で数える」と帯の床の表(Win 509 / 549・Linux 340 / 380)、
  §ウィンドウの縁 の「fetch / push / stash も同じ順で譲り、最後は印だけになる」の段、rules-refs の「821×245」・動詞 `floorH=245`。
  「幅の床 = max(帯の床, ページの床)」は `TopBar.floorWidth` が含むパネルの行を落としている。**`window-floor` の 4 形と
  `badges floor` を両 OS で撃ち直し**、パネルの行の床を足して書き直す(畳み方の段そのものは `TopBar.actionFold` / `wordCut` が
  今も持つので、書き換えるのは置き場と床の勘定)
- **Linux だけメニューの最長行が省略される**(rules-refs)— `AppMenu.widestRow` の `Math.ceil` で直った可能性。Linux で撮って確かめ、
  直っていれば rules-refs の行を消す

### 動詞の網の穴(主張を縛る行が無い)

- **census の行は既定の preset(`basic`)を落として記録される** → gate の撃ち直しで `Arg::WithPreset("basic")` の must_say に当たらず、
  `corner` の `shown=true` は gate で判定されていない(verb-tiers は判定される前提)。census の記録か must_say の照合をコードで直す
- **must_say の行が無い**: `push-retry` / `open-not-a-repo` 系 7 動詞 / `diff-fold-by-hand`・`diff-keep-folded` / `open-again` / `graph-divider`(絵で足りるか)
- **must_say が縛らない値**: `edit-message-focus` の `color=` / `publish` の `dialog=`・`name=` / `drop-commit` の `hold=` /
  `delete-branch` の「左のカードが閉じたか」/ 設定画面の範囲の丸め(同時実行数 0 → 既定・秒 1 → 5)
- **素の `stash` run はどんな帯でも落ちない**(`stashNamed()` は `stashWanted` が空なら常に false)— 全部同じ名前を着せる帯を捕まえる run が無い
- **`--preset longnames` の操作パネルは、開いた直後の自動 fetch の答えがいつ着くかで形が変わる**(着くと diverged になり push の語が
  `push` → `push -f`): `band-actions` / `-none` / `-fold` は作業ツリーの読み込みまでしか待たないので、答えが報告行より先に着けば
  判定も絵も `push -f` の幅(Windows で `want=52`・`w=1041`)、撮影の後なら `push` の幅(`want=40`・`w=975`)、**報告行と撮影の間に
  着くと判定した形と絵の形が違う**(`-none` の行は `folded=false`、絵は畳んだ印)。must_say はどれでも通る。`ops-panel --preset longnames` の
  `push=` も同じ理由で `ready` / `diverged` の 2 通り。**絵を OS 間・run 間で並べる時は、報告行の `want=` / `push=` が同じ run どうしで比べる**。
  直すなら「自動 fetch が終わり、その後の status が着いた」を待つ条件が要る(`busyCount === 0 && !autoFetchRunning` は fetch が
  始まる前にも真)
- **census に形が無い = gate が一度も回さない**: `stash-state` の ready / clean / conflicts / `perf diff`・`perf scroll-none` /
  `commands-fail-shut fold` / `remote-menu`・`remote-url` の `:marked` / `nav-add-remote` の noremote・folded /
  `nav-*-box` の `:away`・幅 / `switch-lands feature/topic-a:2` / `switch-stopped main --preset rebase-conflict`(`-go` の must_say と合わず赤のはず)/
  `code-send columns.txt --preset widechars` / `diff-follow` の staged・untracked 形 / `name-box-drop` の `box=false`

### 不具合(コードを読んで確かめた)

- **検索 `0000` が worktree の行に当たる**: core `find::Query::matches` は空の id だけを飛ばし(「呼び手が非コミットの id を空にする」前提)、
  app `GraphModel::hits` は worktree の行の id(0 が 40 個)をそのまま渡す。規約 §コミットを探す の表「`0000` でも当たらない」に反する。
  core の `a_row_that_is_not_a_commit_matches_nothing` は行を id `""` で作るので、実物の形を縛っていない
