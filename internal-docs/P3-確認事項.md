## 残っている実装

**フル interactive rebase はプラン編集モードとして配線済み**(意匠の正本は
デザイン規約 §フル interactive rebase、実装対応は rules-refs/app-ui.md)。HEAD より古い
コミットの reword もこの画面が道になった。残る磨き(不具合ではない):

- **reword の鏡写しは保存時**(行の subject は `setMessage` で更新)— 打鍵ごとの live
  反映にするなら `MessageEditor` に text-changed の口を切る
- **squash / fixup の「親へ畳む」を言うのは動詞チップだけ**(字下げは撤去 = 3 列を揃える
  指示)。モックにあった接続線(下の行へ肘)は未描画 — 描くなら行を跨ぐので pane 側の
  オーバーレイ
- **プランの読みに行数の上限は無い**(ユーザー判断)— `--root` プランは全履歴を
  `PlanRow` に組む。JetBrains/kotlin で 138,915 行・`read_rows` の git 読みだけで 1.40s・
  stdout 25.8MB。**性能予算はベースライン**(素で表示した時)の話で、利用者が自分で開いた
  全履歴プランの増分は最適実装の分として許容する。規約 §フル interactive rebase の
  ローディング面がこの遅さの受け皿
- **プラン行に ref チップが出ない**(`--update-refs` で連れて動くブランチの可視化)。
  行 0 = 現在ブランチ分だけでも出す価値あり
- **実行後の選択は既定挙動**(旧選択が消えて default select)— 「読んでいた行の
  書き換わった先を追う」は未接続。単体 reword の `followRewrittenCommit` は在るが、
  armは `RepoPage.saveMessage` の 1 箇所だけで、プラン実行はそこを通らない
- **動詞チップに ▾ の描画が無い**(チップ押下と右クリックで開く)。NavIcon に chevron の
  項が無い件(下の §AppCombo)と同じ席
- **Esc でのプランの取り下げ未配線**(ヘッダの `Discard` ボタンのみ)
- **ヘッダ / onto 行のブランチ名は開いた時点の写し** — 端末で base ブランチだけを
  動かされると名前は古くなる(挙動は oid 釘付けで正しいまま。行末の sha が実体)。
  名前の生き直しは refs 更新との突き合わせが要る
- **行に掴み点(grip)の印が無い** — レビューで除去(トークンに点サイズが無く、直書きは
  規約違反)。行全体が掴み手で機能は成立。**印を戻すならトークン追加の人間承認とセット**
- **プラン行の選択は「模型の selected_row + ページの selectedOid」の二重持ち** —
  reorder の追従は模型側 remap で守られているが、所有を模型の oid 1 本に寄せる余地あり
  (レビュー所見・据え置き: 動く実害が無く、寄せると graph 選択との橋が別に要る)
- **プランの push 済み count は模型が持つ**(`RebasePlanModel.pushedCount` — 開く読みが
  数え、refs が動いたら range 名指しで数え直す。共有の publish 枠は無い)。数え直しの読みが
  失敗した時は開いた時の値のまま(異常系のみ・次の `refsMoved` で撃ち直す)
- **クリーン停止の WIP 行は語が場面に合っていない**(目視・`rebase-edit-stop` の絵)—
  `edit` 停止の着地はグラフ最上部の `Uncommitted changes` 行 + 右ペインの
  `UNCOMMITTED CHANGES (0)` + 空のファイル一覧で、**行は「無い物が在る」と名乗る**。
  席そのものは仕様どおり(規約 §進行中の操作から出る「着地は WIP 行」= 出口カードは
  この行の下に吊るので、行を消すとカードの席ごと消える)。**据え置き** — 停止の説明は
  同じペインの底の出口カード(`REBASING — 1 of 2` / `edit Stopped on purpose at <sha8>`)が
  持っており、読み手が次に何をするかは迷わない。直すなら行の語の側(席は動かさない)。
  同じ絵のコミット枠(`commit to HEAD`)は**押せない** — staged ゼロ・amend でなし・
  立っている本文も無い停止では `WipCommitBlock` の可否が降り、断りは
  `Stage something to commit`

### 別 worktree の未コミット行(決定・実装とも済み。残るのは下の実測 1 件)

**他の作業コピーが抱えている未コミットを、その worktree の HEAD の上に点線〇で出す。**
乗る内容は自分の未コミット行と同じ(点線〇・`Uncommitted changes`・6 つの tally)で、
違うのは読む頻度と、**行が読み取り専用であること**。

- **置き場は「着地先に着く合成行のいちばん上」**(ユーザー決定) —— 直上ではない。
  **未コミットはこれからコミットになるもの**なので stash より上に立つ。実装は、
  着地先そのものか、着地先を土台にする stash のどちらかが先に来た所で出すだけ。
  リーシュが stash の行を跨いで伸びるが、**それは自分の行が今やっている形**
  (自分の行は walk の前に先頭へ積まれ、stash は実コミットとして日付順に入る)

- **引き金は 2 つに割れる**(ユーザー決定) —— **listing はページの tick に載せる**
  (実測 23ms・ほぼプロセス起動代)、**他所の `status` は自前の遅い tick**
  (`settings::Defaults::copies_interval_secs` = 30 秒から・設定画面の `GIT PROCESSES` で変えられる。
  1 worktree につき `git status --porcelain=v2 -z --branch -uall` 1 本・同時に走る本数は
  実行枠の background 上限 = `git_concurrency` の半分。実測と既定値は
  [git-slots-windows-x64.md](../ci/baseline/git-slots-windows-x64.md))。
  **残件: 開幕の巡回(`refresh_quick` → `refresh_carried`)はグラフの初回描画と同じ機械を取り合う**
  — 8 コピーの corpus で起動→グラフが 1.16s → 2.0–2.8s(同記録 §読み)。枠は足りていて
  (interactive は待たない)、食われるのは CPU(1 本の status が 11 コア幅)。直すなら開幕の
  1 周を `LogFinished` の後へ遅らせる(focus の巡回はそのまま)。予算 3s の内側なので今は据え置き。
  **10 秒 tick には載せない** —— 支配項が worktree の本数だけ増える(実測: 追跡 109,652
  ファイルで 1 本 0.48s、10 秒 tick の支配項は元から status =
  ci/baseline/poll-cost-windows-x64.md)。**焦点まかせにもしない** ——
  `Main.qml` が「画面に在ることが定期読み直しを駆動する。クリックした時だけ追いつく窓は、
  開いたままにしている当のものを隠す」と言っており、**他の作業コピーに関する物だけが
  その原則から漏れていた**(WORKTREES の行も「別の作業コピーが持つ」の印も、窓を
  クリックするまで凍っていた = 2026-09-13 ユーザー報告)。
  **安い dirty ビットは git に無い**(`diff-index --quiet` 0.27s / `status -uno` 0.29s で、
  untracked を捨てても 4 割しか下がらない)
- **他所の木へ向けても安全なのは、既に立っているから** —— `--no-optional-locks` と
  `GIT_OPTIONAL_LOCKS=0` は**全 invocation の標準**(`process::executor`)。足すものは
  無い。無ければ素の `status` は相手の index を書き、こちらが `index.lock` を握って
  いる間、その worktree で働いている人の `git add` は
  `fatal: Unable to create … index.lock` で落ちる(実測)
- **`-uall` のまま**(`-unormal` にすると同じ木を自分のタブで開いた時と数が食い違う)
- **行は読み取り専用**。書き込みは相手の `index.lock` を必ず取るので避けようがなく、
  書き込みキューはタブ単位(下記「同一リポジトリ複数タブのキュー」と同じ穴)。ファイル
  操作の入口はその worktree を開いたタブの側にしか無い
- **行は worktree 名で名乗る。左のチップだけで、他に変更を加えない**(ユーザー決定) —
  既存の `LabelKind::Worktree` チップ(ブランチを持たない作業コピーがコミットに着ける
  もの)をそのまま使う。語の隣に名前を置く案は落とした(tally の x が行ごとにずれる)。
  **ブランチ名は要らない**: その worktree のブランチは 1 行下のコミットが既に名乗って
  おり、別の作業コピーが持つブランチのチップは木の印を着ける規則が既にある
  (`RefLabel::held_elsewhere`)。**名前は `shown_name` = パスの末尾セグメントのまま**
  (ユーザー決定。木の印が補う)—— この repo の席なら `a`〜`f` の 1 文字になる
- **tally は行へ下ろす** — 今は `ListView.view.wipAdded` = 画面に 1 組しかないので、
  行が 2 本以上になると全部の行が自分の木の数を名乗る(実測の絵で 3 行が同じ `+1 ✎2`)
- **id の族は広げない** —— **全ゼロは全ゼロのまま**。行の同一性をどこへ置くかは下の
  決定(「行の同一性は『どの作業コピーのものか』」)が正

**扉は 2 つ —— 選択でこの窓に読み取り専用で出し、ダブルクリックで別タブで開く**
(ユーザー決定)。**hover では何も出さない**が、**中身は読めなければならない** ——
読むのはこの窓、書くのはその木のタブ。左メニューの WORKTREES の行が開くのと同じ扉
(`SidebarRowGestures.activateRow` → `openRepositoryPathRequested`)は 2 つ目として残る。

| 所作 | この行での扱い | 実装 |
|---|---|---|
| 左クリック(選択) | **その作業コピーを WIP ペインへ読み取り専用で出す**(動詞 `carried-read`) | 行が行番号を上げ(`GraphRowWalk.activated` / `claimRow`)、`RepoPage.openWipFor(row)` が `carriedPath` を決める |
| **ダブルクリック** | **その作業コピーを別タブで開く**(動詞 `carried-open`) | 行が `carriedOpenRequested(path)` を上げ、ページが `openRepositoryPathRequested` へ渡す |
| hover カード | **出さない** | 空のカードに `1970-01-01 09:00` だけが出る(絵で確認) |
| hover の highlight | **出す** — 行は扉を持つので、他の行と同じように明るくなる | |
| 右クリック(コミットメニュー) | 出ない | **既に出ない** — `GraphRowDelegate` の `if (!rowItem.isWip)` |
| チップの改名(間を空けた 2 度目のクリック) | 出ない | **既に出ない** — `W` の `label_kind_word` は `""` |
| 矢印キーの現在行 | **着地させる**(他の行と同じ) | 行番号が id と一緒に上がる(`GraphRowWalk.activated(oidHex, atRow)`) |
| `!`(行末の改行コード注記) | **出さない**(次の `git add` の話 = 自分の木のこと) | 他所の status には `EolMark` が付かない(`CarriedStatusMsg`)ので自然に落ちる |

**独立した 1 つの表示モード `WORKING COPY`**(ユーザー決定 —— 「stage / unstage を
分けるのがダメ」「コミットボタン等も出さない」「通常コミットと同じような表示をベースに」
「作業中 worktree 名がちゃんと分かるように」)。**意匠の正本はデザイン規約
§別の作業コピーを読む**。述語は **`RepoPage.wipWritable` = `carriedPath === ""`** で、
**行の同一性がそのまま述語**(下の「行の同一性」)—— 真なら `WipPane`、偽なら
`CarriedPane`。

- **無効の控えは 1 つも出さない**。押せない物を並べて理由を書く形は採らなかった
  (2026-09-13 に一度そう作って差し戻し)—— **読む画面には読む物だけを置く**
- 残る唯一の無効は**帯の `stash`**(ペインの外・この窓の未コミットを退避するボタン)で、
  理由は元からのツールチップが言う
- **この窓の状態を他所の木に着せない**: conflict の 2 面の名前(`sideOurs` / `sideTheirs`)は
  空に落とす・`Waiting for <mergetool>` は出さない・停止中の操作のカード(`OpExitCard`)は
  立てない。どれも「**この**木が今何の途中か」で、他所のファイルの上に出れば誤属になる
- **`commit … to <branch>` はこの窓のブランチを名乗ったまま**(無効)。押せないボタンが
  名乗るのはそのボタン自身の行き先で、他所のブランチを名乗らせると「ここから
  あそこへコミットできる」と読める

**読みは 2 本目の経路**(core は 1 本を向け直すだけ):

- ファイル一覧は `SessionEvent::CarriedStatusLoaded` → `CarriedStatusMsg` →
  `carried_nav_*` の 3 本 → `NavSectionModel` 3 つ。**自分の木の 3 本とは別インスタンス** ——
  自分の status は 10 秒 tick で届き続けるので、1 組を使い回すと他所の行が毎 tick 消える
- **一度に 1 コピー・最後の ask が勝つ**(`session::latest` の `carried_read`)。別の木は
  読む時間が違うので、着順に任せると「読み手が離れた方」が残る
- diff は**同じ読みを別の木へ向けるだけ**(`RepoSession::load_carried_diff` =
  `publish_diff` に別の workdir)。**epoch は共有**なので自分の木の読みと互いに追い越せる
- **`last_diff` の鍵に workdir を入れる** —— 同じパスでも別のコピーなら別のファイル。
  パスだけを鍵にすると、自分の木の再読みが他所の指紋と一致して「動いていない」と
  答える(再現テスト `a_copys_file_is_not_the_same_file_as_ours_of_that_name`)
- 再読みは**コピー側の tick**(`Metrics.copiesIntervalMs`)。ページの 10 秒 tick へ
  載せると、開いている他所のファイルをこの木へ向けて読んでしまう
  (`DiffModel.refresh_carried` が向きを持つ)

**worktree 特化の右クリックメニューが出来た時**(今は無い — WORKTREES の行もメニューを
持たない):

- **同じ作業コピーのチップは 2 箇所に出る** — ブランチを持たない作業コピーが立っている
  コミットと、この WIP 行。**メニューを足すなら 1 つを両方から開く**(2 つ書けば必ず
  食い違う)
- **ただしこの行からは開かない。** 入口は WORKTREES セクションの行(と、既にチップを
  持っているコミット行)に限る。`worktree remove` / `prune` は破壊的で、**この行が持って
  いる扉は「その作業コピーを開く」1 つだけ**という形を崩すため
- **足すには `label_kind_word` が `W` に語を返すようにする必要がある** — 今は `H`(HEAD の
  印)と同じく `""` = 「名指すものが無い」と答えており、それが「チップは名前であって
  扉ではない」を機械で保証している。**この 1 行を変えると 2 箇所が同時に扉になる**ので、
  変える時は上の 2 つを同時に決める

**別の worktree が汚れた / 綺麗になったことで、他のコミットの色が変わってはならない**
(ユーザー決定)。**済み** —— `fix(core): a leash that lands where one is already waiting
borrows its colour`。**ずれる条件は「着地先に既にレーンが待っている時」だけ**で、tip の
上に差した行は元からずれない(デモの実 walk を写したテストで両方を固定 —
`graph::leash_tests`)。機構は、差し込んだ行が取ったパレット枠が**どのチェーンにも
渡らず捨てられる**こと(コミットはより低いレーンの色で出る)で、`take_color` は取った順の
ラウンドロビンなので以降に開くチェーンが 1 段ずれる。**絵で先に見えた「橙→緑」は帰属が
誤り** —— あれは tip の上の行で、ずれない側だった。

**差し込んだ行は着地先のチェーンの色を借りる**(ユーザー決定 — 今の表示に近い側)。
既に待っているレーンがあればその色、無ければ着地先が取るはずだった色を取って渡す
= 今の HEAD と同じ形。**専用の色は採らない** —— トークンの追加になり、人の承認が要る
(CLAUDE.md 絶対制約)。

**行の同一性は「どの作業コピーのものか」**(ユーザー決定)。**全ゼロは全ゼロのまま** ——
あれは「オブジェクトが無い」という git 自身の綴りで、どの作業コピーの行にとっても
正しい。曲げるべきは**それを行の住所として使っている所**で、自分の行は特例ではなく
作業コピーの 1 つ(たまたまこのタブが開いている方)。

- `wipOid`(全ゼロ判定)は「作業コピーの行か」を答え続ける —— 意味を曲げない
- ペインを開く判定は「**その作業コピーはこのタブのものか**」へ。これが読み取り専用の
  述語そのもの
- **`GraphBuilder.rows`(oid → 行)に合成行を載せない** —— **済み**(`refactor(core):
  a row with no object is not filed under one`)。あの地図はコミットのためのもので、
  読み手 2 つ(`row_of` = ref が指すコミット / 順序ガード = コミットの親)はどちらも
  合成行を訊かない。**id を渡すのもやめた**ので、行が持たない物を builder が受け取る
  形も消えている

- **同じコミットに複数立っていたら全部積む**(ユーザー決定) —— 作業コピーの数だけ行が
  立ち、それぞれ自分の名前チップを持つ。何本あるか・誰かが一目で読める
- **自分の行には名前を出さない**(ユーザー決定) —— 自分の行は名前無しで最上段のまま。
  既存の絵が 1px も動かず、**見分けは「名前が無い方が自分」**になる
- **木の印が縦に並ぶのは許容する**(ユーザー決定) —— 他所の行の `Worktree` チップと、
  下の行のブランチチップ(`held_elsewhere`)が同じ印を着け、同じコミットに 2 つ立てば
  3 連になる。**枠の色で既に分かれている** —— worktree のチップは灰、ブランチの
  チップは色付き
- **`bare` と `prunable` は読みに行かない** —— `prunable` はディレクトリが無いので
  status が必ず失敗する。自分自身は `note_worktree_holders` が既に外している
- **同時に撃つ `status` は 4 本まで**(ユーザー決定 —— **決め打ちで始める**)。上限その
  ものはどの数でも要る: executor に上限が無いので、20 worktree なら 20 プロセスが同時に
  立つ。上限の仕事は「他所の行を速く出すこと」ではなく「**この窓の読みの邪魔をしない
  こと**」 —— **順序で守ろうとしてはいけない**: この窓の status を先に通そうと単一
  フライトを待たせたら輪になり、開いたパスがグラフのローディングのリングのまま止まった
  (実測)。守るのは**別の tick に置くこと**と**上限**の 2 つ。
  **この 4 と 30 秒は次の本計測で取り直して、その数字を出して決め直す**(宿題は
  [perf 記録](../ci/baseline/perf-windows-x64.md) §未取得 の「同時に走る `status` の
  本数と実時間」。1 本 0.48s までは測れている)

## ウィンドウ chrome — 形は決まり、残りは中身

形の正本は [デザイン規約.md](デザイン規約.md) §ウィンドウの縁。Windows の縁に残る 2 つ
(窓メニューの移動・サイズ変更 / Snap Layouts)は [P5-確認事項.md](P5-確認事項.md) §10。
ここに残るのは中身の方:

- **アドバンス検索**(Ctrl+F の基本検索は配線済み — 正本は規約 §コミットを探す):
  - **項目を名指しして探す形**(`author:` / `path:` / `date:`)。素の語を全軸のまま git へ
    降ろすと `--grep` と `--author` は AND なので和集合に 3〜4 スポーン要るが、接頭辞つきなら
    1 クエリ 1 スポーンで各接頭辞が git のフラグ 1 つに対応する
    (`git log --grep=… --author=… -G… -- <path> --format=%H` が SHA を返すので、アプリ側は
    「その SHA が来たら光らせる」= 印の仕掛けは基本検索のものを使い回せる)
  - **最初に出せるのは `description:`** — 外した 4 つのうち Description だけは行が既に
    持っているので、git を 1 プロセスも撃たずに出せる(パス / diff / 日時 / committer は
    git が要る)。**塞ぐ穴は実在する** — 機能名でしか呼ばれない語は今まったく引けない
    (0 件の語の実測は規約 §何に当たるか)。判断は「据え置き、実使用をもう少し重ねてから」
  - **同時に決まるもの 3 つ**:
    1. **日付で探す**。行は epoch 秒しか持たず、画面の `yyyy-MM-dd HH:mm` は表示側が作る。
       Rust 側にタイムゾーン依存を 1 つ足すか、`LOG_FORMAT_ARG` に
       `%ad --date=format-local:%Y-%m-%d %H:%M` を 1 フィールド足す(`LOG_FIELDS` 8→9・
       parser の field 分岐・`CommitMeta` / `LogRow` / fixture)かの二択。**後者が本命** —
       git が DST 込みで正しく組み、行が画面と同じ文字列を持つ。範囲(`date:2026-08` /
       `--since` / `--until`)もそこで一緒に決まる
    2. **窓の外を探すか**。基本検索は読み込み済みの行しか見ない。git へ降ろす検索は窓の外も
       返せるので、返った SHA がグラフに無い時に何をするか(件数だけ言う / 窓を伸ばす /
       その行まで読み込む)が要る
    3. **パスで探す**(実装計画.md §14 のフィルタ 4 軸の最後)。`-- <path>` は git 側でしか
       解けない
  - **絞り込み(行の間引き)は引き続き別物** — レーンとエッジを「隠れたコミットを跨ぐ」形で
    引き直すことになり、core に 2 つ目の walk モードが要る
- **検索の入口をキーだけにしない案(未着手)**: アプリメニューに `Find commits…` の行を足す
  (規約 §メニュー に沿い、キーが届かない場面の逃げ道にもなる)。`Shortcut` の既定は
  `Qt.WindowShortcut` なので、**窓がまだアクティブでない間はキーが届かない**
  (Windows のフォアグラウンド・ロックで前面にならずに起動した窓 = 「中を 1 回
  クリックしたら以後ずっと効く」の形)
- **macOS の形は決定済み・実装は実機ゲート**(Phase 5)。☰ は持たない — 画面上端の
  メニューバーが常に届く場所に既に在る。`QtQuick.Controls` の `MenuBar` は Qt 6.8 以降
  macOS で既定ネイティブ。**作るのは macOS だけ**(`Loader` で分ける — 他 OS では
  非ネイティブの QML メニューバーが窓の中に 2 段目として出る)。ネイティブ MenuBar は
  delegate を使わない = `AppMenu` の意匠は効かないので、**行の定義を 1 か所に置き見せ方
  だけ OS で分ける**。traffic light が帯の中心から約 6px 上は許容(直すには AppKit が要る)。
  `About` / `Settings…` / `Exit` がアプリメニューへ自動で寄るかは実機で確認

- **`--update-refs` は駆動 rebase では不発**: プラン実行は `update_refs: true` で撃つが

  書く形になる — **UI がこの旗で何を約束しているか**(規約 §履歴を合流させるは rebase 側が
  足すのは `--update-refs` だけと決めている)から決める
- **`GitError::Rejected` を `Withheld` へ寄せるか**: **git を撃つ前に断ったものは
  `GitError::Withheld` + `WriteReport` で報せバーへ出す**という形は main に在り、5 つが
  使っている。`Rejected` のまま残っているのは 10 箇所以上で、**大半は UI が先に止めるので
  報せの出しようが無い**(空本文の reword・mergetool 未設定・空の identity・stash rename の
  読み取り失敗 — Save や行が出ないので人はここへ来られない)= ログに残すのが正しく、
  **core は app のゲートを契約にできない**ので消さない。**判断が要るのは画面から届く方**
  —— `RepoSession::rebase_interactive` の `expect_head` ずれ / 立っている操作の上への
  rewrite(`build::carry_across_rewrite`)/ 操作が立っている最中の `rebase`
  (`ops_integrate`)は、いずれもプランを組んだ後に外が動いた時なので人が踏める。
  寄せるなら kind を 1 つ足して 1 コミット。**個別の箇所を数え上げてここに書かない** —
  一覧はすぐ腐る(前版の 5 件の列挙は倍に増えていた)ので `GitError::Rejected` の Grep が正
- **同じリポジトリのサブフォルダを指した時**: 既に開いているタブへ移る判定は
  `repo::open_key` = `canonicalize` のフォルダ一致なので、`repo` と `repo/src` は別と答えて
  2 枚開く。同じと答えるには `rev-parse --show-toplevel` の答えを待つ必要があり、判定が

  別タブのままが正**(作業ツリーが違う = 見るものが違う)
- **グラフ側の名前の箱の断りも `visible` へ寄せるか**: 左メニューの箱

- **質問を立てる残り 2 経路**: グラフ行の右クリックと左メニューから `startPublishAsk()` を

  `timed out 7 ms`(赤)、spawn の失敗は `did not run` + OS の文(`source.to_string()` が
  `CommandFinished.message` に載る。`hub::sink`)。**止められたのがどのコマンドかは
  他のどこにも出ない**ので、ここを閉じると手掛かりが消える
- **幾何・字送りの px 実測をコメントに残すか**: 時間・メモリ・機材構成の実測値は

## 探索で見つかった残件

修正より記録が適切と判断したもの(修正済み分はコミット履歴参照)。

### core

- **合成 write のキャンセル窓**: `carry_across` で stash 後・switch 前にセッションが閉じると、stash に入ったまま通知が出ない(stash list には残る = 復元可能)。クローズ経路の best-effort 通知を検討
- **1 コミット編集(squash / reword / drop)の todo は tip に pin されていない**: `session::build::run_plan` は `Replay` へ空の `expect_head` を渡す。`sequencer::plan_edit` が読んだ oid 列は固定で、carry(refuse → stash → 再 spawn)の間に外から commit が載ると todo から漏れて黙って落ちる — 画面で組むプランと同じ窓で、そちらは `Replay::tip_still_stands` が塞いだ。塞ぐには `rev-parse HEAD` が 1 本増え、**それが最もよく押される 3 操作の応答経路に乗る**(応答は既に予算超過)ので、pin する値を `EditPlan` に持たせるかどうかは実測の上で判断する
- **同一リポジトリ複数タブのキュー**: キューはセッション(タブ)単位のままだが、**走る順序は作業ツリーが持つ**(`session::write_order` — 受理順に place を取り、request 丸ごと握る)ので、`stash@{0}` 前提の合成(`carry_across` / stash rename の selector シフト)の間に**他タブの stash が割り込む経路は閉じた**(合成は 1 つの write request の中で走る = `build::move_carrying`)。残るのはアプリの外の git(端末で撃った `git stash`)だけで、これは順序で守れる類のものではない
- **`cat-file --batch` の常駐(設計済み・未実装 — 採否は操作経路の実測で)**: 数字は
  [git-slots-windows-x64.md](../ci/baseline/git-slots-windows-x64.md) §プロセス再利用(1 本ずつなら
  `rev-parse --verify` 10ms + `cat-file blob` 17ms、常駐なら 2 回とも <1ms。効くのは diff を開く
  1 点の直列 2 本 = `preview::blob_is_there` + `read_source`。`show` は置き換わらない)。設計:
  **① 1 リポジトリ 1 本** — `RepoSession` が持ち、`git cat-file --batch-command`(2.36+、最低版の
  内側)を `stdin` piped で spawn する = **プロセス層の「stdin は常に閉じる」の唯一の例外**で、
  常駐用の別 spawn 経路(`process::Resident`)に閉じ込め、`GitCommand` の道は閉じたまま。
  **② 要求と応答の対応** — 要求は 1 行ずつ、応答は `<oid> <type> <size>\n` + 本体 + `\n`
  (`missing` は 1 行)で、常駐の口は `tokio::sync::Mutex` で直列に使う(1 度に 1 要求 = 応答の
  読み切りまで次を書かない)。**③ キャンセル** — 要求を書いた後の cancel は応答を**読み捨ててから**
  返す(途中で口を離すと次の要求が前の本体を読む)。読み捨てが `SOURCE_BYTE_CAP`(4MB)を超える
  長さなら常駐ごと終了させて次で再起動する方が安い。**④ 異常終了・再起動** — 書き込み / 読み取りの
  EOF で `Dead` にし、次の要求が spawn し直す(1 回だけ再試行、2 度目は一発 `cat-file` へ落とす)。
  **⑤ アイドル解放** — 最後の要求から 30 秒で kill(タイマは `AutoFetchClock` と同じ手回し可能な形)、
  `RepoSession::close` で kill。**⑥ 保持メモリ** — 実測 360KB + 触った pack ページ(pack 6.4GB を
  写像するのは触った分だけ)。`heap_report` に常駐の pid と生存を載せる。**⑦ 枠** — 常駐は
  spawn の 1 回だけ `Slots` の Here プールを通り(`Priority::Interactive`)、以後の要求は枠を取らない
  (プロセスが増えないので)。**⑧ 観測** — コマンドログには常駐の起動 1 行と、要求ごとの行は
  出さない(`Kept::Unasked` の読みなので背景記録が on の時だけ `<spec>` を 1 行)。

  §判定 の diff の行と並べて採否を出す

### 開発環境(Linux コンテナ)

- **コンテナのボリュームは誰も掃除しない**: `forget_older_images` はイメージの古いタグを消して

  作るので、**席が消えても、使い捨ての worktree が消えても、`IMAGE` 定数を変えても、旧い名前の

  無い。足すならイメージ側と同じ「消したものは印字する」規律で。**消してもホストのディスクは
  戻らない** —— Docker の VHDX はスパースではなく、確保済みのブロックを削除後も抱えたままになる。
  WSL のスパース VHD は破損の可能性を理由に既定で無効で、`wsl --manage --set-sparse` は
  `--allow-unsafe` を要求し、`.wslconfig` の `sparseVhd` も同じ理由で効かない。縮めるには
  管理者権限の `Optimize-VHD` か `diskpart` の `compact vdisk` が要る

### 性能(メモリが予算の縁)

**性能改善の着手順**は [メモリと操作応答の改善計画.md](メモリと操作応答の改善計画.md) を参照。

- **超過の帰属は記録の §常駐の内訳 が持つ**(判定行の settled: private 191 = プロセスヒープ 121 +

  / `setApplicationFallbackFontFamilies`(一覧の先頭に前置きするだけ)、`QFont::setFamilies`、
  `QT_DISABLE_EMOJI_SEGMENTER` — いずれも 90 family / 162 ファイルのままで、「qtbridge / QML に

  歩きの分を引いた net で読む** — `cargo xtask perf` が較正 run `run-font-walk` で歩きを毎回測り、

### 見た目の宿題(不具合ではなく、やりたいこと)

- **選択のある hunk で `Discard 3 lines` を出すか**: 行を選べるようになって「素の `×` には
  失うものを書く場所が無い」という理由が消えた。今は `Discard hunk` のまま(規約 §その他の操作)
- **運んでいるタブの脇にツールチップが残りうる**(**実操作待ち**): 出す条件は
  `pointed && !held` なので掴んだ後に新しくは出ないが、**掴む前から立っていた 1 枚**は共有
  インスタンスの keeper が保つ(`SharedToolTip.wanted` = ポインタが的の上に居れば保つ ——
  運ばれているタブはその的のまま)。座席は `freeze()` で固定なので、タブが帯を横切る間その箱は
  置いていかれる。hover は注入できないので**実操作でしか見えない**。直すなら「的が『もう要らない』と
  言える口」を keeper 側に足す形で、タブ側の細工にはしない
- **`AppCombo` の山の側だけが、字より広い所に立っている**: 枠と文字の間はアプリ全体で
  `spaceXs` に揃ったが(規約 §余白 の入力欄の項)、山の席は `spaceSm` のままで、印が箱の中に
  持つ余白と合わせて枠から 13px 空く(実測: 山のインクの右端 x422 / 枠 x435)。
  詰めるには §余白 の引き算に要る実余白が要るが、**`NavIcon` は `chevron` について答えられない**
  (`inkGrid` / `inkTallGrid` に項が無く、既定の 16 = 箱いっぱいと答える。実際に描いているのは
  升目の 4..12 で、しかも欄は 90° 回して使う)。**まず `NavIcon` に `chevron` の項を足して
  実測で裏を取る**のが最初の一歩で、引き算が負になるなら席を `iconSm` へ落とす側
  (§余白「引き算が負になったら詰めすぎではなく席が広すぎる」= タブの `✕` の前例)
- **打つ欄の右で字を止めているのは枠ではなく山**: `AppCombo` の `rightPadding` は他の欄と同じ
  `spaceXs` なので、**長い名前は山の下をくぐる**(欄の中の `TextInput` は省略せず送るだけ)。
  正しい値は「`spaceXs` + 山の席 + 印の実余白」= トークン 1 つでは書けないので、上の項で実余白が
  出てから決める。今のところ実害は「入りきらない行き先の末尾が山に重なる」だけで、
  `pickOnly` の側は一覧から選んだ名前しか入らない

  §設定の画面)—— 読者が変えに行った時にだけ書く。ただし**書けるのはリポジトリ単位
  だけで、`--global` は書かない**(ユーザー判断) —— 利用者の機械そのものを書き換える操作はアプリが
  持たない(上に挙げた他 GUI の事故がまさにそれ)。`core.eol` と `.gitattributes` は
  今も持たない
- **`diff --ignore-cr-at-eol` の表示トグルは作らない**: その patch は `apply` できず、
  EOL のみの差だと diff が空になる(status は modified のまま)。表示用と staging 用で
  diff の bytes を分けない不変条件を壊す
- **成功した git の stderr をコマンドログへ出すことを、EOL を理由には決めない** —
  `autocrlf=true` では読み取りコマンドでも警告が鳴り続けてノイズになる。
  push の `remote:` 行など他の用途で欲しくなった時に別途判断する
- **`Stage file` と `Stage hunk` の右端は揃えない**: ヘッダの語は `✕` の分だけ内側にいて

  読める
- **選択のある hunk でも `Discard hunk` は hunk のまま**: 捨てるのは**見た目上の hunk** =
  今その diff に出ているもの。`--cached` を付けないので index は動かず、部分ステージ済みの
  分は残る(`stage_integration::discard_a_single_hunk` が「the index is untouched」で
  固定している)。行単位の discard は作らない
- **末尾改行が無いファイルへの行追加は部分ステージできない**: 追加行だけを選んだ patch は
  unified diff として表現できない。前提となる行を自動で選択に足す回避策は入れない —
  選んでいない行を黙って index に入れる方が害が大きい
- **untracked ディレクトリの空殻が残る**: 中の 1 ファイルだけを部分ステージできる代わりに、
  全ファイルを discard すると空のディレクトリがディスクに残る(git は空ディレクトリを
  追跡しないので status は clean のまま)
- **`--allow-empty` / `hunk_count` はブリッジへ出さない**: 空コミットを発行する導線を
  持たない(Commit は staged が 1 件以上ある時だけ通る。amend を除く)。hunk 数は diff 行
  モデルから UI 側で数えられる
- **octopus merge(3 親以上)は作れない**: `merge` は 1 リビジョンのみ受ける。要望に無い
- **push 済みの note が窓の外まで答えることは求めない**(コミット行・ref 行の両メニュー。
  実装対応は rules-refs/app-ui.md)。note が読むのは描かれた行なので、窓
  (`--max-count`、既定 2,000 行)の外は答えが実際と違いうる。**倒れる方向が範囲の両端で
  違うので手当ては要らない**: 窓を出るのは古い名前で、そこへの rebase は onto が窓外 =
  HEAD の到達分が丸ごと範囲 = note が出る側へ倒れる。note を落とす側は HEAD が窓外の時
  だけで、その窓にはそもそもグラフが描かれていない

  直接読む修正で実害は根絶済み。tokio 更新時に再現ループ(単独 8 並走)で挙動を見る

### 次の 1 回で何が読めるか

天井で刈られた run の下に、**アプリが歩いた駅が並ぶ**(`the stations it reached:` —
`harness::deadline` が `stations.txt` へ駅ごとに追記し、`verify::wedge` が読む)。
その次の行 `it got as far as ...` は**最後に記録できた駅と、子の時計での到達時刻**を言う。
親の時計とは起点が違うため、親の経過時間との差をその段階の滞在時間としない。
記録が無い・空・読めない場合は到達状況不明。追記が失敗した先の進捗も断定しない。

- **駅は到達時に追記される**ので、正常に書けた分は終了時の一括報告を待たずに読める。
  `wedge.txt`(deadline スレッドが最後に 1 度だけ書く)との違いはここで、
  **`the app left no wedge.txt` だけでは、未到達と書込み失敗を区別できない**。
  外から止められた場合と、**`exiting` から先で止まった場合**(Windows の `ExitProcess` は
  detach ハンドラを回す前に他の全スレッドを終わらせるので、報告できるスレッドがもう無い)が
  同じ形になる。**「deadline スレッドに届いていない」とは読まないこと**
- **`exiting` は駅の 1 つ**(`std::process::exit` の直前)。`hub-down` で終わっている trail と
  `exiting` で終わっている trail は別の答えで、後者は**exit 呼出しの直前まで到達した記録**。
  その後にどこで止まったかは、この記録だけでは特定できない
- **`identity-tip` の口でも同じ行が出る**。watchdog が発火した後の後始末も
  記録するので、正常に終了すれば `exiting` まで並ぶ。発火した事実だけで途中の停止は除外できない
- 並走の状況は同じブロックの `lanes:` 行が数える。account が `out of time in` で始まる場合は、
  天井の後にも駅が進んでいて最後の駅が猶予 10 秒を立ち止まる前に時間切れ =
  詰まりか遅さかはそこからは決められない
- **`threads at the ceiling:` と `a dump of the app:`**(2026-09-13)— 刈る直前のスレッド一覧と、
  Windows の full dump(shot dir の `app.dmp`)。`exiting` で終わる trail に **alive 1 本**が
  並べば `ExitProcess` の中(他スレッドは終了済み = DLL detach の区間)で、dump の `~*k` が
  その 1 本の stack = 止まっている DLL と関数を名指す。**alive が複数**なら exit の手前で、
  名前(Linux)/ 名前と開始モジュール(Windows = `<id> <state> <wait> <名前>@<module> cpu=`。名前は
  `SetThreadDescription` の値で Rust / Qt / tokio のスレッドが持つ、モジュールは開始アドレスの持ち主で
  OS のスレッドを名指す)が誰を待っているかを言う。**`exiting` の平常の顔**(2026-09-13、単独の held run):
  `main@platitude-gg.exe` + `-@ntdll.dll` × 6(スレッドプールの待機、EventPairLow)+ `-@WINMM.dll` × 1
  (タイマー)。Qt / tokio / deadline のスレッドは無い = teardown の後に user-mode の lock を持って死ねる
  スレッドが残っていない。ここに `QSGRenderThread` / `tokio-rt-worker` / `QQmlThread` が並んだら teardown
  の生き残りで、それが次の読み所。**行に出るのは先頭 8 本で、一覧の全文は shot dir の `threads.txt`**(Windows の
  一覧プロセスが自分で書く。Linux は /proc 歩きなのでファイルは無い)。**その下の `the main thread stands in:` が
  main の stack**(2026-09-14 から、**Windows のみ**。一覧の PowerShell が dbghelp の `StackWalk64` で全スレッドを歩く =
  debugger 無しで撮れる。Linux の /proc 歩きは stack を持たず、この行も出ない — wedge-check がこの行を要求するのも
  Windows だけ。frame は `module!export+offset` で、**module は正確・関数名は最寄りの export なので近所の名前**、exe は PDB が
  無いので `+offset` 止まり。全スレッドの stack は `threads.txt` の `stack <tid> …` 行)。**exit の中で止まった run は
  この 1 行で読む** — 他スレッドは detach の前に終了済みなので、一覧の顔ぶれでは原因を切り分けられない。注文した停止(`--fault-hang`)
  では dump を撮らない(原因が判っている停止に数百 MB を払わない)。**どちらの診断にも天井がある**
  (`verify::look::bounded` — 一覧 / dump のプロセスは天井で終了させて待ってから次へ進む。stdout は pipe でなく
  ファイルなので、診断が残した孫が何を握っていても答えは exit の時点で戻る)ので、
  `could not be listed — the listing ran out of time after Ns and was ended` / `no dump: the dumper ran
  out of time` は「診断が止まった」の意味で、アプリの回収と報告はその後も進む。`could not be ended` と
  pid が付く行だけは診断プロセスが残っている可能性を言う。**dump は `MiniDumpWriteDump` を PowerShell の
  `Add-Type` から直接呼ぶ**(`verify::look::DUMP_SCRIPT`)。`rundll32 comsvcs.dll,MiniDump … full` は
  この Windows(11 / 26200、2026-09-13 実測)では**使えない**: header の flags は full memory を名乗るのに
  WS 80 MB のアプリで 0.1 MB(stack だけ)、しかも ACL が SYSTEM / Administrators だけで撮った本人が
  開けない(owner なので `icacls <file> /grant <自分>:F` で戻せはする)。直接呼ぶと同じアプリで 224.5 MB /
  1.1 秒、ACL は普通。単体テスト `a_dump_of_a_standing_process_is_written_and_readable` が ping の
  full dump を撮って「1 MB 超・owner が開ける」を毎回確かめる
- **`> qt-tearing-down ` の駅**(2026-09-13)— `hub-down` と `exiting` の間で `QApp` を落とす区間。ここで
  止まる trail は Qt の破棄(engine / application の destructor)の中で、`exiting` で止まる trail とは
  別の答え

**この経路が止まった run でも働くことは、故障注入で確認する**(`cargo xtask wedge-check`。
gate は `gate::plan::record_of_a_wedge` の 7 ファイルに触れた時に選ぶ。host のみ・4 本で 30 秒弱 + ビルド。
**deadline スレッド無しの 2 本は、trail に注文した駅が出た時点で親が刈る**(`verify::child::ordered_hold`。判定は
`HELD AT <駅>`、天井は駅に届かなかった run だけが払う backstop)ので動詞 1 本ぶんの数秒で終わり、スレッド有りの 1 本だけが
天井 + スレッド自身の 10 秒を払う。**時間を完了の証拠にしない**の型 — 以前は天井 + 親の猶予 20 秒を 2 本が払い、
代役の一覧の天井 15 秒がその上に乗っていた)。
4 つの形を実際に作って読み返す: **`exiting` で握ったまま deadline スレッド無し**
(= 終わらない run と同じ、`wedge.txt` の無い形。本物のスレッド一覧が答えたこと(` alive — `)まで要求する — 見出しだけを
要求すると、一覧が返らなくても緑になる)/ **`exiting` で握ってスレッド有り**
(2 つの記録が一致する。この 2 つは act 完了・撮影成功を要求し、watchdog abort は拒否する)/ **短い天井**(ループは回っていて完了述語に
届かない = `identity-tip` の口)/ **親の側の診断が止まる**(`--fault-stall-look` = 刈る直前のスレッド一覧を
取るプロセスを、答えない代役に差し替える。代役は永遠に答えないので天井の高さは検証の対象でなく、故障専用の短い天井
(`verify::look::STALLED_LOOK_CEILING`)で終了させて待ってから
`could not be listed — the listing ran out of time after Ns and was ended` と言い、その後もアプリの回収
`under the app:` と失敗報告まで進む。本物の一覧の天井は `LISTING_CEILING`、dump も同じ経路で天井付き(`DUMP_CEILING`。
途中で刈った `app.dmp` は消す)。**「動くはず」で済ませず、4 つとも親が実際に読めることを毎回確かめる**。
