## 残っている実装

**フル interactive rebase はプラン編集モードとして配線済み**(意匠の正本は
デザイン規約 §フル interactive rebase、実装対応は rules-refs/app-ui.md)。HEAD より古い
コミットの reword もこの画面が道になった。残る磨き(不具合ではない):

- **reword の鏡写しは保存時**(行の subject は `setMessage` で更新)— 打鍵ごとの live
  反映にするなら `MessageEditor` に text-changed の口を切る
- **squash / fixup の「親へ畳む」を言うのは動詞チップだけ**(字下げは撤去 = 3 列を揃える
  指示)。モックにあった接続線(下の行へ肘)は未描画 — 描くなら行を跨ぐので pane 側の
  オーバーレイ
- **プランの読みに行数の上限は無い**(ユーザー判断)— `--root` プランは全履歴を
  `PlanRow` に組む。JetBrains/kotlin で 138,915 行・`read_rows` の git 読みだけで 1.40s・
  stdout 25.8MB。**性能予算はベースライン**(素で表示した時)の話で、利用者が自分で開いた
  全履歴プランの増分は最適実装の分として許容する。規約 §フル interactive rebase の
  ローディング面がこの遅さの受け皿
- **プラン行に ref チップが出ない**(`--update-refs` で連れて動くブランチの可視化)。
  行 0 = 現在ブランチ分だけでも出す価値あり
- **実行後の選択は既定挙動**(旧選択が消えて default select)— 「読んでいた行の
  書き換わった先を追う」は未接続。単体 reword の `followRewrittenCommit` は在るが、
  armは `RepoPage.saveMessage` の 1 箇所だけで、プラン実行はそこを通らない
- **動詞チップに ▾ の描画が無い**(チップ押下と右クリックで開く)。NavIcon に chevron の
  項が無い件(下の §AppCombo)と同じ席
- **Esc でのプランの取り下げ未配線**(ヘッダの `Discard` ボタンのみ)
- **ヘッダ / onto 行のブランチ名は開いた時点の写し** — 端末で base ブランチだけを
  動かされると名前は古くなる(挙動は oid 釘付けで正しいまま。行末の sha が実体)。
  名前の生き直しは refs 更新との突き合わせが要る
- **行に掴み点(grip)の印が無い** — レビューで除去(トークンに点サイズが無く、直書きは
  規約違反)。行全体が掴み手で機能は成立。**印を戻すならトークン追加の人間承認とセット**
- **プラン行の選択は「模型の selected_row + ページの selectedOid」の二重持ち** —
  reorder の追従は模型側 remap で守られているが、所有を模型の oid 1 本に寄せる余地あり
  (レビュー所見・据え置き: 動く実害が無く、寄せると graph 選択との橋が別に要る)
- **プランの push 済み count は模型が持つ**(`RebasePlanModel.pushedCount` — 開く読みが
  数え、refs が動いたら range 名指しで数え直す。共有の publish 枠は無い)。数え直しの読みが
  失敗した時は開いた時の値のまま(異常系のみ・次の `refsMoved` で撃ち直す)
- **クリーン停止の WIP 行は語が場面に合っていない**(目視・`rebase-edit-stop` の絵)—
  `edit` 停止の着地はグラフ最上部の `Uncommitted changes` 行 + 右ペインの
  `UNCOMMITTED CHANGES (0)` + 空のファイル一覧で、**行は「無い物が在る」と名乗る**。
  席そのものは仕様どおり(規約 §進行中の操作から出る「着地は WIP 行」= 出口カードは
  この行の下に吊るので、行を消すとカードの席ごと消える)。**据え置き** — 停止の説明は
  同じペインの底の出口カード(`REBASING — 1 of 2` / `edit Stopped on purpose at <sha8>`)が
  持っており、読み手が次に何をするかは迷わない。直すなら行の語の側(席は動かさない)。
  **未実測**: 同じ絵でコミット枠も立ち `commit to HEAD` を出しているが、staged ゼロで
  押した時に何が起きるかは撮っていない

## ウィンドウ chrome — 形は決まり、残りは中身

形の正本は [デザイン規約.md](デザイン規約.md) §ウィンドウの縁。Windows の縁に残る 2 つ
(窓メニューの移動・サイズ変更 / Snap Layouts)は [P5-確認事項.md](P5-確認事項.md) §10。
ここに残るのは中身の方:

- **アドバンス検索**(Ctrl+F の基本検索は配線済み — 正本は規約 §コミットを探す):
  - **項目を名指しして探す形**(`author:` / `path:` / `date:`)。素の語を全軸のまま git へ
    降ろすと `--grep` と `--author` は AND なので和集合に 3〜4 スポーン要るが、接頭辞つきなら
    1 クエリ 1 スポーンで各接頭辞が git のフラグ 1 つに対応する
    (`git log --grep=… --author=… -G… -- <path> --format=%H` が SHA を返すので、アプリ側は
    「その SHA が来たら光らせる」= 印の仕掛けは基本検索のものを使い回せる)
  - **最初に出せるのは `description:`** — 外した 4 つのうち Description だけは行が既に
    持っているので、git を 1 プロセスも撃たずに出せる(パス / diff / 日時 / committer は
    git が要る)。**塞ぐ穴は実在する** — 機能名でしか呼ばれない語は今まったく引けない
    (0 件の語の実測は規約 §何に当たるか)。判断は「据え置き、実使用をもう少し重ねてから」
  - **同時に決まるもの 3 つ**:
    1. **日付で探す**。行は epoch 秒しか持たず、画面の `yyyy-MM-dd HH:mm` は表示側が作る。
       Rust 側にタイムゾーン依存を 1 つ足すか、`LOG_FORMAT_ARG` に
       `%ad --date=format-local:%Y-%m-%d %H:%M` を 1 フィールド足す(`LOG_FIELDS` 8→9・
       parser の field 分岐・`CommitMeta` / `LogRow` / fixture)かの二択。**後者が本命** —
       git が DST 込みで正しく組み、行が画面と同じ文字列を持つ。範囲(`date:2026-08` /
       `--since` / `--until`)もそこで一緒に決まる
    2. **窓の外を探すか**。基本検索は読み込み済みの行しか見ない。git へ降ろす検索は窓の外も
       返せるので、返った SHA がグラフに無い時に何をするか(件数だけ言う / 窓を伸ばす /
       その行まで読み込む)が要る
    3. **パスで探す**(実装計画.md §14 のフィルタ 4 軸の最後)。`-- <path>` は git 側でしか
       解けない
  - **絞り込み(行の間引き)は引き続き別物** — レーンとエッジを「隠れたコミットを跨ぐ」形で
    引き直すことになり、core に 2 つ目の walk モードが要る
- **Ctrl+F が開かないことがある(報告・未再現)**。押しても検索バーが降りず、
  一度開いた後はその実行の間ずっと開けた。
  - 潰した容疑者: `Main.qml` の `curPage`(`pageRepeater.itemAt()` が null のまま再評価
    されない形)— タブ復元の経路で実測したが再現せず。F5 も同じ `enabled:` なので、
    **次に起きたら F5 も効かないかを見る**(両方死んでいれば `curPage`、Ctrl+F だけなら下の 2 つ)
  - 残っている容疑者: (1) **窓がアクティブでない** — `Shortcut` の既定は `Qt.WindowShortcut`
    で、`Start-Process` 起動は Windows のフォアグラウンド・ロックで前面にならないことがある
    (「窓の中を 1 回クリックしたら以後ずっと効く」と一致)。(2) **merged chrome の 1 回目の
    クリックが死ぬ既知の形**(rules-refs/app-ui.md §`WM_NCHITTEST` — 幽霊 press が最初の
    1 手を吸う)
  - 次に見るもの: F5 が効くか / タイトル帯以外を 1 回クリックしてから Ctrl+F / `PG_LOG` で
    `startFind` が呼ばれているか(**`startFind()` は質問バーが立っている間は黙って断る**ので
    バーの有無も見る)
  - 入口をキーだけにしない案(未着手): アプリメニューに `Find commits…` の行を足す
    (規約 §メニュー に沿い、キーが届かない場面の逃げ道にもなる)
- **125% / 150% の目視が未実施**。右端の間合いは実測値で組んであるので、拡大率を変えた
  画面で 1 度見ておく
- **macOS の形は決定済み・実装は実機ゲート**(Phase 5)。☰ は持たない — 画面上端の

## 要判断(小さいもの)

§A(interactive rebase の画面)は決着 — 決定はデザイン規約 §フル interactive rebase が
正本(プラン編集モード / 押した行 = 含まれる最古 + onto 行 / 右ペイン連携 / 凍結 /
実行ボタン 3 状態 / edit 停止の答え)。残る判断だけをここに:

- **`--update-refs` は駆動 rebase では不発**: プラン実行は `update_refs: true` で撃つが
  (`rebase_plan/qobject.rs`)、git が `update-ref` 行を書くのは**自分で生成した todo の中**で、
  helper がその todo を丸ごと差し替えるので行ごと消える。**実測**: 範囲の中に居るブランチは
  範囲が書き換わっても古い commit に残る(2.55。範囲内の commit を reword して id を必ず
  変えた上で確認)。直すなら `render_todo` が範囲内の ref を自分で `update-ref` 行として
  書く形になる — **UI がこの旗で何を約束しているか**(規約 §履歴を合流させるは rebase 側が
  足すのは `--update-refs` だけと決めている)から決める
- **`GitError::Rejected` を `Withheld` へ寄せるか**: **git を撃つ前に断ったものは
  `GitError::Withheld` + `WriteReport` で報せバーへ出す**という形は main に在り、5 つが
  使っている。`Rejected` のまま残っているのは 10 箇所以上で、**大半は UI が先に止めるので
  報せの出しようが無い**(空本文の reword・mergetool 未設定・空の identity・stash rename の
  読み取り失敗 — Save や行が出ないので人はここへ来られない)= ログに残すのが正しく、
  **core は app のゲートを契約にできない**ので消さない。**判断が要るのは画面から届く方**
  —— `RepoSession::rebase_interactive` の `expect_head` ずれ / 立っている操作の上への
  rewrite(`build::carry_across_rewrite`)/ 操作が立っている最中の `rebase`
  (`ops_integrate`)は、いずれもプランを組んだ後に外が動いた時なので人が踏める。
  寄せるなら kind を 1 つ足して 1 コミット。**個別の箇所を数え上げてここに書かない** —
  一覧はすぐ腐る(前版の 5 件の列挙は倍に増えていた)ので `GitError::Rejected` の Grep が正
- **同じリポジトリのサブフォルダを指した時**: 既に開いているタブへ移る判定は
  `repo::open_key` = `canonicalize` のフォルダ一致なので、`repo` と `repo/src` は別と答えて
  2 枚開く。同じと答えるには `rev-parse --show-toplevel` の答えを待つ必要があり、判定が
  居るのは同期スロット(`TabsModel::open_repository_path`)の中。**開いてから畳む**
  (解決できた時点で既存タブへ吸収)か**そのままにする**かを決める。**別 worktree は
  別タブのままが正**(作業ツリーが違う = 見るものが違う)
- **cherry-pick / revert の複数選択**: core は複数リビジョンを受ける(`cherry_pick(revs)` /
  `revert(revs)`)が、ブリッジは 1 本だけ受け取って `vec![…]` に包む。グラフでの複数行選択が
  できた時点で、ブリッジも複数対応に広げる
- **`rebase --onto` の branch 指定**: ブリッジは `rebase(upstream, onto, update_refs)` で
  受け取れる。**空でない `onto` を渡す導線が 1 つも無い**(メニューも自動化も `""`)ので、
  出すなら意匠から
- **`merge` のオプション**: ブリッジが受けるのは `--no-ff` / `--ff-only` の 2 つで、
  呼ぶ側は全員 false。`--squash` はブリッジに口が無い(`squash: false` 直書き)。
  rebase 側が足すのは `--update-refs` だけに決めた(規約 §履歴を合流させる)。
  merge のこの 3 つをどう出すかは実使用感で決める
- **質問を立てる残り 2 経路**: グラフ行の右クリックと左メニューから `startPublishAsk()` を
  呼ぶ配線。質問側は 1 つに集約済みなので入口を足すだけ(グラフ行から立てる場合、対象が
  「現在のブランチ」でよいかは要判断)
- **リポジトリを開く `rev-parse` をコマンドログに出すか**(保留): 今は背景読みなので、開けな
  かった画面から `>_` を押してもパネルは空で立つ。出すには利用者用ハンドル(`exec_user`)で
  撃つ 1 行で足りるが、core.md「書き込みキューだけが利用者用を使う」の書き換えを伴う
- **author 側のタイムゾーン**: `AuthorCard` は 2 つの時刻をローカル時刻で出す
  (規約 §author の hover)。書いた人の現地時刻で読ませるなら core が epoch ではなく
  offset 付き(`%aI` 等)を運ぶ必要がある。要否は実使用感で決める
- **コマンドログに保存が無い**: 1 タブ 500 件・超えたら古いものから捨てる(1 件あたりの
  上限は無い — 実質の天井は `process::STDERR_CAP` = 256KB)。ファイルへの保存・
  「全部まとめてコピー」は将来分(コピーはドラッグ + Ctrl+C の 1 本に決めた =
  規約 §git が言ったことを読む場所)。**ファイルへ出す時は `https://user:token@host`
  の userinfo を落とすこと** — 選択のコピーは**画面に出ている綴りをそのまま渡す**方で
  揃えてあり、落とすなら両方揃えて落とす
- **エラー表示が仮置き**: 失敗するとコマンドログのパネルが自ら開き、閉じるまで開いたまま
  になる(**素通しするのは 3 つ** — 質問に化けた拒否 = `RepoPage.expectedRefusals`、
  書き込みの最中に落ちたコマンド = `repoTab.writeRunning`、**報せバーが受けるもの** =
  `GitError::Reported` / `Withheld` が運ぶ報せ(向こうの拒否・こちらが古い push・
  コミットの拒否・こちらが先に断ったもの。規約 §答えの要らない報せ))。ヘッダの 1 行
  (`repoTab.lastError`)は行に出ない失敗のための場所だが、書き込みの失敗では行と二重になる。
  本来のエラー表示を作る時に整理する
- **Answered な失敗コードの行表示**: exit code が答えのコマンド(`merge-base --is-ancestor`)の
  exit 1 行は ok 扱いで右列が空になる。code をそのまま出す表示を検討
- **`TimedOut` / `Spawn` / `GitNotFound` でログを開くのは正しい**(実測)。**行は在って、
  その行だけが何が起きたかを言う**: 時間切れは `git branch -m -- main renamed` の右に
  `timed out 7 ms`(赤)、spawn の失敗は `did not run` + OS の文(`source.to_string()` が
  `CommandFinished.message` に載る。`hub::sink`)。**止められたのがどのコマンドかは
  他のどこにも出ない**ので、ここを閉じると手掛かりが消える

## 探索で見つかった残件

修正より記録が適切と判断したもの(修正済み分はコミット履歴参照)。

### core

- **合成 write のキャンセル窓**: `carry_across` で stash 後・switch 前にセッションが閉じると、stash に入ったまま通知が出ない(stash list には残る = 復元可能)。クローズ経路の best-effort 通知を検討
- **1 コミット編集(squash / reword / drop)の todo は tip に pin されていない**: `session::build::run_plan` は `Replay` へ空の `expect_head` を渡す。`sequencer::plan_edit` が読んだ oid 列は固定で、carry(refuse → stash → 再 spawn)の間に外から commit が載ると todo から漏れて黙って落ちる — 画面で組むプランと同じ窓で、そちらは `Replay::tip_still_stands` が塞いだ。塞ぐには `rev-parse HEAD` が 1 本増え、**それが最もよく押される 3 操作の応答経路に乗る**(応答は既に予算超過)ので、pin する値を `EditPlan` に持たせるかどうかは実測の上で判断する
- **同一リポジトリ複数タブのキュー**: 書き込みキューはセッション(タブ)単位で、同一リポジトリの worktree を 2 タブ開くと `stash@{0}` 前提の合成(`carry_across` / stash rename の selector シフト)が相互レースする
- **open 完了前の write**: セッション open 前に届いた書き込みは `run_write` が debug ログ 1 行で捨てる(`WriteStarted` / `WriteFinished` が出ないので画面には何も起きない)。今は書き込みの入口がタブの open 後にしか無いので実害は出ていない

### app

- **ページに入り切らないチップの一覧は、チップの席を明け渡す**(規約 §グラフ行のダブルクリック
  「1 行目はチップの席にそのまま座る」の外れる場面):縦の clamp
  (`RowHoverHost.openRefList` の `Math.min(席, host.height - cardHeight)`)は前からあるが、
  **カードがページで頭打ちになったので、深い行ではこれが常態**になった —— `--preset stack` の
  行 3(42 ref)は `cardHeight` がページ丸ごとなので `y = 0` に落ち、**手を止めたチップの位置には
  別の名前が来る**。取り得る形は 2 つで、**今のまま**(席を捨てて上から見せる)か、
  **席を保ったままページの底まで伸ばす**(スクロールは同じだが、下の方の行のチップでは
  数行ぶんの高さしか出ない)。どちらが読み手にましかは絵を並べて人が決める話で、
  **`ref-list <行> --preset stack` を行の深さを変えて撮れば両方比べられる**
- **文法経路の巨大ファイルに独自の上限が無い**: 天井は `SOURCE_BYTE_CAP`(4MB)だけで、
  4MB 級の minified / 生成ファイルは全体パース + 全行 span 化(一時数十 MB・~0.5s)を
  払う。実害が出たら行数か byte の第 2 予算を検討
- **conflict した文法言語のファイルは色が出ない**: combined diff は syntect の経路に
  留まる(フェンスを構造として読む機構が `Walk` にある)ので、tree-sitter だけが知る
  言語(.qml / .kt / .zig 等)は conflict の間だけ無色になり、解消すると全行色に戻る
  落差が出る。直すなら文法の行色に `Walk` のフェンス検出を重ねる形
- **メニューの幅が実際に描く幅より狭く出る(Linux 側だけ)**: `AppMenu.implicitWidth` は
  `widestRow + padding` で、`widestRow` は各行の `implicitWidth` の最大。**その幅に合わせた
  はずの一番広い行が、その中で省略される**。**実測**: `linux verify-ui commit-menu
  --preset basic` の `rebase` 行が `main ont…`(Windows の同じ動詞は `main onto it` を
  完全に描く)。`RemoteRowMenu` の `Mark as default remote (origin)` も同じ形で
  `(orig…` になる —— **チップも note も持たない行なので、原因は `codeColW`(`onAboutToShow`

### 見た目の宿題(不具合ではなく、やりたいこと)

- **選択のある hunk で `Discard 3 lines` を出すか**: 行を選べるようになって「素の `×` には
  失うものを書く場所が無い」という理由が消えた。今は `Discard hunk` のまま(規約 §その他の操作)
- **アバターのバッジのツールチップが、アドレスを言わない run がある**(実測・
  **再現待ち**。詳細は rules-refs/app-ui.md の同項): Windows で 2 回、`Choose avatar for `
  のままアドレスが空で止まった。読みは「出ている `ToolTip` の文言は差し替わらないので、
  遅れて届く値を `%1` に入れた文は開いた瞬間に空だとそのまま」だが、**バッジ自体はアドレスが
  空だと出ない**(`avatarBox.editable`)ので辻褄が合っていない — そこを詰めるのが最初の一歩。
  直すなら「開いている間に文が変わったら出し直す」形を共有インスタンス側
  (`SharedToolTip.dressToolTip` の隣)に置く(`%1` を持つツールチップは `signature-tip` の
  `Signed by %1` 等、他にもある)
- **運んでいるタブの脇にツールチップが残りうる**(**実操作待ち**): 出す条件は
  `pointed && !held` なので掴んだ後に新しくは出ないが、**掴む前から立っていた 1 枚**は共有
  インスタンスの keeper が保つ(`SharedToolTip.wanted` = ポインタが的の上に居れば保つ ——
  運ばれているタブはその的のまま)。座席は `freeze()` で固定なので、タブが帯を横切る間その箱は
  置いていかれる。hover は注入できないので**実操作でしか見えない**。直すなら「的が『もう要らない』と
  言える口」を keeper 側に足す形で、タブ側の細工にはしない
- **`AppCombo` の山の側だけが、字より広い所に立っている**: 枠と文字の間はアプリ全体で
  `spaceXs` に揃ったが(規約 §余白 の入力欄の項)、山の席は `spaceSm` のままで、印が箱の中に
  持つ余白と合わせて枠から 13px 空く(実測: 山のインクの右端 x422 / 枠 x435)。
  詰めるには §余白 の引き算に要る実余白が要るが、**`NavIcon` は `chevron` について答えられない**
  (`inkGrid` / `inkTallGrid` に項が無く、既定の 16 = 箱いっぱいと答える。実際に描いているのは
  升目の 4..12 で、しかも欄は 90° 回して使う)。**まず `NavIcon` に `chevron` の項を足して
  実測で裏を取る**のが最初の一歩で、引き算が負になるなら席を `iconSm` へ落とす側
  (§余白「引き算が負になったら詰めすぎではなく席が広すぎる」= タブの `✕` の前例)
- **打つ欄の右で字を止めているのは枠ではなく山**: `AppCombo` の `rightPadding` は他の欄と同じ
  `spaceXs` なので、**長い名前は山の下をくぐる**(欄の中の `TextInput` は省略せず送るだけ)。
  正しい値は「`spaceXs` + 山の席 + 印の実余白」= トークン 1 つでは書けないので、上の項で実余白が
  出てから決める。今のところ実害は「入りきらない行き先の末尾が山に重なる」だけで、
  `pickOnly` の側は一覧から選んだ名前しか入らない

## 触らないと決めたもの(再検討しない)

- **警告から改行コードを直す導線は作らない**: 警告のバーにもカードにも、書く操作へ
  繋がる扉を置かない。ファイル内容の変換も、「`.gitattributes` が無い」という指摘も
  持たない。他 GUI の事故はここに集中している(IntelliJ の `Fix and Commit` が global を
  書き、Sourcetree が勝手に false にする)。**警告は言うだけ**(デザイン規約
  §改行コードの警告)。**`core.autocrlf` を設定画面から書けるのは別件**(デザイン規約
  §設定の画面)—— 読者が変えに行った時にだけ書く。ただし**書けるのはリポジトリ単位
  だけで、`--global` は書かない**(ユーザー判断) —— 利用者の機械そのものを書き換える操作はアプリが
  持たない(上に挙げた他 GUI の事故がまさにそれ)。`core.eol` と `.gitattributes` は
  今も持たない
- **`diff --ignore-cr-at-eol` の表示トグルは作らない**: その patch は `apply` できず、
  EOL のみの差だと diff が空になる(status は modified のまま)。表示用と staging 用で
  diff の bytes を分けない不変条件を壊す
- **成功した git の stderr をコマンドログへ出すことを、EOL を理由には決めない** —
  `autocrlf=true` では読み取りコマンドでも警告が鳴り続けてノイズになる。
  push の `remote:` 行など他の用途で欲しくなった時に別途判断する
- **`Stage file` と `Stage hunk` の右端は揃えない**: ヘッダの語は `✕` の分だけ内側にいて
  hunk の語より 25px 左で終わるが、ヘッダ帯に区切り線が入って「別の箱の中の右端」として
  読める
- **選択のある hunk でも `Discard hunk` は hunk のまま**: 捨てるのは**見た目上の hunk** =
  今その diff に出ているもの。`--cached` を付けないので index は動かず、部分ステージ済みの
  分は残る(`stage_integration::discard_a_single_hunk` が「the index is untouched」で
  固定している)。行単位の discard は作らない
- **末尾改行が無いファイルへの行追加は部分ステージできない**: 追加行だけを選んだ patch は
  unified diff として表現できない。前提となる行を自動で選択に足す回避策は入れない —
  選んでいない行を黙って index に入れる方が害が大きい
- **untracked ディレクトリの空殻が残る**: 中の 1 ファイルだけを部分ステージできる代わりに、
  全ファイルを discard すると空のディレクトリがディスクに残る(git は空ディレクトリを
  追跡しないので status は clean のまま)
- **`--allow-empty` / `hunk_count` はブリッジへ出さない**: 空コミットを発行する導線を
  持たない(Commit は staged が 1 件以上ある時だけ通る。amend を除く)。hunk 数は diff 行
  モデルから UI 側で数えられる
- **octopus merge(3 親以上)は作れない**: `merge` は 1 リビジョンのみ受ける。要望に無い
- **push 済みの note が窓の外まで答えることは求めない**(コミット行・ref 行の両メニュー。
  実装対応は rules-refs/app-ui.md)。note が読むのは描かれた行なので、窓
  (`--max-count`、既定 2,000 行)の外は答えが実際と違いうる。**倒れる方向が範囲の両端で
  違うので手当ては要らない**: 窓を出るのは古い名前で、そこへの rebase は onto が窓外 =
  HEAD の到達分が丸ごと範囲 = note が出る側へ倒れる。note を落とす側は HEAD が窓外の時
  だけで、その窓にはそもそもグラフが描かれていない
