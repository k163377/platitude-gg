## 残っている実装

**フル interactive rebase はプラン編集モードとして配線済み**(意匠の正本は
デザイン規約 §フル interactive rebase、実装対応は rules-refs/app-ui.md)。HEAD より古い
コミットの reword もこの画面が道になった。残る磨き:

- **reword の鏡写しは保存時**(行の subject は `setMessage` で更新)— 打鍵ごとの live
  反映にするなら `MessageEditor` に text-changed の口を切る
- **squash / fixup の「親へ畳む」を言うのは動詞チップだけ**(字下げは撤去 = 3 列を揃える
  指示)。モックにあった接続線(下の行へ肘)は未描画 — 描くなら行を跨ぐので pane 側の
  オーバーレイ
- **プランの読みに行数の上限は無い**(ユーザー判断)— `--root` プランは全履歴を
  `PlanRow` に組む。JetBrains/kotlin で 138,915 行・`read_rows` の git 読みだけで 1.40s・
  stdout 25.8MB。**性能予算はベースライン**(素で表示した時)の話で、利用者が自分で開いた
  全履歴プランの増分は最適実装の分として許容する。規約 §フル interactive rebase の
  ローディング面がこの遅さの受け皿
- **プラン行に ref チップが出ない**(`--update-refs` で連れて動くブランチの可視化)。
  行 0 = 現在ブランチ分だけでも出す価値あり
- **実行後の選択は既定挙動**(旧選択が消えて default select)— 「読んでいた行の
  書き換わった先を追う」は未接続。単体 reword の `followRewrittenCommit` は在るが、
  armは `RepoPage.saveMessage` の 1 箇所だけで、プラン実行はそこを通らない
- **動詞チップに ▾ の描画が無い**(チップ押下と右クリックで開く)。NavIcon に chevron の
  項が無い件(下の §AppCombo)と同じ席
- **捨てる物が在るプランの Esc は無言**(規約 §hover のツールチップ —— その側の `Discard`
  は長押しなので、1 度下りただけの鍵では撃てない)。**残る判断は手応えを足すか** ——
  設定画面が持っている形(1 回目は失う物へ送って `✕` を armed にし、2 回目で
  閉じる = `SettingsDialog.escapeOut`)をプランへ移すなら、`Discard` を armed に見せる姿の
  決定が要る
- **ヘッダ / onto 行のブランチ名は開いた時点の写し** — 端末で base ブランチだけを
  動かされると名前は古くなる(挙動は oid 釘付けで正しいまま。行末の sha が実体)。
  名前の生き直しは refs 更新との突き合わせが要る
- **行に掴み点(grip)の印が無い** — レビューで除去(トークンに点サイズが無く、直書きは
  規約違反)。行全体が掴み手で機能は成立。**印を戻すならトークン追加の人間承認とセット**
- **プラン行の選択は「模型の selected_row + ページの selectedOid」の二重持ち** —
  reorder の追従は模型側 remap で守られているが、所有を模型の oid 1 本に寄せる余地あり
  (レビュー所見・据え置き: 動く実害が無く、寄せると graph 選択との橋が別に要る)
- **プランの push 済み count は模型が持つ**(`RebasePlanModel.pushedCount` — 開く読みが
  数え、refs が動いたら range 名指しで数え直す。共有の publish 枠は無い)。数え直しの読みが
  失敗した時は開いた時の値のまま(異常系のみ・次の `refsMoved` で撃ち直す)
- **クリーン停止の WIP 行は語が場面に合っていない**(目視・`rebase-edit-stop` の絵)—
  `edit` 停止の着地はグラフ最上部の `Uncommitted changes` 行 + 右ペインの
  `UNCOMMITTED CHANGES (0)` + 空のファイル一覧で、**行は「無い物が在る」と名乗る**。
  席そのものは仕様どおり(規約 §進行中の操作から出る「着地は WIP 行」= 出口カードは
  この行の下に吊るので、行を消すとカードの席ごと消える)。**据え置き** — 停止の説明は
  同じペインの底の出口カード(`REBASING — 1 of 2` / `edit Stopped on purpose at <sha8>`)が
  持っており、読み手が次に何をするかは迷わない。直すなら行の語の側(席はそのまま)。
  同じ絵のコミット枠(`commit to HEAD`)は**押せない** — staged ゼロ・amend でなし・
  立っている本文も無い停止では `WipCommitBlock` の可否が降り、断りは
  `Stage something to commit`

### 参照していた行が消えた時の着地 — 残っているのはコミット行の側

**コミット行の着地は席(行番号)**(`RepoPage.followVanishedCommit`)—— 消えた行の席に今立って
いるコミットへ乗り、そこが未コミット行か空なら HEAD のコミットへ。**借りのある着地が先** ——
止まった操作が未コミット行を借りている間(`pendingWipSelect`)は追従しない。追従が先に着地すると
その借りが `activateRow` で取り消され、止まった操作の出口カードに着かない。

**first parent で線を追う案は差し戻し済み**(2026-09-22 ユーザー判断)—— 選択時に first parent と
1 つ下の行を控えて「同じ親を持つ席のコミット → その親 → 自分の木の未コミット行 → HEAD」と
降りる形にしたが、**同じ親から分岐した 3 本目の兄弟が席に来ると跨ぐ**うえ、線が丸ごと消えた時も
自分の木へ落ちる = **要求(閲覧していた線に留まる)とは別物**だった。親と 1 つ下の行を控える
だけでは足りないことの実例は `basic` の `feature/remote-only`(先端の親に乗っている)。

**未コミット行はブランチでなく作業コピーで扱う**(2026-09-21 ユーザー判断)—— detached のまま
進めているコピーが在るため、鍵は**コピーのパス 1 本**(main の作業コピーも listing の 1 エントリ
として同じ引き方)。行はコピーを名乗り(`RepoPage.carriedPath`)、着地先はそのパスで引く
(`NavSectionModel.headOfCopy` = worktree 一覧の `Role::Full` → `Role::OidHex`。detached でも
`head_hex` は在り、空になるのは bare だけ)。**読んでいた別コピーの行が消えたら、そのコピーが
今立っているコミットの行へ着地する**(そのコピーが commit した / 片付けた時)—— 一覧が 1 tick
遅れていれば 1 つ前の HEAD に着くが、同じ線なので次の pass もそこに留まる。コピーが listing
から消えた時(remove / prune / bare)だけ、名乗る物が無いので既定の着地へ落ちる。

**残っている要求(2026-09-21 ユーザー)**: **コミット行を読んでいた時も、閲覧していた線に
合わせて遷移する**。今の着地は席と HEAD しか見ないので、**別ブランチのコミットを読んでいた
時は跨ぐ**。**コミットからブランチを毎回求めるのは到達可能性の walk**(性能予算「操作応答は
コミット数から独立」)なので採れない —— 安い案は **「そこへ連れて行った ref を控える」**
(左メニュー・チップ・タブからの着地でその ref を控え、チップの無い行のクリックは直前の控えを
引き継ぐ)。**着地はコピーへ翻訳して読む** —— その ref を持つコピーが在ればその未コミット行、
無ければそのコピーの HEAD、どのコピーも持っていなければ ref の tip。**定義はユーザー判断待ち**。

**着地が 2 つ armed になる形は非決定**: `drop-commit-go` は、書き込みの答えが arm する 2 つ
(止まった = 未コミット行 / 先端が動いた = コミット)のどちらが先に着くかで絵が変わる。
**素の連続 6 run は同じ絵**だが、8 並列の gate の中では別の絵が撮れて census が動く
(`followVanishedCommit` は撃たれていないことを probe で確認済み = 追従の側の話ではない)。

**diff のファイル一覧も同じ平仄に合わせる** —— 一覧の移り先(規約 §diff のファイル一覧)は、
上が決まってから横展開する。

### 別 worktree の未コミット行 — 残っているのは読みの代金だけ

**決定も実装も済んでいる。** 意匠の正本は [デザイン規約.md](デザイン規約.md)
§別の作業コピーを読む と §未コミット行が名乗るもの、実装対応は
rules-refs/app-ui.md(右のペイン 3 面・全ゼロ id・
WORKTREES 行・`LabelKind::Worktree` のチップ)。ここに残るのは読みの代金と、
まだ建てていない物への手すりだけ:

- **開幕の巡回(`refresh_quick` → `refresh_carried`)はグラフの初回描画と同じ機械を
  取り合う** —— 8 コピーの corpus で起動→グラフが 1.10–1.12s(巡回なし)→ 1.74–2.05s
  ([git-slots-windows-x64.md](../ci/baseline/git-slots-windows-x64.md) §枠の床 /
  §巡回と重なった時)。枠は足りていて(interactive は待たない)、食われるのは CPU
  (1 本の status が 11 コア幅)。直すなら開幕の 1 周を `LogFinished` の後へ遅らせる
  (focus の巡回はそのまま)。**予算 3s の内側なので今は据え置き**
- **要判断: ペインが立っているコピーの二重読み**(実測済み = tick ごとに `status` 1 本ぶん。
  数字と条件は同記録 §ペインが立っているコピーの二重読み)。**一覧は pass の答えと同じ
  コマンドの同じ出力**なので相乗りさせられるが、**選んだ瞬間の 1 本だけは別**
  (次の tick を待たせられない)。直すなら `RepoPage.pollCarried` の側 —— 選択時は今のまま
  読み、tick では pass の答えから配る
- **同時に撃つ `status` 4 本と 30 秒の tick は決め打ちのまま** —— 上限そのものはどの数でも
  要る(executor に上限が無いので、20 worktree なら 20 プロセスが同時に立つ)が、
  **この 2 つの数字は次の本計測で取り直して決め直す**(宿題は
  [perf 記録](../ci/baseline/perf-windows-x64.md) §未取得 の「同時に走る `status` の
  本数と実時間」。1 本 0.48s までは測れている)
- **worktree 特化の右クリックメニューを足す時の手すり**(今は無い —— WORKTREES の行も
  この行もメニューを持たない):
  - **チップが立つのは 1 箇所だけ**(ブランチを持たない作業コピーが立っているコミットの行。
    2026-09-19 にこの WIP 行のチップは廃した = 名乗るのは行の文
    `Uncommitted changes — <木の印><名前>`)。**足すなら入口も 1 つ** —— 2 つ書けば必ず食い違う
  - **ただし入口は WORKTREES セクションの行**(と、既にチップを
    持っているコミット行)だけ。`worktree remove` / `prune` は破壊的で、**この行が
    持っている扉は「その作業コピーを開く」1 つだけ**という形を崩す
  - **足すには `encode::ref_kind_word` が `worktree` に語を返すようにする必要がある** —— 今は
    `head`(HEAD の印)と同じく `""` = 「名指すものが無い」と答えており、それが「チップは名前で
    あって扉ではない」を機械で保証している。**この 1 行を変えるとチップが扉になる**ので、
    変える時は上の 2 つを同時に決める

## ウィンドウ chrome — 形は決まり、残りは中身

形の正本は [デザイン規約.md](デザイン規約.md) §ウィンドウの縁。Windows の縁に残る 2 つ
(窓メニューの移動・サイズ変更 / Snap Layouts)は [P5-確認事項.md](P5-確認事項.md) §10。
ここに残るのは中身の方:

- **アドバンス検索**(Ctrl+F の基本検索は配線済み — 正本は規約 §コミットを探す):
  - **項目を名指しして探す形**(`author:` / `path:` / `date:`)。素の語を全軸のまま git へ
    降ろすと `--grep` と `--author` は AND なので和集合に 3〜4 スポーン要るが、接頭辞つきなら
    1 クエリ 1 スポーンで各接頭辞が git のフラグ 1 つに対応する
    (`git log --grep=… --author=… -G… -- <path> --format=%H` が SHA を返すので、アプリ側は
    「その SHA が来たら光らせる」= 印の仕掛けは基本検索のものを使い回せる)
  - **最初に出せるのは `description:`** — 外した 4 つのうち Description だけは行が既に
    持っているので、git を 1 プロセスも撃たずに出せる(パス / diff / 日時 / committer は
    git が要る)。**塞ぐ穴は実在する** — 機能名でしか呼ばれない語は今まったく引けない
    (0 件の語の実測は規約 §何に当たるか)。判断は「据え置き、実使用をもう少し重ねてから」
  - **同時に決まるもの 3 つ**:
    1. **日付で探す**。行は epoch 秒しか持たず、画面の `yyyy-MM-dd HH:mm` は表示側が作る。
       Rust 側にタイムゾーン依存を 1 つ足すか、`LOG_FORMAT_ARG` に
       `%ad --date=format-local:%Y-%m-%d %H:%M` を 1 フィールド足す(`LOG_FIELDS` 8→9・
       parser の field 分岐・`CommitMeta` / `LogRow` / fixture)かの二択。**後者で決まり** —
       git が DST 込みで正しく組み、行が画面と同じ文字列を持つ。**`format-local` が読み手の
       時計に焼き付くのは織り込み済み** —— 時刻は常に読み手のゾーンで出すと決めてある
       (規約 §author の hover)。範囲(`date:2026-08` / `--since` / `--until`)もそこで一緒に決まる
    2. **窓の外を探すか**。基本検索は読み込み済みの行しか見ない。git へ降ろす検索は窓の外も
       返せるので、返った SHA がグラフに無い時に何をするか(件数だけ言う / 窓を伸ばす /
       その行まで読み込む)が要る
    3. **パスで探す**(実装計画.md §14 のフィルタ 4 軸の最後)。`-- <path>` は git 側でしか
       解けない
  - **絞り込み(行の間引き)は引き続き別物** — レーンとエッジを「隠れたコミットを跨ぐ」形で
    引き直すことになり、core に 2 つ目の walk モードが要る
- **検索の入口をメニューにも置く案(未着手)**: アプリメニューに `Find commits…` の行を足す
  (規約 §メニュー に沿い、キーが届かない場面の逃げ道にもなる)。`Shortcut` の既定は
  `Qt.WindowShortcut` なので、**窓がまだアクティブでない間はキーが届かない**
  (Windows のフォアグラウンド・ロックで前面にならずに起動した窓 = 「中を 1 回
  クリックしたら以後ずっと効く」の形)
- **macOS の形は決定済み・実装は実機ゲート**(Phase 5)。入口は画面上端の
  メニューバー — 常に届く場所に既に在る。`QtQuick.Controls` の `MenuBar` は Qt 6.8 以降
  macOS で既定ネイティブ。**作るのは macOS だけ**(`Loader` で分ける — 他 OS では
  非ネイティブの QML メニューバーが窓の中に 2 段目として出る)。ネイティブ MenuBar は
  delegate を使わない = `AppMenu` の意匠は効かないので、**行の定義を 1 か所に置き見せ方
  だけ OS で分ける**。traffic light が帯の中心から約 6px 上は許容(直すには AppKit が要る)。
  `About` / `Settings…` / `Exit` がアプリメニューへ自動で寄るかは実機で確認

## 要判断(小さいもの)

- **消えた作業コピーの WORKTREES 行を押すと、同じリポジトリに 2 枚目のタブが建つ**(2026-09-22
  に気付いた既存の穴。規約 §タブの所作「同じリポジトリのタブは 1 枚」から外れている側)。
  行が名指すフォルダが無い(`prunable` = `git worktree prune` が落とす行)と `repo::place` が
  断るので、`TabsModel::land` の `Refused` 枝が**そのパスを自分のリポジトリとして** `open_new`
  する(`landing_for` は「git が答えた」時にしか通らない)。結果、**今開いているリポジトリの
  行を押したのに、開けなかった画面を持つ別のタブが 1 枚増える**。
  - **立ち直し(同§「立てない所へは立たない」)とは別の道** —— あちらは*立っているコピーが
    開けなくなった*タブの話で、こちらは*開けないコピーを新しく指した*時の話。前者は tab id を
    持っているので帰る先が分かる
  - 選べる答えは 2 つ: **その行を押した時だけ今のタブの話として断る**(頼んだ行がどのタブの
    左メニューに在ったかは分かっているので、`open_repository_path` にタブを添える)か、
    **今までどおり新しいタブで断る**(道が 1 本で済む代わりに、1 リポジトリ 2 タブが 1 場面だけ
    できる)。**絵は撮れる** —— `worktrees` preset の `gone` 行がまさにこれ
- **REMOTES 行から直接リモートブランチを改名する入口の文言**(2026-09-22 ユーザーに流れを提示、未決):
  手元の改名の続きは「rename とは名乗らず 3 択で訊く」に直した(規約 §手元の改名をリモートへ運ぶ)が、
  **REMOTES 行の「間を空けた 2 回目のクリック」から直接改名する入口は今の文言のまま** ——
  見出し `Rename origin/x to origin/y?` / 下の 1 行 `The old branch is deleted, not moved.` /
  ピル `Rename`(長押し。`RepoPage.askRenameRemote`)。**走るのは同じ作成 + 削除**なので
  「rename の語を使わない」をここにも通すなら、見出しとピルを作成 + 削除の語に直す。
  選択肢は 3 つ(語だけ直す / 今のまま = 直接の入口は「改名したい」という意図そのものだから /
  この入口自体をなくして、リモートを弄るのは改名の続きと `push` / `push --delete` の行だけにする)。
  流れは `rename-remote-box` → `rename-remote` → `rename-remote-go`(引数は
  `origin/feature/topic-a:topic-renamed`)の 3 本で撮れる

- **qtbridge 0.2.0 の `QList<QVariant>` の clone を上流へ報告するか**(2026-09-21。行き先は
  bugreports.qt.io の project **QTBRIDGES**、component Rust — GitHub の qt/qtbridge-rust は issues を
  閉じている): 型ライブラリの `QList_Clone`(`return { src };`)が Linux x86_64 / GCC / Qt 6.10.3
  (= qtbridge が README で要求する版、コンテナも CI も同じ)で「元のリストを 1 要素として抱えた
  長さ 1 のリスト」を返す。**再現は型ライブラリだけの 5 行**(`QVariantList::default()` に map を
  2 つ push → `clone()` → len 1、要素 0 は list。`cargo xtask linux test -p platitude-app wire` に
  固定済み)。標準の規則と整合: 集成体でないクラスの `{ src }` は initializer_list コンストラクタを
  先に見る(CWG 2137)ので、`QVariant(const QList<QVariant> &)` が暗黙にある Qt 6(6.4 と 6.10 の
  qvariant.h で確認)では 1 要素構築が選ばれる。MSVC が複製を返すのはその規則を採らない側 =
  Windows だけ緑になる形。QTBRIDGES を clone / QList / initializer / nested / QVariant / property /
  metatype / convert で検索して該当票なし(90 件を目視)。**`dev` 枝で直っているかは未確認**(生成物の
  パスが 0.2.0 と違い、tree からは引けなかった)。避け方は焼き込み済み(Rust 側で `QList<QVariant>` を
  持たない = `encode::wire` は組んで渡して捨てる)。**判断は「報告するか・票を切るなら誰が」だけ**
  (依存の版を動かす話ではない = 依存とライセンス.md の対象外)。
  **`Optional` を `qproperty!` に置くと qFatal「Property type mismatch」で落ちる件は不具合ではない**:

### 開発環境(Linux コンテナ)

- **新しい依存を初めて取る gate で、共有 registry への展開が 2 つの cargo でぶつかる**(2026-09-23、席 a の gate:
  `verify-linux amend` の release ビルドが `failed to unpack package darling_core … .cargo-ok: File exists (os error 17)`
  で赤 → その側の動詞が全部走らずに終わった)。ボリュームが載せるのは `/usr/local/cargo/registry` だけで
  (`linux::REGISTRY_MOUNT`)、cargo が展開を排他する `$CARGO_HOME/.package-cache` の錠はコンテナごと ——
  別コンテナの cargo(checks 群の `linux test` と動詞の release ビルド)が同じ新しいクレートを同時に展開すると
  衝突する。展開済みになれば再発しないので、依存を足した最初の gate でだけ出る。**直すなら錠も共有する**
  (CARGO_HOME ごとボリュームに載せる / 準備段で `cargo fetch --locked` を 1 本撃ってから群を並走させる)

- **席の木が、どのセッションの transcript にも削除コマンド無しに消えることがある**(2026-09-11〜13 に
  席 b・f、09-17〜18 に席 c。いずれも未マージ commit を持ち作業ツリーは clean、持ち主セッションが
  再起動 / 再開で本体 checkout に戻った直後)。容疑はセッション終了時の worktree の keep / remove
  問い合わせか CCD 側の後始末で、**原因は未特定**。機構側の答えは「木の有無と letter の所有を独立に
  扱う」: 枝の残った letter は `seats` と挨拶に「no tree」で出て、`cargo xtask seat takeover <letter>`
  が枝の上に木を生やし直す(`seats::grow_back`)。原因が判ったら、ここへ書き足すのではなく消す側の経路を塞ぐ

- **コンテナのイメージ・ボリューム・build cache は `linux` が入口で掃く**(`linux::housekeeping`、
  [linux.rs](../crates/xtask/src/linux.rs)。host 側の `docker run` が必ず通る 1 箇所で、プロセスにつき
  1 度)。`git worktree list` が挙げる checkout 全部から名前(`checkout_name`)と tag
  (`image_tag(root, stage)` × 4 stage)の集合を作り、**集合に無い
  `pgg-linux-{target,demo}-<名前>` と `pgg-linux:<stage>-<指紋>` を消して印字する**
  (`pgg-linux-registry` は機械のもので対象外)。**遅れた席の世代を守るのは build cache の上限では
  なく、この keep 集合** —— 席は main より遅れているのが正常なので、Dockerfile / ci.yml /
  rust-toolchain.toml が動いた日は世代が 2 つ同時に生きる。`--max-used-space` は
  **image が共有していない記録しか数えず、shared な記録は削除候補にすらならない**
  (buildkit v0.33。実測は [code-costs](../ci/baseline/code-costs-windows-x64.md))ので、上限が決めるのは
  「死んだ cache をどれだけ抱えるか」だけ —— `CACHE_CEILING` = 64MiB は「抱えない」の意味
  (0 は上限なしと読まれる)。残る罠は 3 つ:
  - **名前は checkout ディレクトリの最後の 1 段のテキストだけ**(`checkout_name`)なので、
    **別の場所にある同名の clone のボリュームは孤児に見え**、逆に**同じ木を別の綴りで指した
    プロセス**(8.3 短縮名・大小違い。`seats::same_tree` が在るのはこの差のため)は別名を作る。
    今は volume を作る側(`workspace_root` = ビルド時の `CARGO_MANIFEST_DIR`)も
    `git worktree list` も長い綴りを返し、席の letter は 1 文字なので短縮も起きない
  - **`git worktree list` が挙げない木は死んだ扱い**。席の木が消える事象(上の項)の最中は letter の
    枝だけが残るので、その席のボリュームは孤児として消える。`seat takeover` が木を生やし直した
    後に `linux` を 1 度撃てば作り直るが、**target は空から**になる
  - **`--rebuild` は cache 全ヒットでも新しい層を書く**(実測: core の unique が 7.17kB → 1.376GB。
    app は古い core の層を持ったままなので 1 世代分が二重になる)。動作確認のために撃つ物ではない
- **消してもホストのディスクは戻らない** —— Docker の VHDX は確保済みのブロックを削除後も抱えたままになる。
  WSL のスパース VHD は破損の可能性を理由に既定で無効で、`wsl --manage --set-sparse` は
  `--allow-unsafe` を要求し、`.wslconfig` の `sparseVhd` も同じ理由で効かない。縮めるには
  管理者権限の `Optimize-VHD` か `diskpart` の `compact vdisk` が要る

- **WSL のメモリ: gate 1 本につき約 900 MB が返らない — 原因は同定済み、対策は未実施**
  ([実測](../ci/baseline/wsl-memory-windows-x64.md) が正。観測は `cargo xtask footprint <コマンド>`)。
  **増えるのは VM の回収可能なキャッシュとスラブ**(Buffers / Cached / SReclaimable / Percpu)で、
  プロセスのメモリ(AnonPages)は増えない。**VM の中は最後まで枯渇していない**(MemAvailable は
  12.4 GB を切らず、PSI の待ちは累計 166 µs、oom_kill 0)ので Linux には回収する理由が無く、
  **WSL がホストへ返すのは VM の中で free なページだけ**だから Windows 側だけが減る。
  gate 後のコンテナ残留は 0 で、**プロセスやコンテナの居残りではない**。
  - **gate を止めた後も伸びる分は gate のものではない** —— コンテナ 0 の 9 分で `vmmemWSL` が
    9.4 → 15.0 GB まで伸び、読んでいるのは Docker Desktop が distro 内で回している
    `/initd services` 1 本(`/proc/<pid>/io` で同定。同時刻の dockerd / containerd は 0 バイト)。
    読む対象を作っているのは gate(席ごとの target ボリューム)なので、上の孤児ボリュームの掃除は
    ディスクだけでなくこの読みにも効くはずだが、**掃除を入れた 2026-09-21 の時点で孤児は 0 本**
    (a〜f + registry が全部生きている)なので、この読みが減るかはまだ測れていない
  - **走査が読んでいるのは gate が置いたデモリポジトリ**(2026-09-19、`/proc/<pid>/fd` で現認)。
    `pgg-linux-demo-a` は **260 万ファイル / 14,895 run ディレクトリ / 10.6 GB** で、
    inode の 99% がここ(`pgg-linux-target-a` は 22,132 ファイル)。gate 1 本が約 500 ディレクトリを足し、
    **コンテナ側には掃除が無かった**(ホストは入口で掃く)。
    **直した** —— 準備ステップが掃く(`linux::runner::SCRIPT`。テンプレートと `.pgg-keep` と
    直近 30 分は残す)。実測 **14,922 → 1,797 → 1,184**、単調増加だった SReclaimable が初めて減った
  - **掃除がどれだけ減らしたかは確定していない** —— 走査の `read_bytes` は窓の長さの違う点しか無く
    (4 分で +0.2 MB / 28 分で +2.43 GB)、削減率は出せない。**掃除の後にも走査は続いている**
  - **掃除の後の実負荷 3 本(2026-09-19 14:30–15:19、`--all --fresh` を背中合わせ)**:
    3 本とも PASS(5m53s / 5m43s / 5m34s)、oom_kill 0、swap は run 3 の 27 MB のみ、
    **`wsl --shutdown` は 3 本とも不要**。**この連続実行の後、ホストは自然に回復した**
    (15:02:09 に 1.6 GB を割り、15:04:12 に底 459 MB、15:08:21 に 2139 MB で復帰、
    15:19 に 6951 MB。約 450–500 MB/分)
  - **run 3 の低空きは gate 終了の後**(gate は ≈14:56 終了、1.6 GB 割れは 15:02:09 = +6 分、
    底 15:04:12)。**run 1 の 139 MB は開始 14 秒後で前の状態の引き継ぎ**、run 2 の 645 MB は gate 中 ——
    **底の位置は run ごとに違う**
  - **窓が揃っていないので、これ以上は断定しない**。run 1 / 2 の観測窓は 240 秒で、
    run 3 で低空きが始まった時刻より手前で終わっている。**「反復で蓄積しない」も
    「gate ごとに同じ症状が起きる」も、この 3 本からは言えない**
  - **`read_bytes` はストレージ読み取り量**。増減だけから走査の開始・停止を判断しない。
    **`drop_caches` の後に増えたのは確認済みだが、新しい走査なのか、キャッシュを失った既存処理の
    読み直しなのかは未確認**
  - **「通った run が自分のデモルートを返す」を入れた**(`verify::ownership::give_back_claimed`)。
    窓を 1200 秒に揃えた 1 対(BEFORE `59f8e0ca` / AFTER `1435fbbe`、開始 VM も揃えた)で
    **効いたのは 1 つだけ**: gate 1 本がボリュームに残す run ディレクトリ **+740 → +99**
    (残り 99 はほぼテンプレート)。**ホスト空きの底・低空きの継続・`initd` の読み取り量は
    この対では改善していない**(2019 → 1395 MB、146 → 438 秒、9178 → 9118 MB)。
    読み取り量がデモの inode 数に比例するという読みは**この対では支持されない**
  - **ボリュームは 264 万ファイル / 10.6 GB → 21.7 万 / 916 MB**(92% 減)。
    ただし大半は 30 分の床を持つ掃除が先に落としたぶん
  - **次の不足**: **コンテナ側の掃除はテンプレートを永久に残す**(ホストは 1 日で連れて行く)。
    fingerprint が動くたび新しい組が建ち、いま 1571 エントリ中 **1334 がテンプレート**。
    次はここをホストと同じ「1 日経ったテンプレートも連れて行く」に揃える
  - **「自然回収で足りる」「`memory=` 上限が唯一の対応」はどちらも断定しない**
  - **単発の `drop_caches` は恒久対策から外す**(2026-09-19 実測、ユーザー指示で 1 度だけ実行)。
    効いたのは約 90 秒(ホスト空き 3290 → 8300 MB、`vmmemWSL` 9922 → 3243)で、
    **落とした分を走査が 25 MB/s で読み直して 3.5 分で元へ戻した**
  - **`/initd services` の走査を起こす条件は未特定**。判っているのは読む対象と、
    **コンテナが 1 つ消えるたびに `fstrim /var/lib/docker` が仕掛け直される**こと
    (gate 中は約 10 秒ごと。`%LOCALAPPDATA%\Docker\log\vm\init.log`)だけで、
    走査そのものはログに 1 行も出ない
  - **`.wslconfig` に `memory=` の上限を置くのは別の問い**。VM が取れる上限を切るので
    Windows が失える最大値が決まるが、**上限を超えるビルドが OOM になり得る**。
    復旧は行を消して `wsl --shutdown`。**効果も適合性も、上限下で実負荷を通して測るまで未判定** ——
    「成功したか」「遅くなったか」「中で逼迫したか」の 3 つを見る。
    **VM の中の余裕(MemAvailable・PSI・oom_kill)を、上限が要らない理由にしない** ——
    ホスト側の低空きとは別の指標で、上限が効くのはまさに「VM が Windows から取れる量」の側。
    **auto mode の分類器が `drop_caches` を Modify Shared Resources で拒否しており、迂回していない**
  - **残骸の削減とホストメモリ症状は別々に判定する**。窓を揃えた 1 対では、
    残す run ディレクトリが 740 → 99 に減っても**ホスト空きの底・低空きの継続・読み取り量は
    動かなかった**。**残骸が減ったことをもって本件を完了扱いにしない**

- **`Get-CimInstance` は計測器のループに使わない**(2026-09-19 実測)。`Win32_OperatingSystem` を
  2 秒ごとに読むループが gate の 5 回目で固まり、プロセスは生きたまま(WS 111 MB)6 分間 1 行も
  書かなかった。ホストのメモリは `GlobalMemoryStatusEx` の直呼びで取る(`xtask::footprint`)

### 次の 1 回で何が読めるか

天井で刈られた run の下に、**アプリが歩いた駅が並ぶ**(`the stations it reached:` —
`harness::deadline` が `stations.txt` へ駅ごとに追記し、`verify::wedge` が読む)。
その次の行 `it got as far as ...` は**最後に記録できた駅と、子の時計での到達時刻**を言う。
滞在時間は子の時計の差で読む(親の時計とは起点が違う)。
記録が無い・空・読めない場合は到達状況不明。追記が失敗した先の進捗も不明。

- **駅は到達時に追記される**ので、正常に書けた分は終了時の一括報告を待たずに読める。
  `wedge.txt`(deadline スレッドが最後に 1 度だけ書く)との違いはここで、
  **`the app left no wedge.txt` だけでは、未到達と書込み失敗を区別できない**。
  外から止められた場合と、**`exiting` から先で止まった場合**(Windows の `ExitProcess` は
  detach ハンドラを回す前に他の全スレッドを終わらせるので、報告できるスレッドがもう無い)が
  同じ形になる。**この形から言えるのは「報告が無かった」まで**
- **`exiting` は駅の 1 つ**(`std::process::exit` の直前)。`hub-down` で終わっている trail と
  `exiting` で終わっている trail は別の答えで、後者は**exit 呼出しの直前まで到達した記録**。
  その後にどこで止まったかは、この記録だけでは特定できない
- **`identity-tip` の口でも同じ行が出る**。watchdog が発火した後の後始末も
  記録するので、正常に終了すれば `exiting` まで並ぶ。発火した事実だけで途中の停止は除外できない
- 並走の状況は同じブロックの `lanes:` 行が数える。account が `out of time in` で始まる場合は、
  天井の後にも駅が進んでいて最後の駅が猶予 10 秒を立ち止まる前に時間切れ =
  詰まりか遅さかはそこからは決められない
- **`threads at the ceiling:` と `a dump of the app:`**(2026-09-13)— 刈る直前のスレッド一覧と、
  Windows の full dump(shot dir の `app.dmp`)。`exiting` で終わる trail に **alive 1 本**が
  並べば `ExitProcess` の中(他スレッドは終了済み = DLL detach の区間)で、dump の `~*k` が
  その 1 本の stack = 止まっている DLL と関数を名指す。**alive が複数**なら exit の手前で、
  名前(Linux)/ 名前と開始モジュール(Windows = `<id> <state> <wait> <名前>@<module> cpu=`。名前は
  `SetThreadDescription` の値で Rust / Qt / tokio のスレッドが持つ、モジュールは開始アドレスの持ち主で
  OS のスレッドを名指す)が誰を待っているかを言う。**`exiting` の平常の顔**(2026-09-13、単独の held run):
  `main@platitude-gg.exe` + `-@ntdll.dll` × 6(スレッドプールの待機、EventPairLow)+ `-@WINMM.dll` × 1
  (タイマー)。Qt / tokio / deadline のスレッドは無い = teardown の後に user-mode の lock を持って死ねる
  スレッドが残っていない。ここに `QSGRenderThread` / `tokio-rt-worker` / `QQmlThread` が並んだら teardown
  の生き残りで、それが次の読み所。**行に出るのは先頭 8 本で、一覧の全文は shot dir の `threads.txt`**(Windows の
  一覧プロセスが自分で書く。Linux は /proc 歩きなのでファイルは無い)。**その下の `the main thread stands in:` が
  main の stack**(2026-09-14 から、**Windows のみ**。一覧の PowerShell が dbghelp の `StackWalk64` で全スレッドを歩く =
  debugger 無しで撮れる。Linux の /proc 歩きは stack を持たず、この行も出ない — wedge-check がこの行を要求するのも
  Windows だけ。frame は `module!export+offset` で、**module は正確・関数名は最寄りの export なので近所の名前**、exe は PDB が
  無いので `+offset` 止まり。全スレッドの stack は `threads.txt` の `stack <tid> …` 行)。**exit の中で止まった run は
  この 1 行で読む** — 他スレッドは detach の前に終了済みなので、一覧の顔ぶれでは原因を切り分けられない。注文した停止(`--fault-hang`)
  では dump を撮らない(原因が判っている停止に数百 MB を払わない)。**どちらの診断にも天井がある**
  (`verify::look::bounded` — 一覧 / dump のプロセスは天井で終了させて待ってから次へ進む。stdout は
  ファイルなので、診断が残した孫が何を握っていても答えは exit の時点で戻る)ので、
  `could not be listed — the listing ran out of time after Ns and was ended` / `no dump: the dumper ran
  out of time` は「診断が止まった」の意味で、アプリの回収と報告はその後も進む。`could not be ended` と
  pid が付く行だけは診断プロセスが残っている可能性を言う。**dump は `MiniDumpWriteDump` を PowerShell の
  `Add-Type` から直接呼ぶ**(`verify::look::DUMP_SCRIPT`)。`rundll32 comsvcs.dll,MiniDump … full` は
  この Windows(11 / 26200、2026-09-13 実測)では**使えない**: header の flags は full memory を名乗るのに
  WS 80 MB のアプリで 0.1 MB(stack だけ)、しかも ACL が SYSTEM / Administrators だけで撮った本人が
  開けない(owner なので `icacls <file> /grant <自分>:F` で戻せはする)。直接呼ぶと同じアプリで 224.5 MB /
  1.1 秒、ACL は普通。単体テスト `a_dump_of_a_standing_process_is_written_and_readable` が ping の
  full dump を撮って「1 MB 超・owner が開ける」を毎回確かめる
- **`> qt-tearing-down ` の駅**(2026-09-13)— `hub-down` と `exiting` の間で `QApp` を落とす区間。ここで
  止まる trail は Qt の破棄(engine / application の destructor)の中で、`exiting` で止まる trail とは
  別の答え

**この経路が止まった run でも働くことは、故障注入で確認する**(`cargo xtask wedge-check`。
gate は `gate::plan::record_of_a_wedge` の 7 ファイルに触れた時に選ぶ。host のみ・4 本で 30 秒弱 + ビルド。
**deadline スレッド無しの 2 本は、trail に注文した駅が出た時点で親が刈る**(`verify::child::ordered_hold`。判定は
`HELD AT <駅>`、天井は駅に届かなかった run だけが払う backstop)ので動詞 1 本ぶんの数秒で終わり、スレッド有りの 1 本だけが
天井 + スレッド自身の 10 秒を払う。**完了の証拠は事実**の型 — 以前は天井 + 親の猶予 20 秒を 2 本が払い、
代役の一覧の天井 15 秒がその上に乗っていた)。
4 つの形を実際に作って読み返す: **`exiting` で握ったまま deadline スレッド無し**
