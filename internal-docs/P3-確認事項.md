# Phase 3 確認事項

UI 変更を伴わない範囲で Phase 3 を実装した時点の、判断が要る点をまとめる。
Phase 2 分は [P2-確認事項.md](P2-確認事項.md)。

## 到達範囲

`platitude-core` の履歴編集操作とセッション配線、ブリッジスロット、および
**単体コミットへの編集（cherry-pick / squash / reword）の UI 配線**まで。
残る UI 作業は conflict ペインと interactive rebase の todo エディタ画面。

| 領域 | core | セッション | ブリッジ | QML |
|---|---|---|---|---|
| cherry-pick(単体) | 済 | 済 | 済 | 済 |
| merge / rebase / revert | 済 | 済 | 済 | 未 |
| continue / abort / skip / quit | 済 | 済 | 済 | 未 |
| conflict 一覧・種別・進行状態 | 済 | 済 | 済(プロパティのみ) | 未 |
| mergetool 起動・片側採用 | 済 | 済 | 済 | 未 |
| 単体コミットの squash / reword | 済 | 済 | 済 | 済 |
| interactive rebase（並べ替え / drop / edit / 複数行） | 済 | 済 | 未 | 未 |
| push 済みコミットの書き換え警告 | 済 | 済 | 済 | 済 |

**フル interactive rebase だけブリッジ未公開** — スロット引数に todo プラン（可変長の
構造リスト）が必要で、QML 側の画面設計と一緒に決めるべきだから。
単体コミットの squash / reword は、プランを**core 側で組み立てる**ことで
その設計を待たずに出せるようにした（下記「7. 単体コミットの編集」）。

## 決定済み・承認待ち

### 1. interactive rebase は「専用ヘルパー実行ファイル」方式

`GIT_SEQUENCE_EDITOR` に **`pg-todo-editor`** を指定し、UI で組んだプランを
git の todo ファイルへ上書きさせる。GUI 本体に `--todo-editor` モードを持たせる案も
あったが、git はエディタを **シェル経由で起動し即座の終了と終了コードを期待する** ため、
ウィンドウアプリにやらせる形にはしなかった。

→ **配布時の要件**: `pg-todo-editor.exe` を本体と同じディレクトリに置く。
   P5 の windeployqt / macdeployqt 手順に追加が必要（無いと interactive rebase だけが動かない）。

### 2. reword は `reword` 行ではなく `pick` + `exec git commit --amend --file`

`reword` 行は `GIT_EDITOR` を開く。プロセス層は `GIT_EDITOR=true` に固定しているので
ハングはしないが、**メッセージが黙って元のまま**になる（無言の no-op）。
`exec` 形式なら新メッセージを明示するので、通るか失敗するかのどちらかになる。
メッセージ無しの reword はプランの時点で拒否する（git を起動する前に落とす）。

### 3. continue の引数

`git merge --continue` と `git rebase --continue` は **引数を一切受け付けない**
（`--no-edit` を付けると usage エラー）。`GIT_EDITOR=true` に依存する。
`--no-edit` を渡すのは cherry-pick と revert のみ。

### 4. 進行中操作の優先順位

conflict で止まった rebase は `CHERRY_PICK_HEAD` も残す。ユーザーが継続すべきは
rebase なので、`InProgress::from_state` は rebase を優先する。

### 5. rebase 進行状況は status リフレッシュに同梱

`op_state.rebasing` が真のときだけ `rebase-merge/msgnum` 等を読む。
ヘッダの「REBASING 2/7」表示が status と同じタイミングで更新される。
rebase 中でなければ追加の git 実行は起きない。

### 6. 「published」の定義

remote-tracking ref から到達可能かどうか。**最後の fetch 時点の情報**でしかない。
リモートが無いリポジトリは何も published ではない（＝警告しない）。

### 7. 単体コミットの編集は core がプランを組む(**実装済み**)

`sequencer::plan_edit(oid, Edit::SquashIntoParent | Edit::Reword(msg))` が
範囲・プラン・`--root` の要否まで決めて `EditPlan` を返す。UI は oid と
（reword なら）新メッセージを渡すだけ。

決めたこと:

- **squash の範囲は `<oid>~2..HEAD`**。`squash` は「プランの 1 行上」へ畳むので、
  親もプランに入っていないといけない。reword は `<oid>~1..HEAD` で足りる
- **履歴の先頭に届く場合は `git rebase --root`**。`<oid>~2` が解決できない
  （= 2 番目のコミットを squash する / root を reword する）ケースは実際にある。
  `RebaseOptions.root` を足し、その時は `-- <upstream>` を付けない
- **範囲にマージコミットがあれば拒否する**。`--rebase-merges` 無しの rebase は
  マージを黙って落として履歴を平坦化する。「想定外の状態を隠さない」方針に反するので
  実行前に `rev-list --merges --count` で見て型付きエラーにする
- **HEAD の reword は amend にする**。replay すると後続コミットの id が全部変わるが、
  amend なら HEAD だけで済む。セッションが HEAD と比べて分岐する

### 8. コミットメッセージは subject / body の 2 欄でやり取りする(**実装済み**)

`commit::join_message` / `split_message` が「1 行目 + 空行 + 本文」の規約を持つ。
QML は 2 つの入力欄をそのまま渡す（**QML で文字列を組まない** — 規約どおり）。

## 要判断（UI 設計時）

### A. interactive rebase の画面

必要な要素: 対象範囲の選択（`<upstream>..HEAD`）、行の並べ替え、
アクション選択（pick/reword/edit/squash/fixup/drop）、reword のメッセージ入力。
`sequencer::plan_for()` が初期プランを返すので、UI は並べ替えとアクション付与だけ。

ブリッジのスロット形状も同時に決める必要がある(候補: プランを 1 行ずつ積む
`beginRebasePlan()` / `addRebaseStep(action, oid, message)` / `runRebasePlan(upstream)`)。

### B. conflict 中の「ours / theirs」の呼び方

**rebase 中は意味が反転する**（再生されるコミット側が theirs）。
git の用語をそのまま出すか、「現在のブランチ / 取り込む側」のように言い換えるか。
GitKraken は後者に近い。core は `Side::Ours` / `Side::Theirs` のまま。

### C. mergetool の扱い

- **Windows ではターミナル系マージツール（vimdiff 等）が使えない** — サブプロセスに
  コンソールを与えていない（`CREATE_NO_WINDOW`）。GUI ツールの設定が前提。
  `conflict::configured_tool()` で `merge.guitool` / `merge.tool` を事前に読めるので、
  未設定なら起動前に案内を出す想定。
- mergetool は**書き込みキューを占有する**（ユーザーがツールを閉じるまで）。
  その間ほかの書き込み操作は待たされる。キャンセル導線が要るかは要判断。

### D. 書き換え警告の出しどころ(**一部決定済み**)

`publish::state_of()` は範囲を渡すと「全体数 / 未 push 数」を返す。

| 操作 | 渡す範囲 | 実装 |
|---|---|---|
| amend | `HEAD^!` | 済（WIP ペインを開いた時と write 完了ごとに問い合わせ → `already pushed` タグ） |
| squash | `<oid>^!` | 済（コミットメニューを開く時に問い合わせ → メニュー行の `already pushed` タグ） |
| reword | `<oid>^!` | 済（メッセージ編集開始時に問い合わせ → 保存行の警告行） |
| force push | — | 済（`publish` は使わず、status の behind = 相手が失う数をそのまま出す） |
| interactive rebase | `<upstream>..HEAD` | 画面ごと未実装 |
| branch -D | 対象ブランチの未マージ範囲 | UI 未配線 |

**答えを置く場所は 1 つ**（`publishRange` / `publishTotal` / `publishPublished`）なので、
問い合わせた側は**自分が聞いた範囲の答えだけを読む**。警告はどれも**尋ねずに言う**
（実行は止めない。答えは `rev-list --count` 1 本なので数フレームで届き、届いた時だけ
タグ・警告行が出る）。

force push の「相手が失うコミット数」は **status の behind をそのまま使う**（決定済み）。
`publish::state_of()` は要らない — behind は `HEAD..@{upstream}` の数、つまり上書きで
相手から消えるコミット数そのもの。ただし**最後の fetch 時点の値**なので、
出す時は必ずいつ時点かを添える（デザイン規約 §リモートへ送る）。
拒否された push が fetch を呼ぶようになったため、この数は上書きの直前には必ず新しい。

### E. squash のメッセージ（**決定済み**）

`squash` は git がメッセージを結合して `GIT_EDITOR` を開く → `true` 固定なので
**結合済みメッセージがそのまま採用される**。これを採用する。
気に入らなければユーザーが後から amend で直せばよい。

## UI 実装時に必ず作るもの

### 1. amend で直前コミットと統合する経路(**実装済み**)

WIP ペインの「Amend the last commit」チェックボックス。オンにすると
`requestHeadMessage()` で HEAD のメッセージを取り寄せて 2 欄に入れる。
push 済みなら確認ダイアログを挟む。

### 2. cherry-pick / revert の複数選択(**未**)

core は複数リビジョンを受ける（`cherry_pick(revs)` / `revert(revs)`）。
ブリッジが 1 件ずつなのは、複数選択 UI がまだ無いから。

## identity 入力導線(UI 実装済み)

起動時に name / email が揃っていなければ専用画面で尋ねる。アプリメニューの
「Identity…」とツールバーの `SET IDENTITY` バッジからも開く。

### 決定

1. **モーダルダイアログ**(ユーザー指示)。開閉は `identityWanted` の状態から
   `open()` / `close()` で駆動する — `visible` を束縛すると Escape の
   `close()` が束縛を壊し、メニューから二度と開けなくなる。閉じたときは必ず
   状態側へ書き戻して整合させる
2. **書き込み先は global 固定**。答えは人に属するもので、リポジトリ単位の上書きは
   Settings の領域(core は `ConfigScope::Local` も持っている)
3. **「Not now」で先へ進める**。読み取りだけなら identity は要らない。未設定である
   ことはツールバーのバッジが示し続ける
4. **アプリ起動ディレクトリで判定する**。リポジトリ外なら global + system の効き目
   そのもの。リポジトリ単位の真値はタブの `identityReady` で、バッジは両方を見る
5. **独自のバリデーションは持たない**(ユーザー判断)。git が拒むのは**空の name
   だけ**で、それも commit 時("Author identity unknown")。core はこれだけを
   早めに拒否し(`GitError::Rejected`、文言はそのまま画面へ)、UI は **git が
   author 行から落とす文字(`<` `>` 改行)を入力段階で弾く**(validator)。
   前後の空白は保存時に trim する — git も author 行では削るため
6. **背後の暗転(scrim)は入れない**(ユーザー判断)。Fusion スタイルは
   `Overlay.modal` を定義しないので既定で暗転せず、**scrim トークンは追加しない**。
   階層は背景色と境界線だけで表す(デザイン規約の方針どおり)

### 要判断

- **リポジトリ単位の identity 上書き**(仕事用メール等)の導線。core は対応済み・UI 未提供
- **署名状態(`signingActive` / `signingFormat`)の表示場所**。プロパティはあるが未使用
- 本文幅 `640` は git バージョン gate からの流用。デザイン規約の表に無い値なので、
  token 化するかは要判断

## コマンドログ(実装済み・残りの判断)

下部パネル(`CommandsPane`)。既定は非表示で、ツールバーの `>_` で開く。
**利用者の能動操作だけを記録する** — 書き込みキューを通ったものが対象で、
auto fetch は除外(誰も頼んでいないものが、オフラインで毎分パネルを上げるのを避ける)。
内部読み取りは `Background reads` を入れた時から記録される。

要判断として残るもの:

- **保存が無い**。1 タブ 500 件・件数を超えたら古いものから捨てる(1 件あたりの上限は
  無い — 途切れた出力の方が害が大きい。実質の天井は `process::STDERR_CAP` = 256KB)。
  ファイルへの保存・「全部コピー」は将来分
- **エラー表示の仮置き**。失敗するとパネルが自ら開き、閉じるまで開いたままになる。
  ヘッダの 1 行(`repoTab.lastError`)は**行に出ない失敗**のための場所だが、
  書き込みの失敗では行と二重になる。本来のエラー表示を作る時に整理する
- **リモート URL のマスクをしていない**。保存もコピーもユーザー操作なので現状は害が
  無いが、ログをファイルに出す時は `https://user:token@host` の userinfo を落とすこと

## 既知の制限・残課題

- **`--autostash` / `--update-refs` は API にあるがブリッジ既定は false**。
  どちらを既定 ON にするかは実使用感で決めたい（要望.md はオプション提供とだけ規定）。
- **octopus merge（3 親以上）は作れない**: `merge` は 1 リビジョンのみ受ける。
  要望に無いので未対応。
- **`rebase --onto` の branch 指定**は core にあるがブリッジ未公開。
- **conflict 中の diff 表示**: `status` は conflict エントリを返すが、3-way の
  ours/theirs/base それぞれの内容取得は未実装（`git show :1:path` 等）。
  外部ツール委譲の方針なら不要かもしれない。
- **interactive rebase 中の `edit` 停止**は git の正常動作だが非ゼロ終了で返る。
  セッションは「失敗」として `WriteFinished{error}` を出すので、UI 側で
  「停止しました」と「失敗しました」を区別する必要がある（op_state を見れば判る）。
