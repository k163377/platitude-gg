## 残っている実装

**フル interactive rebase はプラン編集モードとして配線済み**(意匠の正本は
デザイン規約 §フル interactive rebase、実装対応は rules-refs/app-ui.md)。HEAD より古い
コミットの reword もこの画面が道になった。残る磨き(不具合ではない):

- **reword の鏡写しは保存時**(行の subject は `setMessage` で更新)— 打鍵ごとの live
  反映にするなら `MessageEditor` に text-changed の口を切る
- **squash / fixup の「親へ畳む」を言うのは動詞チップだけ**(字下げは撤去 = 3 列を揃える
  指示)。モックにあった接続線(下の行へ肘)は未描画 — 描くなら行を跨ぐので pane 側の
  オーバーレイ
- **プランの読みに行数の上限は無い**(ユーザー判断)— `--root` プランは全履歴を
  `PlanRow` に組む。JetBrains/kotlin で 138,915 行・`read_rows` の git 読みだけで 1.40s・
  stdout 25.8MB。**性能予算はベースライン**(素で表示した時)の話で、利用者が自分で開いた
  全履歴プランの増分は最適実装の分として許容する。規約 §フル interactive rebase の
  ローディング面がこの遅さの受け皿
- **プラン行に ref チップが出ない**(`--update-refs` で連れて動くブランチの可視化)。
  行 0 = 現在ブランチ分だけでも出す価値あり
- **実行後の選択は既定挙動**(旧選択が消えて default select)— 「読んでいた行の
  書き換わった先を追う」は未接続。単体 reword の `followRewrittenCommit` は在るが、
  armは `RepoPage.saveMessage` の 1 箇所だけで、プラン実行はそこを通らない
- **動詞チップに ▾ の描画が無い**(チップ押下と右クリックで開く)。NavIcon に chevron の
  項が無い件(下の §AppCombo)と同じ席
- **捨てる物が在るプランの Esc は無言**(規約 §hover のツールチップ —— その側の `Discard`
  は長押しなので、1 度下りただけの鍵では撃てない)。**残る判断は手応えを足すか** ——
  設定画面が持っている形(1 回目は閉じずに失う物へ送って `✕` を armed にし、2 回目で
  閉じる = `SettingsDialog.escapeOut`)をプランへ移すなら、`Discard` を armed に見せる姿の
  決定が要る
- **ヘッダ / onto 行のブランチ名は開いた時点の写し** — 端末で base ブランチだけを
  動かされると名前は古くなる(挙動は oid 釘付けで正しいまま。行末の sha が実体)。
  名前の生き直しは refs 更新との突き合わせが要る
- **行に掴み点(grip)の印が無い** — レビューで除去(トークンに点サイズが無く、直書きは
  規約違反)。行全体が掴み手で機能は成立。**印を戻すならトークン追加の人間承認とセット**
- **プラン行の選択は「模型の selected_row + ページの selectedOid」の二重持ち** —
  reorder の追従は模型側 remap で守られているが、所有を模型の oid 1 本に寄せる余地あり
  (レビュー所見・据え置き: 動く実害が無く、寄せると graph 選択との橋が別に要る)
- **プランの push 済み count は模型が持つ**(`RebasePlanModel.pushedCount` — 開く読みが
  数え、refs が動いたら range 名指しで数え直す。共有の publish 枠は無い)。数え直しの読みが
  失敗した時は開いた時の値のまま(異常系のみ・次の `refsMoved` で撃ち直す)
- **クリーン停止の WIP 行は語が場面に合っていない**(目視・`rebase-edit-stop` の絵)—
  `edit` 停止の着地はグラフ最上部の `Uncommitted changes` 行 + 右ペインの
  `UNCOMMITTED CHANGES (0)` + 空のファイル一覧で、**行は「無い物が在る」と名乗る**。
  席そのものは仕様どおり(規約 §進行中の操作から出る「着地は WIP 行」= 出口カードは
  この行の下に吊るので、行を消すとカードの席ごと消える)。**据え置き** — 停止の説明は
  同じペインの底の出口カード(`REBASING — 1 of 2` / `edit Stopped on purpose at <sha8>`)が
  持っており、読み手が次に何をするかは迷わない。直すなら行の語の側(席は動かさない)。
  同じ絵のコミット枠(`commit to HEAD`)は**押せない** — staged ゼロ・amend でなし・
  立っている本文も無い停止では `WipCommitBlock` の可否が降り、断りは
  `Stage something to commit`

### 別 worktree の未コミット行 — 残っているのは読みの代金だけ

**決定も実装も済んでいる。** 意匠の正本は [デザイン規約.md](デザイン規約.md)
§別の作業コピーを読む と §未コミット行が名乗るもの、実装対応は
rules-refs/app-ui.md(右のペイン 3 面・全ゼロ id・
WORKTREES 行・`LabelKind::Worktree` のチップ)。ここに残るのは読みの代金と、
まだ建てていない物への手すりだけ:

- **開幕の巡回(`refresh_quick` → `refresh_carried`)はグラフの初回描画と同じ機械を
  取り合う** —— 8 コピーの corpus で起動→グラフが 1.10–1.12s(巡回なし)→ 1.74–2.05s
  ([git-slots-windows-x64.md](../ci/baseline/git-slots-windows-x64.md) §枠の床 /
  §巡回と重なった時)。枠は足りていて(interactive は待たない)、食われるのは CPU
  (1 本の status が 11 コア幅)。直すなら開幕の 1 周を `LogFinished` の後へ遅らせる
  (focus の巡回はそのまま)。**予算 3s の内側なので今は据え置き**
- **要判断: ペインが立っているコピーの二重読み**(実測済み = tick ごとに `status` 1 本ぶん。
  数字と条件は同記録 §ペインが立っているコピーの二重読み)。**一覧は pass の答えと同じ
  コマンドの同じ出力**なので相乗りさせられるが、**選んだ瞬間の 1 本だけは別**
  (次の tick を待たせられない)。直すなら `RepoPage.pollCarried` の側 —— 選択時は今のまま
  読み、tick では pass の答えから配る
- **同時に撃つ `status` 4 本と 30 秒の tick は決め打ちのまま** —— 上限そのものはどの数でも
  要る(executor に上限が無いので、20 worktree なら 20 プロセスが同時に立つ)が、
  **この 2 つの数字は次の本計測で取り直して決め直す**(宿題は
  [perf 記録](../ci/baseline/perf-windows-x64.md) §未取得 の「同時に走る `status` の
  本数と実時間」。1 本 0.48s までは測れている)
- **worktree 特化の右クリックメニューを足す時の手すり**(今は無い —— WORKTREES の行も
  この行もメニューを持たない):
  - **同じ作業コピーのチップは 2 箇所に出る**(ブランチを持たない作業コピーが立っている
    コミットと、この WIP 行)。**足すなら 1 つを両方から開く** —— 2 つ書けば必ず食い違う
  - **ただしこの行からは開かない。** 入口は WORKTREES セクションの行(と、既にチップを
    持っているコミット行)に限る。`worktree remove` / `prune` は破壊的で、**この行が
    持っている扉は「その作業コピーを開く」1 つだけ**という形を崩す
  - **足すには `label_kind_word` が `W` に語を返すようにする必要がある** —— 今は `H`
    (HEAD の印)と同じく `""` = 「名指すものが無い」と答えており、それが「チップは名前で
    あって扉ではない」を機械で保証している。**この 1 行を変えると 2 箇所が同時に扉になる**
    ので、変える時は上の 2 つを同時に決める

## ウィンドウ chrome — 形は決まり、残りは中身

形の正本は [デザイン規約.md](デザイン規約.md) §ウィンドウの縁。Windows の縁に残る 2 つ
(窓メニューの移動・サイズ変更 / Snap Layouts)は [P5-確認事項.md](P5-確認事項.md) §10。
ここに残るのは中身の方:

- **アドバンス検索**(Ctrl+F の基本検索は配線済み — 正本は規約 §コミットを探す):
  - **項目を名指しして探す形**(`author:` / `path:` / `date:`)。素の語を全軸のまま git へ
    降ろすと `--grep` と `--author` は AND なので和集合に 3〜4 スポーン要るが、接頭辞つきなら
    1 クエリ 1 スポーンで各接頭辞が git のフラグ 1 つに対応する
    (`git log --grep=… --author=… -G… -- <path> --format=%H` が SHA を返すので、アプリ側は
    「その SHA が来たら光らせる」= 印の仕掛けは基本検索のものを使い回せる)
  - **最初に出せるのは `description:`** — 外した 4 つのうち Description だけは行が既に
    持っているので、git を 1 プロセスも撃たずに出せる(パス / diff / 日時 / committer は
    git が要る)。**塞ぐ穴は実在する** — 機能名でしか呼ばれない語は今まったく引けない
    (0 件の語の実測は規約 §何に当たるか)。判断は「据え置き、実使用をもう少し重ねてから」
  - **同時に決まるもの 3 つ**:
    1. **日付で探す**。行は epoch 秒しか持たず、画面の `yyyy-MM-dd HH:mm` は表示側が作る。
       Rust 側にタイムゾーン依存を 1 つ足すか、`LOG_FORMAT_ARG` に
       `%ad --date=format-local:%Y-%m-%d %H:%M` を 1 フィールド足す(`LOG_FIELDS` 8→9・
       parser の field 分岐・`CommitMeta` / `LogRow` / fixture)かの二択。**後者で決まり** —
       git が DST 込みで正しく組み、行が画面と同じ文字列を持つ。**`format-local` が読み手の
       時計に焼き付くことは代金ではない** —— 時刻は常に読み手のゾーンで出すと決めてある
       (規約 §author の hover)。範囲(`date:2026-08` / `--since` / `--until`)もそこで一緒に決まる
    2. **窓の外を探すか**。基本検索は読み込み済みの行しか見ない。git へ降ろす検索は窓の外も
       返せるので、返った SHA がグラフに無い時に何をするか(件数だけ言う / 窓を伸ばす /
       その行まで読み込む)が要る
    3. **パスで探す**(実装計画.md §14 のフィルタ 4 軸の最後)。`-- <path>` は git 側でしか
       解けない
  - **絞り込み(行の間引き)は引き続き別物** — レーンとエッジを「隠れたコミットを跨ぐ」形で
    引き直すことになり、core に 2 つ目の walk モードが要る
- **検索の入口をキーだけにしない案(未着手)**: アプリメニューに `Find commits…` の行を足す
  (規約 §メニュー に沿い、キーが届かない場面の逃げ道にもなる)。`Shortcut` の既定は
  `Qt.WindowShortcut` なので、**窓がまだアクティブでない間はキーが届かない**
  (Windows のフォアグラウンド・ロックで前面にならずに起動した窓 = 「中を 1 回
  クリックしたら以後ずっと効く」の形)
- **macOS の形は決定済み・実装は実機ゲート**(Phase 5)。☰ は持たない — 画面上端の
  メニューバーが常に届く場所に既に在る。`QtQuick.Controls` の `MenuBar` は Qt 6.8 以降
  macOS で既定ネイティブ。**作るのは macOS だけ**(`Loader` で分ける — 他 OS では
  非ネイティブの QML メニューバーが窓の中に 2 段目として出る)。ネイティブ MenuBar は
  delegate を使わない = `AppMenu` の意匠は効かないので、**行の定義を 1 か所に置き見せ方
  だけ OS で分ける**。traffic light が帯の中心から約 6px 上は許容(直すには AppKit が要る)。
  `About` / `Settings…` / `Exit` がアプリメニューへ自動で寄るかは実機で確認

## 要判断(小さいもの)

- **usage ページの verb 見出しをカタログから生成するか**(コマンドの正本を入れた時の見送り分):
  今は verb の綴りが 3 箇所(`crates/xtask/src/main.rs` の dispatch / `crates/xtask/src/usage.rs`
  の見出し / モジュール側の `Command`)にあり、**ズレは `cargo xtask docs` が拒む**
  (`crates/xtask/src/docs/commands.rs` の `dispatched` / `described`)ので実害は止まっている。
  **生成にすれば**その照合と 3 箇所目が消えるが、**usage.rs の解説散文を 20 モジュールへ移す**
  ことになる(見出しだけ生成して散文を残すと、散文と宣言が同じ verb を 2 箇所で説明する =
  今回削った重複が戻る)。**判断の軸は「散文の置き場が責務ごとで正しいか」**
  — 正しいなら移す価値があり、usage が 1 ページとして読まれることに価値があるなら今のまま。
  触るのは `crates/xtask/src/usage.rs` と各モジュール、消えるのは `docs/commands.rs` の
  `usage` / `blocks` / `described` / `header`

§A(interactive rebase の画面)は決着 — 決定はデザイン規約 §フル interactive rebase が
正本(プラン編集モード / 押した行 = 含まれる最古 + onto 行 / 右ペイン連携 / 凍結 /
実行ボタン 3 状態 / edit 停止の答え)。残る判断だけをここに:

- **同じリポジトリのサブフォルダを指した時**: 既に開いているタブへ移る判定は
  `repo::open_key` = `canonicalize` のフォルダ一致なので、`repo` と `repo/src` は別と答えて
  2 枚開く。同じと答えるには `rev-parse --show-toplevel` の答えを待つ必要があり、判定が
  居るのは同期スロット(`TabsModel::open_repository_path`)の中。**開いてから畳む**
  (解決できた時点で既存タブへ吸収)か**そのままにする**かを決める。**別 worktree は
  別タブのままが正**(作業ツリーが違う = 見るものが違う)
- **cherry-pick / revert の複数選択 —— 待っていた前提はもう来ている**。core は複数リビジョンを
  受け(`cherry_pick(revs)` / `revert(revs)`)、**グラフの複数行選択も配線済み**
  (rules-refs/app-ui.md の配線済み一覧)。塞がっているのはブリッジだけで、
  `RepoTab::cherry_pick` / `revert` が 1 本を受けて `vec![…]` に包み、メニューの行も
  `rowMenu.oid` 1 本を渡している。**行き先は既に決まっている** —— 規約 §複数のコミットを選ぶ が
  「選択の先にあるのは複数 cherry-pick」と言い、diff の積み方もその順で書いてある。
  **残っているのは意匠 1 点だけ**: 複数選んだ時にメニューの行が何と名乗り、revert も同じ扱いに
  するか(規約は行の文言まで持っていない)。それが決まれば実装は
  `crates/platitude-app/src/models/repo_tab/qobject.rs` と `CommitRowMenu.qml` の口を広げるだけ
- **`rebase --onto` の branch 指定**: ブリッジは `rebase(upstream, onto, update_refs)` で
  受け取れる。**空でない `onto` を渡す導線が 1 つも無い**(メニューも自動化も `""`)ので、
  出すなら意匠から
- **`merge` のオプション**: ブリッジが受けるのは `--no-ff` / `--ff-only` の 2 つで、
  呼ぶ側は全員 false。`--squash` はブリッジに口が無い(`squash: false` 直書き)。
  rebase 側が足すのは `--update-refs` だけに決めた(規約 §履歴を合流させる)。
  merge のこの 3 つをどう出すかは実使用感で決める
- **質問を立てる残り 2 経路**: グラフ行の右クリックと REMOTES の行から `startPublishAsk()` を
  呼ぶ配線。**対象は呼んだ所が決め、見出しはその対象を名乗る**(2026-09-16 ユーザー判断。
  規約 §はじめてリモートへ送る)—— REMOTES の行は行き先だけを決めるのでブランチは今立って
  いるもの、グラフ行は**その行が名乗るブランチ**が対象。`startPublishAsk()` は今 `workTree.branch`
  を直書きしているので、そのまま呼ぶと**行に関係なく現在のブランチを名乗る**形になる。
  **先に要る 1 手**: 押せるかを決める `GitFacts.pushStanding` が読むのは `WorkTreeModel`
  = status = HEAD のぶんだけ。upstream / ahead / behind は `RefEntry` が行ごとに持っているが、
  **印 `branch.<n>.pushRemote` は HEAD のぶんしか読んでいない**(core の `remote::marks` は
  名指しの 1 ブランチを引く)ので、行ごとに答えるにはその読みを広げる
- **リポジトリを開く `rev-parse` をコマンドログに出すか**(保留): 今は背景読みなので、開けな
  かった画面から `>_` を押してもパネルは空で立つ。出すには利用者用ハンドル(`exec_user`)で
  撃つ 1 行で足りるが、core.md「書き込みキューだけが利用者用を使う」の書き換えを伴う
- **コマンドログに保存が無い**: 1 タブ 500 件・超えたら古いものから捨てる(1 件あたりの
  上限は無い — 実質の天井は `process::STDERR_CAP` = 256KB)。ファイルへの保存・
  「全部まとめてコピー」は将来分(コピーはドラッグ + Ctrl+C の 1 本に決めた =
  規約 §git が言ったことを読む場所)。**ファイルへ出す時は `https://user:token@host`
  の userinfo を落とすこと** — 選択のコピーは**画面に出ている綴りをそのまま渡す**方で
  揃えてあり、落とすなら両方揃えて落とす
- **エラー表示が仮置き**: 失敗するとコマンドログのパネルが自ら開き、読み手が閉じるまで
  開いたまま(**自分で下りるのは失敗した fetch が上げた 1 枚だけ** — 届くようになった
  fetch が下ろす。所有の規則は `CommandsOwner`)。**素通しするのは 3 つ** — 質問に化けた
  拒否 = `RepoPage.expectedRefusals`、書き込みの最中に落ちたコマンド =
  `repoTab.writeRunning`、**報せバーが受けるもの** = `GitError::Reported` / `Withheld` が
  運ぶ報せ(向こうの拒否・こちらが古い push・コミットの拒否・こちらが先に断ったもの。
  規約 §答えの要らない報せ。数えるのは `RepoPage.answeredFailures`)。ヘッダの 1 行
  (`repoTab.lastError`)は行に出ない失敗のための場所だが、書き込みの失敗では行と二重になる。
  本来のエラー表示を作る時に整理する
- **Answered な失敗コードの行表示**: exit code が答えのコマンド(`merge-base --is-ancestor`)の
  exit 1 行は ok 扱いで右列が空になる。code をそのまま出す表示を検討
- **コメントの実測値禁止を機械で守るか**: 規約は書いた(CLAUDE.md §Rust 規約)が
  `cargo xtask` の網は無い。素朴な grep は `Theme.qml` / `Metrics.qml` のトークン・Qt の
  アニメーション長・OS のキーリピート・`100ns` 単位を全部拾うので、**張れるのは
  「`measured` / `実測` と時間・メモリ単位が同じ行に在る」程度の弱い網**。
  誤検出のたびに `// waits(…)` 式の逃がし方が要るかも含めて判断が要る

  置き換わらない)。**枠の側から見ても同じ 2 本が的** — 枠が細い機械で待たされるのはこの直列鎖の頭
  (`rev-parse --verify`)で、常駐にすればその待ちごと消える(同記録 §枠の床)。設計:
  **① 1 リポジトリ 1 本** — `RepoSession` が持ち、`git cat-file --batch-command`(2.36+、最低版の
  内側)を `stdin` piped で spawn する = **プロセス層の「stdin は常に閉じる」の唯一の例外**で、
  常駐用の別 spawn 経路(`process::Resident`)に閉じ込め、`GitCommand` の道は閉じたまま。
  **② 要求と応答の対応** — 要求は 1 行ずつ、応答は `<oid> <type> <size>\n` + 本体 + `\n`
  (`missing` は 1 行)で、常駐の口は `tokio::sync::Mutex` で直列に使う(1 度に 1 要求 = 応答の
  読み切りまで次を書かない)。**③ キャンセル** — 要求を書いた後の cancel は応答を**読み捨ててから**
  返す(途中で口を離すと次の要求が前の本体を読む)。読み捨てが `SOURCE_BYTE_CAP`(4MB)を超える
  長さなら常駐ごと終了させて次で再起動する方が安い。**④ 異常終了・再起動** — 書き込み / 読み取りの
  EOF で `Dead` にし、次の要求が spawn し直す(1 回だけ再試行、2 度目は一発 `cat-file` へ落とす)。
  **⑤ アイドル解放** — 最後の要求から 30 秒で kill(タイマは `AutoFetchClock` と同じ手回し可能な形)、
  `RepoSession::close` で kill。**⑥ 保持メモリ** — 実測 360KB + 触った pack ページ(pack 6.4GB を
  写像するのは触った分だけ)。`heap_report` に常駐の pid と生存を載せる。**⑦ 枠** — 常駐は
  spawn の 1 回だけ `Slots` の Here プールを通り(`Priority::Interactive`)、以後の要求は枠を取らない
  (プロセスが増えないので)。**⑧ 観測** — コマンドログには常駐の起動 1 行と、要求ごとの行は
  出さない(`Kept::Unasked` の読みなので背景記録が on の時だけ `<spec>` を 1 行)。
  実装したら `perf_diff_frame` の p50 / max を [perf 記録](../ci/baseline/perf-windows-x64.md)
  §判定 の diff の行と並べて採否を出す

### 開発環境(Linux コンテナ)

- **コンテナのボリュームは誰も掃除しない**: `forget_older_images` はイメージの古いタグを消して

  作るので、**席が消えても、使い捨ての worktree が消えても、`IMAGE` 定数を変えても、旧い名前の

  判定は機械にできる形で、`git worktree list` に無い名前のものは現行のコードから参照する経路が
  無い。足すならイメージ側と同じ「消したものは印字する」規律で。**消してもホストのディスクは
  戻らない** —— Docker の VHDX はスパースではなく、確保済みのブロックを削除後も抱えたままになる。
  WSL のスパース VHD は破損の可能性を理由に既定で無効で、`wsl --manage --set-sparse` は
  `--allow-unsafe` を要求し、`.wslconfig` の `sparseVhd` も同じ理由で効かない。縮めるには
  管理者権限の `Optimize-VHD` か `diskpart` の `compact vdisk` が要る

- **選択のある hunk で `Discard 3 lines` を出すか**: 行を選べるようになって「素の `×` には
  失うものを書く場所が無い」という理由が消えた。今は `Discard hunk` のまま(規約 §その他の操作)
- **運んでいるタブの脇にツールチップが残りうる**(**実操作待ち**): 出す条件は
  `pointed && !held` なので掴んだ後に新しくは出ないが、**掴む前から立っていた 1 枚**は共有
  インスタンスの keeper が保つ(`SharedToolTip.wanted` = ポインタが的の上に居れば保つ ——
  運ばれているタブはその的のまま)。座席は `freeze()` で固定なので、タブが帯を横切る間その箱は
  置いていかれる。hover は注入できないので**実操作でしか見えない**。直すなら「的が『もう要らない』と
  言える口」を keeper 側に足す形で、タブ側の細工にはしない。**機構は 2 行に絞れている**

  的にしか言えない**、というのが上の「口」。**実操作で再現を撮るまで直さない**(機構は
  読めているが観測が無く、keeper は全ツールチップの共有部品)

  実測で裏を取る**のが最初の一歩で、引き算が負になるなら席を `iconSm` へ落とす側

  **字と山の重なりは別件として直した**(2026-09-15。欄の右の inset が山の席を避ける形になり、

### 次の 1 回で何が読めるか

天井で刈られた run の下に、**アプリが歩いた駅が並ぶ**(`the stations it reached:` —
`harness::deadline` が `stations.txt` へ駅ごとに追記し、`verify::wedge` が読む)。
その次の行 `it got as far as ...` は**最後に記録できた駅と、子の時計での到達時刻**を言う。
親の時計とは起点が違うため、親の経過時間との差をその段階の滞在時間としない。
記録が無い・空・読めない場合は到達状況不明。追記が失敗した先の進捗も断定しない。

- **駅は到達時に追記される**ので、正常に書けた分は終了時の一括報告を待たずに読める。
  `wedge.txt`(deadline スレッドが最後に 1 度だけ書く)との違いはここで、
  **`the app left no wedge.txt` だけでは、未到達と書込み失敗を区別できない**。
  外から止められた場合と、**`exiting` から先で止まった場合**(Windows の `ExitProcess` は
  detach ハンドラを回す前に他の全スレッドを終わらせるので、報告できるスレッドがもう無い)が
  同じ形になる。**「deadline スレッドに届いていない」とは読まないこと**
- **`exiting` は駅の 1 つ**(`std::process::exit` の直前)。`hub-down` で終わっている trail と
  `exiting` で終わっている trail は別の答えで、後者は**exit 呼出しの直前まで到達した記録**。
  その後にどこで止まったかは、この記録だけでは特定できない
- **`identity-tip` の口でも同じ行が出る**。watchdog が発火した後の後始末も
  記録するので、正常に終了すれば `exiting` まで並ぶ。発火した事実だけで途中の停止は除外できない
- 並走の状況は同じブロックの `lanes:` 行が数える。account が `out of time in` で始まる場合は、
  天井の後にも駅が進んでいて最後の駅が猶予 10 秒を立ち止まる前に時間切れ =
  詰まりか遅さかはそこからは決められない
- **`threads at the ceiling:` と `a dump of the app:`**(2026-09-13)— 刈る直前のスレッド一覧と、
  Windows の full dump(shot dir の `app.dmp`)。`exiting` で終わる trail に **alive 1 本**が
  並べば `ExitProcess` の中(他スレッドは終了済み = DLL detach の区間)で、dump の `~*k` が
  その 1 本の stack = 止まっている DLL と関数を名指す。**alive が複数**なら exit の手前で、
  名前(Linux)/ 名前と開始モジュール(Windows = `<id> <state> <wait> <名前>@<module> cpu=`。名前は
  `SetThreadDescription` の値で Rust / Qt / tokio のスレッドが持つ、モジュールは開始アドレスの持ち主で
  OS のスレッドを名指す)が誰を待っているかを言う。**`exiting` の平常の顔**(2026-09-13、単独の held run):
  `main@platitude-gg.exe` + `-@ntdll.dll` × 6(スレッドプールの待機、EventPairLow)+ `-@WINMM.dll` × 1
  (タイマー)。Qt / tokio / deadline のスレッドは無い = teardown の後に user-mode の lock を持って死ねる
  スレッドが残っていない。ここに `QSGRenderThread` / `tokio-rt-worker` / `QQmlThread` が並んだら teardown
  の生き残りで、それが次の読み所。**行に出るのは先頭 8 本で、一覧の全文は shot dir の `threads.txt`**(Windows の
  一覧プロセスが自分で書く。Linux は /proc 歩きなのでファイルは無い)。**その下の `the main thread stands in:` が
  main の stack**(2026-09-14 から、**Windows のみ**。一覧の PowerShell が dbghelp の `StackWalk64` で全スレッドを歩く =
  debugger 無しで撮れる。Linux の /proc 歩きは stack を持たず、この行も出ない — wedge-check がこの行を要求するのも
  Windows だけ。frame は `module!export+offset` で、**module は正確・関数名は最寄りの export なので近所の名前**、exe は PDB が
  無いので `+offset` 止まり。全スレッドの stack は `threads.txt` の `stack <tid> …` 行)。**exit の中で止まった run は
  この 1 行で読む** — 他スレッドは detach の前に終了済みなので、一覧の顔ぶれでは原因を切り分けられない。注文した停止(`--fault-hang`)
  では dump を撮らない(原因が判っている停止に数百 MB を払わない)。**どちらの診断にも天井がある**
  (`verify::look::bounded` — 一覧 / dump のプロセスは天井で終了させて待ってから次へ進む。stdout は pipe でなく
  ファイルなので、診断が残した孫が何を握っていても答えは exit の時点で戻る)ので、
  `could not be listed — the listing ran out of time after Ns and was ended` / `no dump: the dumper ran
  out of time` は「診断が止まった」の意味で、アプリの回収と報告はその後も進む。`could not be ended` と
  pid が付く行だけは診断プロセスが残っている可能性を言う。**dump は `MiniDumpWriteDump` を PowerShell の
  `Add-Type` から直接呼ぶ**(`verify::look::DUMP_SCRIPT`)。`rundll32 comsvcs.dll,MiniDump … full` は
  この Windows(11 / 26200、2026-09-13 実測)では**使えない**: header の flags は full memory を名乗るのに
  WS 80 MB のアプリで 0.1 MB(stack だけ)、しかも ACL が SYSTEM / Administrators だけで撮った本人が
  開けない(owner なので `icacls <file> /grant <自分>:F` で戻せはする)。直接呼ぶと同じアプリで 224.5 MB /
  1.1 秒、ACL は普通。単体テスト `a_dump_of_a_standing_process_is_written_and_readable` が ping の
  full dump を撮って「1 MB 超・owner が開ける」を毎回確かめる
- **`> qt-tearing-down ` の駅**(2026-09-13)— `hub-down` と `exiting` の間で `QApp` を落とす区間。ここで
  止まる trail は Qt の破棄(engine / application の destructor)の中で、`exiting` で止まる trail とは
  別の答え

**この経路が止まった run でも働くことは、故障注入で確認する**(`cargo xtask wedge-check`。
gate は `gate::plan::record_of_a_wedge` の 7 ファイルに触れた時に選ぶ。host のみ・4 本で 30 秒弱 + ビルド。
**deadline スレッド無しの 2 本は、trail に注文した駅が出た時点で親が刈る**(`verify::child::ordered_hold`。判定は
`HELD AT <駅>`、天井は駅に届かなかった run だけが払う backstop)ので動詞 1 本ぶんの数秒で終わり、スレッド有りの 1 本だけが
天井 + スレッド自身の 10 秒を払う。**時間を完了の証拠にしない**の型 — 以前は天井 + 親の猶予 20 秒を 2 本が払い、
代役の一覧の天井 15 秒がその上に乗っていた)。
4 つの形を実際に作って読み返す: **`exiting` で握ったまま deadline スレッド無し**
(= 終わらない run と同じ、`wedge.txt` の無い形。本物のスレッド一覧が答えたこと(` alive — `)まで要求する — 見出しだけを
要求すると、一覧が返らなくても緑になる)/ **`exiting` で握ってスレッド有り**

取るプロセスを、答えない代役に差し替える。代役は永遠に答えないので天井の高さは検証の対象でなく、故障専用の短い天井
(`verify::look::STALLED_LOOK_CEILING`)で終了させて待ってから
`could not be listed — the listing ran out of time after Ns and was ended` と言い、その後もアプリの回収

途中で刈った `app.dmp` は消す)。**「動くはず」で済ませず、4 つとも親が実際に読めることを毎回確かめる**。
