# メモリ消費量と操作応答の改善計画

作成: 2026-08-30。調査対象: `55aaac83`。
既存の性能記録が対象とする `c6128f19` から、この時点の `crates/` に差分はない。

**最初に直すのは計測の成立条件。その後、保持元と待ち時間の内訳を特定して修正する。**
以前の対策を繰り返す、Qt 全体を原因と決める、表示件数を減らして予算内にする、という順には進めない。

今回は計画作成のためのコード・履歴・既存実測・依存ソースの調査であり、
アプリの実装変更、新規の実機性能計測、ヒープトレースは行っていない。
以下の「コードで確認」と「実測が必要」を混同しないこと。

## 1. 今回分かったことと、既存記録の限界

### 1.1 予算と観測値

[既存実測](../ci/baseline/perf-windows-x64.md) は Windows / Kotlin 228,526 commits・
54,272 refs・既定 2,000 commits の窓で、WorkingSet 406.0–417.8MB、
詳細往復 46–155ms。現行予算は 300MB / 操作応答 100ms / 起動 3s / スクロール 60fps。

ただし、この観測値の意味を次節で修正する必要がある。
**メモリの超過が消えたわけではないが、「可視グラフを操作した費用」としては再計測が必要。**
従来値を基準にした不足は約 110MB で、数 MB の改善だけを積んでも足りない。
必要削減量は計測修正後の値から改めて算出する。

`perf/report.rs::mb` は bytes を `1024 * 1024` で割るため、既存の MB 表記は実質 MiB。
当面は比較可能性のため同じ単位・300 の閾値を維持し、新しいログでは bytes と MiB を併記する。
単位の付け替えを改善として数えない。

### 1.2 計測を先に直す具体的な理由

| 発見 | 根拠 | 計画への影響 |
|---|---|---|
| 既定のスクロールベンチは、diff を表示し、非表示のグラフを動かす経路になっている | `RepoPage.qml:2156` の自動処理が最初の diff を開く。`openDiff:1375` が `diffShown=true`、`centreStack:2263` は index 1 の DiffPane を表示する。一方 `PagePerfDriver.qml:106` は graph の `contentY` を動かし、表示復帰しない | 今の fps を可視グラフの 60fps 達成証拠にしない。メモリ増分も hidden/visible を分けて撮り直す |
| `--no-select` は「選択処理なし」ではない | `perf.rs:248` は自動選択フラグを付けないだけ。`RepoPage.qml:1918` の `trySelectDefault` は通常の HEAD 選択を行い、stats / refs の通知から呼ばれる | 「開くだけ」と「選択を追加」の差には、選択する時点・対象・diff の有無が混ざる。さらに no-select 側の完了条件は詳細完了を待たない |
| 詳細の計時がUI反映前に終了する | `DetailsModel::request` で開始、`qobject.rs:113` 付近で到着を記録した後、文字列・ファイル木の作成、reset、changed を行う | 46–155ms は request→drain 到着。入力待ち・モデル反映・QMLレイアウト・描画完了を含まない |
| 起動の計時も初回描画前に終了する | `GraphModel::take_chunk` は `to_row_item` とモデル挿入の前に `graph first chunk` を記録し、`perf.rs::read_app` がそれを終了点にする | 初回表示 3s の非回帰確認にも、画面に出たフレームとの対応が必要 |

非表示グラフの件はコードと Qt の仕様からの判断。
[StackLayout の公式仕様](https://doc.qt.io/qt-6.10/qml-qtquick-layouts-stacklayout.html) は
`currentIndex` に対応する子だけを表示する。実機の各 run の表示状態は未採取なので、
最初の検証でスクロール開始時・中間・終了時の状態と画像を保存して確定する。
過去の数値を削除したり、違う条件の数値に読み替えたりはしない。

### 1.3 メモリについて確定していないこと

- 同じ約 2,000 行の反復で頭打ちになることは、**その範囲では増え続けない**という証拠。
  新しい行・異なる文字列・別のファイル・タブ切替でも保持が増えない証拠ではない。
  行や文字列ごとのキャッシュ、未解放の native object、解放済みヒープの保持を区別する。
- `GlobalAlloc` の計数は Rust の割当要求を数える。
  `WorkingSet - rust_live` は Qt の生存ヒープではない。ヒープ管理領域、解放済み領域、
  C/C++ 側の確保、スタック、DLL/ファイルの常駐ページ、GPU 関連領域などが混在する。
  ソース diff では tree-sitter 等の native 確保も対象に入る。
- subject を定数化して −74MB、Canvas を描かず −42.6MB という過去の切り分けは有用。
  ただし共有キャッシュや処理経路が変わるため、**独立した削減可能量として足せない**。
  所有者を見ていない段階で「文字列が74MBを保持」「Canvasの画像が42MB」と断定しない。
- 開く前の約145MBも、アプリのQMLオブジェクトを含む窓の総量。
  別日に測った最小 Qt ウィンドウとの差を引いて「変更不能な Qt の床」としない。
  Settings / Clone の Loader 化で既に床を減らせた記録もある。
- 名前付き Rust 常駐約17.2MBに対し、未帰属が約39.3MBある。
  小さい名前付き構造だけを見て「アプリ側は削り切った」と判断しない。

## 2. 完了条件を先に固定する

**既定 2,000 commits、表示・省略・punch・検索・git の意味を維持する。**
[実装計画 §9](実装計画.md) は操作応答に即時フィードバックを含める一方、
従来の baseline は詳細データ往復を100msで判定している。片方へのすり替えを防ぐため両方測る。

| 指標 | 測るものと判定 |
|---|---|
| 操作フィードバック | 実際の入力投入→選択・押下・読込中表示が反映されたフレーム。100ms以内 |
| 詳細表示 | 同じ入力→対象OIDのファイル一覧・本文が反映されたフレーム。従来シナリオでは100msを維持。request→dataも比較用に残す |
| 重いdiff・git書込 | 受付表示とキャンセル操作は100ms以内。処理完了は別指標とし、行表示・最終色付け・git完了を分ける。署名検証を詳細表示の待ちに足さない |
| スクロール | 可視グラフと可視diffを別に測る。平均fpsだけでなくフレーム間隔のp50/p95/p99/最大、16.7ms超・100ms超の件数も保存。60fpsを維持し長い停止を隠さない |
| 起動 | プロセス開始→グラフの先頭行が反映されたフレームで3s以内。初回チャンク時刻は内訳に降格 |
| メモリ | 出荷相当releaseで、正しい表示状態を通る一連の操作のアプリWorkingSet最大が300MiB以下。private bytes、操作後の値も必ず併記。子gitプロセスは別系列で測り、別プロセスへの付け替えを見落とさない |
| 長時間使用 | 同一範囲反復に加え、新しい履歴・ファイル・タブを通過しても、保持量が定義した上限へ収束する。セッション解放後の生存オブジェクト数・処理中要求数も戻る |

短い単発値・最小値では合格にしない。応答はシナリオごとに最低200操作を採り、
p50/p95/p99/最大と100ms超過率を報告する。これは原因探索の開始量であり、
稀な裾を保証するには追加サンプルが要る。**p95が緑でも予算超過を赤のまま記載する。**
同じコミットへの再クリックだけで水増しせず、複数の固定OIDへの移動を含める。

フレーム終了点は対象のrequest ID / OID / model generationと結び付ける。
無関係な `frameSwapped` を対象更新の完了と扱わない。これはアプリ内での描画完了の近似であり、
パネルの発光まで測った値ではない。OS入力待ちやpresentが疑わしい場合はOSトレースを重ねる。

## 3. 第1段階: 比較可能な計測にする〔最優先〕

対象: [xtask perf](../crates/xtask/src/perf.rs)、
[sampler](../crates/xtask/src/perf/sampler.rs)、
[PagePerfDriver](../crates/platitude-app/src/auto/PagePerfDriver.qml)、
[WindowPerfDriver](../crates/platitude-app/src/auto/WindowPerfDriver.qml)、
[RepoPage](../crates/platitude-app/src/ui/RepoPage.qml)。

### 実装すること

1. 自動化専用の選択方針を「なし / 通常の初期選択 / 指定OID」に分ける。
   選択なしでは `trySelectDefault` も抑止する。diff自動表示を選択と別の設定にする。
   通常起動の振る舞いは変えない。
2. ベンチを明示した段階で動かす: 空窓→repo open→指定OIDの詳細→指定ファイルdiff→
   graph表示復帰→可視graphスクロール→可視diffスクロール→解放・settle。
   段階別に新規プロセスでも測り、累積最大値の差だけで各段の費用を推定しない。
3. graphのベンチは `visible`、stackの現在項目、実際の行範囲、contentYの移動量を検証する。
   diffを閉じて再表示したフレームを待ってから開始する。diff閉鎖がデータを解放する現行仕様も記録する。
   開始・中間・終了の画像確認は専用の検証runで行い、撮影の負荷を性能runに混ぜない。
4. request ID付きの単調時計を用意し、入力、slot開始、タスク実行開始、spawn開始/終了、
   stdout完了、parse完了、feed投入、drain開始/終了、モデル通知、対応するフレームを記録する。
   QMLとRustの異なる時計を直接引かず、共通時計または同期イベントで結ぶ。
5. 操作中のgraph pass、refs/status読込、署名検証、diff色付けの実行数と、
   UI feedの深さ・推定bytes・待機時間・空drain回数を採取する。
   単一スレッドのCPU占有、ロック待ち、ディスク待ちも見る。総CPU6%だけでは競合を否定できない。
6. 最大値だけでなく時系列をファイルへ保存する。500msのRust内訳採取は `perf_done` 後の
   settle / 解放確認中も必要。100msのプロセスメモリ採取では短い峰を見逃すため、診断時は
   OSのpeak情報・割当イベントも照合する。ゼロ値・欠損・対象違いはbare-windowも含め失敗にする。
7. repoのHEAD・refs集合、変更状態、設定、選択OID/パス、features、バイナリのhash、
   Qt/qtbridge/git、OS、GPUアダプタ、driver、DPI、画面名・リフレッシュレート(Hz)、window位置と寸法、render backendをrunに記録する。
   `--no-build` でも出荷構成か計数構成か判別できるようにする。

### 再現性

- リフレッシュレートの異なるディスプレイが混在している。同じ画面・Hz・DPI・window寸法で比較し、
  移動や画面設定変更のあったrunは比較から外す。画面とHzが不明な既存fpsを回帰判定に使わず、
  差をコードやノイズのせいと先に決めない。`frameSwapped` は物理走査の完了を保証しない。
- 現行Kotlinの固定HEADを維持し、refs/作業ツリーも動かさない。fetchやmaintenanceの最中は別条件。
  ソースdiffは同じrepo内の別の固定OID/パスを指定し、基準HEADの変更で代用しない。
- 同一環境でA/Bを交互に実行し、順序を反転した組も採る。まず各6回以上、最初の起動を別記し、
  ウォーム比較とは分ける。小さい差がノイズと分離しなければ「効果未確認」とする。
- GPUの選択はログで確認する。Qtの
  [描画設定](https://doc.qt.io/qt-6.10/qtquick-visualcanvas-scenegraph-renderer.html) に従い、
  診断時にはbackendと `QT_D3D_ADAPTER_INDEX` を固定して環境差を分離する。
  固定条件での改善確認後、出荷時の自動選択でも再確認し、軽いGPU条件だけで合格にしない。
- 通常の出荷相当release、`memprobe`、詳細トレースの3構成を分ける。
  詳細トレースは原因説明用で、予算判定には使わない。プロファイラ自身の保持を削減量に数えない。

**完了条件:** 各runの「何が表示され、何が完了したか」がログと画像で一致する。
可視グラフの新baselineと、旧ハーネス条件の再現値を別に残す。
差がハーネス修正によるものか、アプリ修正によるものか追跡できる状態にする。

## 4. 第2段階: メモリの保持元を突き止める

### 4.1 ネイティブ側まで測る

WindowsではWPRのCPU/待機/ヒープ情報と、段階ごとのheap snapshotを主に使う。
この環境に `wpr.exe` はあるが、WPA・Qtの一致するシンボル・必要な権限は未確認。
[WPRのheap snapshot](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/record-heap-snapshot)
で確保元のスタックを比較し、生存確保と解放済み領域の保持を分ける。
収集開始前の割当にはスタックがないため、起動の床と操作中の増分は収集開始点も分ける。
ヒープで説明できない差は、mapped image、private region、スタック、GPU関連の内訳へ進む。

対象は自分が起動したPIDに限定する。既存の他人のトレースを停止せず、
exe名に対する恒久的なIFEO設定を既定手順にしない。設定を使った場合は終了時に戻す。
追加インストールやOS設定変更が必要なら、その具体的範囲が判明した時点で扱う。
ログはローカルへ保存し、環境変数や認証情報、不要な本文を記録・外部送信しない。

QML Profilerはbinding・JS・生成数の補助には使えるが、
[Memory UsageはJS側の計測](https://doc.qt.io/qtcreator/creator-qml-performance-monitor.html) であり、
C++ヒープの答えにはならない。接続用debug/profiling機能は出荷物へ入れず、
プロジェクトの通信制約を満たす接続方法を確認してから使う。利用できなくてもWPRと局所カウンタで進める。

### 4.2 原因を区別する実験

| 実験 | 区別するもの | 記録・採用判断 |
|---|---|---|
| 同じ行の4周 / 新しい行を順次読む / 同じ件数で別の文字列へ置換 | 再利用できる一時領域、行ごとの保持、文字列・glyphごとの保持 | visible delegate数と独立して増えるnativeの確保スタックを特定 |
| subject通常/定数 × Canvas通常/no-op の2×2 | 各処理の寄与と両者の相互作用 | 合計値を足さず、4条件の差と保持者を比較。無描画版は診断専用 |
| 同じ文字集合・同じ長さで異なるsubject / 多言語subject / 同一subject | 文字列数・text shaping・font fallback・model role変換 | Qt text、font、QString/QVariant、delegate modelのどこが増えるかを見る |
| CutNameを表示せずroleだけ読む / 固定幅で測定だけ行う / 通常表示 | データ変換、全文計測・省略処理、描画の分離 | 常駐量に加え、1更新当たりrelayout回数・測定回数・総確保bytesを比較 |
| 可視/非表示graph、横パンなし/あり、レーン数・DPIの違い | Canvas寸法、画像、texture転送、見えない項目の更新 | 実際のCanvas幅×高さ×DPR²×4と個数を算出。画像とGPU資源の複数実体は別計上 |
| 割当avatarなし/多数、行を再利用、割当画像を変更 | Canvasが画像URLごとに保持するキャッシュ | `loadImage`と`unloadImage`の対応、画像数・decoded bytesの上限を確認 |
| 100/500/1,000/2,000行、さらに手動追加 | 行数と無関係な床、行数・履歴依存の増分 | 既定値を変えず診断だけで傾きを測る。2,000行の合否とは別 |
| graph→diff→graph、タブA→B→A、タブclose、最後のrepo close | ページ、セッション、feed、native resourceの寿命 | Rustのdrop・nativeの生存量・private bytes・WorkingSetを同時記録 |

`GraphLaneCell.qml:88` は画像URLを読み込み、同じCanvasを再利用するが、現状この経路に
`unloadImage` はない。公式に
[Canvas画像の明示的なunloadがある](https://doc.qt.io/qt-6.10/qml-qtquick-canvas.html)
ため調査対象にする。ただし**avatarを割り当てていない基準runの超過原因とは断定しない**。
横パン時に `fullWidth` のCanvasになる経路も、既定のスクロールとは別条件で調べる。

Rust側は `session::heap_report` の未計上保持者を追加して、共有Arcの同じ確保は重複計上しない。
特に `lex_cache`、diff/source/marks、読込中のrefs、feed内容、処理中タスクの保持を確認する。
計数で分かる要求サイズとOSヒープの実消費量は別欄にする。

**完了条件:** 大きい増分について「どのスタックが確保し、何が生存させ、いつ解放されるか」が
少なくとも1つの再現ケースで説明できる。分類できない差は未帰属として残す。
計測開始点やシンボル不足で説明できないまま、割当方式や描画方式を全面変更しない。

## 5. 第3段階: 操作応答の修正を、確定した構造から進める

### 5.1 最新の選択だけを完遂する〔正しさを含む優先項目〕

コードで確認できる流れは次のとおり。

`load_details` / 署名要求 → `spawn_read` → セッション共通の `root_cancel` → git。
選択を変えただけでは古い要求を止めない。
diffも `load_diff` でepochを進めるが、raw diff / source / previewは共通cancelで動く。
色付けの開始前後ではepochを確認するものの、開始済みのblocking処理はそのまま走る。
`DiffModel::clear` は表示保持を消すだけで、coreの要求キャンセルを行わない。

さらに `BridgeSink` の詳細は `push_replace`、`DetailsModel::drain` は最後の到着だけを取り、
OIDが違えば捨てる。**Aを選択→Bを選択→Bの完了→Aの完了→UI drain**という順序なら、
Bの答えがAに上書きされ、Bを待つloadingが残る可能性がある。
これはコード上の成立経路であり、今回UIで再現試験した不具合ではない。

実装順:

1. A/B完了順をbarrierで制御する再現テストを先に作る。古い成功・古い失敗の双方を試す。
   A→B→Aも含め、OIDだけで新旧を判断できないことを確認する。
2. 詳細・diff・署名に要求世代を持たせ、core→feed→モデルまで同じ世代を運ぶ。
   最新選択の成功/失敗が、古い完了により失われない契約にする。
3. 古いreadをキャンセルし、起動前の要求を最新へ集約する。
   UIスレッドはchild停止を待たない。readごとの実行数と待機数に上限を置く。
   graph、poll、書込キューのcancelとは分離し、選択変更で書込を止めない。
4. diff閉鎖・タブ切替で不要なsource/preview/colour要求も無効化する。
   blocking色付けは実行同時数と待機要求数を制限し、可能な境界で世代を確認する。
   単に結果を捨てるだけでは、既に確保したメモリやCPUは節約できない。
5. 連打を減速させる固定長debounceは既定の解決策にしない。
   受付は即時、完遂する高コストreadを最新にする。

主な対象: [session/query.rs](../crates/platitude-core/src/session/query.rs)、
[session/repo_session.rs](../crates/platitude-core/src/session/repo_session.rs)、
[hub/sink.rs](../crates/platitude-app/src/hub/sink.rs)、
[details/qobject.rs](../crates/platitude-app/src/models/details/qobject.rs)、diffモデル。

### 5.2 UIスレッドの一括仕事を減らす

| 対象・確定した構造 | 計測で確かめること | 修正方針 |
|---|---|---|
| `Feed::push/push_replace` が毎回wake、`drain` が待機分を全回収 | 空drain数、Qtイベント待ち、1回のdrain時間、pending bytes | wakeを集約し、1回の適用量を制限。空→非空の競合と再通知のlost wakeをテストする |
| `GraphModel::take_chunk/replace_walk` がUI側で全行encode、差分比較 | chunk/replaceと遅い選択の重なり、encodeとQt通知の内訳 | Rustのプレーンな描画用データを背景側で準備し、世代付きで適用。QObject・QVariant・UI状態へ背景側から触らない |
| `GraphModel::set_find` がキーごとに全行走査、matches用の一時Vecを作る | 2,000行および追加読込後の入力遅延・確保数 | 検索用の共有snapshotとquery世代を使う背景処理。現行検索規則と順序を維持し、全行deep cloneをキーごとに作らない |
| clickで `stashRefOf`、一部の着地で `rowOf` が全行探索 | 多く読み込んだ場合の入力経路への寄与 | 既知rowを渡すかOID索引を更新時に作る。世代更新・stash消失・行の移動との整合性を保つ |
| diff初回整形と色更新で全patchをflatten、色更新は全行通知 | ソースdiffで初回表示後の停止、markup確保量、role再評価 | 初回行・色付け行の整形を背景側へ。必要な範囲とroleだけ更新し、選択・スクロール・fingerprintを保持する |

feedは種類ごとに扱う。refs/statusのsnapshotは最新化できるが、graphのStarted/Chunk/Finishedを
無差別に捨ててはいけない。古い世代を破棄する場合も開始と完了の契約を保つ。
backpressureを入れるなら、sessionロック保持中のsink呼出をブロックしない設計にする。
workerへ移しただけでキューの中に何世代も複製を保持するとメモリが増えるため、bytes上限も検証する。

特に `session/walk.rs::emit_rows` はsharedロックを持ったままsinkへ送る。
**encodeを単純に `BridgeSink::event` の中へ移すだけでは、ロック保持とstdout処理を長くする。**
ロック外の準備工程、または順序を保つ有界の準備workerへ分ける。
chunkごとの無制限spawnにはせず、avatar・refs等の入力snapshotが途中更新された場合の世代も扱う。
旧LogRow・準備済み行・現在のモデルが同時に存在する峰をA/Bの対象に含める。

UI適用時間の内部目安は1回数msから始め、実測したframe budgetへ合わせる。
通知回数を増やしすぎて総費用が悪化しないよう、適用量と待機時間を同時に見る。

### 5.3 git・背景処理との競合は内訳を見て選ぶ

同じOIDを、アイドル / tag込みwalk中 / refs更新中 / status更新中 / 色付け中 / 連続選択中で読む。
spawnが長いのか、git本体が長いのか、UIが受け取れないのかを分ける。

- UI待ちなら5.2を優先する。gitを並列化しても解決しない。
- 古い要求の多重実行なら5.1を優先する。
- git本体/起動との資源競合なら、対話的なreadを優先し、背景readの同時数を調整する。
  正しさに必要なpollを落とさず、遅らせた更新が最終的に完了することを検証する。
- 詳細の再訪でgitの費用が支配的な場合だけ、bytes上限付きの小さなキャッシュを検討する。
  表示結果はmailmapや設定にも依存するので、OIDだけの永久キャッシュにはしない。
  新規OIDの遅延を改善したようには報告しない。

[非同期化の候補](非同期化の候補.md) のrefs分割やstatus変更は自動採用しない。
`status -uall`を省いて件数の意味を変える案は仕様判断を伴い、今回の前提には置かない。

## 6. 第4段階: メモリ改善は保持元に対応した変更を選ぶ

| 証拠で支配的だったもの | 最初に試す変更 | 採用しない条件 |
|---|---|---|
| 古いread、queue内の複数世代、source/patchの重複 | 5.1/5.2の要求制御・共有所有・寿命短縮 | 待ち時間または常駐量が他方へ移っただけ |
| CutNameの測定・変換に伴う大量の一時確保 | 同一状態のrelayoutを集約し、可視項目の結果だけ再利用。text/幅/font/DPI変更時の無効化を明示 | native保持量も遅延も有意に変わらない。全履歴分のlayout cacheを増やすだけ |
| Qt delegate/modelが訪問行ごとのデータを保持 | 本文等の不要なrole供給を絞る、可視範囲との境界や解放タイミングを見直す | hover/検索の規則を失う、スクロールごとにgitを起動する、bridge全置換が先行する |
| Canvas画像・大きなsurface・texture | 古い画像のunload、保持URL数の上限、可視幅での描画と座標変換、不要な更新の抑制 | punch・AA・クリップ・横パンの結果が変わる。可視graphで転送/描画時間が悪化 |
| 生存確保は減るがOSのprivate領域が戻らない | 大きな一時確保を避ける・再利用単位を小さく固定する。native側の確保頻度とsize classを減らす | WorkingSetを強制trimしただけ、ページフォールト増で応答が悪化、別指標で増量 |
| ウィンドウの未使用object tree | 未使用の大きいペイン/ダイアログの遅延生成。破棄する状態と残す編集状態を分離 | 初回操作が100msを超える、編集内容や読んでいた位置を失う |

文字列とCanvasを小さく改善するだけで約110MBを削れるとは約束しない。
各案は同じ可視シナリオでA/Bし、**測定ノイズを越える差、所有者の説明、機能維持**が揃ったものだけ採用する。
大きな作り直しの前に、対象カテゴリ全体を除去したときの実測上限を取り、
現在の不足額に対して十分な余地があるか判断する。

### 最初から繰り返さないもの

- Rust allocatorのmimalloc化、`gc()`、atlas縮小、`Canvas.Immediate`、
  CutNameの二分探索、Canvasを二つから一つへまとめる案は過去の結果を再利用する。
  [P3の実験記録](P3-確認事項.md) にある対策を、未実装の案として再提案しない。
- exe/同梱文法のサイズ削減を常駐メモリの削減とみなさない。
- Shape全面化を先に選ばない。既存の `destination-out` と同等な合成が必要。
- 既定行数を減らす、メモリ予算を緩める、software描画に固定することで合格にしない。

過去に効果なしでも、今回特定した保持元・可視状態が異なる場合は、その違いを明示して再実験できる。
「計測がおかしかったから全部やり直す」という無制限な再試行にはしない。

### 検証シナリオ

- 空窓、空repo、既定Kotlin、初期walk中と定常状態。
- 複数OIDのマウス/キーボード選択、検索入力、refジャンプ、diff開閉、列幅変更・横パン。
- 非ソース小diff、Kotlinなど対応ソース、フォールバック対象、長い行、大きいdiff、画像preview。
- 固定範囲4周と未訪問範囲、追加読込、2つの大きいrepoのタブ切替・閉鎖。
  1つのセッションしか保持しない設計でも、native cacheや終了前のタスクが戻るか実測する。
- poll/refs更新/色付けと操作が重なる場合。操作を止めた後に正しい最新状態へ収束すること。

正しさのテストはタイミングの偶然に頼らず、開始・停止・世代の通知とbarrierで組む。
性能の100ms判定を機能テストの短いtimeoutに転用しない。
同期変更ではlost wake、閉じた後の応答、同じOIDへの再訪、失敗時のloading解除を含める。
UI変更は既存verify-uiのWindows/Linux同一動詞とPNG確認を使い、検索位置・選択・
省略端・顔のpunch・stash/WIP・ハイライト到着後の位置を確認する。
実装はworktree座席で行い、段2を完了させる。実機のないOSの性能達成は主張しない。

### この範囲で300MiBに届かない場合

P3後に「残る常駐のカテゴリ」「そのカテゴリの除去上限」「代替の保守費用」を並べる。
Qt/qtbridge由来の保持なら、最小再現と一致する版で依存修正・版変更の効果を確認する。
その先のcustom描画/CXX-Qt、Qtカスタムビルドは、狭い試作の結果を得てから別の判断にする。
ブリッジ移行だけでtextやGPUの保持が減るとは仮定しない。

依存追加・版変更、C++混在、意匠/トークン変更、既定行数や予算の変更は、
現行規約上の判断を伴う。必要になった場合に、具体案・実測効果・維持費をまとめて承認対象にする。
それまでは現在の構成と仕様で進める。
Qtカスタムビルドの既存検討は [P5 §14](P5-確認事項.md) を参照するが、
同項の古い絶対値や「削り切った」という結論を今回の開始条件にはしない。

到達の報告では、実装した一覧よりも、**同条件の削減量、遅い操作の内訳の変化、
まだ超過するケース、再現手順**を先に示す。
