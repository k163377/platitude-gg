# メモリ消費量と操作応答の改善計画

各段は前段の根拠の上に積む — 対策の繰り返し・Qt を原因と決める・表示件数を減らす順には進めない。
**判定に使う数字は [実測記録](../ci/baseline/perf-windows-x64.md)
が正本**(本書は方針だけ)。

`perf/report.rs::mb` は bytes を `1024 * 1024` で割るため、既存の MB 表記は実質 MiB。
当面は比較可能性のため同じ単位・300 の閾値を維持する。
改善に数えるのは実消費の減少だけ。

## 2. 完了条件を先に固定する

**既定 2,000 commits、表示・省略・punch・検索・git の意味を維持する。**
[実装計画 §9](実装計画.md) は操作応答に即時フィードバックを含める。

| 指標 | 測るものと判定 |
|---|---|
| 操作フィードバック | 実際の入力投入→選択・押下・読込中表示が反映されたフレーム。100ms以内 |
| 重いdiff・git書込 | 受付表示とキャンセル操作は100ms以内。処理完了は別指標とし、行表示・最終色付け・git完了を分ける |
| メモリ | 子gitプロセスは別系列で測り、別プロセスへの付け替えを見落とさない |
| 長時間使用 | 同一範囲反復に加え、新しい履歴・ファイル・タブを通過しても、保持量が定義した上限へ収束する。セッション解放後の生存オブジェクト数・処理中要求数も戻る |

## 5. 第3段階: 操作応答の修正を、確定した構造から進める

### 5.1 最新の選択だけを完遂する

diffは `load_diff` でepochを進めるが、raw diff / source / previewは共通cancelで動く。
色付けの開始前後ではepochを確認するものの、開始済みのblocking処理はそのまま走る。
`DiffModel::clear` は表示保持を消すだけで、coreの要求キャンセルを行わない。

実装順:

1. 古いreadをキャンセルし、起動前の要求を最新へ集約する。
   child停止は背景で待つ。readごとの実行数と待機数に上限を置く。
   graph、poll、書込キューのcancelとは分離する(書込は選択をまたぐ)。
2. diff閉鎖・タブ切替で不要なsource/preview/colour要求も無効化する。
   blocking色付けは実行同時数と待機要求数を制限し、可能な境界で世代を確認する。
   単に結果を捨てるだけでは、既に確保したメモリやCPUは節約できない。
3. 連打への答えは受付の即時化。
   完遂する高コストreadを最新のものにする。

### 5.2 UIスレッドの一括仕事を減らす

| 対象・確定した構造 | 計測で確かめること | 修正方針 |
|---|---|---|
| `Feed::push/push_replace` が毎回wake、`drain` が待機分を全回収 | 空drain数、Qtイベント待ち、1回のdrain時間、pending bytes | wakeを集約し、1回の適用量を制限。空→非空の競合と再通知のlost wakeをテストする |
| `GraphModel::set_find` がキーごとに全行走査 | 2,000行および追加読込後の入力遅延・確保数 | 検索用の共有snapshotとquery世代を使う背景処理。現行検索規則と順序を維持し、全行deep cloneをキーごとに作らない |
| diff初回整形と色更新で全patchをflatten、色更新は全行通知 | ソースdiffで初回表示後の停止、markup確保量、role再評価 | 初回行・色付け行の整形を背景側へ。必要な範囲とroleだけ更新し、選択・スクロール・fingerprintを保持する |

`GraphModel::take_chunk/replace_walk` のUI側encodeは [非同期化の候補](非同期化の候補.md) §1。

feedは種類ごとに扱う。refs/statusのsnapshotは最新化でき、graphのStarted/Chunk/Finishedは
順序ごと通す。古い世代を破棄する場合も開始と完了の契約を保つ。
backpressureを入れるなら、sessionロック保持中のsink呼出は即座に返る設計にする。
workerへ移しただけでキューの中に何世代も複製を保持するとメモリが増えるため、bytes上限も検証する。

UI適用時間の内部目安は1回数msから始め、実測したframe budgetへ合わせる。
適用量と待機時間は同時に見て、総費用で判断する。

### 5.3 git・背景処理との競合は内訳を見て選ぶ

同じOIDを、アイドル / tag込みwalk中 / refs更新中 / status更新中 / 色付け中 / 連続選択中で読む。
spawnが長いのか、git本体が長いのか、UIが受け取れないのかを分ける。

- UI待ちなら5.2を優先する。gitを並列化しても解決しない。
- 古い要求の多重実行なら5.1を優先する。
- 詳細の再訪でgitの費用が支配的な場合だけ、bytes上限付きの小さなキャッシュを検討する。
  表示結果はmailmapや設定にも依存するので、鍵はOIDとそれらの組。
  改善として報告するのは再訪の分だけ。

[非同期化の候補](非同期化の候補.md) のrefs分割やstatus変更は内訳で選ぶ。

## 6. 第4段階: メモリ改善は保持元に対応した変更を選ぶ

| 証拠で支配的だったもの | 最初に試す変更 | 採用しない条件 |
|---|---|---|
| 古いread、queue内の複数世代、source/patchの重複 | 5.1/5.2の要求制御・共有所有・寿命短縮 | 待ち時間または常駐量が他方へ移っただけ |
| Qt delegate/modelが訪問行ごとのデータを保持 | 本文等の不要なrole供給を絞る、可視範囲との境界や解放タイミングを見直す | hover/検索の規則を失う、スクロールごとにgitを起動する、bridge全置換が先行する |
| 生存確保は減るがOSのprivate領域が戻らない | 大きな一時確保を避ける・再利用単位を小さく固定する。native側の確保頻度とsize classを減らす | WorkingSetを強制trimしただけ、ページフォールト増で応答が悪化、別指標で増量 |
| ウィンドウの未使用object tree | 未使用の大きいペイン/ダイアログの遅延生成。破棄する状態と残す編集状態を分離 | 初回操作が100msを超える、編集内容や読んでいた位置を失う |

各案は同じ可視シナリオでA/Bし、**測定ノイズを越える差、所有者の説明、機能維持**が揃ったものだけ採用する。
大きな作り直しの前に、対象カテゴリ全体を除去したときの実測上限を取り、
現在の不足額に対して十分な余地があるか判断する。

QML Profilerはbinding・JS・生成数の補助には使えるが、
[Memory UsageはJS側の計測](https://doc.qt.io/qtcreator/creator-qml-performance-monitor.html) であり、
C++ヒープの答えにはならない。接続用debug/profiling機能は開発ビルドだけ、
プロジェクトの通信制約を満たす接続方法を確認してから使う。

### 最初から繰り返さないもの

[P3の実験記録](P3-確認事項.md) の結果がそのまま判断の根拠。
再試行は違いを示せた案に限る。

## 7. 実施順と出口

| 順序 | 成果物 | 次へ進む条件 |
|---|---|---|
| P2 要求制御とUI経路 | 最新要求の完遂、必要なUI仕事の分割 | 連続操作でも最終選択が必ず着地し、古い仕事・queueが有界 |
| P3 支配的メモリ項の削減 | 1変更ごとのA/Bと所有者の減量記録 | メモリ削減が応答・描画・仕様の退行を伴わない |
| P4 全体検証 | 長時間・多タブ・ソースdiffを含む実測、Windows/LinuxのUI確認、更新した記録 | 予算と機能ゲートを満たす。未達なら残額と残因を報告 |

### 検証シナリオ

- 複数OIDのマウス/キーボード選択、検索入力、refジャンプ、diff開閉、列幅変更・横パン。
- 未訪問範囲、追加読込、2つの大きいrepoのタブ切替・閉鎖。
  1つのセッションしか保持しない設計でも、native cacheや終了前のタスクが戻るか実測する。
- poll/refs更新/色付けと操作が重なる場合。操作を止めた後に正しい最新状態へ収束すること。

同期変更ではlost wake、閉じた後の応答、同じOIDへの再訪、失敗時のloading解除を含める。
UI変更は検索位置・選択・省略端・顔のpunch・stash/WIP・ハイライト到着後の位置を確認する。

### この範囲で300MiBに届かない場合

P3後に「残る常駐のカテゴリ」「そのカテゴリの除去上限」「代替の保守費用」を並べる。
Qt/qtbridge由来の保持なら、最小再現と一致する版で依存修正・版変更の効果を確認する。
その先のcustom描画/CXX-Qt、Qtカスタムビルドは、狭い試作の結果を得てから別の判断にする。

依存追加・版変更、C++混在、意匠/トークン変更、既定行数や予算の変更は、
現行規約上の判断を伴う。必要になった場合に、具体案・実測効果・維持費をまとめて承認対象にする。
Qtカスタムビルドの既存検討は [P5 §14](P5-確認事項.md) を参照するが、
開始条件は今回の実測から作る。

到達の報告では、実装した一覧よりも、**同条件の削減量、遅い操作の内訳の変化、
まだ超過するケース、再現手順**を先に示す。
