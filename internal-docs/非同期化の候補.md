# 非同期化・並列化の候補

**未着手の提案だけを置く。**

計測環境は `JetBrains/kotlin`、Windows x64、ウォームキャッシュ、3 回の最小値。

## 1. UI スレッドでのグラフ行の組み立て(効果: 中 / 難度: 中)

**現状**: `GraphModel::drain` の `to_row_item`(`encode::lanes_of` /
`chips_of` / `mates_of` と文字列の clone)が Qt メインスレッドで走る。walk のチャンクごとに
入る。

**提案**: 行の組み立てを tokio 側へ移し、メインスレッドは
出来上がった Vec を差し替えるだけにする。行の型を app 側の共有型に切り出す
必要がある。

`session/walk.rs::emit_rows` はsharedロックを持ったままsinkへ送る。
**encodeはロック外の準備工程、または順序を保つ有界の準備workerへ分ける。**
`BridgeSink::event` の中へ移すとロック保持とstdout処理が伸びる。
spawnはchunk数に上限を持たせ、avatar・refs等の入力snapshotが途中更新された場合の世代も扱う。
旧LogRow・準備済み行・現在のモデルが同時に存在する峰をA/Bの対象に含める。

サイドバーの側は対象外 — `NavSectionModel` は届いたものを持って
`data(index, role)` で答えるので、組み立てる行が無い。

## 2. `for-each-ref` の名前空間割りと `publish_status` の直列(効果: 小 / 難度: 小)

**現状**: `publish_refs` の読みは実質 `for-each-ref` 1 本。
`publish_status` 側は `status::load` と `opstate::detect` が直列(互いに独立)。

**提案**: `publish_status` の 2 本を `tokio::join!` する。`for-each-ref` は
名前空間ごとに割って並列に撃つ(パースは名前空間を見て振り分けているので、
3 本の出力を連結しても結果は同じ)。並列に撃てば上限は `refs/tags` 単独の 226ms(現状 304ms)=
78ms 短くなる。タグが支配的なのは `%(creatordate:unix)` が注釈付きタグのオブジェクトを読ませるため。

**効果が小さい理由**: ポーリング 1 tick では refs 側と status 側が
既に並走しており、status の `-uall` が長い方を決めているので、
**refs 側を詰めても tick の実時間は変わらない**。効くのは refs だけを読む経路
(`refresh_refs` = リモートタグの読みの後)と、開いた直後の `refresh_quick`
(ここは起動→初回表示の予算に乗る)。

## 3. ポーリングの支配項は `status -uall`(効果: 大 / 難度: 大・仕様判断)

**現状**: tick のコストはほぼこれ 1 本で決まる([poll-cost](../ci/baseline/poll-cost-windows-x64.md))。
`-uall` は hunk / 行ステージングと未追跡ファイルの件数表示に要る。

**提案(要仕様判断)**: 見出しの件数と WIP 一覧で読みを分ける。
最前面タブで WIP ペインが開いている間だけ `-uall` を撃つ、等。
**未追跡の件数が「ディレクトリ 1 件」に畳まれる**ので、見出しの数字の意味が
変わる = デザイン規約の判断が要る。着手はその判断の後。

## 4. `git log` のストリームがパースと行の組み立てを同じコールバックで回す(効果: 中 / 難度: 中)

**現状**: `RepoSession::stream_log` の `run_streaming` コールバックが、その場で
`sift_batch` → `make_row`(レーン割当)→ `sink.event` まで走る。その間 git の
stdout パイプは読まれない。

**提案**: パース(バイト → `CommitMeta`)と行の組み立て(`GraphBuilder`)を
チャネルで分ける。**レーン割当は順序に依存する**ので並列化はできない —
分けられるのは「git を読み続ける」ことだけ。

## 見送った案

- **refs / status のポーリングをタブごとに別スレッドへ**: 既に tokio の
  マルチスレッドランタイム上で spawn されており、直列化しているのは
  `poll_slot` の permit(意図的 — 遅いリポジトリはポーリング間隔が自然に伸びる)
- **リモートタグの索引(`remote_tag_index`)の構築を別タスクへ**: fetch の
  たびに 1 度だけなので、隔離する意味が無い
- **グラフの walk の並列化**: レーン割当が順序に依存する以上、
  walk を割っても合流で同じ順序に戻す必要がある
