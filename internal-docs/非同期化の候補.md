# 非同期化・並列化の候補

**着手していない提案だけを置く。** 実測済みの基準値は [ci/baseline/](../ci/baseline/)、
既に決まっている並行構造(書き込みキュー・ポーリングの permit・2 段ストリーミング)は
[.claude/rules/core.md](../.claude/rules/core.md) が正本。

計測環境は `JetBrains/kotlin`(コミット 226,973 / refs 53,614 = タグ 45,782 +
リモートブランチ 7,831 / ワーキングツリー 64,000 ファイル級)、Windows x64、
ウォームキャッシュ、3 回の最小値。

## 1. UI スレッドでの行の組み立て(効果: 大 / 難度: 中)

**現状**: `NavSectionModel::drain` は `RefsSnapshot` を受け取ってから `NavItem` の
Vec を組み立て、`reset_unnotified` がそれをもう 1 度 `items` へ複製する。どちらも
Qt メインスレッド。`GraphModel::drain` の `to_row_item`(`encode_geometry` /
`encode_labels` / 文字列 4 本)も同じ場所。

refs が実際に動いた時だけになった(スナップショットが同一なら
`Arc::ptr_eq` で降りる)ので**アイドル中のコストは無い**が、fetch やコミットの
直後は tags セクションだけで 45,782 行 ×(構築 + 複製)を 1 スロットの中で回す。
参考値: `RefsSnapshot`(45,782 タグ)の deep clone が 1 本 5ms、`NavItem` は
文字列 8 本なのでこれより重い。

**提案**: セクションごとの行の組み立てを `BridgeSink`(tokio 側)へ移し、
メインスレッドは出来上がった Vec を差し替えるだけにする。`Feed<Vec<NavItem>>` に
なるので `NavItem` を app 側の共有型に切り出す必要がある。

**注意**: `reset_unnotified` の `all` → `items` の複製は**フィルタと折り畳みの
都合**で残る。ここを消すには `items` を「`all` への添字」にする必要があり、
デリゲートが読むロールの経路が変わる。分けて考えること。

## 2. `publish_refs` の 3 本の読みが直列(効果: 小 / 難度: 小)

**現状**: `refs::load` → `refs::head_state`(2 spawn)→ `remote::list` を順に
await している。互いに独立。

| コマンド | 実測 |
|---|---|
| `for-each-ref`(refs::load) | 308 ms |
| `symbolic-ref -q --short HEAD` | 16 ms |
| `rev-parse --verify -q HEAD` | 16 ms |
| `config --get-regexp '^remote\..*\.url$'` | 13 ms |
| **直列の合計** | **353 ms** |
| `tokio::join!` した場合の上限 | 308 ms |

**提案**: 3 本を `tokio::join!` する。`publish_status` 側も `status::load` と
`opstate::detect` が直列。

さらに `for-each-ref` 自体も名前空間ごとに割れる(パースは名前空間を見て
振り分けているので、3 本の出力を連結しても結果は同じ):

| 撃ち方 | 実測 |
|---|---|
| 3 名前空間まとめて(現状) | 304 ms |
| `refs/tags` だけ | 226 ms |
| `refs/remotes` だけ | 118 ms |
| `refs/heads` だけ | 17 ms |

並列に撃てば上限は 226ms = **78ms 短くなる**。タグが支配的なのは
`%(creatordate:unix)` が注釈付きタグのオブジェクトを読ませるため。

**効果が小さい理由を先に書いておく**: ポーリング 1 tick では refs 側と status 側が
既に並走しており、status の `-uall`(下記)が 710ms で長い方を決めているので、
**refs 側を詰めても tick の実時間は変わらない**。効くのは refs だけを読む経路
(`refresh_refs` = リモートタグの読みの後)と、開いた直後の `refresh_quick`
(ここは起動→初回表示の予算に乗る)。

## 3. ポーリングの支配項は `status -uall`(効果: 大 / 難度: 大・仕様判断)

**現状**: 710 ms。tick のコストはほぼこれ 1 本で決まる([poll-cost](../ci/baseline/poll-cost-windows-x64.md))。
`-uall` は hunk / 行ステージングと未追跡ファイルの件数表示に要る。

**提案(要仕様判断)**: 見出しの件数と WIP 一覧で読みを分ける。
最前面タブで WIP ペインが閉じている間は `-uall` を撃たない、等。
**未追跡の件数が「ディレクトリ 1 件」に畳まれる**ので、見出しの数字の意味が
変わる = デザイン規約の判断が要る。安易に入れないこと。

## 4. `git log` のストリームがパースと行の組み立てを同じコールバックで回す(効果: 中 / 難度: 中)

**現状**: `RepoSession::stream_log` の `run_streaming` コールバックが、その場で
`sift_batch` → `make_row`(レーン割当)→ `sink.event` まで走る。その間 git の
stdout パイプは読まれない。

**提案**: パース(バイト → `CommitMeta`)と行の組み立て(`GraphBuilder`)を
チャネルで分ける。**レーン割当は順序に依存する**ので並列化はできない —
分けられるのは「git を待たせない」ことだけ。

## 5. `sent_rows` が配信済みの行をもう 1 部持つ(効果: 小 / 難度: 小)

**現状**: `emit_rows` は組み立てた行を `shared.sent_rows` へ clone し、同じものを
イベントで送る。ウィンドウ 2,000 行ぶんの二重持ち。`sent_rows` は
「バックグラウンド再構築が同じ絵かどうか」を見るためだけに在る。

**提案**: 行を `Arc<LogRow>` にするか、`sent_rows` を行そのものではなく
**指紋**(ハッシュ)にする。後者なら比較が O(n) のまま持ち物がゼロになるが、
`apply_refs` がチップの差し替えを `sent_rows` へ書き戻している経路
(`session::apply_refs` 末尾)を作り直す必要がある。

## 見送った案

- **refs / status のポーリングをタブごとに別スレッドへ**: 既に tokio の
  マルチスレッドランタイム上で spawn されており、直列化しているのは
  `poll_slot` の permit(意図的 — 遅いリポジトリはポーリング間隔が自然に伸びる)
- **リモートタグの索引(`remote_tag_index`)の構築を別タスクへ**: fetch の
  たびに 1 度だけ(45,782 名で 19ms)になったので、隔離する意味が無い
- **グラフの `--topo-order` walk の並列化**: レーン割当が順序に依存する以上、
  walk を割っても合流で同じ順序に戻す必要がある。2 段ストリーミングで
  「速い絵を先に出す」形が既に答え
