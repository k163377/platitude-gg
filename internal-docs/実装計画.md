# 実装計画(MVP)

**進捗の正本は [CLAUDE.md](../CLAUDE.md) 現在のフェーズ。** 達成済みの Phase は本書から落としてある — 何が配線済みかは [.claude/rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md) が正。
**節番号はコードとドキュメントから参照される固定アンカー**なので、節を削っても残る節の番号はそのまま(欠番が出るのは正常)。

## 1. 前提と基本方針

- **製品の狙い**:「インストール済み git の CLI を実行するだけの薄い GUI」に徹し、git 操作そのもののUXだけに投資する。
- **スコープ外**:forge API の直接利用(PR判定はgitのref経由)/ 内蔵conflictエディタ(外部ツールへ委譲)/ git の操作の Undo / Redo(Ctrl+Z。失った物は破棄記録から復元する)。**Intel Mac非対応**は [CLAUDE.md](../CLAUDE.md) 冒頭。
- **pull はスコープ内**(ユーザー決定)。**走らせるのは `git pull` 1 本**で、統合の仕方(`pull.rebase` / `pull.ff`)も素の pull の行き先も git の設定が決める — アプリが fetch と merge を組むと、同じリポジトリの端末と違う答えを返す実装が 2 つになる(意匠は [デザイン規約.md](デザイン規約.md) §リモートから取り込む の pull の項)。
- **ゴール**:必須要望の全充足 = **Phase 5完了**(v1.0相当)。
- **常に動く状態で縦に積む**:各Phaseの終わりに「起動して使えるアプリ」が存在する。自分自身の開発はこのアプリで行う(dogfooding)。
- **Windows単独開発への対応**:
  1. 実装と手動検証はWindows先行。コードは最初からクロスプラットフォームを意識する(パス・プロセス生成・改行の扱いを`platitude-core`に閉じ込める)。
  2. GitHub ActionsでWindows / Ubuntu / macOS(arm64)の3OSビルド+テストを回す(初回実行はP5)。
  3. mac / Ubuntuの**実機GUI検証**はPhase 5の検証ゲートにまとめる(内容は§8)。

## 2. アーキテクチャ(正本は分割先)

- bridge層は「coreの結果をQMLへ写すだけ」に保ち、**Qt Bridges → CXX-Qt乗り換え時に書き直す範囲をこの層に閉じ込める**(QML資産とcoreは流用)。
- gitはUIスレッドの外で走る。書き込みはセッション単位で直列化する — 順序が意味を持つので**キュー**。1リポジトリ=1セッションでタブは多重化する。グラフはレーン形状をRust側で前計算し、**UI側は届いた形を描くだけ**。

## 7. Phase 4 の残り:リモート自動追従と全状態可視化

- **ブランチ状態バッジへの「PR中」判定の接続**(**ローカルのみ / リモートあり(PR無し)/ リモートあり(PR中)**の3状態完成)
  - PR判定:fetchサイクル時に`git ls-remote origin "refs/pull/*/head" "refs/merge-requests/*/head"`でPR先端SHA表を取得し、各ブランチ先端と突合(refだけで判定する原則を維持)
  - マージ済み判定:pruneによるリモートブランチ削除の検知を主とし、可能ならancestry判定を併用
- **破棄記録と復元**(実装済み。正本は [破棄記録仕様.md](破棄記録仕様.md)):破壊的な操作が失わせた物を、git の reflog と PGG 自身の記録からリポジトリで 1 本の一覧に出し、選ぶとグラフに仮表示し、追加の操作として復元する。reflog ベースの操作履歴ビューと到達不能コミットの表示・復旧はこれへ吸収した
- **UI の入口だけが無い設定**(値はファイル経由で効いている):
  - ネットワークタイムアウト(`[defaults] network_timeout_secs`)— 設定ダイアログに数値入力を足すだけ。`Hub::set_auto_fetch_minutes` と同じ形の slot と、`settings::Defaults` への書き戻しが要る

**設定はマシン単位で持つ**(ユーザー決定)。auto fetch の間隔もネットワークタイムアウトも「このマシンがどれだけ回線へ手を伸ばすか」の答えなので、マシンに 1 つ。**リポジトリ単位で変わるのは状態だけ** — リモートが 1 本も無い / 続けて失敗して止まった、の 2 つで、どちらもセッションが持つ。git が既にリポジトリ毎に憶えているもの(identity・merge ツール)はそのリポジトリの config に置いたままにする。

## 8. Phase 5:仕上げ・クロスプラットフォーム・配布(=必須要望コンプリート)

- diff強化:unified / side-by-side 切り替え(**実装済み**。シンタックスハイライトも実装済み)
- 性能総仕上げ:基準リポジトリで性能要件4項目を再計測し改善。必要なら`git commit-graph write --reachable`を任意実行できる設定を提供(リポジトリへの書き込みになるため既定は手動)
- 配布:
  - Windows:`windeployqt` → zip(コード署名なしから開始)
  - macOS(arm64):`macdeployqt` → dmg / zip
  - Ubuntu:依存同梱のtar.gz(AppImage化は様子を見て検討)
  - **LGPL遵守**:Qtは動的リンク、ライセンス文書の同梱、Qtライブラリ差し替え可能性の説明をREADMEに記載
- **ネットワーク非通信の証明(§11)**:Qt のカスタムビルドで Qt6Network を配布物から外せた後に、リリースworkflowへ配布物の検査(同梱一覧の許可リスト照合+全バイナリの import 検査)を組み込み、`actions/attest-build-provenance`でprovenanceを発行。SECURITY.md(主張の明文化・CIチェックへのリンク・Verify it yourself手順)を整備する。カスタムビルドが立つまでは見送り
- **mac / Ubuntu実機検証ゲート**:日本語IME(特にmac)・グラフ描画・配布物の起動を実機確認。実機が用意できない間はpre-release運用
- GitHub Releasesへv0.xとして公開

検証・判断待ちの積みは [P5-確認事項.md](P5-確認事項.md)。

## 10. テスト戦略

- **platitude-core単体テスト**:レーン割当はエッジケース(octopus merge・orphanブランチ等)を重点的に
- **統合テスト**:3OSのCIで実行し、実機のないmac / Linuxの挙動差(パス・改行・git出力差)を早期検出する
- **テストはマシンの外へ出ない**:リモートは`file://`のローカルbareで、fetch / push / clone もローカルで完結させる(答えが回線と相手の状態に左右されない)
- **性能テスト**:基準リポジトリでの計測手順(ci/baseline の各記録が再現コマンドを持つ)
- **GUI検証**:ヘッドレスは verify-ui スキル。実機ゲート(IME・conflictフロー等)はPhase 5

## 11. ネットワーク非通信の証明(全Phase横断)

**証明する主張**:配布物(実行ファイルと、同梱するライブラリ・プラグインの全部)のコードに、git をサブプロセスとして起こす以外に通信する経路が無い(git の認証・プロキシも git の設定に従い、アプリは関与しない)。配布物の外から来る経路は §11.6。

**証明は配布物そのものの静的検査で立てる。実行時の観測は採らない** — 通信を遮断した中でテストを通す・CI の job の通信を見張る、のどちらも、言えるのは「観測した経路で通信しなかった」までで、バイナリに経路が無いことは示さない(job を見張る道具が見るのはビルドとテストの通信で、配布物ではない)。

| 層 | 主張 | 手段 | 状態 |
|---|---|---|---|
| ① 依存(§11.1) | 依存閉包に通信の crate が入らず、自コードがソケット型を使わない | cargo-deny bans・clippy disallowed-types | 済(deny.toml / clippy.toml) |
| ② 配布物(§11.2) | 同梱する全バイナリに通信の経路が無い | 同梱一覧の許可リスト照合・全バイナリの import 検査 | **Qt のカスタムビルドまで見送り** |
| ③ 由来(§11.4) | 配布物は ② を通った公開ソースから作られた | actions/attest-build-provenance(SLSA provenance) | ② の後 |

### 11.1 依存閉包に通信能力がないこと(静的)

- 導入済み — 通信系crate(+ libgit2 / gitoxide)の名指し禁止は `deny.toml`(cargo-deny bans)、自コードでの`std::net`ソケット型の禁止は `clippy.toml` の `disallowed-types`(`Cargo.toml` の `[workspace.lints.clippy]` が deny にするので、机の clippy でも効く)。リストの正本は各ファイル
- **証明ではなく、書いた時点で止める網**。crate 名の拒否リストは名前を知っている物しか止めず、std と tokio(`process` が mio の `net` を有効にする)はソケットの型を持ったまま — 経路が無いことを示すのは ②

### 11.2 配布物に通信の経路が無いこと(成果物の検査)

- **前提は Qt6Network を配布物から外すこと = Qt のカスタムビルド**。既定ビルドの Qt では Qt6Qml と Qt6Quick が Qt6Network をハードインポートし(P0 実測:[ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))、QML の XMLHttpRequest も持つので、配布物に経路が残る。どれも Qt の feature `qml-network` が入れている(qtdeclarative 6.12.0 の `src/qml` / `src/quick` の `CMakeLists.txt` と `src/qml/configure.cmake`)ので、`-no-feature-qml-network` で組んだ Qt([P5-確認事項.md](P5-確認事項.md) §14)で外れる。**それまで ② の検査は組まない**(ユーザー了承 2026-10-06)
- 見送りの間も、通信系のプラグイン(tls / networkinformation)と QML デバッガ(qmltooling。`qmldbg_tcp` が TCP で待ち受ける)は同梱しない — mac は `cargo xtask package` が組んだ bundle を許可リスト(`crates/xtask/src/package/contents.rs`)とちょうど突き合わせ、どれも入らない。Windows / Linux の配布物を組む手順も同じ形にする
- 検査(カスタムビルドの後、リリース workflow に組む):
  - **同梱一覧の許可リスト照合** — Qt6Network・通信系のプラグイン・QML デバッガが入っていないこと
  - **全バイナリの import 検査** — 同梱する実行ファイル・ライブラリ・プラグインの全部の import を読み(Windows `dumpbin /imports` / Linux `objdump -T` / macOS `nm -u`)、ネットワークへ出るソケットを作る入口と、内部でソケットを使う OS の HTTP・名前解決の API を import する物が無いこと。**ライブラリ名では判定しない** — Windows の Qt6Core は WS2_32 を import し(P0 実測)、Linux / mac のソケット API は libc / libSystem の中にある。**ローカルの IPC にも使う入口は呼び手を読んで判定する** — tokio の signal driver(Unix)は AF_UNIX しか作れない `socketpair` を使う。Qt6Core が WS2_32 から引く関数が通信の API でないかは、カスタムビルドの時に関数単位で読む

### 11.4 配布物の由来証明(provenance)

- リリースworkflowで`actions/attest-build-provenance`によりSLSA provenanceを発行。署名はSigstore透明性ログに記録される(改ざん不能な第三者記録)ため、監査者は以下だけで「② の検査を含む公開workflowがビルドした成果物」であることを暗号学的に検証できる:

```bash
gh attestation verify platitude-gg-win64.zip --repo <owner>/platitude-gg
```

### 11.5 監査者向けパッケージング(SECURITY.md)

- SECURITY.mdに (1) 上記主張の明文化、(2) 各CIチェックへのリンク、(3) **「Verify it yourself」節**を整備し、「手元で再現できるコマンド一覧」の形にする:
  - §11.2 と同じ道具で、配布物の全バイナリの import を自分で読む
  - `gh attestation verify`で由来検証
- 公開リポジトリのCIログ自体が公開証拠であり、フォークすれば誰でも同一の検証を再実行できることを明記する

### 11.6 論理構成上の限界(SECURITY.mdにも正直に明記する)

- import 検査が見るのは、ロード時に結ぶ API まで。実行時に名前で引く読み込み(`LoadLibrary` + `GetProcAddress` / `dlopen` + `dlsym`)と直のシステムコールは import に出ない。Qt はプラグインを名前で読むので、読む先を配布物の中に閉じる(許可リストと `qt.conf`。利用者が環境変数 `QT_PLUGIN_PATH` で足す探索先は配布物の外)
- import 検査は、起こす子プロセスが何かを区別しない — アプリが起こすのは git(platitude-core の `GitExecutor`)と、再起動する自分自身(platitude-app の `main.rs`)だけで、これはコードで示す
- 配布物の外の経路は主張の外: OS がプロセスに読み込む部品(ネイティブのファイルダイアログのシェル拡張・IME など)と、ネットワーク上のファイルシステムに置いたリポジトリ(ファイル I/O を OS が通信にする)
- gitそのものは通信する(それが仕様)

## 14. Post-MVPバックログ(追加要望・未確定事項)

1. コミット検索 / フィルタ(メッセージ・作者・SHA・パス)— `git log`の各種フィルタをそのまま使う(基本検索は実装済み — 残りはアドバンス検索。[P3-確認事項.md](P3-確認事項.md))
