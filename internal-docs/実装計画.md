# 実装計画(MVP)

**進捗の正本は [CLAUDE.md](../CLAUDE.md) 現在のフェーズ。** 達成済みの Phase は本書から落としてある — 何が配線済みかは [.claude/rules-refs/app-ui.md](../.claude/rules-refs/app-ui.md) が正。
**節番号はコードとドキュメントから参照される固定アンカー**なので、節を削っても残る節の番号はそのまま(欠番が出るのは正常)。

## 1. 前提と基本方針

- **製品の狙い**:「インストール済み git の CLI を実行するだけの薄い GUI」に徹し、git 操作そのもののUXだけに投資する。
- **スコープ外**:forge API の直接利用(PR判定はgitのref経由)/ 内蔵conflictエディタ(外部ツールへ委譲)。**Intel Mac非対応**は [CLAUDE.md](../CLAUDE.md) 冒頭。
- **pull はスコープ内**(ユーザー決定)。**走らせるのは `git pull` 1 本**で、統合の仕方(`pull.rebase` / `pull.ff`)も素の pull の行き先も git の設定が決める — アプリが fetch と merge を組むと、同じリポジトリの端末と違う答えを返す実装が 2 つになる(意匠は [デザイン規約.md](デザイン規約.md) §リモートから取り込む の pull の項)。
- **ゴール**:必須要望の全充足 = **Phase 5完了**(v1.0相当)。
- **常に動く状態で縦に積む**:各Phaseの終わりに「起動して使えるアプリ」が存在する。自分自身の開発はこのアプリで行う(dogfooding)。
- **Windows単独開発への対応**:
  1. 実装と手動検証はWindows先行。コードは最初からクロスプラットフォームを意識する(パス・プロセス生成・改行の扱いを`platitude-core`に閉じ込める)。
  2. GitHub ActionsでWindows / Ubuntu / macOS(arm64)の3OSビルド+テストを回す(初回実行はP5)。
  3. mac / Ubuntuの**実機GUI検証**はPhase 5の検証ゲートにまとめる(内容は§8)。

## 2. アーキテクチャ(正本は分割先)

- bridge層は「coreの結果をQMLへ写すだけ」に保ち、**Qt Bridges → CXX-Qt乗り換え時に書き直す範囲をこの層に閉じ込める**(QML資産とcoreは流用)。
- gitはUIスレッドの外で走る。書き込みはセッション単位で直列化する — 順序が意味を持つので**キュー**。1リポジトリ=1セッションでタブは多重化する。グラフはレーン形状をRust側で前計算し、**UI側は届いた形を描くだけ**。

## 7. Phase 4 の残り:リモート自動追従と全状態可視化

- **ブランチ状態バッジへの「PR中」判定の接続**(**ローカルのみ / リモートあり(PR無し)/ リモートあり(PR中)**の3状態完成)
  - PR判定:fetchサイクル時に`git ls-remote origin "refs/pull/*/head" "refs/merge-requests/*/head"`でPR先端SHA表を取得し、各ブランチ先端と突合(refだけで判定する原則を維持)
  - マージ済み判定:pruneによるリモートブランチ削除の検知を主とし、可能ならancestry判定を併用
- **reflogベースの操作履歴ビュー**(`git reflog --format=...`。HEADおよび各ブランチ)
- **到達不能コミットの表示と復旧**:reflog由来のSHA集合のうち`git rev-list <集合> --not --all`で残るものを別色でグラフに表示し、「ここからブランチ作成」で復旧できるようにする
- **UI の入口だけが無い設定**(値はファイル経由で効いている):
  - ネットワークタイムアウト(`[defaults] network_timeout_secs`)— 設定ダイアログに数値入力を足すだけ。`Hub::set_auto_fetch_minutes` と同じ形の slot と、`settings::Defaults` への書き戻しが要る

**設定はマシン単位で持つ**(ユーザー決定)。auto fetch の間隔もネットワークタイムアウトも「このマシンがどれだけ回線へ手を伸ばすか」の答えなので、マシンに 1 つ。**リポジトリ単位で変わるのは状態だけ** — リモートが 1 本も無い / 続けて失敗して止まった、の 2 つで、どちらもセッションが持つ。git が既にリポジトリ毎に憶えているもの(identity・merge ツール)はそのリポジトリの config に置いたままにする。

## 8. Phase 5:仕上げ・クロスプラットフォーム・配布(=必須要望コンプリート)

- diff強化:unified / side-by-side 切り替え(**実装済み**。シンタックスハイライトも実装済み)
- 性能総仕上げ:基準リポジトリで性能要件4項目を再計測し改善。必要なら`git commit-graph write --reachable`を任意実行できる設定を提供(リポジトリへの書き込みになるため既定は手動)
- 配布:
  - Windows:`windeployqt` → zip(コード署名なしから開始)
  - macOS(arm64):`macdeployqt` → dmg / zip
  - Ubuntu:依存同梱のtar.gz(AppImage化は様子を見て検討)
  - **LGPL遵守**:Qtは動的リンク、ライセンス文書の同梱、Qtライブラリ差し替え可能性の説明をREADMEに記載
- **ネットワーク非通信証明の仕上げ(§11)**:リリースworkflowへ成果物スキャン(同梱Qtモジュールallowlist+import table baseline照合)を組み込み、`cargo auditable`でビルドし、`actions/attest-build-provenance`でprovenanceを発行。SECURITY.md(主張の明文化・CIチェックへのリンク・Verify it yourself手順)を整備する
- **mac / Ubuntu実機検証ゲート**:日本語IME(特にmac)・グラフ描画・配布物の起動を実機確認。実機が用意できない間はpre-release運用
- GitHub Releasesへv0.xとして公開

検証・判断待ちの積みは [P5-確認事項.md](P5-確認事項.md)。

## 9. 性能設計(全Phase横断)

| 要件 | 主な戦略 |
|---|---|
| 初回表示3秒以内 | logストリーミング+先頭チャンク即表示(全件パースを待たない)。ref列挙等は並行実行 |
| 操作応答100ms | git実行は全て非同期・UIは即時応答(進行中表示)。走行中コマンドのキャンセル機構 |
| スクロール60fps | リスト仮想化・行高固定・レーン形状のRust側前計算・モデル追記のバッチ化 |
| メモリ300MB以下 | コミットメタデータをRust側でコンパクトに保持(作者名等はintern)。メッセージ本文・diffは遅延取得。QMLへは表示範囲のみ供給 |

**メモリ300MBは提案値**で見直してよい(残る3項目は要件)。

計測は各PhaseのDone条件に組み込み、`cargo xtask corpus` の合成リポジトリで実測する(Windows機。他OSはPhase 5ゲートで確認)。

## 10. テスト戦略

- **platitude-core単体テスト**:レーン割当はエッジケース(octopus merge・orphanブランチ等)を重点的に
- **統合テスト**:3OSのCIで実行し、実機のないmac / Linuxの挙動差(パス・改行・git出力差)を早期検出する
- **オフライン担保**:統合テストと起動スモークはネットワーク遮断環境でも全件パスさせる(§11.3)
- **性能テスト**:基準リポジトリでの計測手順(ci/baseline の各記録が再現コマンドを持つ)
- **GUI検証**:ヘッドレスは verify-ui スキル。実機ゲート(IME・conflictフロー等)はPhase 5

## 11. ネットワーク非通信の証明(全Phase横断)

「git・GitHub以外の外部接続皆無」はCIで継続的に機械検証する。単一で完全な証明は存在しないため、**能力の不在(静的)と挙動の不在(動的)を層で積んで論証する**。

**証明する主張**:本アプリのプロセス自身は一切ソケットを開かない。ネットワークI/Oが発生するのは、ユーザーがインストール済みのgitをサブプロセスとして実行した場合のみ(認証・プロキシ等もgit側の設定に従い、アプリは関与しない)。

| 層 | 主張 | 手段 | 導入 |
|---|---|---|---|
| ① 依存 | 依存閉包に通信能力がない | cargo-deny bans・clippy disallowed-types | 済(deny.toml / clippy.toml) |
| ② 成果物 | 配布物に通信能力がない | Qtモジュールallowlist・import table baseline・cargo auditable | P0でbaseline実測済 / P5で照合をCI化 |
| ③ 挙動 | 実行時に通信しない | 完全オフラインテストjob・Harden-Runner(block mode) | workflow記述済(初回実行はP5) |
| ④ 由来 | 配布物は①〜③を通った公開ソースから作られた | actions/attest-build-provenance(SLSA provenance) | P5 |

### 11.1 依存閉包に通信能力がないこと(静的)

- 導入済み — 通信系crate(+ libgit2 / gitoxide)の名指し禁止は `deny.toml`(cargo-deny bans)、自コードでの`std::net`ソケット型の禁止は `clippy.toml` の `disallowed-types`(CIは`-D clippy::disallowed-types`付き)。リストの正本は各ファイル
- 残り(P5):`cargo tree`の出力をSECURITY.mdに掲示する(依存閉包の小ささを監査材料にする)

### 11.2 配布物に通信能力がないこと(成果物スキャン)

- **要のinvariantは「通信経路を持つのはgitだけ」**。Qt6Network自体はQt6Qmlのロード時依存のため**同梱は必須**(P0実測:[ci/baseline/windows-x64.md](../ci/baseline/windows-x64.md))。したがって主張は①アプリ実行ファイルのimport tableにQtNetwork・winhttp・wininet等の通信系がないこと、②ネットワーク系Qtプラグイン(tls / networkinformation等)を同梱から除外すること、③完全オフラインでの動作検証(§11.3)、の3点で構成する。QMLの`Image { source: "http://..." }`やXMLHttpRequestの経路は②と自コードのレビュー(qmllint も検討)で塞ぐ
- windeployqt / macdeployqt / Linux同梱物に対し、**同梱Qtモジュール・プラグイン一覧のallowlist照合**を`ci/`のスクリプトでリリースworkflowに組み込む
- **import table検査**:Windows `dumpbin /imports`、Linux `objdump -p`、macOS `otool -L`
  - **Phase 0で実測したbaselineをpinし、差分でfail**させる。Qt CoreがOSのsocket APIをリンクしている可能性があるので「ネットワーク系シンボルゼロ」は主張しない(QtNetwork・winhttp・wininet等の不在は明示的にassert)
- `cargo auditable`でビルドしてバイナリ自身に依存一覧を埋め込む → 監査者は配布物**単体**から`cargo audit bin`で中身のcrateを確認できる

### 11.3 実行時に通信しないこと(動的)

- **完全オフラインテストjob**(実体は ci.yml 内の `offline-test` ジョブ。CI の分割方針は [P5-確認事項.md](P5-確認事項.md) §3.5 が正):Linuxランナーの`docker run --network=none`(または`sudo unshare -n`)内で統合テスト全件+`QT_QPA_PLATFORM=offscreen`の起動スモークを実行
  - リモートは`file://`のローカルbareを基本とし、netns内の127.0.0.1に`git daemon`を立てて**fetch / push / auto-fetchのリモートプロトコル経路もネットワーク非依存で演習**する
- **Harden-Runner(step-security/harden-runner)をblock modeで全workflowに適用**(記述済み — 正本は workflow):
  - allowlist外への接続試行はjobで検知され、全egressが第三者(StepSecurity)のダッシュボードに記録として残る
  - jobごとに必要なendpoint(aqtinstall等)は最小限で追記する

### 11.4 配布物の由来証明(provenance)

- リリースworkflowで`actions/attest-build-provenance`によりSLSA provenanceを発行。署名はSigstore透明性ログに記録される(改ざん不能な第三者記録)ため、監査者は以下だけで「①〜③のチェックを含む公開workflowがビルドした成果物」であることを暗号学的に検証できる:

```bash
gh attestation verify platitude-gg-win64.zip --repo <owner>/platitude-gg
```

### 11.5 監査者向けパッケージング(SECURITY.md)

- SECURITY.mdに (1) 上記主張の明文化、(2) 各CIチェックへのリンク、(3) **「Verify it yourself」節**を整備し、「手元で再現できるコマンド一覧」の形にする:
  - `dumpbin /imports`(Win)/ `objdump -p`(Linux)/ `otool -L`(mac)でネットワークライブラリ不在を確認
  - `gh attestation verify`で由来検証、`cargo audit bin`で同梱依存の確認
  - `strace -f -e trace=network`等での実行時確認例
- 公開リポジトリのCIログ自体が公開証拠であり、フォークすれば誰でも同一の検証を再実行できることを明記する

### 11.6 論理構成上の限界(SECURITY.mdにも正直に明記する)

- 動的検査(§11.3)は「観測した範囲で通信ゼロ」しか言えず、静的検査(§11.1 / §11.2)はOS標準ライブラリ内部のシンボル(Linuxの`getaddrinfo`はlibc内)を判別できない
- gitそのものは通信する(それが仕様)。テストが`file://`リモートを使うのは「アプリ自身の通信」と「gitの通信」を切り分けて示すため

## 12. リスク(現存分のみ)

| リスク | 影響 | 対策                                                                                                               |
|---|---|--------------------------------------------------------------------------------------------------------------------|
| mac実機がない | mac品質を保証できない | CIビルド+テストで検証(初回実行はP5)。実機検証をPhase 5ゲート化し、それまでpre-release扱い                          |
| IME問題(mac) | コミット編集が実用不能 | macはゲートで確認し、問題時はQtの入力周り設定・バージョンで対処を調査                 |
| qtbridgeの破壊的変更 | 追従コスト | バージョン固定+意図したタイミングでのみ更新                                                                        |
| 巨大リポジトリでのメモリ超過 | 性能要件未達 | 実測は予算超過([ci/baseline/perf-windows-x64.md](../ci/baseline/perf-windows-x64.md))。残件と残る手は [P3-確認事項.md](P3-確認事項.md) §性能。多タブでの実測は未取得 — [P5-確認事項.md](P5-確認事項.md) §14(Qt カスタムビルド)と併せて計測する |
| Qt本体がOSのsocket API等をリンクしており、import table検査を「ゼロ」にできない | 非通信証明の説得力低下 | 「シンボルゼロ」は主張せずbaseline pin+QtNetwork不在を主軸に(§11.2)、動的検査(§11.3)で補完                         |
| 検証用外部サービス(Harden-Runner等)の停止・仕様変更 | CI停止・記録欠落 | 証明の本体は自前で完結するチェック(オフラインjob・成果物スキャン)に置き、Harden-Runnerは追加の第三者記録と位置付け |

## 14. Post-MVPバックログ(追加要望・未確定事項)

追加要望(Phase 5以降、優先度順の目安):

1. コミット検索 / フィルタ(メッセージ・作者・SHA・パス)— `git log`の各種フィルタをそのまま使う(基本検索は実装済み — 残りはアドバンス検索。[P3-確認事項.md](P3-確認事項.md))
2. 操作undo(reflogベース。Phase 4のreflog基盤の上に構築)
3. ファイル履歴・blame表示
4. 新バージョン通知(自リポジトリへの`git ls-remote --tags`。設定でオフ可。優先度低)

未確定事項と判断タイミング:

| 事項 | 判断タイミング |
|---|---|
| フォーカス時の即時fetchの有無(間隔既定は 1 分で確定済み) | Phase 4着手時 |
| 最近開いたリポジトリ一覧(タブ復元は実装済み) | dogfooding所感で優先度判断 |
| 複数リモート(origin / upstream) | Phase 4のPR判定設計時に考慮(初期はoriginのみ) |
| サイドバーの高度な検索・絞り込み(インクリメンタル絞り込みを超えるもの) | Phase 4以降(実使用感を見て) |
| キーボードショートカット | 段階導入(長押しのSpace / Enter・Ctrl+F等は導入済み) |
| submodule / LFS | 初期は存在表示のみ。要望が出たら拡張(worktreeは一覧・立ち位置の切り替えまで実装済み) |
| ファイル変更の自動検知(watcher / fsmonitor) | Phase 5以降(それまでは可視性ポーリングで代替 — rules-refs/core.md) |
