# レビュー観点

修正全体が本質的に正しいか・効果が確かかを、机上と実測の両面で見る。指摘は鵜呑みにせず木で確かめる。

## 進め方

- **読むだけの subagent にも読ませる** — 差分の固定 SHA とこのファイルのパスを渡す(結論ではなく差分)。観点 6 は依頼を見ているセッションが受け持つ
- **見る範囲は差分の行ではなく、触った単位の全体** — 関数・型・モジュール・doc コメント・呼び手・その挙動を語る文書

## 観点(この順で)

1. **一次資料** — 主張を該当版の一次資料(git / Qt / OS のソース)と突き合わせる
2. **テストの空振り** — 緑が変えた経路を通っているか(変更前のコード、またはその経路を外した形で赤になるか)
3. **削った所の回帰** — 消した分岐・呼び手・文言が担っていた物の行き先
4. **1 から組んだ想定** — 触った単位を今の役目で 1 から書いたらこの形になるか。部分の手直しで済ませた跡を拾う:
   - 名前(関数・引数・型・変数・テスト・ファイル)が今の役目を言っていない
   - 設計が今の役目に合っていない — 継ぎ足しの分岐・使われなくなった引数・意味の変わった戻り値・責務に合わない置き場
   - コメント・doc・文書に過程が残る — 「〜に変更」「以前は」「今回」・試した経緯・消した経緯への言及(理由付きの不採用は決定事項として残す)。コメントは現在形の制約と罠だけ(rules/code.md)、文書も今の事実だけ
   - コメント・doc・文書とコードの食い違い — 直した挙動の古い説明・改名した物の旧名

   直すのは本来有るべき形まで。移動は移動だけのコミットに、改名・変更はそれと別のコミットに(rules/structure.md §分割)
5. **規約** — CLAUDE.md・`.claude/rules`・`.claude/rules-refs` と、それらが正本として指す文書(デザイン規約.md・依存とライセンス.md 等)の該当項
6. **依頼との照合** — 依頼の各句と途中の訂正を満たしているか、頼まれていない範囲の変更が無いか(要る付随の修正は依頼の内)。レビューを頼む発話には `hook::review` が同じ観点を添える
