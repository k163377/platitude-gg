## git サブプロセス規約(各論)

- **`GIT_LITERAL_PATHSPECS` は使わない** — `git stash push -u` が成功を報告しながら untracked を stash しなくなる(実測)。パスは `:(literal)` で包む(`process::literal_pathspec`)。`--no-index` の引数は pathspec ではない
- `git merge --continue` / `git rebase --continue` は引数を受け付けない(`--no-edit` も不可)。`--no-edit` は cherry-pick / revert のみ
- **`git merge` の終了コードは 1 が両義**(実測 2.55: conflict = 1 / マージできない名前 = **1** / `--ff-only` の拒否 = 128 / 作業ツリーが上書きされる = 2)。rebase と違い 1 だけでは答えと失敗を分けられないので、**exit 1 の後に** `opstate::detect` で **merge が立っているか**を訊いて `integrate::Landing::{Done, Stopped}` を返す(`Stopped` は失敗ではない = `SessionEvent::WriteStopped` → エラー帯もログの持ち上げも出さない。2026-08-22 ユーザー報告)。**コードを読まずに marker だけ見ない** — 既に立っている merge の上で撃った merge は `MERGE_HEAD` を残したまま 128(実測 2.55: 未解決なら `unresolved conflict`、解決済みなら `You have not concluded your merge`)。**`--squash` の conflict だけはこの網に掛からない** — `SQUASH_MSG` を書いて `MERGE_HEAD` を作らないので失敗として出る(画面からは撃たない。網は `integrate_integration::merge`)
- **止まった merge を `git commit` で終わらせたものは `merge --continue` と同一**(実測 2.55: 木・2 つの親・メッセージ・走るフック `pre-commit` / `prepare-commit-msg` / `commit-msg` / `post-commit` まで一致。`post-merge` / `pre-merge-commit` はどちらでも走らない = 止まらずに済んだ merge のフック)。**解決結果が HEAD と同一でも書ける**(空のマージコミット)。だから画面は `--continue` の行を持たず commit ボタン 1 つで終わらせる(規約 §進行中の操作から出る)。箱に入れる文言は `conflict::stopped_message`(`MERGE_MSG` からコメント行を落とす — `commit::commit` は `--cleanup=whitespace` なので落とさないと `# Conflicts:` が記録される。`core.commentChar` を変えたリポジトリでは落ちないが、箱に見えているので消せる)。網は `integrate_integration::merge`
- **`git switch --merge` は使わない** — conflict しても exit 0 で `MERGE_HEAD` を作らず `merge --abort` が効かない上、staged が 1 つでもあると拒否(実測)。未コミット変更は stash → switch → `stash pop --index` で運ぶ(`session::carry_across`)
- **`git stash pop` の非ゼロは「無処理」を意味しない** — 作業ツリー conflict はマージ済み+stash 残置、staged 衝突は丸ごと拒否(`conflicts in index. Try without --index.` → `--index` 無しで再試行)。判定は exit code でなく unmerged の有無(実測)
- **終了コードを自分で読むコマンドには `answers_by_code(<答えのコード>)` を付ける** — 付けないとコマンドログが勝手に開く。対象は `switch` / `rebase` / `merge` / `cherry-pick` / `revert` / `stash pop` / `stash apply`(pop と同じ exit 1 = conflict で載った、の答え。`conflicts_now` の判定も pop と同型)/ `rev-parse refs/stash`(exit 1 = stash ゼロ本。持ったことのない全リポジトリが返す)/ **config の読み取りは `--get` / `--get-regexp` とも全部**(未設定 = exit 1 = 答え。identity / remote list / tracking branches / push plan の upstream / merge tool / autocrlf / mergetool.cmd — 網は `tests/it/config_reads.rs`)/ **HEAD の読み**(`symbolic-ref -q` = exit 1 が detached、`rev-parse --verify -q HEAD` = exit 1 が unborn。`refs::head_state` と `remote` の current_branch)/ untracked の `diff --no-index`(exit 1 = 差分あり = 常態)/ stash rename の移動確認 `rev-parse --verify` — 網は `tests/it/answer_reads.rs`。**`cat-file` には付けられない — 無い側は exit 128 で 0/1 の枠外、しかも「リポジトリが無い」も 128 なので枠を広げると本物の失敗が消える。読む前に `rev-parse --verify -q <spec>` で訊く**(無い側は全部 exit 1 = 答え、在る側は 0 + oid を stdout。unborn HEAD の `HEAD:` / added の `<parent>:` / index に無い `:0:` で実測 2.55。`preview::blob_is_there` が preview と source_text の両方の入口)。代償は git プロセス 1 本 = Windows で ~25ms(`cat-file` も `diff-tree` も同じ ~24ms でプロセス生成が支配的)。`cat-file --batch-check` なら exit 0 で "missing" を返せるが **stdin 必須で不可**(プロセス層は stdin を常に閉じる — `scratch.rs`)。失敗判定は書き込みの答え側(規約 §git が言ったことを読む場所)
- **答えのコードは 1 とは限らない** — `config --global --unset <key>`(merge editor を空にした時)は「元から無い」を **exit 5** で言う(ファイルが無い時・キーが無い時・multivalue で消せない時が全部 5、実測 2.55。multivalue は消さずに 5 なので「消えた」とは言い切れないが、直後の refresh が本当の値を出す)。1 で印を付けると失敗行になり、設定カードを閉じただけでコマンドパネルが開く(2026-08-21 ユーザー報告)。**枠を広げて 0/1/5 を全部答えにはしない** — 理由は `cat-file` の 128 と同じで、コードの意味はコマンドごと。網は `tests/it/integrate_integration/mergetool.rs`
- **`--autostash` はどこにも渡さない** — autostash の復帰は素の `stash apply` で staged が全部 unstaged になる(`--index` を渡す口が無い。実測)。carry は自前(`session::carry_across_rewrite`)、代償は `--continue` / `--abort` 後の自動復帰。止まった時は `pop` しない — unmerged のある index へ git は書かない(判定は `opstate::detect`)
- **止まった cherry-pick / revert も `Landing::Stopped`** — conflict は exit 1 + 自分の marker(`CHERRY_PICK_HEAD` / `REVERT_HEAD`。複数リビジョンなら sequencer も。実測 2.55)。判定は `integrate::landed` 1 か所で、**exit 1 かつ `InProgress::from_state` が自分と答えた時だけ**(止まった merge の上で撃った cherry-pick は marker が merge のもの)。**この網に掛かるのは conflict だけ** — 汚れた木・読めない名前・unmerged の残る index は全部 exit 128 で marker を残さず、**既に立っている同種の上で撃った時だけ 128 で自分の marker が在る**(実測 2.55 — だからコードを読まずに marker だけ見ると、git の「もう 1 つ動いている」という説明を握り潰す)。空で止まった側は先に `left_nothing_to_record` が拾うのでここへ来ない(着地は `Done` = 「何も起きなかった」)。網は `integrate_integration::pick_revert`
- **止まった rebase も同じ**(2026-08-22 ユーザー判断) — `RebaseOutcome::Stopped`。判定は `integrate::landed` 1 か所で、**exit 1 かつ `rebase-merge` / `rebase-apply` が立っている時だけ**。**コードを読まないと誤読する**: 「既に rebase-merge がある」失敗は marker を残したまま **exit 128**(実測 2.55。拒否と停止だけが 1、読めない upstream も 128)。拒否(`work_is_in_the_way`)を先に見るので carry は変わらない。`Blocked` があるので `Landing` には寄せられず、`build::rewrite_carrying` が carry の後に `Landing` へ落とす(拒否は画面に届かない = 回り直すのが答え)。`squash` / drop / reword も同じ 1 本を通るので 5 経路すべてが `WriteStopped` を出す。網は `integrate_integration::rebase` と `session_integration::carry_rewrite`
- **cherry-pick と revert は「空になった」の答え方が別**(実測 2.55・`integrate_integration`): cherry-pick は `CHERRY_PICK_HEAD` + stderr `The previous cherry-pick is now empty`、revert は `--allow-empty` が無く `nothing to commit` で拒まれ stderr 空・stdout に status。状態も 3 通り — cherry-pick は marker あり / 単体 revert は無し / 複数 revert は sequencer だけ(`opstate::detect` は None → `opstate::sequence_pending` を見ないと残骸を「きれい」と誤答)。判定は `integrate::left_nothing_to_record` / `still_stepping` の 2 か所だけ
- **元から空のコミットは `--allow-empty` で写す** — 付けないと「後から空になった」と同じ文言で止まり区別が付かない。`--empty=drop` は git 2.45 からで最低バージョン外
- **拒否の見分けは `integrate::work_is_in_the_way` の 1 か所** — 素の rebase と `--interactive` は同じ文言で拒む(実測 `integrate_integration`)ので carry も `integrate::RebaseOutcome` も 2 つに割らない。未追跡だけの木は拒まれない = stash も取らない
- **`session_integration::rewrite_route` は先頭一致で読む** — status refresh の `rev-parse --git-path rebase-merge/msgnum`(`conflict::rebase_progress`)が部分一致では 4 手目の `rebase` に化ける(実測)
- **`stash pop` の非ゼロを conflict と読めるのは元の tree に unmerged が無かった時だけ** — unmerged のある index へは丸ごと拒否(`needs merge`)で残る conflict は元のもの。`conflicts_now` だけ見ると無処理の pop が成功に化ける(実測。`session::stash_pop` の `settled_first`)
- **`rev-list --exclude` は名前空間を外して書く** — `--branches` に `refs/heads/` を付けると何も除外されず「他の誰かが掴んでいる」が常に真(エラーも警告も無し。実測)。`--tags` / `--remotes` も同様。`--glob` / `--all` だけ `refs/` 始まり
- **`--glob=<pattern>` は階層にしか当たらない** — `--glob=refs/stash` は 0 件(`refs/stash*` なら拾う。実測)。素の rev `refs/stash` は stash 無しで `fatal: ambiguous argument`、`--ignore-missing` は間違った oid も黙って捨てる = 安全側と逆。`reachable::command` は `--glob` を採る
- **`--all` で HEAD は外せない** — `--exclude=<現在のブランチ> --all` でも先端が negative に残る(実測)。外したい walk は `--branches --remotes` を並べる
- `git config <key> <value>` に `--` を付けない(`--` が値として保存される)。ダッシュ始まりの値はそのまま通る
- **`config --get-regexp` は低いレベル順・実効値は最後の行** — 1 件目で判定すると system が常に勝つ(Git for Windows は system に `core.autocrlf=true` を書く。実測)。単一キーは `--get`、複数キーは最後の出現で上書き読み。TestRepo が隔離するのは撃つ git だけで、コード側は開発機の system / global を見る
- **`core.autocrlf` の綴りは git の bool 語彙**(実測 2.55): `input` は大小無視で先に見る / true = `true` `yes` `on` と非ゼロの整数 / false = `false` `no` `off` `0` と**空の値** / 値なしのキー(`=` が無い)は true / それ以外は `fatal: bad boolean config value` で git が動かない。**読みは `None` に倒す**(`eol::setting::AutoCrlf::of_record`)— 「未設定」と同じ席で、設定画面はその 4 つ目の行しか選べないから。**警告(`eol::normalises`)と設定画面は同じ 1 本の読みを通る** — 2 通りに読むと「git が決めているか」に答えが 2 つできる
- **`core.autocrlf` の書きは 1 キーなので撃ち直さない**(identity の 2 連書きと違う)— ただし**先に読む**: `--unset` は無かった時も多値の時も exit 5 で、読んでおくと前者を撃たずに済む(`eol::setting::set`。`identity::local` と同じ理由)。スコープは `--global` / `--local` を必ず綴る(既定に頼らない)
- **identity(`user.name` / `user.email`)に独自バリデーションを足さない** — git が拒むのは空の name だけ(空 email は通り `<>` になる)。`<` `>` 改行は author 行から黙って落ち、config 書き込みは `\n` エスケープで注入は起きない(実測)
- **identity の 2 連書きは原子化できない**(実測: `git config` は 1 プロセス 1 キー・`--edit` はロックを取らない・自前 lock は config ライタ再実装・libgit2 は絶対制約で閉)— 書いた後に実効設定を読み直し、違えば 1 回だけ撃ち直す(`identity::set_identity`)。半端(新 name + 旧 email)は `Identity::is_complete()` 真で黙って居座る。競合でない失敗は何度でも同じ = 2 回で止める。不採用: 書く前に読んで失敗時に戻す(戻しが同じロックを踏む)
- **半端の再現は多値の `user.email`**(`identity_integration`)— `--add` 2 回のキーへの set は `cannot overwrite multiple values` で exit 5、隣の `user.name` は通る(実測)。`.git/config.lock` 先置きで両方不着地も作れる(読みはロック不要)
- **「そのリポジトリ自身が何を書いているか」は `--local` でしか読めない**(`config::get_regexp_local` / `identity::load_local`)— 実効レベルの `--get-regexp` は全レベルを低い順に返すだけで**どのファイルの record かを言わない**ので、継承しているだけの値と自分で書いた値が同じ姿で届く。書き戻しの読み直しも `--local` 側で読む(`identity::set_local_identity`)
- **`--local` の書き込みは「今の値を先に読んで、違うキーだけ撃つ」**(`identity::write_local_pair`)— 空欄 = `--unset` だが、**`--unset` の「元から無い」と「多値なので触れない」は同じ exit 5**(実測 git 2.55。git の doc は 5 と 6 に分かれると書いてあるが分かれない)ので、先に読まないと本物の失敗が無害な答えに化ける。ついでに「何も変えない Save」が git を 1 本も撃たなくなる(2026-08-21 の「無い物の unset がログを開く」報告と同じ形)。**`--local` は set 側にも明示する** — 素の `git config <key> <value>` / `--unset` も既定でローカルに書く(実測: global にしか無いキーの素の `--unset` は exit 5 で global を触らない)が、読む側と書く側が同じ語を名乗る形にしておく
- **署名の有無を `%G?` だけで判定しない** — SSH 署名は `gpg.ssh.allowedSignersFile` 未設定だと未署名と同じ `N`。存在は `cat-file commit` の `gpgsig` ヘッダで確認。署名パスフレーズは扱わない(agent の GUI pinentry 必須 — サブプロセスに端末が無い)
  - **`--format=` のどのプレースホルダでも見分けられない**(2026-08-11 実測 git 2.55): 未署名と ssh 署名済みで `%G?` `%GS` `%GK` `%GG` `%GF` `%GP` `%GT` が完全一致 — 1 コマンド化の道は無い
  - **先に `cat-file commit`、ヘッダ無しなら `Absent` で終わり**(`identity::verify_commit`)— 未署名は 1 プロセスで済み gpg / ssh-keygen を起動しない。`%G?` の `N` は「判定できなかった」と読む。プロセス数は `identity_integration` の observer テストが固定
- **`ls-files --eol` は worktree の実ファイルを読む** — グロブ渡しは基準リポジトリ級で数十秒(kotlin 全件 24.7s。実測)。候補列挙(索引のみ 85ms)と `--eol`(確定した数パスだけ 42ms)を必ず別コマンドに分ける。未チェックアウトは `w/` が空
- **改行コードの判定は patch の bytes から**(`eol::read`)— `ls-files --eol` は「今どう見えるか」で、どの行が新しいかは diff しか知らない。`--eol` は未追跡と近傍標本だけ
- **`diff --ignore-cr-at-eol` の patch は `apply` できない**(実測 `patch does not apply`)— 表示用と staging 用で diff の bytes を分けない不変条件(`details::file_diff_raw`)を壊すので使わない
- **worktree の diff は index 空間で出る** — `autocrlf=true` でも patch に CR は現れず `apply --cached` / `apply -R` が通る。index blob に CR があるファイルは変換されない = 設定切替で全ファイルが modified にはならない(実測)
- **`git mergetool` は `--no-prompt` だけでは stdin を踏む**(`conflict::mergetool`)— ツール未設定だと確認を stdin に出す(閉じていて失敗)ので `--tool=` 必須。`--gui` も必須(無いと `merge.guitool` と食い違う)。`mergetool.writeToTemp=true` を撃つ(既定は一時ファイルが隣に出て WIP ペインが untracked で埋まる)。`keepBackup` は触らない(`.orig` は利用者の安全網)。引数なしで撃たない(全衝突ファイルを順に開き書き込みキューが塞がる)。自前 `cmd` ツールは exit code を信用されず BACKUP の mtime 比較 — 保存せず閉じると「失敗」でマーカーが戻る
- **`mergetool --tool-help` は Windows で約 8 秒**(実測)— 書き込みキューに載せず・誰も待たせず・プロセスで 1 回だけ(`conflict::available_tools` の `OnceCell`)。`--gui` でも絞られず、端末ツール除外は説明文の `(requires a graphical session)` パースしかない(取れなければ候補ゼロ = 無害側)。自前定義は `config --get-regexp '^mergetool\..*\.cmd$'` が 34ms なので即出す

- **Windows ではプロセス 1 個が約 18ms — 対話の予算は本数で決まる**(実測 `git --version` warm 18.1ms)。行選択の詳細は `git show` 1 本にまとめる(`details::commit_details`。実測 25ms 対 直列 2 本 68ms)。`--diff-merges=first-parent` が要る(無いとマージのファイル一覧が空)。レコードと一覧の切れ目は NUL 10 個で決める(`split_record`)— 形で探すとメッセージ中の `M\tsrc/main.rs` が変更ファイル表に化ける。空コミットはレコード後ろに改行すら無い
- **`git diff-tree <p1> <c>` は `git show <c>` より遅い**(kotlin で 42ms 対 24ms。実測)— プランビング側が速いと決めてかからない

## セッション・実装の決定事項(各論)

- **メモリの内訳は `cargo xtask perf --breakdown` で出す**(推測しない)。取りこぼしは「残り」が膨らむ形で出るので総量は嘘にならない。実測記録は [ci/baseline/perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md)
- **refs に比例する名前は `crate::Name`(`compact_str`)で持つ** — 24 バイトまで inline(ref 名の実測平均 20.2 字)。app 側から型の名指しが要る形にしない(§core の API は純 Rust 型のみ)。**`Footprint` は `SmallVec` に明示 impl が要る** — 無いと `[T]` へ deref して溢れたバッファを数え落とす
- **バイト数より確保の個数が効く帯がある** — 305,213 個の削減が計数 −3.1MB なのに WorkingSet −12MB(差はヒープ管理領域 = 計数アロケータに見えない側)。`classes=` の**件数**を必ず見る
- **mimalloc は不採用(実測)** — WorkingSet +38〜55MB / private +83MB、環境変数で抑えても private +43MB。起動・応答に差なし。数字は [perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md) §アロケータと確保の個数
- **refs に比例する常駐データは「1 要素の器」を作らない**(タグ 45,901 本で実測): `BTreeMap` は 1 件でも 11 スロットのノード(43.5MB → `RemoteTagIndex` 6.5MB)/ `HashMap<K, Vec<V>>` は push 1 回で 4 スロット(20.5MB → `LabelIndex` 6.4MB)/ hex 40 字の `String` は 1 行 1 確保。`String` → `Vec<u8>` では 1 バイトも減らない — 減るのは表現を変えた時だけ
- **メモリ予算の約半分(`--no-open` 実測 143.6MB — ci/baseline/perf-windows-x64.md)は空リポジトリで既に埋まっている**(Rust ヒープは 1.2MB)。「全部 Qt」と読まない — Qt の床 84MB / 自前 QML シェル 32MB / ページ実体化 16MB(積み方は ci/baseline/perf-windows-x64.md)。software 描画は代替にならない — GPU −25MB だが 56fps で予算割れ(実測)

- interactive rebase は `GIT_SEQUENCE_EDITOR` に別実行ファイル `pg-todo-editor` を差す。**配布物に同梱必須**(本体と同じディレクトリ)
- **全行 `drop` のプランを拒むのは `--root` の時だけ**(`sequencer::rebase_interactive`)— `--root` は placeholder へ replay するので空 tree・空メッセージのコミットが残る(実測)。回避に範囲を 1 つ広げない — 下のマージが範囲に入り `plan_edit` が拒む
- **テストが差し込む実行ファイルは rename で置く** — Linux は write fd の下の exec が `ETXTBSY`(git ではなく `sh` が Text file busy を返し rebase 失敗に見える)。`session_integration` の replay 系 5 本が持ち回りで赤くなったらここ(実測: 24 スレッドで 8 回中 6 回赤 → `Once` + staging へ copy + `rename` publish で 0)
  - **`--test-threads` を下げて隠さない** — 4 なら通る(実測)が CI のコア数で戻る。Windows では出ない — `cargo xtask linux` でしか観測できない
  - `Once` は copy を 1 回にするためでなく**待たせる**ために要る(exec が copy 中に重ならない)。staging 名を使い回すなら Once と対 — でないと書きかけが publish される
  - **fork が継承した write fd は Once + rename では防げない**(子の `execve` まで隣の exec が `ETXTBSY`。実測 8 回中 1 回、fork〜execve 間 300ms 停止で 100%)。手当ては exec 側の `ETXTBSY` リトライ(`run_published_helper`)。リトライの締めは固定秒でなく `QUIET_BUDGET`(窓は他プロセスのスケジューリングの物で、壁時計の verdict は負荷が上回る)
  - **rename に負けた残置 helper はバイト一致の時だけ使う**(`publish_helper`)— 一致しない残置は古い helper を今日の assert の下で走らせるので、その場でエラーにする(Windows は実行中の exe も読める — 拒まれるのは書きと rename)
- **integration test の Git 環境は executor ごとに隔離する**(2026-08-16 Windows sandbox 実測: `~/.config/git/ignore` の permission warning が stderr に混ざり、nothing-to-commit / empty revert 3件が同時に赤)。`support::exec::isolated` は test-binary 固有の `GIT_CONFIG_GLOBAL` / `XDG_CONFIG_HOME` と `GIT_CONFIG_NOSYSTEM=1` を `GitExecutor::with_env` へ渡し、`TestRepo` の setup Git も同じく XDG を自身の temp 配下へ向ける。process-global env mutation は並行 test と競合するので不採用
- **baseline を取る待ちは、走っている git を沈黙に数えない** — 沈黙だけだと待ちが途中で抜ける(実測: 5830ms の walk 中に無イベント 2415ms)。`support::settled` は本数一致と沈黙の両方を要求。**開幕の読みを数えるなら生成時に決める** — `RepoSession::open_recording(.., Recording::WithBackground)`(`open` は `UserOnly`)。open 直後に `set_recording` を撃つ形は、開きが `Opened` の受理と同時に spawn する読み(refs / status / log / author / open fetch)のうち何本を捕まえるかがスケジューリング次第になる。open 後だけを数える時だけ `set_recording(Recording::WithBackground)` を使い、`opened_graph` / `opening_settled` で開きを閉じてから撃つ(以後の読みは ask → spawn が store を運ぶので正確)
  - 開いた時の tag 込み pass はチップが出揃った後(実測: `LabelsChanged` の 639ms 後)なので、**tracked refresh 1 本では baseline を閉じられない** — その要求は pass を cancel するだけで、cancel は「止めてくれ」であって「止まった」ではなく、外に落ちた walk が「バッジが walk を起こした」に化ける。守りは 2 つ揃い: 始まる前に取り上げられた pass は walk しない(`run_swap_pass` 冒頭の cancel 判定)と、既に始まっていた pass は `RepoSession::wait_for_graph_passes` が閉じる(`GraphPasses` は spawn 前に登録・task 終了で返却)。walk を数えるテストは `CaptureSink::opened_graph` を通す(`remote_tags_integration::learning_what_the_remotes_carry_repaints_chips_without_swapping_the_graph`)
- **グラフの walk は `--date-order`(`--topo-order` 不採用)** — topo は孤立ルートを端へ沈める(実測: `origin/gh-pages` が 323 行中 322 行目)。この形のテストは「孤立側の後に本流へもう 1 コミット」まで書かないと topo でも緑(`session_integration::an_independent_history_sits_where_its_date_puts_it`)。親を子より先に出さない保証は同じ(GraphBuilder・stash の sift の前提)。レーンは pull request 型で激減(実測: jackson-module-kotlin 277 → 9)、速度差なし
- グラフは **2 段ストリーミング**(タグ無し即描画→無フリッカー置換。44k タグのフロンティア初期化コスト対策)+ `--max-count=2000`。バックグラウンド更新は `refresh_log()` = 一致なら無イベント(アイドル中のチラつき対策)。リセット→ストリーミングは open / Reload / タグ切替 / 件数変更のみ
- **未コミット行の条件は「木が汚れている」ではなく「積まれるコミットがある」** — conflict を全部 ours のまま `git add` すると `status --porcelain` は空・`MERGE_HEAD` は立ったまま・commit は 2 親のマージを書く(実測 2.55。同じ状態の cherry-pick は `nothing to commit` で拒むので、止まった sequencer はこの行にならない)。**行の有無と walk が `MERGE_HEAD` から始まるかは同じ 1 つの答え**(`session::walk::pending_commit`)— 別々に決めると、行の無い綺麗な木にチップも点線も無いコミットが現れて merge の開始・終了で出入りする。demo preset は `conflict-ours`、網は `session_integration::stream`
- **`conflict::git_file` は不在と失敗を同じ空文字で返す** — `opstate::merge_heads` はそれを `Option` に畳んで「読めなかった」と「マージが無い」を分ける。畳まずに空 `Vec` を返すと、失敗した 1 回が「merge が終わった」に化けて点線を落とす全歴史再構築 → 次の poll で戻す再構築の 2 度歩き(基準リポジトリで 2000 行 × 2)。読めなかった poll は前の答えを保つ(`session::refresh` の `merge_moved`)。網は `integrate_integration::merge`
- **行番号を渡すイベントは渡した先が見ている世代を名乗る**(`LabelsChanged` の `generation`)— walk が入れ替わるとチップが別コミットに貼り付き、`applied` が残るので自己修復しない。守りは「読みと送信を同じ `shared` ロック内」と世代タグの 2 つ揃い。**`Shared::generation` は log_gen ではない** — swap を省いたパスも上げるので、写すと以後のチップが全部落ちる(実測・`remote_tags_integration` が赤で捕捉)
- **アバターは取り込む時に作り直す**(`picture::normalize`、保管は 256px PNG のみ)。ファイルサイズ上限は画素を縛らない(4MB の PNG の内側に 4GB の絵。実測 [ci/baseline/avatar-shrink-windows-x64.md](../../ci/baseline/avatar-shrink-windows-x64.md))— 寸法はヘッダだけ読んでデコード前に弾く(`picture::MAX_PIXELS`)。形式は中身で決める(`avatar::EXTENSIONS` はダイアログ専用)。不変条件「保管庫に入るものは必ず描ける」— 破ると輪だけの空円になり理由を言う場所が無い。`png` の `zlib-rs` feature を立てない(C の zlib に倒れ 3OS ビルドの前提が変わる)
- **アプリ自身の 2 ファイルは `settings` モジュール**(`settings.toml` = 人が決めた値 / `state.toml` = 自動)— 1 ファイルだと state フラッシュがエディタでの手直しを消す。ウィンドウ位置を roaming に載せない。環境変数が無ければ推測せずファイル無しに倒す。`Store::locate` は純関数 = mac / Linux の配置も Windows でテストできる
- **読みは `toml::Table` からキーごとに取る**(derive 不採用)— `#[serde(default)]` はキー欠落だけで、型違いは文書ごと失う(実測)= 打ち間違い 1 字が全設定のリセット。**使えない値は型違いと同じに扱う**(幅 0 は `"wide"` と同罪 = 既定へ落とす)。**「使えない」と「上限を越えた」は分ける** — 上限が製品の決め事でしかない値は既定へ落とさず上限へ寄せる(auto fetch 間隔。`120` を既定の 1 分に落とすと、頼まれた 120 倍の頻度で撃つ = 越えた側より遠い)。寄せる先を読み側が数えないこと — `session::auto_fetch_minutes` のように上限の適用点を 1 つ持ち、画面の slot と file 読みの両方をそこへ通す
- **書きは temp + `rename`** — 書きかけはパースに失敗せず `180` が `18` と読める(実測)ので、キー毎フォールバックでは拾えない。rename 失敗は古いファイルを残して諦める(次の tick が撃ち直す)
- **1 つの store を持てるのは 1 プロセスだけ**(`Store::claim`。ジャンプリスト起動で後勝ちの潰し合いが実際に起きた)。鍵はカーネル(`File::try_lock`)= kill でも stale が残らない。**ロックは専用ファイル `lock`** — 2 ファイルは rename で置き換わるので、そこへのロックは孤児を守る(実測: Windows でも rename は open ハンドル越しに成功)。置き場所は state 側(roaming に置くと別マシンへ同期される)
- **拒否の理由になるのは `WouldBlock` だけ** — ロックの仕組みが答えない(ネットワーク共有等)ことを窓の開かない理由にしない。ephemeral な store はロックを持たない = 自動化は何本でも並走する
- **開発ビルドは自分の store を持つ**(`platitude-gg/dev` / `dev-<tree>`)。同じツリーの debug と release は 1 つ(人にとって 1 つのビルド)。初回だけ実 store から `seed_from`(`avatars/` も — 索引だけだと顔の出ない行が並ぶ)。`PG_CONFIG_DIR` はビルドに関係なくそのディレクトリ(2 回の実行で 1 つを共有する検証が乗る)
- **`PG_*` が 1 つでも立っていたらファイル無しに倒す**(例外は `PG_CONFIG_DIR` と `PG_LOG`)— 無いとスクショ実行が実設定にウィンドウ位置を書く。`PG_LOG` を例外にしないと、ログを上げて自分の窓を触った人が設定を失う
- **両ファイルのパスは `repo_key` を通す**(区切り正規化)。**`\\?\` / `\\.\` だけは触らない** — Windows へ宛てた接頭辞(パス解析を切る指示)で、書き換えると別の場所を指す
- **担当を決めるのはキャンセルトークン 1 つ**(`log_cancel`。呼び出し順 = 担当の順)。`log_gen` は spawn 順で呼び出し順と一致しない — 両方を判定に使うと双方が降りて Reload が無反応になる。**降ろされたパスは state を一切触らない** — reset すると送信済み記録まで消え、次の再構築が同じ絵を貼り直す(アイドル中のチラつき)。世代カウンタは順序付け専用
- **`restart_log` の着地はストリームとは限らない** — cancel された walk は `LogFinished` / `LogFailed` を出さず、後ろの `refresh_log` が `LogReplaced` で置き換える(中身は正しい)。待つ側が形を決め打つと race 待ちになる(`session_integration::pass_of` が両方を読む。実測: 負荷下で時間切れ)。**swap を省く判定は行とフッタの両方**(`Shared::sent_footer`)— 行だけだとフッタしか動かない変更を追い越しで取りこぼし「履歴は切られている」と言い続ける(再現: `a_window_change_only_the_footer_notices_still_lands`)。同オプションの再構築は今までどおり黙る
- **表示更新はポーリング**(watcher 不採用: WSL / ネットワークで通知が来ない。他 GUI も watcher + 手動 refresh の両持ち)。契機はフォーカスでなく可視性、間隔は `Metrics.pollIntervalMs`。**refs が動いたら必ずグラフを作り直す** — チップだけ貼り替えると walk が見ていないコミットを指して消える。コストは [ci/baseline/poll-cost-windows-x64.md](../../ci/baseline/poll-cost-windows-x64.md)
- **refs のキーは join の入力を全部覆う**(`session/joins.rs` の `refs_key`)。**動いていない tick は join を組まない** — 毎 tick だと kotlin で 43.4ms/tick(`refs_join_at_scale` 実測)。publish は同じ `Arc` を出し続ける(attach 待ちの consumer 用)。世代は索引が実際に変わった時だけ上げる(`remerge_remote_tags`)
- **同じ答えを 2 度 git に訊かない**: HEAD は `for-each-ref` の `%(HEAD)` に在る(`refs::head_in`。印が無いのは detached と unborn だけ)/ `core.autocrlf` と remotes は `Derived::get_or_try_init` の single-flight。write 前は両方破棄、refs move 後は EOL を即破棄し remotes は external move の時だけ次 read 用に破棄する(初回/post-write read は今読んだ remotes を捨てない)。read 中の破棄は世代不一致で再読。判定は同時 miss を作ってプロセス数も固定する(`concurrent_diffs_share_the_line_ending_setting_read`; 答えだけなら二重実行でも緑)。`stream_log` だけは refs 未着地なら `head_state` を撃つ
- **同じスナップショットの読みは 1 本しか走らない**(`ReadSlot`)。**2 人目は「もう 1 周」を予約する(落とさない)** — 落とすと書き込み直後の refresh が書き込み前の答えのままになる(`session_integration::a_request_made_while_a_read_runs_gets_a_read_of_its_own` が読みを窓際で止めて踏む。落とす実装でも 3 連打型のテストは緑)。`SlotHeld` は正常 `finish` で必ず disarm してから Drop する — IDLE 返却直後の次 owner を Drop が消すと、その owner の `finish` は CPU 100% の永久 loop になる。baseline は snapshot event 後に `wait_for_snapshot_reads` で slot 返却まで閉じる。`refresh_poll` と書き込み後は対象外(`poll_slot` / `write_busy` が持ち場)
- **完了 ack は single-flight permit を返した後に送る** — `refresh_poll_tracked` / `refresh_remote_tags_tracked` の `outcome()` から即座に次を要求しても `Busy` へ落ちないことが契約。`WriteFinished` は Git command の終了通知で、後続 snapshot / graph refresh と `write_busy` の解除までは含まない。queue idle が必要ならこのイベントを流用せず専用 ack を足す
- **タグのリモート状態は `ls-remote --tags` で訊くしかない**(`refs/remotes/` 相当の記録が無い)。届かなかった remote は前回の答えを保つ。尋ねられず読むのは auto fetch 有効かつタグ表示中だけ(`session::catch_up_remote_tags`)。開いた時の fetch(次項)が走った開き方では読まない — fetch が出際に読んでいる。**この読みは書き込みキューを通さない** — 通すと `write_busy` が立ってポーリングが止まる。**ズレは fetch では直らない** — `--prune` はタグを残し、`--prune-tags` は exit 1(実測)。**読み中に来た要求は `Busy` で捨てる — `ReadSlot` の「もう 1 周」は足さない**(2026-08-23 判断): 予約が要るのは 2 人目が 1 人目の知らない変化を持つ時で、この読みの**許可ゲートを通る要求元**(開き終わり / `install_auto_fetch`)は何も持たない — 許可が off の間は読みが走れないので許可を入れた要求が `Busy` になることも無い。つまりそこでの `Busy` は同じ remote へ同じ問いを投げている読みの重複で、その読みの publish が答えになる。**取りこぼしを拾うのは poll ではなく次の auto fetch tick** — poll は remote tag を読まない
- **リモートのタグを消す refspec は `refs/tags/<名前>` で修飾する**(`remote::delete_remote_tag`)— 裸の名前は向こうの全 ref に照らされるので、同名のブランチが在ると `error: dst refspec … matches more than one` で**両方とも消えない**(実測 2.55)。**修飾形は「向こうに無い」を拒まない** — 解決が要らないので `warning: deleting a non-existent ref` + exit 0(裸なら `remote ref does not exist` で exit 1)。つまり**在るかどうかは撃つ前にこちらが知っているしかない**(`offers::TagSides`)。**`remote::delete_remote_branch` は裸のまま**で同じ曖昧さを抱えている(同名タグが在ると拒まれる)— 直すなら `refs/heads/` 修飾だが、「無い時に失敗する」挙動が消えるので別の判断
- **`push_tag` は自分で読み直す** — タグを送ると remote が持つタグが動くが、それを言う記録が手元に無い(上項)ので、**成功した push の中で撃った remote だけを `read_remote_tags` し直す**(`session::push_tag`。`fetch_and_read_tags` と同じ側 = 押した人が既にネットワークへ出ることに同意しているので許可ゲートを通さない)。**拒まれた push は何も動かしていない**ので前の答えを残す。`RefsSnapshot.tag_drifts`(メニューが同期で引くズレの run)もこの読みで更新される。**書き込みの中から `refresh_refs()` を呼ばない** — `AfterWrite::Graph` が閉じた後に `publish_refs` するので、中から頼むと refs 全走査が 2 周する(refs を持つリポジトリでこのアプリ最長の読み)
- **開いたら 1 回 fetch する**(`session::fetch_on_open`・op は `OPEN_FETCH_OP`。規約 §リモートから取り込む)— 開いた直後の読み(author / log / refs / status)より先に write キューへ載せる。許可は auto fetch の間隔で、off なら撃たない。**ask と開き終わりはどちらが先でもよい** — app は設定を入れた直後に呼び、workdir がまだ無ければセッションが握って開き終わりが回収する(片方向にすると `repo::open` の速さ次第で黙って落ちる)。`auto_fetch_slot` を共有するのでタイマーの tick と二重に走らない。1 セッション 1 回(`OpenFetch::Spent`)。**間隔を後から on にしても撃たない** — 「間隔を入れることは write キューに何も載せない」は `remote_tags_integration` が持つ決定。**remote が 1 本も無くても失敗しない**(`fetch --prune --all` は exit 0。実測 git 2.55)
- **diff の構文色の主経路は tree-sitter**(`highlight::grammar`、文法 crate を言語ごとに同梱)。**フォールバックが syntect + two-face**(文法 crate の無い言語。fancy-regex — onig は `Regex` が Send でなく UI の runtime から出せないので不採用)。fancy で落ちる定義は 4 本だけで主要言語は残る
- **テーマは同梱を使わず `highlight::PALETTE` で組む**(規約 §シンタックスハイライト)。既製 4 テーマは実機で全て却下 — 地の文字が `textPrimary` より 1 段暗い(2026-08-13 ユーザー判断)。syntect の `default-themes` feature も落とした
- **構文の読みはファイル先頭から hunk まで歩いて fork する**(`highlight::patch_colors`)— hunk ローカルは文脈が薄いのではなく規則が違う(2026-08-13 実測: QML の `readonly property` は位置で別トークン、先頭行だけ色が違った)。歩く上限は 5,000 行(約 180ms)。ファイルが hunk と食い違ったら使わない(`hunk_agrees`)
- **tree-sitter の crate 同梱クエリには「単体では無色」の差分クエリがある**(qmljs / typescript / tsx / cpp / objc の 5 本 — JS・C のベースクエリへ載せる設計。2026-08-23 に QML の実 diff が全行無色になった)。`grammar::layered()` で特化を先・ベースを後に連結する(同一ノードは先勝ち)。**`; inherits:` を書いているのは objc だけなので、宣言の Grep では見つからない** — 判定は実測(代表スニペットを流して PLAIN 以外のインクが出るか)。**言語を足したら `grammar::SAMPLES` に代表スニペットを 1 行足す**(`every_grammar_colours_a_sample_of_its_language` が全エントリを突き合わせ、サンプルの無い言語もインクの出ない言語もその場で赤くなる。「configuration がビルドできる」guard は色が出ることを言わない)
- **コンフリクトのマーカは状態機械で読む** — 2 つの側は順序ではなく選択肢なので、片側が開いた `/*` を反対側へ持ち込まない(`>>>>>>>` 後は ours の終端状態)。判定は 7 文字ちょうど + 行末か空白、かつ `is_combined` の中だけ = Markdown の見出し下線もマーカ引用も素通し
- **`load_diff` の色付けは `spawn_blocking`**(大きい diff でランタイムのワーカを占有しない)。JoinError は色なしで出し直す — fancy-regex には panic の実績(bat #3156)
- **`refresh_diff` は fingerprint が動いた時しかイベントを出さない**(ページの tick が開いている diff に撃つ read)。生 diff 1 本 = 1 プロセスで先に訊き、`last_diff` に控えた指紋と同じなら**そこで止まる** — 行 / 色 / preview / 改行の残りは動いた時だけ払う。**指紋を控えるのはイベントを出す所**(読んだ所ではない)= ペインが受け取らなかった diff の指紋を控えると、そのファイルはそのまま停まっている限り二度と更新されない。epoch も**出すと決めてから**取る(静止した tick が、飛んで来ているクリックの色付けを取り消さないため)。完了境界は `DiffRefreshTask` — 通常の答えが沈黙なので、待っても「まだ」と「もう来ない」が区別できない
- **staleness のハッシュは問いごとに持ち、寄せない**(2026-08-23 判断)。`details::fingerprint`(生 diff のバイト列)と `highlight::patch::source_hash`(`LexCache` が歩いたソース本文)は名前も `DefaultHasher` も似ているが、**入力が別の流れで、外した時の代償が違う** — 前者は hex でペインへ出て hunk 選択と共に戻り、誤った「不変」が動いたバイト列へ partial write を通す(`stage::verify_fingerprint`)。後者は private フィールドで `Clone` も serde も持たず、比較の両辺を同じバイナリが同じ run で作るので誤答は塗り直しで済む。**`DefaultHasher` を std が保証しない件も片側にしか効かない** — 固める必要が出るのは `fingerprint` だけで、`LexCache` は run を跨げないので同じ要求を持ちようがない。加えて core の staleness ハッシュは 7 箇所(残り 5 本は `session::joins` 3 / `session::print` 2 の、数える項目を選ぶ構造化ハッシュ)で、**2 本だけを「概念の置き場」に見える名前へ束ねると残り 5 本がそこに無い嘘になる**(共通化は 3 箇所目から = structure.md)。`highlight` → `details` の向き(純 CPU の色付けが git を撃つモジュールを名指す)も同時に避ける。**棚卸しの入口は両側の doc** — `source_hash` と `fingerprint` が互いを名指し、後者は「固めるならここで止まる」と書いてある
- **構文色の実測(2026-08-12、release / Ryzen 9 9900X)**: Kotlin 2,000 行の patch で 71ms、初回ロード約 6ms、diff 1 枚のヒープ増は約 2.8MB で頭打ち
- **`a_poll_rebuilds_the_graph_once` は `refresh_poll_tracked().outcome()` の後で数える** — 600ms の固定待ちは負荷下で poll / rebuild の途中を読む。`RefreshTask` は無変更も含む tick と、その tick が要求した swap の完了までを因果的に閉じる
- **「開き終わりより前」を読むテストは current_thread ランタイムで縁を作る** — 既定 flavor の `#[tokio::test]` は spawn したタスクをテスト側が await するまで poll しないので、`RepoSession::open` 直後の `fetch_on_open()` は負荷によらず `OpenFetch::Held`。multi_thread だと開き全体が次の 2 行の間に収まり得て、held 側でなく「remote 未読は "no" ではない = fetch する」側(`known_to_have_no_remote`)を読む — 実測 2026-08-20、Linux コンテナ + ホスト並走で `an_ask_held_for_a_local_only_repository_fires_nothing` が赤。`Opened` を待ってから読む使い捨て probe で確認: remote 皆無のリポジトリでも `OpenFetch::Started` + open fetch 1 本(`set_info` は remote リスト読みより前)。`auto_fetch` の held 2 本だけ既定 flavor で、開き後を読む兄弟は `opened()` の後に読むので multi_thread のまま
- **flaky 方針の pilot 実測(2026-08-16 / Windows)** — `rebuild` 6 件・`query` 8 件・`state` 5 件を 3 test binary process 同時のまま 10 回、計 190 件で NG 0。Cargo 自体の build lock を並列性と取り違えないため binary を直接起動し、各 harness の test thread 数は下げていない
- **flaky 方針の全体適用実測(2026-08-16)** — Windows では修正確定後、`session_integration` 54 件・`remote_tags` 7 件・core unit 302 件・xtask unit 59 件を 4 独立 process 同時のまま 10 回、計 4,220 件で NG 0。適用中の NG は opening reader の slot 未返却と正常終了 guard の owner 上書きを露出し、修正後の正式 10 回を最初から数え直した。同じ最終実装は段 2 の host workspace + Linux core 並走でも PASS。10 回 campaign 自体は Windows だけなので、Linux 固有の再現条件を含む反復実測とは数えない
- **cleanup campaign の回数は対象 suite だけに払う** — 発生率 1/8 の flaky は 10 回すべて緑でも約 26% で見逃す。率を観測できた時は最低 10 回かつ概ね逆数の 3 倍以上、未知なら 10 回を入口にし、元の OS・runner 並走・負荷形態を優先する。日常変更の全 suite をこの回数で反復する根拠にはしない
- **`remote::clone` は行き先を必ず名指しする**(`remote/clone.rs`)— 省くと git が決めた名前を `Cloning into '…'` から読み直すことになり、機械可読形式だけをパースする規約に反する。**cwd は行き先の親**(在る時だけ。git は足りない親フォルダを自分で作るので、無い時は cwd 無しで撃つ)。**行き先の検査はしない** — 取られている行き先も答えない URL も git が `Failed{stderr}` で返し、それがダイアログに出る文言そのもの。`folder_name_for` は**箱の prefill 専用**で `guess_dir_name` の移植ではない(最後の区切りの後ろ + `.git` を 1 つ落とすだけ。`https://host/` は `host` を返すが、行き先を必ず名指しする以上ただの提案)。**セッションを持たない唯一の書き込み**なので `RepoSession` の直列化キューを通らない(呼ぶのは `Hub::clone_repo` の 1 か所)
- **push の印の読みは `remote::push_marks` 1 本だけ**(`remote/marks.rs`。`config -z --show-scope --get-regexp` で `branch.<n>.pushRemote` と `remote.pushDefault` を 1 プロセス両キー — record は `<scope>\0<key>\n<value>\0`・両方未設定は exit 1 の答え。**パターンは regex なのでブランチ名は `config::regexp_literal` でエスケープ** — 素だと `wip.v2+x` が `wipAv22x` の印を拾う。実測 2.55)。送信の `plan_current_push` と、ツールバーが行き先を言うための status tick(pushRemote は status に同乗 → `WorkTreeModel.pushRemote`)が同じ関数を通る。**行き先の解決も 1 本**: 純関数 `remote::push_target`(`remote/standing.rs` — `push_standing` と同じファイル、実行側の `push.rs` と隣)が `plan_current_push` と同じ順を写す。2 つ目の綴りを別の層に置いた結果が 2026-08-23 の修正(QML 側が `remote.pushDefault` だけを読み、fork 運用でラベルと送信先が食い違った)。統合テストは 2 つの印の 6 通り + global スコープを `plan_current_push` の答えと突き合わせる(`push_default_integration`)
- **repo ローカル config の stat は 2 つの答えを落とす**(`RepoSession::forget_what_the_config_decides`): remotes と `core.autocrlf`。設定画面の改行コードの書きはセッションを通らない(パスへ spawn する = 端末で `git config` を打つのと同じ)ので、これが無いと**変換すると言われたリポジトリが、その変換するファイルについて警告し続ける** — 次の write / ref move までずっと。stat は元から毎 tick 撃っているので追加の git プロセスは 0。**`--global` 側は今も次の write / ref move まで見えない**(識別のための `git config` を毎 tick 撃つのはキャッシュを置いた理由そのもの)。回帰は `session_integration::query::the_line_ending_setting_written_beside_the_session_reaches_the_notices`
- **`remote.pushDefault` の鮮度は status tick が持つ**: remotes キャッシュ(`session::eol`)の無効化は repo ローカル config の stat だけで `--global` の書換えを見ない — tick が `push_marks` で読んだ印を `Derived::peek` の保持値と比べ、違えば `forget` + `refresh_refs` で snapshot を出し直す(`RepoSession::note_push_default`。`join_key` が印をハッシュに混ぜているので印だけの変化でも再発行される)。放置するとラベルだけ古い行き先を言い、送信(`plan_current_push` = 実効 config)は新しい印へ行く。detached 中は tick が印を読まない(push は Closed)ので、その間の外部変更は次の write / ref move まで見えない。回帰は `session_integration::query::a_global_mark_moved_in_a_terminal_reaches_the_snapshot`
- `remote.pushDefault`(push の行き先の印)の実測: **git の解決順は `branch.<n>.pushRemote` > `remote.pushDefault` > `branch.<n>.remote`** で、印が在ると `origin/main` を追跡するブランチも**同名 refspec で別リモートへ**飛ぶ(`plan_current_push` はこの順を写す)。読みは `config -z --show-scope --get remote.pushDefault` = `<scope>\0<value>\0` の 2 フィールド・未設定は exit 1(答え)。`--get-regexp` はキーを小文字で返す(`remote.pushdefault`)ので既存の `^remote\..*\.(url|pushurl)$` には掛からない。書きは旧形式 `config remote.pushDefault <name>` —— **`--end-of-options` は要らない**(キーの後は option を探さないので `-x` という名前の remote も値として通る。実測 2.55)。消しは `--unset` で **exit 5 = 元から無い**(答え)。**ローカルへ空文字を書いても global を打ち消せない** —— 「未設定」ではなく「行き先が無い」になり push が `No configured push destination.` で落ちる = repo 単位で外す手が git に無い。`git remote rename` / `remove` はローカルの `pushDefault` / `pushRemote` を追随させるが **global のは warning を出すだけで直さない**。存在しない名前は URL 扱いで `'nope' does not appear to be a git repository`。**`@{push}` / `%(push:short)` は当てにできない** —— 既定の `push.default=simple` の三角運用では `cannot resolve 'simple' push to a single destination` / 空を返す(`push.default=current` なら出る)ので行き先はアプリが解く
- `session/joins.rs` の `join_key` は **remotes の名前・URL と印の全部**を混ぜる —— 印だけが動いた refresh は、混ぜないと「同じ入力」と判定されて**保持していたスナップショットが出し直され**、サイドバーの印が元の行に残る
- **統合テストの executor は stock timeout を `OVERALL_BUDGET`(900s)へ上げる**(`support::exec` の `with_stock_timeout` — 外さない)— 負荷下の suite では git 1 本が単独の約 25 倍(`wait.rs` 実測)で、日常の固定壁時計は正しさでなく負荷で判定する。900s は負荷では破れず livelock だけが踏む床で、executor を直接 await するテストでも wedged git がテスト名付きの赤になる(外していた頃は suite が無名のままハングした)。sink 経由の待ちは `Patience` が先に効き、セッション境界の await には `support::wait::bounded` も使える。コマンド個別の締めは `GitCommand::timeout`(`TimeBudget::At`)、外すのは `no_timeout()`、既定 `Stock` は executor の持つ `DEFAULT_TIMEOUT`。**`repo::open` の probe も `Stock`** — 個別の短い壁時計は「持ち上げ済み」の帳尻を最初のコマンドで破る
- **イベント列は clear せず基準位置で切る** — `sink.events.clear()` は reader と競る(clear と次の待ちの間に届いた分ごと消える)。件数で待つ時は先に `len()` を控えて `evs[from..]` を読み、スナップショット数も base を控えて `settle(base + 1)` を待つ(`session_integration::query` の形)
- **hook で reader を停めるテストは `worker_threads = 2` を明記する** — 停めた hook はその worker を専有し、worker 1 本の環境では残りの仕事が回らない(既定の worker 数は CPU 数依存で環境が決める)。前提は `hook_once` 自身が arm 時に `num_workers >= 2` を assert する — 明記を忘れた新テストは小さいランナーで 900 秒の livelock ではなく名指しの即失敗になる
- **2 段ストリーミングの fast pass は、開き中は着地が保証されない** — 追い越した再構築が無言で飲む(`pass_of` の 実測)。開き中の assert は「在れば swap より前」の順序だけにし、**存在と行数の網は settled な baseline の後のトグルで張る**(baseline 後は誰も log token を取れないので fast pass は必ず語る — `window::tag_only_commits_follow_the_include_tags_option` 後半の形)
- **`stage::discard_chosen` の bucket は呼び手(選択)が言い、status から引き直さない** — 両側に変更のあるファイルは unstaged / staged に 1 行ずつ持ち、「どちらの行を選んだか」は status では復元できない。status を読むのは staged リネームの旧名を足すためだけで、write ロックの中で読む(`stage_conflicted` と同じ理由 — UI で集めた一覧は前に並んだ書き込みより古い)。コマンドは unstaged(`restore --worktree`)→ untracked(`clean`)→ staged(`restore --staged --worktree`)の順に最大 3 本で、1 手目の失敗で止まる
