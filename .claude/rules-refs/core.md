## git サブプロセス規約(各論)

- **`status` の答えの中で末尾が `/` の path は「git が開かなかったディレクトリ」** — 作業コピーの中に居る別リポジトリは `-uall` でも `vendor/nest/` 1 行のまま(境界の向こうのファイルはそのリポジトリの物。実測)。**`/` で切って畳む読み手はここでだけ空の末尾に当たる**ので、行はそのディレクトリ自身として 1 行描く(`models::pathtree` — 末尾の `/` を名前に残す)。`git diff --no-index -- /dev/null <dir>` は patch を作れない(exit 1 + stderr。`answers_by_code(1)` が飲む)ので diff は空。網は `status_integration`
- **パスは `:(literal)` で包む**(`process::literal_pathspec`)— `GIT_LITERAL_PATHSPECS` だと `git stash push -u` が成功を報告しながら untracked を stash しなくなる(実測)。`--no-index` の引数は pathspec ではない
- **`--no-optional-locks` / `GIT_OPTIONAL_LOCKS=0` は `git diff` に効かない** — 作業ツリーの diff は index を refresh し、そのために `.git/index.lock` を取る(実測 2.55: 旗付きの `status` は index を書かないが、旗付きの `diff` は書く。`status` は錠を取る前に旗を訊き、`diff` は訊かない)。この錠は書き込みが**待たずに死ぬ**側なので(`hold_locked_index` は fatal)、キューの外を走るポーリングの diff が commit の錠に当たると commit が落ちる(`fatal: Unable to create ... index.lock: File exists`)。止めるのは `-c diff.autoRefreshIndex=false` で、`process::executor` の `FIXED_ARGS` に常時入っている。**答えは 1 つも変わらない**(実測: stat だけ動いたファイルは patch も `--name-only` も `--quiet` も「変化なし」と答える)が、**代金は index の stat キャッシュが誰にも更新されなくなること** — 読み取りで refresh するコマンドがこれで消えるので、中身が同じまま stat だけ全部動いた作業ツリーは毎回ハッシュし直される(実測 780 ファイルで `status` 72ms 対 refresh 済み 28ms。普通の編集で汚れるのは数本だが、git の外から複製した木は全部汚れる)。**遅い pre-commit フックは錠を握らない** — git は hook を走らせる前に錠を返す(実測: 20 秒眠るフックの最中に `.git/index.lock` は無い)ので、`--preset slowhook` が押さえているのは「書き込みが飛んでいること」だけ。網は `tests/it/exec.rs::a_work_tree_read_leaves_the_index_untouched`
- `git merge --continue` / `git rebase --continue` は引数を受け付けない(`--no-edit` も不可)。`--no-edit` は cherry-pick / revert のみ
- **`git merge` の終了コードは 1 が両義**(実測 2.55: conflict = 1 / マージできない名前 = **1** / `--ff-only` の拒否 = 128 / 作業ツリーが上書きされる = 2)。rebase と違い 1 だけでは答えと失敗を分けられないので、**exit 1 の後に** `opstate::detect` で **merge が立っているか**を訊いて `integrate::Landing::{Done, Stopped}` を返す(`Stopped` は失敗ではない = `SessionEvent::WriteStopped` → エラー帯もログの持ち上げも出さない。2026-08-22 ユーザー報告)。**marker はコードと併せて読む** — 既に立っている merge の上で撃った merge は `MERGE_HEAD` を残したまま 128(実測 2.55: 未解決なら `unresolved conflict`、解決済みなら `You have not concluded your merge`)。**`--squash` の conflict だけはこの網に掛からない** — `SQUASH_MSG` を書いて `MERGE_HEAD` を作らないので失敗として出る(画面からは撃たない。網は `integrate_integration::merge`)
- **`git pull` の終了コードも 1 が両義**(実測 2.55: conflict = 1 / tracking information 無し = 1 / 作業ツリーが上書きされる = 1 / **両側が進んでいて `pull.rebase` も `pull.ff` も未設定 = 128 で何もせずに断る**(`fatal: Need to specify how to reconcile divergent branches`))。merge と同じ形で**exit 1 の後に** `opstate::detect` を訊き、**merging か rebasing のどちらかが立っていれば `Landing::Stopped`**(`pull.rebase` の設定次第でどちらの標識も出るので両方見る — `MERGE_HEAD` / `rebase-merge`)。**`git pull <remote> <branch>` は remote-tracking ref も書く**(`* [new branch] fresh -> origin/fresh` — 実測)ので、取り込んだ後のグラフは向こうの現在地を描く。網は `remote_integration` の `a_pull_*`。**その断りに UI からは当たらない**(割れた木では行が無効 = rules-refs/app-ui.md の pull の項)が、数が古い木では届きうるので landing の判定は残す。**「指示が在る」と見なされる鍵は 3 つで値は問わない**(`pull.rebase` / `pull.ff` / `branch.<名前>.rebase` — 実測 2.55 でどれも divergent な pull を通す)、**Git for Windows は system の gitconfig に `pull.rebase false` を置いている** — どちらも「素の環境なら断られる」と仮定した設計をしないための実測
- **止まった merge を `git commit` で終わらせたものは `merge --continue` と同一**(実測 2.55: 木・2 つの親・メッセージ・走るフック `pre-commit` / `prepare-commit-msg` / `commit-msg` / `post-commit` まで一致。`post-merge` / `pre-merge-commit` はどちらでも走らない = 止まらずに済んだ merge のフック)。**解決結果が HEAD と同一でも書ける**(空のマージコミット)。だから画面は commit ボタン 1 つで終わらせる(規約 §進行中の操作から出る)。箱に入れる文言は `conflict::stopped_message`(`MERGE_MSG` からコメント行を落とす — `commit::commit` は `--cleanup=whitespace` なので落とさないと `# Conflicts:` が記録される。`core.commentChar` を変えたリポジトリでは落ちないが、箱に見えているので消せる)。網は `integrate_integration::merge`
- **未コミット変更は stash → switch → `stash pop --index` で運ぶ**(`session::carry_across`)— `switch --merge` は conflict しても exit 0 で `MERGE_HEAD` を作らず `merge --abort` が効かない上、staged が 1 つでもあると拒否(実測)
- **`switch --force-create` は start が remote-tracking だと upstream を書き換える** — `branch.autoSetupMerge`(既定 on)が**既存ブランチにも**効き、`branch.<local>.remote` / `.merge` が start のものに差し替わる(実測 2.55: `origin/topic` → `up/2.21`。`checkout -B` も同じ / `reset --hard` と `branch -f` は無傷 / start が local branch なら無傷)。reflog が言うのは `branch: Reset to <start>` だけなので、失った upstream はログにも画面にも出ない。**壊した移動を後から探す検出子はこの文字列** — 素の `reset --hard` は `reset: moving to <start>` と書いて upstream を保つので、両者は reflog のメッセージで初めて分かれる(実測 2.55。`switch -C` は HEAD へは別ブランチからなら `checkout: moving from A to B`、同じブランチ上なら `checkout: moving from B to B` と書く = HEAD 側だけでは判らない)(2026-09-21 ユーザー報告 — 「ブランチをここへ移す」で別リモートの別名ブランチが upstream になり、以後の ahead/behind と push 先がそこを向いた)。**だから `CheckoutTarget::ForceCreate` は `--no-track` を常に付ける**。網は `upstream_integration::moving_a_branch_onto_a_remote_ref_leaves_its_upstream_alone`
- **`git stash pop` の非ゼロは「無処理」を意味しない** — 作業ツリー conflict はマージ済み+stash 残置、staged 衝突は丸ごと拒否(`conflicts in index. Try without --index.` → `--index` 無しで再試行)。判定は unmerged の有無(実測)
- **`git stash push` は unmerged が 1 本でも在れば丸ごと拒む** — パスを名指しても同じで、conflict していないファイルだけを渡しても `error: could not write index` / `<path>: needs merge` で exit 1、退避は起きない(実測 2.51)。**「木に conflict が在るか」が答え**なので、退避の可否は `stash::standing` 1 本で決める(`FileRowMenu.canStash` / `BandStashButton.mode`)
- **`commit::commit` の答えは git の終了コードだけ**(戻り値は `()`)— HEAD を読み返す 2 本目のコマンドは自分の理由で失敗しうる = 着地したコミットを失敗として報告する経路になる。動いた先が要る側は書き込みの後段のパスで読む
- **終了コードを自分で読むコマンドには `answers_by_code(<答えのコード>)` を付ける** — 付けないとコマンドログが勝手に開く。対象は `switch` / `rebase` / `merge` / `cherry-pick` / `revert` / `stash pop` / `stash apply`(pop と同じ exit 1 = conflict で載った、の答え。`conflicts_now` の判定も pop と同型)/ `rev-parse refs/stash`(exit 1 = stash ゼロ本。持ったことのない全リポジトリが返す)/ **config の読み取りは `--get` / `--get-regexp` とも全部**(未設定 = exit 1 = 答え。identity / remote list / tracking branches / push plan の upstream / merge tool / autocrlf / mergetool.cmd — 網は `tests/it/config_reads.rs`)/ **HEAD の読み**(`symbolic-ref -q` = exit 1 が detached、`rev-parse --verify -q HEAD` = exit 1 が unborn。`refs::head_state` と `remote` の current_branch)/ untracked の `diff --no-index`(exit 1 = 差分あり = 常態)/ stash rename の移動確認 `rev-parse --verify` — 網は `tests/it/answer_reads.rs`。**`cat-file` は読む前に `rev-parse --verify -q <spec>` で訊く — 無い側は exit 128 で 0/1 の枠外、しかも「リポジトリが無い」も 128 なので枠を広げると本物の失敗が消える**(無い側は全部 exit 1 = 答え、在る側は 0 + oid を stdout。unborn HEAD の `HEAD:` / added の `<parent>:` / index に無い `:0:` で実測 2.55。`preview::blob_is_there` が preview と source_text の両方の入口)。代償は git プロセス 1 本 — Windows での 1 本の値段はこのファイルの `process::program` の項(`cat-file` も `diff-tree` も同じで、プロセス生成が支配的)。`cat-file --batch-check` なら exit 0 で "missing" を返せるが **stdin 必須**(プロセス層は stdin を常に閉じる — `scratch.rs`)。失敗判定は書き込みの答え側(規約 §git が言ったことを読む場所)
- **頼まれていない fetch は `Kept::UnaskedUnlessItFails` のハンドルで走る**(`session::write::run_write` の分岐、`exec_unasked_fetch`)— `CommandFeed` が spawn 時の行を握っておき、**git が断った時だけ** `CommandStarted` + `CommandFinished` を後から流す。**理由はパネル側**: 連続 fetch 失敗の 1 回目はパネルを開けるので、その行が無いと開いた先に並ぶのは利用者が最後にやったこと(2026-09-04 ユーザー報告「push を押すとログが立ち上がる」の正体)。**行が「利用者の doing か」は `CommandStarted.asked` で運ぶ** — false の行は app 側で `failed` にも `failure()` にも入らない(`models::commands`)ので、オフラインで毎分開くことはない。網は `session_integration::auto_fetch::an_unasked_fetch_leaves_a_row_only_when_git_says_no`(着地とお断りの 2 本立てで 1 本)
- **答えのコードは 1 とは限らない** — `config --global --unset <key>`(merge editor を空にした時)は「元から無い」を **exit 5** で言う(ファイルが無い時・キーが無い時・multivalue で消せない時が全部 5、実測 2.55。multivalue は消さずに 5 なので「消えた」とは言い切れないが、直後の refresh が本当の値を出す)。1 で印を付けると失敗行になり、設定カードを閉じただけでコマンドパネルが開く(2026-08-21 ユーザー報告)。**枠はこのコマンドの 5 だけ** — 理由は `cat-file` の 128 と同じで、コードの意味はコマンドごと。網は `tests/it/integrate_integration/mergetool.rs`
- **carry は自前(`session::carry_across_rewrite`)** — `--autostash` の復帰は素の `stash apply` で staged が全部 unstaged になる(`--index` を渡す口が無い。実測)。代償は `--continue` / `--abort` 後の自動復帰。止まった時は stash を残す — unmerged のある index へ git は書かない(判定は `opstate::detect`)
- **止まった cherry-pick / revert も `Landing::Stopped`** — conflict は exit 1 + 自分の marker(`CHERRY_PICK_HEAD` / `REVERT_HEAD`。複数リビジョンなら sequencer も。実測 2.55)。判定は `integrate::landed` 1 か所で、**exit 1 かつ `InProgress::from_state` が自分と答えた時だけ**(止まった merge の上で撃った cherry-pick は marker が merge のもの)。**この網に掛かるのは conflict だけ** — 汚れた木・読めない名前・unmerged の残る index は全部 exit 128 で marker を残さず、**既に立っている同種の上で撃った時だけ 128 で自分の marker が在る**(実測 2.55 — だからコードを読まずに marker だけ見ると、git の「もう 1 つ動いている」という説明を握り潰す)。空で止まった側は先に `left_nothing_to_record` が拾うのでここへ来ない(着地は `Done` = 「何も起きなかった」)。網は `integrate_integration::pick_revert`
- **止まった rebase も同じ**(2026-08-22 ユーザー判断) — `RebaseOutcome::Stopped`。判定は `integrate::landed` 1 か所で、**exit 1 かつ `rebase-merge` / `rebase-apply` が立っている時だけ**。**コードを読まないと誤読する**: 「既に rebase-merge がある」失敗は marker を残したまま **exit 128**(実測 2.55。拒否と停止だけが 1、読めない upstream も 128)。拒否(`work_is_in_the_way`)を先に見るので carry は変わらない。`Blocked` があるので `Landing` には寄せられず、`build::rewrite_carrying` が carry の後に `Landing` へ落とす(拒否は画面に届かない = 回り直すのが答え)。`squash` / drop / reword も同じ 1 本を通るので 5 経路すべてが `WriteStopped` を出す。網は `integrate_integration::rebase` と `session_integration::carry_rewrite`
- **cherry-pick と revert は「空になった」の答え方が別**(実測 2.55・`integrate_integration`): cherry-pick は `CHERRY_PICK_HEAD` + stderr `The previous cherry-pick is now empty`、revert は `--allow-empty` が無く `nothing to commit` で拒まれ stderr 空・stdout に status。状態も 3 通り — cherry-pick は marker あり / 単体 revert は無し / 複数 revert は sequencer だけ(`opstate::detect` は None → `opstate::sequence_pending` を見ないと残骸を「きれい」と誤答)。判定は `integrate::left_nothing_to_record` / `still_stepping` の 2 か所だけ
- **元から空のコミットは `--allow-empty` で写す** — 付けないと「後から空になった」と同じ文言で止まり区別が付かない。`--empty=drop` は git 2.45 からで最低バージョン外
- **拒否の見分けは `integrate::work_is_in_the_way` の 1 か所** — 素の rebase と `--interactive` は同じ文言で拒む(実測 `integrate_integration`)ので carry も `integrate::RebaseOutcome` も 1 本。未追跡だけの木は拒まれない = stash も無し
- **`edit` 停止だけは exit 0 で止まる**(実測 2.55 — 頼まれた停止なので git は失敗に数えない)。`integrate::landed` は **Ok 側でも** `opstate::detect` を訊き、rebasing が立っていれば `Stopped`。なぜ止まったかは `integrate::rebase_standing`(`rebase-merge/amend` の存在 = edit・**その中身 = 対象**。apply backend に edit は無いので merge 側だけ読む)— status refresh が rebasing の間だけ載せる(`StatusLoaded.stop`)。網は `integrate_integration::plan`
- **停止の対象は `rebase-merge/amend` の中身**(実測 2.55・`an_edit_stop_after_a_reword_names_the_replayed_commit_not_the_todos`)— `stopped-sha` は **todo の元 oid** なので、`edit` の手前に reword / squash / 並べ替えが 1 つでもあると replay 後の HEAD と別物になり、**今の履歴に居ないコミットを名指す**。その中身が git 自身の書いた停止時 HEAD(full hex)で、これがカードの名指しと amend の的の両方。全 pick の時だけ両者が一致するので、**全 pick のテストでは差が出ない**
- **`edit` 停止中の amend の門は `offers::message_edit` の `editing && HEAD 自身の行` だけ**(実測: 1 回 amend すると HEAD は動き、`rebase-merge/amend` を含め `rebase-merge/` の**どのファイルも追随しない**)。amend と「停止中に端末が上に積んだコミット」を見分けるには ancestry を毎 tick 撃つしかなく、断る先は git 自身が通す操作 = 割に合わない(規約 §フル interactive rebase の edit 停止)
- **`rebase_standing` の Err は前回の stop を保つ**(`RepoSession::rebase_stop_seen`)— 1 tick でも `editing:false` に落ちると出口カードの `--skip` が長押しから素クリックへ戻り、その 1 クリックは停止中のコミットを取り去る。progress は落とす(古い N/M は「進んだ」と読める方が害)
- **`rebase_standing` の `--git-path` の並びは前提** — `rebase-merge/msgnum` / `rebase-merge/end` / `rebase-apply/next` / `rebase-apply/last` / `rebase-merge/amend` の順で、progress は添字の対 `(0,1)` `(2,3)` で読み `amend` は 4 番。**並べ替えても型は変わらないのでコンパイルは通り**、進捗と停止理由が黙って入れ替わる
- **WIP 行は「木が汚れている or 操作が立っている」で出す**(`refresh::publish_status` の wip_dirty)— edit 停止と空停止は木がきれいなまま出口カードへ着地する必要があり、着地は WIP 行(規約 §進行中の操作から出る)。きれいな木 + 操作なしの従来条件はそのまま
- **プラン preview は `rebase_plan::preview`**(from の親を upstream に、merge を先に断り、行が from で始まらなければ off-branch = 別ブランチのクリック。答えは `PlanAnswer` の型付きで文は QML 側)。onto のブランチ名は `for-each-ref refs/heads --points-at`(先頭 1 本、無ければ空 = sha フォールバック)。網は `integrate_integration::plan`
- **プラン実行も 1 コミット編集も先端を釘付けにする**(`RepoSession::rebase_interactive` の `expect_head` / `EditPlan::tip`)— spawn 直前に `head_oid` と照合し、ずれたら `report::rewrite_tip_moved()`(= `Withheld` + 報せバー)で止まる(端末や他セッションが動かした履歴の上へ、組んだ todo が黙って落とすものを作らない)。**1 コミット編集の pin は行から取る** — 範囲は必ず HEAD で終わり `read_rows` が git の新しい順を反転して返すので、最後の step が先端そのもの = プロセスは 1 本も増えない。**pin の無い replay は無い** —— 空の `expect_head` は照合に落ちて refuse する(黙って外れる番人を作らない)。**carry は replay を 2 度撃つので照合も 2 度**(`Replay::tip_still_stands` が spawn ごと)。窓は狭まるだけで閉じない(git は todo を取るが、その todo が書かれた先端は取らない)
- **`Withheld` へ寄せたのは画面から届く 3 つだけ**(先端のずれ / 立っている操作の上への rewrite = `build::carry_across_rewrite` / 操作が立っている最中のプラン実行 = `ops_integrate`)。**残る `GitError::Rejected` は UI が先に止めるもの**(空本文の reword・mergetool 未設定・空の identity・stash rename の読み取り失敗・大文字小文字だけのタグ改名 = 箱が断る)で、ログに残すのが正しく、**core は app のゲートを契約にできない**ので残す。個別の箇所は `GitError::Rejected` の Grep が正

- **同じスナップショットの読みは 1 本しか走らない**(`ReadFlight`)。**入口は全部そこを通る** — `refresh_refs` / `refresh_status` も `refresh_poll` も書き込みの後始末も `read_refs` / `read_status` 経由(`poll_slot` / `write_running` は持ち場が違う: replay 中は poll がわざと通るし、フォーカスと `ask_merge_tool` はどちらとも突き合わされていない。二重に読むと corpus では `status -uall` 2.9s / 2.3 CPU 秒を二重に払う)。**順序も flight が持つ** — pass は repository を見る前から publish の後まで flight を握るので、古い答えが新しい答えを追い越す窓が無く、`publish_*` の側に世代の関門は無い(置いても発火しない)。**2 人目は待つ**: 自分が訊いた後に始まった pass が landed していればその答えを貰い(プロセス 0 本)、無ければ自分が次の 1 周を走らせる — 落とすと書き込み直後の refresh が書き込み前の答えのままになる(`session_integration::a_request_made_while_a_read_runs_gets_a_read_of_its_own` が読みを窓際で止めて踏む。落とす実装でも 3 連打型のテストは緑)。重なりは `the_ways_in_to_a_status_read_never_run_two_at_once` が spawn の所で読みを park して踏む(コマンドログの start/finish から同時本数を数える)。**replay の下だけは踏み方が違う** — poll は replay 中の書き込みを通り抜けるので(`running_write()` の kind が `replays_history`)、`a_poll_let_through_by_a_replay_does_not_read_beside_it` は park で書き込みを request の中に留め、**git の答えを合図に tick を撃つ**(`WriteFinished` は後始末の読みより先に出て、`write_running` は refresh を含む request 全体に掛かる = `write::serve`)。baseline は snapshot event 後に `wait_for_snapshot_reads` で閉じる
- **完了 ack は single-flight permit を返した後に送る** — `refresh_poll_tracked` / `refresh_remote_tags_tracked` の `outcome()` から即座に次を要求しても `Busy` へ落ちないことが契約。`WriteFinished` は Git command の終了通知で、後続の読み直しは含まない。**後続更新完了の境界は `WriteSettled { id, kind, failed }`**(2026-09-12)— status / refs / graph / stash・worktree の一覧 **と一覧が頼んだ派生の読み(worktree の join と walk = `refresh_worktrees` が flight を離した後に自分で await する。flight の答え `WorktreeRead` が news を運ぶので相乗りした caller も待つ)** / author config の publish が済み、次の request を取る直前に出る(head reach の walk だけは含まない = 前の walk が居ると skip する問い)。**`failed: Vec<FollowUp>` が着地しなかった読みを id 付きで名指す**(`OpFailed` は id を持たない — label は同じ語)。各読みは失敗を型で返す: refs / status の flight の答えは `Reread::{Same, Moved, Failed}`、listing の task は `Vec<FollowUp>`、グラフは `RefreshOutcome::landed()`(新しい ask に取られた `Cancelled` はそもそも答えではないので、`graph_answer` がその ask の着地まで追ってから判定する = 上項)。`ReadFlight<A>` は答えの型を持つ(既定 bool = published)。queue idle が必要ならこれを待つ(`support::session::write_settled` が `failed` を返す)
