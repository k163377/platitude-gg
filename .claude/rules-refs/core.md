# platitude-core 各論(git の実測挙動・実装の決定事項)

[.claude/rules/core.md](../rules/core.md) の参照資料 — **1 項目 1 行**(コード・docs の「core.md」参照はここへ移った行も指す)。

## git サブプロセス規約(各論)

- **コマンドログは executor の observer 1 本**(`process::CommandObserver` + `process::Kept` の 3 ハンドル)— 分類は `session::write::run_write` の 1 箇所: 利用者用 `Asked` / 背景の読み `Unasked` / 頼まれていない fetch `UnaskedUnlessItFails`(行になるのは git が断った時だけ)
- **`&str` をバイト長で切らない** — キーの前方一致は `as_bytes().get(..KEY.len())` + `eq_ignore_ascii_case`。`l[..KEY.len()]` は多バイト文字を跨いだ瞬間に落ち、walk のワーカで落ちるとグラフはリングのまま無言で止まる(「サイドバーは出るのにグラフだけ空」はまず stderr のパニック)
- **Windows の git は `CREATE_NO_WINDOW` のまま — `DETACHED_PROCESS`(console 無し)に替えない**。git 自身は console が無ければ子も console 無しで起こすが、その子が MSYS のシェル(`git mergetool` のスクリプト・フック・sh 経由の textconv / fsmonitor)だと自分で console を作り、既定のターミナルが Windows Terminal の機械では見える WT の窓が立って残る。代金は git 1 本ごとの `conhost.exe` で、払わずに済ませる形は internal-docs/ハング調査.md の要判断

- **`status` の答えの中で末尾が `/` の path は「git が開かなかったディレクトリ」** — 作業コピーの中に居る別リポジトリは `-uall` でも `vendor/nest/` 1 行のまま。`/` で切って畳む読み手はここでだけ空の末尾に当たるので、行はそのディレクトリ自身として 1 行描く(`models::pathtree` — 末尾の `/` を名前に残す)。`git diff --no-index -- /dev/null <dir>` は patch を作れない(exit 1 + stderr。`answers_by_code(1)` が飲む)ので diff は空。網は `status_integration`
- **パスは `:(literal)` で包む**(`process::literal_pathspec`)— `GIT_LITERAL_PATHSPECS` だと `git stash push -u` が成功を報告しながら untracked を stash しなくなる。`--no-index` の引数は pathspec ではない
- **`--no-optional-locks` / `GIT_OPTIONAL_LOCKS=0` は `git diff` に効かない** — 作業ツリーの diff は index を refresh し、そのために `.git/index.lock` を取る(実測 2.55)。この錠は書き込みが待たずに死ぬ側なので、キューの外を走るポーリングの diff が commit の錠に当たると commit が落ちる(`fatal: Unable to create ... index.lock: File exists`)。止めるのは `-c diff.autoRefreshIndex=false` で、`process::executor` の `FIXED_ARGS` に常時入っている。答えは 1 つも変わらない(stat だけ動いたファイルは patch も `--name-only` も `--quiet` も「変化なし」と答える)が、代金は index の stat キャッシュが誰にも更新されなくなること — 中身が同じまま stat だけ全部動いた作業ツリー(git の外から複製した木)は毎回ハッシュし直される。遅い pre-commit フックは錠を握らない — git は hook を走らせる前に錠を返すので、`--preset slowhook` が押さえているのは「書き込みが飛んでいること」だけ。網は `tests/it/exec.rs::a_work_tree_read_leaves_the_index_untouched`
- `git merge --continue` / `git rebase --continue` は引数を受け付けない(`--no-edit` も不可)。`--no-edit` は cherry-pick / revert のみ
- **`git merge` の終了コードは 1 が両義**(実測 2.55: conflict = 1 / マージできない名前 = 1 / `--ff-only` の拒否 = 128 / 作業ツリーが上書きされる = 2)。1 だけでは答えと失敗を分けられないので、exit 1 の後に `opstate::detect` で merge が立っているかを訊いて `integrate::Landing::{Done, Stopped}` を返す(`Stopped` は失敗ではない = `SessionEvent::WriteStopped` → エラー帯もログの持ち上げも出さない)。marker はコードと併せて読む — 既に立っている merge の上で撃った merge は `MERGE_HEAD` を残したまま 128(実測 2.55: 未解決なら `unresolved conflict`、解決済みなら `You have not concluded your merge`)。`--squash` の conflict だけはこの網に掛からない — `SQUASH_MSG` を書いて `MERGE_HEAD` を作らないので失敗として出る(画面からは撃たない。網は `integrate_integration::merge`)
- **`git pull` の終了コードも 1 が両義**(実測 2.55: conflict = 1 / tracking information 無し = 1 / 作業ツリーが上書きされる = 1 / 両側が進んでいて `pull.rebase` も `pull.ff` も未設定 = 128 で何もせずに断る(`fatal: Need to specify how to reconcile divergent branches`))。exit 1 の後に `opstate::detect` を訊き、merging か rebasing のどちらかが立っていれば `Landing::Stopped`(`pull.rebase` の設定次第でどちらの標識も出るので両方見る — `MERGE_HEAD` / `rebase-merge`)。`git pull <remote> <branch>` は remote-tracking ref も書く。網は `remote_integration` の `a_pull_*`。その断りに UI からは当たらない(割れた木では行が無効 = rules-refs/app-ui.md の pull の項)が、数が古い木では届きうるので landing の判定は残す。「指示が在る」と見なされる鍵は 3 つで値は問わない(`pull.rebase` / `pull.ff` / `branch.<名前>.rebase` — 実測 2.55 でどれも divergent な pull を通す)、Git for Windows は system の gitconfig に `pull.rebase false` を置いている — どちらも「素の環境なら断られる」と仮定した設計をしない
- **止まった merge を `git commit` で終わらせたものは `merge --continue` と同一**(実測 2.55: 木・2 つの親・メッセージ・走るフック `pre-commit` / `prepare-commit-msg` / `commit-msg` / `post-commit` まで一致。`post-merge` / `pre-merge-commit` はどちらでも走らない)。解決結果が HEAD と同一でも書ける(空のマージコミット)。だから画面は commit ボタン 1 つで終わらせる(規約 §進行中の操作から出る)。箱に入れる文言は `integrate::stopped_message`(`MERGE_MSG` からコメント行を落とす — `commit::commit` は `--cleanup=whitespace` なので落とさないと `# Conflicts:` が記録される。`core.commentChar` を変えたリポジトリでは落ちないが、箱に見えているので消せる)。網は `integrate_integration::merge`
- **未コミット変更は stash → switch → `stash pop --index` で運ぶ**(`session::carry_across`)— `switch --merge` は conflict しても exit 0 で `MERGE_HEAD` を作らず `merge --abort` が効かない上、staged が 1 つでもあると拒否
- **`switch --force-create` は start が remote-tracking だと upstream を書き換える** — `branch.autoSetupMerge`(既定 on)が既存ブランチにも効き、`branch.<local>.remote` / `.merge` が start のものに差し替わる(実測 2.55: `checkout -B` も同じ / `reset --hard` と `branch -f` は無傷 / start が local branch なら無傷)。reflog が言うのは `branch: Reset to <start>` だけなので、失った upstream はログにも画面にも出ない。壊した移動を後から探す検出子はこの文字列 — 素の `reset --hard` は `reset: moving to <start>` と書いて upstream を保つ(`switch -C` は HEAD へは別ブランチからなら `checkout: moving from A to B`、同じブランチ上なら `checkout: moving from B to B` と書く = HEAD 側だけでは判らない)。**だから `CheckoutTarget::ForceCreate` は `--no-track` を常に付ける**。網は `upstream_integration::moving_a_branch_onto_a_remote_ref_leaves_its_upstream_alone`
- **`git stash pop` の非ゼロは「無処理」を意味しない** — 作業ツリー conflict はマージ済み+stash 残置、staged 衝突は丸ごと拒否(`conflicts in index. Try without --index.` → `--index` 無しで再試行)。判定は unmerged の有無
- **`git stash push` は unmerged が 1 本でも在れば丸ごと拒む** — パスを名指しても同じで、conflict していないファイルだけを渡しても `error: could not write index` / `<path>: needs merge` で exit 1、退避は起きない(実測 2.51)。「木に conflict が在るか」が答えなので、退避の可否は `stash::standing` 1 本で決める(`FileRowMenu.canStash` / `BandStashButton.mode`)
- **`commit::commit` の答えは git の終了コードだけ**(戻り値は `()`)— HEAD を読み返す 2 本目のコマンドは自分の理由で失敗しうる = 着地したコミットを失敗として報告する経路になる。動いた先が要る側は書き込みの後段のパスで読む
- **終了コードを自分で読むコマンドには `answers_by_code(<答えのコード>)` を付ける** — 対象は `switch` / `rebase` / `merge` / `cherry-pick` / `revert` / `stash pop` / `stash apply`(pop と同じ exit 1 = conflict で載った、の答え)/ `rev-parse refs/stash`(exit 1 = stash ゼロ本)/ config の読み取りは `--get` / `--get-regexp` とも全部(未設定 = exit 1 = 答え。網は `tests/it/config_reads.rs`)/ HEAD の読み(`symbolic-ref -q` = exit 1 が detached、`rev-parse --verify -q HEAD` = exit 1 が unborn。`refs::head_state` と `remote` の current_branch)/ untracked の `diff --no-index`(exit 1 = 差分あり = 常態)/ stash rename の移動確認 `rev-parse --verify` — 網は `tests/it/answer_reads.rs`。**`cat-file` は読む前に `rev-parse --verify -q <spec>` で訊く — 無い側は exit 128 で 0/1 の枠外、しかも「リポジトリが無い」も 128 なので枠を広げると本物の失敗が消える**(無い側は全部 exit 1 = 答え。unborn HEAD の `HEAD:` / added の `<parent>:` / index に無い `:0:` で実測 2.55。`preview::blob_is_there`)。`cat-file --batch-check` なら exit 0 で "missing" を返せるが stdin 必須(プロセス層は stdin を常に閉じる — `scratch.rs`)
- **頼まれていない fetch は `Kept::UnaskedUnlessItFails` のハンドルで走る**(`exec_unasked_fetch`)— git が断った時だけ `CommandStarted` + `CommandFinished` を後から流す。理由はパネル側: 連続 fetch 失敗の 1 回目はパネルを開けるので、その行が無いと開いた先に並ぶのは利用者が最後にやったこと。**行が「利用者の doing か」は `CommandStarted.asked` で運ぶ** — false の行は app 側で `failed` にも `failure()` にも入らない(`models::commands`)。網は `session_integration::auto_fetch::an_unasked_fetch_leaves_a_row_only_when_git_says_no`
- **答えのコードは 1 とは限らない** — `config --global --unset <key>`(merge editor を空にした時)は「元から無い」を exit 5 で言う(ファイルが無い時・キーが無い時・multivalue で消せない時が全部 5、実測 2.55。multivalue は消さずに 5 なので「消えた」とは言い切れないが、直後の refresh が本当の値を出す)。1 で印を付けると失敗行になり、設定カードを閉じただけでコマンドパネルが開く。枠はこのコマンドの 5 だけ — コードの意味はコマンドごと。網は `tests/it/integrate_integration/mergetool.rs`
- **carry は自前(`session::carry_across_rewrite`)** — `--autostash` の復帰は素の `stash apply` で staged が全部 unstaged になる(`--index` を渡す口が無い)。代償は `--continue` / `--abort` 後の自動復帰。止まった時は stash を残す — unmerged のある index へ git は書かない(判定は `opstate::detect`)
- **止まった cherry-pick / revert も `Landing::Stopped`** — conflict は exit 1 + 自分の marker(`CHERRY_PICK_HEAD` / `REVERT_HEAD`。複数リビジョンなら sequencer も。実測 2.55)。判定は `integrate::landed` 1 か所で、exit 1 かつ `InProgress::from_state` が自分と答えた時だけ(止まった merge の上で撃った cherry-pick は marker が merge のもの)。この網に掛かるのは conflict だけ — 汚れた木・読めない名前・unmerged の残る index は全部 exit 128 で marker を残さず、既に立っている同種の上で撃った時だけ 128 で自分の marker が在る(実測 2.55 — コードを読まずに marker だけ見ると、git の「もう 1 つ動いている」という説明を握り潰す)。空で止まった側は先に `left_nothing_to_record` が拾うのでここへ来ない(着地は `Done`)。網は `integrate_integration::pick_revert`
- **止まった rebase も同じ**(ユーザー決定) — `RebaseOutcome::Stopped`。判定は `integrate::landed` 1 か所で、exit 1 かつ `rebase-merge` / `rebase-apply` が立っている時だけ。コードを読まないと誤読する: 「既に rebase-merge がある」失敗は marker を残したまま exit 128(実測 2.55。拒否と停止だけが 1、読めない upstream も 128)。`Blocked` があるので `Landing` には寄せられず、`build::rewrite_carrying` が carry の後に `Landing` へ落とす。網は `integrate_integration::rebase` と `session_integration::carry_rewrite`
- **cherry-pick と revert は「空になった」の答え方が別**(実測 2.55・`integrate_integration`): cherry-pick は `CHERRY_PICK_HEAD` + stderr `The previous cherry-pick is now empty`、revert は `--allow-empty` が無く `nothing to commit` で拒まれ stderr 空・stdout に status。状態も 3 通り — cherry-pick は marker あり / 単体 revert は無し / 複数 revert は sequencer だけ(`opstate::detect` は None → `opstate::sequence_pending` を見ないと残骸を「きれい」と誤答)。判定は `integrate::left_nothing_to_record` / `still_stepping` の 2 か所だけ
- **元から空のコミットは `--allow-empty` で写す** — 付けないと「後から空になった」と同じ文言で止まり区別が付かない。`--empty=drop` は git 2.45 からで最低バージョン外
- **拒否の見分けは `integrate::work_is_in_the_way` の 1 か所** — 素の rebase と `--interactive` は同じ文言で拒むので carry も `integrate::RebaseOutcome` も 1 本。未追跡だけの木は拒まれない = stash も無し
- **`edit` 停止だけは exit 0 で止まる**(実測 2.55)。`integrate::landed` は Ok 側でも `opstate::detect` を訊き、rebasing が立っていれば `Stopped`。なぜ止まったかは `integrate::rebase_standing`(`rebase-merge/amend` の存在 = edit・その中身 = 対象。apply backend に edit は無いので merge 側だけ読む)。網は `integrate_integration::plan`
- **停止の対象は `rebase-merge/amend` の中身**(実測 2.55・`an_edit_stop_after_a_reword_names_the_replayed_commit_not_the_todos`)— `stopped-sha` は todo の元 oid なので、`edit` の手前に reword / squash / 並べ替えが 1 つでもあると replay 後の HEAD と別物になり、今の履歴に居ないコミットを名指す。その中身が git 自身の書いた停止時 HEAD(full hex)で、これがカードの名指しと amend の的の両方。**全 pick のテストでは差が出ない**
- **`edit` 停止中の amend の門は `offers::message_edit` の `editing && HEAD 自身の行` だけ** — 1 回 amend すると HEAD は動き、`rebase-merge/amend` を含め `rebase-merge/` のどのファイルも追随しない。amend と「停止中に端末が上に積んだコミット」を見分けるには ancestry を毎 tick 撃つしかなく、断る先は git 自身が通す操作 = 割に合わない(規約 §フル interactive rebase の edit 停止)
- **`rebase_standing` の Err は前回の stop を保つ**(`session::standing` の `rebase_stop()` / `set_rebase_stop()`)— 1 tick でも `editing:false` に落ちると出口カードの `--skip` が長押しから素クリックへ戻り、その 1 クリックは停止中のコミットを取り去る。progress は落とす(古い N/M は「進んだ」と読める方が害)
- **`rebase_standing` の `--git-path` の並びは前提** — `rebase-merge/msgnum` / `rebase-merge/end` / `rebase-apply/next` / `rebase-apply/last` / `rebase-merge/amend` の順で、progress は添字の対 `(0,1)` `(2,3)` で読み `amend` は 4 番。**並べ替えても型は変わらないのでコンパイルは通り**、進捗と停止理由が黙って入れ替わる
- **WIP 行は「木が汚れている or 操作が立っている」で出す**(`graph::wip_row_stands`)— edit 停止と空停止は木がきれいなまま出口カードへ着地する必要があり、着地は WIP 行(規約 §進行中の操作から出る)
- **プラン preview は `rebase_plan::preview`**(merge を先に断り、行が from で始まらなければ off-branch。答えは `PlanAnswer` の型付きで文は QML 側)。onto のブランチ名は `for-each-ref refs/heads --points-at`(先頭 1 本、無ければ空 = sha フォールバック)。網は `integrate_integration::plan`
- **プラン実行も 1 コミット編集も先端を釘付けにする**(`RepoSession::rebase_interactive` の `expect_head` / `EditPlan::tip`)— spawn 直前に `head_oid` と照合し、ずれたら `report::rewrite_tip_moved()`(= `Withheld` + 報せバー)で止まる(端末や他セッションが動かした履歴の上へ、組んだ todo が黙って落とすものを作らない)。1 コミット編集の pin は行から取る — 範囲は必ず HEAD で終わり `read_rows` が git の新しい順を反転して返すので、最後の step が先端そのもの。**pin の無い replay は無い** — 空の `expect_head` は照合に落ちて refuse する(黙って外れる番人を作らない)。carry は replay を 2 度撃つので照合も 2 度(`Replay::tip_still_stands` が spawn ごと)。窓は狭まるだけで閉じない(git は todo を取るが、その todo が書かれた先端は取らない)
- **`Withheld` へ寄せたのは画面から届く 3 つだけ**(先端のずれ / 立っている操作の上への rewrite = `build::carry_across_rewrite` / 操作が立っている最中のプラン実行 = `ops_integrate`)。残る `GitError::Rejected` は UI が先に止めるもので、core は app のゲートを契約にできないので残す。個別の箇所は `GitError::Rejected` の Grep が正
- **立っている操作の上への rewrite は断る — `work_is_in_the_way` では見分けられない**(実測 2.55、網は `integrate_integration::standing_op` / `session_integration::standing_op`)。merge / cherry-pick / revert が立っている木への rebase は素も `--interactive` も `cannot rebase: Your index contains uncommitted changes.` で拒まれ(未解決なら `unstaged changes` が加わる)、git は操作の名を出さないので拒否文言は汚れた木と同一。続く `git stash push` は解決済み+staged の index を書けてしまい、その操作の marker を道連れに落とすため、carry は解決をただの staged 変更として戻し、成功として報告する。守りは 2 枚: `RepoSession::rebase_interactive` が `opstate::detect().any()`(= 画面の `opText != ""`)で spawn 前に `Rejected`、`build::carry_across_rewrite` が stash の前に `InProgress::from_state` で `Rejected`(5 経路すべての backstop)。**bisect は除く** — stash を跨いで生き残るので carry してよい(`from_state` を読む理由)。未解決 conflict だけが偶然安全(unmerged な index に stash push が `could not write index` で失敗する)
- **`session_integration::carry_rewrite::rewrite_route` は先頭一致で読む** — 止まった rebase の後の status refresh が撃つ `rev-parse --git-path rebase-merge/msgnum …` が部分一致では 4 手目の `rebase` に化ける
- **`stash pop` の非ゼロを conflict と読めるのは元の tree に unmerged が無かった時だけ** — unmerged のある index へは丸ごと拒否(`needs merge`)で残る conflict は元のもの。`conflicts_now` だけ見ると無処理の pop が成功に化ける(`session::stash_pop` の `settled_first`)
- **`rev-list --exclude` は名前空間を外して書く** — `--branches` に `refs/heads/` を付けると何も除外されず「他の誰かが掴んでいる」が常に真(エラーも警告も無し)。`--tags` / `--remotes` も同様。`--glob` / `--all` だけ `refs/` 始まり
- **`--glob=<pattern>` は階層にしか当たらない** — `--glob=refs/stash` は 0 件(`refs/stash*` なら拾う)。素の rev `refs/stash` は stash 無しで `fatal: ambiguous argument`、`--ignore-missing` は間違った oid も黙って捨てる = 安全側と逆。`reachable::command` は `--glob` を採る
- **`--all` で HEAD は外せない** — `--exclude=<現在のブランチ> --all` でも先端が negative に残る。外したい walk は `--branches --remotes` を並べる
- `git config <key> <value>` はダッシュ始まりの値もそのまま(`--` は値として保存される)
- **`config --get-regexp` は低いレベル順・実効値は最後の行** — 1 件目で判定すると system が常に勝つ(Git for Windows は system に `core.autocrlf=true` を書く)。単一キーは `--get`、複数キーは最後の出現で上書き読み。TestRepo が隔離するのは撃つ git だけで、コード側は開発機の system / global を見る
- **`core.autocrlf` の綴りは git の bool 語彙**(実測 2.55): `input` は大小無視で先に見る / true = `true` `yes` `on` と非ゼロの整数 / false = `false` `no` `off` `0` と空の値 / 値なしのキー(`=` が無い)は true / それ以外は `fatal: bad boolean config value` で git が動かない。**読みは `None` に倒す**(`eol::setting::AutoCrlf::of_record`)— 「未設定」と同じ席で、設定画面はその 4 つ目の行しか選べないから。警告(`eol::normalises`)と設定画面は同じ 1 本の読みを通る — 2 通りに読むと「git が決めているか」に答えが 2 つできる
- **`core.autocrlf` の書きは 1 キーなので 1 発** — ただし先に読む: `--unset` は無かった時も多値の時も exit 5 で、読んでおくと前者を撃たずに済む(`eol::setting::set`)。スコープは `--global` / `--local` を必ず綴る
- **identity(`user.name` / `user.email`)の検証は git に任せる** — git が拒むのは空の name だけ(空 email は通り `<>` になる)。`<` `>` 改行は author 行から黙って落ち、config 書き込みは `\n` エスケープで注入は起きない
- **identity の 2 連書きは原子化できない**(`git config` は 1 プロセス 1 キー・`--edit` はロックを取らない・自前 lock は config ライタ再実装・libgit2 は絶対制約で閉)— 書いた後に実効設定を読み直し、違えば 1 回だけ撃ち直す(`identity::set_identity`)。半端(新 name + 旧 email)は `Identity::is_complete()` 真で黙って居座る。競合でない失敗は何度でも同じ = 2 回で止める。不採用: 書く前に読んで失敗時に戻す(戻しが同じロックを踏む)
- **半端の再現は多値の `user.email`**(`identity_integration`)— `--add` 2 回のキーへの set は `cannot overwrite multiple values` で exit 5、隣の `user.name` は通る。`.git/config.lock` 先置きで両方不着地も作れる(読みはロック不要)
- **「そのリポジトリ自身が何を書いているか」は `--local` でしか読めない**(`config::get_regexp_at` / `identity::load_local`)— 実効レベルの `--get-regexp` はどのファイルの record かを言わないので、継承しているだけの値と自分で書いた値が同じ姿で届く。書き戻しの読み直しも `--local` 側で読む(`identity::set_local_identity`)
- **`--local` の書き込みは「今の値を先に読んで、違うキーだけ撃つ」**(`identity::write_local_pair`)— 空欄 = `--unset` だが、`--unset` の「元から無い」と「多値なので触れない」は同じ exit 5(実測 git 2.55。git の doc は 5 と 6 に分かれると書いてあるが分かれない)ので、先に読まないと本物の失敗が無害な答えに化ける。**`--local` は set 側にも明示する** — 素の `git config <key> <value>` / `--unset` も既定でローカルに書くが、読む側と書く側が同じ語を名乗る形にしておく
- **署名の有無は `cat-file commit` の `gpgsig` ヘッダで確認** — SSH 署名は `gpg.ssh.allowedSignersFile` 未設定だと `%G?` が未署名と同じ `N`
  - **`--format=` のどのプレースホルダでも見分けられない**(実測 git 2.55): 未署名と ssh 署名済みで `%G?` `%GS` `%GK` `%GG` `%GF` `%GP` `%GT` が完全一致 — 1 コマンド化の道は無い
  - **先に `cat-file commit`、ヘッダ無しなら `Absent` で終わり**(`identity::verify_commit`)— 未署名は 1 プロセスで済む。`%G?` の `N` は「判定できなかった」と読む。プロセス数は `identity_integration` の observer テストが固定
- **`ls-files --eol` は worktree の実ファイルを読む** — グロブ渡しは基準リポジトリ級で数十秒。候補列挙(索引のみ)と `--eol`(確定した数パスだけ)を必ず別コマンドに分ける。未チェックアウトは `w/` が空
- **改行コードの判定は patch の bytes から**(`eol::read`)— `ls-files --eol` は「今どう見えるか」で、どの行が新しいかは diff しか知らない。`--eol` は未追跡と近傍標本だけ
- **帯の `NO LFS` の件数は LFS が先・属性が後**(`session::lfs`、改行コードの印と同じ「status が動いた / stale」の拍): 作業ツリーから stage する中身の在る行(`lfs::stages_content` = 未追跡・未ステージ・未解決の conflict)が在れば、まず `git lfs version`(**無い時は git の `'lfs' is not a git command` = exit 1 なので `answers_by_code(1)`** — 付けないと答えのたびにログが赤くなる)。**答えた LFS はセッションの間覚え、同時の問いは 1 本に束ねる**(`Derived` — Git for Windows は LFS を持つので、机では `check-attr` を 1 度も撃たない)。無い時だけ全パスに `check-attr -z filter` を**バイト長で区切って**撃つ(本数で区切ると長いパスが Windows のコマンドライン 32767 字を越えて起動ごと失敗する)。**無い間は件数が立っている時だけ tick ごとに LFS を訊き直す**(入れたら次の tick で消える)。**数えられなかった読みは件数を据え置き、次の tick で数え直す**(待つと tree が動くまで警告が出ない)。`.gitattributes` の編集が status を動かさない形(既に保留中のもの・`info/attributes`)は次に動いた拍で数える。実測は `tests/it/lfs_integration.rs`(`lfs::runs` は mry で差し替え、実物は `git lfs version` を直に撃った答えと突き合わせる = 机は有り・コンテナは無しで両方の道を通る)
- **`diff --ignore-cr-at-eol` の patch は `apply` できない**(`patch does not apply`)— 表示用と staging 用の diff は同じ bytes(`details::file_diff_raw` の不変条件)
- **worktree の diff は index 空間で出る** — `autocrlf=true` でも patch に CR は現れず `apply --cached` / `apply -R` が通る。index blob に CR があるファイルは変換されない = 設定切替で全ファイルが modified にはならない
- **`git mergetool` は `--no-prompt` だけでは stdin を踏む**(`conflict::mergetool`)— ツール未設定だと確認を閉じた stdin に出すので `--tool=` 必須。`--gui` も必須(無いと `merge.guitool` と食い違う)。`mergetool.writeToTemp=true` を撃つ(既定は一時ファイルが隣に出て WIP ペインが untracked で埋まる)。`keepBackup` は素のまま(`.orig` は利用者の安全網)。パスは 1 つ以上(引数なしは全衝突を順に開き書き込みキューを塞ぐ)。自前 `cmd` ツールは exit code を信用されず BACKUP の mtime 比較 — 保存せず閉じると「失敗」でマーカーが戻る
- **`mergetool --tool-help` は Windows で約 8 秒** — キューの外で非同期に・プロセスで 1 回だけ(`conflict::available_tools` の `OnceCell`)。`--gui` でも絞られず、端末ツール除外は説明文の `(requires a graphical session)` パースしかない(取れなければ候補ゼロ = 無害側)。自前定義は `config --get-regexp '^mergetool\..*\.cmd$'` で即出す

- **Windows では対話の予算はプロセスの本数で決まり、PATH の `Git\cmd\git.exe` を通すと 1 本の代金が倍になる**(数は code-costs の `process::program` の行)。インストーラが PATH に足す `cmd\git.exe` は環境を整えて本物を spawn するだけの 2 段目で、本物は自分で `libexec/git-core` / `mingw64/bin` / `usr/bin` を子の PATH に足し、HOME と system config も自分で引く。`GitExecutor::new()` は `Command` が最初に見つける `git.exe` が `cmd\git.exe` の時だけ、隣の `{mingw64,clangarm64,mingw32}\bin\git.exe` を撃つ(`process::program`。先に別の git が在ればそのまま、`with_program` は名指しのまま)
- **行選択の詳細は `git show` 1 本にまとめる**(`details::commit_details`)。`--diff-merges=first-parent` が要る(無いとマージのファイル一覧が空)。レコードと一覧の切れ目は NUL 10 個で決める(`split_record`)— 形で探すとメッセージ中の `M\tsrc/main.rs` が変更ファイル表に化ける。空コミットはレコード後ろに改行すら無い
- **`git diff-tree <p1> <c>` は `git show <c>` より遅い**
- **実行枠 `process::Slots`** — spawn 直前に `acquire` して reap で Drop が返す(`GitExecutor::execute` の中だけ。上の層は枠を持たない = 複合操作が枠を跨いで待つ形が作れない)。プールは 1 つ・click の予約付き: `Limits::of(n)` = 全体 `n` / うち `reserve` = `n - max(1, n/4)` は interactive かつ `Pace::Here` だけが取れる(予約 3 本が要る — diff を開く click は `diff-tree` / `check-attr` / `rev-parse`→`cat-file` の 3 本を同時に撃つので、予約が 2 本以下だと直列鎖の頭が枠待ちになる)。`Pace::Elsewhere`(fetch / push / ls-remote / clone / mergetool / 署名検証の gpg)と `Priority::Background` は残り `max(1, n/4)`(`Limits::shared()`)を分け合う(両方に当たる 1 本は 1 と数える)。**別プール案(Here n + Elsewhere n = 2n)は却下** — 設定の「全体で N・背景はその一部まで」と食い違う。優先度はハンドル側(`GitExecutor::background()` — セッションの `exec_background`。poll 自身の status / refs は interactive のまま — 見ている画面の読みで single-flight なので枠 1 つで足りる)、ペースはコマンド側(`GitCommand::paced_elsewhere()`)。待ちは token で終わる(`execute` が `select!` — `Latest` に置き換えられた選択・閉じた画面・閉じたセッションの待機読みは spawn せず `CommandEnd::Cancelled` の行を残す)。公平性は aging(`OVERTAKEN_LIMIT` = 4 本の interactive に追い越された background は次に出る)。同一の background 読み(program / cwd / args / env が同じ、buffered `run` のみ)は queued の leader に follow して 1 プロセス(`run_shared`。started 済みの run には乗らない。leader が cancel / unwind したら follower は撃ち直す)。素の `GitExecutor::new()` は unbounded(テストの既定)で、アプリだけが Hub で `scheduled(Slots::new(Limits::of(settings.git_concurrency)))` を挿す。既定は `default_concurrency()` = スレッド数 / 3 を 4..=8 に収める(床が 4 なのは click の 3 本が入る最小だから — ci/baseline/git-slots-windows-x64.md)。網は `process::slots` の単体 + `tests/it/slots.rs`(実 git。競合相手は `poll_once` で門に置く)
- **`CommandStarted` は「訊かれた」であって「並んだ」ではない** — `GitExecutor::execute` は observer に告げてから `Slots::acquire` へ進む(告げる位置は仕様: 待っているコマンドを要求時点から出すためで、動かしてはいけない)。なので `CommandStarted` を見た瞬間の `report().queued_interactive` は 0 でありうる。観測口は `Slots::settled(|report| …)` — `notified()` を先に取ってから状態を見て、届いていなければ await し、起きたら必ず見直す(`notify_waiters` は permit を残さないので、取るのが後だとその窓の stir を落として永久に待つ)。`stirred()` はロックを離してから呼ぶ(queue / running を触る 4 か所 = `acquire` / `unqueue` / `release` / `set_limits`)。順序の網の入口は述語のクロージャ — 述語の中で 2 本目の `acquire` を `poll_once` すれば、まさにその窓で enqueue できる(別スレッドも、本体のテスト用フックも要らない)。通知を取る位置を `report()` の後ろへ動かすと、この網だけが Pending で赤くなる
- **合成行(自分の未コミット行・他コピーの行)は「出す瞬間に立っている読み」で組み直してから publish する**(`session::relay`。規約 §未コミット行が名乗るもの)— 行が立つかは status が決め描くのは walk で、別プロセスなので walk の開始時の答えで出すと、木が一度も言っていないことをグラフが言う。git は 0 本(`GraphBuilder::push_ids`)。合成行の出し入れで下の履歴のレーン・配色は動かない(`graph::leash_tests` が等値で固定)ので、組み直しは合成行とその leash が跨ぐ行だけを動かす。描画時に行を抜くと、下の行がその列の線分を持っているので行き先の無い辺が残る
- **`git worktree list` で「リポジトリ自身の作業コピー」を名乗る属性は無い — 順が答え**(`worktrees::WorktreeEntry.main` = 最初の 1 件)。git は main working tree を先頭に置き、リンクされたコピーがその後に続く(どの作業コピーから撃っても同じ順)。bare のリポジトリではその席に bare の entry が来る = それでも「自身」で、作業コピーが無いことを理由に落とすのは読む側(`models::nav::drain`)
- **他コピーの読みが古いかは worktree 一覧の HEAD と突き合わせて判る**(`RepoSession::copy_heads` — 一覧はページの tick、読みは `status` 1 本で 30 秒 tick)。古い読みの行は落とし、`refresh_carried()` をその場で頼む。この HEAD 表は `worktree_holders` と別に持つ — あちらは refs 読みと walk を起こす集合なので、隣のコミットを畳み込むと 5 万 refs の listing を毎回払う。網は `session_integration/carried_moved.rs`(不変条件 = 移動後のどの pass も、そのコピーを離れたコミットの上に描かない)
- **`git worktree remove` の答えは終了コードで 2 つに割れる**(`report::worktree_not_removed`)— **128 = `die()` で何も消していない**(未コミット / ロック / submodule / main)、**それ以外 = 記録を消した後にフォルダを消し切れなかった**(`remove_worktree` は `delete_git_work_tree` の失敗後も `delete_git_dir` へ進む。Windows で中のファイルかカレントを別プロセスが掴むと `error: failed to delete …: Permission denied` で 255)。**ignored は数えずに消える**・フォルダの消えたコピーは素通り(記録だけ消える)・ロックは `-f` 1 本では通らない(`-f -f`)。実行中のコピー自身を消すと途中で止まるので、画面は今立っているコピーの行を無効にする。網は `tests/it/worktree_remove.rs` と `report` の単体(半端な方は実 run の写し)。**一覧は `looked` を刻む**(`WorktreesLoaded.looked` — 消した行を待つ app の `StandIn` が読む。stash と同じ理由)。**可否は `offers::worktree_card`**(main = 行無し / ロック → 今のコピー → busy の順で灰)、ブランチの無いコピーの行は `offers::RefKind::Worktree`(`held_by_worktree` が自分のパスの時だけ `switch` = Open、`delete` は常に偽 = 削除はカードの物)。網は `offers/worktree_tests.rs`
- **他コピーの読み(`carried::Copies`)は switch・行・進行中の pass の token・`turned` の世代を 1 つの lock で持つ** — `set_copies_read(false)` は行を落として pass を cancel し、着地は `turned` が同じ時だけ(`Landing::Refused`)。flag と行を別々に持つと、Never にした瞬間に走っていた巡回が完了後に行を復活させる。`refresh_carried()` は `Option<CarriedPass>`(`outcome()` = `Landed { moved }` / `Dropped`)を返し、`wait_for_carried_pass()` が「巡回が飛んでいない」境界(網は `carried.rs` の単体 + `session_integration/carried.rs`)
- **`core.fsmonitor` / `core.untrackedCache` は製品条件(`GIT_OPTIONAL_LOCKS=0`)では効かない** — index が二度と書かれないので token も cache も更新されない。不採用(ci/baseline/git-slots-windows-x64.md §status の高速化機構)
- **`cat-file --batch` の常駐は保留・設計済み**(設計は P3-確認事項 §core)
- **upstream の書き込みは 2 通りで、分かれ目は追跡 ref が手元に在るか**(`branch::set_upstream`)— 在れば `branch --set-upstream-to=refs/remotes/<remote>/<branch>`、無ければ `config --local branch.<name>.remote` → `.merge refs/heads/<branch>` の順に直書き(`.remote` が先 = `.merge` だけ残ると git は既定のリモートで読む / `.remote` だけなら upstream 無しになる)。git 自身は手元に無い名前を拒む(`fatal: the requested upstream branch … does not exist` exit 128)が、その状態は git 自身が作れる = `status --porcelain=v2` は `branch.upstream` を出して `branch.ab` を出さず(`upstream_tracked=false`)、`%(upstream:track)` は `[gone]`(実測 2.55)。そこから `plan_current_push` は設定どおり `<local>:refs/heads/<branch>` を組んで新規作成し、追跡 ref が付いて数が動き出す — 素の `git push` とは違う(`push.default=simple` は名前が違うと `fatal: The upstream branch … does not match` で拒む。アプリは常に明示 refspec なので当たらない)。在否は `rev-parse --verify --quiet --end-of-options <ref>` + `answers_by_code(1)`。網は `upstream_integration::an_upstream_the_next_push_has_to_make_is_recorded_all_the_same`

## セッション・実装の決定事項(各論)

- **git を撃つ前に答えが出る分岐は `#[cfg(test)]` の単体テストへ**。**証人を 2 つ置く** —— `CommandObserver` の `started` を数えて 0 と、在りもしないプログラム名 + 在りもしない木(すり抜けた分岐は spawn で落ちる)。先例は `stage::partial`。**統合テストに残すのは git が答えてから断る側**(fingerprint のズレ・combined diff・実際の patch 適用と復旧)
- **読みの並びの後の判断は純関数に割る**。先例は `remote::push::decide_push`。**統合テストに残すのは「読みが git の持ち物を持って返るか」**(scope・正規表現になる名前・実 push の代表例)と、`config_reads::planning_a_push_answers_by_code`
- **同じ割り方の 2 例目・3 例目**: `identity::local::keys_to_write`(組合せ全件が単体、実 git に残すのは**発行されたコマンドがその判断どおりであること**)/ `sequencer::plan::decide_edit`(**拒否の順**は単体。実 git に残すのは shallow clone の縁が縁として返ること)。**割る前に測る対象は「その判断 1 通りあたり何プロセス・何リポジトリか」** —— 純関数を足しただけで元の統合テストを全部残すのは未完了

- **メモリの内訳は `cargo xtask perf --breakdown` で出す**。実測記録は [ci/baseline/perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md)
- **refs に比例する名前は `crate::Name`(`compact_str`)で持つ** — 24 バイトまで inline。**`Footprint` は `SmallVec` に明示 impl が要る** — 無いと `[T]` へ deref して溢れたバッファを数え落とす
- **バイト数より確保の個数が効く帯がある** — 個数の削減は計数より WorkingSet に大きく出る(差はヒープ管理領域。計数アロケータには見えない)。`classes=` の**件数**を必ず見る
- **mimalloc は不採用** — WorkingSet が増え(環境変数で抑えても private が増える)、起動・応答に差なし。数字は [perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md) §アロケータと確保の個数
- **refs に比例する常駐データは平らな索引 1 本で持つ**: `BTreeMap` は 1 件でも 11 スロットのノード(→ `RemoteTagIndex`)/ `HashMap<K, Vec<V>>` は push 1 回で 4 スロット(→ `LabelIndex`)/ hex 40 字の `String` は 1 行 1 確保。`String` → `Vec<u8>` では 1 バイトも減らない — 減るのは表現を変えた時だけ
- **メモリ予算の半分は空リポジトリで既に埋まっている**(`--no-open` — ci/baseline/perf-windows-x64.md。Rust ヒープは 1.2MB)。software 描画は fps が予算割れ(GPU −25MB でも)

- interactive rebase は `GIT_SEQUENCE_EDITOR` に別実行ファイル `pgg-todo-editor` を差す。**配布物に同梱必須**(本体と同じディレクトリ)

  - **lock ファイルは握ったまま消し、取る側は名前が残っているか確かめる**(消す = `still::held` / `still::announcing`、取る = `still::lock_beside`)— 先に離すと、その数 µs に同じ名前を開いた相手が「名前から消えた inode」を握り、announce が lock の無い note を残して次の読み手に litter として消される。**Windows も POSIX と同じ**(`remove_file` は自分や他人が開いていても成功し、名前は即消え、同名の新ファイルで別の lock が取れる)ので OS 分岐は無し。取る側は `WouldBlock`(掃除中)も `metadata` 不在(掃除済み)も**名前を開き直す** — pid は再利用され各 run の最初の announce は同じ番号なので、死んだ run の残骸と新しい run が同じ名前でぶつかる。**名前が共有の lock ファイルは残す**(`still::Name::Shared` / `verify::ownership`)
  - **rename に負けた残置 helper はバイト一致の時だけ使う**(`publish_helper`)— 一致しない残置は古い helper を今日の assert の下で走らせるので、その場でエラーにする(Windows は実行中の exe も読める — 拒まれるのは書きと rename)

- **ペインの diff の読みは、追い越された時点で止まる**(`session::query::publish_diff` が `diff_epoch` を bytes を読んだ直後と絵を書いた後の 2 か所で見る)— 色も**行も**止める。行が一緒に運ぶ fingerprint が次の部分ステージの判定材料(`stage::refusal::verify_fingerprint`)なので、古い読みが後に着いたペインは消えた bytes の fingerprint を握って以後の部分ステージを `StaleStage` で断り続ける。**1 回の部分ステージが同じ target の読みを 2 本立てる**ので普通に重なる。追い越された読みは自分のプレビューファイルも掃く(`sweep_before(epoch + 1)` — 追い越した側は自分より下しか掃かない)。読みの完了境界は `RepoSession::read_diff` と `DiffReadOutcome`
- **HEAD はタブに 1 つの record**(`session::standing::Standing`)。読みは git を起こす前に stamp を取り(`standing.stamp()`)、write の終わりが fence を上げる(`run_write`)— fence より古い stamp の読みは丸ごと捨て(`current(looked)`)、HEAD の offer は `head_at` で順序付け(古い読みの HEAD は `Stale`。**fence と head_at は別** — 一緒にすると先に着いた status が後の refs 読みを丸ごと落とす)。**捨てた読みは読み直す**(`read_status_from` / `read_refs_from` に `ReadFlight::stamp()` を渡す)— 書き込み側は refs が動いた時しか status を読み直さないので、何も持って来ない fetch に fence された status は次の tick まで誰も答えない。**stamp は捨てた pass の中で取る** — spawn した task の中で stamp すると後読みの pass より新しくなり 3 本目の listing を撃つ。refs 読みの hold(`HeadHold`)は offer が `Stale` でなかった時だけ書く(reach の起点は最新の tip)。回帰は `session_integration::head`
- **HEAD の報告は番号付きで、番号はプロセス全体で単調**(`NEXT_HEAD_SEQ`。session を跨ぐ — feed は session より長生き)。番号を取るのは**送る報告だけ**(動いた時と write 後の最初の読み)。`fence()` は**2 つの数を返す**(`Fence`。互いに比較できない): `head_seq` = 「この write の後の最初の報告が取り得る最小番号」で `WriteFinished { head_seq }` に乗り、consumer は `headSeq >= head_seq` で「write 後の報告」を判定する。`reads_from` = 「write の後に見た読みが取り得る最小 stamp」で、`RefsLoaded { looked }` / `StashesLoaded { looked }`(どちらも **git を撃つ前**に打つ)と突き合わせる。**着いたことは証拠にならない** — 答えと一覧は別の feed を通って順不同で届くので、write の終了時に飛んでいた読みが答えの後から適用され得る(消した行を戻す側がこれで戻し過ぎる。app の `ops::StandIn`)。`StatusLoaded { head_seq }` = その status が横に立つ報告の番号(`WorkTreeModel.statusSeq`)。**consumer は配られた HEAD(`SessionEvent::HeadObserved`)だけを見る**(graph の pin は HEAD 行が未描画の間は直前の HEAD 行に留まり、pass が着地したら追う = `pinned_oid`)
- **HEAD の派生も record が持つ**: `HeadPublished`(窓外だけ `publish::only` を latest-wins で 1 本、**(oid, refs_key) が動いた時だけ問い直す**(`claim_published_ask`)。HEAD が動いたら record の答えは捨てる(次の walk の答えが同値でも送る)。walk の答えは record の HEAD と同じ HEAD についてのものだけ受ける)/ `HeadReach` / `wip_dirty` / `merge_incoming` / `rebase_stop` / `merge_tool`。`conflict::sides` の ours は status が読んだブランチを渡す。`check_branch_delete` の基準は snapshot の `BranchItem.upstream_oid` か HEAD(解決しない upstream 名は `publish::delete_reference` が HEAD へ倒す = git と同じ)。**読めなくても必ず答える** — `merged` は `Option<bool>` で、`None` = 読みが落ちた(QML には `unknown`)。落とした読みは行を素の形に残し、削除そのものは git が判定する
- **1 問 1 読みの読みは `session::latest::Latest`** で前の読みを cancel。番号で答えを選ぶ consumer(details / plan)は `Latest::begin_numbered`(番号と slot を同じ lock で取る)。`TabMsg::Remotes` は snapshot の `Weak` が変わった時だけ
- **`RefsSnapshot` は `tags_by_name` 索引 + `local_named` / `remote_named` / `tag_named` の二分探索**(メニューが名前で問う)。`publish::reaches(rows, from, to)` は merged を行で答える(`Option<bool>`、窓外は `None` → git)
- **同じスナップショットの読みは 1 本しか走らない**(`ReadFlight`)。**入口は全部そこを通る** — `refresh_refs` / `refresh_status` も `refresh_poll` も書き込みの後始末も `read_refs` / `read_status` 経由(`poll_slot` / `write_running` は持ち場が違う: replay 中は poll がわざと通るし、フォーカスと `ask_merge_tool` はどちらとも突き合わされていない)。**順序も flight が持つ** — pass は repository を見る前から publish の後まで flight を握るので、`publish_*` の側に世代の関門は無い(置いても発火しない)。**2 人目は待つ**: 自分が訊いた後に始まった pass が landed していればその答えを貰い、無ければ自分が次の 1 周を走らせる — 落とすと書き込み直後の refresh が書き込み前の答えのままになる(`session_integration::a_request_made_while_a_read_runs_gets_a_read_of_its_own` が読みを窓際で止めて踏む。落とす実装でも 3 連打型のテストは緑)。**replay の下だけは踏み方が違う** — poll は replay 中の書き込みを通り抜けるので、`a_poll_let_through_by_a_replay_does_not_read_beside_it` は park で書き込みを request の中に留め、**git の答えを合図に tick を撃つ**(`WriteFinished` は後始末の読みより先に出る)。baseline は snapshot event 後に `wait_for_snapshot_reads` で閉じる
- **完了 ack は single-flight permit を返した後に送る** — `refresh_poll_tracked` / `refresh_remote_tags_tracked` の `outcome()` から即座に次を要求しても `Busy` へ落ちないことが契約。`WriteFinished` は Git command の終了通知で、後続の読み直しは含まない。**後続更新完了の境界は `WriteSettled { id, kind, failed }`** — status / refs / graph / stash・worktree の一覧 **と一覧が頼んだ派生の読み(worktree の join と walk = `refresh_worktrees` が flight を離した後に自分で await する)** / author config の publish が済み、次の request を取る直前に出る(head reach の walk だけは含まない = 前の walk が居ると skip する問い)。**`failed: Vec<FollowUp>` が着地しなかった読みを id 付きで名指す**(`OpFailed` は id を持たない)。各読みは失敗を型で返す: refs / status の flight の答えは `Reread::{Same, Moved, Failed}`、listing の task は `Vec<FollowUp>`、グラフは `RefreshOutcome::landed()`。queue idle が必要ならこれを待つ(`support::session::write_settled` が `failed` を返す)
- **タグのリモート状態は `ls-remote --tags` で訊くしかない**(`refs/remotes/` 相当の記録が無い)。届かなかった remote は前回の答えを保つ。尋ねられず読むのは auto fetch 有効かつタグ表示中だけ(`session::catch_up_remote_tags`)。開いた時の fetch(`session::fetch_on_open`)が走った開き方では読まない — fetch が出際に読んでいる。**この読みは書き込みキューの外** — 通すと request が立っている間ポーリングが止まる(`running_write`)。**ズレは fetch では直らない** — `--prune` はタグを残し、`--prune-tags` は exit 1。**読み中に来た要求は `Busy` で捨てる** — この読みの**許可ゲートを通る要求元**(開き終わり / `install_auto_fetch`)は 1 人目の知らない変化を何も持たないので、そこでの `Busy` は同じ remote へ同じ問いを投げている読みの重複で、その読みの publish が答えになる。**取りこぼしを拾うのは次の auto fetch tick** — poll は remote tag を読まない。**答えなかった remote は名前で返る**(`RemoteTagsRead::unread` → 追跡形の `RemoteTagRefreshOutcome::Unanswered`)— 読めなかった読みと「何も動いていない」読みは下流で同じ静寂(イベント無し・スナップショット無し・バッジ無し)なので、バッジを待つ側が落とす物を持たずに予算を丸ごと使う。**バッジ 1 つで fetch は成功のまま**なので、fire-and-forget の側は沈黙
- **リモートのタグを消す refspec は `refs/tags/<名前>` で修飾する**(`remote::delete_remote_tag`)— 裸の名前は向こうの全 ref に照らされるので、同名のブランチが在ると `error: dst refspec … matches more than one` で**両方とも消えない**(2.55)。**修飾形は素だと「向こうに無い」を拒まない**(`warning: deleting a non-existent ref` + exit 0。裸なら `remote ref does not exist` で exit 1)が、**lease を掛けると `[rejected] (stale info)` で拒む**(2.43 / 2.55)。**ブランチも同じく `refs/heads/<名前>` で修飾する**(`remote::delete_remote_branch`)— 裸だと同名タグで両方消えず、向こうが既に消した名前は lease を量る前に `remote ref does not exist` で落ちて素の失敗になる(git の `remote.c` `match_explicit` は `refs/` で始まる名前だけ判定まで進める)
- **リモートのブランチ・タグの削除は画面の先端へ lease を掛ける**(`remote::delete_remote_branch` / `delete_remote_tag` と、それを中に持つ `replace_remote_*`・`Delete both`。ユーザー決定)— oid は押下が運ぶ(remote-tracking は背景の fetch で進むので pin にならない = `PushForce`)。**注釈付きタグの lease は tag object** — peel 先の commit では stale で拒まれ、`<oid>^{}` の綴りも受けない(2.43 / 2.55)。画面は commit しか持たない(`RemoteTag::commit`)ので、`remote::tags::lease_on` が撃つ直前に `ls-remote` で object を引き、peel が画面と一致した時だけそれを使う(一致しなければ画面の commit のまま = git が拒む)。**読みで答えの出る拒否は `ReportKind::is_outdated` の 4 種**(`refusal::refusal` / `tag_refusal`): `Outdated`(`fetch first` / `non-fast-forward` / `remote ref updated since checkout`)・`Moved` / `MovedDelete`(`stale info`。ブランチもタグも)・`TagElsewhere`(素のタグ push の `already exists`)で、**追いつく読みまで push と同じ道**: ブランチは `catch_up_after` の fetch、タグは同じ write の中で `read_remote_tags`(`session::tags_moved`)。**素の `Failed` にすると理由が出ない** — 理由は `--porcelain` の stdout に在り、失敗の文(stderr 優先)は `failed to push some refs` だけ。**`already exists` は tag object が違うだけでも返る**(同じ commit の軽量タグ・別の注釈、2.55)ので、`remote::push_tag` は向こうの peel と手元の commit が同じなら成功として返す(向こうの object はそのまま)。**向こうのタグの読み(この判定と削除の lease の object)は push の URL へ訊く**(`remote get-url --push`)— `ls-remote <名前>` は fetch の URL を読むので、別の repository を指す `pushurl` では送らない先を量る
- **`push --delete` は remote-tracking ref も一緒に消す** — その後の素の `branch --delete` は upstream を失って HEAD とだけ比べ、upstream にだけマージ済みのブランチを `not fully merged` で拒む(2.43 / 2.55)。だから **ブランチの `Delete both` はローカル先行**(lease で断られると「ローカルだけ消え、commit は追いつきの fetch が進めた `<remote>/<b>` から届く(force push されていれば reflog)」半分で止まり、断られた半分の報せで終わる — 手元を消す前の `push --dry-run` はしない。ユーザー決定)、**タグの `Delete both` はリモート先行**(タグに追跡 ref は無く、lease の拒否で何も触らずに止まる)— `session::delete_branch_everywhere` / `delete_tag_everywhere`

- **イベント列は基準位置で切る** — `sink.events.clear()` は reader と競る(clear と次の待ちの間に届いた分ごと消える)。件数で待つ時は先に `len()` を控えて `evs[from..]` を読み、スナップショット数も base を控えて `settle(base + 1)` を待つ(`session_integration::query` の形)
- **hook で reader を停める配信は `block_in_place` の下で走らせる**(`CaptureSink::event`)。**素の park は Linux で確定的に止まる**: 子プロセスの終了(pidfd)・pipe・`Patience` のタイマは全部 hook に塞がれた worker の epoll の中で、外から起こす者が無いので 0% CPU のまま gate の天井を踏む。Windows では見えない。`worker_threads = 2` を明記する — `block_in_place` は current_thread を拒み、`hook_once` は arm 時に `num_workers >= 2` を assert する
- **2 段ストリーミングの fast pass は、開き中は着地が保証されない** — 追い越した再構築が無言で飲む。開き中の assert は「在れば swap より前」の順序だけにし、**存在と行数の網は settled な baseline の後のトグルで張る**(baseline 後は誰も log token を取れないので fast pass は必ず語る — `window::tag_only_commits_follow_the_include_tags_option` 後半の形)
- **`stage::discard_chosen` の bucket は呼び手(選択)が言う** — 両側に変更のあるファイルは unstaged / staged に 1 行ずつ持ち、「どちらの行を選んだか」は status では復元できない。status を読むのは staged リネームの旧名を足すためだけで、write ロックの中で読む(UI で集めた一覧は前に並んだ書き込みより古い)。コマンドは unstaged(`restore --worktree`)→ untracked(`clean`)→ staged(`restore --staged --worktree`)の順に最大 3 本
- **C の build script は解禁(ユーザー決定)** — tree-sitter の文法 crate 群のため。画像経路が純 Rust である条件は platitude-core/Cargo.toml のコメントが正
- `session::published` はグラフの walk が行に「リモートが既に持っている」印を付ける経路(`LogRow::published`)。**窓の中だけで数えて厳密**な根拠は `--date-order` で、親は全ての子より後にしか出ない = 行はトポロジカルな prefix なので、窓の中の行がリモート tip の祖先ならその tip も窓の中に居る。tips は refs スナップショット(`RefsSnapshot.remotes`)から取る — `LabelIndex` の label map はローカルと同名のリモートを chip に畳んで落とす(`build_label_map` の `joins.folded`)ので、名前が一致する時だけ tip が消える。スナップショット未着の pass だけ `refs::remote_tips` を撃つ — open では walk が先に着きうるが、**初回の refs 読みは `refs_moved` にならない**(比較対象が無い)ので、そこで印を落とすと誰も直しに来ない。`--remotes` にタグは入らないので tip はブランチだけ
- `publish::range_rewrites_published` は同じ問いの**範囲版**を、walk が印を付けた行に訊く経路(呼ぶのは `GraphModel.rebaseRewritesPublished`)。`onto..head` に印の付いた行が 1 つでも在るか = 2 色を親へ流す 1 パスで、行が walk 順(親は全ての子より後)である限り最初の当たりで抜けられる。**`state_of` の 2 プロセスと同じ答えを返すのは窓の中だけ** — 窓外は倒れる方向が両端で違う(head が窓外 = 範囲が空 = `false` / onto が窓外 = head の到達分が丸ごと範囲。後者は「窓より古い名前への rebase」の正解でもある)。`LogRow::parents` は sift 後なので stash は第 1 親だけ・WIP 行は空(描く leash は親ではない)
- **詳細の要求番号は結果キューとUI照合まで保持する** — 完了順で1件に潰すとA→BのB→A完了でBを失い、OIDだけの照合はA→B→Aの古いAを通す。番号はfeedがセッションを跨ぐためプロセス内で単調増加とし、古い読みはキャンセルする。失敗も番号付きで送り、現要求と照合したUIだけがエラー面へ渡す。
- **画像プレビューの blob 側は一時ファイルへストリームで書く**(`preview::PreviewFiles` / `write_blob`。置き場は `temp_dir()/platitude-gg-<pid>/s<セッション連番>/<diff epoch>-<old|new>.<ext>`)。掃除の規則は epoch: `publish_diff` が読みを公開する直前に `sweep_before(epoch)` = 書き終えた(settled)読みのうち epoch 未満を消す(画像でない読みも掃く — ペインは移っている)。書きかけの読みは番号に関わらず残す(遅い読みが速い読みの後に着いても、ペインに渡すファイルが在る)。最後のセッションの Drop は run ディレクトリも `remove_dir` する。**「最後」は生存セッション数**(`preview::SESSIONS` の `Mutex<usize>` を Drop が握ったまま消す) — 空の run ディレクトリは「まだ何も書いていないセッションのもの」で、それを消すと相手の `create_dir_all`(親と子で 2 手)が 2 手目で `NotFound` になり(Linux は ENOENT、Windows は削除保留の `ERROR_ACCESS_DENIED` も混じる)、side が file 無しの size only で着地する。同じファイルの再読みは新しい名前(URL が変わらないと `Image` が再読込しない)。網は `preview_integration` と `session_integration::query::a_pictures_file_goes_with_the_pane_and_its_directory_with_the_session`(size only で着地した読みはその場で赤くする。判定は `wait_for` の外へ出す: 述語は sink の events lock の中で呼ばれ、そこで panic すると lock が毒になる)。なぜ size only で着地したかは side が持ち歩く(`PreviewSide::unwritten` = `WriteBlobError` の文。`write_blob` の 3 段をパスごと名乗る)。素の `Io(#[from] std::io::Error)` では `NotFound` だけでどの段が落ちたか読めず、file 無しの side は「絵が要求されなかった side」と区別が付かない
- **コマンドログの行が「利用者の doing か」は行に付いて回る**(`CommandStarted.asked`。rules/core.md §コマンドログ — セッションが `Kept` の 3 ハンドルを挿す口は `GitExecutor::observed`)— 頼んでいない行は赤い印もパネルも動かさない。**開いたパネルは、それを開けたコマンドを持っていなければならない**。背景の読みで記録しない時は `records()` で早期に降りる
- **待つ述語の偽陽性の実例**(rules/core.md §待つ述語): 空の台帳でも `0 landing(s) in line` と言うので、`"landing"` を探す待ちは常に即真
- **baseline は開始条件を列挙して待つ** — `Opened` は path を受理しただけで、その後の refs / status / log は未完了。snapshot event も reader 内から送られ、その後に graph refresh を要求し得る。`opening_snapshots` → `wait_for_snapshot_reads` → tracked graph refresh → 追い出した pass の停止(`wait_for_graph_passes` — 要求は前の pass を cancel するだけで、cancel は止まった証拠ではない)→ 着地した pass の順で閉じる(`CaptureSink::opened_graph`)
- **完了境界を足した先例**(rules/core.md §正しさは因果で待つ): `RefreshTask` / `RefreshOutcome` / `RemoteTagRefreshTask`、タイマは `RepoSession::auto_fetch_ticker`。**複合操作の失敗後に走ってよい読み取り**の先例は `catch_up_after` の fetch(§複合操作は 1 手目が失敗したら止める)
- **`poll_once` で門に止める先例**(rules/core.md §競合の相手は手で進める): `state_tests` / `read_flight` の tests、`session_integration` の diff の読み。spawn した相手に到着を言わせる境界は `ReadFlight::wait_for_askers`

- **時間の仕様を固定する先例**(rules/core.md §時間の仕様は機能テストから外す): タイマの「間隔が来たら 1 回・停止が overdue の tick に勝つ・最初の tick は間隔 1 つ先」は `session::auto_fetch::drive_auto_fetch` / `AutoFetchClock` の単体テスト。統合テストは全 tick を `RepoSession::auto_fetch_ticker` で手で進める
- **`cargo xtask waits` が読む範囲**(rules/core.md §waits。名指す形の例: 答えを捨てた待ちは `let _ =`): 統合スイート + support・各クレートの `#[cfg(test)]` 区画(`mod` / `fn` / `impl`、`all(test, …)` / `any(test, …)` も。`mod x;` は `#[path]` まで追う)/ `*_tests.rs`・`tst_*.qml`。試験装置 = xtask の `src` と app のハーネス両半分(動詞の QML `src/auto` と、run を運転・観測する Rust `src/harness`)で、どれも本体まで読む。**製品本文は対象外**
- **偶発的な赤は再現条件と失敗を残して、当該変更で直すか専用 cleanup task に切り出す**。本格的な flaky cleanup task だけ反復 campaign を行う — 対象を再現に必要な最小 suite に絞り、観測された OS・runner の並走・負荷形態を含める。修正した実装ごとに 0 から数え、最低 10 回連続 OK。全 workspace / 段 2 は最後に 1 回
