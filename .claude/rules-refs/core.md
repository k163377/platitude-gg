## git サブプロセス規約(各論)

- **`GIT_LITERAL_PATHSPECS` は使わない** — git 内部の pathspec magic まで無効化し、`git stash push -u` が成功を報告しながら untracked を一切 stash しなくなる(実測)。パスは 1 件ずつ `:(literal)` で包む(`process::literal_pathspec`)。`--no-index` の引数は pathspec ではないので付けない
- `git merge --continue` / `git rebase --continue` は**引数を一切受け付けない**(`--no-edit` も不可)。`--no-edit` を渡すのは cherry-pick / revert のみ
- **`git switch --merge` は使わない** — conflict しても exit 0 の「成功」で着地し、`MERGE_HEAD` を作らないので `merge --abort` が効かず(素の switch も「needs merge」で拒まれ、逃げ道は捨てる `switch --force` だけ)、さらに **staged が 1 つでもあると衝突ファイルでなくても拒否**する。未コミット変更を移動先へ運ぶのは **stash → switch → `stash pop --index`**(`session::carry_across`。**switch が拒否した時に自動で回り直す** — 尋ねない)。staged / unstaged の区別が残り、conflict 時は stash が残って戻れる
- **`git stash pop` の非ゼロ終了は「何も起きなかった」を意味しない** — 作業ツリー側の conflict なら**マージ済み**でマーカーを残し stash も残す(`Index was not unstashed`)が、staged 側が衝突すると**丸ごと拒否**して何もしない(`conflicts in index. Try without --index.` → `--index` 無しで再試行する)。判定は exit code ではなく status の unmerged 有無で行う(実測)
- **終了コードを自分で読むコマンドには `answers_by_code()` を付ける** — 付けないとコマンドログが勝手に開く。対象は `switch`(exit 1 = 「作業が邪魔」= stash で回り直す合図)・**`rebase`(素・`--interactive` とも)**(exit 1 = 同じ拒否か、途中で止まったか。**どちらも画面に着地を持つ**)・**`cherry-pick` / `revert`(`--skip` も)**(exit 1 = conflict で止まったか、写すものが残っていなかったか。後者は下の項)・`stash pop` / `pop --index`(exit 1 = conflict 着地か無処理かは tree が決める)・`rev-parse --verify --quiet refs/stash`(exit 1 = 「stash が 1 つも無い」。**stash を持ったことのない全リポジトリが返す**)。操作が本当に失敗したかは書き込みの答えが言う(規約 §git が言ったことを読む場所)— **ログを持ち上げるのはその答えの側**(`RepoPage` の `lastWriteError`)なので、付けても止まった rebase の文言は今までどおりログを開く
- **`--autostash` はどこにも渡さない**(`RebaseOptions` にフィールドが無い)— ブランチ単位の `rebase` onto も replay(`rebase --interactive`)も、未コミット変更は switch と同じ自前の carry で運ぶ(`session::carry_across_rewrite`。素のまま撃つ → git が「作業が邪魔」で拒んだら stash → rebase → `pop --index`)。**決め手は 1 つで、autostash は素の `stash apply` で戻す = staged が全部 unstaged になる**(`--index` を渡す口が無い。実測)。止まっている間の autostash が `stash list` に出ないのは事実だが**理由としては軽い** — `.git/rebase-merge/autostash` は普通のコミットの oid で、読めば出せる。**gc でも消えない**(`gc --prune=now` を撃っても生き残る。実測)。**代わりに捨てているのは自動復帰** — autostash は `--continue` / `--abort` の後に git が戻すが、こちらの stash は人が戻す。**止まった時は `pop` しない** — unmerged のある index へ git は書かず、何もしないまま conflict を報告する(下の行と同じ罠)。判定は `opstate::detect`
- **cherry-pick と revert は「空になった」を別々の言葉と別々の状態で答える**(いずれも実測 2.55・`integrate_integration`)。写す先が既に同じ内容を持っている時、**cherry-pick は `CHERRY_PICK_HEAD` を残して `The previous cherry-pick is now empty` と stderr で言う**が、**revert はそのメッセージに辿り着かない** — `--allow-empty` を持たない(git がフラグごと拒む)ので、書こうとした commit が `nothing to commit` で拒まれて終わる = **stderr は空・stdout に git status**(`failure_message()` がそちらを拾う)。しかも状態の残り方が 3 通り: cherry-pick は marker あり / **単体の revert は marker も sequencer も無し**(`--skip` は `no revert in progress` で **128** = コマンドログに赤い行)/ **複数の revert は marker 無しで sequencer だけ**(`opstate::detect` は None を返すので、`opstate::sequence_pending` を見ないと**残骸を残したまま「きれい」と答える**)。判定は `integrate::left_nothing_to_record` と `still_stepping` の 2 か所だけに置く
- **元から空のコミットは `--allow-empty` で写す** — 付けないと git は**「後から空になった」ものと同じ言葉で止める**ので、停止の文言では区別が付かない。付ければ前者は着地し、後者だけが止まる = `--skip` を撃ってよい停止に絞れる。**`--empty=drop` は使えない**(cherry-pick / revert に届いたのは git 2.45 で、最低バージョンより後)
- **拒否の見分けは `integrate::work_is_in_the_way` の 1 か所**(`cannot rebase:` + `unstaged changes` / `uncommitted changes`)。**素の rebase と `--interactive` は同じ文言で拒む**(実測 `integrate_integration`)ので、carry も答えの型(`integrate::RebaseOutcome`)も 2 つに割らない — 割ると「どちらの入口から書き換えたか」で staging の運命が変わる状態がまた作れてしまう。**未追跡だけの木は拒まれない**ので stash も取らない
- **`session_integration::rewrite_route` は先頭一致で読む** — 止まった rebase の後の status refresh が `rev-parse --git-path rebase-merge/msgnum`(`conflict::rebase_progress`)を撃つので、部分一致では**背景読みが 4 手目の `rebase` に化ける**(実測)
- **`stash pop` の非ゼロを conflict と読んでよいのは、元の tree に unmerged が無かった時だけ** — git は unmerged なファイルがある index へは戻さず**丸ごと拒否**する(`could not write index` / `<path>: needs merge`)ので、後に残る conflict は元のもの。前後を比べずに `conflicts_now` だけを見ると、何もしなかった pop が成功に化ける(実測。`session::stash_pop` の `settled_first`)
- **`rev-list --exclude` のパターンは名前空間を外して書く** — `--branches` に対しては `refs/heads/` を**付けない**(`--exclude=refs/heads/main --branches` は何も除外せず、除外したつもりの ref が negative に残るので**「他の誰かが掴んでいる」が常に真**になる。エラーも警告も出ない。実測)。同じ理由で `--tags` には `refs/tags/` を、`--remotes` には `refs/remotes/` を付けない。`--glob` / `--all` だけは `refs/` 始まりで書く
- **`--glob=<pattern>` は階層にしか当たらない** — `--glob=refs/stash` は refs/stash を 1 つも拾わない(`--glob=refs/stash*` なら拾う。実測)。素の rev として `refs/stash` を渡す手もあるが、**stash が 1 つも無いリポジトリで `fatal: ambiguous argument`** になり、逃げの `--ignore-missing` は**間違った oid まで黙って捨てる**(= 「何も残らない」= 安全側と逆の答え)。`reachable::command` はこれで `--glob` を採っている
- **`--all` で HEAD を外すことはできない** — `--all` は refs/ に加えて HEAD も tip に入れるので、`--exclude=<現在のブランチ> --all` でもそのブランチの先端が negative に残る(実測)。現在のブランチを外したい walk は `--branches --remotes` を明示的に並べる
- `git config <key> <value>` に **`--` セパレータを付けない**(`--` 自体が値として保存される)。ダッシュ始まりの値はそのまま渡して通る
- **`config --get-regexp` は全レベルを低い順に並べて返す — 実効値は最後の行**。1 件目で判定すると system の設定が常に勝つ:Git for Windows のインストーラは system の gitconfig に `core.autocrlf=true` を書くので、リポジトリが `false` を持っていても 1 行目は `true`(実測。2 行返り順序は system → local)。**単一キーなら `--get`(最後の値を返す)、複数キーを 1 spawn で取るなら最後の出現で上書きしながら読む**。テストで踏むのは統合テストだけ — TestRepo が隔離するのは自分が撃つ git で、**コードの側は開発機の system / global 設定を見る**
- **identity(`user.name` / `user.email`)に独自バリデーションを足さない** — git が拒むのは**空の name だけ**(空 email は通り author 行が `<>` になる)。`<` `>` と改行は author 行から黙って落とされ、前後の空白・句読点は削られる。config 書き込み時に改行は `\n` にエスケープされるので設定注入は起きない(実測)
- **identity の 2 連書きは原子的にできない。だから書いた後に読み直し、違えば 1 回だけ撃ち直す**(`identity::set_identity` → `IdentityWrite`)。**config のロックは呼び出しごとに取って離す**ので、1 手目が通って 2 手目がロックを失うと**半端な identity が残る** — しかも `Identity::is_complete()` は真なので、**付け替え(個人用 → 仕事用)では新しい名前 + 古いアドレスが「完成した identity」として黙って居座り**、以後のコミットがその組み合わせで記録される。**原子化する道は無い**(いずれも実測): `git config` は**1 プロセス 1 キー**でバッチ形式が無く、`git config --edit` は**ロックを取らない**(エディタに渡るのは lock ファイルではなく実ファイルで、開いている間に別プロセスの `config` 書き込みが着地する)。自分で `.gitconfig.lock` を取るのは git のロック規約と config ライタの再実装。**libgit2 には `git_config_lock` + `git_transaction_commit` があるが、絶対制約で閉じている道**。**代わりに買うのは収束と正直さ** — set は冪等なので 2 パス目は安全で、ロック競合は「2 手目の spawn の間だけ誰かが持っていた」= transient(libgit2 も同じ結論で rename をリトライしている)。**2 回で止める**(競合でない失敗は何度撃っても同じ)。**読み直しは実効設定を読む**ので、repo-local が global 書き込みの上に座っている場合も同じ 1 本が捕まえる。**判定は `name_saved` / `email_saved` の対**で、書き込みが失敗しても `message` を持って `Ok` を返す(**「何が入ったか」を答えられなくなった時だけ `Err`**)。**書く前に読んで失敗時に戻す形は採らない** — 戻す書き込みが同じロックを踏むので保証にならない
- **半端を再現するテストは多値の `user.email`**(`identity_integration`)。`--add` を 2 回打ったキーへの素の set は `cannot overwrite multiple values` で **exit 5** に落ち、**隣の `user.name` は通る**(実測)= ロック競合と同じ形が決定的に作れる。ロックそのものは `.git/config.lock` を先置きすれば「どちらも着地しない」側が作れる(**読みはロックを要らない**ので読み直しは答える)
- **署名の有無を `%G?` だけで判定しない** — SSH 署名は `gpg.ssh.allowedSignersFile` 未設定だと未署名と同じ `N` を返す。`git cat-file commit` のヘッダ(`gpgsig`)で存在を確認する。署名パスフレーズはアプリが扱わない(gpg-agent / ssh-agent の pinentry に委譲。**GUI pinentry 必須** — サブプロセスに端末が無い)
- **`ls-files --eol` は worktree の実ファイルを読む** — `w/` 列のために内容を全部読むので、グロブを渡すと基準リポジトリ級で数十秒(`JetBrains/kotlin` 全件 24.7s / 120MB のファイル 1 件 213ms、実測)。**候補列挙(`ls-files`、索引のみ = 64,012 件ヒットで 85ms)と EOL 読み(`--eol` に確定した数パスだけ = 42ms)を必ず別コマンドに分ける**。未チェックアウトのパスは `w/` が空で返る
- **改行コードの判定は patch の bytes から**(`eol::read`)。`ls-files --eol` は「今どう見えるか」で、問うているのは「この変更が何をしたか」— 元から混在のファイルはこの変更のせいではないし、同じファイルが変更の 1 行で警告に変わる。**どの行が新しいかは diff しか知らない**。`ls-files --eol` を使うのは未追跡ファイル(patch がまだ無い = 「何で終わっているか」が問いのすべて)と、近傍の標本を読む時だけ
- **`diff --ignore-cr-at-eol` で作った patch は `apply` できない**(実測 `patch does not apply`)。EOL のみの差に掛けると diff が空になる一方 status は modified のまま — 表示用と staging 用で diff の bytes を分けない不変条件(`details::file_diff_raw`)を壊すので使わない
- **worktree の diff は index 空間で出る** — `core.autocrlf=true` でも patch に CR は現れず、`apply --cached` / `apply -R` はそのまま通る(untracked の `--no-index` にも変換が効き `git add` と結果が一致する)。**index blob に CR があるファイルは `autocrlf=true` でも変換されない**ので、設定を切り替えても全ファイルが modified にはならない(いずれも実測)
- **`git mergetool` は `--no-prompt` だけでは stdin を踏む**(いずれも同梱スクリプトで確認・`conflict::mergetool`): ツール未設定だと git が推測して `guessed_merge_tool` を立て、**`--no-prompt` を無視して**確認を stdin に出す(閉じているので失敗)→ **`--tool=` を必ず明示**する。**`--gui` も必須** — 付けないと git は `merge.tool` しか見ず、`configured_tool()` が先に読む `merge.guitool` と食い違う。**`mergetool.writeToTemp=true` を撃つ**(既定 false は一時ファイルを衝突ファイルの隣に作り、WIP ペインが untracked で埋まる)。`keepBackup` は触らない(`.orig` は利用者の安全網)。**引数なしで撃たない**(全衝突ファイルを順に開き、その間ずっと書き込みキューが塞がる)。**自前 `cmd` のツールは exit code を信用されない** — git は BACKUP を touch してから mtime を比べ、動いていなければ stdin で聞く = **保存せず閉じると「失敗」で返りマーカーが戻る**(ハングはしない)
- **`git mergetool --tool-help` は Windows で約 8 秒**(warm で 3 回とも 8.1〜8.3s、実測)。`show_tool_names` が同梱定義 ~25 本を**2 周 source** し、1 本ごとに `is_available` が PATH かレジストリ + Program Files を走査するため。**書き込みキューに載せない・誰も待たせない・プロセスで 1 回だけ**(`conflict::available_tools` の `OnceCell`。何が入っているかは計算機の性質でリポジトリの性質ではない)。`--gui` を付けても絞られない(`mode_ok` は diff / merge の別で GUI 判定ではない)ので、**端末ツールを外すのは説明文の `(requires a graphical session)` を見るしかない** = 人間向け出力のパース。**壊れ方が無害な方向にしか行かないことが条件**(取れなければ候補ゼロ = 自由入力のまま)。自前定義は `config --get-regexp '^mergetool\..*\.cmd$'` が 34ms で返すので、そちらは絞らず即出す

## セッション・実装の決定事項(各論)

- **メモリの内訳は `cargo xtask perf --breakdown` で出す**(推測しない)。`memprobe` feature の計数グローバルアロケータが Rust ヒープの実数を持ち(Qt は C++ の `operator new` を通るのでこの境界が「アプリのデータ」と「その下の道具」を正確に分ける)、`mem::Footprint` が中身を保持者へ割り当て、**名前の付かない残りを残りとして印字する** — 割り当ての取りこぼしは残りが膨らむ形で出るので総量が嘘にならない。**サイズ級別(`classes=`)は bytes と件数の両方**を出す: 1 個の 30MB バッファと 3 万個の小ノードは同じ bytes で全く別の話になる。実測記録は [ci/baseline/perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md)
- **refs に比例する常駐データは「1 要素の器」を作らない** — タグ 45,901 本で実測した 3 つ: `BTreeMap` の内側マップは 1 件でも **11 スロットのノードを丸ごと確保**する(45,901 個で 43.5MB → 平坦な整列 Vec の `RemoteTagIndex` で 6.5MB)/ `Vec` は `push` 1 回で **4 スロット要求**するので `HashMap<K, Vec<V>>` は 47,715 個の 4 スロット Vec + テーブルで 20.5MB(整列 Vec + 二分探索の `LabelIndex` で 6.4MB)/ 40 字の hex を `String` で持つと 1 行 1 確保(`BranchItem` / `TagItem` は `Oid` を持ち、表示する所で綴る)。**`String` → `Vec<u8>` に替えても 1 バイトも減らない**(どちらも 24 バイト + capacity)— 減るのは**表現を変えた時だけ**
- **メモリ予算の 44% は空リポジトリで既に埋まっている**(実測 131MB = Qt ランタイム + QML エンジン + シーングラフ。その時点の Rust ヒープは 1.2MB)。予算の議論はこの床の上で行う — アプリ側のデータをゼロにしても 131MB は動かない

- interactive rebase は `GIT_SEQUENCE_EDITOR` に**別実行ファイル `pg-todo-editor`** を差す方式。**配布物に同梱必須**(本体と同じディレクトリ)
- **全行が `drop` のプランを拒むのは `--root` の時だけ**(`sequencer::rebase_interactive`)— 足場があれば git はブランチを upstream へ置いて成功する。`--root` にはそれが無く、git が用意する placeholder へ replay するので、全行落とすと**空 tree・空メッセージのコミット**が先端に残る(いずれも実測)。**全行 drop を避けるために範囲を 1 つ広げない** — 下にマージが居るだけでそれが範囲に入り、`plan_edit` が**触るはずのない replay を拒む**(`Edit::depth` は squash だけが 2)
- **テストが差し込む実行ファイルは rename で置く** — Linux は**書き込みで開かれているファイルを exec できない**(`ETXTBSY`)。`session_integration` の replay 系 5 本は `pg-todo-editor` を**テストバイナリの隣**(`target/debug/deps/`。session が `current_exe()` から探すため)へ置いてから git に渡すので、素の `fs::copy` を各テストが撃つと**片方の write fd の下でもう片方が exec** する。git は自分では失敗せず `sh` が `pg-todo-editor: 1: …: Text file busy` を返す = **rebase が失敗したように見える**。落ちるテストが毎回入れ替わるので interactive rebase 側のロジック不具合に見えるが、**同じ 5 本の持ち回り**なら疑うのはここ(実測: 24 スレッドで 8 回中 6 回赤 → `Once` + staging 名へ copy して `rename` で publish 後は 12 回中 0 回。`the_helper_is_replaced_rather_than_written_over` が inode で固定)
  - **`--test-threads` を下げて隠さない** — 4 なら通る(実測)が、レースは残り CI のコア数で戻ってくる。**Windows では出ない**ので `cargo xtask linux` でしか観測できない
  - `Once` は「1 回だけ copy する」ためではなく**待たせる**ために要る(call_once から戻った = copy 完了なので、exec が copy 中に重ならない)。`rename` はその上で `target/` を共有する別プロセスまで面倒を見る。**staging 名を並行して使い回すと publish されるのが書きかけになる**ので、名前を 1 つにするなら Once と対で使う
  - **`Once` + rename が塞ぐのは「同時に copy が走ること」だけで、「fork が握った write fd」は別物** — `rename` は inode を保つので publish されるのは copy が write で開いていた inode そのもの。`i_writecount` は open file description 単位なので、**copy の最中に別スレッドが git を fork すると子が同じ fd を継承**し、`CLOEXEC` が閉じるのは子の `execve` = そこまでは exec できない(`ETXTBSY`)。**fork した側のスレッドには見えない窓**(`spawn` は子の execve でエラーパイプが閉じてから戻る)で、隣のスレッドだけが踏む。**copy が終わった後に出る**ので rename では防げず、当たるのは `Once` の外で publish する `the_helper_is_replaced_rather_than_written_over`(実測: 8 回中 1 回。fork と execve の間で 300ms 眠る子を作ると 100% 再現)。**手当ては exec 側の `ETXTBSY` リトライ**(`run_published_helper`。cargo / rustup が自分で書いたバイナリの周りに置いているのと同じ形)で、待つのではなく一時エラーを撃ち直す — 最後の答えがそのままテストへ渡る
- **グラフの walk は `--date-order`(`--topo-order` を使わない)** — `--topo-order` は「独立した履歴を混ぜない」ことを保証する = **繋がっていない系列を丸ごと端へ寄せる**ので、gh-pages のような孤立ルートが**日付では 2 行目なのに 260 行目に沈む**(実測: `sealed-class-enumizer` の `origin/gh-pages` が 323 行中 322 行目。行自体もチップも正しく出ているので「消えた」ようにしか見えない)。**沈むのは先端が全体で最新でない時だけ** — 最新なら topo でも先頭に出るため、**この形のテストは「孤立側を作った後にもう 1 つ本流へコミットする」まで書かないと topo でも緑になる**(`session_integration::an_independent_history_sits_where_its_date_puts_it`)。`--date-order` も**親を子より先に出さない保証は同じ**(GraphBuilder の前提・stash の合成親の sift もこれに乗っている)。代償はレーンが増えること(kotlin で 36 → 41 本)と本流の連続性が切れること、得るものは他 GUI と同じ時系列。速度は落ちない(kotlin の 2000 行 walk で 685ms → 619ms、実測)。**レーンが増えるのは kotlin のように本当に多系列が同時に生きている履歴だけで、pull request 型の履歴では逆に激減する** — topo は「本流のマージ列を先に流し切る」ので**マージ 1 本につきレーンが 1 本開きっぱなしになり、横スクロールしないと件名が読めない**幅まで伸びる(同時に開いたレーンの最大数の実測: kogera 27 → 5・jackson-module-kotlin 277 → 9・kotlin 26 → 34)。**この形は「ずっと横に広がっていく」という見え方で報告される**(2026-08-08 kogera で報告 → `--date-order` 後は 1451 行を通して最大 5 本、GitKraken の同じ位置と行順まで一致)
- グラフは **2 段ストリーミング**(タグ無し即描画→タグ込みを単一 drain で無フリッカー置換。44k タグのフロンティア初期化コスト対策)+ `--max-count=2000` ウィンドウ。**WIP(未コミット)を HEAD の子の仮想行**として、**stash を walk 参加の実行行**として描く(合成親コミットは sift で除去)— いずれも `platitude-core::session` 参照。**バックグラウンド更新(auto fetch 後・write 後・dirty ⇄ clean 変化)は `refresh_log()`** = オフスクリーン構築→送信済み行と一致ならイベントを一切出さない(アイドル中のチラつき対策)。リセット→ストリーミングは open / Reload / タグ切替 / 件数変更のみ
- **行番号を渡すイベントは、渡した先が見ている世代を名乗る**(`SessionEvent::LabelsChanged` の `generation` = `Shared::generation`)。チップの差分は「今画面に在るグラフ」の行番号で作られるので、作ってから送るまでの間に walk が入れ替わると**別のコミットに貼り付く**(WIP 行が 1 つ増えるだけで全行がずれる)。しかも**自己修復しない** — session は貼れたつもりで `applied` を持つので次の読みは差分ゼロ、次の再構築も送信済みと一致して swap を省く。守りは 2 つ揃って要る: **読みと送信を同じ `shared` ロックの中で行う**(`apply_refs` / `run_swap_pass` / `run_direct_pass` / `emit_rows` すべて)ことで割り込みの窓自体を消し、**世代タグ**が「送ったが採用されなかったパス」を拾う。**`Shared::generation` は log_gen ではない** — カウンタは lock を取る前に上がり、**一致して swap を省いたパスも上げる**ので、それを写すと以後のチップが全部落ちる(実測・`remote_tags_integration` が赤で捕まえた)。更新するのはイベントを送る行の隣だけ
- **アバターの画像は取り込む時に作り直す**(`picture::normalize`)— 保管庫が持つのは**中央の正方を切った 256px の PNG だけ**で、選ばれたファイルは読むだけ。**ファイルサイズの上限は画素を 1 つも縛らない**(平坦な PNG はファイルの約 1,000 倍にデコードする = 4MB の内側に 4GB の絵が入る。普通のスマホ写真でも常駐 46MB。実測 [ci/baseline/avatar-shrink-windows-x64.md](../../ci/baseline/avatar-shrink-windows-x64.md))ので、**寸法はヘッダだけ読んでデコード前に弾く**(`picture::MAX_PIXELS`)。**形式は中身で決める**(`avatar::EXTENSIONS` はファイルダイアログの絞り込み専用で、判定には使わない)。**保管庫に入るものは必ず描ける**のが不変条件 —— 描画側(`GraphRowDelegate.face()`)は url があれば identicon へ落ちないので、読めない画像を入れると**輪だけの空円**になり、理由を言える場所がもう無い。**`png` の `zlib-rs` feature を立てない**(flate2 が C の zlib に倒れ、C ツールチェーン不要という 3OS ビルドの前提が変わる)
- **アプリ自身の 2 ファイルは `settings` モジュール**(`settings.toml` = 人が決めた値 / `state.toml` = 触っているうちに決まった値)。**分けるのは上書き事故のため** — 1 ファイルだと、アプリを起動したままエディタで直した設定を次の state フラッシュ(ペインを 1px ドラッグすれば走る)が消す。「レイアウトを戻したい → `state.toml` を消す」も言えなくなる。置き場所は Windows = `%APPDATA%` / `%LOCALAPPDATA`(ウィンドウ位置を roaming に載せない)・XDG = `$XDG_CONFIG_HOME` / `$XDG_STATE_HOME`・macOS = Application Support に両方。**環境変数が無ければ推測せずファイル無しに倒す**。判定は `Store::locate(Platform, &Env)` の純関数なので、実機の無い mac / Linux の配置も Windows 上でテストできる
- **読みは `toml::Table` からキーごとに取る**(derive を使わない)。`#[serde(default)]` が効くのは「キーが無い」時だけで、**キーはあるが型が違うと文書ごと失う**(実測)ため、ひと文字の打ち間違いが全設定のリセットになる。**値域外も型違いと同じに扱う** — 保存された幅 0 は `"wide"` と同じくらい使えない。derive を捨てると `serde_derive` / `syn` がビルドから消える副産物もある(14 → 8 クレート・-38KB 実測)
- **書きは temp + `rename`**。**書きかけのファイルはパースに失敗しない** — `180` が `18` として**読めてしまう**(実測)ので、キー毎フォールバックでは拾えない。rename が失敗したら古いファイルを残したまま諦める(次の tick が撃ち直す)
- **1 つの store を持てるのは 1 プロセスだけ**(`Store::claim`)。2 つが同じ `state.toml` を書くとタブと窓の形が後勝ちで潰し合う(タスクバーのジャンプリストの起動エントリから実際に起きた)。鍵は**カーネルが持つ**(`File::try_lock`)ので、kill でもクラッシュでも必ず外れる = stale ファイルも PID も残らない。**ロックは専用ファイル `lock`** — 2 ファイルは temp + rename で置き換わるので、そこに掛けたロックは最初の flush で**孤児を守る**(実測: Windows で rename は open ハンドル越しに成功し、次のプロセスは新しいファイルを何事もなくロックできた。POSIX の rename は元から開いているファイルを気にしない)。置き場所は **state 側**(per-machine。roaming する `%APPDATA%` に置くと別マシンへ同期される)
- **拒否の理由になるのは `WouldBlock` だけ**。それ以外のエラー(リダイレクトされたプロファイル・ネットワーク共有・答えないファイルシステム)では**ファイルを持ったまま起動する** — ロックが取れないことと、ロックの仕組みが答えないことは別で、後者が窓の開かない理由になってはいけない。**ephemeral な store はロックを持たない**(守る相手が無い)ので、自動化は何本でも並走する
- **開発ビルドは自分の store を持つ**(`Build { tree, debug }` → `platitude-gg/dev` / `dev-<tree>`)。同じツリーの debug と release は 1 つとして扱う(人にとって 1 つのビルドだから)。**初回だけ実 store からコピーする**(`seed_from`。`avatars/` も連れて行く — 索引だけ来ると出ない顔の行が並ぶ)。以後は別々に進む。**`PG_CONFIG_DIR` はビルドに関係なくそのディレクトリ** — 2 回の実行で 1 つを共有する検証がそこに乗っている
- **`PG_*` が 1 つでも立っていたらファイル無しに倒す**(例外は `PG_CONFIG_DIR` と **`PG_LOG`**)。`PG_*` はほぼ全部自動化用なので、1 つでも在れば人が窓の前に居ない。これが無いとスクショ実行が開発者の実設定にウィンドウ位置を書き、次の実行がそこから始まる。**`PG_LOG` を例外にしないとログを上げて自分の窓を触った人が設定を失う** — その変数はうるささを言うだけで誰が運転しているかを言わない
- **両ファイルのパスは `repo_key` を通す**(区切りを `/` に正規化・末尾の `/` を落とす)。同じリポジトリが `[repo.…]` の見出しとタブ一覧で同じ文字列になり、ついでにどちらのファイルにもバックスラッシュのエスケープが出ない。**`\\?\` / `\\.\` だけは触らない** — その接頭辞は Windows へ宛てたもの(パス解析を切る指示)で、書き換えると別の場所を指す
- **今どのパスが担当かを決めるのはキャンセルトークン 1 つ**(`log_cancel`。`restart_log` / `refresh_log` は**呼ばれたその場で**前のトークンを cancel して自分のを挿すので、呼び出し順 = 担当の順)。**`log_gen` はタスクが走り出した順**に振られ、spawn の順は呼び出し順と一致しないので**両方を判定に使うと食い違う** — 呼び出しが新しい方が「世代が古い」と見なされて降り、古い方はトークンが死んでいて降り、**Reload が無反応になる**。判定は担当かどうかで揃える: `run_direct_pass` / `run_swap_pass` は state を触る前に `cancel.is_cancelled()`、`emit_rows` / `emit_wip_row` は `shared.generation` が自分か(= 画面に出ているグラフを作ったのは自分か)。**降ろされたパスは state を一切触らない** — reset すると画面が空になるだけでなく、送信済み行の記録まで消えて**次の再構築が同じ絵を貼り直す**(アイドル中のチラつき)。世代カウンタはメッセージの順序付け専用
- **`restart_log` を撃っても、着地するのがストリームだとは限らない** — 直後に誰かがグラフを求めれば(dirty ⇄ clean を見つけた status 読み・ポーリング・書き込みの後始末)`run_direct_pass` はトークンが死んでいて**何も言わずに降り**(途中で cancel された walk も `LogFinished` / `LogFailed` のどちらも出さない)、後ろの `refresh_log` が `LogReplaced` で置き換える。**運ばれる中身は正しい** — どちらの入口もトークンを挿した後に `log_options()` を読むので、勝った方が必ず新しいオプションを持つ。**待つ側が形を 1 つに決め打つと race を待つことになる**(`session_integration::pass_of` が両方を読む。実測: 負荷の掛かった機械で件数変更が `LogReplaced { generation: 4 }` として着地し、`LogFinished` を待っていたテストが時間切れ)。**swap を省く判定は行とフッタの両方で行う**(`Shared::sent_footer`)— 行だけで比べると、**窓の広さだけが変わってフッタ(`walked` / `truncated`)が動く変更を追い越された時に取りこぼす**(2 コミットで `--max-count=2` → `3` は行が同じまま truncated が倒れる。ストリームは黙って降り、後ろの再構築が「同じ絵」と見て何も送らないので、**グラフは正しいのに「履歴は切られている」と言い続ける**)。**同じオプションの再構築は今までどおり黙る** — 動かないリポジトリを同じ窓で歩けば walked も同じなので、アイドル中の無再描画は変わらない(`background_refresh_swaps_only_on_change` / `a_write_rebuilds_the_graph_once` / `a_poll_rebuilds_the_graph_once`)。追い越しの再現は `session_integration::a_window_change_only_the_footer_notices_still_lands`
- **表示更新はポーリング**(watcher を入れない — WSL / ネットワークで通知が来ず、他 GUI は例外なく watcher + 手動 refresh の両方を持つ)。**契機はフォーカスではなく可視性**(最小化中のみ停止・最前面タブのみ)、間隔は `Metrics.pollIntervalMs`。1 tick = `RepoSession::refresh_poll`(refs + status のみ。前回未了と書き込み中はスキップ)→ どちらかが動いた時だけ `refresh_log()`。**refs が動いたら必ずグラフを作り直す** — チップだけ貼り替えると walk が見ていないコミットを指してチップが消える。コストは [ci/baseline/poll-cost-windows-x64.md](../../ci/baseline/poll-cost-windows-x64.md)
- **タグのリモート状態のデータ**: fetch が `ls-remote --tags` を続けて撃ち(`remote::list_tags`)、名前とピール済みコミットを session が remote 別に保持する(ブランチと違い `refs/remotes/` に相当する記録が無く、fetch 済みタグは手元のものと見分けが付かないため、訊く以外に手が無い)。届かなかった remote は前回の答えを保つ。**尋ねられずに読むのは auto fetch が有効 かつ グラフがタグを出している時だけ**(`session::catch_up_remote_tags`。前者は通信の許可・後者は優先度)。**この読みは書き込みキューを通さない** — 通すと `write_busy` が立ってポーリングが止まり、以後の書き込みが全部バッジ 1 つの後ろに並ぶ。開いた直後(`repo::open` 成功後)と、設定で auto fetch を入れた時の 2 箇所から入る。**ズレは fetch では直らない** — `--prune` は黙って手元のタグを残し、`--prune-tags` は `would clobber existing tag` で exit 1 する。**リモートにしか無いタグ**が残るのは fetch が落とせないコミットを指す時だけで、落とせるものは auto-follow が手元に作る = 状態が消える(いずれも実測)
- **session は 1 ファイルではなく帯ごとの `session/` モジュール** — `mod.rs` が全公開型・`RepoSession` 定義・ライフサイクル・内部ヘルパを持ち、auto_fetch / log / refresh / write / ops_tree / ops_remote / ops_integrate / query / eol / build が各自の `impl RepoSession` ブロック。公開パスは全て `session::` 直下のまま(子へ移ったのは private と impl だけ)。帯またぎの呼び出しは `pub(super)`
