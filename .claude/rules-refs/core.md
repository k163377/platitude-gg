# platitude-core 各論(git の実測挙動・実装の決定事項)

[.claude/rules/core.md](../rules/core.md) の参照資料 — **1 項目 1 行**、コマンド名・モジュール名・関数名で Grep して該当行と前後だけを読み(全読みしない)、追記も 1 行(コード・docs の「core.md」参照はここへ移った行も指す)。

## git サブプロセス規約(各論)

- **`GIT_LITERAL_PATHSPECS` は使わない** — `git stash push -u` が成功を報告しながら untracked を stash しなくなる(実測)。パスは `:(literal)` で包む(`process::literal_pathspec`)。`--no-index` の引数は pathspec ではない
- **`--no-optional-locks` / `GIT_OPTIONAL_LOCKS=0` は `git diff` に効かない** — 作業ツリーの diff は index を refresh し、そのために `.git/index.lock` を取る(実測 2.55: 旗付きの `status` は index を書かないが、旗付きの `diff` は書く。`status` は錠を取る前に旗を訊き、`diff` は訊かない)。この錠は書き込みが**待たずに死ぬ**側なので(`hold_locked_index` は fatal)、キューの外を走るポーリングの diff が commit の錠に当たると commit が落ちる(`fatal: Unable to create ... index.lock: File exists`)。止めるのは `-c diff.autoRefreshIndex=false` で、`process::executor` の `FIXED_ARGS` に常時入っている。**答えは 1 つも変わらない**(実測: stat だけ動いたファイルは patch も `--name-only` も `--quiet` も「変化なし」と答える)が、**代金は index の stat キャッシュが誰にも更新されなくなること** — 読み取りで refresh するコマンドがこれで消えるので、中身が同じまま stat だけ全部動いた作業ツリーは毎回ハッシュし直される(実測 780 ファイルで `status` 72ms 対 refresh 済み 28ms。普通の編集で汚れるのは数本だが、git の外から複製した木は全部汚れる)。**遅い pre-commit フックは錠を握らない** — git は hook を走らせる前に錠を返す(実測: 20 秒眠るフックの最中に `.git/index.lock` は無い)ので、`--preset slowhook` が押さえているのは錠ではなく「書き込みが飛んでいること」だけ。網は `tests/it/exec.rs::a_work_tree_read_leaves_the_index_untouched`
- `git merge --continue` / `git rebase --continue` は引数を受け付けない(`--no-edit` も不可)。`--no-edit` は cherry-pick / revert のみ
- **`git merge` の終了コードは 1 が両義**(実測 2.55: conflict = 1 / マージできない名前 = **1** / `--ff-only` の拒否 = 128 / 作業ツリーが上書きされる = 2)。rebase と違い 1 だけでは答えと失敗を分けられないので、**exit 1 の後に** `opstate::detect` で **merge が立っているか**を訊いて `integrate::Landing::{Done, Stopped}` を返す(`Stopped` は失敗ではない = `SessionEvent::WriteStopped` → エラー帯もログの持ち上げも出さない。2026-08-22 ユーザー報告)。**コードを読まずに marker だけ見ない** — 既に立っている merge の上で撃った merge は `MERGE_HEAD` を残したまま 128(実測 2.55: 未解決なら `unresolved conflict`、解決済みなら `You have not concluded your merge`)。**`--squash` の conflict だけはこの網に掛からない** — `SQUASH_MSG` を書いて `MERGE_HEAD` を作らないので失敗として出る(画面からは撃たない。網は `integrate_integration::merge`)
- **止まった merge を `git commit` で終わらせたものは `merge --continue` と同一**(実測 2.55: 木・2 つの親・メッセージ・走るフック `pre-commit` / `prepare-commit-msg` / `commit-msg` / `post-commit` まで一致。`post-merge` / `pre-merge-commit` はどちらでも走らない = 止まらずに済んだ merge のフック)。**解決結果が HEAD と同一でも書ける**(空のマージコミット)。だから画面は `--continue` の行を持たず commit ボタン 1 つで終わらせる(規約 §進行中の操作から出る)。箱に入れる文言は `conflict::stopped_message`(`MERGE_MSG` からコメント行を落とす — `commit::commit` は `--cleanup=whitespace` なので落とさないと `# Conflicts:` が記録される。`core.commentChar` を変えたリポジトリでは落ちないが、箱に見えているので消せる)。網は `integrate_integration::merge`
- **`git switch --merge` は使わない** — conflict しても exit 0 で `MERGE_HEAD` を作らず `merge --abort` が効かない上、staged が 1 つでもあると拒否(実測)。未コミット変更は stash → switch → `stash pop --index` で運ぶ(`session::carry_across`)
- **`git stash pop` の非ゼロは「無処理」を意味しない** — 作業ツリー conflict はマージ済み+stash 残置、staged 衝突は丸ごと拒否(`conflicts in index. Try without --index.` → `--index` 無しで再試行)。判定は exit code でなく unmerged の有無(実測)
- **`git stash push` は unmerged が 1 本でも在れば丸ごと拒む** — パスを名指しても同じで、conflict していないファイルだけを渡しても `error: could not write index` / `<path>: needs merge` で exit 1、退避は起きない(実測 2.51)。**「その行が conflict か」ではなく「木に conflict が在るか」が答え**なので、退避の可否は `stash::standing` 1 本で決める(`FileRowMenu.canStash` / `BandStashButton.mode`)
- **`commit::commit` は書いた後に何も読まない** — 成功の答えは git の終了コードで、HEAD を読み返す 2 本目のコマンドは自分の理由で失敗しうる = 着地したコミットを失敗として報告する経路になる(だから戻り値は `()`)。動いた先が要る側は書き込みの後段のパスで読む
- **終了コードを自分で読むコマンドには `answers_by_code(<答えのコード>)` を付ける** — 付けないとコマンドログが勝手に開く。対象は `switch` / `rebase` / `merge` / `cherry-pick` / `revert` / `stash pop` / `stash apply`(pop と同じ exit 1 = conflict で載った、の答え。`conflicts_now` の判定も pop と同型)/ `rev-parse refs/stash`(exit 1 = stash ゼロ本。持ったことのない全リポジトリが返す)/ **config の読み取りは `--get` / `--get-regexp` とも全部**(未設定 = exit 1 = 答え。identity / remote list / tracking branches / push plan の upstream / merge tool / autocrlf / mergetool.cmd — 網は `tests/it/config_reads.rs`)/ **HEAD の読み**(`symbolic-ref -q` = exit 1 が detached、`rev-parse --verify -q HEAD` = exit 1 が unborn。`refs::head_state` と `remote` の current_branch)/ untracked の `diff --no-index`(exit 1 = 差分あり = 常態)/ stash rename の移動確認 `rev-parse --verify` — 網は `tests/it/answer_reads.rs`。**`cat-file` には付けられない — 無い側は exit 128 で 0/1 の枠外、しかも「リポジトリが無い」も 128 なので枠を広げると本物の失敗が消える。読む前に `rev-parse --verify -q <spec>` で訊く**(無い側は全部 exit 1 = 答え、在る側は 0 + oid を stdout。unborn HEAD の `HEAD:` / added の `<parent>:` / index に無い `:0:` で実測 2.55。`preview::blob_is_there` が preview と source_text の両方の入口)。代償は git プロセス 1 本 — Windows での 1 本の値段はこのファイルの `process::program` の項(`cat-file` も `diff-tree` も同じで、プロセス生成が支配的)。`cat-file --batch-check` なら exit 0 で "missing" を返せるが **stdin 必須で不可**(プロセス層は stdin を常に閉じる — `scratch.rs`)。失敗判定は書き込みの答え側(規約 §git が言ったことを読む場所)
- **頼まれていない fetch は `Kept::UnaskedUnlessItFails` のハンドルで走る**(`session::write::run_write` の分岐、`exec_unasked_fetch`)— `CommandFeed` が spawn 時の行を握っておき、**git が断った時だけ** `CommandStarted` + `CommandFinished` を後から流す(着地・cancel・`answers_by_code` の答えは流さない)。**理由はパネル側**: 連続 fetch 失敗の 1 回目はパネルを開けるので、その行が無いと開いた先に並ぶのは利用者が最後にやったこと(2026-09-04 ユーザー報告「push を押すとログが立ち上がる」の正体)。**行が「利用者の doing か」は `CommandStarted.asked` で運ぶ** — false の行は app 側で `failed` にも `failure()` にも入らない(`models::commands`)ので、オフラインで毎分開くことはない。網は `session_integration::auto_fetch::an_unasked_fetch_leaves_a_row_only_when_git_says_no`(着地とお断りの 2 本立てで 1 本)
- **答えのコードは 1 とは限らない** — `config --global --unset <key>`(merge editor を空にした時)は「元から無い」を **exit 5** で言う(ファイルが無い時・キーが無い時・multivalue で消せない時が全部 5、実測 2.55。multivalue は消さずに 5 なので「消えた」とは言い切れないが、直後の refresh が本当の値を出す)。1 で印を付けると失敗行になり、設定カードを閉じただけでコマンドパネルが開く(2026-08-21 ユーザー報告)。**枠を広げて 0/1/5 を全部答えにはしない** — 理由は `cat-file` の 128 と同じで、コードの意味はコマンドごと。網は `tests/it/integrate_integration/mergetool.rs`
- **`--autostash` はどこにも渡さない** — autostash の復帰は素の `stash apply` で staged が全部 unstaged になる(`--index` を渡す口が無い。実測)。carry は自前(`session::carry_across_rewrite`)、代償は `--continue` / `--abort` 後の自動復帰。止まった時は `pop` しない — unmerged のある index へ git は書かない(判定は `opstate::detect`)
- **止まった cherry-pick / revert も `Landing::Stopped`** — conflict は exit 1 + 自分の marker(`CHERRY_PICK_HEAD` / `REVERT_HEAD`。複数リビジョンなら sequencer も。実測 2.55)。判定は `integrate::landed` 1 か所で、**exit 1 かつ `InProgress::from_state` が自分と答えた時だけ**(止まった merge の上で撃った cherry-pick は marker が merge のもの)。**この網に掛かるのは conflict だけ** — 汚れた木・読めない名前・unmerged の残る index は全部 exit 128 で marker を残さず、**既に立っている同種の上で撃った時だけ 128 で自分の marker が在る**(実測 2.55 — だからコードを読まずに marker だけ見ると、git の「もう 1 つ動いている」という説明を握り潰す)。空で止まった側は先に `left_nothing_to_record` が拾うのでここへ来ない(着地は `Done` = 「何も起きなかった」)。網は `integrate_integration::pick_revert`
- **止まった rebase も同じ**(2026-08-22 ユーザー判断) — `RebaseOutcome::Stopped`。判定は `integrate::landed` 1 か所で、**exit 1 かつ `rebase-merge` / `rebase-apply` が立っている時だけ**。**コードを読まないと誤読する**: 「既に rebase-merge がある」失敗は marker を残したまま **exit 128**(実測 2.55。拒否と停止だけが 1、読めない upstream も 128)。拒否(`work_is_in_the_way`)を先に見るので carry は変わらない。`Blocked` があるので `Landing` には寄せられず、`build::rewrite_carrying` が carry の後に `Landing` へ落とす(拒否は画面に届かない = 回り直すのが答え)。`squash` / drop / reword も同じ 1 本を通るので 5 経路すべてが `WriteStopped` を出す。網は `integrate_integration::rebase` と `session_integration::carry_rewrite`
- **cherry-pick と revert は「空になった」の答え方が別**(実測 2.55・`integrate_integration`): cherry-pick は `CHERRY_PICK_HEAD` + stderr `The previous cherry-pick is now empty`、revert は `--allow-empty` が無く `nothing to commit` で拒まれ stderr 空・stdout に status。状態も 3 通り — cherry-pick は marker あり / 単体 revert は無し / 複数 revert は sequencer だけ(`opstate::detect` は None → `opstate::sequence_pending` を見ないと残骸を「きれい」と誤答)。判定は `integrate::left_nothing_to_record` / `still_stepping` の 2 か所だけ
- **元から空のコミットは `--allow-empty` で写す** — 付けないと「後から空になった」と同じ文言で止まり区別が付かない。`--empty=drop` は git 2.45 からで最低バージョン外
- **拒否の見分けは `integrate::work_is_in_the_way` の 1 か所** — 素の rebase と `--interactive` は同じ文言で拒む(実測 `integrate_integration`)ので carry も `integrate::RebaseOutcome` も 2 つに割らない。未追跡だけの木は拒まれない = stash も取らない
- **`edit` 停止だけは exit 0 で止まる**(実測 2.55 — 頼まれた停止なので git は失敗に数えない)。`integrate::landed` は **Ok 側でも** `opstate::detect` を訊き、rebasing が立っていれば `Stopped`。なぜ止まったかは `integrate::rebase_standing`(`rebase-merge/amend` の存在 = edit・**その中身 = 対象**。apply backend に edit は無いので merge 側だけ読む)— status refresh が rebasing の間だけ載せる(`StatusLoaded.stop`)。網は `integrate_integration::plan`
- **停止の対象に `stopped-sha` を使わない**(実測 2.55・`an_edit_stop_after_a_reword_names_the_replayed_commit_not_the_todos`)— `stopped-sha` は **todo の元 oid** なので、`edit` の手前に reword / squash / 並べ替えが 1 つでもあると replay 後の HEAD と別物になり、**今の履歴に居ないコミットを名指す**。`rebase-merge/amend` の中身が git 自身の書いた停止時 HEAD(full hex)で、これがカードの名指しと amend の的の両方。全 pick の時だけ両者が一致するので、**全 pick のテストでは差が出ない**
- **`edit` 停止中の amend を「HEAD が停止時のコミットのままか」で門にしない**(実測: 1 回 amend すると HEAD は動き、`rebase-merge/amend` を含め `rebase-merge/` の**どのファイルも追随しない**)。amend と「停止中に端末が上に積んだコミット」を見分けるには ancestry を毎 tick 撃つしかなく、断る先は git 自身が通す操作 = 割に合わない。門は `offers::message_edit` の `editing && HEAD 自身の行` だけ(規約 §フル interactive rebase の edit 停止)
- **`rebase_standing` の Err は前回の stop を保つ**(`RepoSession::rebase_stop_seen`)— 1 tick でも `editing:false` に落ちると出口カードの `--skip` が長押しから素クリックへ戻り、その 1 クリックは停止中のコミットを取り去る。progress は保たない(古い N/M は「進んだ」と読める方が害)
- **`rebase_standing` の `--git-path` の並びは前提** — `rebase-merge/msgnum` / `rebase-merge/end` / `rebase-apply/next` / `rebase-apply/last` / `rebase-merge/amend` の順で、progress は添字の対 `(0,1)` `(2,3)` で読み `amend` は 4 番。**並べ替えても型は変わらないのでコンパイルは通り**、進捗と停止理由が黙って入れ替わる
- **WIP 行は「木が汚れている or 操作が立っている」で出す**(`refresh::publish_status` の wip_dirty)— edit 停止と空停止は木がきれいなまま出口カードへ着地する必要があり、着地は WIP 行(規約 §進行中の操作から出る)。きれいな木 + 操作なしの従来条件はそのまま
- **プラン preview は `rebase_plan::preview`**(from の親を upstream に、merge を先に断り、行が from で始まらなければ off-branch = 別ブランチのクリック。答えは `PlanAnswer` の型付きで文は QML 側)。onto のブランチ名は `for-each-ref refs/heads --points-at`(先頭 1 本、無ければ空 = sha フォールバック)。網は `integrate_integration::plan`
- **プラン実行は先端を釘付けにする**(`RepoSession::rebase_interactive` の `expect_head`)— spawn 直前に `head_oid` と照合し、ずれたら `GitError::Rejected` で何も撃たない(端末や他セッションが動かした履歴の上へ、組んだ todo が黙って落とすものを作らない)
- **立っている操作の上へ rewrite を撃たない — `work_is_in_the_way` では見分けられない**(実測 2.55、網は `integrate_integration::standing_op` / `session_integration::standing_op`)。merge / cherry-pick / revert が立っている木への rebase は素も `--interactive` も `cannot rebase: Your index contains uncommitted changes.` で拒まれ(未解決なら `unstaged changes` が加わる)、**git は操作の名を出さない**ので拒否文言は汚れた木と同一。続く `git stash push` は解決済み+staged の index を書けてしまい、**その操作の marker を道連れに落とす**(`MERGE_HEAD` / `CHERRY_PICK_HEAD` / `REVERT_HEAD` が消える)ため、carry は木を空にして履歴を書き換え、解決をただの staged 変更として戻し、**成功として報告する**。守りは 2 枚: `RepoSession::rebase_interactive` が `opstate::detect().any()`(= 画面の `opText != ""`)で spawn 前に `Rejected`、`build::carry_across_rewrite` が stash の前に `InProgress::from_state` で `Rejected`(5 経路すべての backstop)。**bisect は除く** — stash を跨いで生き残るので carry してよい(`any()` でなく `from_state` を読む理由)。未解決 conflict だけが偶然安全(unmerged な index に stash push が `could not write index` で失敗する)
- **`session_integration::rewrite_route` は先頭一致で読む** — 止まった rebase の後の status refresh が撃つ `rev-parse --git-path rebase-merge/msgnum …`(`integrate::rebase_standing`。プロセス無しで数える `integrate::rebase_progress` とは別物)が部分一致では 4 手目の `rebase` に化ける(実測)
- **`stash pop` の非ゼロを conflict と読めるのは元の tree に unmerged が無かった時だけ** — unmerged のある index へは丸ごと拒否(`needs merge`)で残る conflict は元のもの。`conflicts_now` だけ見ると無処理の pop が成功に化ける(実測。`session::stash_pop` の `settled_first`)
- **`rev-list --exclude` は名前空間を外して書く** — `--branches` に `refs/heads/` を付けると何も除外されず「他の誰かが掴んでいる」が常に真(エラーも警告も無し。実測)。`--tags` / `--remotes` も同様。`--glob` / `--all` だけ `refs/` 始まり
- **`--glob=<pattern>` は階層にしか当たらない** — `--glob=refs/stash` は 0 件(`refs/stash*` なら拾う。実測)。素の rev `refs/stash` は stash 無しで `fatal: ambiguous argument`、`--ignore-missing` は間違った oid も黙って捨てる = 安全側と逆。`reachable::command` は `--glob` を採る
- **`--all` で HEAD は外せない** — `--exclude=<現在のブランチ> --all` でも先端が negative に残る(実測)。外したい walk は `--branches --remotes` を並べる
- `git config <key> <value>` に `--` を付けない(`--` が値として保存される)。ダッシュ始まりの値はそのまま通る
- **`config --get-regexp` は低いレベル順・実効値は最後の行** — 1 件目で判定すると system が常に勝つ(Git for Windows は system に `core.autocrlf=true` を書く。実測)。単一キーは `--get`、複数キーは最後の出現で上書き読み。TestRepo が隔離するのは撃つ git だけで、コード側は開発機の system / global を見る
- **`core.autocrlf` の綴りは git の bool 語彙**(実測 2.55): `input` は大小無視で先に見る / true = `true` `yes` `on` と非ゼロの整数 / false = `false` `no` `off` `0` と**空の値** / 値なしのキー(`=` が無い)は true / それ以外は `fatal: bad boolean config value` で git が動かない。**読みは `None` に倒す**(`eol::setting::AutoCrlf::of_record`)— 「未設定」と同じ席で、設定画面はその 4 つ目の行しか選べないから。**警告(`eol::normalises`)と設定画面は同じ 1 本の読みを通る** — 2 通りに読むと「git が決めているか」に答えが 2 つできる
- **`core.autocrlf` の書きは 1 キーなので撃ち直さない**(identity の 2 連書きと違う)— ただし**先に読む**: `--unset` は無かった時も多値の時も exit 5 で、読んでおくと前者を撃たずに済む(`eol::setting::set`。`identity::local` と同じ理由)。スコープは `--global` / `--local` を必ず綴る(既定に頼らない)
- **identity(`user.name` / `user.email`)に独自バリデーションを足さない** — git が拒むのは空の name だけ(空 email は通り `<>` になる)。`<` `>` 改行は author 行から黙って落ち、config 書き込みは `\n` エスケープで注入は起きない(実測)
- **identity の 2 連書きは原子化できない**(実測: `git config` は 1 プロセス 1 キー・`--edit` はロックを取らない・自前 lock は config ライタ再実装・libgit2 は絶対制約で閉)— 書いた後に実効設定を読み直し、違えば 1 回だけ撃ち直す(`identity::set_identity`)。半端(新 name + 旧 email)は `Identity::is_complete()` 真で黙って居座る。競合でない失敗は何度でも同じ = 2 回で止める。不採用: 書く前に読んで失敗時に戻す(戻しが同じロックを踏む)
- **半端の再現は多値の `user.email`**(`identity_integration`)— `--add` 2 回のキーへの set は `cannot overwrite multiple values` で exit 5、隣の `user.name` は通る(実測)。`.git/config.lock` 先置きで両方不着地も作れる(読みはロック不要)
- **「そのリポジトリ自身が何を書いているか」は `--local` でしか読めない**(`config::get_regexp_local` / `identity::load_local`)— 実効レベルの `--get-regexp` は全レベルを低い順に返すだけで**どのファイルの record かを言わない**ので、継承しているだけの値と自分で書いた値が同じ姿で届く。書き戻しの読み直しも `--local` 側で読む(`identity::set_local_identity`)
- **`--local` の書き込みは「今の値を先に読んで、違うキーだけ撃つ」**(`identity::write_local_pair`)— 空欄 = `--unset` だが、**`--unset` の「元から無い」と「多値なので触れない」は同じ exit 5**(実測 git 2.55。git の doc は 5 と 6 に分かれると書いてあるが分かれない)ので、先に読まないと本物の失敗が無害な答えに化ける。ついでに「何も変えない Save」が git を 1 本も撃たなくなる(2026-08-21 の「無い物の unset がログを開く」報告と同じ形)。**`--local` は set 側にも明示する** — 素の `git config <key> <value>` / `--unset` も既定でローカルに書く(実測: global にしか無いキーの素の `--unset` は exit 5 で global を触らない)が、読む側と書く側が同じ語を名乗る形にしておく
- **署名の有無を `%G?` だけで判定しない** — SSH 署名は `gpg.ssh.allowedSignersFile` 未設定だと未署名と同じ `N`。存在は `cat-file commit` の `gpgsig` ヘッダで確認。署名パスフレーズは扱わない(agent の GUI pinentry 必須 — サブプロセスに端末が無い)
  - **`--format=` のどのプレースホルダでも見分けられない**(2026-08-11 実測 git 2.55): 未署名と ssh 署名済みで `%G?` `%GS` `%GK` `%GG` `%GF` `%GP` `%GT` が完全一致 — 1 コマンド化の道は無い
  - **先に `cat-file commit`、ヘッダ無しなら `Absent` で終わり**(`identity::verify_commit`)— 未署名は 1 プロセスで済み gpg / ssh-keygen を起動しない。`%G?` の `N` は「判定できなかった」と読む。プロセス数は `identity_integration` の observer テストが固定
- **`ls-files --eol` は worktree の実ファイルを読む** — グロブ渡しは基準リポジトリ級で数十秒(kotlin 全件 24.7s。実測)。候補列挙(索引のみ 85ms)と `--eol`(確定した数パスだけ 42ms)を必ず別コマンドに分ける。未チェックアウトは `w/` が空
- **改行コードの判定は patch の bytes から**(`eol::read`)— `ls-files --eol` は「今どう見えるか」で、どの行が新しいかは diff しか知らない。`--eol` は未追跡と近傍標本だけ
- **`diff --ignore-cr-at-eol` の patch は `apply` できない**(実測 `patch does not apply`)— 表示用と staging 用で diff の bytes を分けない不変条件(`details::file_diff_raw`)を壊すので使わない
- **worktree の diff は index 空間で出る** — `autocrlf=true` でも patch に CR は現れず `apply --cached` / `apply -R` が通る。index blob に CR があるファイルは変換されない = 設定切替で全ファイルが modified にはならない(実測)
- **`git mergetool` は `--no-prompt` だけでは stdin を踏む**(`conflict::mergetool`)— ツール未設定だと確認を stdin に出す(閉じていて失敗)ので `--tool=` 必須。`--gui` も必須(無いと `merge.guitool` と食い違う)。`mergetool.writeToTemp=true` を撃つ(既定は一時ファイルが隣に出て WIP ペインが untracked で埋まる)。`keepBackup` は触らない(`.orig` は利用者の安全網)。引数なしで撃たない(全衝突ファイルを順に開き書き込みキューが塞がる)。自前 `cmd` ツールは exit code を信用されず BACKUP の mtime 比較 — 保存せず閉じると「失敗」でマーカーが戻る
- **`mergetool --tool-help` は Windows で約 8 秒**(実測)— 書き込みキューに載せず・誰も待たせず・プロセスで 1 回だけ(`conflict::available_tools` の `OnceCell`)。`--gui` でも絞られず、端末ツール除外は説明文の `(requires a graphical session)` パースしかない(取れなければ候補ゼロ = 無害側)。自前定義は `config --get-regexp '^mergetool\..*\.cmd$'` が 34ms なので即出す

- **Windows ではプロセス 1 個が約 10ms、PATH の `Git\cmd\git.exe` を通すと約 20ms — 対話の予算は本数で決まる**(実測 warm、shell から: `git --version` が launcher 経由 22.7ms / `mingw64\bin\git.exe` 直 10.3ms、行選択の `git show` が 19.0 / 10.7ms。インストーラが PATH に足す `cmd\git.exe` は環境を整えて本物を spawn するだけの 2 段目で、本物は自分で `libexec/git-core` / `mingw64/bin` / `usr/bin` を子の PATH に足し、HOME と system config も自分で引く — Git ディレクトリを全部外した PATH と HOME 無しで `!` alias が通ることで実測)。**`GitExecutor::new()` は `Command` が最初に見つける `git.exe` が `cmd\git.exe` の時だけ、隣の `{mingw64,clangarm64,mingw32}\bin\git.exe` を撃つ**(`process::program`。先に別の git が在ればそのまま、`with_program` は名指しのまま。コマンドログの完全形はその path を綴る)。行選択の詳細は `git show` 1 本にまとめる(`details::commit_details`。launcher 経由の実測 25ms 対 直列 2 本 68ms)。`--diff-merges=first-parent` が要る(無いとマージのファイル一覧が空)。レコードと一覧の切れ目は NUL 10 個で決める(`split_record`)— 形で探すとメッセージ中の `M\tsrc/main.rs` が変更ファイル表に化ける。空コミットはレコード後ろに改行すら無い
- **`git diff-tree <p1> <c>` は `git show <c>` より遅い**(kotlin で 42ms 対 24ms。実測)— プランビング側が速いと決めてかからない

## セッション・実装の決定事項(各論)

- **メモリの内訳は `cargo xtask perf --breakdown` で出す**(推測しない)。取りこぼしは「残り」が膨らむ形で出るので総量は嘘にならない。実測記録は [ci/baseline/perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md)
- **refs に比例する名前は `crate::Name`(`compact_str`)で持つ** — 24 バイトまで inline(ref 名の実測平均 20.2 字)。app 側から型の名指しが要る形にしない(§core の API は純 Rust 型のみ)。**`Footprint` は `SmallVec` に明示 impl が要る** — 無いと `[T]` へ deref して溢れたバッファを数え落とす
- **バイト数より確保の個数が効く帯がある** — 305,213 個の削減が計数 −3.1MB なのに WorkingSet −12MB(差はヒープ管理領域 = 計数アロケータに見えない側)。`classes=` の**件数**を必ず見る
- **mimalloc は不採用(実測)** — WorkingSet +38〜55MB / private +83MB、環境変数で抑えても private +43MB。起動・応答に差なし。数字は [perf-windows-x64.md](../../ci/baseline/perf-windows-x64.md) §アロケータと確保の個数
- **refs に比例する常駐データは「1 要素の器」を作らない**(タグ 45,901 本で実測): `BTreeMap` は 1 件でも 11 スロットのノード(43.5MB → `RemoteTagIndex` 6.5MB)/ `HashMap<K, Vec<V>>` は push 1 回で 4 スロット(20.5MB → `LabelIndex` 6.4MB)/ hex 40 字の `String` は 1 行 1 確保。`String` → `Vec<u8>` では 1 バイトも減らない — 減るのは表現を変えた時だけ
- **メモリ予算の半分(`--no-open` 実測 151.3–151.7MB — ci/baseline/perf-windows-x64.md)は空リポジトリで既に埋まっている**(Rust ヒープは 1.2MB)。「全部 Qt」と読まない — Qt 自身の床は 84MB(同 baseline §Qt の床)で、残りは自前の QML シェルとページの実体化。software 描画は代替にならない — GPU −25MB だが 56fps で予算割れ(実測)

- interactive rebase は `GIT_SEQUENCE_EDITOR` に別実行ファイル `pgg-todo-editor` を差す。**配布物に同梱必須**(本体と同じディレクトリ)
- **駆動 rebase だけ `--no-rebase-merges` で釘付け**(`integrate::rebase_command` の `todo_editor` 側)— `rebase.rebaseMerges` が立つと git の書く todo が `label onto` / `reset onto`(`--root` は `reset [new root]`)で始まる。helper が todo を丸ごと差し替えるので**今は結果が変わらない**(2.55 実測: 素・`--root`・reword の `exec` 行・`--update-refs` 併用の全形で config 有無が同一)が、それは merge backend が label 無しの todo を通す偶然に乗っているだけなので、プランの全体を git に言わせる形に固定する。**素の rebase は釘付けしない**(守るプランが無い = config は利用者のもの)。網は `integrate_integration::todo::a_plan_runs_whole_with_rebase_merges_set_in_the_config`(最低バージョンでの実測を兼ねる — 2.43 のマニュアルは `--no-rebase-merges` を明記している)
- **全行 `drop` のプランを拒むのは `--root` の時だけ**(`sequencer::rebase_interactive`)— `--root` は placeholder へ replay するので空 tree・空メッセージのコミットが残る(実測)。回避に範囲を 1 つ広げない — 下のマージが範囲に入り `plan_edit` が拒む
- **テストが差し込む実行ファイルは rename で置く** — Linux は write fd の下の exec が `ETXTBSY`(git ではなく `sh` が Text file busy を返し rebase 失敗に見える)。`session_integration` の replay 系 5 本が持ち回りで赤くなったらここ(実測: 24 スレッドで 8 回中 6 回赤 → `Once` + staging へ copy + `rename` publish で 0)
  - **`--test-threads` を下げて隠さない** — 4 なら通る(実測)が CI のコア数で戻る。Windows では出ない — `cargo xtask linux` でしか観測できない
  - `Once` は copy を 1 回にするためでなく**待たせる**ために要る(exec が copy 中に重ならない)。staging 名を使い回すなら Once と対 — でないと書きかけが publish される
  - **fork が継承した write fd は Once + rename では防げない**(子の `execve` まで隣の exec が `ETXTBSY`。実測 8 回中 1 回、fork〜execve 間 300ms 停止で 100%)。手当ては exec 側の `ETXTBSY` リトライ(`run_published_helper`)。リトライの締めは固定秒でなく `QUIET_BUDGET`(窓は他プロセスのスケジューリングの物で、壁時計の verdict は負荷が上回る)
  - **同じ罠は xtask のテストにも出る** — `gate.rs` が `fs::copy` で席の build slot へ置いた runner を隣のテストの fork が握り、`land_steps_out_of_the_build_slot_the_gate_builds_into` が持ち回りで `Text file busy`(実測)。exec 側は `output_past_a_busy_image`(`Sandbox::gate` / `land_from`)を通す。網は `a_runner_held_open_for_writing_is_run_once_the_handle_goes`(linux 限定 — POSIX は `execve` が拒む「かも」としか言わない)
  - **lock は close でなく unlock で離す** — `flock` は open file description に付き fork がそれを全部複製するので、close だけで離した lock は隣のスレッドが fork した子の `execve` まで運ばれる(コンテナ実測 20 万回中 200 回。`unlock()` を撃ってから close は 0/200000)。Windows はどちらも 0/20000 で窓が無い — Rust の File ハンドルは継承されず、`LockFileEx` は子に届かない。**離す型は `xtask::locks::Locked` に包む**(Drop で unlock → close。名前を消すのは下の行のまま lock を握ったまま、消した後に unlock)、core は `settings::lock::Lock` の Drop。網は gate スイートの `a_lock_frees_the_tree_when_unlocked_and_not_when_merely_closed` と `lanes` / `still` / `settings::lock` の `a_lock_let_go_of_is_free_though_a_forked_child_holds_the_description`(linux 限定 — description を stdin に渡した子で窓を作る)。**離した直後の答えをリトライで読む必要は無い** — 残る待ちは掃除側が lock を握ったまま名前を消す µs だけ(その窓の天井が `still::SWEEP`、間隔が `wait::TRY_AGAIN` — `lanes::mark` / `sole`、`still::hold_in` / `lock_beside` の 4 箇所)
  - **lock ファイルは握ったまま消し、取る側は名前が残っているか確かめる**(消す = `still::held` / `still::announcing` / `lanes::a_landing_waits`・`Waiting::drop`、取る = `lanes::mark_polled` / `still::lock_beside`)— 先に離すと、その数 µs に同じ名前を開いた相手が「名前から消えた inode」を握り、印を立てたつもりの landing が全 gate から見えない / announce が lock の無い note を残して次の読み手に litter として消される。**Windows も POSIX と同じ**(実測 rustc 1.97.1 / Win11: `remove_file` は自分や他人が開いていても成功し、名前は即消え、同名の新ファイルで別の lock が取れる)ので OS 分岐は要らない。取る側は `WouldBlock`(掃除中)も `metadata` 不在(掃除済み)も**エラーにせず名前を開き直す** — pid は再利用され各 run の最初の announce は同じ番号なので、死んだ run の残骸と新しい run が同じ名前でぶつかる。**名前が共有の lock ファイルは消さない**(`still::Name::Shared` / `verify::ownership`)
  - **rename に負けた残置 helper はバイト一致の時だけ使う**(`publish_helper`)— 一致しない残置は古い helper を今日の assert の下で走らせるので、その場でエラーにする(Windows は実行中の exe も読める — 拒まれるのは書きと rename)
- **integration test の Git 環境は executor ごとに隔離する**(2026-08-16 Windows sandbox 実測: `~/.config/git/ignore` の permission warning が stderr に混ざり、nothing-to-commit / empty revert 3件が同時に赤)。`support::exec::isolated` は test-binary 固有の `GIT_CONFIG_GLOBAL` / `XDG_CONFIG_HOME` と `GIT_CONFIG_NOSYSTEM=1` を `GitExecutor::with_env` へ渡し、`TestRepo` の setup Git も同じく XDG を自身の temp 配下へ向ける。process-global env mutation は並行 test と競合するので不採用
- **baseline を取る待ちは、走っている git を沈黙に数えない** — 沈黙だけだと待ちが途中で抜ける(実測: 5830ms の walk 中に無イベント 2415ms)。`support::settled` は本数一致と沈黙の両方を要求。**開幕の読みを数えるなら生成時に決める** — `RepoSession::open_recording(.., Recording::WithBackground)`(`open` は `UserOnly`)。open 直後に `set_recording` を撃つ形は、開きが `Opened` の受理と同時に spawn する読み(refs / status / log / author / open fetch)のうち何本を捕まえるかがスケジューリング次第になる。open 後だけを数える時だけ `set_recording(Recording::WithBackground)` を使い、`opened_graph` / `opening_settled` で開きを閉じてから撃つ(以後の読みは ask → spawn が store を運ぶので正確)
  - 開いた時の tag 込み pass はチップが出揃った後(実測: `LabelsChanged` の 639ms 後)なので、**tracked refresh 1 本では baseline を閉じられない** — その要求は pass を cancel するだけで、cancel は「止めてくれ」であって「止まった」ではなく、外に落ちた walk が「バッジが walk を起こした」に化ける。守りは 2 つ揃い: 始まる前に取り上げられた pass は walk しない(`run_swap_pass` 冒頭の cancel 判定)と、既に始まっていた pass は `RepoSession::wait_for_graph_passes` が閉じる(`GraphPasses` は spawn 前に登録・task 終了で返却)。walk を数えるテストは `CaptureSink::opened_graph` を通す(`remote_tags_integration::learning_what_the_remotes_carry_repaints_chips_without_swapping_the_graph`)
- **グラフの walk は `--date-order`(`--topo-order` 不採用)** — topo は孤立ルートを端へ沈める(実測: `origin/gh-pages` が 323 行中 322 行目)。この形のテストは「孤立側の後に本流へもう 1 コミット」まで書かないと topo でも緑(`session_integration::an_independent_history_sits_where_its_date_puts_it`)。親を子より先に出さない保証は同じ(GraphBuilder・stash の sift の前提)。レーンは pull request 型で激減(実測: jackson-module-kotlin 277 → 9)、速度差なし
- グラフは **2 段ストリーミング**(タグ無し即描画→無フリッカー置換。44k タグのフロンティア初期化コスト対策)+ `--max-count=2000`。バックグラウンド更新は `refresh_log()` = 一致なら無イベント(アイドル中のチラつき対策)。リセット→ストリーミングは open / Reload / タグ切替 / 件数変更のみ
- **未コミット行の条件は「木が汚れている」ではなく「積まれるコミットがある」** — conflict を全部 ours のまま `git add` すると `status --porcelain` は空・`MERGE_HEAD` は立ったまま・commit は 2 親のマージを書く(実測 2.55。同じ状態の cherry-pick は `nothing to commit` で拒むので、止まった sequencer はこの行にならない)。**行の有無と walk が `MERGE_HEAD` から始まるかは同じ 1 つの答え**(`session::walk::pending_commit`)— 別々に決めると、行の無い綺麗な木にチップも点線も無いコミットが現れて merge の開始・終了で出入りする。demo preset は `conflict-ours`、網は `session_integration::stream`
- **`conflict::git_file` は不在と失敗を同じ空文字で返す** — `opstate::merge_heads` はそれを `Option` に畳んで「読めなかった」と「マージが無い」を分ける。畳まずに空 `Vec` を返すと、失敗した 1 回が「merge が終わった」に化けて点線を落とす全歴史再構築 → 次の poll で戻す再構築の 2 度歩き(基準リポジトリで 2000 行 × 2)。読めなかった poll は前の答えを保つ(`session::refresh` の `merge_moved`)。網は `integrate_integration::merge`
- **行番号を渡すイベントは渡した先が見ている世代を名乗る**(`LabelsChanged` の `generation`)— walk が入れ替わるとチップが別コミットに貼り付き、`applied` が残るので自己修復しない。守りは「読みと送信を同じ `shared` ロック内」と世代タグの 2 つ揃い。**`Shared::generation` は log_gen ではない** — swap を省いたパスも上げるので、写すと以後のチップが全部落ちる(実測・`remote_tags_integration` が赤で捕捉)
- **アバターは取り込む時に作り直す**(`picture::normalize`、保管は 256px PNG のみ)。ファイルサイズ上限は画素を縛らない(4MB の PNG の内側に 4GB の絵。実測 [ci/baseline/avatar-shrink-windows-x64.md](../../ci/baseline/avatar-shrink-windows-x64.md))— 寸法はヘッダだけ読んでデコード前に弾く(`picture::MAX_PIXELS`)。形式は中身で決める(`avatar::EXTENSIONS` はダイアログ専用)。不変条件「保管庫に入るものは必ず描ける」— 破ると輪だけの空円になり理由を言う場所が無い。`png` の `zlib-rs` feature を立てない(C の zlib に倒れ 3OS ビルドの前提が変わる)

- **同じスナップショットの読みは 1 本しか走らない**(`ReadFlight`)。**入口は全部そこを通る** — `refresh_refs` / `refresh_status` も `refresh_poll` も書き込みの後始末も `read_refs` / `read_status` 経由で、`publish_*` を直呼びしない(`poll_slot` / `write_running` は持ち場が違う: replay 中は poll がわざと通るし、フォーカスと `ask_merge_tool` はどちらとも突き合わされていない。二重に読むと corpus では `status -uall` 2.9s / 2.3 CPU 秒を二重に払う)。**順序も flight が持つ** — pass は repository を見る前から publish の後まで flight を握るので、古い答えが新しい答えを追い越す窓が無く、`publish_*` の側に世代の関門は置かない(置いても発火しない)。**2 人目は落とさず待つ**: 自分が訊いた後に始まった pass が landed していればその答えを貰い(プロセス 0 本)、無ければ自分が次の 1 周を走らせる — 落とすと書き込み直後の refresh が書き込み前の答えのままになる(`session_integration::a_request_made_while_a_read_runs_gets_a_read_of_its_own` が読みを窓際で止めて踏む。落とす実装でも 3 連打型のテストは緑)。重なりは `the_ways_in_to_a_status_read_never_run_two_at_once` が spawn の所で読みを park して踏む(コマンドログの start/finish から同時本数を数える)。**replay の下だけは踏み方が違う** — poll は replay 中の書き込みを通り抜けるので(`running_write()` の kind が `replays_history`)、`a_poll_let_through_by_a_replay_does_not_read_beside_it` は park で書き込みを request の中に留め、**git の答えを合図に tick を撃つ**(`WriteFinished` は後始末の読みより先に出て、`write_running` は refresh を含む request 全体に掛かる = `write::serve`)。時間で待たない。baseline は snapshot event 後に `wait_for_snapshot_reads` で閉じる
- **完了 ack は single-flight permit を返した後に送る** — `refresh_poll_tracked` / `refresh_remote_tags_tracked` の `outcome()` から即座に次を要求しても `Busy` へ落ちないことが契約。`WriteFinished` は Git command の終了通知で、後続の読み直しは含まない。**後続更新完了の境界は `WriteSettled { id, kind, failed }`**(2026-09-12)— status / refs / graph / stash・worktree の一覧 **と一覧が頼んだ派生の読み(worktree の join と walk = `refresh_worktrees` が flight を離した後に自分で await する。flight の答え `WorktreeRead` が news を運ぶので相乗りした caller も待つ)** / author config の publish が済み、次の request を取る直前に出る(head reach の walk だけは含まない = 前の walk が居ると skip する問い)。**`failed: Vec<FollowUp>` が着地しなかった読みを id 付きで名指す**(`OpFailed` は id を持たない — label は同じ語)。各読みは失敗を型で返す: refs / status の flight の答えは `Reread::{Same, Moved, Failed}`、listing の task は `Vec<FollowUp>`、グラフは `RefreshOutcome::landed()`(新しい ask に取られた `Cancelled` はそもそも答えではないので、`graph_answer` がその ask の着地まで追ってから判定する = 上項)。`ReadFlight<A>` は答えの型を持つ(既定 bool = published)。queue idle が必要ならこれを待つ(`support::session::write_settled` が `failed` を返す)
- **タグのリモート状態は `ls-remote --tags` で訊くしかない**(`refs/remotes/` 相当の記録が無い)。届かなかった remote は前回の答えを保つ。尋ねられず読むのは auto fetch 有効かつタグ表示中だけ(`session::catch_up_remote_tags`)。開いた時の fetch(次項)が走った開き方では読まない — fetch が出際に読んでいる。**この読みは書き込みキューを通さない** — 通すと request が立っている間ポーリングが止まる(`running_write`)。**ズレは fetch では直らない** — `--prune` はタグを残し、`--prune-tags` は exit 1(実測)。**読み中に来た要求は `Busy` で捨てる — `ReadFlight` の「もう 1 周」は足さない**(2026-08-23 判断): 予約が要るのは 2 人目が 1 人目の知らない変化を持つ時で、この読みの**許可ゲートを通る要求元**(開き終わり / `install_auto_fetch`)は何も持たない — 許可が off の間は読みが走れないので許可を入れた要求が `Busy` になることも無い。つまりそこでの `Busy` は同じ remote へ同じ問いを投げている読みの重複で、その読みの publish が答えになる。**取りこぼしを拾うのは poll ではなく次の auto fetch tick** — poll は remote tag を読まない

- `publish::range_rewrites_published` は同じ問いの**範囲版**を、git ではなく walk が印を付けた行に訊く経路(`LogRow::parents` + `published` を `WalkedRow` で渡す。呼ぶのは `GraphModel.rebaseRewritesPublished`)。`onto..head` に印の付いた行が 1 つでも在るか = **2 色を親へ流す 1 パス**で、行が walk 順(親は全ての子より後)である限り、行に着いた時点でその行の 2 つの答えは確定しているので最初の当たりで抜けられる。**`state_of` の 2 プロセスと同じ答えを返すのは窓の中だけ** — 窓外は倒れる方向が両端で違う(head が窓外 = 範囲が空 = `false` / onto が窓外 = head の到達分が丸ごと範囲。後者は「窓より古い名前への rebase」の正解でもある)。**`LogRow::parents` は sift 後**なので stash は第 1 親だけ・WIP 行は空(描く leash は親ではない)
- **詳細の要求番号は結果キューとUI照合まで保持する** — 完了順で1件に潰すとA→BのB→A完了でBを失い、OIDだけの照合はA→B→Aの古いAを通す（回帰テストあり）。番号はfeedがセッションを跨ぐためプロセス内で単調増加とし、古い読みはキャンセルする。失敗も番号付きで送り、現要求と照合したUIだけがエラー面へ渡す（coreから先にOpFailedを流さない）。
- **画像プレビューの blob 側は一時ファイルへストリームで書く**(`preview::PreviewFiles` / `write_blob` = `run_streaming` の callback で `File::write_all`、全体をメモリに持たない。置き場は `temp_dir()/platitude-gg-<pid>/s<セッション連番>/<diff epoch>-<old|new>.<ext>`)。**掃除の規則は epoch**: `publish_diff` が読みを公開する直前に `sweep_before(epoch)` = **書き終えた(settled)読みのうち epoch 未満**を消す(画像でない読みも掃く — ペインは移っている)。書きかけの読みは番号に関わらず残す(遅い読みが速い読みの後に着いても、ペインに渡すファイルが在る)。`release()` = ペインが閉じた(settled 全部)、`remove_all()` = `close()` と Drop(ディレクトリごと。最後のセッションの Drop が run ディレクトリも `remove_dir` する。app の `Hub::shutdown` が `remove_run_dir()` で念押し)。**「最後」は空かどうかではなく生存セッション数**(`preview::SESSIONS` の `Mutex<usize>` を Drop が握ったまま消す) — **空の run ディレクトリは「捨てられた」ではなく「まだ何も書いていないセッションのもの」**で、それを消すと相手の `create_dir_all`(親と子で 2 手)が **2 手目で `NotFound`** になり、side が file 無しの size only で着地する。実測 2026-09-08: 兄弟セッションを作って捨てるだけのスレッドを 1 本添えると 400 読み中 368 が size only(Linux は ENOENT、Windows は削除保留の `ERROR_ACCESS_DENIED` も混じる)。数えるようにして 400/400。**同じファイルの再読みは新しい名前**(URL が変わらないと `Image` が再読込しない)。網は `preview_integration` と `session_integration::query::a_pictures_file_goes_with_the_pane_and_its_directory_with_the_session`(**size only で着地した読みは「まだ来ていない」ではない** — 後から file が生えることは無いので、待たずにその場で赤くする。判定は `wait_for` の外へ出す: 述語は sink の events lock の中で呼ばれ、そこで panic すると lock が毒になって sink 側スレッドも道連れになる)。**なぜ size only で着地したかは side が持ち歩く**(`PreviewSide::unwritten` = `WriteBlobError` の文。`write_blob` の 3 段 — session ディレクトリ作成 / ファイル open / stream 書き込み — をパスごと名乗る)。**ここを素の `Io(#[from] std::io::Error)` へ戻さない** — `NotFound` だけではどの段が落ちたか読めず、file 無しの side は「絵が要求されなかった side」と区別が付かない
