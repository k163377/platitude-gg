# 分割・共通化基準(Rust / QML 共通)

既存の超過はラチェット式 — 触った時に寄せる。一斉整形だけのコミットを作らない。

## 長さの閾値(コード行)

- **1 ファイル 1000 行 / fn 100 行 — どちらもコメント行と空行を数えない** — **機械化済み: `cargo xtask structure`(check に内蔵)**、fn は clippy(workspace lints + clippy.toml の閾値)。数字の出所は clippy の `too_many_lines`(fn = 100)と、提案中の `too_many_lines_in_file`(ファイル = 既定案 1000・`restriction`)で、**このリポジトリの現在行数から逆算した数字ではない**。`structure` はコード行と「コメント + 空行」の割合を報せる — **「コメントで長い」と「コードで長い」は別の答えを要する**
- **これは上限ではなく「設計を問い直す閾値」** — 超えた事実が答えではなく、そのファイルの設計を人が見る合図。**src / tests で数字を分けない**(出荷されるかどうかの差は数字ではなく §分割 の設計規則の側)
- **追記の手順はこの順**:
  1. **一旦、行数は無視して書く** — 見るのは設計の妥当性と、コメントが無駄に冗長になっていないかだけ
  2. 結果が閾値を超えたら、**まず冗長を削る** — 何も言っていないコメント、言い換えただけのコード。**数えるのはコード行なのでコメントを削っても数字は動かない**(削るのは読み手のためで、閾値を通すためではない)
  3. それでも超えるなら**分割を設計する**
  4. **分割が成り立たないならユーザーへ確認する** — 無理な形へ勝手に割らない
- **分割不能と決めたファイルは理由を書く**。置き場は閾値の内か外かで決まる: **閾値以下なら、そのファイルの冒頭コメント**(先例 `crates/platitude-app/src/models/app_backend/qobject.rs` — 何が既に委譲済みか・残っているのは何か・次の一手が分割ではなく再設計であること・着手前に訊くこと、まで書いてある)/ **閾値超過なら [rules-refs/structure.md](../rules-refs/structure.md) の §分割しない判断**(記載の無い超過は違反)
- 台帳に**行数は書かない** — 機械が見るのはそのパスのファイルが今も在るかだけで、割り終わったら行を消す。**代わりに理由を厚く書く**: 何が既に出してあるか・残りが何を共有しているか・割るなら先に何が要るか。**理由は書いた時点の主張なので、その台帳に触る時は読み直して、実態を説明していなければ書き直すか割る**
- 既存超過の固定先: ファイルは `crates/xtask/structure-baseline.txt`(縮めば自動追従・伸ばせば fail)、fn は `#[expect(clippy::too_many_lines)]`。**どちらも縮めた時に外す必要がある** — 基準線は書き換わったファイルを commit、`#[expect]` は剥がす(貼ったまま fn が 100 行を切ると unfulfilled で赤くなる)

## 分割

- **割る単位は責務であって行数ではない**。**製品コードは責務で割る** / **ハーネス・統合テストは 1 主題なら長くてよい**(主題が 2 つ入った時に割る)
- 挙動不変・**移動だけのコミット**(変更・リネームを混ぜない)。公開名は `pub use` / qmldir で不変に保つ
- Rust: ディレクトリ化は **mod.rs 方式(既存踏襲)**。mod.rs は mod 宣言・re-export・共有型のみ(実装を置かない)。`#[cfg(test)]` は対象と同じファイルへ付いて行く(テストだけ巨大なら同ディレクトリの `#[cfg(test)]` 専用ファイルへ)
- **クレート root(lib.rs / main.rs / tests/it/main.rs)は宣言と再エクスポートだけ** — ヘルパ関数・型・定数を置かない。root は全モジュールへ dispatch し、そこにヘルパがあると全モジュールが root を読む = gate の依存木でどの変更も全体へ届くハブになる。**機械化済み: `cargo test -p xtask`(`the_crate_roots_have_no_readers`)** — 置き場は責務名のモジュール(`tree` / `subprocess`、core は `model`)
- 統合テストは tests/it/ 内のモジュール分割(1 バイナリ規約は core.md)
- QML: **1 ファイル = 1 コンポーネント**(Qt の指針。ファイル名がそのまま型名で、粒度は qmldir と型システムが決める — 行数ではない)。子コンポーネント切り出し(ui/ フラット・登録 2 箇所は app-ui.md)。inline `component` は 2 ファイル目が使う時か親が閾値を超えた時に独立ファイル化
- Qt: `#[qobject]` ブロック(`qproperty!` / `#[qsignal]` / `#[qslot]`)は QMetaInfo の一貫性で **1 型 1 ファイルから動かせない** — スロット本体を素の `impl` へ委譲して痩せさせる(委譲化は移動と別コミット)。それでも割れない分は §長さの閾値 の「分割不能と決めたファイルは理由を書く」へ

## 共通化

- 同じロジックは **3 箇所目が出た時に共通化**(2 箇所は静観)。挙動が半端に違う実装を無理に束ねない
- 置き場は**使う全員から到達できる最深のモジュール**。util / misc / helpers という名のモジュールを作らない(名前は責務)
- xtask は依存 std のみ — core / app と共通化せず重複を許容
- QML の繰り返す意匠は既存部品を先に探す(一覧は ui/qmldir)

## QML 整理

- 1 行の最大横幅は 120 文字
- 属性順は Qt 規約: id → property → signal → JS 関数 → オブジェクトプロパティ → 子要素(触る箇所だけ揃える)
- 数行を超えるスクリプトは名前付き関数へ(ロジックを QML に書かない規約は app-ui.md)
