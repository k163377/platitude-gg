# アバターの取り込み縮小: 実測(Windows x64)

仕様は [デザイン規約.md](../../internal-docs/デザイン規約.md) §アバターを与える と
[.claude/rules-refs/core.md](../../.claude/rules-refs/core.md) の picture 項が正本。
**ここはその値を選んだ根拠だけ**を持つ。

**測ったのは製品ではなく使い捨ての probe**(木の外・コミットしない。Rust から同じ
画像を通しただけのもの)。環境: Windows 11 / x64 / release / ウォームキャッシュ。
`Canvas` の解像度(§5)だけは Qt の `qml` に使い捨てのシーンを食わせて offscreen で
測った。

## 1. ファイルサイズのキャップは画素を 1 つも縛らない

ファイルサイズのキャップ(`avatar::MAX_BYTES`)だけでは画素を 1 つも縛れない。実測:

| 与えるもの | ファイル | 画素 | デコード後(RGBA 4B/px) |
|---|---|---|---|
| 4000×3000 の写真(JPEG q82) | **0.87MB** | 12.0Mpx | **45.8MB** |
| 3840×2160 のスクリーンショット(RGBA PNG) | 0.17MB | 8.3Mpx | 31.6MB |
| 8192×8192 の単色 PNG | 0.26MB | 67Mpx | 256MB |
| 16384×16384 の単色 PNG | 1.02MB | 268Mpx | **1,024MB** |

**平坦な PNG はファイルの約 1,000 倍にデコードする**(実測 1,006 倍)ので、4MB の
内側に 4GB の絵が入る。**普通のスマホ写真はキャップの 2 割で 46MB**。

デコードは URL ごとに 1 回(Qt の pixmap キャッシュ。[avatar-log](avatar-log-windows-x64.md))
なので**行数には比例しない**が、**参照が生きている限り常駐する**ので**画像を与えた
人数ぶん積まれる**。予算は 300MB([CLAUDE.md](../../CLAUDE.md) §性能予算)で、3 人に
写真を与えると 137MB = **予算の 46% が顔だけで消える**。

**バイト上限だけでは防げないのは PNG と GIF**(LZW / deflate が平坦な絵を潰すため)。
JPEG はエントロピーの下限があるのでバイト上限がほぼ画素上限を兼ねる。**画素の
チェックが要るのはその 2 つのため**。

## 2. 描画は repaint のたびに元画像から作り直す

`GraphRowDelegate.face()` は `ctx.drawImage(url, x, y, 2r, 2r)`。Context2D は縮小済みの
コピーを持たないので、**repaint のたびに元の画素から 20px を作る**。契機は 4 つで、
一度に描き直す行数が違う:

| 契機 | 一度に描き直す行 |
|---|---|
| 行の再利用(スクロール) | 1〜2 行 / フレーム |
| `onWidthChanged`(**グラフ列の仕切りドラッグ**・窓リサイズ) | **可視行すべて(~35)** |
| ロール変化(`avatar` / `geometry` / `node_lane`) | その行だけ |
| `refreshAvatars`(割り当ての反映) | 変わった行だけ |

**最悪はスクロールではなく仕切りドラッグ**。

1 face のコストは経路次第で 2 桁ぶれる — dest 画素ぶんだけ双一次サンプリングするなら
0.05〜0.2ms、source のフォーマット変換が `drawImage` ごとに走るなら 12Mpx の変換で
10〜30ms(= 1 行の repaint でフレームを使い切る)。**縮めればどちらでも 0.001ms 台に
落ちて差が消えるので、どちらかを実測しないまま縮める**と決めた(§8)。

## 3. 縮めた後

| | 縮小なし | 256px 保存後 | 比 |
|---|---|---|---|
| 保存ファイル | 0.87MB | 80KB | 1/11 |
| デコード後メモリ | 45.8MB | **256KB** | **1/183** |
| 再サンプルの元 | 12.0Mpx | 0.066Mpx | 1/183 |
| 初回デコード(ローダスレッド) | 23ms | 1ms 未満 | — |

**取り込み時に 1 度だけ払う代金**: 普通の写真(12Mpx)で **約 60ms**、上限 32Mpx で
**約 150ms**(読み 10 + デコード 61 + 縮小 19 + PNG 書き出し 40 の外挿)。モーダルの
ファイルダイアログが閉じた直後の 1 回きりなので、UI スレッドで同期に走らせる。

## 4. 保存辺 256 を選んだ根拠

2×2 の双一次サンプリングを仮定して 20px のノードへ描いた時の、理想(面積平均)との
誤差と、サンプリンググリッドが半テクセルずれた時の変化量(= スクロール中のちらつき
の代理)。いずれも 0〜255 のスケール:

| 保存辺 | 20px への縮小率 | 理想との誤差(RMS) | ちらつき(RMS / ピーク) | 保存 | デコード後 / 人 |
|---|---|---|---|---|---|
| 96 | 4.8x | 0.73 | 1.24 / 3.30 | 10.3KB | 36KB |
| 128 | 6.4x | 0.87 | 1.09 / 3.60 | 18.3KB | 64KB |
| 192 | 9.6x | 1.18 | 1.14 / 4.40 | 42.9KB | 144KB |
| **256** | 12.8x | **1.53** | **1.50 / 5.60** | **79.8KB** | **256KB** |
| 3000(= 縮小なし) | 150x | **19.50** | 21.09 / **64.25** | — | 45.8MB |

**保存辺の間の差は誤差 1 段未満で見えない**(0.3% 対 0.6%)。**見えるのは縮小なしの
行だけ**で、それはどの保存辺でも消える。したがって画質は選定条件にならず、**上を
取って 256**(`Metrics.detailsAvatar` = 40 が DPR 6.4 まで、トークンを 80 へ倍にしても
DPR 3.2 まで耐える)。20 人ぶんで 5.0MB = 300MB 予算の 1.7%。

## 5. `Canvas` は device 解像度で描く(引き伸ばしではない)

40 論理 px の `Canvas` に 1px の円と対角線を描き、`QT_SCALE_FACTOR` 1 / 2 で焼いて比較:

| | scale 1 | scale 2 | 2 倍に引き伸ばしただけなら |
|---|---|---|---|
| 焼けた画像 | 40×40 | **80×80** | 80×80 |
| 円のストロークが乗る行数 | 38 | **74** | 76 |
| 中線上のストローク幅 | 2px | **3px** | 4px |
| 1x を最近傍で 2 倍にしたものとの RMS | — | **64.07** | 0 |

**その解像度で改めてラスタライズされている**ので、4K / 200% では顔のノードに
40 device px・詳細ペインの顔に 80 device px が実際に配られる = 保存辺を上げた分が
そのまま効く。offscreen + `grabToImage`(= verify-ui と同じ経路)で測った。

**副産物**: `antialiasing: true` を付けても階調が 2 段のまま = **この経路では Canvas の
図形が非アンチエイリアスで焼かれている**。画像の縮小は別経路なのでアバターの判断には
影響しないが、輪やレーンの縁の見え方は別に見る価値がある。

## 6. 依存の候補と値段

同じ仕事(デコード → 中央切り → 正方 → PNG 書き出し)を組んで実測。空の実行ファイル
130KB を基準にした増分:

| | 追加クレート | 実行ファイル増 | 受け取れる形式 | 縮小 |
|---|---|---|---|---|
| `image`(`png,jpeg,webp,bmp`) | 19 | +900KB | png / jpg / webp / bmp | 27ms |
| `image`(`png,jpeg`) | 17 | +634KB | png / jpg | 27ms |
| **`png` + `zune-jpeg` + 自前** | **10** | **+396KB** | **png / jpg** | **7ms** |
| 同 + `gif`(採らない) | 13 | +444KB | + gif | — |

**採ったのは 3 行目**。`image` は縮小と切り出しを自前 30 行に置き換えるだけの薄さしか
足しておらず、7 クレート・238KB 高い。**GIF を採らない理由は値段ではない** ——
[GitHub もアバターの GIF はアニメーションさせず 1 フレーム目を出す](https://github.com/orgs/community/discussions/46598)ので、
受け取っても静止画になる。グラフのノードは Canvas に描くのでアニメーションさせると
可視行が毎フレーム repaint = §2 の問題そのものになる。

**ライセンス**(採る木ぜんぶ。`cargo metadata` の宣言値):

| クレート | ライセンス |
|---|---|
| png / flate2 / fdeflate / crc32fast / cfg-if / bitflags | MIT OR Apache-2.0 |
| zune-jpeg / zune-core | MIT OR Apache-2.0 OR Zlib |
| miniz_oxide | MIT OR Zlib OR Apache-2.0 |
| adler2 | 0BSD OR MIT OR Apache-2.0 |
| simd-adler32 | MIT |

**GPL / LGPL は 1 つも無い**。許可集合の外に出る綴り(`0BSD`)を持つものも MIT を
選べる。**C ツールチェーンも要らない**: build script は `crc32fast` の 1 つだけで
rustc を叩くのみ、`cc` / `libz-sys` / `pkg-config` / `libc` は木に居ない。ただし
**`flate2` の feature は固定する** —— 既定の `rust_backend`(miniz_oxide)から
`zlib-rs` / `libz-sys` へ倒すと C が入る。

**webp / bmp / gif / heic / avif を入口から外した**のはこの値段のためだけではない:
HEIC は HEVC のプール(Access Advance / Via LA)が現役で、**許容ライセンスの純 Rust
デコーダが存在しない**(libheif / libde265 は LGPL / GPL)。AVIF も Sisvel が AV1 の
プールを主張していて係争中。**WebP(VP8)と JPEG と GIF(LZW)は特許的には解決済み**
(VP8 は 2013 年に MPEG LA がプール結成を取り下げ、JPEG は 2006 年、LZW は 2004 年に
失効)なので、外したのは純粋に「入口を広げる価値がコストに見合わない」判断。

## 7. 縮小でしか直らないもの(fps とは別)

1. **縦横比**。`drawImage(url, dx, dy, 2r, 2r)` は 4:3 の写真を正方形に**押し潰す**
   (`IdentIcon` も同じ)。取り込み時に中央を正方で切れば消える。QML 側で直すと
   9 引数版の sx/sy/sw/sh を JS で計算することになり、app-ui.md の「QML に
   ビジネスロジックを書かない」に当たる
2. **読めない画像が「輪だけの空円」になる**。`face()` は url があれば identicon へ
   落ちない(`isImageLoaded` が false でも輪だけ描いて戻る)。**保管庫は一度も
   デコードしないので、描けないファイルが普通に入る**。取り込み時にデコードすれば
   その場で拒否でき、保管庫の中身は全部描けることが構造で決まる
3. **可搬性**。保存が常に PNG になれば、imageformats プラグインの有無に依存しない

**EXIF の回転は扱わないと決めた**。アバターに使うファイルは各人が既に持っている
アイコンで、カメラの原本ではない —— 縦位置の写真を直立させる親切のために、
IFD の解析(自前 50 行)か `kamadak-exif`(+2 クレート)を抱えない。

## 8. 測らないと決めたこと / 残っていること

- **縮小前の 1 face の描画コスト**(§2 の 2 桁の幅)は**測らない**。答えがどちらでも
  縮める判断は動かず、入れた後は測れなくなるが、残るのは記録上の興味だけ
- **実 4K モニタの実窓**での見え方は Phase 5 の実機ゲート。§5 は offscreen の測定
