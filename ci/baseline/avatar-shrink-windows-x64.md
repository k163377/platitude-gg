# アバターの取り込み縮小: 実測(Windows x64)

仕様は [デザイン規約.md](../../internal-docs/デザイン規約.md) §アバターを与える と
[.claude/rules-refs/core.md](../../.claude/rules-refs/core.md) の picture 項が正本。

**測ったのは使い捨ての probe**(木の外・コミットしない)。環境: Windows 11 / x64 / release / ウォームキャッシュ。

## 1. ファイルサイズのキャップは画素を 1 つも縛らない

ファイルサイズのキャップ(`avatar::MAX_BYTES`)だけでは画素を 1 つも縛れない。実測:

| 与えるもの | ファイル | 画素 | デコード後(RGBA 4B/px) |
|---|---|---|---|
| 4000×3000 の写真(JPEG q82) | **0.87MB** | 12.0Mpx | **45.8MB** |
| 16384×16384 の単色 PNG | 1.02MB | 268Mpx | **1,024MB** |

**平坦な PNG はファイルの約 1,000 倍にデコードする**。

デコードは URL ごとに 1 回(Qt の pixmap キャッシュ)で、参照が生きている限り常駐するので
画像を与えた人数ぶん積まれる。3 人に写真を与えると 137MB = 予算 300MB の 46%。

## 2. 描画は repaint のたびに元画像から作り直す

`GraphLaneCell.face()` は `ctx.drawImage(url, x, y, 2r, 2r)`。Context2D は縮小済みの
コピーを持たないので、repaint のたびに元の画素から 20px を作る。**最悪はグラフ列の
仕切りドラッグ・窓リサイズ**(`onWidthChanged` で可視行すべて ~35 を描き直す)。

縮小前の 1 face のコスト(未測定。入れた後は測れない)は経路次第で 2 桁ぶれる。
縮めればどちらでも 0.001ms 台に落ちて差が消えるので、そのまま縮めると決めた。

## 3. 縮めた後

| | 縮小なし | 256px 保存後 | 比 |
|---|---|---|---|
| 保存ファイル | 0.87MB | 80KB | 1/11 |
| デコード後メモリ | 45.8MB | **256KB** | **1/183** |
| 初回デコード(ローダスレッド) | 23ms | 1ms 未満 | — |

取り込み時に 1 度だけ払う代金: 普通の写真(12Mpx)で約 60ms、上限 32Mpx で
約 150ms(外挿)。**モーダルの
ファイルダイアログが閉じた直後の 1 回きりなので、UI スレッドで同期に走らせる**。

## 4. 保存辺 256 を選んだ根拠

2×2 の双一次サンプリングを仮定して 20px のノードへ描いた時の、理想(面積平均)との
誤差と、サンプリンググリッドが半テクセルずれた時の変化量(= スクロール中のちらつき
の代理)。いずれも 0〜255 のスケール:

| 保存辺 | 20px への縮小率 | 理想との誤差(RMS) | ちらつき(RMS / ピーク) | 保存 | デコード後 / 人 |
|---|---|---|---|---|---|
| 96 | 4.8x | 0.73 | 1.24 / 3.30 | 10.3KB | 36KB |
| 128 | 6.4x | 0.87 | 1.09 / 3.60 | 18.3KB | 64KB |
| 192 | 9.6x | 1.18 | 1.14 / 4.40 | 42.9KB | 144KB |
| **256** | 12.8x | **1.53** | **1.50 / 5.60** | **79.8KB** | **256KB** |
| 3000(= 縮小なし) | 150x | **19.50** | 21.09 / **64.25** | — | 45.8MB |

**保存辺の間の差は誤差 1 段未満で見えない**。見えるのは縮小なしの
行だけ。決め手は画質の外で、上を取って 256(`Metrics.detailsAvatar` = 40 が DPR 6.4 まで、
トークンを 80 へ倍にしても DPR 3.2 まで耐える)。20 人ぶんで 5.0MB = 300MB 予算の 1.7%。

## 5. `Canvas` は device 解像度で描く(引き伸ばしではない)

40 論理 px の `Canvas` に 1px の円と対角線を描き、`QT_SCALE_FACTOR` 1 / 2 で焼いて比較:

| | scale 1 | scale 2 | 2 倍に引き伸ばしただけなら |
|---|---|---|---|
| 焼けた画像 | 40×40 | **80×80** | 80×80 |
| 円のストロークが乗る行数 | 38 | **74** | 76 |
| 中線上のストローク幅 | 2px | **3px** | 4px |
| 1x を最近傍で 2 倍にしたものとの RMS | — | **64.07** | 0 |

**その解像度で改めてラスタライズされている**ので、4K / 200% では顔のノードに
40 device px・詳細ペインの顔に 80 device px が実際に配られる。offscreen + `grabToImage`(= verify-ui と同じ経路)で測った。

この試験の 1px の円と対角線は `antialiasing: true` を付けても階調が 2 段のまま。製品の印(顔の輪・
レーン)は同じ offscreen の経路で縁に中間色を持ち、`basic` の 1 行では実窓と画素まで一致した
([P5-確認事項.md](../../internal-docs/P5-確認事項.md) §実測済み。この試験との差の理由は未調査)。
画像の縮小は別経路なのでアバターの判断には影響しない。4K の実窓での確認は同 §9。

## 6. 依存の候補と値段

同じ仕事(デコード → 中央切り → 正方 → PNG 書き出し)を組んで実測。空の実行ファイル
130KB を基準にした増分:

| | 追加クレート | 実行ファイル増 | 受け取れる形式 | 縮小 |
|---|---|---|---|---|
| `image`(`png,jpeg,webp,bmp`) | 19 | +900KB | png / jpg / webp / bmp | 27ms |
| `image`(`png,jpeg`) | 17 | +634KB | png / jpg | 27ms |
| **`png` + `zune-jpeg` + 自前** | **10** | **+396KB** | **png / jpg** | **7ms** |
| 同 + `gif`(採らない) | 13 | +444KB | + gif | — |

**採ったのは 3 行目**。`image` は縮小と切り出しを自前 30 行に置き換えるだけの薄さしか
足していない。GIF を外した理由は表示の側 —— グラフのノードは
Canvas に描くのでアニメーションさせると可視行が毎フレーム repaint になる。

webp / bmp / gif / heic / avif を入口から外した理由は値段の外にもある:
HEIC は許容ライセンスの純 Rust デコーダが存在しない(libheif / libde265 は LGPL / GPL)。
AVIF も Sisvel が AV1 のプールを主張していて係争中。WebP(VP8)と GIF(LZW)は特許的には
解決済みなので、外したのは「入口を広げる価値がコストに見合わない」判断。

## 7. 縮小でしか直らないもの(fps とは別)

**可搬性**。保存が常に PNG になれば、imageformats プラグインの有無に依存しない。

**画像は保存された向きのまま**。アバターに使うファイルは各人が既に持っている
アイコン。
