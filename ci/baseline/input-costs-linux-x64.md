# メッセージ・パッチの渡し方の実測(Linux x64・コンテナ)

[input-costs-windows-x64.md](input-costs-windows-x64.md) と同じ比較を `cargo xtask linux` のコンテナで撃った物。
**実機ではない**(Windows 11 の WSL 3 の VM の中の Ubuntu 24.04、ディスクは VM の仮想ディスク)— 実機の
baseline は [P5-確認事項.md](../../internal-docs/P5-確認事項.md) §23。読むのは前後の差だけ。

## 採否

- **採用**: commit のメッセージ・部分ステージと部分破棄のパッチ・復元のパッチを全部 stdin で渡す
  (`process::Input`)。**1 MiB を越える入力は git の stdin のパイプを 1 MiB に広げる**(`process::child::PIPE_WIDTH`、
  `F_SETPIPE_SZ`。広がらなければ既定の幅のまま送る)。1 MiB 以下は既定の幅のまま
- **設計上の不採用**:
  - 大きな入力も既定の幅(64 KiB)のパイプで送る — git が読むのが 1 回あたり 1 MiB のパイプより約 26ms 重い
    (下の §git だけの切り分け)
  - memfd を stdin に開く — 1 回の読みは 1 MiB のパイプと p10–p90 が重なる(下の表)。2 回読ませる復元では 1 回の
    書き込みで 2 回読めるぶん有利になりうるが測っていない。Linux だけ別の送り方(送信の失敗・git が読み残した
    ことの見分けが別物)を持つ保守に見合わないと判断した
  - 復元だけ一時ファイル — 製品の計測で前後の差が幅の内(下の表)。ただし前の木の復元はパッチの置き場を訊く
    `rev-parse --absolute-git-dir` を 1 本余計に撃っていて(`worktree_at` が git dir を既に読んでいる)、その分は
    前に不利。git だけの表から見積もると、それを除いたファイル方式は約 9ms(3%)速い(推論 — 下)。ディスクへの
    書き込みと、パッチの一時ファイルの寿命(作る・sync・消す・落ちた時の残り)を持たないことを取って stdin にした
  - OS で渡し方を分ける(Windows は stdin、Linux は一時ファイルを書いて stdin に開く。git の引数は `-` のまま
    なので、差はプロセス層に閉じられる)— git だけの表から見積もると、1 回読ませる時は 1 MiB のパイプが約 2ms
    速く、2 回読ませる復元では一時ファイルが約 8ms 速い(推論 — 下)。Linux だけパッチの一時ファイルの寿命と
    ディスクへの書き込みを持ち、送り方とその網が OS で 2 通りになる保守に見合わないと判断した
- **保留**: macOS の渡し方(パイプを広げる手段が無い。代わりの候補は送り側の容量を広げた socketpair か、macOS
  だけ一時ファイル)— macOS で測るまで(P5-確認事項 §23)
- **検討していない**: 送り手の作り(tokio の非同期の書き込みの代わりの、書き込み専用のスレッドや `splice`)。
  1 MiB のパイプで、既定の幅のパイプが「パスで渡す」に足す分の大半が消えたので、要が出たら測る

## 条件

- 前: `6fe8bd271`(reword の置き場まで。メッセージ・パッチは一時ファイル)の製品から、NUL を含むメッセージの
  拒否とコメントを除いた木 / 後: `2992503ec`(stdin)の製品と、止めた run が stdin を閉じる所・幅を広げたことを
  テストが見る口・コメントだけが違う木(止めない run の処理は同じ)。計測のテスト(`tests/it/input_costs.rs`)は
  前後とも同じ物で、`12424386e` の物とはコメントだけが違う。git 2.43.0(最低版)
- §git だけの切り分け は `12424386e` とコメントとテストの名前だけが違う木で撃った。プローブは git の本体を最初に
  1 度だけ探し、時計はコマンドを組み立てた後から始める(memfd への書き込みは時間に入る)
- 撃ち方: 前の木で `--target-dir target/bench-before` に組み、後の木で cargo の runner に台本を差す(cargo が組んだ
  後の exe を引数に受ける)

  ```
  cargo xtask linux test --config=profile.release.debug-assertions=true --release --target-dir target/bench-before -p platitude-core --test it --no-run
  cargo xtask linux test '--config=target.x86_64-unknown-linux-gnu.runner=["sh","../../<台本>"]' --config=profile.release.debug-assertions=true --release -p platitude-core --test it
  ```

  台本(リポジトリには置かない)は、前の exe(`target/bench-before/release/deps/it-*`)と受けた後の exe で、6 つの
  操作を 1 操作 1 プロセスで前・後・後・前 × 5 ブロック(1 変種 10 run)撃ち、各 run の前後で `/proc/diskstats`
  の `sd*` / `vd*` / `nvme*n*` の書き込みセクタを読む。runner はクレートのフォルダを cwd にして呼ばれるので、
  台本は席の直下に置いて `../../` で指す。§git だけの切り分け は runner を差さずに撃つ

  ```
  cargo xtask linux test --config=profile.release.debug-assertions=true --release -p platitude-core --test it -- --ignored --exact --nocapture input_ways::ways_in
  ```
- **静かさ**: ABBA の間はホストで 5 秒ごとに CPU と、誰かの gate・land・verify-ui・perf の数を記録した。CPU
  平均 14.1%・最大 46.6%(1 回)、他の作業 0。§git だけの切り分け も同じ記録を付けた(コンテナの立ち上げから
  終わりまで): CPU 6.1–11.5%(5 回)、他の作業 0
- 1 run の中身は Windows の記録と同じ(小さな入力は 30 回、約 32MB の入力は 10 回)
- 計る物: 1 回ずつの時間の run 内中央値 / 自プロセスの `VmHWM` / 刈り取った子の `ru_maxrss` の最大
  (`getrusage(RUSAGE_CHILDREN)`、仕込みの git も入る)/ VM のディスク書き込み(1 run)。**WSL のカーネルに
  `/proc/self/io` は無く、cgroup の `memory.peak` はコンテナから戻せない**(書けないので run ごとの峰にならない)
- **子の `ru_maxrss` の下限**: exec は差し替える前の mm の峰を exec した側の `signal->maxrss` に畳み込む
  (v6.18 の `fs/exec.c` の `exec_mmap()` が `setmax_mm_hiwater_rss(&tsk->signal->maxrss, old_mm)`)。std の
  posix_spawn は vfork で親の mm を共有するので、子の値は**産んだ時の親の峰を下回らない**。子の峰として読める
  のは親より大きい時だけ

## git だけの切り分け(不採用案の値を含む)

約 31.8MB のパッチを読ませる時間(`tests/it/input_ways.rs`。読ませ方を 1 周に 1 回ずつ 40 周、周ごとの順は
固定の種から並べ替える。一時ファイルはその後で 40 回)。git の峰は時間の後の別の 1 回で、終わった git を
`wait4` で刈り取って読んだ `ru_maxrss`(その時の自プロセスの峰 39.6–40.0 MiB が下限)。

## 観測

- 小さな入力の 3 つ(commit・部分ステージ(小)・復元(小))は後が 2.4–4.7ms 速く、run の幅は重ならない
- 大きな入力を 1 回読ませる 2 つは後が 8.8–12.3ms 速い(幅は重なる)。2 回読ませる復元(大)の差は −1.0ms で幅の内
- VM のディスク書き込みはどの操作でも後が少ない。大きな入力で 1 run あたり 304–305 MiB 減る。部分破棄だけは
  後にも 172 MiB 残る
- 自プロセスの峰は前後で 2 MiB 以内。子の峰は、復元(大)では前後とも 103.6 MiB で親の峰(約 40 MiB)より大きい。
  部分ステージ・部分破棄(大)では親と同じ値で、git の峰は読めていない(§条件 の下限)
- git だけ: git 自身の峰は 5 つの読ませ方で 103.1–103.5 MiB。既定の幅のパイプは「パスで渡す」より +36.0ms、
  1 MiB のパイプより +25.6ms。git 無しで同じパイプを `cat` へ送るだけで 33.5ms。1 MiB のパイプは「パスで渡す」
  より +10.4ms、`cat` へは 10.2ms。ファイルを stdin に開くのは「パスで渡す」と、memfd は 1 MiB のパイプと
  p10–p90 が重なる

## 推論(確かめていない)

- 既定の幅で git の読みが重いのは、パッチの解釈ではなく**パイプを渡る転送**: git 無しの `cat` でもほぼ同じだけ
  かかり(33.5ms と +36.0ms)、幅を広げると両方縮む(10.2ms と +10.4ms)。送り手(tokio)・kernel のパイプ・
  切り替えのどれがどれだけかは分けていない(`cat` も同じ送り手で送っている)
- 復元(大)でファイル方式が勝ちうる幅: 「パスで渡す」2 回 + 一時ファイル 1 回(2 × 70.9 + 12.1 = 153.9ms)と
  1 MiB のパイプ 2 回(2 × 81.3 = 162.6ms)の差で約 9ms。製品の計測(前は `rev-parse` 1 本込み)では差が出て
  いないので、操作全体では読みの差がほかと重なっていると読む
- OS で分ける案(一時ファイルを stdin に開く)の見積もり: 1 回読ませる時は 71.5 + 12.1 = 83.6ms と 1 MiB の
  パイプの 81.3ms、2 回読ませる時は 2 × 71.5 + 12.1 = 155.1ms と 162.6ms
- VM のディスク書き込みの減りは、1 回にパッチ 1 本分の一時ファイルが無くなった分。部分破棄の後に残る分は
  作業ツリーへの書き戻し(16MB × 10 回)
- 復元(大)の子の峰 103.6 MiB は git だけの表の git の峰(103.1–103.5 MiB)に近いので、`apply` か、同じ大きさの
  パッチを書き出す `diff-tree` のどちらか
