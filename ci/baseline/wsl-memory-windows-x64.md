# gate を繰り返した時の WSL のメモリ(Windows x64)

`cargo xtask footprint gate --all --fresh` を**間に `wsl --shutdown` を挟まず 3 本連続**で撃った実測。
計測日: 2026-09-19、席 a、HEAD `bc9bd45a`。生の行は `target/footprint/<run>/`(`host.csv` / `vm.txt` /
`docker-before.txt` / `docker-after.txt`)。

## 読み方

- **`vmmemWSL` のワーキングセット = Windows が失った量**、**VM の `/proc/meminfo` = Linux が使っていると思っている量**。
  メモリは名前空間で割れないので後者はコンテナを含む VM 全体で、**`docker stats` の合計はこれの代わりにならない**
- **`MemFree` では判定しない** — 回収できるキャッシュが育っただけの VM も小さく見える。枯渇したかを言うのは
  `MemAvailable` と PSI(`/proc/pressure/memory`)と `oom_kill`
- **ホストの空きの低下を外部負荷の証拠にしない** — 下の表のとおり、低下分はほぼ `vmmemWSL` の増加分と同じ

## 出発点(11:40、run 1 の直前)

ホスト 31903 MB。空き **12506 MB**、`vmmemWSL` **1594 MB**。VM の MemTotal は 15564 MB(ホストの約 50%)。
`~/.wslconfig` は `[experimental] autoMemoryReclaim=gradual` のみで **`memory=` の上限は無い**。
常駐の内訳(11:59 の実測、372 プロセスで WS 合計 25413 MB): chrome 3451 / idea64 2438 / claude 1334 /
MsMpEng 1180 / svchost 1176 / ChatGPT 906 / gitkraken 483 / Discord 323 MB。
**この常駐は 3 本を通しての初期条件**で、差分の説明には使わない。

## 3 本の gate(連続、リセット無し)

`--all --fresh` を使うのは、**キャッシュの当たった gate は何も実行しないから**(`cached 1049` で 8 秒)。
「繰り返すと膨らむ」は実行される gate の話で、空回りでは再現しない。
run 1 のホスト側は 5 行で止まっている(下の §計測器の穴)。「終了後」は run 2 以降はコマンド終了 +60 秒。

| | run 1 (6m19s) | run 2 (6m01s) | run 3 (5m03s) |
|---|---|---|---|
| ホスト空き 前 → 後 | 12528 → —— | 5916 → **5062** | 4915 → **4312** |
| ホスト空き 最小 | —— | **1615** | **1636** |
| `vmmemWSL` 前 → 後 | 1558 → —— | 7435 → **8556** | 8548 → **9452** |
| `vmmemWSL` ピーク | —— | 10378 | 11443 |
| VM MemAvailable 最小 | 12644 | 12621 | 12466 |
| VM Cached 後 | 5118 | 5425 | 5726 |
| VM Buffers 後 | 899 | 1205 | 1542 |
| VM SReclaimable 後 | 358 | 579 | 777 |
| VM Percpu 後 | 33 | 57 | 82 |
| VM AnonPages ピーク | 2242 | 1953 | 2045 |
| コンテナ(延べ / 同時最大 / 最大 peak) | —— | 513 / 10 / 1112 MB | 513 / 10 / 543 MB |
| PSI `some` 累計 / oom_kill | 0 / 0 | 160 µs / 0 | 166 µs / 0 |
| gate 後のコンテナ残留 | 0 | 0 | 0 |

**1 本あたり返らない分は約 900 MB**(run 2 終 → run 3 終で VM の使用量 +882 MB、`vmmemWSL` +896 MB、
ホスト空き −750 MB)。内訳は **Buffers +337 / Cached +301 / SReclaimable +198 / Percpu +25 / SUnreclaim +25**、
AnonPages は +2 = **育つのは全部キャッシュとカーネルのスラブで、プロセスのメモリではない**。
`Percpu` の単調増加は cgroup を 513 個作って捨てた分。

**VM の中は枯渇していない** —— MemAvailable は 3 本とも 12.4 GB を下回らず、PSI の待ちは累計 166 µs、
oom_kill は 0。つまり Linux には回収する理由が無く、**WSL がホストへ返すのは VM の中で free なページだけ**なので、
Windows 側だけが減る。

## gate を止めた後も増える(2026-09-19 12:04–12:20、実測)

run 3 の後、**gate もコンテナも 1 つも走っていない 9 分間**、ホスト側だけを 10 秒ごとに読んだ
(VM には一切触っていない = `target/footprint/quiet-after-run3.csv`)。

- ホスト空き **4352 → 447 MB**、`vmmemWSL` **9447 → 14966 MB**
- その時点の VM: Buffers **8.46 GB**、SReclaimable **2.92 GB**、Cached 1.68 GB、MemFree 1204 MB、
  MemAvailable **14.3 GB**(やはり枯渇していない)
- 読んでいるのは **`/initd services`(PID 68、Docker Desktop が distro の中で回している常駐)** 1 本。
  30 秒で **+718 MB**(≒24 MB/s)読み続け、同時刻の `dockerd` と `containerd` の `read_bytes` は 1 バイトも動かない
  (`/proc/<pid>/io`)。`/proc/diskstats` の `sdd` も同じ幅で伸びる

**この 9 分の間、`autoMemoryReclaim=gradual` は 1 度も返していない**(伸び続けた)。

## 読み手が黙れば返る(12:21–12:23、実測)

`/initd services` の `read_bytes` が **100 秒で +0.5 MB**(= 実質停止)になったところから、20 秒ごと:

| 時刻 | ホスト空き | `vmmemWSL` |
|---|---|---|
| 12:21:07 | 3882 | 12874 |
| 12:21:47 | 4416 | 12374 |
| 12:22:27 | 4716 | 12102 |
| 12:22:47 | **4960** | **11802** |

同時刻の VM: MemFree 1204 → **4861 MB**、Buffers 9.37 → **7.18 GB**、Cached 1.42 → **0.54 GB**、
SReclaimable 2.92 → **2.31 GB**。**返る速さは約 600 MB/分**。

**この 1 回は、読み手が黙ってから返った。** アイドル判定は VM の中を見るので、
**Docker Desktop の常駐が 24 MB/s で読み続けている間はアイドルにならない**。
**「必ず操作困難になる前に回復する」ことは証明できていない** —— 下の 13:24–13:27 では、
読み手が動いたままホストの空きが 1.2〜1.6 GB で横ばいだった。

## 読み手が何を読んでいるか(13:05、`/proc/68/fd` で現認)

走査中の `/initd services` が開いていたのは
`/var/lib/docker/volumes/pgg-linux-demo-a/_data/one-commit-43-…-0/repo/.git` ——
**gate が作ったコンテナ用のデモリポジトリ**。同時刻のボリュームの中身:

| ボリューム | ファイル数 | 大きさ |
|---|---|---|
| `pgg-linux-demo-a` | **2,646,738**(run ディレクトリ 14,895) | 10.6 GB |
| `pgg-linux-target-a` | 22,132 | 10.4 GB |

**inode の 99% はデモ側**で、gate 1 本が約 500 ディレクトリ(約 9 万ファイル)を足し、
**誰も消していなかった**。ホストは gate の入口で自分のぶんを掃く
(`verify::ownership::sweep_yesterdays_runs`)が、コンテナ側にはその掃除が無かった。
`/initd` のログ(`%LOCALAPPDATA%\Docker\log\vm\init.log`)は
**コンテナが 1 つ消えるたびに `fstrim /var/lib/docker` を仕掛け直し**(gate 中は約 10 秒ごと)、
**走査そのものは 1 行も記録しない**(12:04–12:22 の 22 分でログは 5,700 行、その間に GB 単位の読み)。

## 対策と、その前後(同じ `gate --all --fresh`)

対策は**コンテナ側にも掃除を持たせた**こと(`linux::runner::SCRIPT`。テンプレートと
`.pgg-keep` と直近 30 分は残す)。**開始状態が揃っていない**ので、読めるのは
「掃除が効いたか」と「VM の中の向き」だけ。

| | BEFORE (12:47) | AFTER (13:09) |
|---|---|---|
| 開始時のホスト空き | 3334 MB | **1141 MB**(不利な側) |
| ホスト空き 最小 | **150 MB** | **613 MB** |
| デモの run ディレクトリ | 14,895(増える一方) | **14,922 → 1,797** |
| VM SReclaimable | 1562 → **2523**(増) | 2521 → **2325**(**初めて減った**) |
| VM Cached 終値 | 1520 MB | **564 MB** |
| PSI `some` の増分 | +434 ms | +228 ms |
| `vmmemWSL` 終値 | 10568 MB | 14805 MB |

**言えるのは 3 つ**: 掃除は 13,125 ディレクトリ(約 230 万ファイル)を実際に落とした /
それまで単調増加だった SReclaimable が初めて減った / 同じ仕事を**より低い空きから**始めて
最小値は 150 → 613 MB に上がった。
**`vmmemWSL` の終値は比較に使えない** —— AFTER は 15.5 GB の Buffers を抱えた状態から始まっており、
Buffers はアイドルになるまで返らないので、この列は開始状態の話をしている。

## `/initd services` のストレージ読み取り量 — 区間で分けて読むこと

**`read_bytes` はストレージから読んだバイト数であって、何かの「開始・停止」ではない。**
増えたことは「そのプロセスがディスクを読んだ」としか言わず、止まったことは
「キャッシュに当たっていた」でも成り立つ。以下は**区間ごとの読み取り量**であり、
窓の長さが違うので**この行から削減率を出してはいけない**。

| 区間 | 長さ | 累計 read_bytes | 区間内の増分 | 平均 |
|---|---|---|---|---|
| 13:27 → 13:31 | 約 4 分 | 46.27 → 46.29 GB | **+0.2 MB** | ほぼ 0 |
| 13:38 → 14:06 | 28 分 | 46.29 → **48.72 GB** | **+2.43 GB** | 約 1.4 MB/s |
| 14:11 → 14:15(drop 直後) | 4 分 | 48.73 → **54.75 GB** | **+6.0 GB** | 約 25 MB/s |

掃除の前に測った 24 MB/s とこの 1.4 MB/s は**同じ条件で並べた 2 点ではない**
(前者は 260 万ファイルが在った時の gate 直後、後者は掃除後の静穏時)ので、
**削減率は確定していない**。言えるのは「掃除の後にもこのプロセスはディスクを読んでいる」ことだけ。

13:27–13:31 の間に VM は返し始めている: `vmmemWSL` 14150 → 13575 MB、ホスト空き 651 → 1877 MB。

## 単発の `drop_caches` は恒久対策にしない(14:11、実測)

| | 直前 14:11:08 | 直後 14:11:36 | +3.5 分 14:15:14 |
|---|---|---|---|
| ホスト空き | 3290 MB | **8300**(ピーク 9469) | 4428 |
| `vmmemWSL` | 9922 MB | **3243**(最小 2831) | 7959 |
| VM Buffers | 3.39 GB | **266 MB** | 4.96 GB |
| VM SReclaimable | 2.42 GB | **181 MB** | 2.03 GB |

**効いたのは約 90 秒**で、そのあと `read_bytes` が 25 MB/s で伸びて元の水準へ戻った(上の表の 3 行目)。
**キャッシュを落とせばディスクからの読み直しが増えるのは当然**なので、恒久対策としては採らない。
撃った 14:11 の時点で VM は自力で 10 GB 級 → 3.4 GB まで返し終えており、
**この 6.7 GB は「もっと早い時点なら 10 GB 級だった」量の残り**である。

**この再増加が何だったかは未確認。** 観測できたのは「キャッシュを落とした後に読み取り量が増えた」ことだけで、
**それが新しく始まった走査なのか、キャッシュを失った既存の処理が読み直しただけなのかは区別できていない。**

**「自然回収で足りる」とも言えない。** 返った観測(12:21 の 600 MB/分、13:27 の 150 MB/分)と、
返らずに横ばいだった観測(13:24–13:27 にホスト空き 1.2〜1.6 GB)が両方ある。

## 掃除を入れた後の連続実行(14:30–15:19、実負荷 3 本)

`gate --all --fresh` を背中合わせで 3 本。**キャッシュの当たる gate は負荷に数えない**
(この HEAD の素の `gate` は 1048 cached / 0 run = 8 秒で何も実行しない)ので、
3 本とも 1049 ステップ・約 515 コンテナを実際に回している。**実行対象は増やしていない** ——
これまでの arm と同じ `--all --fresh` で、比較できるようにするため。

**底の位置は run ごとに違う。** run 1 の 139 MB は開始 14 秒後 = **前の状態を引き継いだもの**
(この run は 763 MB から始まっている)。run 2 の 645 MB は gate 中。
**run 3 の 459 MB だけが gate 終了の後**(≈14:56 終了、15:04:12 に底)。

**窓の長さが読みを変える。** run 1 / 2 の観測窓は 240 秒で、run 3 で低空きが始まった

**run 1 / 2 に同じことが起きなかったとは言えない** —— 観測していない。
同じ理由で、**「gate ごとに同じ症状が起きる」も「反復で蓄積しない」も、この 3 本からは断定できない。**

各 run の開始時の `vmmemWSL` は 13263 → 10443 → 9115 MB と下がっているが、
**これも窓の長さが揃っていないので、蓄積の有無の証拠にはしない。**

## この 3 本の後、自然に回復した(15:06–15:19、実測)

run 3 の観測窓が終わった直後から 1 分ごと。**この記録は「今回の連続実行の後、自然に回復した」
という 1 回の実測であり、毎回そうなることの証明ではない。**

| 時刻 | ホスト空き | `vmmemWSL` |
|---|---|---|
| 15:06:20 | 1052 | 13820 |
| 15:08:21 | 2139 | 12892 |
| 15:10:21 | 3904 | 11488 |
| 15:14:21 | 5092 | 10005 |
| 15:19:29 | **6951** | **8280** |

**約 450–500 MB/分**。1.6 GB を割っていたのは **15:02:09 から 15:08:21 までの約 6 分**
(15:07:20 が 1558 MB、15:08:21 に 2139 MB で復帰)で、**その全部が gate 終了の後**。
gate 終了(14:56)から 6.9 GB までは **約 23 分**。
同時刻の VM: Buffers 1.92 GB / MemFree 10.3 GB / MemAvailable 14.6 GB / oom_kill 0。
**swap は run 3 で 27 MB 使われたのが唯一**(3962 → 3935)。
**3 本とも `wsl --shutdown` 無しで完走した。**

**判定**: **この 3 本を背中合わせに回した後、ホストは自然に回復した**(23 分で 6.9 GB)。
それ以上は言わない —— 「反復で蓄積しない」も「gate ごとに同じ症状が起きる」も、
**観測窓が揃っていない 3 本からは断定できない**。

## 「通った run が自分のデモルートを返す」の前後(窓を揃えた 1 対)

同じ `gate --all --fresh`、**終了後の観測窓はどちらも 1200 秒**(run 3 で低空きが始まった
gate 終了 +6 分と、そこからの回復を含む長さ)。BEFORE = `59f8e0ca`(掃除だけ)、
AFTER = `1435fbbe`(掃除 + 返却)。**開始時の VM を揃えてから始めた**(`vmmemWSL` 6226 / 5578 MB)。

| | BEFORE | AFTER |
|---|---|---|
| gate | 6m21s **PASS** | 6m28s **PASS** |
| 開始ホスト空き / `vmmemWSL` | 7994 / 6226 | 5846 / 5578 |
| ホスト空き 最小(時刻) | **2019**(15:55:16) | **1395**(16:31:17) |
| その最小は | gate 終了 +11 分 | gate 終了 +11 分 |
| 2.5 GB 未満だったサンプル | 73 行(146 秒) | **219 行(438 秒)** |
| 窓の終わりのホスト空き | 4903 | 6058 |
| `vmmemWSL` 最大 / 終 | 12058 / 8399 | 12007 / 8156 |
| VM MemAvailable 最小 | 12431 | 12822 |
| VM SReclaimable 前 → 後 | 1339 → 1914 | 1835 → **1733** |
| PSI `some` の増分 | +76 ms | +39 ms |
| SwapFree / oom_kill | ほぼ不変 / 0 | ほぼ不変 / 0 |

**効いたのは 1 つだけ。** gate 1 本がデモボリュームに残す run ディレクトリは **740 → 99**
(514 の動詞に対して。残った 99 はほぼテンプレートで、実測: volume 1571 エントリ中 **1334 が
テンプレートの印を持つ**)。

**効いていないもの。** ホスト空きの底(2019 → 1395)、2.5 GB 未満の継続(146 → 438 秒)、
`/initd services` の読み取り量(9178 → 9118 MB)—— **この 1 対では改善していない**。
読み取り量が 1% 差だったことの説明は**仮説のまま**: 2 本の arm が回っていた時の
ボリュームの大きさが近かった(掃除の後で 1212 / 1472 ディレクトリ)から、という読みは
**確かめていない**。確かめるなら、ボリュームの大きさを桁で変えた 2 本を同じ窓で撮る。
言えるのは、**この対では読み取り量が動かなかった**ことと、
**読み取り量がデモの inode 数に比例するという読みがこの対では支持されない**ことだけ。
ホスト空きの差は開始時点で 2.1 GB 違っており、**この 1 対から返却の効果とは言えない**。

**ボリューム自体はこのセッションを通して 264 万ファイル / 10.6 GB → 21.7 万 / 916 MB**
(92% 減)。ただしその大半は 30 分の床を持つ掃除が先に落としたぶんで、
**返却の寄与はこの 1 対が示す「1 本あたり 740 → 99」の側**。

## 残っている不足(観測されたもの)

**コンテナ側の掃除はテンプレートを永久に残す。** ホストの掃除は 1 日でテンプレートも
連れて行くが、コンテナ側の床はテンプレートを明示的に spare する。fingerprint が動くたびに
新しい組が建つので、いまボリュームの **1571 中 1334 がテンプレート**。
次はここを、ホストと同じ「1 日経ったテンプレートは連れて行く」に揃えるのが筋。

**ただしこれは残骸の話であって、ホストの低空きの話ではない。** 上の 1 対が示したとおり、
残骸を減らしても**ホスト空きの底・低空きの継続・読み取り量は動かなかった**。
**2 つは別々に判定する** —— 残骸が減ったことをもって WSL の低空き症状を片付いたことにしない。

**背中合わせの gate ではデモボリュームが増えていた** —— 1838 → 2492 → 3146。
掃除の床が 30 分なので、30 分以内に積んだぶんが残っていた(run 3 でようやく 406 個が床を越えた)。
**これは直した(実装済み)**: 通った run が自分のデモルートを返す
(`verify::ownership::give_back_claimed`。失敗した run のものは
[現場](../internal-docs/P3-確認事項.md)のために残す)。前後の測定は上の 1 対。

## 言えること / 言えないこと

- **実測で言える**: 連続 gate 1 本につきホストは約 750 MB、`vmmemWSL` は約 900 MB 増え、走っている間は返らない。
  増えるのは回収可能なキャッシュ(Buffers / Cached / SReclaimable)とスラブで、VM の中は枯渇していない
- **実測で言える**: 走査の読み手は `/initd services` で、読んでいるのは **gate が置いたデモリポジトリ**
  (`/proc/<pid>/fd` で現認、260 万ファイル)。掃除でそれを 1,797 ディレクトリまで落とした
- **実測で言える**: 読み手が黙った 100 秒間は `autoMemoryReclaim=gradual` が約 600 MB/分で返した
- **言えない**: **掃除が走査をどれだけ減らしたか**(区間の長さが違う 2 点しかない。上の表)
- **言えない**: **自然回収で足りること**。返った観測と横ばいの観測が両方ある
- **言えない**: **`memory=` 上限が唯一の対応であること**。他に手が無いと確かめたわけではない
- **言えない**: **`memory=` 上限が要るか要らないか**。**VM の中の余裕(MemAvailable・PSI・oom_kill)と、
  Windows 側の低空きは別の指標**で、前者に余裕があることは後者の対策が不要な理由にならない
  —— 上限が効くのはまさに「VM が Windows から取れる量」の側である。
  **効果も適合性も、上限を置いた状態で実負荷を通して測るまで未判定**
- **言えない**: `/initd services` がどのサービスとして走査しているか。読む対象と、
  コンテナ削除ごとに `fstrim` が仕掛け直されることは判ったが、走査そのものを起こす条件は
  ログに 1 行も無い
- **ホストの空きの低下を外部負荷のせいにしない**。常駐の内訳を挙げる時は
  **同時刻に撮ったプロセス表**を添える(11:59 と 14:06 の 2 枚がそれ)。時刻の違う 2 枚の差は
  外部負荷の証拠にならない
