# 性能実測記録(Windows x64)

計測: 2026-08-29、commit 22fd9ae3。**§Qt の床 と §アロケータ の 2 表だけは
2026-08-11 のまま** — 道具の側を測ったもので、アプリ側の変更が届く場所ではない。

## 計測条件

- 対象: `JetBrains/kotlin` full clone — 228,523 commits、refs 54,267 本
  (タグ 46,371 / リモートブランチ 7,894)、commit-graph chain あり
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ)。自動化 env が設定ストアを空にするので既定値そのまま
- `cargo xtask perf --repo <path>` が条件を持つ — release ビルド、**実ウィンドウ**
  (offscreen ではメモリも fps も表示性能にならない)、ウォームキャッシュ、
  `PG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング最大値、
  デッドライン + kill ガード。1 回目は捨てて以降を採る
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / 1920x1080@100Hz / Windows 11 build 26200 /
  git 2.55.0。**GPU は 2 枚(AMD 内蔵 + NVIDIA RTX 3070)+ DisplayLink 2 台**で、
  Qt がどのアダプタを掴むかはこの条件が固定していない(§読み方)
- 数値は 3 回連続実行の範囲(全数)。**出荷構成のビルド**(`memprobe` feature 無し)

## 判定

| 予算 | 実測 | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 1,126–1,170ms | ✅ |
| 操作応答 100ms | 41–92ms | ✅ |
| スクロール 60fps | 123.6–129.0fps | ✅ |
| メモリ 300MB | **350.3–364.0MB** | ❌ **64MB 超過** |

- private bytes は 328.9–341.7MB。予算は WorkingSet に対して読む
- **操作応答は機械の静けさで動く** — この 1 点はプロセス 1 個ぶんなので、同じ
  コミットを続けて撃った 1 本前の run は 90–112ms で予算を跨いだ。**赤く見えたら
  まず機械を静めて撃ち直す**(§この記録の読み方)
- fps は `onFrameSwapped` の実数。表示は 100Hz なので、vsync が乗った回はその値で
  頭打ちになるはずだが、この機材では乗らない回の値(124–142fps)が出る。予算
  60fps に対してはどちらも余るので、どちらが出たかは判定を動かさない
- 操作応答はハーネスが撃つ行選択→詳細の 1 点で、タグ込み walk が裏で走っている
  最中に当たる。**この 1 点はプロセス 1 個ぶん**(`git show` に書式とファイル一覧を
  まとめて訊く)で、Windows のプロセス生成 18ms がその半分近くを占める
- 数字が取れなかった run は `missing` として報告ごと落ちる(`xtask perf`)。
  前提はログが無色であること — 色コードが乗ると `key=value` が検索不能になる
  (`platitude_gg::init_tracing` は色を付けない)

## メモリの内訳: 何を足すといくら増えるか

同じビルドで、ハーネスに撃たせるものを 1 段ずつ足した WorkingSet:

| 何をした窓か | WorkingSet | 前段からの差 |
|---|---|---|
| リポジトリを開かない(`--no-open`) | 143.6MB | — |
| 基準リポジトリを開くだけ(`--no-select --no-scroll`) | 272.4–284.5MB | **+129〜141** |
| + ハーネスの行選択(`--no-scroll`) | 298.1–299.2MB | +14〜27 |
| + スクロールベンチ | **350.3–364.0MB** | **+52〜65** |

**予算を割っているのはスクロール。** ベンチ無しなら 298–299MB で予算の内側だが、
余白はほとんど無い。積んでいるのは Qt 側 — **run 全体を通しても Rust ヒープは
常駐 24.8MB / ピーク 34.2MB**(下表)で、この差はそもそもヒープに入らない大きさ。

**それは漏れではない。** 4 つの実測がそう言う(`--settle-ms` と 4 周ベンチ):

- **戻らない**: 8 秒アイドル後も峰とほぼ同じ。ベンチ無しは同じアイドルで 20MB 返すので、
  返せる分は返している
- **頭打ちする**: 同じ 1,961 行を 4 周(約 7,844 行ぶん)しても 1 周と同じ。決めるのは
  **一度見た行の数**で、走った距離ではない
- **デリゲートの作り直しではない**: 12 秒で作られたのは 57 個だけ(`reuseItems` は効いている)
- **行のデリゲートの中身**: 空デリゲートに差し替えると 223.2MB、本物は 370.9MB(同条件)。
  内訳は **subject の文字列 −74.0MB**(定数にした時)と **Canvas の描画 −42.6MB**
  (`onPaint` を no-op にした時)

つまり **2,000 行を組むのに要った C++ ヒープが高いまま返らない**形で、`gc()`・
`QSG_ATLAS_*` の縮小・`Canvas.Immediate` はいずれも動かさない。残る手は
[P3-確認事項.md](../../internal-docs/P3-確認事項.md) §app。

**リポジトリを開くだけで +129〜141MB** が次に大きい。この段では refs 5 万本の
索引(下表の上位 2 件で 10.6MB)と、グラフ 2,001 行の Qt 側の実体化が入る。

## Rust ヒープ

`cargo xtask perf --breakdown`(`memprobe` feature = 計数グローバルアロケータ。
Qt は C++ の `operator new` を通り `GlobalAlloc` に乗らない = この境界が
「アプリのデータ」と「その下の道具」を分ける)。

| 区分 | 実測 |
|---|---|
| 常駐(`rust_live`) | 24.8MB |
| ピーク(`rust_peak`) | 34.2MB |
| 名前の付いた分 | 12.6MB |
| 名前の無い分 | 12.2MB |

**常駐・ピークはサンプルで揺れる** — ポーリングのどこに当たったかで、refs
パイプラインが一時的に抱えている分が乗る。**変化を読むなら下の名前付きの表**
(同じ refs 数なら再現する)。

| 保持者 | bytes | 要素数 |
|---|---|---|
| `session::LabelIndex` | 5,541,232 | 48,074 |
| `RefsSnapshot` | 5,040,547 | 54,264 |
| `GraphModel` の行 | 2,302,328 | 2,001 |
| walk のビルダ | 176,624 | 2,031 |
| 適用済みの差分 | 82,043 | 505 |
| 送信済み行の指紋(背景差分用) | 32,016 | 2,001 |
| 詳細のファイル一覧 | 6,774 | 26 |
| diff の行 | 3,125 | 16 |
| サイドバー 8 セクション合計 | 1,916 | 54,272 |

`session::RemoteTagIndex` はこの run では 0 — fetch の後にだけ建つ。

**refs の本数がメモリを決める。** 上位 2 件はどちらも refs の本数に比例し、
合計 10.6MB — 名前の付いた分の 84%。commits ではなく refs が支配的。
**行数に比例するのは 2 件だけ**(`GraphModel` の行 1,150 B/行 + walk のビルダ
87 B/行 = **1,237 B/行**)。サイドバーは 8 セクション合計 1,916 バイト —
54,272 行の中身は `RefsSnapshot` を読む(規約は rules-refs/app-ui.md)。

## Qt の床(2026-08-11)

Qt そのものの値なので、アプリ側の変更では動かない:

| 積み上げ | WorkingSet | 差分の中身 |
|---|---|---|
| Qt の `qml.exe` + 素の `Window` | 75.5MB | Qt Quick + D3D + GPU ドライバの床 |
| 同 + Controls(Fusion)+ `ListView` | 83.9MB | +8.4 = このアプリも使う部品 |

描画経路の寄与は同条件の差で取った: リポジトリ無しが software 描画 90.9–91.3MB に
対し D3D(既定)115.7–116.3MB = **+25MB が D3D / GPU ドライバ経路**。
**software 描画は代替にならない** — 同条件で 56.4–57.8fps と 60fps 予算を割る。

**exe に積んだバイト数はメモリではない**(2026-08-29 実測)。tree-sitter 37 文法の
静的テーブルで exe は 61.1MB あるが、**`ENTRIES` を空にして exe を 10.5MB にしても
`--no-open` の WorkingSet は 198.7–199.4 対 199.0–199.1 で動かない** — 触られない
読み取り専用ページは常駐しない。exe のサイズを見てメモリを語らないこと。

## アロケータと確保の個数(2026-08-11)

**バイト数より個数が効く帯がある。** Windows ヒープは確保 1 個ずつに管理領域を持ち、
管理領域とサイズ級の丸めは**計数アロケータには見えない** — 確保の個数を減らす変更
(`crate::Name` + `SmallVec<[Name; 1]>` で 305,213 個)は、計数側 −3.1MB が
WorkingSet では −12MB に出た。

**mimalloc は不採用**(実測)。同一コミットでの A/B:

| | 既定(Windows heap) | mimalloc | mimalloc + 即時 purge |
|---|---|---|---|
| WorkingSet | 288.8–296.3MB | 326.4–351.0MB | 289.4–299.5MB |
| private | 305.9–311.1MB | 388.3–397.3MB | 348.8–354.2MB |

遅延解放を切って WorkingSet でようやく並ぶが private は +43MB のままで、しかも
配布時に環境変数を撃つ前提になる。起動・操作応答にも差は出なかった。

## この記録の読み方

**この 4 つを固定しないと数字は再現しない**:

1. **スクロールベンチの有無**(上表のとおり 85MB 動く)。判定の 300MB は
   ベンチ込みの行に対して読む
2. **基準リポジトリの HEAD**。ハーネスは先頭行を選んで詳細と diff を出すので、
   `git fetch` でリポジトリが進むと**別のコミットの差分**を測ることになる
   (ファイル数も中身も変わる)
3. **どの GPU で描いたか**。この機材は GPU 2 枚 + DisplayLink 2 台で、上の
   「D3D 経路は +25MB」がアダプタごとに違う値になりうる
4. **窓が実物であること**(offscreen は表示性能にならない)

**過去の記録との差を回帰と読まないこと** — 上の 1〜4 のどれかが動いていれば、
同じコミットでも数十 MB 違う。回帰を疑う時は**その場で対照コミットを測り直す**
(`git checkout --detach <対照> && cargo xtask perf …`)。
