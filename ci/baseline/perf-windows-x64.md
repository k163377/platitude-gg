# 性能実測記録(Windows x64)

計測: 2026-08-12、commit 7f1e160。**§固定費の 4 行だけは 2026-08-11 のまま** —
リポジトリを開かない窓と Qt の床を測ったもので、以後の変更が届く場所ではない。

## 計測条件

- 対象: `JetBrains/kotlin` full clone — 227,321 commits、refs 53,728 本
  (タグ 45,901 / リモートブランチ 7,825)、commit-graph chain あり
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ)。自動化 env が設定ストアを空にするので既定値そのまま
- `cargo xtask perf --repo <path>` が条件を持つ — release ビルド、**実ウィンドウ**
  (offscreen ではメモリも fps も表示性能にならない)、ウォームキャッシュ、
  `PG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング最大値、
  デッドライン + kill ガード。1 回目は捨てて以降を採る
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / 1920x1080@100Hz / Windows 11 build 26200 /
  git 2.55.0
- 数値は 3 回連続実行の範囲(全数)。**出荷構成のビルド**(`memprobe` feature 無し)

## 判定

| 予算 | 実測 | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 782–1,025ms | ✅ |
| 操作応答 100ms | 36–73ms | ✅ |
| スクロール 60fps | 178.3–178.5fps | ✅ |
| メモリ 300MB | 252.6–266.1MB | ✅ |

- メモリはスクロールベンチ込み。ベンチ無し(起動 + 行選択 + 差分表示のみ)は
  241.9–254.8MB
- private bytes は 268.5–278.5MB。予算は WorkingSet に対して読む
- fps は `onFrameSwapped` の実数。**この 3 回は vsync が乗らなかった回**で、
  乗った回は表示の 100Hz で頭打ちになる(99.6–99.8fps)。予算 60fps に対しては
  どちらも余るので、どちらが出たかは判定を動かさない
- 操作応答はハーネスが撃つ行選択→詳細の 1 点で、タグ込み walk が裏で走っている
  最中に当たる。**この 1 点はプロセス 1 個ぶん**(`git show` に書式とファイル一覧を
  まとめて訊く)で、Windows のプロセス生成 18ms がその半分近くを占める
- **数字が取れなかった run は報告されず落ちる**(`xtask perf` の `missing`)。
  以前は `-` が出て報告から行ごと消えたので、**何も測れていない run が
  よく測れた run と同じ顔をした** — アプリのログが色を持ち始めて
  `key=value` が全て検索不能になっていたのを、この予算を測り直すまで
  誰も気付かなかった(`platitude_gg::init_tracing` は色を付けない)

## 内訳

`cargo xtask perf --breakdown`(`memprobe` feature = 計数グローバルアロケータ)。
Qt は C++ の `operator new` を通り Rust の `GlobalAlloc` を通らないので、
**この境界が「アプリのデータ」と「その下の道具」を正確に分ける**。

| 区分 | 実測 |
|---|---|
| 固定費(空リポジトリ 1 コミットで開いた窓) | 128.4–130.1MB |
| Rust ヒープ(常駐) | 32.8MB |
| Rust ヒープ(ピーク) | 54.3MB |
| 生存確保の個数 | 94,634 |

**常駐とピークと個数はサンプルで、名前の付いた分より揺れる** — 報告はポーリングの
どこに当たったかで変わり、refs パイプラインが一時的に抱えている分がそのまま乗る。
**変化を読むなら下の名前付きの表**(こちらは同じ refs 数なら再現する)。

**予算 300MB の 43% はリポジトリを開く前に埋まっている**(その時点の Rust ヒープは
1.2MB = 中身はほぼ全て Qt と QML 側)。その 130MB の割れ方:

| 積み上げ | WorkingSet | 差分の中身 |
|---|---|---|
| Qt の `qml.exe` + 素の `Window` | 75.5MB | Qt Quick + D3D + GPU ドライバの床 |
| 同 + Controls(Fusion)+ `ListView` | 83.9MB | +8.4 = このアプリも使う部品 |
| platitude-gg、リポジトリ無し | 115.7–116.3MB | **+32 = 自前 QML シェルとアプリ本体** |
| platitude-gg、空リポジトリ | 131.3–132.4MB | **+15.6 = ページの実体化** |

描画経路の寄与は同条件の差で取る: リポジトリ無しが software 描画 90.9–91.3MB に対し
D3D(既定)115.7–116.3MB = **+25MB が D3D / GPU ドライバ経路**(空リポジトリでは
102.2–103.5 対 131.3–132.4 で +29MB)。**software 描画は代替にならない** — 同条件で
56.4–57.8fps と 60fps 予算を割る。

積んでいるものの重複や過剰ではない: exe 5.3MB / 埋め込み QML 1.05MB(60 コンポーネント、
qmldir・`include_bytes_qml!` とも過不足なし、未参照ゼロ)。48MB は**積んだバイト数では
なく、QML をコンパイルして実体化した後のランタイム構造**。

Rust ヒープ 32.8MB のうち名前の付いた 19.4MB:

| 保持者 | bytes | 要素数 |
|---|---|---|
| `session::LabelIndex` | 5,492,017 | 47,715 |
| `RefsSnapshot` | 4,991,575 | 53,724 |
| `session::RemoteTagIndex` | 4,850,008 | 45,923 |
| `GraphModel` の行 | 2,134,799 | 2,001 |
| 送信済み行(背景差分用) | 1,645,183 | 2,001 |
| walk のビルダ | 172,440 | 2,028 |
| 適用済みの差分 | 87,173 | 589 |
| サイドバー 6 セクション合計 | 1,476 | 53,732 |

残り 13.4MB は名前が付いていない。サイズ級別の内訳から、その大半は refs パイプラインが
**ポーリング中に一時的に抱えるもの**(`git for-each-ref` の出力 6.9MB と、そこから
起こした `Vec<RefEntry>`)。報告はサンプルなので、常駐とピークの差はその時点で
どこまで抱えていたかで決まる。

**refs の本数がメモリを決める。** 上表の上位 3 件はすべて refs の本数に比例し、
合計 15.3MB — 名前の付いた分の 79%。commits ではなく refs が支配的。
**サイドバーはもうこの表に載らない** — 6 セクション合わせて 1,476 バイトで、
53,732 行の中身は上の `RefsSnapshot` を読んでいる(規約は rules-refs/app-ui.md)。

## アロケータと確保の個数

**バイト数より個数が効く帯がある。** 常駐 32.8MB は 94,634 個の確保に散っており、
Windows ヒープはその 1 個ずつに管理領域を持つ。`crate::Name`(inline 24 バイト)と
`SmallVec<[Name; 1]>` が **305,213 個**を消した効果は、計数側の −3.1MB に対し
WorkingSet では −12MB に出る — 差が管理領域とサイズ級の丸めで、**計数アロケータには
見えない側**。個数の側で最も効くのは**行を持たないこと**で、45,901 本のタグを
`NavItem` で持っていた時はこの 1 セクションだけで 10 万個級の確保だった。

**mimalloc は不採用**(実測)。同一コミットでの A/B:

| | 既定(Windows heap) | mimalloc | mimalloc + 即時 purge |
|---|---|---|---|
| WorkingSet | 288.8–296.3MB | 326.4–351.0MB | 289.4–299.5MB |
| private | 305.9–311.1MB | 388.3–397.3MB | 348.8–354.2MB |

遅延解放を切って WorkingSet でようやく並ぶが private は +43MB のままで、しかも
配布時に環境変数を撃つ前提になる。起動・操作応答にも差は出なかった
(この表は `crate::Name` 導入前の基準に対するもの)。

## 余白

WorkingSet の最悪回は 266.1MB で、予算まで 33.9MB。**2 タブ目は予算を割る** —
上表のうちセッションが持つ分(refs 3 件で 15.3MB)はタブごとに増え、固定費
128–130MB は増えないので、1 タブあたり実質 +20MB 前後になる。

余白を広げる手はアプリ側のデータでは尽きており、次は床の側 —
[P5-確認事項.md](../../internal-docs/P5-確認事項.md) §14「Qt のカスタムビルド」に
止め時込みで積んである。
