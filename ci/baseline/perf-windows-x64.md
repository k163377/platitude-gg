# Phase 1 性能実測記録(Windows x64)

実装計画 §4 Done 条件の実測エビデンス。計測日: 2026-08-02。

- 対象: `JetBrains/kotlin` full clone(`git rev-list --count --all` = 225,818、
  refs 52,479 本 = タグ 44,710 / リモートブランチ 7,767)
- デフォルト表示: `HEAD --branches --remotes --tags` を `--max-count=2000` で
  ウィンドウ表示(GitKraken の初期値に合わせた製品判断。打ち切り時はフッターに表示)
- ビルド: `cargo build --release`、計測はウォームファイルキャッシュ
- 自動計測ハーネス: `PG_AUTO_OPEN` / `PG_AUTO_SCROLL` / `PG_AUTO_SELECT` /
  `PG_LOG=info`(数値は tracing 出力と WorkingSet サンプリング)

| 予算(要望.md) | 実測(デフォルト設定) | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | **673ms**(2段ストリーミングの高速パス) | ✅ |
| 操作応答 100ms | **88ms**(行選択→コミット詳細+ファイル一覧表示) | ✅ |
| スクロール 60fps | **99–100fps**(100Hz環境、アバター描画込み) | ✅ |
| メモリ 300MB(提案値) | **peak 222MB / 静定 220MB** | ✅ |

補足:

- **タグ表示は 2 段ストリーミング**で予算と両立: kotlin の 44,710 タグは
  `--topo-order` のフロンティア初期化を数秒化する(git first-byte 0.42s→2.1〜2.8s、
  commit-graph 完全生成済みでも同じ、`--max-count` では回避不能)ため、
  まずタグ無し walk を即描画(673ms)し、裏でタグ込み walk を再構築して
  約 3.8s 時点で一括差し替える(モデル reset+一括挿入を単一 drain で処理する
  ためフリッカーなし。選択行は oid で復元)。ヘッダの「⚑ Tags」トグルで
  タグ除外(=単段・高速のみ)にもできる
- **メモリはウィンドウ制限で解決**。内訳: Qt ランタイム+QML+ペイン一式の
  ベースライン ≈160MB、グラフ行データ ≈73MB/10万行(制限前の全 224k 行表示では
  peak 324MB だった)。2,000 行ウィンドウでは行データは誤差レベルになり、
  残りはほぼ Qt 固定費
- 全ウィンドウ(2,000 行)のストリーム完了は first chunk +0.2s。スクロール
  ベンチは 3,000 行 /12s の自動スクロールでの実測
- コールドキャッシュ初回はディスク I/O が支配的で上記より数秒遅い(タグONの
  全履歴時代の実測で 7.8s)。予算は「快適に扱える」趣旨のウォーム前提で判定した
