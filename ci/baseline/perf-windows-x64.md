## 計測条件

**判定 4 行を撃ち直す 2 行**:

```
cargo xtask corpus
PGG_ALLOW_GUI=1 cargo xtask perf --at <測る commit> --repo <上の 1 行が印刷した path> --runs 5
```

段ごとの表は 2 行目にフラグを足しただけで、**撃ち方は各節が持つ**。`--at` は計測台 rig
(roster 外の worktree)に名指しの commit を建てて測る — 席の編集は測られず、同じ commit の
2 度目はビルド無し(rules-refs/app-ui.md「計測は計測台(rig)で撃つ」)。この記録を撃ち直すなら
`--at` は冒頭の 2 つの木を持つ commit で、**全節が同じ commit**(feature 集合が変わる
§Rust ヒープ と §出荷ビルドとの差 だけ棚にもう 1 本ビルドが載る)。既定で最初に較正 run
(`run-font-walk`)が走り、report の `font walk` / `net` 行になる(rules-refs/app-ui.md
「perf の判定行は net で読む」)。

- 対象: **`cargo xtask corpus` が生成する合成リポジトリ**。**corpus token
  `23da9ebd03a156a5937d265abb0a353fc60e7b75`**(`show-ref` 全体の blob id)—
  HEAD `e512482ebce1b16fd3a7908a4000c229896fcf7e`、コミット 200,000、
  refs 50,004 本(タグ 42,800 / リモートブランチ 7,200 / `main` / 追跡 `main` /
  リモート 2 本の `HEAD`)、追跡ファイル 109,652、pack 5 本 + multi-pack-index、
  commit-graph chain あり、作業ツリーは clean。
  **生成器が固定なので、消して作り直しても同じ token が出る**
- **なぜ clone ではなく生成か**: 人が使っているリポジトリの clone は計測の裏で
  fetch され、`HEAD` を動かさずに描く行・refs の本数・diff を測るコミットが
  全部変わる。**この記録の前提は「リポジトリが止まっていること」**で、それを
  clone で保証する手段は無い(§この記録の読み方 2)
- **形は `JetBrains/kotlin` の実測に寄せてある**が、**寄っていない軸がある** —
  何が寄っていて何が寄っていないかは §コーパスと kotlin の距離(そこが正本)
- ハーネスが選ぶ行(`--selection first` = ref から届く最新)は HEAD と同じ
  `e512482e`(**76 ファイル変更**)。既定で開く diff はその 1 件目
  `…/checker_codegen38182.java`(**34,059 バイト**の中の **+47 −3**)。
  **操作応答と diff frame の数字はこのコミットのもの**で、**大きいファイルの中の
  小さい diff = 文法ハイライトの最も高い経路**(ファイル全体をパースして全行に
  span を張り、変わった数行を塗る)。`--file` で名指しすれば同じコミットの
  7,070,205 バイトの `.kt` も開ける — `preview::SOURCE_BYTE_CAP`(4MB)の外側
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ、2,001 行)
- **窓は `\\.\DISPLAY2`(180Hz、1920x1080、原点 (0,0))に 1440x900 で固定**。
  run ごとの `PGG_CONFIG_DIR` に `state.toml` を書いて渡す。**画面を固定しないと
  fps はどの画面に出たかで決まる** — この機材は 100 / 180 / 100Hz の 3 画面。
  **窓の復元はカーソルのある画面を基準に出る**ので、撃つ前にカーソルをその画面に置く
  (P3-確認事項 §app)。**`--screen '\\.\DISPLAY2'` は Git Bash から渡すと
  引数変換でバックスラッシュが 1 本落ちて `\.\DISPLAY2` になり、perf が名前で refuse する**
  — この機材では DISPLAY2 が primary なので、名指ししなければ既定でそこに乗る
  (report の `screen` 行がどの画面だったかを毎回言う)
- ビルドは `cargo build --release --features automation`(ハーネス込み)
- **実ウィンドウ**(offscreen ではメモリも fps も表示性能にならない)、ウォーム
  キャッシュ、`PGG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング
  最大値、`perf_done` による因果完了、デッドライン + kill ガード。1 回目は捨てて以降を採る
- **機械の状態も測って、駄目な run は落として撮り直す**(`--retries` 既定 3): ロック /
  セキュアデスクトップ(連続 3 tick から)/ 最小化 / 落ち着いた後の画面移動 / 画面 Hz に
  対して配信フレームが半分未満 / 対象以外が機械の 35% 超。窓が被さられた時は上げ直し、
  それでもベンチが 30 秒動かなければ run ごと落とす(被さりが 2 度続けば諦める)。
  捨て run は同じ exe・corpus を数分内に温めた invocation の直後なら省く(`perf::warmth`)。
  **run の前に別プロセスのビルドが走っていれば、終わるまで機械を止めて待つ** — この記録は
  10 invocation とも待ちゼロで撃てている(他席が同時に動いていない時に撮ったもの)
- **gate は 4 つとも閉じたまま通る**(`--allow-noisy` を足していない)。`--allow-noisy` が
  開けるのは **CPU の 3 つの閾(run 前 / 平均 / 峰)と配信フレームの床の 4 つだけ**で、
  ロック・最小化・画面移動・画面の取り違えは元から閉じている。**対象プロセスの CPU は
  job object で子孫まで込み**(`perf::sampler`。報告の machine 行が
  `not this process or its children` と言い、`memory.csv` の `children_counted` が
  全 tick で 1)なので、アプリがリポジトリを開くたびに撃つ
  `git status --porcelain=v2 -z --branch -uall` — 追跡 109,652 / 無視 78,000 を
  preload-index の並列 lstat で歩き、**1 本 2.2–2.4 CPU 秒を wall 200ms に詰める
  = 約 11 コア幅** — は「対象以外」に数えられない。**10 invocation の峰は 14.6–54.7% で
  閾 75% の内側**、平均のほうは対象以外 5.1–25.9% で閾 35% の内側
- **短い段ほど対象以外の平均は高く出る**(開くだけ・行選択の段 9.7–25.9% に対し判定
  7.8–11.5%)が、それは同じ git の仕事が 2 秒の run と 14 秒の run で割られるだけで、
  機械が忙しいのではない — **段どうしで機械の列を並べない**
- **画面は invocation の間ずっと起こしておく** — ビルドと run の間の待ちも含めて。
  `ES_DISPLAY_REQUIRED` は run の間だけでは足りない(**既に暗い画面は起こせない**ので、
  2 本目以降の run が毎回暗い画面から始まる)。起こすのは入力なので 0 ピクセルの
  マウス移動を注入する。**その結果 `away_ms` は「人が居たか」を答えない** —
  答えるのは「起こす側が動いているか」だけ(`perf::sampler::Awake`)
- **表示に依らず撮るなら `--software`**(`PGG_ALLOW_GUI=1 cargo xtask perf --software --at <commit>
  --repo <corpus>`)。表示が点いていても消えていても、途中で人が付け消ししても同じ run で、
  待ちも打ち切りも撮り直しも無い(表示の状態は `memory.csv` の `display_off` 列と report の
  `display` 行に証跡として残るだけ)。入力を注入せず、窓を前面へ上げ直さない。
  **表示が消えている間 D3D は 1 枚も present しない**(実窓・実フォント DB のまま 80 秒待っても
  `perf_graph_frame` が出ず、ドライバは最初の段で止まる)ので software scene graph
  (`QT_QUICK_BACKEND=software`)で描く。**読めるのはメモリだけ**で、それも D3D の床(§Qt の床)を
  持たない別の量 — §判定 には使わず、同じ commit の D3D 値と並べて読む。fps / startup /
  details / diff の行は表示経路の値ではない(report が注記する)。実測は §表示に依らない計測
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / Windows 11 build 26200 / git 2.55.0 /
  Qt 6.10.3。GPU 3 系統のうち Qt が掴んだのは **Adapter 0 `NVIDIA GeForce RTX 3070`**
  (D3D11、`Animation Driver: using vsync: 5.56 ms`)。**kept run は全部同じ
  グラフィックス構成でなければ通らない**(違ったら報告ごと落ちる)
- 数値は **min–中央–max**(kept run の全数)。**判定は max、比較は中央**を読む —
  範囲は run を増やすほど広がるだけなので、範囲だけでは何も言えない
- 撃った時の機械: 10 invocation を通して全体 5.5–40.3% busy、うち対象プロセス以外 5.1–25.9%
  (最悪の 1 tick で 14.6–54.7%)。
  **静かな機械ではない**(ブラウザ・IDE・コンテナランタイム・他席のセッションが動いている
  24 スレッド機)

## 判定

`b5340916` の座り(較正 run + 捨て 1 + 5 run。証跡は席の
`target/perf/1789032529760863200/`):

| 予算 | 実測(5 run) | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 1093–1157–1205ms | ✅ |
| 操作応答 100ms | **78.4–85.0–88.8ms** | ✅ **max で 11.2ms 余す**(5 run とも内側 — ただし縁。下の注) |
| スクロール 60fps | 177.6–177.7–178.0fps | ✅ |
| メモリ 300MB | gross 300.7–302.6–303.1MB / **net 257.4–259.2–259.8MB** | ✅ **net で読む**(gross は max で 3.1MB 超過。規則は rules-refs/app-ui.md) |

- **較正 run が量った歩きは WorkingSet +43.4MB / private +18.5MB**(208.3 → 251.7)で、
  それを引いた net は 5 run とも予算の内側。**どの段で出るかは §メモリの段**(出るのは
  スクロールの段)。**何で出るかは §常駐の内訳**(一族に無いグリフ 1 つでフォント DB を
  全 family populate する代金)。8 秒置いた settled は §峰と settled
- **操作応答は 5 run とも内側だが、縁であることは変わらない**。行選択→詳細が描かれるまでの
  1 点(`perf_details_frame`)を run ごとに往復(`details request round trip`)と対にすると、
  51→78.4 / 47→81.0 / 52→88.8 / 48→85.0 / 49→86.5ms。**データだけの往復(`git show`
  1 プロセス)は 47–49–52ms に収まり、描く側は 27–38ms**。**縁の正体は往復の揺れ** —
  往復はプロセス生成が主で git 自身の仕事は 1ms 級なので、跳ねた 1 本が出れば
  max は 100ms を越えうる(判定は max で読む規則)
- diff を開くのは別の 1 点で **101.8–105.8–114.8ms**。予算表の「操作応答」はこの点では
  ないが、**人が待つ長さとしては最長**なので併記する
- **4 行ともハーネス込みのビルドで撮っている。** 出荷ビルドで撮れるのはメモリと
  グラフまでの時間だけで、**fps と操作応答は出荷ビルドでは定義できない**(駆動する口も
  フレームを報告する口も `automation` feature の中)。積んだ分の代金は §出荷ビルドとの差
- 起動の行が読んでいるのは `startup`(**目に見えるグラフのフレームが出るまで**)。
  stream が終わるまで(`to a graph` = 出荷ビルドも答える唯一の点)は 1111–1174–1212ms、
  うち walk は 120–127–147ms
- private bytes は 278.3–279.9–282.5MB。予算は WorkingSet に対して読む
- fps は画面の **98.6–98.7–98.9%**。予算 60fps に対して余る。**16.7ms を跨いだフレームは
  1–1–2 本**、p95 6.2–6.4ms / p99 6.8–7.4ms。frame max は 129.4–148.7–151.1ms で、
  跨いだその 1 本がこれ(100ms 級)。較正 run の歩き(`perf_font_walk_begin` → `done`)は
  この座りで 775ms(その日最初の invocation)、**温まった以降の 8 本は 116–155ms で
  この 1 本と同じ幅** — **同じ事象である**(§旧フォント backend との A/B: 歩きを払わない
  backend では 16.7ms を跨ぐフレームが 1 本も出ない)
- 撃った時の機械: 5 run とも全体 12.4–14.6–16.3% busy、対象以外 7.8–9.9–11.5%
  (峰 20.7–39.3%)、窓は全 tick で最前面
- **判定対象は合成コーパス** — §コーパスと kotlin の距離 の各profileの範囲に限る。
  diffのp90・最大には3割以上の不足があり、別の軸の重さでは補えない
- 数字が取れなかった run は `missing` として報告ごと落ちる(`xtask perf`)。
  前提はログが無色であること — 色コードが乗ると `key=value` が検索不能になる
  (`platitude_gg::init_tracing` は色を付けない)

## 操作 1 点の内訳 — 読み / 適用 / 描画(2026-09-15)

**別の座り** — 席 c の木(`b06eec32`)、**`corpus --copies 8` の作業コピーが立ったコーパス**
(token `fb3d090c4261f4500bd61c8db7389485d515feab`、refs 50,012)に `--allow-noisy` で撃った
3 run。開幕の巡回がグラフと機械を取り合う条件なので**絶対値は §判定 の行と並べない** —

入り、変更通知も出た = `details rows` / `diff rows`)、そしてハーネスが見たフレーム
(`details frame` / `diff frame`)。**run ごとに**(ms、3 run とも同じ invocation):

  142.5–153.1–156.6ms で、差(約 43–62ms)はこの表の適用 + 描画と合う

  適用の 30–50ms はモデルを組む側の代金

  1 本ごとの起動と実行は静かな机で撮った
  [git-slots-windows-x64.md](git-slots-windows-x64.md) §操作 1 回の内訳 が正で、長い鎖も同じ
  2 本(`rev-parse` → `cat-file`)—— [P3-確認事項.md](../../internal-docs/P3-確認事項.md) §性能 の
  「commit の diff は詳細一覧が status を知っているので probe 1 本が消える」はその鎖の頭のこと

## 表示に依らない計測(`--software`)

同じ `ea004354` を棚の exe のまま software scene graph で撮った 2 座り(2026-09-06。各 較正 run +
捨て 1 + **2 run**、`--settle-ms 4000`)。片方は表示が消えたまま(kept run の全 tick で off、
`--attribute` 付き)、もう片方は人が在席して表示が点いたまま(全 tick で on、窓は run ごとに前面
0% と 96%、撮り直し 0)。**software scene graph の値なので、§判定 の予算行とは並べない** — 読むのは
同じ commit の D3D 値との差と、2 座りが同じ帯に居ること:

| | D3D(§判定、5 run、点灯) | software、消灯(2 run) | software、点灯・在席(2 run) |
|---|---|---|---|
| WorkingSet gross | 293.4–300.3–302.6 | 257.2–261.8 | 256.3–259.4 |
| net(較正 run の歩きを引く) | 241.8–248.6–250.9 | 207.3–212.0 | 205.0–208.1 |
| font walk(較正 run) | +51.6 / private +23.0 | +49.8 / private +21.8 | +51.3 / private +22.9 |
| settled net(4 秒) | — | 200.3–205.0 | 198.8–203.2 |
| フォントの常駐(`--attribute`) | — | 31.3–33.0 MiB / 165–166 ファイル | — |
| scroll | 177.7–178.1 fps | 123.2–123.7 fps | 122.9–124.6 fps |
| details frame | 77.9–85.3–108.8 ms | 109.3–134.7 ms | 86.4–99.9 ms |

- **差は renderer の差**で、アプリの差ではない。software は D3D の床(§Qt の床の +25MB)も
  描いた行のグリフ texture も持たない — その分だけ軽く出る。**歩き(font walk)は同じ大きさ**で、
  フォント DB の populate は scene graph に依らない
- **表示の状態は値を動かさない**: 消灯の座りと点灯・在席の座りの gross は互いに 1〜3MB の中に居て、
  5 run で 7〜10MB 散る幅(§この記録の読み方 5)より小さい。scroll / details / diff の行は表示経路の
  値ではない(software raster の速さ) — 読まない
- **使い道は 2 つ**: 同じ renderer どうしで A/B を撮る(表示は付け消ししてよい —
  `--software --at <対照>` と `--software --at <変更>`)、歩きの帰属を撮る。**§判定 の撮り直しは
  できない** — 予算行は点灯した D3D の値で、それには表示が要る
- fps / startup / details / diff は software raster の速さで、report が全行に「not the display path」と
  付ける。frame gate(画面 Hz の半分)は software では効かせない

## メモリの段(各 5 run)

|---|---|---|

## この記録の読み方

**1 は機械が見る。2〜6 は人が揃える。**

1. **機械が見る**: 窓の出た画面と Hz / 掴んだ GPU アダプタと描画バックエンド /
   コーパスの token(run の前後で 2 回)。加えて run ごとに
   ロック・最小化・画面移動・配信フレーム・機械の忙しさを見て、駄目な run は
   撃ち直す。**同じ画面・同じアダプタ・同じコーパスでない数字は並ばない**。
   **忙しさも機械が見ている** — 閾は 1 つも開けていない(§計測条件 の「gate」)
2. **コーパス**。生成器が固定なので**もう勝手には動かない** — token が違う時に
   起きたことは 2 つに 1 つで、**生成器を変えた**(なら記録ごと取り直す)か、
   **`--repo` が生成物ではない別のリポジトリを指している**(なら指し直す)。
   `--corpus <token>` を足すと、違った時に measure ではなく refuse する。
   操作応答だけを跨いで比べたいなら `--select-oid` でコミットを名指しする
   (その oid が 2,000 行の窓に残っている間だけ効く)
3. **スクロールベンチの有無**。判定の 300MB はベンチ込みの行に対して読む。ベンチの代金は
   §メモリの段 の +64MB で、中身は §常駐の内訳 のとおり **見えた行が呼んだフォールバックの
   歩き**(フォント +30 とヒープ外 +34)— 窓に絵文字の行が無いリポジトリでは出ない
4. **座り(計測の機会)は残っている**。窓の位置とアダプタが固定された分だけ狭まったが、
   絶対値がゼロになったわけではない。**同じコミットの対照は同じ座りで撃つ**
   (`cargo xtask perf --at <対照> …` — 計測台 rig が建てるので席は動かない)
5. **採取数**。スクロールまで撃つと 1 つの invocation の中で WorkingSet は 2〜10MB 散る
   (判定 300.7–303.1、峰と settled の座り 297.8–308.1、Rust ヒープの座り 303.1–308.8)。
   **数 MB の差は 5 回採りでは分離できない**。中央値どうしで読み、範囲は「どこまで散ったか」
   としてだけ読む。窓だけの段は 1.9MB しか散らないので、そこは違う読み方でよい
6. **net の絶対値は、その invocation の較正 run が量った charge に依る**。同じ日・同じ
   commit の 9 invocation で charge は **WorkingSet +43.4〜+51.6MB** に散り(判定の座りは
   その最小)、net はその差だけ動く。**net で数 MB を比べるなら charge も並べて読む**
   (report の `font walk` 行)。**歩きの停止時間はもっと散る** — その日最初の invocation だけ
   775ms で、以降の 8 本は 116–155ms(フォントのファイルが OS のキャッシュに乗るまでの差)

7. **操作の裾は変種の差を読めない**。`--cases` の run が 1 ケースにつき採るのは 36 操作で、
   **その p95 と max は同じ設定を背中合わせに撃っても動く**(実測: 同一 exe・同一設定の
   2 invocation で diff の p95 が 346 → 589ms、p50 は 86.5 → 79.1ms =
   ci/baseline/git-slots-windows-x64.md §条件)。**変種を比べる時に読むのは p50 と
   「100ms を越えた操作の割合」**、裾を読みたいなら A/B(`--compare`、ABBA)で
   同じ条件を交互に撃って両変種のサンプルを束ねる

**機械の忙しさの閾(対象以外 35%)は設計上の選び方で、それが数字を動かすかどうかは
測っていない。** 上の実測は 5.1–25.9% の負荷の下で撮ったもので、静かな機械との
背中合わせは取っていない — 閾を動かす前にそれを撮る。

**過去の記録との差を回帰と読まないこと** — 上のどれかが動いていれば、同じコミットでも
数十 MB 違う。判定は**予算に対する絶対値**で、前回比ではない。
