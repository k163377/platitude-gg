# 性能実測記録(Windows x64)

計測: 2026-09-04。測ったのは `3443a122` の `crates/platitude-app` /
`crates/platitude-core`、ハーネスも同じ `3443a122` の `xtask`。**5 run の本計測**で、
段ごとの表も同じ座りの中で撮っている。
**§Qt の床 と §アロケータ の 2 表だけは 2026-08-11 のまま** — 道具の側を
測ったもので、アプリ側の変更が届く場所ではない。

**CPU の閾と配信フレームの床は開けて撮っている**(`--allow-noisy`)。**閉じたままでは
1 run も通らない**理由と、開けたことが何を汚していないかは §計測条件 の「峰の gate」。
ロック・最小化・画面移動・画面の取り違えの gate は閉じたままで、全 run が通っている。

## 計測条件

**判定 4 行を撃ち直す 2 行**:

```
cargo xtask corpus
PG_ALLOW_GUI=1 cargo xtask perf --repo <上の 1 行が印刷した path> --runs 5 --allow-noisy
```

段ごとの表は 2 行目にフラグを足しただけで、**撃ち方は各節が持つ**。

- 対象: **`cargo xtask corpus` が生成する合成リポジトリ**。**corpus token
  `23da9ebd03a156a5937d265abb0a353fc60e7b75`**(`show-ref` 全体の blob id)—
  HEAD `e512482ebce1b16fd3a7908a4000c229896fcf7e`、コミット 200,000、
  refs 50,004 本(タグ 42,800 / リモートブランチ 7,200 / `main` / 追跡 `main` /
  リモート 2 本の `HEAD`)、追跡ファイル 109,652、pack 5 本 + multi-pack-index、
  commit-graph chain あり、作業ツリーは clean。
  **生成器が固定なので、消して作り直しても同じ token が出る**
- **なぜ clone ではなく生成か**: 人が使っているリポジトリの clone は計測の裏で
  fetch され、`HEAD` を動かさずに描く行・refs の本数・diff を測るコミットが
  全部変わる。**この記録の前提は「リポジトリが止まっていること」**で、それを
  clone で保証する手段は無い(§この記録の読み方 2)
- **形は `JetBrains/kotlin` の実測に寄せてある**が、**寄っていない軸がある** —
  何が寄っていて何が寄っていないかは §コーパスと kotlin の距離(そこが正本)
- ハーネスが選ぶ行(`--selection first` = ref から届く最新)は HEAD と同じ
  `e512482e`(**76 ファイル変更**)。既定で開く diff はその 1 件目
  `…/checker_codegen38182.java`(**34,059 バイト**の中の **+47 −3**)。
  **操作応答と diff frame の数字はこのコミットのもの**で、**大きいファイルの中の
  小さい diff = 文法ハイライトの最も高い経路**(ファイル全体をパースして全行に
  span を張り、変わった数行を塗る)。`--file` で名指しすれば同じコミットの
  7,070,205 バイトの `.kt` も開ける — `preview::SOURCE_BYTE_CAP`(4MB)の外側
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ、2,001 行)
- **窓は `\\.\DISPLAY2`(180Hz、1920x1080、原点 (0,0))に 1440x900 で固定**。
  run ごとの `PG_CONFIG_DIR` に `state.toml` を書いて渡す。**画面を固定しないと
  fps はどの画面に出たかで決まる** — この機材は 100 / 180 / 100Hz の 3 画面
- ビルドは `cargo build --release --features automation`(ハーネス込み)
- **実ウィンドウ**(offscreen ではメモリも fps も表示性能にならない)、ウォーム
  キャッシュ、`PG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング
  最大値、`perf_done` による因果完了、デッドライン + kill ガード。1 回目は捨てて以降を採る
- **機械の状態も測って、駄目な run は落として撮り直す**(`--retries` 既定 3): ロック /
  セキュアデスクトップ(連続 3 tick から)/ 最小化 / 落ち着いた後の画面移動 / 画面 Hz に
  対して配信フレームが半分未満 / 対象以外が機械の 35% 超。窓が被さられた時は上げ直し、
  それでもベンチが 45 秒動かなければ run ごと落とす
- **峰の gate は開けてある**(`--allow-noisy`)。**閉じたままではこのコーパスで 1 run も
  通らない** — アプリはリポジトリを開くたびに
  `git status --porcelain=v2 -z --branch -uall` を撃ち、追跡 109,652 / 無視 78,000 を
  preload-index の並列 lstat で歩くこれが **1 本 2.2–2.4 CPU 秒を wall 200ms に詰める
  = 約 11 コア幅**。ハーネスが引いているのは**アプリ 1 プロセスの CPU だけ**なので、
  **子プロセスの git は「対象以外」に数えられて** 1 tick が 77–84% になる(閾 75%)。
  スパイクの時刻は再試行の間で 100ms 以内に一致し、**リポジトリを開かない `--no-open` の
  段では峰が 11.3–19.0% に落ちる** — 出所はアプリ自身の git であって機械ではない。
  `--allow-noisy` が開けるのは **CPU の 3 つの閾(run 前 / 平均 / 峰)と配信フレームの
  床の 4 つだけ**で、ロック・最小化・画面移動・画面の取り違えは閉じたまま
- **開けたことが数字を汚していない根拠は平均のほう**: 判定 run の対象以外は 7.7–9.4%
  で、閉じている時の閾 35% の 1/4。**短い段ほどこの平均は高く出る**(開くだけ
  28.0–34.8%)が、それは同じ git の仕事が 2 秒の run と 14 秒の run で割られるだけで、
  機械が忙しいのではない — **段どうしで機械の列を並べない**
- **画面は invocation の間ずっと起こしておく** — ビルドと run の間の待ちも含めて。
  `ES_DISPLAY_REQUIRED` は run の間だけでは足りない(**既に暗い画面は起こせない**ので、
  2 本目以降の run が毎回暗い画面から始まる)。起こすのは入力なので 0 ピクセルの
  マウス移動を注入する。**その結果 `away_ms` は「人が居たか」を答えない** —
  答えるのは「起こす側が動いているか」だけ(`perf::sampler::Awake`)
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / Windows 11 build 26200 / git 2.55.0 /
  Qt 6.10.3。GPU 3 系統のうち Qt が掴んだのは **Adapter 0 `NVIDIA GeForce RTX 3070`**
  (D3D11、`Animation Driver: using vsync: 5.56 ms`)。**kept run は全部同じ
  グラフィックス構成でなければ通らない**(違ったら報告ごと落ちる)
- 数値は **min–中央–max**(kept run の全数)。**判定は max、比較は中央**を読む —
  範囲は run を増やすほど広がるだけなので、範囲だけでは何も言えない
- 撃った時の機械: 全体 9.7–11.5% busy、うち対象プロセス以外 7.7–9.4%
  (最悪の 1 tick で 73.6–82.8% — その峰は上の「峰の gate」でアプリ自身の git)。
  **静かな機械ではない**(ブラウザ・IDE・コンテナランタイムが開いている 24 スレッド機)

## 判定

| 予算 | 実測(5 run) | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 1108–1133–1156ms | ✅ |
| 操作応答 100ms | **87.9–105.6–129.5ms** | ❌ **max で 29.5ms 超過** |
| スクロール 60fps | 177.5–177.7–177.9fps | ✅ |
| メモリ 300MB | **353.8–376.2–390.9MB** | ❌ **min でも 53.8MB 超過** |

- **メモリは予算の外に丸ごと出ている** — 跨いでいるのではなく、最小の run が既に
  +53.8MB。**どの段で出るかは §メモリの段**(出るのは行を選んだところ)
- **操作応答は 1 組の外れではない**。行選択→詳細が描かれるまでの 1 点
  (`perf_details_frame`)を、この座りで 4 組 20 run 撮っていて、**4 組とも max が
  100ms を超える**(101.4 / 112.7 / 127.3 / 129.5ms)。中央は 91.5–105.6ms で予算の
  縁に載っている。**データだけの往復(`git show` 1 プロセス)は 53–58–87ms** なので、
  残りの 30–50ms は描く側
- diff を開くのは別の 1 点で **64.0–225.2–242.8ms**。予算表の「操作応答」はこの点
  ではないが、**人が待つ長さとしては最長**なので併記する
- **4 行ともハーネス込みのビルドで撮っている。** 出荷ビルドで撮れるのはメモリと
  グラフまでの時間だけで、**fps と操作応答は出荷ビルドでは定義できない**(駆動する口も
  フレームを報告する口も `automation` feature の中)。積んだ分の代金は §出荷ビルドとの差
- private bytes は 331.8–357.9–376.8MB。予算は WorkingSet に対して読む
- fps は画面の **98.6–98.7–98.8%**。予算 60fps に対して余る。**16.7ms を跨いだフレームは
  2,157 本中 1–1–2 本**、p95 6.6–6.8ms / p99 7.4–7.5ms。frame max は 122.9–147.8ms で、
  跨いだ 1–2 本のうち 1 本が 100ms 級
- **判定対象は合成コーパスへ移った** — §コーパスと kotlin の距離 に N は無く、
  コーパスが軽い軸は 3 つとも 1 割強に収まっている
- 数字が取れなかった run は `missing` として報告ごと落ちる(`xtask perf`)。
  前提はログが無色であること — 色コードが乗ると `key=value` が検索不能になる
  (`platitude_gg::init_tracing` は色を付けない)

## コーパスと kotlin の距離(2026-09-04 実測)

**両列とも同じ実装で撮る**:

```
cargo xtask corpus
cargo xtask corpus --against <kotlin の clone>
```

片方を別の数え方で撮った表は比較ではなく 2 つの定義なので、**手で数えた数字を
この表に足さない**。`--against` は読むだけで、相手には何も書かない。
R = 再現、A = 近い(コーパスが重い側)、L = コーパスが軽い。

| 設定済みリモート | 2 | 2 | R |

**`git status` の差は形ではなく clone の設定**。基準リポジトリは
`core.fsmonitor=true` で、**それが半秒を足している**(実測: 同じ warm な状態で
fsmonitor 有効 0.72–0.76s / 無効 0.28–0.29s)。歩く量そのものはコーパスの方が重い
(無視ファイル 78,000 対 278 — 基準リポジトリの clone はビルド出力を持っていない)。
**コーパスは fsmonitor を設定しない** — 設定すればデーモンのその日の調子を測ることに
なる。

**コーパスが軽い軸は 3 つだけ**(コミット数・refs 本数・開く diff)で、いずれも 1 割強。
残りは同等か重い側にある。

**リポジトリごとのメモリ差の出所は Rust ヒープではない**(実測)。§Rust ヒープ の表を
構造体レイアウトと実際の名前一覧から組み直すと実測を 0.15% で再現し、同じ模型を
この class の 2 つのリポジトリに当てた差は **−0.3MB** — 数十 MB の差の 1% 未満。
**差は C++ / Qt 側かホスト側**にあり、残件は
[P3-確認事項.md](../../internal-docs/P3-確認事項.md) §app。

## Qt の床(2026-08-11)

Qt そのものの値なので、アプリ側の変更では動かない:

| 積み上げ | WorkingSet | 差分の中身 |
|---|---|---|
| Qt の `qml.exe` + 素の `Window` | 75.5MB | Qt Quick + D3D + GPU ドライバの床 |
| 同 + Controls(Fusion)+ `ListView` | 83.9MB | +8.4 = このアプリも使う部品 |

描画経路の寄与は同条件の差で取った: リポジトリ無しが software 描画 90.9–91.3MB に
対し D3D(既定)115.7–116.3MB = **+25MB が D3D / GPU ドライバ経路**。
**software 描画は代替にならない** — 同条件で 56.4–57.8fps と 60fps 予算を割る。

**exe に積んだバイト数はメモリではない**(2026-08-29 実測)。tree-sitter 37 文法の
静的テーブルで exe は 61.1MB あるが、**`ENTRIES` を空にして exe を 10.5MB にしても
`--no-open` の WorkingSet は 198.7–199.4 対 199.0–199.1 で動かない** — 触られない
読み取り専用ページは常駐しない。exe のサイズを見てメモリを語らないこと。

## アロケータと確保の個数(2026-08-11)

**バイト数より個数が効く帯がある。** Windows ヒープは確保 1 個ずつに管理領域を持ち、
管理領域とサイズ級の丸めは**計数アロケータには見えない** — 確保の個数を減らす変更
(`crate::Name` + `SmallVec<[Name; 1]>` で 305,213 個)は、計数側 −3.1MB が
WorkingSet では −12MB に出た。

**mimalloc は不採用**(実測)。同一コミット・同一コーパスでの A/B:

| | 既定(Windows heap) | mimalloc | mimalloc + 即時 purge |
|---|---|---|---|
| WorkingSet | 288.8–296.3MB | 326.4–351.0MB | 289.4–299.5MB |
| private | 305.9–311.1MB | 388.3–397.3MB | 348.8–354.2MB |

遅延解放を切って WorkingSet でようやく並ぶが private は +43MB のままで、しかも
配布時に環境変数を撃つ前提になる。起動・操作応答にも差は出なかった。
**この 3 列は 1 回の座りの中の A/B なので、絶対値を上の判定表と並べない。**

## この記録の読み方

**1 は機械が見る。2〜5 は人が揃える。**

1. **機械が見る**: 窓の出た画面と Hz / 掴んだ GPU アダプタと描画バックエンド /
   コーパスの token(run の前後で 2 回)。加えて run ごとに
   ロック・最小化・画面移動・配信フレーム・機械の忙しさを見て、駄目な run は
   撃ち直す。**同じ画面・同じアダプタ・同じコーパスでない数字は並ばない**。
   **忙しさの列だけは今この記録では人が読む** — 閾を開けて撮っている
   (§計測条件 の「峰の gate」)
2. **コーパス**。生成器が固定なので**もう勝手には動かない** — token が違う時に
   起きたことは 2 つに 1 つで、**生成器を変えた**(なら記録ごと取り直す)か、
   **`--repo` が生成物ではない別のリポジトリを指している**(なら指し直す)。
   `--corpus <token>` を足すと、違った時に measure ではなく refuse する。
   操作応答だけを跨いで比べたいなら `--select-oid` でコミットを名指しする
   (その oid が 2,000 行の窓に残っている間だけ効く)
3. **スクロールベンチの有無**(kotlin では 38MB 以上動いた。合成コーパスでは
   **0 か +30MB 級かの二択** — §二峰)。判定の 300MB はベンチ込みの行に対して読む
4. **座り(計測の機会)は残っている**。窓の位置とアダプタが固定された分だけ狭まったが、
   絶対値がゼロになったわけではない。**同じコミットの対照は同じ座りで撃つ**
   (`git checkout --detach <対照> && cargo xtask perf …`)
5. **採取数**。**スクロールまで撃つと 1 つの invocation の中で WorkingSet は
   40MB 近く散り、しかも連続ではなく 2 つの塊に落ちる**(§二峰)。**10MB 級の差は
   5 回採りでも分離できない**。中央値どうしで読み、範囲は「どこまで散ったか」
   としてだけ読む。窓だけの段は 1.5MB しか散らないので、そこは違う読み方でよい

**機械の忙しさの閾(対象以外 35%)は設計上の選び方で、それが数字を動かすかどうかは
測っていない。** 上の実測は 7.7–9.4% の負荷の下で撮ったもので、静かな機械との
背中合わせは取っていない — 閾を動かす前にそれを撮る。

**過去の記録との差を回帰と読まないこと** — 上のどれかが動いていれば、同じコミットでも
数十 MB 違う。判定は**予算に対する絶対値**で、前回比ではない。
