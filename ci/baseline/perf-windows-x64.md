# 性能実測記録(Windows x64)

計測: 2026-08-30、commit c6128f19。**§Qt の床 と §アロケータ の 2 表だけは
2026-08-11 のまま** — 道具の側を測ったもので、アプリ側の変更が届く場所ではない。

## 計測条件

- 対象: `JetBrains/kotlin` full clone — HEAD `db1bc5055f24`、`rev-list --all`
  228,526、refs 54,272 本(タグ 46,377 / リモートブランチ 7,893)、commit-graph
  chain あり。**リモートタグは fetch 済みの定常状態**(`session::RemoteTagIndex`
  が建っている側)
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ)。自動化 env が設定ストアを空にするので既定値そのまま
- **この記録はハイライトの経路を測っていない。** ハーネスは先頭行を選ぶだけで、
  その HEAD の diff は非ソース 1 ファイル・10 行削除(`diff-lines` は 56 行)。
  文法もレクサーも実質走らないので、**ハイライト側の変更はここには出ない**。
  ハイライトのコストを問うなら、それを踏む diff を選ぶ別の計測が要る
- `cargo xtask perf --repo <path>` が条件を持つ — release ビルド、**実ウィンドウ**
  (offscreen ではメモリも fps も表示性能にならない)、ウォームキャッシュ、
  `PG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング最大値、
  デッドライン + kill ガード。1 回目は捨てて以降を採る
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / 1920x1080@100Hz / Windows 11 build 26200 /
  git 2.55.0。**GPU は 2 枚(AMD 内蔵 + NVIDIA RTX 3070)+ DisplayLink 2 台**で、
  Qt がどのアダプタを掴むかはこの条件が固定していない(§読み方)
- **どの表も 6 回連続実行の範囲(全数)**。**出荷構成のビルド**(`memprobe`
  feature 無し。Rust ヒープの表だけ `memprobe` 有り)。総 CPU 負荷 6% 台の
  静かな機械で撃った

## 判定

| 予算 | 実測 | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 1,022–1,121ms | ✅ |
| 操作応答 100ms | **46–155ms** | ❌ **裾が跨ぐ** |
| スクロール 60fps | 107.5–176.6fps | ✅ |
| メモリ 300MB | **406.0–417.8MB** | ❌ **約 110MB 超過** |

- private bytes は 384.9–396.7MB。予算は WorkingSet に対して読む
- **操作応答は最小が安定し、最大が散る** — 最小は 30〜46ms、最大は run をまたぐと
  84〜171ms に散り、**6 回採りでも 100ms を跨ぐ方が多い**。静かな機械(総 CPU 6%)
  でこれなので、機械の騒がしさでは説明が付かない。跨ぐのは裾だけなので体感は
  最小側に寄るが、**予算の判定としては赤**
- 操作応答はハーネスが撃つ行選択→詳細の 1 点で、タグ込み walk が裏で走っている
  最中に当たる。**この 1 点はプロセス 1 個ぶん**(`git show` に書式とファイル一覧を
  まとめて訊く)で、Windows のプロセス生成 18ms が最小側の半分近くを占める
- **fps は同じ invocation の中で 2 つの帯に割れる** — この run は 6 本のうち 2 本が
  107 帯、4 本が 176 帯。表示は 100Hz で、176 帯は vsync が乗っていない。
  **どちらの帯でもメモリは同水準**なので、**fps はメモリの帯の印にならない**。
  予算 60fps に対してはどちらも余る
- 数字が取れなかった run は `missing` として報告ごと落ちる(`xtask perf`)。
  前提はログが無色であること — 色コードが乗ると `key=value` が検索不能になる
  (`platitude_gg::init_tracing` は色を付けない)

## メモリの内訳: 何を足すといくら増えるか

同じビルドで、ハーネスに撃たせるものを 1 段ずつ足した WorkingSet:

| 何をした窓か | WorkingSet | 前段からの差 |
|---|---|---|
| リポジトリを開かない(`--no-open`) | 143.7–145.5MB | — |
| 基準リポジトリを開くだけ(`--no-select --no-scroll`) | 247.7–253.5MB | **+102〜110** |
| + ハーネスの行選択(`--no-scroll`) | **327.0–330.9MB** | +74〜83 |
| + スクロールベンチ | **406.0–417.8MB** | +75〜91 |

**予算はスクロールに入る前に割れている** — 行選択までで既に 327–331MB。ベンチは
その上へ更に 75〜91MB 積む。窓の床 145MB は Qt 側で、そこから先が全部アプリの分。

積んでいるのは Qt 側 — **run 全体を通しても Rust ヒープは常駐 56.5MB**(下表)で、
超過分はそもそも Rust のヒープに入らない大きさ。

**行を組んだ分は返ってこない**(8 秒アイドル、`--settle-ms 8000`):

| | 峰 | 8 秒アイドル後 |
|---|---|---|
| ベンチ込み | 410.0–420.3MB | 403.3–406.9MB |
| ベンチ無し | 346.9–352.7MB | 344.6–344.8MB |

どちらも 10MB 前後しか返さない。**「ベンチ無しなら返す」という対比は付かない** —
返らないのはベンチ固有ではなく、一度組んだ行の分がそのまま居座る形。

切り分けの実測(2026-08-29 の run。**下の絶対値はその座りのもの**、§読み方 3):

- **頭打ちする**: 同じ 1,961 行を 4 周(約 7,844 行ぶん)しても 1 周と同じ。
  決めるのは**一度見た行の数**で、走った距離ではない
- **デリゲートの作り直しではない**: 12 秒で作られたのは 57 個だけ
  (`reuseItems` は効いている)
- **行のデリゲートの中身**: 空デリゲートに差し替えると 223.2MB、本物は 370.9MB
  (同条件)。内訳は **subject の文字列 −74.0MB**(定数にした時)と
  **Canvas の描画 −42.6MB**(`onPaint` を no-op にした時)

つまり **2,000 行を組むのに要った C++ ヒープが高いまま返らない**形で、`gc()`・
`QSG_ATLAS_*` の縮小・`Canvas.Immediate` はいずれも動かさない。残る手は
[P3-確認事項.md](../../internal-docs/P3-確認事項.md) §app。

**リポジトリを開くだけで +102〜110MB** が次に大きい。この段では refs 5 万本の
索引(下表の上位 3 件で 14.8MB)と、グラフ 2,001 行の Qt 側の実体化が入る。

## Rust ヒープ

`cargo xtask perf --breakdown`(`memprobe` feature = 計数グローバルアロケータ。
Qt は C++ の `operator new` を通り `GlobalAlloc` に乗らない = この境界が
「アプリのデータ」と「その下の道具」を分ける)。

| 区分 | 実測 |
|---|---|
| 常駐(`rust_live`) | 56.5MB |
| ピーク(`rust_peak`) | 56.5MB |
| 名前の付いた分 | 17.2MB |
| 名前の無い分 | 39.3MB |

**常駐・ピークと「名前の無い分」はサンプルで揺れる** — ポーリングのどこに当たったかで、
refs パイプラインが一時的に抱えている分が乗る。**変化を読むなら下の名前付きの表**
(同じ refs 数なら再現する)。

| 保持者 | bytes | 要素数 |
|---|---|---|
| `session::LabelIndex` | 5,541,520 | 48,075 |
| `RefsSnapshot` | 5,040,879 | 54,268 |
| `session::RemoteTagIndex` | 4,897,392 | 46,378 |
| `GraphModel` の行 | 2,294,837 | 2,001 |
| walk のビルダ | 176,624 | 2,031 |
| 適用済みの差分 | 82,287 | 506 |
| 送信済み行の指紋(背景差分用) | 32,016 | 2,001 |
| diff の行 | 10,929 | 56 |
| サイドバー 8 セクション合計 | 1,916 | 54,278 |
| 詳細のファイル一覧 | 690 | 2 |
| 行末の印 | 40 | 0 |

**refs の本数がメモリを決める。** 上位 3 件はどれも refs の本数に比例し、
合計 14.8MB — 名前の付いた分の 86%。commits ではなく refs が支配的。
`session::RemoteTagIndex` は fetch の後にだけ建つので、fetch していない
リポジトリではこの 4.7MB が無い。**行数に比例するのは 2 件だけ**
(`GraphModel` の行 1,147 B/行 + walk のビルダ 87 B/行 = **1,234 B/行**)。
サイドバーは 8 セクション合計 1,916 バイト — 54,278 行の中身は `RefsSnapshot`
を読む(規約は rules-refs/app-ui.md)。

## Qt の床(2026-08-11)

Qt そのものの値なので、アプリ側の変更では動かない:

| 積み上げ | WorkingSet | 差分の中身 |
|---|---|---|
| Qt の `qml.exe` + 素の `Window` | 75.5MB | Qt Quick + D3D + GPU ドライバの床 |
| 同 + Controls(Fusion)+ `ListView` | 83.9MB | +8.4 = このアプリも使う部品 |

描画経路の寄与は同条件の差で取った: リポジトリ無しが software 描画 90.9–91.3MB に
対し D3D(既定)115.7–116.3MB = **+25MB が D3D / GPU ドライバ経路**。
**software 描画は代替にならない** — 同条件で 56.4–57.8fps と 60fps 予算を割る。

**exe に積んだバイト数はメモリではない**(2026-08-29 実測)。tree-sitter 37 文法の
静的テーブルで exe は 61.1MB あるが、**`ENTRIES` を空にして exe を 10.5MB にしても
`--no-open` の WorkingSet は 198.7–199.4 対 199.0–199.1 で動かない** — 触られない
読み取り専用ページは常駐しない。exe のサイズを見てメモリを語らないこと。
(この A/B の絶対値だけは上の内訳表の `--no-open` と揃わない。**読むのは差**で、
絶対値の水準は §読み方 3 の座り差の範囲。)

## アロケータと確保の個数(2026-08-11)

**バイト数より個数が効く帯がある。** Windows ヒープは確保 1 個ずつに管理領域を持ち、
管理領域とサイズ級の丸めは**計数アロケータには見えない** — 確保の個数を減らす変更
(`crate::Name` + `SmallVec<[Name; 1]>` で 305,213 個)は、計数側 −3.1MB が
WorkingSet では −12MB に出た。

**mimalloc は不採用**(実測)。同一コミットでの A/B:

| | 既定(Windows heap) | mimalloc | mimalloc + 即時 purge |
|---|---|---|---|
| WorkingSet | 288.8–296.3MB | 326.4–351.0MB | 289.4–299.5MB |
| private | 305.9–311.1MB | 388.3–397.3MB | 348.8–354.2MB |

遅延解放を切って WorkingSet でようやく並ぶが private は +43MB のままで、しかも
配布時に環境変数を撃つ前提になる。起動・操作応答にも差は出なかった。

## この記録の読み方

**この 5 つを固定しないと数字は再現しない**:

1. **スクロールベンチの有無**(上表のとおり 75MB 以上動く)。判定の 300MB は
   ベンチ込みの行に対して読む
2. **基準リポジトリの HEAD**。ハーネスは先頭行を選んで詳細と diff を出すので、
   `git fetch` でリポジトリが進むと**別のコミットの差分**を測ることになる
   (ファイル数も中身も変わる)。この記録は `db1bc5055f24`
3. **座り(計測の機会)**。この機材は GPU 2 枚 + DisplayLink 2 台で、Qt がどの
   アダプタを掴むかは固定していない。**同じコミットでも座りをまたぐと WorkingSet が
   350–420MB の幅で動く**。**fps はその印にならない** — 1 回の invocation の中で
   107 帯と 176 帯が混ざり、どちらでもメモリは同水準だった
4. **窓が実物であること**(offscreen は表示性能にならない)
5. **採取数**。1 つの invocation の中でも WorkingSet は 15MB 前後散る。**10MB 級の
   差は 6 回採りでも分離できない**

**過去の記録との差を回帰と読まないこと** — 上の 1〜5 のどれかが動いていれば、
同じコミットでも数十 MB 違う。回帰を疑う時は**同じ座りで対照コミットを測り直す**
(`git checkout --detach <対照> && cargo xtask perf …`)。3 の幅は座りをまたぐと
回帰を丸ごと隠せる大きさなので、**座りをまたいだ引き算はしない**。
