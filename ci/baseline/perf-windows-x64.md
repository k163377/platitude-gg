## 計測条件

**判定の行を撃ち直す 2 行**:

```
cargo xtask corpus
PGGDEV_ALLOW_GUI=1 cargo xtask perf --at <測る commit> --repo <上の 1 行が印刷した path> --runs 5
```

段ごとの表は 2 行目にフラグを足しただけで、**撃ち方は各節が持つ**。既定で最初に較正 run (`run-font-walk`)が走り、report
の `font walk` / `net` 行になる(internal-docs/性能.md 「perf の判定行は net で読む」)。

- 対象: **`cargo xtask corpus` が生成する合成リポジトリ**。**corpus token
  `23da9ebd03a156a5937d265abb0a353fc60e7b75`**(`show-ref` 全体の blob id)— HEAD
  `e512482ebce1b16fd3a7908a4000c229896fcf7e`、コミット 200,000、 refs 50,004 本(タグ 42,800 / リモートブランチ 7,200 /
  `main` / 追跡 `main` / リモート 2 本の `HEAD`)、追跡ファイル 109,652、pack 5 本 + multi-pack-index、 commit-graph
  chain あり、作業ツリーは clean
- **形は `JetBrains/kotlin` の実測に寄せてある**が、**寄っていない軸がある** — §コーパスと kotlin の距離(そこが正本)
- ハーネスが選ぶ行(`--selection first` = ref から届く最新)は HEAD と同じ `e512482e`(**76 ファイル変更**)。既定で開く
  diff はその 1 件目 `…/checker_codegen38182.java`(**34,059 バイト**の中の **+47 −3**)。
  **既定の run の操作の数字はこのコミットを、プロセスで最初に 1 回押した時のもの**で、
  **大きいファイルの中の小さい diff = 文法ハイライトの最も高い経路**
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` のウィンドウ、2,001 行)
- **窓は `\\.\DISPLAY2`(180Hz、1920x1080、原点 (0,0))に 1440x900 で固定**。**fps は出た画面で決まる** — この機材は 100 /
  180 / 100Hz の 3 画面。
  **窓の復元はカーソルのある画面を基準に出る**ので、撃つ前にカーソルをその画面に置く (P3-確認事項
  §app)。**`--screen '\\.\DISPLAY2'` は Git Bash から渡すと引数変換でバックスラッシュが 1 本落ちて `\.\DISPLAY2` にな
  り、perf が名前で refuse する** — この機材では DISPLAY2 が primary なので、名指ししなければ既定でそこに乗る
- ビルドは `cargo build --release --features automation`(ハーネス込み)
- **実ウィンドウ**(offscreen ではメモリも fps も表示性能にならない)、ウォームキャッシュ、WorkingSet と private bytes の
  sampler の刻み(100ms 寝て読む。実際の間隔は中央 113ms)の最大値。1 回目は捨てて以降を採る
- **gate は閉じたまま通る**(`--allow-noisy` を足していない — §操作 1 点の内訳 の 1 座りだけが例外)。撮り直しになった run
  は無い。**本体 checkout の窓が 1 枚立ったままの台**で撮っている
- **短い段ほど対象以外の平均は高く出る**が、それは同じ git の仕事が 2 秒の run と 14 秒の run で割られるだけ — **機械の
  列は段の中で読む**
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / Windows 11 build 26300 / git 2.55.0 / Qt 6.12.0(`--at` の commit が `.qt-version`
  で固定する版)。GPU 3 系統のうち Qt が掴んだのは **Adapter 0 `NVIDIA GeForce RTX 3070`**
  (D3D11、`Animation Driver: using vsync: 5.56 ms`)。**kept run は全部同じグラフィックス構成でなければ通らない**(違った
  ら報告ごと落ちる)
- 数値は **min–中央–max**(kept run の全数)。**判定は max、比較は中央**を読む
- 撃った時の機械: 「今」の判定の invocation で全体 9.6–10.2–13.0% busy、うち対象プロセス以外 4.8–5.7–8.2%(最悪の 1 tick
  で 15.3–47.1%)。「`168b42b99` の木」は 9.8–11.4–12.1% / 5.2–6.9–7.4% (同 20.2–47.0%)。**他の仕事が載る台**(ブラウ
  ザ・IDE・コンテナランタイム・他席のセッションが動いている 24 スレッド機)

## 操作 1 点の内訳 — 読み / 適用 / 描画

**main `168b42b99` を、`method` を言わない計測口で撮った値**(フレームは頼んだ後に最初に届いた 1 枚)。読むのは割り方で、
絶対値は §判定 と並べない。

**別の座り** — **`corpus --worktrees 8` の worktree が立ったコーパス** (token
`fb3d090c4261f4500bd61c8db7389485d515feab`、refs 50,012)に `--allow-noisy` で撃った 3 run(**この token は
`corpus --worktrees 8` では再現しない** —— 枝名が token に入るので、撃ち直す時はこの節を丸ごと取り直す)。開幕の巡回がグ
ラフと機械を取り合う条件なので、
**読むのは割り方**。

3 段に割る 3 つの印は、要求した時刻からの経過として全部 app が言う —— `… request round trip` (答えが drain された =
report の `details data` / `diff data`)、`… rows applied`(行がモデルに入り、変更通知も出た = `details rows` /
`diff rows`)、そしてハーネスが見たフレーム (`details frame` / `diff frame`)。

| | 読み(`data`) | モデルに入るまで(`rows`) | フレーム(`frame`) |
|---|---|---|---|
| 詳細 | 57–129–181 | 83–177–227 | 98.8–205.5–252.9 |
| diff | 61–111–220 | 97–155–283 | 110.2–168.4–301.4 |

機械は全体 32.6–42.4–98.0% busy、対象以外 16.5–27.1–84.1% —— 散りの大半は機械の側。
**同じ木・同じ計測口の静かな座り(5 run)の同じ 3 印**は 詳細 49–55–62 / 75–83–95 / 84.3–95.5–109.0、 diff 61–61–71 /
93–97–103 / 94.4–109.5–115.1。

- **読みは座りで大きく散る**(57–220ms)が、**適用(rows − data)は中央どうしで 詳細 28〜48ms・ diff 36〜44ms、描画(frame −
  rows)は 詳細 12〜29ms・diff 13ms** —— 待ちの本体は読みで、残り 2 段のうち**重いのはモデルの側**
- **一覧のデリゲートの作り直しが乗るのは「モデルに入ってからフレームまで」の小さい側** —— `reset()` を `dataChanged` に
  替える案(P3-確認事項 §性能)が狙えるのは小さい方の半分で、適用はモデルを組む側の代金
- **読みの中は全部プロセス**: `diff-tree -r -p` / `config --get-regexp core.autocrlf` /

  後の 1 本が返った 0.3ms 後に届く** —— **diff の組み立ては前の待ちの陰に隠れていて、測れる残りを持たない**。 1 本ごとの
  起動と実行は [git-slots-windows-x64.md](git-slots-windows-x64.md) §操作 1 回の内訳 が正で、長い鎖も同じ 2
  本(`rev-parse` → `cat-file`)

## この記録の読み方

1. **機械が見る**: 窓の出た画面と Hz / 掴んだ GPU アダプタと描画バックエンド / コーパスの token(run の前後で 2 回)/ 計測
   口の測り方(report の `method`)。
   **並ぶのは同じ画面・同じアダプタ・同じコーパス・同じ `method` の数字だけ** — `method` が違う 2 つで並ぶのはメモリと
   fps
2. **コーパス**。生成器が固定なので**もう勝手には動かない** — token が違う時に起きたことは 2 つに 1 つで、**生成器を変え
   た**(なら記録ごと取り直す)か、 **`--repo` が生成物ではない別のリポジトリを指している**(なら指し直す)。
   `--corpus <token>` を足すと、違った時に refuse する。既定の run の操作だけを跨いで比べたいなら `--select-oid` でコ
   ミットを名指しする (その oid が 2,000 行の窓に残っている間だけ効く)
3. **スクロールベンチの有無**。判定の 300MB はベンチ込みの行に対して読む。ベンチの代金は §メモリの段 の +65〜69MB で、そ
   の大半は **見えた行が呼んだフォールバックの歩き** (§常駐の内訳)— 窓に絵文字の行が無いリポジトリでは出ない
4. **座り(計測の機会)は残っている**。**同じコミットの対照は同じ座りで撃つ** (`cargo xtask perf --at <対照> …`)
5. **採取数**。スクロールまで撃つと 1 つの invocation の中で WorkingSet は 5〜12MB 散る。
   **数 MB の差は 5 回採りでは分離できない**。中央値どうしで読み、範囲は「どこまで散ったか」としてだけ読む。窓だけの段は
   1〜2MB しか散らない
6. **net の絶対値は、その invocation の較正 run が量った charge に依る**。この記録の invocation で charge は
   **WorkingSet +50.0〜+54.4MB** に散り、net はその差だけ動く。 **net で数 MB を比べるなら charge も並べて読む**(report
   の `font walk` 行)。**歩きの停止時間はもっと散る** — その日最初の invocation だけ 775ms で、以降は 116–155ms(フォント
   のファイルが OS のキャッシュに乗るまでの差)
7. **操作の完了は run が丸ごとずれる**(§ケース の 2 つの帯)。**変種を比べる時に読むのは report の `p50 by run` と「100ms
   を越えた操作の割合」**、裾を読みたいなら A/B(`--compare`、ABBA)で同じ条件を交互に撃って両変種のサンプルを束ねる。p95
   は 20 操作、p99 は 100 操作に満たない標本では出ない
8. **既定の run の操作は 1 run に 1 回**(プロセスで最初の選択と、その diff)。同じ操作の分布は §ケース の撃ち
   方(`--cases --cycles`)で取る
9. **途中で Hz を変えて戻した run は見分けられない** — 画面の Hz を読むのは run の前後 (`display-before.txt` /
   `display-after.txt`)だけで、前後 snapshot の一致では途中の変更を検出できない。計測中は画面の設定を触らない
