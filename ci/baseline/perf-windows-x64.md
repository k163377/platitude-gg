# 性能実測記録(Windows x64)

計測: 2026-09-02。測ったのは `14056101` の `crates/platitude-app` /
`crates/platitude-core`、**ハーネスは `14056101` の `xtask`**(下の §計測条件 が
説明するハーネスはそれより新しい — 条件の説明は現在の道具のもので、**数字は撮った
時の道具のもの**。取り直せば両方が揃う)。
**§Qt の床 と §アロケータ の 2 表だけは 2026-08-11 のまま** — 道具の側を
測ったもので、アプリ側の変更が届く場所ではない。

## 計測条件

**この記録の全部を撃ち直す 1 行**:

```
PG_ALLOW_GUI=1 cargo xtask perf --repo <kotlin> --runs 5
```

`perf` は見つけた corpus token を印刷する。**下の token と違えば、この記録の
数字とは比較できない** — その時に読めるのはそれだけで、直せる不具合ではない
(§この記録の読み方 2)。measure ではなく refuse させたい時に
`--corpus <token>` を足す。**この clone は fetch で動くので、token を
記録へ焼いた 1 行はいずれ必ず止まる**。

- 対象: `JetBrains/kotlin` full clone。**corpus token
  `0093cd89a856e0b170a2c17507e73012638dae98`**(`show-ref` 全体の blob id)—
  HEAD `db1bc5055f24`、`rev-list --all` 227,051、refs 54,286 本(タグ 46,463 /
  リモートブランチ 7,821)、作業ツリーに未コミット 1 件、commit-graph chain あり。
  リモートタグは fetch 済み(**ただし `session::RemoteTagIndex` はこの run では
  建っていない** — §Rust ヒープ)。**`HEAD` は止まったまま中身が動く**ので、
  比較する時は token を突き合わせる(§この記録の読み方 2)
- ハーネスが選ぶ行(`--selection first` = ref から届く最新):
  `9f27f51dd5349129c08e300c1957a9085c313853`(75 ファイル変更)。開く diff は
  `…/KaFirScopeProvider.kt`(+47 / −3)。**操作応答と diff frame の数字はこの
  コミットのもの**で、`.kt` なので**文法ハイライトの経路を踏んでいる**
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ、2,001 行)
- **窓は `\\.\DISPLAY2`(180Hz、1920x1080、原点 (0,0))に 1440x900 で固定**。
  run ごとの `PG_CONFIG_DIR` に `state.toml` を書いて渡す。**画面を固定しないと
  fps はどの画面に出たかで決まる** — この機材は 100 / 180 / 100Hz の 3 画面
- ビルドは `cargo build --release --features automation`(ハーネス込み)。
  **出荷ビルドとの差は §出荷ビルド**で別に測ってある。Rust ヒープの表だけ
  `--breakdown` = `memprobe` 有り
- **実ウィンドウ**(offscreen ではメモリも fps も表示性能にならない)、ウォーム
  キャッシュ、`PG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング
  最大値、`perf_done` による因果完了、デッドライン + kill ガード。1 回目は捨てて以降を採る
- **機械の状態も測って、駄目な run は落として撮り直す**(`--retries` 既定 3): ロック /
  セキュアデスクトップ(連続 3 tick から)/ 最小化 / 落ち着いた後の画面移動 / 画面 Hz に
  対して配信フレームが半分未満 / 対象以外が機械の 35% 超。窓が被さられた時は上げ直し、
  それでもベンチが 45 秒動かなければ run ごと落とす
- **画面は invocation の間ずっと起こしておく** — ビルドと run の間の待ちも含めて。
  `ES_DISPLAY_REQUIRED` は run の間だけでは足りない(**既に暗い画面は起こせない**ので、
  2 本目以降の run が毎回暗い画面から始まる)。起こすのは入力なので 0 ピクセルの
  マウス移動を注入する。**その結果 `away_ms` は「人が居たか」を答えない** —
  答えるのは「起こす側が動いているか」だけ(`perf::sampler::Awake`)
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / Windows 11 build 26200 / git 2.55.0 /
  Qt 6.10.3。GPU 3 系統のうち Qt が掴んだのは **Adapter 0 `NVIDIA GeForce RTX 3070`**
  (D3D11、`Animation Driver: using vsync: 5.56 ms`)。**kept run は全部同じ
  グラフィックス構成でなければ通らない**(違ったら報告ごと落ちる)
- 数値は **min–中央–max**(kept run の全数)。**判定は max、比較は中央**を読む —
  範囲は run を増やすほど広がるだけなので、範囲だけでは何も言えない
- 撃った時の機械: 全体 10.5–15.5% busy、うち対象プロセス以外 9.2–13.2%
  (最悪の 1 tick で 29.7–55.4%)。**静かな機械ではない**(ブラウザ・IDE・
  コンテナランタイムが開いている 24 スレッド機)

## 判定

| 予算 | 実測 | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 1,120–1,156–1,191ms | ✅ |
| 操作応答 100ms | 57.3–64.9–66.8ms | ✅ |
| スクロール 60fps | 176.9–177.0–177.2fps | ✅ |
| メモリ 300MB | **379.5–381.0–387.5MB** | ❌ **約 80–88MB 超過** |

- **4 行ともハーネス込みのビルドで撮っている。** 出荷ビルドで撮れるのはメモリと
  グラフまでの時間だけで、**fps と操作応答は出荷ビルドでは定義できない**(駆動する口も
  フレームを報告する口も `automation` feature の中)。メモリ行が出荷ビルドでどうなるかは
  §出荷ビルド の背中合わせを読む
- private bytes は 356.7–360.9–368.0MB。予算は WorkingSet に対して読む
- 操作応答は行選択→詳細が描かれるまでの 1 点(`perf_details_frame`)。**5 run 全部が
  予算内**で、データだけの往復(`git show` 1 プロセス)は 24–25–26ms
- diff を開くのは別の 1 点で **220.1–227.3–249.2ms**。予算表の「操作応答」はこの点
  ではないが、**人が待つ長さとしては最長**なので併記する
- fps は画面の **98.3–98.5%**。予算 60fps に対して余る。**16.7ms を跨いだフレームは
  2,150 本中 2–3 本**、p95 7.0–7.2ms / p99 7.7–8.9ms。ただし **1 run に 1 回、
  125–155ms の 1 フレーム**が出る(`frame_max_ms`。位置を問うなら
  `--trace-frames` の run が要る)
- 数字が取れなかった run は `missing` として報告ごと落ちる(`xtask perf`)。
  前提はログが無色であること — 色コードが乗ると `key=value` が検索不能になる
  (`platitude_gg::init_tracing` は色を付けない)

## メモリの内訳: 何を足すといくら増えるか

同じビルドで、ハーネスに撃たせるものを 1 段ずつ足した WorkingSet:

| 何をした窓か | WorkingSet | 前段からの差 |
|---|---|---|
| リポジトリを開かない(`--no-open`) | 151.3–151.6–151.7MB | — |
| 基準リポジトリを開くだけ(`--no-select --no-scroll`) | 252.8–255.2–256.9MB | **+101〜105** |
| + 行選択と diff(`--no-scroll`) | 340.1–347.5–349.2MB | +87〜92 |
| + スクロールベンチ | **379.5–381.0–387.5MB** | +38〜39 |

**予算はスクロールに入る前に割れている** — 行選択と diff までで既に 340–349MB。
窓の床 151MB は Qt 側で、そこから先が全部アプリの分。

**行を組んだ分は返ってこない**(8 秒アイドル、`--settle-ms 8000`):
峰 377.4–379.5–386.6MB に対し settled 368.9–373.4–379.9MB = **返るのは 7〜8MB**。

残る手は [P3-確認事項.md](../../internal-docs/P3-確認事項.md) §app。

## 出荷ビルド(feature 無し)との差

`cargo xtask perf --shipped` は `cargo build --release` = 出荷ビルドを測る。
**駆動も報告もできない**(`PG_AUTO_*` に答える口も `perf_*` を言う口も
`automation` feature の中)ので、答えられるのは**メモリと `graph stream finished`
までの時間だけ**。リポジトリは run の `state.toml` の `[tabs]` から開く —
出荷ビルドに引数の口は無く、これは人が復元されるタブで開くのと同じ経路。

同じ座り・同じ corpus・同じ画面での背中合わせ:

| | WorkingSet | private | グラフまで |
|---|---|---|---|
| ハーネス込み(`--no-select --no-scroll`) | 252.8–255.2–256.9MB | 265.3–266.1–267.4MB | 1,094–1,100–1,104ms |
| 出荷ビルド(`--shipped`) | 251.0–255.6–256.6MB | 260.7–265.3–265.6MB | 1,092–1,144–1,183ms |

**ハーネスを積んだ分はメモリに出ない** — 中央値の差 0.4MB、範囲はほぼ重なる。
出荷ビルドの方が**多くやっている**(復元経路は HEAD を自動選択して詳細を引く —
`details request round trip` が 42–44ms 出る)のに同水準なので、差があっても
測定の散らばりより小さい。

**ハーネスは動いてはいる** — `HarnessSeat.wanted` は `AppBackend.harnessPresent`
= `cfg!(feature = "automation")` なので、`PG_*` を何も設定しない run でも
`WindowHarness` / `PageHarness` とその無条件の子は建つ(タイマーも
per-frame の接続も止まっている)。**exe に積んだバイト数はメモリではない**のと
同じ話で、建っただけの QObject 数十個は WorkingSet に出ない。

## Rust ヒープ

`cargo xtask perf --breakdown`(`memprobe` feature = 計数グローバルアロケータ。
Qt は C++ の `operator new` を通り `GlobalAlloc` に乗らない = この境界が
「アプリのデータ」と「その下の道具」を分ける)。

| 区分 | 実測 |
|---|---|
| 常駐(`rust_live`) | 20.5MB |
| ピーク(`rust_peak`) | 33.8MB |
| 名前の付いた分 | 11.9MB |
| 名前の無い分 | 8.5MB |

**常駐・ピークと「名前の無い分」はサンプルで揺れる** — 500ms ポーリングのどこに
当たったかで、refs パイプラインが一時的に抱えている分が乗る。**変化を読むなら下の
名前付きの表**(同じ refs 数なら再現する)。

| 保持者 | bytes | 要素数 |
|---|---|---|
| `session::LabelIndex` | 5,542,256 | 48,075 |
| `RefsSnapshot` | 5,036,439 | 54,282 |
| `GraphModel` の行 | 1,652,194 | 2,000 |
| walk のビルダ | 172,464 | 2,030 |
| 適用済みの差分 | 82,270 | 518 |
| 送信済み行の指紋(背景差分用) | 32,000 | 2,000 |
| サイドバー 8 セクション合計 | 1,480 | 54,287 |
| `session::RemoteTagIndex` | 40 | 0 |

**refs の本数がメモリを決める。** 上位 2 件はどちらも refs の本数に比例し、合計
10.6MB — 名前の付いた分の 89%。commits ではなく refs が支配的。**行数に比例するのは
2 件**(`GraphModel` の行 826 B/行 + walk のビルダ 85 B/行 = **911 B/行**)。
サイドバーは 8 セクション合計 1,480 バイト — 54,287 行の中身は `RefsSnapshot` を読む
(規約は rules-refs/app-ui.md)。

**`session::RemoteTagIndex` はこの run では建っていない**(0 要素)。建つのは fetch
の後の一部の状態だけで、建っている run ではここに 4.7MB 級が乗る — 名前付きの表を
run 間で引き算する時は、まずこの行が両方で同じかを見る。

## Qt の床(2026-08-11)

Qt そのものの値なので、アプリ側の変更では動かない:

| 積み上げ | WorkingSet | 差分の中身 |
|---|---|---|
| Qt の `qml.exe` + 素の `Window` | 75.5MB | Qt Quick + D3D + GPU ドライバの床 |
| 同 + Controls(Fusion)+ `ListView` | 83.9MB | +8.4 = このアプリも使う部品 |

描画経路の寄与は同条件の差で取った: リポジトリ無しが software 描画 90.9–91.3MB に
対し D3D(既定)115.7–116.3MB = **+25MB が D3D / GPU ドライバ経路**。
**software 描画は代替にならない** — 同条件で 56.4–57.8fps と 60fps 予算を割る。

**exe に積んだバイト数はメモリではない**(2026-08-29 実測)。tree-sitter 37 文法の
静的テーブルで exe は 61.1MB あるが、**`ENTRIES` を空にして exe を 10.5MB にしても
`--no-open` の WorkingSet は 198.7–199.4 対 199.0–199.1 で動かない** — 触られない
読み取り専用ページは常駐しない。exe のサイズを見てメモリを語らないこと。
(この A/B の絶対値だけは上の内訳表の `--no-open` と揃わない。**読むのは差**で、
絶対値の水準は §この記録の読み方 4 の座り差の範囲。)

## アロケータと確保の個数(2026-08-11)

**バイト数より個数が効く帯がある。** Windows ヒープは確保 1 個ずつに管理領域を持ち、
管理領域とサイズ級の丸めは**計数アロケータには見えない** — 確保の個数を減らす変更
(`crate::Name` + `SmallVec<[Name; 1]>` で 305,213 個)は、計数側 −3.1MB が
WorkingSet では −12MB に出た。

**mimalloc は不採用**(実測)。同一コミットでの A/B:

| | 既定(Windows heap) | mimalloc | mimalloc + 即時 purge |
|---|---|---|---|
| WorkingSet | 288.8–296.3MB | 326.4–351.0MB | 289.4–299.5MB |
| private | 305.9–311.1MB | 388.3–397.3MB | 348.8–354.2MB |

遅延解放を切って WorkingSet でようやく並ぶが private は +43MB のままで、しかも
配布時に環境変数を撃つ前提になる。起動・操作応答にも差は出なかった。

## この記録の読み方

**1 は機械が見る。2〜5 は人が揃える。**

1. **機械が見る**: 窓の出た画面と Hz / 掴んだ GPU アダプタと描画バックエンド /
   ベンチマークリポジトリの corpus token(run の前後で 2 回)。加えて run ごとに
   ロック・最小化・画面移動・配信フレーム・機械の忙しさを見て、駄目な run は
   撃ち直す。**同じ画面・同じアダプタ・同じ corpus でない数字は並ばない**
2. **corpus**。fetch は `HEAD` を動かさずにこの記録の前提を全部変える — 選ぶ行が
   変わり、ref の本数が変わればメモリの支配項も動く。**取り直す時は §計測条件 の
   1 行をそのまま撃つ**。`--corpus` が拒んだら、それは「リポジトリが動いた」であって
   直せる不具合ではない — **記録ごと取り直すか、比較を諦めるかの二択**。ハーネスは
   corpus を止めておく手段を持たない(凍結クローンを置くかどうかは未決 —
   [P5-確認事項.md](../../internal-docs/P5-確認事項.md) §17)。操作応答だけを
   跨いで比べたいなら `--select-oid` でコミットを名指しする(その oid が 2,000 行の
   窓に残っている間だけ効く)
3. **スクロールベンチの有無**(上表のとおり 38MB 以上動く)。判定の 300MB は
   ベンチ込みの行に対して読む
4. **座り(計測の機会)は残っている**。窓の位置とアダプタが固定された分だけ狭まったが、
   絶対値がゼロになったわけではない。**同じコミットの対照は同じ座りで撃つ**
   (`git checkout --detach <対照> && cargo xtask perf …`)
5. **採取数**。1 つの invocation の中でも WorkingSet は 8MB 前後散る。**10MB 級の
   差は 5 回採りでも分離できない**。中央値どうしで読み、範囲は「どこまで散ったか」
   としてだけ読む

**機械の忙しさの閾(対象以外 35%)は設計上の選び方で、それが数字を動かすかどうかは
測っていない。** 上の実測は 9.2–13.2% の負荷の下で撮ったもので、静かな機械との
背中合わせは取っていない — 閾を動かす前にそれを撮る。

**過去の記録との差を回帰と読まないこと** — 上のどれかが動いていれば、同じコミットでも
数十 MB 違う。判定は**予算に対する絶対値**で、前回比ではない。
