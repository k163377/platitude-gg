# 性能実測記録(Windows x64)

計測: 2026-09-05。測ったのは `6c885b38` の `crates/platitude-app` /
`crates/platitude-core`、ハーネスも同じ `6c885b38` の `xtask`。**5 run の本計測**で、
段ごとの表も同じ座りの中で撮っている。
**§Qt の床 と §アロケータ の 2 表だけは 2026-08-11 のまま** — 道具の側を
測ったもので、アプリ側の変更が届く場所ではない。

**gate は 1 つも開けずに撮っている**(`--allow-noisy` 無し)。ロック・最小化・画面移動・
画面の取り違え・配信フレームの床・CPU の 3 つの閾が全部閉じたままで、**7 座り 42 run が
1 度も落ちずに通っている**(撃ち直し 0)。根拠は §計測条件 の「gate」。

## 計測条件

**判定 4 行を撃ち直す 2 行**:

```
cargo xtask corpus
PG_ALLOW_GUI=1 cargo xtask perf --at <測る commit> --repo <上の 1 行が印刷した path> --runs 5
```

段ごとの表は 2 行目にフラグを足しただけで、**撃ち方は各節が持つ**。`--at` は計測台 rig
(roster 外の worktree)に名指しの commit を建てて測る — 席の編集は測られず、同じ commit の
2 度目はビルド無し(rules-refs/app-ui.md「計測は計測台(rig)で撃つ」)。この記録の commit を
撃ち直すなら `--at 6c885b38`。

- 対象: **`cargo xtask corpus` が生成する合成リポジトリ**。**corpus token
  `23da9ebd03a156a5937d265abb0a353fc60e7b75`**(`show-ref` 全体の blob id)—
  HEAD `e512482ebce1b16fd3a7908a4000c229896fcf7e`、コミット 200,000、
  refs 50,004 本(タグ 42,800 / リモートブランチ 7,200 / `main` / 追跡 `main` /
  リモート 2 本の `HEAD`)、追跡ファイル 109,652、pack 5 本 + multi-pack-index、
  commit-graph chain あり、作業ツリーは clean。
  **生成器が固定なので、消して作り直しても同じ token が出る**
- **なぜ clone ではなく生成か**: 人が使っているリポジトリの clone は計測の裏で
  fetch され、`HEAD` を動かさずに描く行・refs の本数・diff を測るコミットが
  全部変わる。**この記録の前提は「リポジトリが止まっていること」**で、それを
  clone で保証する手段は無い(§この記録の読み方 2)
- **形は `JetBrains/kotlin` の実測に寄せてある**が、**寄っていない軸がある** —
  何が寄っていて何が寄っていないかは §コーパスと kotlin の距離(そこが正本)
- ハーネスが選ぶ行(`--selection first` = ref から届く最新)は HEAD と同じ
  `e512482e`(**76 ファイル変更**)。既定で開く diff はその 1 件目
  `…/checker_codegen38182.java`(**34,059 バイト**の中の **+47 −3**)。
  **操作応答と diff frame の数字はこのコミットのもの**で、**大きいファイルの中の
  小さい diff = 文法ハイライトの最も高い経路**(ファイル全体をパースして全行に
  span を張り、変わった数行を塗る)。`--file` で名指しすれば同じコミットの
  7,070,205 バイトの `.kt` も開ける — `preview::SOURCE_BYTE_CAP`(4MB)の外側
- 表示は既定設定(`HEAD --branches --remotes --tags` を `--max-count=2000` の
  ウィンドウ、2,001 行)
- **窓は `\\.\DISPLAY2`(180Hz、1920x1080、原点 (0,0))に 1440x900 で固定**。
  run ごとの `PG_CONFIG_DIR` に `state.toml` を書いて渡す。**画面を固定しないと
  fps はどの画面に出たかで決まる** — この機材は 100 / 180 / 100Hz の 3 画面。
  **窓の復元はカーソルのある画面を基準に出る**ので、撃つ前にカーソルをその画面に置く
  (P3-確認事項 §app)
- ビルドは `cargo build --release --features automation`(ハーネス込み)
- **実ウィンドウ**(offscreen ではメモリも fps も表示性能にならない)、ウォーム
  キャッシュ、`PG_AUTO_*` フック、WorkingSet と private bytes の 100ms サンプリング
  最大値、`perf_done` による因果完了、デッドライン + kill ガード。1 回目は捨てて以降を採る
- **機械の状態も測って、駄目な run は落として撮り直す**(`--retries` 既定 3): ロック /
  セキュアデスクトップ(連続 3 tick から)/ 最小化 / 落ち着いた後の画面移動 / 画面 Hz に
  対して配信フレームが半分未満 / 対象以外が機械の 35% 超。窓が被さられた時は上げ直し、
  それでもベンチが 30 秒動かなければ run ごと落とす(被さりが 2 度続けば諦める)。
  捨て run は同じ exe・corpus を数分内に温めた invocation の直後なら省く(`perf::warmth`)。
  **run の前に別プロセスのビルドが走っていれば、終わるまで機械を止めて待つ** — この記録では
  2 座りが別席の `verify-ui` のビルドを待ってから撃っている(2 分と 11 秒)
- **gate は 4 つとも閉じたまま通る**(`--allow-noisy` を足していない)。`--allow-noisy` が
  開けるのは **CPU の 3 つの閾(run 前 / 平均 / 峰)と配信フレームの床の 4 つだけ**で、
  ロック・最小化・画面移動・画面の取り違えは元から閉じている。**対象プロセスの CPU は
  job object で子孫まで込み**(`perf::sampler`。報告の machine 行が
  `not this process or its children` と言い、`memory.csv` の `children_counted` が
  全 tick で 1)なので、アプリがリポジトリを開くたびに撃つ
  `git status --porcelain=v2 -z --branch -uall` — 追跡 109,652 / 無視 78,000 を
  preload-index の並列 lstat で歩き、**1 本 2.2–2.4 CPU 秒を wall 200ms に詰める
  = 約 11 コア幅** — は「対象以外」に数えられない。**7 座り 42 run の峰は 10.8–45.5% で
  閾 75% の内側**、平均のほうは対象以外 3.4–19.1% で閾 35% の内側
- **短い段ほど対象以外の平均は高く出る**(出荷ビルドの段 8.3–19.1% に対し判定
  6.8–8.9%)が、それは同じ git の仕事が 2 秒の run と 14 秒の run で割られるだけで、
  機械が忙しいのではない — **段どうしで機械の列を並べない**
- **画面は invocation の間ずっと起こしておく** — ビルドと run の間の待ちも含めて。
  `ES_DISPLAY_REQUIRED` は run の間だけでは足りない(**既に暗い画面は起こせない**ので、
  2 本目以降の run が毎回暗い画面から始まる)。起こすのは入力なので 0 ピクセルの
  マウス移動を注入する。**その結果 `away_ms` は「人が居たか」を答えない** —
  答えるのは「起こす側が動いているか」だけ(`perf::sampler::Awake`)
- 機材: Ryzen 9 9900X(12C/24T)/ 32GB / Windows 11 build 26200 / git 2.55.0 /
  Qt 6.10.3。GPU 3 系統のうち Qt が掴んだのは **Adapter 0 `NVIDIA GeForce RTX 3070`**
  (D3D11、`Animation Driver: using vsync: 5.56 ms`)。**kept run は全部同じ
  グラフィックス構成でなければ通らない**(違ったら報告ごと落ちる)
- 数値は **min–中央–max**(kept run の全数)。**判定は max、比較は中央**を読む —
  範囲は run を増やすほど広がるだけなので、範囲だけでは何も言えない
- 撃った時の機械: 7 座りを通して全体 6.6–36.0% busy、うち対象プロセス以外 3.4–19.1%
  (最悪の 1 tick で 10.8–45.5%)。
  **静かな機械ではない**(ブラウザ・IDE・コンテナランタイム・他席のセッションが動いている
  24 スレッド機)

## 判定

| 予算 | 実測(5 run) | 判定 |
|---|---|---|
| 起動→グラフ初回表示 3s | 1125–1141–1164ms | ✅ |
| 操作応答 100ms | 80.7–92.5–96.1ms | ✅(縁 — 下の注) |
| スクロール 60fps | 177.7–177.9–178.0fps | ✅ |
| メモリ 300MB | **296.4–300.4–303.7MB** | ❌ **max で 3.7MB 超過**(中央 +0.4、min は内側) |

- **メモリは予算の縁に載っている** — 5 run のうち内側 1 本(296.4)、外側 4 本
  (300.2–303.7)。同じ記録のスクロール込み 3 組 15 run(判定 / 峰と settled / Rust ヒープ)
  では 294.8–308.8 で、内側 5 本・外側 10 本。**どの段で出るかは §メモリの段**(出るのは
  スクロールの段)。**何で出るかは §常駐の内訳**(絵文字 1 文字が呼ぶフォールバックの歩き)。
  8 秒置いた settled は 5 run とも内側(§峰と settled)だが、予算は峰で読む
- **操作応答は 5 run とも内側だが、縁**。行選択→詳細が描かれるまでの 1 点
  (`perf_details_frame`)は、判定の座りで 80.7–92.5–96.1ms。同じ記録のハーネス込み
  3 組 15 run では 100ms を跨いだのが 2 本 — 峰と settled の座りで 101.2ms、計数アロケータ
  (`memprobe`)を積んだ座りで 110.1ms。**データだけの往復(`git show` 1 プロセス)は
  57–58–73ms**(3 組で 55–75ms)なので、残りの 25–35ms が描く側
- diff を開くのは別の 1 点で **112.9–121.1–125.8ms**(3 組を通した max は 130.7ms)。
  予算表の「操作応答」はこの点ではないが、**人が待つ長さとしては最長**なので併記する
- **4 行ともハーネス込みのビルドで撮っている。** 出荷ビルドで撮れるのはメモリと
  グラフまでの時間だけで、**fps と操作応答は出荷ビルドでは定義できない**(駆動する口も
  フレームを報告する口も `automation` feature の中)。積んだ分の代金は §出荷ビルドとの差
- 起動の行が読んでいるのは `startup`(**目に見えるグラフのフレームが出るまで**)。
  stream が終わるまで(`to a graph` = 出荷ビルドも答える唯一の点)は 1132–1154–1182ms、
  うち walk は 237–237–287ms
- private bytes は 272.0–279.9–286.0MB。予算は WorkingSet に対して読む
- fps は画面の **98.7–98.8–98.9%**。予算 60fps に対して余る。**16.7ms を跨いだフレームは
  5 run とも 1 本**、p95 6.2–6.3ms / p99 6.8–7.2ms。frame max は 123.2–149.7ms で、
  跨いだその 1 本がこれ(100ms 級)
- **判定対象は合成コーパス** — §コーパスと kotlin の距離 に N は無く、
  コーパスが軽い軸は 3 つとも 1 割強に収まっている
- 数字が取れなかった run は `missing` として報告ごと落ちる(`xtask perf`)。
  前提はログが無色であること — 色コードが乗ると `key=value` が検索不能になる
  (`platitude_gg::init_tracing` は色を付けない)

上の座りの帰属。`VirtualQueryEx` で private / mapped / image に割り、`QueryWorkingSetEx` で
常駐だけを数え、プロセスヒープは `RtlQueryProcessDebugInformation` でブロックごとに歩く
(撮り方は xtask `perf::attribution`。run ごとの表は `attribution.txt`):

| 種類 | 常駐 | 中身 |
|---|---|---|
| private | 187.6–190.7–191.3 | プロセスヒープ busy 119.4–121.1–122.1(546,732–547,799 ブロック、free 18.4–21.2)+ ヒープ外 ~70 |
| mapped(ファイルの写像) | 34.7–35.2–35.5 | **うちフォント 31.4–32.4–33.0(165–166 ファイル)** |
| image(DLL / exe のコード) | 71.1 | exe 8.5・NVIDIA のユーザーモードドライバ 11.0・Qt の DLL 群 ~15 |

**段ごとに同じ帰属を撮る**(各 2 run、`--settle-ms 8000 --attribute` に段のフラグを足す)と、
増分の種類が段で違う:

| 段 | settled | private | うちヒープ busy(ブロック) | mapped | うちフォント(ファイル) |
|---|---|---|---|---|---|
| 窓だけ | 137.4–137.8 | 66.6–67.0 | 51.5(262.6K) | 4.7 | 2.6(9) |
| 開くだけ | 200.7–202.5 | 128.5–130.4 | 95.5–96.4(449.4K) | 4.7 | 2.6(9) |
| 行選択と diff まで | 230.0–231.0 | 154.4–155.4 | 118.9–119.0(529.3K) | 4.8 | 2.8(9) |
| スクロールまで | 293.4–297.9 | 187.6–191.3 | 119.4–122.1(547.3K) | 34.7–35.5 | 31.4–33.0(165–166) |

- **開く +62 はヒープ**(busy +44、+187K ブロック — うち Rust は §Rust ヒープ の 18.7MB、
  残りはページの QML オブジェクト群)。**行選択と diff の +26 もヒープ**(+23、+80K ブロック)
- **スクロールの +65 はヒープではない**(busy +2)。**フォントの写像 +30** と、**ヒープ外の
  private +30**(2〜4MB の確保が 6 → 14 個)の 2 つで、どちらも同じ引き金で出る(次項)
- **フォント 31MB の正体は「一族に無いグリフ 1 つで Qt がフォント DB の全 family を populate する」
  代金**で、CJK ではない(fallback 一覧を作る `QPlatformFontDatabase::fallbacksForFamily` が
  writing system で絞る前に全 family へ `ensurePopulated()` を当て、DirectWrite の populate は
  family ごとに face を作って残す — 検索は Segoe UI Emoji で止まるが、一覧を作った時点で全部
  開いている)。165 ファイルが各 0.1–1.5MB ずつ触られていて、
  `calibri` / `cambria` / `corbel` / `constantia` / `ebrima` / `gabriola` / `Nirmala` …
  CJK と無関係なラテン字体まで並ぶ(`attribution.txt` の resident by file)。populate で作った
  face(DirectWrite の face + Qt のエンジン)は残るので、ヒープ外の private +30 も
  同じ歩きの代金。**引き金はコーパスの 2,000 行に 2 つ入る絵文字の subject**(`corpus::shape` —
  基準リポジトリの窓の写し)。同じ demo リポジトリ(`basic`、日本語の subject 入り)を
  開くだけの settled で切り分けると: 絵文字なし 164.7–165.6(フォント 2.8MB / 9 ファイル)、
  **絵文字 1 文字の subject を持つコミットを 1 つ足す → 220.4–221.5(フォント 31.5–33.0MB /
  165–166 ファイル、private +25)**。**見えている行に絵文字が 1 つあれば +55MB**、日本語の
  subject は何も足さない。QML の `font` 型には `families` が無く(Qt 6.10.3 の
  `QQuickFontValueType` は `family` と `contextFontMerging` まで)、qtbridge にも `QFont` の口が
  無く、あっても `QFontDatabase` の fallback / emoji API は一覧の先頭に前置きするだけで populate を
  止めない(使い捨てプローブの実測: 90 family / 162 ファイルのまま。止まるのは色フォントを primary に
  した run だけ)— 扱いは [P3-確認事項.md](../../internal-docs/P3-確認事項.md) §性能
- **image の 71MB は動かない**(窓だけ 66.1 → 判定 71.1。増分 5MB は文法ハイライトの経路が
  触った exe のページ)

## コーパスと kotlin の距離(2026-09-04 実測)

**両列とも同じ実装で撮る**:

```
cargo xtask corpus
cargo xtask corpus --against <kotlin の clone>
```

片方を別の数え方で撮った表は比較ではなく 2 つの定義なので、**手で数えた数字を
この表に足さない**。`--against` は読むだけで、相手には何も書かない。
R = 再現、A = 近い(コーパスが重い側)、L = コーパスが軽い。

| | kotlin | コーパス | |
|---|---|---|---|

対し D3D(既定)115.7–116.3MB = **+25MB が D3D / GPU ドライバ経路**。

## アロケータと確保の個数(2026-08-11)

**バイト数より個数が効く帯がある。** Windows ヒープは確保 1 個ずつに管理領域を持ち、
管理領域とサイズ級の丸めは**計数アロケータには見えない** — 確保の個数を減らす変更
(`crate::Name` + `SmallVec<[Name; 1]>` で 305,213 個)は、計数側 −3.1MB が
WorkingSet では −12MB に出た。

**mimalloc は不採用**(実測)。同一コミット・同一コーパスでの A/B:

| | 既定(Windows heap) | mimalloc | mimalloc + 即時 purge |
|---|---|---|---|
| WorkingSet | 288.8–296.3MB | 326.4–351.0MB | 289.4–299.5MB |
| private | 305.9–311.1MB | 388.3–397.3MB | 348.8–354.2MB |

配布時に環境変数を撃つ前提になる。起動・操作応答にも差は出なかった。

## この記録の読み方

**1 は機械が見る。2〜5 は人が揃える。**

1. **機械が見る**: 窓の出た画面と Hz / 掴んだ GPU アダプタと描画バックエンド /
   コーパスの token(run の前後で 2 回)。加えて run ごとに
   ロック・最小化・画面移動・配信フレーム・機械の忙しさを見て、駄目な run は
   撃ち直す。**同じ画面・同じアダプタ・同じコーパスでない数字は並ばない**。
   **忙しさも機械が見ている** — 閾は 1 つも開けていない(§計測条件 の「gate」)
2. **コーパス**。生成器が固定なので**もう勝手には動かない** — token が違う時に
   起きたことは 2 つに 1 つで、**生成器を変えた**(なら記録ごと取り直す)か、
   **`--repo` が生成物ではない別のリポジトリを指している**(なら指し直す)。
   `--corpus <token>` を足すと、違った時に measure ではなく refuse する。
   操作応答だけを跨いで比べたいなら `--select-oid` でコミットを名指しする
   (その oid が 2,000 行の窓に残っている間だけ効く)
3. **スクロールベンチの有無**。判定の 300MB はベンチ込みの行に対して読む。ベンチの代金は
   §メモリの段 の +70MB で、中身は §常駐の内訳 のとおり **見えた行が呼んだフォールバックの
   歩き**(フォント +30 とヒープ外 +30)— 窓に絵文字の行が無いリポジトリでは出ない
4. **座り(計測の機会)は残っている**。窓の位置とアダプタが固定された分だけ狭まったが、
   絶対値がゼロになったわけではない。**同じコミットの対照は同じ座りで撃つ**
   (`cargo xtask perf --at <対照> …` — 計測台 rig が建てるので席は動かない)
5. **採取数**。スクロールまで撃つと 1 つの invocation の中で WorkingSet は 7〜10MB 散る
   (判定 296.4–303.7、峰と settled の座り 298.7–308.8)。**数 MB の差は 5 回採りでは
   分離できない**。中央値どうしで読み、範囲は「どこまで散ったか」としてだけ読む。
   窓だけの段は 1.4MB しか散らないので、そこは違う読み方でよい

**機械の忙しさの閾(対象以外 35%)は設計上の選び方で、それが数字を動かすかどうかは
測っていない。** 上の実測は 3.4–19.1% の負荷の下で撮ったもので、静かな機械との
背中合わせは取っていない — 閾を動かす前にそれを撮る。

**過去の記録との差を回帰と読まないこと** — 上のどれかが動いていれば、同じコミットでも
数十 MB 違う。判定は**予算に対する絶対値**で、前回比ではない。
