# 差分ペインの画像の運び方の実測(Windows x64)

画像の履歴側(index・commit の版)を、差分ペインへどう運ぶかの比較です。**読むのは同じ組(背中合わせに撮った A/B)の列の間の差**で、予算行との絶対値は [perf-windows-x64.md](perf-windows-x64.md) §判定 が正です。
運び方の決定は `platitude_core::preview` の module doc です(base64 で渡さない、開いた絵の代金は復号した画素、ペインが移るか閉じれば全部返る)。

## 比べた列

土台はすべて main の e8512b7d2 です。

| 列 | 運び方 | 測った commit |
|---|---|---|
| 一時ファイル | 差分を読む時に blob を一時ファイルへ書き、`file:` URL で渡す | 193ae6d2d(どのブランチにも無い) |
| 持ち続け | 差分を読む時に blob を全部読み、ペインが出している間メモリに持つ | e8512b7d2 |
| 描く時に読む | 差分を読む時は大きさだけを読み、`Image` が求めた時にセッションの git で丸ごと読み、Qt の画像読み込みスレッドで復号する | f40422254 |
| 描く時に読む+その場で乗算 | 描く時に読むの復号の後で、ARGB32 の絵をその場で乗算済みの形にする | e1e9bd030(どのブランチにも無い) |
| 流す | 描くスレッドを 1 面に 1 本立て、git の出力を流しながら Qt の読み手へ渡す(流せない形式は丸ごと読む) | 4bff914f2 |
| 流す+その場で乗算(採用) | 流すの後で、ARGB32 の絵をその場で乗算済みの形にする | 7db4825e3 |

作り直し方:

- 一時ファイル: e8512b7d2 の上で `git revert 1de724d0f` を撃ちます。衝突は `session/open.rs` のセッションの欄の並び 1 か所だけで、`preview_files: preview::PreviewFiles::new(),` を main が足した欄の前へ戻します。
- 描く時に読む+その場で乗算: f40422254 の `preview_images.rs` に、採用形の `for_texture`(と、それが使う `QImage::convertTo` の束縛・`ImageConversionFlags`)を足し、`finish` で復号した絵に掛けます。

## 測り方

- `cargo xtask perf --software --no-scroll --repo <素材> --at <A> --compare <B> --runs 3`(ABBA、各列 6 標本)。組ごとに背中合わせに撮ります。
- 素材: `cargo xtask demo-repo bigpicture`。最新コミットで、両面とも 3000×3000 の RGBA PNG(`big.png`、透明な画素なし)が変わります。perf が既定で開く差分がこれです。corpus token は 0d4d09eb70da。**この PNG はほぼ無圧縮で、圧縮バイト列(36,005,813 バイト)と復号した画素(ARGB32 で 36,000,000 バイト)がどちらも片面 34.3 MiB です** — 生涯の最大だけでは、どちらの山かを分けられません。分けるために「その場で乗算」の有無の列を並べています。
- 機材: Windows 11 / x64 / Qt 6.12.0 / release + `automation` / software scene graph(`--software`。読めるのはメモリだけで、WorkingSet は D3D の表示経路とは別の量)/ 画面 DISPLAY2(180Hz)。
- 機械: 対象以外の CPU は組 1 が 2.9〜11.3%(最悪の tick 33.3%)、組 2 が 3.9〜7.5%(最悪の tick 18.4%)、組 3 が 3.8〜12.2%(最悪の tick 34.9%)、組 4 が 2.2〜7.5%(最悪の tick 24.2%)。組 2〜4 を撃つ直前に動いていた他の作業は、ユーザーの窓 1 つだけでした。

## 読み

- **描く間の一時の山は 2 つあります**。採用形では生涯の最大が標本の峰と一致し、一時ファイルと同じです(組 3)。
  - **テクスチャの写し**: Qt Quick のテクスチャ工場(`QQuickDefaultTextureFactory`、`qquickpixmapcache.cpp`)は、乗算済み ARGB32・RGB32 などの決まった形でない絵を、写しを作って乗算済み ARGB32 に変えます。その間、応答が持つ元の絵と写しが並び、面ごとに復号した大きさの山が出ます。RGBA の PNG は ARGB32 に復号されるので、この形です。Qt Quick 自身がファイルを読む経路は、透明な画素の無い絵をその場で RGB32 に変えてから工場へ渡すので(`maybeRemoveAlpha`)、一時ファイルの列には出ません。採用形は、描くスレッドで ARGB32 をその場で乗算済みにしてから渡します(`preview_images::for_texture`)。
  - **復号を待つ圧縮バイト列**: 丸ごと読む形は、面の圧縮バイト列を読み終えてから復号の終わりまで持ちます。流す形が持つのは、復号の手前で待っている chunk だけです。
- **それぞれの山の大きさ**(組 2・組 4。山の無い採用形の生涯の最大 280.3 からの差):
  - 描く時に読む+その場で乗算は +34 MiB です。1 面分の圧縮バイト列で、描く時に読む形の復号は Qt の画像読み込みスレッド 1 本で面ごとに順に走るため、1 面分ずつです。
  - 流す(乗算なし)は +69 MiB です。2 面の写しで、流す形は面ごとのスレッドで並べて復号するため、2 面の写しが重なります。
  - 描く時に読む(乗算なし)は、4 標本で +69、2 標本で +33〜34 です。
- **diff が出るまで**: 描く時に読む 4 列は、差分を読む時に blob を読まず、大きさだけを読みます。一時ファイルと持ち続けは、ここで両面の 72MB を git から読みます。復号はその後に別スレッドで走るので、この時間に入りません。
- **プロセス**: 面を描くたびに `git cat-file blob` が 1 本立ちます(セルは pixmap のキャッシュを使いません)。名前の形式は流せるのに中身が流せない形式の絵(BMP を `.png` と名乗る等)は、流しを止めて丸ごと読み直すので 2 本です。

## 流す形の受け渡し(実測)

機材は上と同じです。debug ビルドのテストから、release の Qt と git を呼んで測りました。

| 量 | 無圧縮 36MB(big.png) | 圧縮 21MB(3000×3000 RGBA、雑音入りの写真に近い PNG) |
|---|---|---|
| git の出力が届く chunk | 約 2,000 回(平均 18KiB、最大 64KiB) | — |
| 丸ごと: git が読み終えるまで | 69〜73 ms | 83〜203 ms |
| 丸ごと: その後の復号 | 18 ms | 111 ms |
| 流す: 読みと復号を重ねて終えるまで(git が生きて枠を握る間) | 70〜73 ms | 130〜151 ms |

- **受け渡しの上乗せ**: 同じ 36MB をメモリから復号すると 19 ms、18KiB ずつスレッド間で渡して復号すると 30 ms です。この 11 ms は git の出力を待つ間に重なって隠れます。chunk を束ねて回数を減らす形は、効き目が小さいので採りません。
- **git の実行枠**: 流す読みの git は、復号が追いつくまで生きます。その間、クリック用の予備(`process::Slots`)の枠を 1 本握り、圧縮の効いた絵ほど長く握ります(上の 21MB で 83 ms → 130 ms)。丸ごと読む形は、読み終えた時点で枠を返していました。絵が出るまでの時間は、流す形の方が短くなります(194 ms → 130 ms)。
- **時間の上限**: 読みの上限 30 秒(`DEFAULT_TIMEOUT`、起動から数える)に、流す形では復号の時間も入ります。超えた読みは失敗に終わり、その面は丸ごと読み直します。

## 流す形の効かない所

- BMP・ICO・TIFF・WebP は丸ごと読みます。理由はそれぞれ次のとおりです(`preview_decode::streams`)。
  - BMP: 順次デバイスでは画素の開始位置への seek を飛ばすので、隙間のあるファイルはずれた絵になります。
  - ICO・TIFF: 読み手が seek します。
  - WebP: 読み手が全部そろうまで順次デバイスを受けません。
- gzip した SVG は、Qt の SVG の読み手が全部を読み込んでから解きます。
- 動く SVG は、描くスレッドが Qt のスレッドでないため、読み込みの中でタイマーを起こせません。Qt が警告を 1 行出します(`QObject::startTimer: current thread's event dispatcher has already been destroyed`)。絵は最初のフレームで、Qt のスレッドで復号した時と同じです。

## 採らなかった案

- **透明な画素の無い絵を RGB32 にする**(Qt Quick のファイルの経路と同じ形): 描く結果は乗算済みと同じで、画素を走査する束縛が要ります。
- **ARGB32 以外の形も描くスレッドで変える**: 深さの違う形は、どこで変えても新しい画素の場所が要るので、工場に任せています。
