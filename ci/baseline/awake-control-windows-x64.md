# Windows のスリープ保持: 実測

2026-10-16。holder revision 26、activity protocol 1(`cargo xtask awake`、`crates/xtask/src/awake`)。
デスクトップアプリのログによる補助と実スリープ試験の記録は [ログ補助](../../internal-docs/awake-ログ補助.md)。

## 判定

保持・解除の Windows API 呼び出し、互換ビルドの holder が共有する activity、読取りと hook の競合、
保持中の読取りの間引き、判定の履歴、消えた保持の出し直し、書き手の無い subagent の扱い、Stop hook が走り
終わるまでのターンの扱い、静かな保持の上限を確かめた。
要望全体の完了ではない。Claude から通知されない許可・入力待ちは
[P3 の未達](../../internal-docs/P3-確認事項.md#開発環境スリープ止め-cargo-xtask-awake)に残る。
ここのテストは、実際の Claude の許可画面からのイベント配信を証明しない。

## 実 API 試験

`awake::tests::holder::coordination::compatible_holders_apply_and_clear_real_windows_requests_together`。
テスト専用の一時ディレクトリと Claude 役のプロセスを使い、通常の `apply` から WMI で起動する holder(r26)と、
同じスクリプトで holder 名だけ r27 にした互換ビルドを同時に動かす。OS API は置き換えない。
session / hook の入力は fixture で、Claude 本体ではない。

`SetThreadExecutionState` の非 0 の戻り値は、成功とそのスレッドの直前の状態を示す
([Microsoft の仕様](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate))。
両 holder とも保持時の戻り値は `0x80000000`、解除時は `0x80000001` —— system の継続要求を設定・解除でき、
display の継続要求は加えていない。

| 遷移 | r26(WMI 起動) | r27(互換ビルド) |
| --- | ---: | ---: |
| 最初の Prompt → 保持 | 3380 ms | 885 ms |
| s が Stop、t は質問待ち → 解除 | 46 ms | 12 ms |
| t の質問への回答 → 保持 | 40 ms | 15 ms |
| t も Stop → 解除 | 49 ms | 11 ms |

質問待ちになる前から s が作業中なら、t の質問だけでは解除しないことも同じテストで確かめる。
数値は単発の観測値で、遅延の上限ではない。最初の保持は
WMI の起動と PowerShell の C# 型のコンパイルを含み、成立するまで保持の無い区間がある ——
「呼び出しの実行前に必ず保持済み」の保証には使えない。

使われなくなったビルドの holder は `a_started_holder_of_a_quiet_build_quits` で確かめる。WMI で起動した holder の
hook の印(`hooks-r<n>`)を 10 分より前に戻し、hook が動いている互換ビルドと並べると、前者は次の読取りで名前を外して
プロセスごと終わり、claim は残り、互換ビルドが保持を続けた。降りる判定そのものは、holder 本体を 1 回だけ読ませる
試験で場合分けする(使用中の別ビルドがある / 1 本だけ / 全部静か / 相手の心拍が古い)。

awake の Windows テストは **116 passed / 0 failed / 3 ignored**(55.29 秒。律速は tick 待ちを含むテストで、
他席の負荷で揺れる)。
ignored は、親テストが専用環境で呼ぶ子プロセスの入口 2 本と、手動の実スリープ試験 1 本。子コマンドの背景実行、
質問・許可待ち、複数セッション、subagent、通知、所有者の終了、読取りの妨害、同時起動、hook のパイプの解放、
互換ビルドの同居、照会中に始まった仕事、owner の一覧の後に始まったコマンド、使われなくなったビルドの holder が
降りること、ログ補助、保持中の読取りの間引き、静かな保持の上限、履歴(理由の表記・切り詰め・書き手ごとの最後の行)を含む。

## 保持の消失と出し直し

一度立てた継続要求は、黙って数えられなくなることがある。2026-10-12〜13 の本番(holder r16、アプリ側の保持は Off):

| 時刻(JST) | 出来事 |
| --- | --- |
| 10/12 10:30:08 | r16 が保持を立てる(`SetThreadExecutionState` の戻り値 `0x80000000`)。以後、判定は 10/13 01:12 まで holding のまま変わらず、API を呼び直していない |
| 10/12 16:00:48 | スリープ(Kernel-Power 42 の理由 Application API = スタートメニュー等の API から始めたスリープ)。16:40:39 に復帰 |
| 10/12 17:52:34・21:04:03、10/13 00:43:52 | スリープ(理由 System Idle)。どれも履歴は holding、作業中のセッションあり |
| 10/13 00:47 | `CallNtPowerInformation(SystemExecutionState)` は `0x0`。r16 の台本を回すスレッド(10/11 03:00:45 起動、CPU の大半を使う 1 本)は生きている |

保持を立てたスレッドが生きたまま、要求は数えられていなかった。その間の出来事は API からのスリープと復帰だけで、
何が要求を外したかは確かめていない(制御したスリープ試験は未実施)。

`SetThreadExecutionState(0)`(`ES_CONTINUOUS` 無し・フラグ無し)は要求を変えず、そのスレッドの今の要求を返す
(別プロセスでの実測: 新しいスレッド `0x80000000`、保持中 `0x80000001`、解除後 `0x80000000`。その間の
`SystemExecutionState` は保持中だけ `0x1`)。holder(r19〜)は保持中の読取りのたびにこの読みと
`SystemExecutionState` を見て、どちらかが保持を失っていれば解除してから立て直す(要求を変えるため。何も
数えられていない間の解除は何も外さない)。立て直した直後と、保持を立てた直後に数えに映らなければ、要求を
専用のスレッドから立て、解除まで持たせる。専用スレッドからも映らなければ、数えが要求を映さない環境として、
次に保持を立てるまでスレッドの要求だけを読む(映らない値を毎回の消失と読まないため)。履歴には消失 1 回に
つき `lost` 行を 1 行書く。

同じスレッドからの立て直しで数え直されるか、専用スレッドからなら数えられるかは、実機では確かめていない
(消失を起こせないため)。確かめたのは、新しいプロセスの holder を起こした直後に `SystemExecutionState` が
`0x1` に戻ったこと(10/13 01:12)と、下のテスト:

- `a_request_that_stops_being_counted_is_asked_again` — OS 要求を記録係に置き換え、スレッドの要求が消えた形・
  要求が変わるまで数えられない形・どう変えても数えられない形(専用スレッドで直る)の 3 つ
- `a_kept_request_goes_with_the_hold_and_comes_back_with_it` — 専用スレッドの要求は解除で外れ、元のスレッドが
  数えられないまま保持し直すと専用スレッドから立て直す。保持を立てた時から数えられない場合も同じ
- `a_loss_is_told_once_and_a_count_that_shows_nothing_is_not_read` — 何をしても直らない消失は 1 行だけで、
  専用スレッドも残さない。保持を立てた時から何も映らない数えは読まない
- `a_real_request_let_go_of_behind_the_holder_is_asked_again` — 実 API。holder 自身のスレッドの要求を裏で外すと、
  次の読取りが `lost thread:80000000,system:…,after:…` を書き、そのスレッドの要求が `0x80000000` から
  `0x80000001` に戻り、名前の最後の設定時刻が最初の保持より進む
- `a_request_kept_apart_starts_and_ends_on_the_real_api` — 実 API。専用スレッドの立て・外しを繰り返しても止まらない

どれも、この読みを外した台本では赤になる(最後の 1 本は専用スレッドそのものの試験)。

## Stop hook が走り終わるまでのターン

2026-10-13 10:14 の本番(holder r19)。席 b のセッションのターンが終わる間際に、背景コマンドの完了通知が
キューに積まれた:

| 時刻(JST) | 出来事 |
| --- | --- |
| 10:13:59.681 | モデルの最後の応答 |
| 10:14:02.490 | 通知の `queue-operation` `enqueue`(`<task-notification>`) |
| 10:14:02 | Stop hook が claim を idle に書き、その読取りで holder が解除。同じ秒にスリープ開始(Kernel-Power 42 は System Idle、就寝時刻 10:14:02.89) |
| 10:14:04.212 | Stop hook の記録(`stop_hook_summary`)。7 ms 後に `dequeue`、その 3 ms 後に通知の user 行 |
| 10:14:04 | holder が通知の行を読んで保持し直す(就寝は既に始まっていた) |

Stop の読取りから通知の行が書かれるまでの間、数えるものが無かった。無操作タイマーが切れていれば、解除の瞬間に
眠る。

Claude Code は、Stop hook(このリポジトリの物とユーザーの物)を全部走らせて `stop_hook_summary` を書き、
その後でキューに積まれた物を次のターンに取る。このプロジェクトの 2026-10-01 以降の transcript で:

- 応答で終わったターン 1,583 回のうち 1,577 回の後に `stop_hook_summary` があった。残り 6 回は、その前に
  次の発話(人 3・通知 1・不明 2)が書かれていた。応答の最後の行から記録までは中央値 3.5 秒、90% 点 9.6 秒、
  99% 点 20 秒、最長 199 秒
- 通知が積まれる時機は決まっていない。最後の応答を書いている途中(その後に応答の行が続く)、Stop hook が
  走っている途中、溜まった通知を 1 件ずつ取る間のどれも、記録の後に取り出される。最後の応答より後に積まれ
  取り出されないまま Stop した 19 回は、どれも記録から 14 ms 以内に取り出された(9 月以前の版には、数分〜
  数時間取り出されない例がある)。Stop hook の途中に積まれた例では、記録から取り出しまで 453 ms あった
  (席 f、10/12 22:11:05)
- API エラー(使用量の上限など)で止まったターン 75 回(9/15 以降)には記録が無い。hook に止められた発話
  (ターンが始まらない)で走る Stop にも無い
- 今ある idle の claim で、こちらの Stop hook が claim を書いた時刻から記録までは 1.3〜1.7 秒

holder(r22〜)は、止まった(idle の)セッションを、transcript がその Stop より後の `stop_hook_summary` を
持つまで `turn:` として数える。上限は Stop から 60 秒(`awake::STOPPING`。記録の来ない Stop がそこで解ける)。
この待ちに掛けないのは transcript の無いセッション(Codex など)だけ(r26〜)。holder が読むのは transcript の
末尾 256 KB で、そこに記録が無いことは記録を書かない版の印にならない: 1 ターンの呼び出しと結果がその幅を
越え、最初のターンの前には記録が無い。このプロジェクトの 10/13 以降の transcript で、Stop 404 回のうち 125 回は
直前の記録が末尾 256 KB の外にあった(最長 10 MB)。2026-10-16 04:17 の本番(r25)がこの形 — 前の記録から
1.0 MB 書いた 2 時間のターンの最後の応答の途中に gate の完了通知が積まれ、Stop の読取りで解除した時刻
(04:17:20.823)が、そのまま就寝の時刻(Power-Troubleshooter の Sleep Time)になり、3.5 時間止まった。
記録の後も、最後の発話より後の `queue-operation` が `enqueue` で終わっている(積まれてまだ取り出されていない)
間は数える(積まれてから 60 秒まで)。通知の行が書かれれば、通知でターンが始まる規則が引き継ぐ
(`a_stopped_session_counts_until_its_stop_hooks_have_run`・`a_stop_counts_until_its_record_with_none_in_sight`。
どの扱いも、外した台本では赤になる)。
キューを「enqueue で +1、dequeue・remove で −1」と数える読み方は使わない: ターンの途中の通知は取り出しの
記録無しに添付で届くので、数えが空にならない。

残る窓: 記録から通知の行が書かれるまで(最後の応答の途中に積まれた物は記録から、Stop hook の途中に積まれた
物は取り出しから。実測で十数 ms 以内)に読取りが当たると、その読取りは解除する。次の読取り(最長で 1 tick)で
保持し直す。

## 静かな保持の上限

読取りの漏れ(終わりの来ない呼び出し、人待ちを作業と取り違えた保持)は、それを終わらせる物が無い。holder(r25〜)は、
保持中に何も起きないまま、起きている時間で 2 時間(`awake::QUIET`。`QueryUnbiasedInterruptTime` で測るので、
眠っていた時間は数えない)経ったら、数えている物が残っていても保持を解き、次に何かが起きるまで保持しない。
眠らせるのは電源プランで、人が操作していれば眠らない。「何かが起きた」は、前の読取りと比べて次のどれかが
あったこと:

- どれかのビルドの `hooks-r<n>`(hook が動くたびに書かれる)か、立っている claim の transcript が書き直された
- 数えている背景プロセス(走っているシェル呼び出しの子と、その下の全プロセス)に、前に無かった物がある
- 前にもあった数えている背景プロセスが、合わせて 1 コアの 10%(`holder::BUSY`)を超えるプロセッサ時間を
  使った(起きている時間で 1 tick = 15 秒以上の間隔で判定)

読取りの途中で claim が変わった時も、何かが起きた扱い。発火は履歴に `released quiet:<分>m` と残る。

2 時間の根拠(2026-10-04〜10-13 の履歴の保持区間 110 本と、全セッションの transcript の書き込み時刻の突き合わせ。
保持したまま機械が眠っていた区間は除く):

| 種類 | 全セッションの transcript が書かれなかった最長 | 中身 |
| --- | ---: | --- |
| 正当 | 111 分 | 他席の反映を待つループ(`sleep 600` と git を繰り返す。10/11 16:25、`process:`) |
| 正当 | 75 分 | 背景の `cargo test`(10/12 04:25) |
| 正当 | 57 分 | 他席の反映を待つループ(`until git grep …; do sleep …; done`。10/13 13:32) |
| 漏れ | 266 分 | アプリの許可画面待ちを保持し続けた(10/05 未明、r6 で修正) |
| 漏れ | 13 時間 44 分 | 書き手の無い subagent の呼び出し(10/12、r19 で修正) |

正当な無音は、プロセッサを使う背景コマンドか、新しいプロセス(`sleep`・git)を起こし続ける待ちループで、
どちらも上の「何かが起きた」に当たるので、2 時間を超えても保持が続く。漏れの 2 件には背景プロセスが無い。

確かめるテストは 4 本(`awake::tests::holder::quiet`)。出荷する holder の台本(判定の間隔 15 秒・閾値 10%)を
probe で回し、起きている時間を 1 tick ずつ進めて、最後に何かが起きた時刻を上限の 1 分先までずらす:

- `a_quiet_hold_lets_go_past_its_bound_until_something_happens` — 何もしない背景プロセスだけの保持が上限で
  解け、さらに 10 分経っても解けたまま、hook の書き込みと transcript の書き込みでそれぞれ保持し直す
- `a_counted_process_at_work_is_something_happening` — 孫プロセスが 1 tick の 10% を超えるプロセッサ時間を
  使った読取りでは保持する
- `a_counted_command_starting_processes_is_something_happening` — 短いプロセスを毎秒起こす待ちループの間は
  保持する
- `a_claim_changed_under_a_reading_is_something_happening` — 読取りの途中で claim が変わった読取りでは保持し、
  上限はそこから数える

それぞれの扱い(hook と transcript の書き込み・閾値・新しいプロセス・claim の変化)を外した台本では、その
テストだけが赤になる。

## holder の負荷

holder は event(claim の書き換え、デスクトップアプリのログの追記)のたびに読取りを始める。hook は 1 回の
ツール呼び出しで claim を 4 回書き、holder 自身の書き戻しも 1 回の event になるので、セッションが動いている間は
event が途切れない。保持している間の読取りは解除しかできない(保持は既に立っている)ので、event で起きる読取りを
間引く: **60 回分の猶予を使い切ると 5 秒に 1 回**で、猶予は 5 秒に 1 回分ずつ戻る(`holder::BURST` /
`holder::PACE`。数えるのは進むだけの時計)。保持していない間の読取りは待たせない。15 秒周期の読取り
(プロセスの開始・終了、transcript の伸び)は別枠で、心拍の間隔は最長でも 20 秒強。

本番の `.awake`(claim 8 件、うち作業中 3 セッション)で、猶予を使い切った後の 187 秒(revision 5。
revision 6 との差はログ補助の許可画面の扱い —— 結び付ける呼び出しの範囲、claim を確かめられなかった読取りの
結び付けの決め直し、中断の行 —— だけで、読取りの回数と中身は同じ):

| | 値 |
| --- | ---: |
| 読取り | 11 回/分 |
| CPU | 1,625 ms(1 コアの 0.9%、読取り 1 回 49 ms) |
| ワーキングセット | 140〜180 MB |

猶予が残っている間は event ごとに読む(起動直後の 127 秒: 23 回/分、1 コアの 3.7%)。読取り 1 回の支配項は、
作業中のセッションの transcript の末尾 256 KB の読み直し。伸びていない transcript は読み直さないので、
開いたままの idle なセッションの claim に掛かるのは、ファイルを開いて長さを見る分と owner の照会だけ。
プロセスの照会は一覧(Toolhelp)1 回で全 claim に答える(一覧と owner 11 件への問い合わせで 7.7 ms)。
一覧は 1 回の読取りで 2 回まで取る: 始めに owner 用、transcript を全部読んだ後に子プロセス用
(コマンドは結果より先に起きるので、子を読む一覧は transcript より新しくなければならない)。

間引きは `a_held_machine_s_readings_are_paced_past_a_burst` が、holder 本体を偽の時計で回して確かめる
(保持中は猶予を超えた後 5 秒に 1 回、保持していない間は待たない)。一覧の順は
`a_command_started_once_the_owners_are_listed_keeps_its_call` が、owner の一覧の直後にコマンドを起こして確かめる。

## 運用中の記録

## 判定の履歴

holder(revision 5 以降)の判定は `.awake/history` に残る。全 revision の holder が同じ 1 本へ、判定か、
保持の理由の組が変わるたびに 1 行書く。行の形(session の id は略記):

```text
1791092805997 r5 56572 holding process:8c49584e-…,turn:2390b74a-…,turn:8166f3c3-…
1791093405120 r5 56572 released -
1791093990004 r5 56572 quit -
```

左から、時刻(ミリ秒)、書いた holder の revision と pid、判定、理由。理由は整列済みのカンマ区切りで、
`turn:<session>`(応答か呼び出しが数えられている。止まったターンの Stop hook が走り終わっていない。subagent の
分も session に寄せる)、
`process:<session>`(シェル呼び出しのプロセスが走っていて、その session の `turn` が数えられていない)、
`wake:<session>`(予約した再開が先にある)。`holding -` は、読取りの途中で claim が変わったので保持を続けた、の意。
`lost thread:<16 進>,system:<16 進>,after:<16 進>`(r19〜)は、読取りが保持の消失(または立てたばかりの保持が
数えられていないこと)を見つけて立て直した行で、スレッドが求めていた値、system が数えていた値
(`SystemExecutionState`)、立て直した後に数えた値を書く。消失 1 回につき 1 行、その読取りの判定の行の後。
`released quiet:<分>m`(r25〜)は、何も起きないまま上限を過ぎて保持を解いた行。
4 MB を超えたら新しい側の半分を残す。数セッションが動く時間帯で 1 時間に 50〜90 行。
`cargo xtask awake` は、holder ごとにその holder が最後に書いた 1 行を出す。
スリープの記録(上の System ログ)との突き合わせは、この履歴で直接できる。

## 未実施・限界

- `powercfg /requests` は管理者権限が無く取得できない。`CallNtPowerInformation(SystemExecutionState)` は
  他アプリの要求も含む全体の値で、この実装の保持・解除の帰属には使わない。holder は「何も数えられていない」
  ことの確認にだけ使うので、他プロセスの要求が立っている間は自分の保持の消失を見落とし、相手が解く次の読取りで
  立て直す
- 要求が数えられなくなる仕組みは確かめていない(API からのスリープを挟んだ 1 例だけ)。強制スリープと復帰を
  制御して挟む試験は、作業中のセッションを止めるので行っていない
- 静かな保持の上限は、新しいプロセスを起こさず、プロセッサもほとんど使わずに 2 時間以上待つ背景処理
  (長いダウンロード、PowerShell の `Start-Sleep` で回る待ち)を途中で眠らせうる。プロセス木の外で進む仕事も
  見えない: `cargo xtask linux …` の中身は WSL の VM で走り、プロセッサ時間は claude.exe の子孫に載らない。
  Codex のシェル呼び出しはプロセスに結び付かないので、長い実行の間は hook だけが頼り。シェル以外の呼び出し
  (MCP・WebFetch、アプリ内 MCP の許可待ちを含む)も、何も書かないまま 2 時間を超えれば途中で解く
- 逆に、空回りしてプロセッサを使い続けるプロセスや、終わらない待ちループは働いて見えるので、上限では解けない。
  終わりの来ない呼び出しは、その後に Claude の本体が起こすプロセス(MCP サーバーの起こし直しなど)も自分の物と
  数え、それで続く
- Stop hook の記録を待つ規則は、記録の来ない Stop(API エラー、hook に止められた発話)でも 60 秒保持する。
  Stop hook が 60 秒より長く走って、その後に通知が取り出されるターンは、上限の後に解除しうる(応答から記録まで
  の最長は 199 秒)
- 書き手の無い subagent の判定は、Claude Code の置き場(`<session>/subagents/agent-<id>.jsonl` と
  `.meta.json`)に何も無いことを根拠にする。置き場が変わると、Agent ツールの subagent も最初の呼び出しで
  止まった扱いになり、背景の subagent の MCP・fetch・思考の間を保持しない。置き場の実測は、このプロジェクトの
  2026-07-24 以降の `.meta.json` 968 件: 965 件は transcript と組で、どれも transcript の最初の記録が最初の
  tool_use より 1.4 秒以上前(残り 3 件は `.meta.json` だけ = この規則には掛からない)
- Claude の実際の許可操作、アプリ独自の許可画面、実際の MCP の内部実行は再現していない。
  P3 の upstream の未達を fixture の成功で解消したとは扱わない
- 無入力タイマーの設定値(AC のスリープまでの時間)と人の入力は記録に残らない。運用中の記録の期間は
  判定の履歴も無いので、アプリの解除から眠るまでの間が無入力タイマーなのか別の保持なのかは判定できない
